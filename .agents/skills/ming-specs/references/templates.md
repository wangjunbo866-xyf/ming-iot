# Ming IoT 规格协作记录模板

这些模板是 [团队开发约定](../../../../docs/runbook/team-development.md) 的记录格式，不另行定义审批与生效规则。按任务选用所需部分；简单变更可合并为一份文档。尖括号内容由真实材料填写，未知项保留“待确认”，示例不构成事实或批准。

## 认领记录

```markdown
# <任务标识>：<模块 / 任务>

- 模块 ID 与入口：
- 类型：blueprint / feature / patch / sunset
- 完成条件：
- 需求负责人 / 模块负责人：
- 实施者 / 评审者：
- Agent 执行身份（若使用）：
- 前台：仓库、路由/页面；或不涉及的理由
- 后台：仓库、API 领域/接口、允许修改的代码路径
- 规格：基线路径、版本、条款 ID、本次修改范围
- 共享影响：数据归属、权限、Schema、事件、公共库、协同方
- 并行关系：相关在途任务、重叠范围、依赖与处理顺序
- 确认依据：确认人、来源、日期、精确范围；或待确认
- 未决事项：需要谁决定什么、只阻塞哪些动作
- 首次接入（如适用）：现状 observed 基线、源码版本、已知缺陷；任务级委托与 AI 细化分别记录
```

模块入口保存长期责任和当前版本，任务记录保存本次认领及引用的入口版本；避免同时维护两份独立的长期责任清单。

## 规格与变更

下列共同字段适用于正式规格及变更记录。Blueprint 采用本节末尾的探索格式。

```markdown
---
status: draft
revision: R1
---

# <标识>：<标题>

- 类型：feature / patch / sunset
- 模块与任务：
- 需求来源：原文或可访问来源；AI 整理部分单独标明
- 基线：规格路径、版本、稳定条款 ID；新能力说明尚无基线
- 人的责任与认领：引用本次认领记录
- 确认：人、来源、版本及范围；未取得时写待确认
- 适用代码版本：仓库及完整 SHA / 交付版本；未实现时明确
- 部署事实：环境及发布证据；未知或不涉及时如实填写

## 目标、角色与范围
<要解决的问题、使用方、包含和不包含的行为>

## 当前行为与变更后的完整行为
<按稳定条款 ID 说明正常、异常、权限与数据约束>

## 验收条件
<每条行为怎样从外部观察和验证；允许哪些失败情况>

## 技术方案与取舍
<涉及的模块、接口、数据变化、兼容、迁移、测试；必要时链接单独设计>

## 待决事项与依赖
<假设、冲突、所需确认、阻塞范围>

## 验证、评审与生效依据
<实际结果或尚未执行，不提前生成通过结论>
```

**Patch 增补：** 开头声明替代/新增/删除的具体条款及未变约束；写明依赖或替代哪个 Patch，给出主规格的反向入口。实现修正且规格无变化时，明确引用被恢复的行为及验证，不虚构被替代条款。

采用 v2 check.json 的 Patch 只在上述开头元数据维护当前 status/revision；投影不再复制两者。元数据使用不带引号的简单标量，历史决定保留在正文表格中。

**Sunset 增补：** 旧能力与替代入口、使用方、停止新接入/兼容/迁移/退出的里程碑、数据处理、回退条件及验证；区分计划日期与实际完成证据。

**Feature 增补：** 新模块的职责、接口和数据归属、与已有模块的关系；不凭源码目录自动确定业务边界。

**Blueprint 格式：** 标题、exploring/promoted/closed 状态、探索问题与边界、事实及来源、假设、候选方案、比较/试验结果、未决事项；转正式时链接真实 feature/patch 并建立回链。

## 双向指针示例

以下为示意，使用时替换成存在的路径、版本和条款：

```markdown
<!-- Patch 开头 -->
覆盖基线：<spec 路径>@<版本> 的 <条款 ID>。
变化：<旧行为> → <新行为>；未变约束：<范围>。
状态：confirmed，尚未在交付版本生效。
主规格反向入口：<实际路径与锚点>。

<!-- 主规格对应位置 / 模块入口 -->
<条款 ID> 当前按 <基线版本> 生效。
候选 <Patch 链接> 拟修改此条，状态 confirmed；当前尚未覆盖基线。
```

在同一候选内完成主规格收敛并评审，吸收后标明主规格的新版本和来源；合并、部署另记。遗留有效覆盖需标出收敛任务。链接成功不证明覆盖声明正确，仍需语义核对。

## 差异报告

```markdown
# Spec-Code 差异报告：<任务>

- 检查类型：暂存区 / 工作区 / PR或分支
- 比较对象：仓库、基线、候选完整 SHA；未提交时标明候选快照标识
- 暂存区身份：git write-tree 的 tree；工作区/未跟踪文件是否在候选外；结构报告与语义结论分别记录
- 规格输入：主规格与有效补丁的路径、条款、版本/内容指纹
- 覆盖：变更文件、模块与条款；排除项及理由
- 上下文缺口：不可访问的外部契约、配置或未确认需求
- 总体结论：声明范围内未发现差异 / 发现差异 / 信息不足

| ID | 条款与 Spec 意图 | 代码/测试依据与实际行为 | 差异及影响 | 建议 | 处理负责人 | 真实决定与来源 | 重验结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| <ID> | <路径@版本#条款> | <位置@版本及观察> | <遗漏/额外/偏离/不明确> | <修代码/提Patch/澄清> | <人> | 待决定 | 未运行 |

规格无变化的变更：<逐项说明理由与依据>。
实际检查：<命令、作用范围、退出码、结果与证据>。
未运行 / 未实现 / 未配置：<具体项及其影响>。
合并前尚需处理：<未决条款、越界、覆盖冲突、验证缺口>。
```

不要为“未发现差异”伪造占位差异行。AI 自检与独立评审分别记录。报告对应的代码或规格改变后，旧报告只保留历史适用性。

## 澄清与决定记录

在 Change 内按需使用以下两节；不要求新增 questions.md、audit.md 或第二套状态文件。

```markdown
## 来源与澄清
- 原始诉求 / 可访问来源：
- 已核实事实及代码/规格版本：
- AI 假设或候选：

| 问题 ID | 业务分歧、选项与影响 | 真实回答及来源 | 决定 ID / 未决时阻塞动作 |
| --- | --- | --- | --- |

## 决定与 revision
| 决定 ID | 决定者角色 / 实际来源 / 日期 | 选择与理由 | 覆盖条款及 revision / 排除范围 | proposed / confirmed / superseded |
| --- | --- | --- | --- | --- |

| revision | 行为变化 | 继承的决定 | 新决定或待确认项 | 验收变化 |
| --- | --- | --- | --- | --- |
```

仅填写实际发生的回答和决定；无关键分歧时写沿用哪项确认，不制造问答数量。业务确认、实施授权、接收回执、验收结论分开引用。

## 交接记录

```markdown
- 模块 README / 当前 spec、任务或 PR 的决定与验证入口：
- 实际代码版本、当前待办、允许修改范围：
- 接收人（如有）、下一步与关键验证命令：
- 可选：离线/跨权限/特定外部交付使用的原始快照地址及摘要：
- 未决事项、阻塞动作：引用 Change 中对应条款；没有则写无
- 交接性质：实际成员交接 / 独立 AI 会话演练；实际 Agent 身份与人的责任角色分别记录
```

本模板可放入原任务或 PR，不要求另建文件或机器快照。仅在确需冻结输入的例外交付场景使用 v2 快照；已选择快照时接收者核对原附件，不能重新生成替代。旧手写包保留为历史。

## 接收回执

```markdown
- 接收身份、角色与时间：
- 交接对象、实际代码 commit、规格 revision / 内容指纹：
- 本次变化的复述：
- 未变约束与写范围：
- 有效决定、待决事项、旧确认是否覆盖当前 revision：
- 实际复跑命令、结果与证据：
- 结论：received / accepted / returned；只表明本次交接状态
- 退回项、恢复条件、下一步与责任人：
- 成本：查找与复验耗时、补问次数；未测量项写 unknown
```

# Ming IoT 规格维护

版本：0.10.0-draft。组织 AI 的操作；业务正文归模块规格，协作规则归团队约定，确定性检查归工具。本 Skill 不执行业务审批，也不自动安装 Hook 或启用合并门禁。

## 先定位，再选择操作

先从用户指定工作树的 AGENTS.md 和[通用接入](../../../docs/runbook/cross-agent-development.md)判断任务方式。普通任务在原任务/Issue/PR 留证，不要求 LoopX；已明确纳管任务读其专用约定并满足准入。宿主未发现 Skill 时可直接读取本文件，按相对路径进入引用；本说明不要求安装全局 Skill。

读取[团队开发约定](../../../docs/runbook/team-development.md)、[业务地图](../../../docs/specs/README.md)，再进入相关模块 README 和当前 spec。仅按需追溯历史 Patch；不要让接手者拼接历史才能知道当前行为。核对任务已采用的入口，未获授权时不切换规格权威。

| 请求 | 读取约定 | 结果 |
| --- | --- | --- |
| 业务域 / Feature / 服务划分、目录归属或新能力命名 | [划分标准](../../../docs/runbook/team-development.md#domain-feature-service)，然后读业务地图、当前规则及实际实现 | 按持续职责判断域与完整能力，再分别记录 Feature ID、服务映射及当前状态，最后判断本次变更；纯术语问题不创建变更 |
| 收到一句话目标，尚缺细节 | [受理到交付操作页](../../../docs/runbook/requirement-to-delivery.md) | 保留原话、定位模块及当前事实，落盘已确认边界与待决事项；回报文件位置和可继续的部分 |
| 认领或准备工作 | 模块认领 | 在现有任务中明确边界、责任、并行冲突及确认来源 |
| 澄清或接受新决定 | 需求澄清与决策留存 | 区分事实、假设、人的决定及适用 revision |
| 使用可选分析 Skill，或接收其分析结果 | [可选分析接入与写回](../../../docs/runbook/team-development.md#optional-analysis-skills) | 将所选方法接入当前模块；已有决定继续适用，新发现写回同一 Change |
| 新增、调整、退出或探索 | 先读术语约定，再读四种变更类型；按风险选择记录深度 | 先确定域与 Feature，再选择本次 feature/patch/sunset/blueprint 及必要记录 |
| 小修改：错字、修复、重构、补说明或局部规则调整 | [小修改处理步骤](../../../docs/runbook/team-development.md#small-changes) | 先判断规则是否变化，再检查影响；按表选择文件、确认点和验证，复用原任务记录 |

| 收敛与交付 | patch：双向指针与并行收敛；交付与交接 | 候选内完整主规格、吸收关系、实际版本及证据 |
| 新成员或新会话接手 | 交付与交接 | 从仓库入口恢复规则并复验，疑问回到正文 |

仅在需要记录格式时读取[模板](references/templates.md)对应部分。一次只读检查不自动升级为实施、远端写入或发布。

## 执行

1. **定位与认领。** 按[划分标准](../../../docs/runbook/team-development.md#domain-feature-service)先识别域与完整 Feature，再分别记录实现/服务映射及本次变更；以职责、可观察结果和验收说明粒度依据。读取当前条款、在途变更、相关实现与测试；检查 API、数据/权限、共享契约和已有认领。区分人的长期负责人、任务级委托及 Agent 身份。已有确认覆盖本次范围就继续；只对改变业务承诺、验收或写范围的分歧请求决定。没有规格的既有能力按约定建立 observed 基线，不把补建目录当新增能力，也不把代码现状当批准。
2. **分类与澄清。** 小修改先执行约定的四步：找到适用条款并判断规则是否变化，检查影响，选择最小记录，核对完成条件。无条款或有歧义时先调查/澄清，不借用无关条款声明规则不变。复用原 Issue/PR/Change 保存来源、旧/新行为、不变项、验收与实际决定。原始需求只追加或引用；业务含义变化更新 revision，标明继承或替代的决定。实现细节在授权内自行选择，待决行为保持候选。
3. **同步候选。** 只修改实际受影响的实现、测试与文档。规则不变的修复引用现行条款和回归，不为通过检查机械修改主规格或建立 Patch；规则变化在同一候选收敛主规格，Patch 指向基线条款，主规格或模块入口反向指向 Patch。获准从跨域 Patch 提取独立正文时，在域/Feature 入口建立唯一当前规格，原 Patch 保留来源、决定与依赖回链，并同步导航、索引及有界检查；文档登记与产品差异映射分开说明。发生偏差时先判断实现错误、需求歧义或合理调整，不能因代码已写完就改写确认的意图。缺陷结论回到唯一规格和对应回归，避免新建平行规则。
4. **检查差异。** 固定实际 base/head 或 staged tree，解释每个变更路径的规则归属或规格无变化理由。检查测试期望来自已确认规则；兼容用例使用旧版本实际可产生的输入。结构检查与 AI 语义检查分别留证；未知、未运行、未验证的真实依赖不记 PASS。
5. **收敛。** 合并前在同一候选内写出完整当前规则，与实现一起评审；吸收的 Patch 标 absorbed，保留基线、决定、出处和吸收位置。当前入口不要求叠加所有历史补丁。分别记录候选、合并、部署和验证事实；报告入库时由外部回执绑定最终 Head，避免自引用。

## 接入可选分析方法

仅在用户选择某种方法、任务存在真实歧义，或需要接收分析结果时，读取上述接入约定。成员可选择 `grill-with-docs` 等方法；本 Skill 不把它们自动设为依赖或默认调用。

1. 固定模块、输入 revision、已有决定、问题范围和唯一写回位置。读取所选 Skill 的实际入口与必要依赖；显式调用设置仍有效，不可用时如实记录并按团队约定继续已授权分析。
2. 先核对事实，再用反例检查目标。将“源码可查”“范围内技术选择”“需负责人决定”分开；分轮询问有前置依据的业务分歧，保留已确认决定。成员建议不是批准，AI 不能充当业务负责人。
3. 依接入约定把术语、选项、真实回答、未决项及验收影响写回原 Change；将外部 Skill 默认输出映射到现有正文。本轮限定同一 Patch 时，保持这个边界；事实修正与目标方案分开，保留 observed/draft 身份。
4. 以实际文件差异和语义复核检查：确认来源是否真实、未决项是否只阻塞相关步骤、导航与 revision 是否一致、是否产生重复正文。记录本轮结果和维护成本；待回答时明确“分析进行中”，不代答或启动依赖决定的实现。

## 检查真实 PR 与本地提交

PR 使用 [完整差异检查](references/pr-check.md)：先读取 `tooling/specs-map.json`，按实际所有路径汇总模块，生成 PR 说明中的一个 `ming-specs` JSON 块。模块映射只是导航投影，规则仍以当前主规格为准。多个模块分别声明；同一路径属于多个模块时须覆盖全部。不得为了通过检查放宽历史认领或缩小 PR 基线。

- 行为变化引用当前 v2 Patch、revision 和真实决定，在同一 PR 收敛主规格。
- 规则不变的小修复引用当前版本、条款、路径与理由，不强建 Patch 目录。`no_behavior_change` 指约定行为未变，允许修正错误实现；影响较大的修复仍需对应验证。
- 文档、团队工具、历史材料分开说明；归档移动用 from/to 核对字节和模式。未登记的产品代码必须显式列出归属缺口和依据，继续接受语义评审。

从仓库根检查明确的目标分支 tip 和不可变 Head：

```bash
python3 tooling/specs_pr.py --base <目标分支commit> --head <候选commit> --declaration <本地JSON路径>
```

工具自行计算唯一 merge-base；不要用前一次提交冒充完整 PR 基线。GitHub 工作流从事件读取 base/head 和 PR 正文，要求检出真实 head。只读候选 Git 对象，未提交修改另报。声明和映射本身也需评审；结果始终是 `STRUCTURE_OK_REVIEW_REQUIRED`，不证明真实授权、语义或服务端必需检查已启用。

单个 Patch 的暂存区提前反馈仍用原入口：

```bash
python3 .agents/skills/ming-specs/scripts/preflight.py \
  --change <仓库相对check.json> --base <实际基线commit> --staged
```

该入口是单 Patch 范围检查；多模块 PR 用完整差异入口，不能把整个 PR 塞进一个历史 Patch。详细反例与例外快照见[试跑回归说明](references/pilot-regressions.md)。历史零差异结构检查不能证明当前 PR 范围；新仓使用新证据，旧仓 SHA 与历史回执原样保留。S2 工作流已随 PR #5 合并并有[托管检查记录](../../../docs/changelog/2026-10-16-specs-merged-next-plan.md)；本轮新增流程仍是本地候选。远程必需检查与新候选 CI 需分别核验。

## 日常接手与例外交付

默认提供模块入口、明确候选版本、当前待办和关键验证方法，结果留在原任务/PR/CI。接手者找到当前条款、复述变化与不变项、核对范围及来源、复跑相关检查；发现理解缺口优先修复入口、主规格或验证说明。独立 AI 演练明确实际身份，不代写人的批准。

仅在离线、跨权限或特定外部交付需要冻结输入时，按约定使用固定快照。收到快照时校验原附件与指定候选，不能重新生成来消除失配；absorbed 历史 Patch 不重新生成实施交接包。普通接手无需专门交接包或重复问答。

完成时核对：域与 Feature 的职责和验收是否完整，服务映射是否独立描述，是否分清本次变更、文档登记、产品映射及运行状态；提取正文后原来源和跨域依赖是否仍可追溯。提供实际文件、版本、验证与独立评审结果，以及仍未解决的事项。草拟可以以 draft 完成；只读检查可以以发现差异或证据不足完成，不伪造批准或 PASS。

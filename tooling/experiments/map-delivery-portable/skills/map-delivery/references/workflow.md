# 交付工作流

用于创建、实施、验证或继续一个 Change。先读取当前模块入口及其权威规格，再选择与当前工作对应的步骤；不要求重新执行已经有可靠结果的步骤。

## 1. 定位能力与本次范围

沿地图入口找到模块，读取现行规格、候选 Change 和相关共享契约。检查其他未结束变更是否覆盖同一要求锚点，或修改本次依赖的接口。锚点不重叠也可能影响同一跨模块行为，应明确兼容性与集成验证需求。

每次 Change 选一个稳定 ID；已有项目编号时复用。记录目标、边界、受影响模块与要求、依赖和当前进展。跨模块交付选择一个主 Change，其他模块入口引用它；项目已有拆分规则时按规则拆分并关联依赖。

完成条件：本次范围与排除范围明确；活动变更的重叠点、共享依赖及尚缺需求可见。缺失批准范围的内容保持候选状态，继续执行已明确且已获授权的部分。

## 2. 写要求和场景

每项要求表达一个完整、可观察的行为，并具有稳定锚点。优先沿用现有锚点格式；新地图可采用显式 ID，标题重命名时保留 ID。场景 ID 在模块内唯一，删除场景时在 Change 中说明退役及替代关系。

```markdown
<a id="req-access"></a>
### REQ-ACCESS：访问受限资源

系统只向获授权的成员返回受限资源。

#### SC-ACCESS-01：获授权的成员读取资源
- 前提：成员拥有目标资源的读取权限，资源存在。
- 当：成员请求该资源。
- 则：返回资源内容。

#### SC-ACCESS-02：权限不足
- 前提：成员没有目标资源的读取权限。
- 当：成员请求该资源。
- 则：拒绝读取，响应不包含资源内容。
```

这是写法示例，不是产品默认权限规则。实际场景写出项目约定的响应、状态或错误；只有需要区分失败原因时才加入相应细节。

场景覆盖本次行为与真实风险：正常路径、失败、权限、边界或重复执行按需选择。小修复可以复用已有场景；只有行为发生变化或覆盖不足时才新增。实现细节放在计划中。

现行 `spec.md` 保持完整模块行为。既有模块的候选 `change.md` 标明新增、修改、删除的要求；修改项包含变更后的完整要求及场景，说明当前行为与变化原因。首次实施的 Change 引用已起草的完整初版规格和真实锚点。

完成条件：每个受影响要求有可观察的预期结果；实施者无需猜测关键行为。尚需产品决定的取舍明确标为待确认，不编写成已批准事实。

## 3. 计划与实施

将工作拆为可交接的任务，关联要求或场景、涉及仓库、依赖和验证方式。规模较小时直接写在 Change；并行、多仓或依赖复杂时使用独立 Plan。计划中的验证是待执行工作，不是证据。

对每个正在实施的仓库记录项目原生的精确修订标识；Git 使用可解析的完整提交标识，不限定字符长度。未提交改动另记工作区状态或可复现补丁，不能把基线提交声称为全部候选。需求、实现或依赖变化时，更新受影响范围与计划。

完成条件：实际实现覆盖授权范围，未完成任务和实现偏差有据可查；声称完成的任务具有符合项目要求的验证结果。

## 4. 验证与审查

执行与受影响场景对应的测试、构建或人工验证，记录执行时间、候选修订、所依据的规格版本、方法、实际结果及可访问证据。失败、未运行和部分覆盖分别说明。规格版本可以是文档提交或可复现的内容快照；仅场景 ID 相同不能证明要求未变化。

Evidence 在真实执行后编写。重复结果引用已有记录，避免复制同一事实。独立 Review 在实际独立审查后编写，记录审查者或执行主体、范围、候选版本、发现及结论；作者自检标记为自检，不能替代项目要求的独立评审。

候选修订或要求内容变化后，比较变化与已验证范围：保留历史结果，标明仍有效的依据、需要重跑的验证和需要重审的范围。无法证明旧结果覆盖新候选时，将对应结论列为待重新验证。

完成条件：结论与实际场景、规格版本和候选内容匹配；接手者能复现验证，知道哪些结果尚未获得。

## 5. 核查与下一步

先使用项目已经规定的校验命令。失败时区分本次内容、既有数据或执行环境问题，保留真实失败信息；不要改写为“通过”。没有校验器时执行以下人工检查并标注检查方式：

- **导航**：地图、模块、Change 及实际产物可达，没有指向不存在文件的链接。
- **语义**：现行与候选区分清楚，受影响模块和共享契约没有遗漏已知依赖。
- **追溯**：任务和证据中的锚点、场景确实存在，结果覆盖本次要求与候选版本。
- **事实**：未运行、未评审、未核实的信息保留原状态，没有把文件存在当作通过。

这些检查不能证明业务实现正确，也不能替代项目指定的测试、审批或远端状态核实。`context.py` 仅定位，不提供检查结论。

按缺口给出下一步，无需维护另一份重复的状态数据库：

| 已知情况 | 下一步与完成条件 |
| --- | --- |
| 关键行为或批准范围缺失 | 补充具体需求；只对已明确且已获授权的范围继续实施 |
| 要求已明确，任务缺验证方式 | 关联场景与验证方法，使实施者知道如何判定完成 |
| 实施条件满足，任务未完成 | 执行依赖已满足的任务并记录实际结果 |
| 实现完成，场景尚未验证 | 运行相应验证，保留成功或失败证据 |
| 规格或候选变化 | 重新判断影响，更新需补验或复审的范围 |
| 项目要求独立审查，尚无真实结论 | 取得对应候选的独立审查 |
| 本地材料齐全，远端状态未知 | 按项目要求核实真实 PR/MR、CI、合入或部署状态 |

## 6. 生效与交接

更新现行规格的条件由项目定义；它可能要求规格确认、代码合入或其他条件。保持候选内容与目标分支上仍生效的规格可区分，满足条件后把完整变更内容并入现行规格，并保留历史 Change 与来源链接。

分别记录规格确认、实施、合入、部署的实际情况。只完成其中一项时不推断其他项。跨仓交付逐仓说明候选与落地版本，核实依赖满足情况。生效或发布需要权限时，先完成已授权的准备与验证，再按项目规则处理尚缺的批准。

完成条件：接手者能找到当前权威内容、已完成范围、真实验证、未满足条件，以及继续工作的下一步；交付完成的声明符合项目自己的完成条件。

## 模板选择

仅为本次需要的产物采用模板，并按项目语言和既有格式裁剪。方括号占位内容需要替换；没有发生的事实写明状态，不填写想象中的结果。

| 模板 | 使用时机 |
| --- | --- |
| [模块入口](../assets/templates/module-readme.md) | 新模块需要导航或现有入口缺少必要关系 |
| [完整规格](../assets/templates/spec.md) | 起草完整模块规格或补充行为结构 |
| [候选变更](../assets/templates/change.md) | 新建一次 Change，包含小型计划与导航 |
| [实施计划](../assets/templates/plan.md) | 任务、依赖或多仓协作超出 Change 中的小型计划 |
| [验证证据](../assets/templates/evidence.md) | 已实际运行验证，需要记录可复现结果 |
| [独立审查](../assets/templates/review.md) | 已实际完成独立审查，需要记录真实结论 |

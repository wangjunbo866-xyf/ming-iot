# Ming IoT 团队开发约定（草案）

本稿以《天猫 AI 项目研发协同实践》的“超级研发小分队”阶段为参考，组织多人、多个 AI 会话共同维护代码与规格。目标是让每项工作有边界，让并行变更可协调，让代码偏离需求成为显式决策。

## 适用范围与采纳状态

- 本稿尚未成为团队现行制度。2026-10-13 用户已授权选一个真实小改动试跑，具体范围见 [试跑记录](../changelog/2026-10-13-ming-specs-pilot.md)。文中的“必须”描述采纳后的要求；局部试跑不等于全团队采纳或门禁启用。
- 2026-10-14 用户授权补充需求澄清、决策留存、分角色交接，并选择真实业务规则试跑需求调整；见 [第二次试跑](../changelog/2026-10-14-ming-specs-handoff-pilot.md)。沿用现有文档与 LoopX，不引入完整 AIDLC。
- 按 2026-10-15 用户决定，将工作区全部项目迁入 GitHub ming-iot 并收敛为一个 monorepo，Insight 在仓内统一维护。巡检先作为同仓独立业务模块；MQTT 网关保留可复用组件边界，代码与基本契约同仓。当前迁移依据见[单仓迁移方案](../architecture/monorepo-migration.md)，不以 r-doc 正式采用为前提。
- ming-iot-rd-docs、iot-doc、ai-native 是迁移来源资料。旧文件中的规则、状态及代理指令不会因复制或引用而自动生效。OpenSpec 仍是候选，不是本约定的依赖。
- 本稿的试跑范围由实际任务明确；现有任务沿用其已确认的规格和交付入口。切换时按模块登记新入口与旧入口的替代关系，避免双重权威。
- 项目事实、业务规则和人的决定保存在项目文档或明确引用的任务记录中；Skill 负责操作步骤，LoopX 如被采用只管理任务调度及执行状态。

## 人、AI、Skill 与工具的责任

| 责任方 | 负责的结果 | 完成依据 |
| --- | --- | --- |
| 需求负责人 | 业务目标、范围、验收条件，以及对行为变化的取舍 | 可追溯的明确确认，标明确认范围与版本 |
| 模块负责人 | 认领边界、接口与数据归属、跨模块协同、主规格收敛 | 模块认领记录、相关负责人的处理结论 |
| 实施者（人使用 AI） | 在授权范围内形成代码、文档和验证结果 | 可复现的候选版本、验证命令及结果 |
| 评审者 | 独立检查需求、实现、验证与交付条件 | 针对实际候选版本的评审；AI 可辅助，实施者自述不替代评审 |
| AI | 查找上下文、起草、实现、验证、提出差异和修改建议 | 可检查的产物、来源、命令结果与未解决项 |
| Skill | 规定何时读取哪些材料、怎样处理变更、交付什么 | 执行记录和实际产物；“已加载 Skill”不等于检查通过 |
| 工具 | 运行确定性检查、留存证据、执行配置好的合并限制 | 工具实际退出码、检查记录和服务端配置回读 |

小团队可兼任多个责任角色，但必须能识别谁确认需求、谁实施、谁验收。AI 身份不替代人的责任归属。

人的确认可来自已批准的任务、评审或当前明确指示；已有确认覆盖本次范围时继续执行，不逐文件重复请示。新增业务承诺、验收条件改变、跨认领范围修改、共享契约变化、下线与数据迁移需要相应负责人的确认。格式、导航修正及已确认范围内的实现由实施者和 AI 连续完成。

## 需求澄清与决策留存

### 澄清到可以判断行为

先查当前规格、调用方和测试，再把原始诉求整理为行为变化：谁在什么条件下做什么，成功、异常和范围外分别是什么。把已核实事实、AI 推测、候选方案和人的决定分开。现有实现只能证明现状，不能自行证明业务要求正确。

只询问会改变业务承诺、验收或认领边界的分歧；问题同时给出可检查的旧/新行为、推荐理由及影响。已确认范围内的实现选择由 AI 继续执行。纯修复可沿用现行条款，不要求每个阶段重新批准。

在同一变更的“来源与澄清”节保存原始需求或可访问来源、问题 ID、选项、真实回答及未决项。可将长篇原始材料单独链接；不要求复制完整聊天。没有回答的事项保持 pending，只阻塞依赖它的实现、确认或生效动作。

### 决定绑定具体内容

每个改变业务含义或范围的决定使用稳定 ID，记录决定者的责任角色、真实来源、选择及理由、覆盖条款和规格 revision、排除范围、日期与后继决定。AI 提议记 proposed，人的真实选择记 confirmed；任务级委托只覆盖原指令允许的范围。

规格 revision 随业务含义变化而更新。保留旧决定与当时适用版本；新版本标出继承哪些决定、哪些需重确认。修改行为、验收、共享契约或授权范围时，旧确认不自动覆盖新内容。错字和链接修复说明语义未变即可，无需重复确认。

决定发生变化后，核对当前模块导航、待交出的包及进行中报告是否仍指向旧 revision 或待决状态。历史记录保留原状态并注明历史适用范围；当前材料优先链接决定正文，只保留必要的版本绑定，减少多处手写状态。

姓名、邮箱、Git 作者和文档中的 confirmed 字样仅是记录，不能验证真实身份或批准。项目合并阶段仍检查可追溯的任务/评审来源与实际候选版本；工具检查字段和版本关系，不替人判断业务取舍。

需求负责人确认行为，实施者确认已理解并接手，评审者确认候选与要求一致，这三类回执分别记录。`approve` 表示接受记录中明确的对象与范围；`continue` 表示在已有授权内接续任务。接收材料不扩大写范围，确认需求也不代表实现完成、测试通过或允许发布。

## 模块认领

业务地图入口为 [specs 导航](../specs/README.md)。按业务能力划分认领单元，代码目录只提供实现线索，不能直接用 saas/share/things 目录名称代替完整业务边界。

每次任务开始前形成一条认领记录，最少包含：

| 字段 | 要求 |
| --- | --- |
| 任务与模块 | 任务标识、模块标识、feature/patch/sunset/blueprint 类型、完成条件 |
| 人的责任 | 需求负责人、模块负责人、实施者、评审者；尚未分配就写“未分配” |
| 前台范围 | 所属仓、页面或路由；不涉及则说明理由 |
| 后台范围 | 所属仓、API 领域或明确接口、允许修改的代码路径 |
| 规格范围 | 当前正文、版本、章节或稳定条款 ID，以及本次允许修改的范围 |
| 共享影响 | 公共库、数据归属、Schema、权限、事件或跨仓契约；列出协同方 |
| 并行关系 | 已有认领、覆盖同一条款的变更、依赖与约定的处理顺序 |
| 确认依据 | 真实确认来源与适用范围；待确认项与其阻塞的动作 |

AI 先读取模块现行规格、适用补丁及在途变更，再给出认领草案；负责人确认分工。缺少范围时可继续调查和起草，不能把空白视为无限修改权限。只暂停依赖未决事项的工作，继续范围已经清楚的部分。

独立任务使用独立分支/worktree。认领是协作责任，不是源码读取权限隔离：允许读取其他模块理解调用关系；需要写入认领范围外的内容时，先列出接口、文件和影响，再取得相应协同结论。

公共组件、数据库迁移、共享 API 和事件契约必须有明确负责人。目录分开只能减少冲突；同一共享契约的并行变更仍需协调和集成验证。

### 已有模块首次接入

没有正式 Spec 时，先为本次涉及的最小能力写可核实的现状基线：标明 `status: observed`、来源 commit、代码/测试依据、已知缺陷与未确认事项。`observed` 是资料来源状态，不是正式变更状态；不能据此声称已批准整个模块，也不能把已知缺陷变成必须维持的需求。Patch 分别引用现状和本次实际授权，只有获确认的范围进入正式维护。

用户明确委托选择并修复小问题时，AI 可细化验证条件；记录“任务级委托，AI 细化”，不要伪造逐条人工签字。长期模块负责人未分配时，记录本次范围责任和该缺口；不因长期治理未定反复请求已获授权的小修复，也不把临时委托变成长期所有权。

## 四种变更类型

| 类型 | 使用场景 | 材料归属 | 人确认的关键事项 |
| --- | --- | --- | --- |
| blueprint | 能力探索、方案比较、尚未形成正式开发承诺 | `docs/wiki/blue-print/` | 探索范围；何时正式转为 feature/patch |
| feature | 新业务能力或一个新模块的正式规格 | `docs/specs/<业务域>/<模块>/` | 模块边界、业务行为、验收和技术取舍 |
| patch | 已有模块的局部演进或对实现的修正 | 模块内 `patches/<变更ID>/` | 覆盖哪些条款；是否改变需求和共享契约 |
| sunset | 功能退出、替代、兼容期与迁移 | 模块内 `sunset/<变更ID>/` | 替代方案、迁移责任、兼容与退出条件 |

四种类型不是每个需求必须走完的四个步骤。bugfix、重构等可以作为 patch 的原因标签，不增加第五种规格类型。修复代码以符合现行规格时，保留规格正文，记录“实现修正、规格无变化”的依据与验证结果；无需制造需求变化。

### feature：原始需求、正式规格与方案

保留人工需求来源和原意；AI 整理、补充的问题、假设与人的回答应能区分。原始描述不能直接充当完整验收条件。

规格至少说明目标、角色、范围、关键流程、权限和数据约束、异常行为、可检查的验收条件及范围外事项。需要技术取舍时补充模块接口、数据变化、依赖、迁移和验证方案。小任务可同文件分节，大任务再拆文件；跨模块的架构决定链接到 architecture 中的同一份决策正文。

### patch：双向指针与并行收敛

Patch 必须写明基线规格的路径、版本和条款，完整说明变更前后行为、未变约束、验收、依赖及生效条件。它应独立可读，不能只写“同主文档”。必要的受影响背景可以复述，其他规则通过精确引用复用。

Patch 指向被覆盖的主规格条款；主规格相应位置或模块入口明确反向指向 Patch、覆盖范围与状态。主正文尚未收敛时，入口必须说明“基线 + 已生效覆盖”，避免旧正文被单独当成当前事实。

两个 Patch 覆盖同一条款时，负责人明确依赖、兼容、替代或合并关系。未解决的重叠不能同时生效，也不按时间戳或编号大小自动决定优先级。编号使用真实任务号或唯一标识，避免多人各自领取“下一个序号”。

稳定后，模块负责人安排收敛；AI 按已确认的覆盖关系更新主规格和导航，将已吸收 Patch 标记为 absorbed 并保留出处。收敛后的规格必须能表达当前完整行为。

### sunset：退出条件与历史可发现性

保留旧规格的日落声明和替代入口，记录受影响使用方、兼容期、数据处理、迁移步骤、验证、回退条件与负责人。发起下线、停止新接入、迁移完成、彻底移除是不同里程碑；有退出证据后才把旧能力标为已退出。

### blueprint：探索与正式承诺分开

明确问题、已知事实、假设、候选方案、成本和未决项。成熟后创建或关联正式 feature/patch，建立双向来源链接，将蓝图标为 promoted；放弃则标为 closed。探索材料可以支撑决策，但不会因技术方案写完而自动成为实施依据。

## 类型、状态与适用版本

正式变更采用以下状态；状态词是本草案约定，不代表已有状态机程序：

| 状态 | 含义与进入条件 |
| --- | --- |
| draft | 正在起草，假设与未决项明确，不代表需求或实施已获批 |
| confirmed | 有对应范围的真实确认，足以开展该范围工作；尚不证明实现或部署 |
| effective | 确认的行为已在指定候选/交付版本实现并完成要求的验证与评审；写明适用代码版本 |
| absorbed | 仅用于已收敛进主规格的 Patch，保留替代版本与出处 |
| withdrawn | 已取消的候选，说明原因及后继材料 |

Blueprint 使用 exploring、promoted、closed。模块入口列出当前基线、有效覆盖、尚未生效的候选与已退出版本，不混用这些状态。

需求确认、代码合并、规格对某个代码版本生效、生产部署分别记录。`effective` 不能宣称所有环境已经上线；部署事实另指向实际版本组合及环境证据。已有有效规格后续被替代时保留历史适用范围，而非把它改成“从未生效”的 withdrawn。

## 提交时的 Spec-Code 差异提醒

触发点是准备提交变更。由 Agent 提交流程或实际配置的 Hook 调用检查；Skill 文件本身不是 Git 回调。每个提交做本次范围检查，PR 阶段再检查完整候选差异，避免多个提交叠加后遗漏问题。

1. **明确比较对象。** 本地提交检查记录暂存区候选与基线；PR 检查记录基线和候选完整 commit SHA。工作区未暂存内容单独标明，不能拿它替代待提交内容。报告标明规格/有效补丁的版本以及检查覆盖范围。
2. **定位所有变更的语义归属。** 从实际代码差异映射到模块和条款；格式、构建或实现修正可声明规格无变化，但必须给出理由。不能仅凭改了某个目录或没有找到 Spec 就判定无需检查。
3. **比较意图与实现。** 检查遗漏、额外行为、相反行为、接口/权限/数据变化、测试覆盖与不确定处。每项结论附条款和代码/测试依据。动态配置或外部契约不可读时标记覆盖缺口。声称兼容旧格式时，用上一版本实际可生成的输出构造输入，再验证新实现；只用新格式模拟“旧数据”不能证明兼容。
4. **形成差异清单。** 使用 [差异报告模板](../../.agents/skills/ming-specs/references/templates.md#差异报告)。每项有事实、影响、建议、处理负责人、实际决定和验证结果；未确认的决定保持待决。
5. **按决定处理。** 保持原意则修代码；接受业务变化则起草/修订 Patch 并获得对应确认；需求不清则澄清。AI 可以提出规格修改草案，但不能因代码已写好就把它改成现行意图。
6. **重验并交接。** 改动影响原结论时重跑相关检查；PR 新代码不能继承旧候选的通过结论。报告作为 PR/检查附件保存时绑定被审查的 Head；若报告本身入库，仍须由外部回执标识最终提交，避免报告内自引用最终 SHA。

暂存区候选用 `git write-tree` 记录 tree，并从该 tree 读取认领、规格和 Patch；未暂存的修复不能替代暂存区中的旧版本。主语义检查针对实际候选，工作区测试若覆盖了不同内容必须重跑或明确绑定差别。新工具的退出 0 只表示其声明的确定性检查通过；结构正常且没有语义审查时仍为 `STRUCTURE_OK_REVIEW_REQUIRED`。

检查历史 commit 时，还要比较当前索引、工作区与 HEAD：工作区干净可能只是新改动已经提交，并不证明它们包含在被检查的旧候选里。工具没有回读 Hook/CI 配置时只报告未核验；项目配置状态由单独证据说明。

报告区分“在已声明范围内未发现差异”“发现差异”“上下文或验证不足”。未知、未运行和工具缺失都不能记为 PASS。发现差异本身是提醒；未经处理的需求变化、认领越界、重叠覆盖与关键验证缺失属于合并前必须解决的事项。对确认为误报的项保留理由和评审确认。

流程试跑可以带着已定位的门禁失败结束并交付结论，但候选不能因此转为 effective 或声称可合并。基线也失败时记录原始失败、独立复现及缺陷交接；本次相关测试通过不覆盖完整 Profile 的失败，不用跳过测试或改小范围掩盖它。

## 哪些依靠工具强制检查

以下是检查契约。0.3.0 的 [手动 preflight](../../.agents/skills/ming-specs/scripts/preflight.py) 检查明确指定的 Patch 和固定候选，并可核对机器生成的实施交接快照；**未配置 Hook、CI 或分支保护**。现有代码验证不能替代规格维护检查。

| 检查 | 程序可确定检查的部分 | 仍需 AI/人判断的部分 | 本稿状态 |
| --- | --- | --- | --- |
| 认领完整性 | 任务/模块、确认来源字段、候选路径在声明范围内 | 身份和授权真实性、分工合理性、并发冲突、共享影响 | LOCAL_PARTIAL：字段与范围；不验证人和排他认领 |
| 类型与状态 | Patch 的枚举与必要字段 | 类型是否合理、状态转换条件是否满足 | LOCAL_PARTIAL：仅 Patch 静态字段；完整状态机未实现 |
| 双向指针 | 明示链接、显式条款锚点、规格版本及反向链接存在 | 覆盖语义准确性、重叠 Patch 的关系 | LOCAL_PARTIAL：显式给定的一个 Patch；全库冲突检查未实现 |
| 候选与证据 | tree/commit、diff 与输入指纹、所有变更路径列表 | 语义一致性、证据充分性及实际最终版本评审 | LOCAL_PARTIAL：身份指纹；测试/Review 回执仍需独立核验 |
| 实施交接快照 | 固定 commit/tree、基线、Change revision/status、认领范围和输入指纹逐项一致；接收工作树与候选一致 | 决定是否真实、业务是否理解、包的可信来源及运行结果是否充分 | LOCAL_PARTIAL：v2 Patch；仅本地手动检查，非签名或授权验证 |
| 提交与 PR 检查 | Hook/CI 实际调用约定检查，输出明确结果 | 差异处理与需求取舍 | NOT_CONFIGURED |
| 合并限制 | 必需检查、负责人评审、实际候选更新后的再评审 | 有权限者作出接受或退回决定 | NOT_CONFIGURED |

校验程序必须能区分“字段里写了一个确认”与“从受信评审/任务来源验证到确认”。仅检查字段存在不能充当批准证明。CI 负责执行可验证条件，AI 的自然语言自评不能直接变成自动放行凭据。

本地 Hook 用于提前反馈；服务端合并规则承担团队强制要求。Git 的 pre-commit 可被跳过；GitHub 的 CODEOWNERS 也需要与负责人评审和分支保护配置配合。将来接入时验证失败确实阻止合并，不能只验证绿色路径。

手动检查用法与限制见 Skill 的 [试跑回归说明](../../.agents/skills/ming-specs/references/pilot-regressions.md)。它不会安装 Hook、不自动寻找所有 Patch，也不验证 `check.json` 是否擅自放宽范围；认领投影本身的修改仍需按真实授权评审。

## 交付与交接

每个任务交付：任务及验收条件、认领范围、变更类型与状态、代码/规格版本、已完成内容、实际验证命令与结果、Spec-Code 差异及处理结论、未完成项、接收人及下一步。

接收者应能从模块入口找到适用规格、取得候选版本并复现关键验证。只有生成了文档、加载了 Skill、完成了 Todo 或提交了代码，都不能单独宣称需求验收完成。

交接只在责任或执行上下文发生切换时建立，不把每个内部步骤拆成一份文档。小任务在同一 Change 内保存澄清、决定与验证；交接包链接这些正文，不再抄一份规格。LoopX 记录任务与等待，正文记录业务含义，二者通过任务 ID 关联。

### 最小记录与固定交接快照

普通小改动复用一份 Change 保存需求、决定、验收和验证链接；本轮试验报告用于评估方法，不作为每个日常 Patch 的必备文件。新接入或实质更新的 Patch 可使用 v2 check.json：Change 开头的 `status` 与 `revision` 为唯一当前声明，认领投影只保存任务、模块、指针、确认来源和范围。历史 v1 继续能检查结构，不自动视为具备版本校验。

在责任切换时，由工具从已提交候选生成交接 JSON，绑定基线、候选 commit/tree、Change revision/status、范围及四份实际输入的 SHA-256。交接说明只补充接收角色、下一步与验证命令；机器快照作为该次交出的不可变附件保存到接收者可访问的位置，地址和摘要写入同一任务回执。它不是新的决定正文，也不需要持续同步。

接收检查读取收到的快照并与明确指定的候选比较。缺字段、版本/指纹/范围失配或接收工作树、索引、HEAD 与候选不同，均先退回相关实施动作。交出方确认正确输入后重新交出，旧包保留历史。快照匹配只表示输入一致；`confirmed` 文字、摘要或持有同一包都不证明批准或来源真实，接收者仍须核对实际授权与业务语义。

生成快照要求 v2 Patch 和固定 commit；draft、absorbed、withdrawn 可继续结构检查，但不生成实施交接包。入库会改变 commit，因此交接 JSON 不写回它所绑定的同一提交；按任务保存附件，避免自引用。具体命令与限制见[固定版本交接](../../.agents/skills/ming-specs/references/pilot-regressions.md#固定版本交接)。

交出者使用 [交接记录](../../.agents/skills/ming-specs/references/templates.md#交接记录)，提供固定代码 commit、规格 revision/内容指纹、有效决定、未完成项、允许修改的路径和可复现命令。报告随代码入库时，最终 commit 由后续回执绑定，避免自引用。

接收者用新上下文独立完成四项核对：

1. 找到当前条款与有效 Patch，复述本次变化及至少一项未变约束。
2. 核对决定覆盖的 revision、写范围、待决项；版本过旧、原意冲突或关键来源不可读时退回依赖这些信息的动作。
3. 取得指定候选并复跑关键检查。仅完成阅读时写 received，不写 accepted；检查失败时保留失败结果。
4. 写接收回执：实际执行身份、检查的 commit/revision、复述结果、检查结果、accepted/returned 与下一步。accepted 仅表示能够接手指定工作；完整门禁失败仍阻止合并，不能被接收回执覆盖。

人未参与的交接明确记为“独立 AI 会话交接演练”，不能填写虚构同事或声称真人交接已通过。真实团队收益需要后续由实际成员验证。

每次试跑分别记录首次接入成本与后续变更成本：新增/更新文件数、需要人决定的问题数、接收者补问数、找到现行规则和复跑验证的耗时、发现的差异及返工。等待、工具准备和实际操作耗时分开；未知时间或 token 成本写 unknown。小样本证明可执行性，不能据此声称缺陷率或长期效率提升。

## 草案的试跑与采纳

先选择真实任务，分别验证新增能力、已有功能修改及一次差异处理；下线与蓝图转正式若暂无真实任务，可用清楚标注的演练检查流程，不能冒充生产验证。

正式采纳前确认模块责任人、选择试跑范围、验证跨人交接，并决定工具检查的实现顺序。优先完成结构/链接校验和 PR 证据绑定，再接提交提醒和服务端门禁。每一项按实际结果从 NOT_IMPLEMENTED/NOT_CONFIGURED 更新，不能随文档合并批量改成“已启用”。

本约定是规则正文；[ming-specs Skill](../../.agents/skills/ming-specs/SKILL.md) 是执行入口；[模板](../../.agents/skills/ming-specs/references/templates.md) 是记录格式。更改规则时更新本文件，Skill 通过引用读取，避免维护另一套规则。迁移完成后再决定旧 map-delivery 等入口的退出方式。

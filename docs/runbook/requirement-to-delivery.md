# 从一句话需求到可接手的交付

这是[团队开发约定](team-development.md)的操作页。试跑目标是让需求、决定、当前规格、代码与证据形成一条可追溯的路径，后续开发者从模块入口即可接手。收到目标但尚缺细节时读取本页；理解已有规则先进入 Feature 当前 spec。示例使用 [Eventbus 迁移](../specs/platform/eventbus/README.md)，各阶段是否完成以模块当前入口及证据为准。

## 第一次接到一句话时

人只需描述目标，不必先填写技术模板。AI 先查模块和现状，把原话保留在已有 Change 的来源节；像 Kafka 这种跨模块、需要多轮澄清的需求，可用模块内 `raw.md` 持续追加原话。复用现有 Issue/PR 时可直接引用可访问来源。原话、AI 判断和已确认决定分别标明。

先按[划分标准](team-development.md#domain-feature-service)识别业务/能力域与完整 Feature，另行记录服务映射，再判断本次变更类型。例如 Eventbus 是长期单元，NATS → Kafka 是它的 Patch；既有能力补录文档不因新建目录成为新增功能。

AI 首次回报应能回答四件事：**文档落在哪里；已确认什么；还要决定什么；接下来哪部分能直接推进。** 不把每次回答都拆成新文档，也不要求人先学会 Spec、Patch 或 consumer group 才能提出需求。

## 一条需求的推进路径

| 步骤 | 持久结果与所在位置 | 人负责什么 | AI 与工具做什么；何时可继续 |
| --- | --- | --- | --- |
| 1. 受理与认领 | 模块 README 指向当前 spec 和在途 Change；原话留在 Change / raw；认领在原任务记录 | 确定目标，补充实际责任与范围 | AI 找当前模块、在途工作、相关调用方；缺规格先写 observed。已授权的调查和环境准备可继续 |
| 2. 澄清到可验收 | 同一 Change 的来源、问题、决定表：旧/新行为、不变项、异常与验收 | 只对改变业务承诺、范围或验收的分歧作决定 | AI 用具体例子提出选项并记录真实回答。待决项只阻塞依赖它的实现，不阻塞独立工作 |
| 3. 技术方案与实施安排 | 团队知识复用当前 Spec / Change；规则不变的小修复留原任务。有协作依赖时在同一 Change 或任务补顺序；[个人 plan/task 不要求入仓](team-development.md#collaboration-records)；跨模块长期约束在 architecture 留单一正文 | 接受必要的业务取舍与风险、协调认领及共享依赖；已有授权覆盖的细节不反复确认 | 成员可自行选择 Skill 写个人计划并执行 TDD；AI 将验收例子关联条款、拟实现接口和验证层次，需共享的决定、前置条件与结果写回团队记录 |
| 4. 确定验证路径，先运行测试 | runbook 保存可复现方法；原任务留规则/用例、源代码及测试版本、环境与实际结果 | 确认业务预期与环境限制，处理影响验收的未决项 | 按 [TDD 适用范围](team-development.md#tdd-scope)选路径：实现/修复先运行失败测试，重构先建立通过的行为保护，文档等用对应检查。仅准备相关隔离依赖，不强求启动全平台 |
| 5. 实现与同步规格 | 代码、回归测试、完整候选主规格、Patch 双向指针在同一候选；[过程及最终证据](team-development.md#tdd-evidence)留原任务附件 | 对新业务分歧确认处理，已有决定继续有效 | 按行为逐项实现、测试通过、必要整理；与第 4 步循环。交付前再运行现行完整验证和必要集成测试；差异按“修实现 / 改需求 / 证据不足”处理 |
| 6. 检查与独立审计 | 原 PR/任务关联真实 base/head、声明、验证和 Review；发现及修复留原记录 | 相关责任人决定业务取舍、风险接受与交付；AI 复审标明身份 | 工具检查完整 diff、指针、版本、lint/测试；独立评审按[审计流程](team-development.md#independent-audit)核对四个方面并复验发现，缺证据退回对应事项 |
| 7. 收敛与接手 | 模块入口指向完整当前 spec、实现及验证；吸收的 Patch 保留变化原因；合并/部署分开记 | 决定业务验收与方法采用范围 | AI 更新入口与吸收关系，记录遗漏、返工和维护成本。下一位开发者无需拼全部历史或领取额外交接包 |

第 2–3 步允许往返。需求改了就更新原 Change revision 和决定适用范围，评估受影响实现与测试；不另开一个同义模块，也不让后写的代码自动变成需求。四种变更类型及状态沿用[团队约定](team-development.md#四种变更类型)。

第 4–6 步的出口分别是：选定适用路径且测试/检查结果有依据；实现符合确认规则并完成要求的验证；独立审计发现已处置、证据覆盖最终候选。不适用 TDD 与缺少原始过程证据分别记录，按团队约定处理；无需为每一步创建新文件。

## 当前 Kafka 需求如何落盘

```text
docs/specs/platform/eventbus/
├── README.md                         当前入口、责任、状态与在途变更
├── raw.md                            用户原话，只追加来源
├── spec.md                           p1-v1：本地 P1 当前规则及旧链路观察
└── patches/PATCH-20261017-kafka-migration/
    └── change.md                     当前 Patch：已确认政策、分析记录、验收候选和实施切片
```

当前规则及生效范围从 [Eventbus spec](../specs/platform/eventbus/spec.md)读取，尚未实施的迁移内容、决定与验收从模块入口进入活动 Patch；本操作页不维护第二份 revision 或决定表。可选分析方法按[接入与写回约定](team-development.md#optional-analysis-skills)嵌入第 2–3 步，已有实际试跑来源保留在原 Patch。

ProtocolApplication 的协议适配职责已建立[能力域](../specs/protocol/README.md)及[上行 Feature](../specs/protocol/uplink-normalization/README.md)。该 Feature 的需求与澄清在本地 raw，当前设计在本地 spec；Kafka Patch 保留历史来源和依赖。分别维护实现状态与部署事实，按对应变更在候选内收敛主规格。

## harness 由什么组成

这里的 harness 是让上述流程可重复执行、偏差可发现、结果可追溯的工具与执行约束。它组合仓库现有入口，具体规则只在上述正文维护。

| 层 | 当前可用入口 / 能证明什么 | 责任与限制 |
| --- | --- | --- |
| 找到上下文 | AGENTS → [知识导航](../README.md) → 模块 README / spec / Change | ming-specs 按场景读取；导航不复制业务规则，历史资料不自动生效 |
| 协作记录 | 原任务/Issue/PR | 保存认领、范围、决定和证据位置，复用现有记录；个人执行工具自行选择 |
| 测试驱动 | 成员自选方法执行 [TDD 约定](team-development.md#tdd-scope)，测试代码与[过程证据](team-development.md#tdd-evidence)关联规则 | 先红再绿适用于相应实现任务；真实小修复及原始过程见[通知试跑](../changelog/2026-10-18-notification-tdd-pilot.md)，工具没有自动认证真实开发顺序的能力 |
| 文档检查 | `make knowledge-check`：当前选定正文的链接、可达性、索引/替代关系及检查器回归 | 范围由 tooling/knowledge.json 明确；不自动去重、归档或覆盖全库 |
| 差异检查 | `tooling/specs_pr.py`：真实 base/head、所有变化路径、登记模块条款/声明与 Patch 投影 | 每次读取候选的[实际模块映射](../../tooling/specs-map.json)并检查；本地 P1 已加入 Eventbus。路径覆盖不能证明全部业务规则已收敛或通过验收 |
| 运行验证 | `make verify-pr` 加任务所需的显式 integration suite；[部署入口](../../deploy/README.md) | verify-pr 不启动真实依赖；新增通知基线的真实运行结果单列，不能推导 Kafka 故障或全平台验收 |
| 审计与交付 | 自检后按[独立审计](team-development.md#independent-audit)核对需求、测试、实现/集成与知识；人的业务取舍另有依据 | 证据绑定最终候选及必要组合版本，发现需闭环；确定性检查不认证业务批准或过程真实性，远程必需检查需另查配置 |

Skill 负责组织 AI 执行这些步骤，本身不是 Hook；只有实际被调用的检查才有阻止错误继续的作用。先复用现有检查，发现真实遗漏后增加最小检查及一个能失败的反例。跨工具使用者可以不用同一 Skill，但交付相同的规则、实现与证据。

## 何时算这套流程试跑有效

在同一真实任务记录中核对：一句话能追到明确决定；决定能追到验收例子；例子能追到有效测试、适用的开发过程及最终实现；独立审计能发现并闭环偏差；接手者只凭当前入口能复述规则并复跑验证。过程证据、测试有效性、集成结果和人的接受分别判断；未实现、未确认、未运行分别保留。[通知小修复](../changelog/2026-10-18-notification-tdd-pilot.md)提供本例的真实 TDD 过程、审计及成本记录；不据单例推断团队长期采用。

记录新增/修改文件数、人工决策次数、重复填写、补问、文档维护与验证耗时、遗漏、误报和返工；首次环境/工具建设与日常需求成本分开，未测量写 unknown。先完成这次真实需求，再决定哪些步骤保留、简化或自动化，不预设效率提升。

小修改继续使用[轻量路径](team-development.md#small-changes)：原任务的范围、规则依据、变化与验证四行通常足够。只有实际复杂度需要才展开为本例的多文件结构。

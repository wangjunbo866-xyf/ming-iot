# 从一句话需求到可接手的交付

这是[团队开发约定](team-development.md)的操作页。试跑目标是让需求、决定、当前规格、代码与证据形成一条可追溯的路径，后续开发者从模块入口即可接手。当前用 [Eventbus 迁移](../specs/platform/eventbus/README.md)试跑；尚未完成这项需求的开发与团队采用验证。

## 第一次接到一句话时

人只需描述目标，不必先填写技术模板。AI 先查模块和现状，把原话保留在已有 Change 的来源节；像 Kafka 这种跨模块、需要多轮澄清的需求，可用模块内 `raw.md` 持续追加原话。复用现有 Issue/PR 时可直接引用可访问来源。原话、AI 判断和已确认决定分别标明。

AI 首次回报应能回答四件事：**文档落在哪里；已确认什么；还要决定什么；接下来哪部分能直接推进。** 不把每次回答都拆成新文档，也不要求人先学会 Spec、Patch 或 consumer group 才能提出需求。

## 一条需求的推进路径

| 步骤 | 持久结果与所在位置 | 人负责什么 | AI 与工具做什么；何时可继续 |
| --- | --- | --- | --- |
| 1. 受理与认领 | 模块 README 指向当前 spec 和在途 Change；原话留在 Change / raw；认领在原任务记录 | 确定目标，补充实际责任与范围 | AI 找当前模块、在途工作、相关调用方；缺规格先写 observed。已授权的调查和环境准备可继续 |
| 2. 澄清到可验收 | 同一 Change 的来源、问题、决定表：旧/新行为、不变项、异常与验收 | 只对改变业务承诺、范围或验收的分歧作决定 | AI 用具体例子提出选项并记录真实回答。待决项只阻塞依赖它的实现，不阻塞独立工作 |
| 3. 设计与计划 | 小任务在 Change 分节；必要时拆 design；跨模块共同约束在 architecture 留单一正文 | 接受必要的业务取舍与风险；已有授权覆盖的细节不反复确认 | AI 给接口、数据、事件、失败处理、测试与切片方案；将每个验收点连接到拟实现路径和验证方法 |
| 4. 先有对照，再改实现 | runbook 保存可复现启动/测试方法；原任务留输入、预期、实际和环境身份 | 提供只有人能决定的真实业务预期与环境限制 | 工具启动本任务隔离环境；AI 复现现状。相关运行基线成立后实施；单测型任务不强求启动全平台 |
| 5. 实现与同步规格 | 代码、回归测试、完整候选主规格、Patch 双向指针在同一候选中 | 对出现的新业务分歧确认处理，已有决定继续有效 | AI 依确认的验收实现并运行验证；差异按“修实现 / 改需求 / 证据不足”处理。规则不变的小修走轻量路径 |
| 6. 检查与独立复审 | 原 PR/任务关联真实 base/head、声明、验证和 Review；changelog 只留必要阶段记录 | 评审业务正确性及未覆盖风险；合并按当前仓库约定 | 工具检查真实完整 diff、指针、版本、lint/测试；独立评审核对语义和证据。结论只覆盖被检查候选 |
| 7. 收敛与接手 | 模块入口指向完整当前 spec、实现及验证；吸收的 Patch 保留变化原因；合并/部署分开记 | 决定业务验收与方法采用范围 | AI 更新入口与吸收关系，记录遗漏、返工和维护成本。下一位开发者无需拼全部历史或领取额外交接包 |

第 2–3 步允许往返。需求改了就更新原 Change revision 和决定适用范围，评估受影响实现与测试；不另开一个同义模块，也不让后写的代码自动变成需求。四种变更类型及状态沿用[团队约定](team-development.md#四种变更类型)。

## 当前 Kafka 需求如何落盘

```text
docs/specs/platform/eventbus/
├── README.md                         当前入口、责任、状态与在途变更
├── raw.md                            用户原话，只追加来源
├── spec.md                           observed-v0：当前已核实行为与缺口
└── patches/PATCH-20261017-kafka-migration/
    └── change.md                     R2：调用范围、决定、业务选项、验收候选和步骤
```

当前只有迁移目标、开发测试一次切换及环境保留边界被确认。可靠性、旧消息处理和具体事件验收链已在 R2 中给出具体推荐与替代选项，人的决定仍待记录；spec 仍描述当前源码，不提前写成“Kafka 已生效”。技术方案、实施映射和机器检查投影等到所需内容确定后补齐，不创建空文件占位。

后续开发仍回到这个模块：确认目标语义后实施，在同一候选形成完整新主规格，再把本次 Patch 标为 absorbed 并注明吸收版本。架构图、启动说明和回执各司其职，引用这份规格中的业务规则。

## harness 由什么组成

这里的 harness 是让上述流程可重复执行、偏差可发现、结果可追溯的工具与执行约束。它组合仓库现有入口，具体规则只在上述正文维护。

| 层 | 当前可用入口 / 能证明什么 | 责任与限制 |
| --- | --- | --- |
| 找到上下文 | AGENTS → [知识导航](../README.md) → 模块 README / spec / Change | ming-specs 按场景读取；导航不复制业务规则，历史资料不自动生效 |
| 连续执行 | 原任务/PR；本次长程工作使用同一 LoopX Goal | 保存认领、范围、待办与证据位置。普通小修改不新建 Goal；调度成功不代表产品通过 |
| 文档检查 | `make knowledge-check`：当前选定正文的链接、可达性、索引/替代关系及检查器回归 | 范围由 tooling/knowledge.json 明确；不自动去重、归档或覆盖全库 |
| 差异检查 | `tooling/specs_pr.py`：真实 base/head、所有变化路径、登记模块条款/声明与 Patch 投影 | 每次候选变更后重新检查。现有登记仅通知与 API 校验；Eventbus 在正式实施前补映射，当前受理不冒充已覆盖 |
| 运行验证 | `make verify-pr` 加任务所需的显式 integration suite；[部署入口](../../deploy/README.md) | verify-pr 不启动真实依赖；新增通知基线的真实运行结果单列，不能推导 Kafka 故障或全平台验收 |
| 语义与交付 | AI 自检、独立 Review、人的业务取舍；证据绑定同一候选 | 程序可拒绝结构错误和测试失败，不能认证“confirmed”字段的真实性或决定业务是否正确；远程必需检查需另查配置 |

Skill 负责组织 AI 执行这些步骤，本身不是 Hook；只有实际被调用的检查才有阻止错误继续的作用。先复用现有检查，发现真实遗漏后增加最小检查及一个能失败的反例。跨工具使用者可以不用同一 Skill，但交付相同的规则、实现与证据。

## 何时算这套流程试跑有效

在同一任务记录中核对：一句话能追到明确决定；决定能追到验收；验收能追到实际代码/测试及结果；接手者只凭当前入口能复述规则并复跑验证。未实现、未确认、未运行分别保留，不以文档齐全替代通过。

记录新增/修改文件数、人工决策次数、重复填写、补问、文档维护与验证耗时、遗漏、误报和返工；首次环境/工具建设与日常需求成本分开，未测量写 unknown。先完成这次真实需求，再决定哪些步骤保留、简化或自动化，不预设效率提升。

小修改继续使用[轻量路径](team-development.md#small-changes)：原任务的范围、规则依据、变化与验证四行通常足够。只有实际复杂度需要才展开为本例的多文件结构。

# 跨 Agent 接入与全新 clone 小修改试跑

用户授权补齐通用入口、区分普通开发和 LoopX，再用另一 coding agent 试跑小修改并独立复审；不推送、不启用新强制门禁。现有 Goal、协议契约待办、旧仓、私有备份和历史均保留。

## 交付设计

根 AGENTS 保留共同规则，LoopX 控制面要求移入[条件入口](../runbook/loopx-development.md)；新成员从[通用接入](../runbook/cross-agent-development.md)开始。ming-specs 继续指向同一团队约定和模块主规格，不要求每位成员安装同一宿主或私有调度环境。已纳管任务保留原准入约束。

## 独立试跑任务

在从完整本地候选创建、没有原项目私有状态的全新 clone 中，委托 ZCode 补充通知模块 SCENE-BUTTON 的字符数和同长首项回归，并完善现有规格的验证说明。只允许改原测试文件及当前 spec；不修改生产代码、行为、映射或已吸收 Patch。按 current-v1 的既有规则采用 no_behavior_change，不新建需求 Patch。

试跑实际目标 `pilot-base` 固定为 `27d3ef51ffa88160f7d9c11d0ecd021d814ab022`，候选为 `deb331014206efc1271e707ce586f400e518c8c3`；工具计算的 merge-base 与目标一致。克隆使用完整 Git 对象而非共享 alternates，没有原项目的 LoopX 状态、私有配置或聊天历史。协调者通过本地 cherry-pick 保留该改动，不推送。

## 结果与限制

实际执行者为 ZCode CLI，安装包版本 3.15.3-35、运行时 0.16.9，实际模型 GLM-5.3，build 模式。原始任务要求先读仓库入口；运行记录确认其调用了仓内 ming-specs，并读取团队约定、模块当前规格、代码和差异检查说明。结论是 `current-v1#scene-button` 的既有规则不变，采用 `no_behavior_change`，没有新建 Patch 或修改规格语义版本。

首次无界面运行遇到缺少权限确认客户端，保留失败后转入正常交互客户端，逐项确认允许的操作，没有改用全量放行模式。ZCode 的命令终端起初找不到 Go，协调者提供已安装工具的位置，执行者只调整本任务命令环境。这两项已回写通用接入说明。CLI 模式也以实际运行结果核对，未将帮助文本或启动成功当作完成证据。

因此本次证明的是：**另一 coding agent 能在仓内规则和限定委托下维护同一规格，并使用与宿主无关的差异检查；接入仍需要环境准备和权限协调。** 未证明所有 Agent 自动加载、零人工接入、全新账号认证、其他操作系统、真人接手或长期节省工时。试跑复用了本机账号和依赖/编译缓存；未连接数据库、设备或生产，也未重新执行真实通知渠道集成。

## 维护成本与取舍

- 日常小任务只改原测试与原规格，未新增 Patch、映射、并行业务文档或跟踪的交接包；声明及执行结果保留在本次私有证据。
- 本轮一次性整理共同入口和 LoopX 条件入口，同步团队约定、Skill 与索引。维护文档清单只增加这两个入口；检查器、CI、Hook 和服务器强制规则均未改变。
- 接入成本包括 CLI 模式核对、无界面权限恢复、命令环境修复，以及交互确认。不能把这些成本隐藏在“Agent 已安装”之下，也不能用一次演练推算团队收益比例。
- 普通任务可按原任务/Issue/PR 留证；已明确纳管任务仍由原 Goal 管理。被委托者不复制控制面状态，协调者把结果绑定同一 Todo。
- ZCode 另注意到实现注释使用“信息最完整”，而当前规格明确按字符数判断；实现本身遵循现行规则。本次保留这一措辞观察，不越过两文件委托修改生产文件，也不从注释推导新业务含义。

完整输入、工具调用、反例/正例、日志及复审回执私有保留，最终候选由 Goal 外部回执绑定，避免报告引用自身提交。后续恢复协议适配上行的技术契约评估；本轮不授权实现、推送或新增强制门禁。旧环境、旧仓、备份和历史回执继续保留。

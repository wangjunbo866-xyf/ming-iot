# 跨 Agent 接入与全新 clone 小修改试跑

用户授权补齐通用入口、区分普通开发和 LoopX，再用另一 coding agent 试跑小修改并独立复审；不推送、不启用新强制门禁。现有 Goal、协议契约待办、旧仓、私有备份和历史均保留。

## 交付设计

根 AGENTS 保留共同规则，LoopX 控制面要求移入[条件入口](../runbook/loopx-development.md)；新成员从[通用接入](../runbook/cross-agent-development.md)开始。ming-specs 继续指向同一团队约定和模块主规格，不要求每位成员安装同一宿主或私有调度环境。已纳管任务保留原准入约束。

## 独立试跑任务

在从完整本地候选创建、没有原项目私有状态的全新 clone 中，委托 ZCode 补充通知模块 SCENE-BUTTON 的字符数和同长首项回归，并完善现有规格的验证说明。只允许改原测试文件及当前 spec；不修改生产代码、行为、映射或已吸收 Patch。按 current-v1 的既有规则采用 no_behavior_change，不新建需求 Patch。

试跑实际目标 `pilot-base` 固定为 `27d3ef51ffa88160f7d9c11d0ecd021d814ab022`，候选为 `deb331014206efc1271e707ce586f400e518c8c3`；工具计算的 merge-base 与目标一致。克隆使用完整 Git 对象而非共享 alternates，没有原项目的 LoopX 状态、私有配置或聊天历史。协调者通过本地 cherry-pick 保留该改动，不推送。

## 结果与限制

实际执行者为 ZCode CLI，安装包版本 3.15.3-35、运行时 0.16.9，实际模型 GLM-5.3，build 模式。原始任务要求先读仓库入口；运行记录确认其调用了仓内 ming-specs，并读取团队约定、模块当前规格、代码和差异检查说明。结论是 `current-v1#scene-button` 的既有规则不变，采用 `no_behavior_change`，没有新建 Patch 或修改规格语义版本。

首次无界面运行遇到缺少权限确认客户端，保留失败后转入正常交互客户端，逐项确认允许的操作，没有改用全量放行模式。ZCode 的命令终端起初找不到 Go，协调者提供已安装工具的位置，执行者只调整本任务命令环境。这两项已回写通用接入说明。CLI 模式也以实际运行结果核对，未将帮助文本或启动成功当作完成证据。

因此本次证明的是：**另一 coding agent 能在仓内规则和限定委托下维护同一规格，并使用与宿主无关的差异检查；接入仍需要环境准备和权限协调。** 未证明所有 Agent 自动加载、零人工接入、全新账号认证、其他操作系统、真人接手或长期节省工时。试跑复用了本机账号和依赖/编译缓存；未连接数据库、设备或生产，也未重新执行真实通知渠道集成。

## 维护成本与取舍

- 日常小任务只改原测试与原规格，未新增 Patch、映射、并行业务文档或跟踪的交接包；声明及执行结果保留在本次私有证据。
- 本轮一次性整理共同入口和 LoopX 条件入口，同步团队约定、Skill 与索引。维护文档清单只增加这两个入口；检查器、CI、Hook 和服务器强制规则均未改变。
- 接入成本包括 CLI 模式核对、无界面权限恢复、命令环境修复，以及交互确认。不能把这些成本隐藏在“Agent 已安装”之下，也不能用一次演练推算团队收益比例。
- 普通任务可按原任务/Issue/PR 留证；已明确纳管任务仍由原 Goal 管理。被委托者不复制控制面状态，协调者把结果绑定同一 Todo。
- ZCode 另注意到实现注释使用“信息最完整”，而当前规格明确按字符数判断；实现本身遵循现行规则。本次保留这一措辞观察，不越过两文件委托修改生产文件，也不从注释推导新业务含义。

完整输入、工具调用、反例/正例、日志及复审回执私有保留，最终候选由 Goal 外部回执绑定，避免报告引用自身提交。后续恢复协议适配上行的技术契约评估；本轮不授权实现、推送或新增强制门禁。旧环境、旧仓、备份和历史回执继续保留。

## 追加：入口地图与四条协作路径（2026-10-18）

本段为后续同日试跑，保留上文原时点的 ZCode 全新 clone 结果。本轮复用原候选工作树，依据《天猫 AI 项目研发协同实践》第 3–4、7–9 页和用户授权，将 AGENTS 收敛为入口地图，ming-specs 改为按任务读取与写回。根入口 62 行，Skill 正文连同元数据 43 行；交付细则移到团队约定，原授权、公开和保留边界继续适用。

### 实际演练范围与结果

两位不继承原聊天的 GPT-6 Astra / High 子 Agent，分别只从 AGENTS 进入通知和上行 Feature，各执行四条路径。A/B 使用真实当前规则和本轮 README 导航差异；C/D 使用明确标注的模拟提议，草稿仅留私有证据，不写入真实 raw、主规格或业务决定。主任务负责原 Goal 的认领与结算，被委托者不复制或操作控制面。

| 路径 | 通知 Feature 的结果 | 上行 Feature 的结果 |
| --- | --- | --- |
| A：只读定位 | README → current-v1 即可解释昵称回退及发送调用边界；没有先拼接历史 Patch | 当前 spec 0.2.1-draft 可解释部分批次、重发及迟到规则，并明确 15 个运行场景未执行；没有拼接 Eventbus raw/Patch |
| B：规则不变的小修改 | 为实际 README 导航改动准备模块 no_behavior_change 声明，保留版本和条款；没有新建业务 Patch | 为实际 README 导航改动准备 documentation 例外；明确文档归属已建立、产品差异映射尚未登记，不伪造模块覆盖 |
| C：行为变化 | “自动也优先昵称”整理为 draft，识别系统标记与账号缺失的取舍；历史 manual 授权不覆盖该提议 | “迟到数据也触发实时告警”整理成 Change、完整候选正文及反向入口草稿；与 PA-D3 冲突的提议保持待确认 |
| D：并行冲突 | 两份同基线认领覆盖同一 auto 条款；昵称优先与只用账号互斥，列出选择、撤销及收敛路径 | 两份同基线认领涉及同一迟到条款和 DM 数据责任；补历史并告警与丢弃历史互斥，列出协调人/写回人缺口及收敛路径 |

C/D 的出口是“可以评审的提案与明确未决冲突”，不是业务已批准或冲突已解决。双方都保留原确认，说明最新基线复核与同候选主规格收敛要求，没有虚构真人、有效批准、实施或运行验收。通知和上行真实主规格、上行 raw 的字节保持不变。

### 试跑发现与修订

1. 两位 Agent 初次处理四项组合请求时均尝试一次读取整份团队约定，出现输出截断和补读。虽然规则与写回判断正确，这一过程不能判为阅读负担已优化。根入口及 Skill 补充“先读锚点章节、确有依赖再展开”，另用一个无聊天历史的独立小任务复测。
2. 上行候选未实施时，“直接修订原稿还是新建 Patch”缺少明确判定。已在团队约定的 [Patch 收敛](../runbook/team-development.md#patch-convergence)补齐：已有同需求 Change 继续追加 revision；无 Change 时补未决细节/不变含义可修订草案，改变已确认主规格行为或独立并行任务使用 Patch。基线为候选与业务确认分别表述。另用新上下文核验三种写回分支。
3. 长期负责人、DM/告警当前规格入口和上行产品映射仍有缺口；本轮不为演练虚构负责人或批量建立新模块。真实 PA 实施前补齐相关契约与实际写范围。
4. 子 Agent 如实指出验证期间主任务继续调整方法文件，早期检查只绑定其输入快照；最终候选由主任务重新检查并独立复审，不沿用旧快照冒充最终通过。

小修改复测：另一无原聊天的 GPT-6 Astra / High 会话，仅接收通知 README 小任务，从 AGENTS 找到当前 spec；团队约定只读认领、小修改、Patch 收敛与交付所需章节，没有通读整页，也未读取历史 Patch 或业务源码。正确准备模块轻量声明，文档检查通过、工具输出无截断。这证明该样例可按需执行，不是所有 Agent 都会稳定遵循的保证。

候选修订复测：另一新上下文分别处理“补未决 profile 字段”“独立推翻已确认迟到规则”“原 Change 收到澄清”，正确选择原候选修订、draft Patch、原 Change 追加 revision 三个写回位置，并区分设计确认与对实现版本生效；真实业务正文未改。

### 验证和维护成本

- 初轮现有 make knowledge-check：42 份维护正文、44 条来源绑定及 67 项工具 + 25 项 preflight 回归通过；8 个历史范围外锚点仍未读取，外部链接未联网检查。程序不会验证业务决定、并行互斥或正文语义完整性。

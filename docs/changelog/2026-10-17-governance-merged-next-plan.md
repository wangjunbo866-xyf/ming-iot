## 建议执行顺序与完成条件

### 1. 小范围收尾：校准两个模块的当前入口

核对两个 README 的已合并状态、适用代码版本及验证入口，引用 PR #5/#6 与 main 的真实证据。只修正事实时点，不更改 `current-v1` 业务规则，不补造部署或真人验收结论。完成条件：当前入口能直接说明已合并、未部署验证和适用范围，链接检查与独立语义复核通过。此项为下一步建议，本轮未修改模块正文。

### 2. 有真实需求时，启动一个 S4 切片

优先延续通知模块；若近期真实工作在 API 校验，则选择该模块。由业务确认人说明“现在怎样、希望怎样、哪些不能变”，确认模块责任、本次实施者与评审者。长期负责人尚未确定时保留缺口，不自动指派 AI 或小黄。

从当前主规格进入，按[小修改约定](../runbook/team-development.md#small-changes)处理：恢复既有规则的修复引用现有条款并补回归；改变约定的需求建立短 Patch，同步主规格和双向指针。真实 PR 差异、适用验证与独立评审绑定最终候选；如涉及数据库、设备或消息链路，再选择相应真实依赖验证。

完成条件：能说明新旧规则和不变项，受影响实现/测试/文档一致，实际差异无遗漏，未验证项明确。当前没有该需求输入，未启动业务实现。

### 3. 在同一任务里验证接手与成本

接手者只从仓库和模块入口说明当前规则、边界及验证方式；日常交接直接使用代码和一致的文档，无需另建交接包。有实际同事参与时记录真人结果；只有独立 AI 参与时明确标为 AI 演练，不恢复已废弃的小黄反馈任务。

在原任务/PR 或 Patch 里记录定位时间、文档维护时间、追问、重复填写、误报和返工；缺数据写 unknown，不追加第二套台账。完成条件：有可追溯的实际记录，能区分一次性建设成本与日常维护成本，并指出至少哪些步骤有用或造成负担；不预设节省比例。

### 4. 用结果决定保留、简化或扩域

用户根据本次连续演进和成本证据决定采用范围。只有发现具体缺口时才改进检查或扩展一个业务域；不先补齐全平台规格、引入完整框架或新增 Hook。若证据不足，保持未完成，不因 PR 合并关闭整个 Goal。

## 保留边界

旧仓、私有备份、原候选及历史回执继续保留。同一个 `ming-iot-knowledge-pilot` 持续记账；小黄反馈及依赖任务保持废弃。未启用自动去重、自动归档、全库门禁或新的服务端必需检查。

现有检查不证明外链在线有效、语义去重或全部历史正文正确；8 处范围外历史锚点仍未验证。无外部服务验证不等于真实 Kafka、数据库、设备、推送或生产验收。后续执行顺序由[当前总纲](../project-charter.md)及新任务授权确定，本记录保留 2026-10-17 的事实与建议。

## 建议执行顺序与完成条件

### 1. 当前入口校准：本地候选已修正

两个模块的 `current-v1` 已随 PR #5 合并；主规格 `source_revision` 继续保留原来源 `c165a56531f58421a870a0b8794f24556b60d3b2`。本次比较该提交与合并 main `56006502324800448c9775944d28478254be6142`：通知 `notifymanage` 目录、API 校验 `cmd/apicheck` 目录及 `internal/apicontract/metadata.go` 无差异，当前规则仍适用。比较只覆盖这些路径，不声称全仓实现未变。

本轮分类为文档事实修正：两份主规格、实现、测试、已吸收 Patch、S1/S3 原始记录均不改写，不新建业务 Patch；只更新入口的状态与证据导航。最终候选的链接/索引检查、两个模块聚焦测试、完整分支差异映射和独立语义评审见同一 Goal 本轮回执。历史里的“候选”仍描述历史时点，不全库替换。

### 2. 业务联调前：先跑通所需最小环境

**只读预检结果（2026-10-17，本机时点快照）：**

| 层次 | 已核实 | 仍缺什么 |
| --- | --- | --- |
| 主机工具 | Go 1.25.4、Python 3.12.3、Docker Compose 5.1.3；默认本地 Unix socket 的 Docker 服务 29.4.0 可达，无 Docker 环境路由覆盖 | 这些版本可用不等于整个系统兼容或业务可运行 |
| 本仓 Compose 项目 | 按 `ming-iot-saas`、`ming-iot-things-baseline`、`ming-iot-kafka-local` 项目标记查询，均无容器，包括已停止容器 | 未检查任意其他项目或非容器服务，不能据此称整台机器没有环境 |
| 旧共享依赖 | 旧 SaaS 使用的 `cloudx_net` 网络存在；按既有名称查询，`postgres` 容器运行中，未见 `ienv-redis` / `ienv-nats` | 未测试 PostgreSQL 健康、身份、库或数据归属，不据此复用；同类服务可能使用其他名称 |
| Things 配置 | 日常 main 与本候选的 `deploy/profiles/things-baseline/.env.local` 均不存在；未读取任何密钥 | 需私有配置及隔离的数据目标；Things profile 还依赖宿主 PostgreSQL，引导会建库，必须先明确目标 |
| 运行与业务验证 | 本轮仅执行只读预检 | **NOT_RUN：**未启动服务、建库、迁移数据、发送通知或进行真实 API 冒烟；没有新运行验收结论 |

[部署说明](../../deploy/README.md)已有分层入口，应复用并核对依赖，不另造框架：`make verify-pr` 只做构建/测试/静态检查；`verify-integration` 才启动所选 Kafka 或 Things suite。Kafka profile 不替代 SaaS 的 NATS 事件链路。旧 SaaS Compose 依赖预先存在的 PostgreSQL/PostGIS、Redis、NATS 和共享网络；不能直接照旧入口启动并宣称建立了隔离的开发环境。

下一步按一个连贯任务推进：

1. **选链路并准备隔离环境。** 先用一条真实需求确定首条验收路径、所需服务、开发数据库/测试数据、端口、配置与凭据来源。需求澄清可先做。API 校验 CLI/辅助函数单测无需完整平台；通知联调至少需要 SaaS、实际配置所需依赖及可观察的发送通道。仅当需求涉及设备或 Things/Kafka 时增加对应组件；未提供的前端/网关不假定已可用。
2. **启动必要服务并验证依赖。** 复用现有部署入口，修复已证实的最小缺口；准备独立项目、数据与开发身份，避免旧共享库被自动迁移。配置只放私有文件，不提交密钥；不清库、删卷或接触生产。记录服务健康与依赖可达结果，失败保留原始状态。
3. **跑一条现有行为的基线。** 从请求/事件输入到可观察结果，保存输入、预期、实际、数据准备和日志定位；健康检查成功不代替业务成功。若使用测试接收端，明确只证明接入该接收端，真实外部推送仍未验证。
4. **验证可重复启动与清理。** 重启/重跑后得到同样结果，操作说明直接进入现有 runbook 或部署说明；清理只停止本任务服务并保留数据，不删除旧环境、旧仓或备份。

完成条件：另一位开发者能按仓库入口复现同一基线，当前需求依赖无未说明阻塞，已运行与 NOT_RUN 清楚分开；在这之后，用同一路径比较业务变更前后结果。这里只形成计划，尚未执行启动或新增运行工具，也不把所有平台服务启动设为每种任务的统一门槛。

### 3. 需求确认且适用基线可用后，启动一个 S4 切片

优先延续通知模块；若近期真实工作在 API 校验，则选择该模块。由业务确认人说明“现在怎样、希望怎样、哪些不能变”，确认模块责任、本次实施者与评审者。长期负责人尚未确定时保留缺口，不自动指派 AI 或小黄。

从当前主规格进入，按[小修改约定](../runbook/team-development.md#small-changes)处理：恢复既有规则的修复引用现有条款并补回归；改变约定的需求建立短 Patch，同步主规格和双向指针。真实 PR 差异、适用验证与独立评审绑定最终候选；如涉及数据库、设备或消息链路，先取得上一节对应运行基线，再以相同验收路径验证调整后的行为；不把基线准备推迟到开发结束。

完成条件：能说明新旧规则和不变项，受影响实现/测试/文档一致，实际差异无遗漏，未验证项明确。当前没有该需求输入，未启动业务实现。

### 4. 在同一任务里验证接手与成本

接手者只从仓库和模块入口说明当前规则、边界及验证方式；日常交接直接使用代码和一致的文档，无需另建交接包。有实际同事参与时记录真人结果；只有独立 AI 参与时明确标为 AI 演练，不恢复已废弃的小黄反馈任务。

在原任务/PR 或 Patch 里记录定位时间、文档维护时间、追问、重复填写、误报和返工；缺数据写 unknown，不追加第二套台账。完成条件：有可追溯的实际记录，能区分一次性建设成本与日常维护成本，并指出至少哪些步骤有用或造成负担；不预设节省比例。

### 5. 用结果决定保留、简化或扩域

用户根据本次连续演进和成本证据决定采用范围。只有发现具体缺口时才改进检查或扩展一个业务域；不先补齐全平台规格、引入完整框架或新增 Hook。若证据不足，保持未完成，不因 PR 合并关闭整个 Goal。

## 保留边界

旧仓、私有备份、原候选及历史回执继续保留。同一个 `ming-iot-knowledge-pilot` 持续记账；小黄反馈及依赖任务保持废弃。未启用自动去重、自动归档、全库门禁或新的服务端必需检查。

现有检查不证明外链在线有效、语义去重或全部历史正文正确；8 处范围外历史锚点仍未验证。无外部服务验证不等于真实 Kafka、数据库、设备、推送或生产验收。后续执行顺序由[当前总纲](../project-charter.md)及新任务授权确定，本记录保留 2026-10-17 的事实与建议。

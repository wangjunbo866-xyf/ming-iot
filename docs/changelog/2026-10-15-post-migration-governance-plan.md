# 迁移后的文档、ming-specs 与团队流程盘点

本轮按用户要求梳理缺口、提出计划，沿用 `ming-iot-knowledge-pilot`。盘点基线为迁移后 main 的 `c165a56531f58421a870a0b8794f24556b60d3b2`。本稿是下一阶段提案，不表示以下改进已实施、团队已采纳或已经上线。旧仓、历史记录及私有备份继续保留；小黄反馈任务已废弃，不重新催办。

结论：单仓迁移和入口切换已经完成，知识体系已有可用骨架和两次局部试跑。当前最需要解决的是“主分支行为、主规格、执行约定不同步”，随后才是扩展覆盖和提高自动检查能力。无需重新迁移目录，也不以 r-doc、OpenSpec 或完整 AI-DLC 的采用为前提。

## 真实缺口

### G1 / P1：当前主规格落后于已合入实现

通知模块入口仍写“本地候选”“不覆盖主分支现状”，[spec.md](../specs/saas/notification-trigger/spec.md)仍以所有类型账号优先为 observed-v0，并称当前无生效覆盖。当前 [FormatTriggerUserLine](../../backend/saas/service/syssvr/internal/logic/notifymanage/triggerUserParams.go)已对 manual 优先取昵称，其他类型保持账号优先；[R2 Patch](../specs/saas/notification-trigger/patches/PATCH-20261014-display-name/change.md)保存了对应用户决定。

API 校验也一样：[主规格](../specs/engineering/api-contract/spec.md)仍描述不存在路径和全空白输入误报成功的旧缺陷，而当前 [lintFileSelection](../../backend/tools/cmd/apicheck/main.go)已校验可扫描文件并拒绝空选择。读者必须拼接旧主规格、Patch 和迁移历史才能确定当前行为。

修复方向：逐条核对已确认决定与当前实现，把已接受行为整理进对应版本的完整主规格；在入口说明“main 已包含、部署未验证”，保留旧 observed 基线和 Patch 历史来源。不能仅因代码已合并就将整个模块或所有环境标为已验收，也不能倒改需求来迁就代码。

### G2 / P1：提纲与实际执行方法尚未收敛

[治理提纲](../wiki/team-development-outline.md)已提出“合并前收敛候选主规格”“普通交接以代码和一致文档为入口”“按风险选择轻量路径”。团队约定仍规定稳定后安排收敛，并在责任切换时生成固定交接 JSON；ming-specs 的接手流程仍从交接包开始。

这是已知设计差异，并非所有旧规则都无效。下一步应把选定规则同步到团队约定、Skill 与模板：日常接手默认模块入口、固定版本、待办和验证；快照仅用于确有离线、权限或外部交付需要的场景。保留历史 AI 演练材料，不继续把它当日常必填产物。确定性输出应统一，个人开发方法不必强制统一为一个 Skill。

### G3 / P1：通过检查器测试，不代表检查过本次真实变更

`knowledge-check`核对清单中的 23 份文档入口、局部链接和 Skill 文件，并运行工具及 preflight 回归。当前 CI 没有把 PR 的实际 base/head、受影响模块和 `check.json` 交给 preflight；模块 `spec.md`、Patch 等也不在该 23 份导航清单中。它不验证业务含义、批准真实性或全部锚点。

本仓没有跟踪 CODEOWNERS；本轮未读取 GitHub ruleset/分支保护，因此远端强制 Review、必需检查与绕过规则状态为“未核验”，不能断言没有保护。CI 绿色、PR 模板、Hook 和真实服务端合并限制分别验收。

修复方向：先定义真实 PR 的差异到模块映射、无规格变化的合理说明及多 Patch 检查方式，再接确定性 CI。跨模块 PR 应按全部认领的并集核对，不把整份 PR 差异强塞给单个 Patch 后判为越界。业务语义提醒交给 AI 和评审，不能靠改了某个 Markdown 文件就自动放行。

### G4 / P1：旧证据可追溯，但不能直接充当新仓执行输入

抽查通知基线 `7d4063ef…`、API 基线 `da80f056…`、通知候选 `824849b0…`、AI 接收版本 `97430381…`，均不能在当前新仓解析为 commit。以旧通知基线运行 preflight 返回 BLOCKED。这符合另建公开候选历史的迁移方式，不表示历史证据被删除，也不是检查器应放宽的错误。

修复方向：在现行模块中登记新仓可解析基线、适用版本与本轮验证；旧回执继续明确属于旧仓/旧版本，通过来源记录追溯。不能将旧 SHA 静默换成新 SHA，也不能把私有完整历史重新推入公开仓。新开发者仅克隆新仓即可完成日常验证；追溯原始实验可以依赖获授权的私有资料。

### G5 / P2：目录职责已有定义，业务和运行知识覆盖仍有限

目前顶层 `architecture/` 只有迁移设计；`runbook/` 为日常开发、团队约定和 CI 三份文档。设备接入、遥测、OTA、租户权限、场景联动等还没有在当前 `specs/` 地图建立完整导航和负责人关系。相关知识散在产品子目录和历史材料中，不能直接整体升级为现行权威。

修复方向：先用一个真实领域贯通“业务规则 → 代码/API/数据或事件 → 验证 → 必要架构和操作说明”。再按后续任务逐域提取历史中的有效内容，登记来源和替代关系。共享接口只维护一份正文；未核实部分保留 unknown/observed，不批量生成貌似完整的规格。

### G6 / P2：维护成本和团队收益仍缺足够证据

历史 AI 接收试跑有具体结果，通知真实通道验证仍为 NOT_RUN；小黄任务取消后没有真人验收。新仓从零接手能否迅速找到当前规则、同一规则连续演进后是否仍完整、误报和日常文书成本是否降低，尚不能用已有单次试跑或 CI PASS 证明。

修复方向：在上述收敛后安排不继承聊天历史的 AI 接手验证；待实际出现新需求时验证连续演进，不能为了实验编造产品需求。真人收益保持未验证，不重新建立已废弃的小黄任务。记录定位时间、追问次数、漏掉的不变项、重复字段、误报和返工；首次建体系成本与日常修改成本分开。

## 拟采用的最小日常流程

1. **定位与认领：** 从模块入口读当前规格，确定代码/规格范围、负责人和共享影响；AI 整理，人在职责或业务承诺不明确时决定。
2. **分类与澄清：** feature / patch / sunset / blueprint 表达变化性质；风险决定深度。错字直接改；恢复既定规则的修复引用条款和回归；行为变化留下简短差异及确认。
3. **实施与同步：** AI 在授权范围实现和验证，并更新同分支主规格；原 Change 保存理由和决定，避免另造一套动态状态。
4. **差异提醒与 Review：** 工具检查范围、指针、版本和实际候选；AI 检查代码到规则的差异，评审者检查语义和测试有效性。性能/集成验证按实际风险选择，未知不能记为 PASS。
5. **合并与知识留存：** 主规格表达该版本完整行为，Patch 转历史并保留双向追溯；合并、发布、部署分开。下一个开发者直接从模块入口接手。

以上为 S1/S2 拟落地方式，不替代尚未修订的现行入口，也不证明新门禁已启用。

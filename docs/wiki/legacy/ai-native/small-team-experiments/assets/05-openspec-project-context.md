# 以 OpenSpec 为核心的全栈项目上下文

日期：2026-10-10。状态：用户已选择路线 A，具体决定见 [最小文档维护决策](../issues/05-document-maintenance.md#answer)。本文保留方案依据和落地建议；具体迁移、查询实现、示例需求及试点指标尚未确认，也未安装工具或验证实际收益。

## 1. 判断

默认 OpenSpec 不会自动生成天猫 collar 那种完整的全栈知识库，但可以承接其中的规格与变更主干。补上薄的项目导航、明确的知识来源，以及按需读取动态事实的通道，就能复现其核心上下文机制；不必另建一套 SDD 系统。能否达到同样的研发效果，需要在本项目用新会话导航和真实需求交付验证。

用户说的“spec 是 AI 的 RAG 库”，强调的是将项目知识变成 AI 可检索、可引用的上下文。为避免歧义，本方案暂用三个词区分：

- **项目知识库**：业务意图、架构与决策、代码与接口、运行事实、操作知识、历史和参考资料组成的整体。
- **业务规格**：其中描述系统应有什么行为的权威来源，由 OpenSpec 承载；不能把未采纳的研究、旧实现或现场观察都写成要求。
- **任务上下文**：针对当前问题，从知识库按需读取的一组相关内容和版本。它不是整个知识库的副本。

这是术语建议，尚未写入已确认协作词表。这里的检索可以通过目录、链接、全文搜索和只读工具实现，不预设向量数据库。语义索引可后续加入，但索引应指回原始来源。

## 2. 天猫真正值得复用的机制

来源：用户提供的 [天猫 PDF](</mnt/c/Users/Administrator/Documents/kimi/tasks/2026-10-08/15-52-46-fd39deab/天猫AI项目研发协同实践.pdf>)，以下页码为 PDF 页序；文章描述属于作者自报。

1. **入口到细节的导航**（p2–6）：根 AGENTS.md 先说明项目和子仓，再指向业务地图、约定和详细知识。文章的 120 行是其团队约定，不是本方案硬阈值。
2. **不同知识有不同作用**（p4–9）：specs/changelog、architecture/runbook、vendor/wiki 相互补充；探索材料与正式规格区分，当前行为与历史演进区分。
3. **按业务路径横跨多个仓库**（p7–10）：一个业务模块连接前端路由、API、领域实现、规格和负责人。文件放在同一工作区便于读取，但物理同目录并不自动证明版本相容。
4. **补齐代码以外的事实**（p10–12）：DB 中的 Prompt 等通过只读 MCP 按业务锚点和环境查询，同时规定何时查、如何解释。IoT 的运行配置、协议映射、物模型或规则版本同样可能需要此入口，具体以本项目实际存放方式为准。
5. **变化触发知识更新**（p5、p10）：识别实现与意图差异，由责任人决定修改规格或纠正实现，不能自动把代码现状升级为业务要求。

本方案不要求照搬六个固定目录、六个强制 Skills 或每次提交同时改三份说明。保留这些知识职能，维护方式由信息来源和实际复用需求决定。

## 3. OpenSpec 覆盖与补充

核查入口：[官方概念](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)、[v1.14.1 定制](https://github.com/Fission-AI/OpenSpec/blob/v1.14.1/docs/customization.md)、[存量项目接入](https://github.com/Fission-AI/OpenSpec/blob/v1.14.1/docs/existing-projects.md)、[stores 指南](https://github.com/Fission-AI/OpenSpec/blob/v1.14.1/docs/stores-beta/user-guide.md)。本次研究固定 main `9111a7654d7800391459431fff4eaf66e33a3d2e` 和 tag v1.14.1 `87c3595ace6a2e22957f39ebe5b74c2f2316e0cb`，关键定制、stores、schema、config、explore/apply 文件在两版本内容相同；不把 main 的包版本字符串当作已发布内容证明。

完整事实、源码出处与检查范围见 [OpenSpec 项目上下文能力研究](/home/wangjunbo/.cache/ai-native-wayfinder-worktrees/openspec-context-20261010/docs/research/2026-10-10-openspec-project-context.md)。研究只做静态核读，未证明真实 Agent 行为或本项目接入效果。

| 上下文能力 | OpenSpec 可承接的部分 | 团队还需提供的内容 |
| --- | --- | --- |
| 系统应该怎样工作 | 现行 specs、候选 delta specs、具体行为场景 | 业务能力命名、边界和认可的行为语义 |
| 这次为何改、怎样改 | proposal、design、tasks；归档保留变更上下文 | 与代码、接口、环境和验收的有效引用 |
| 项目共同背景 | config 的 context、按产物的 rules；apply/archive 的运行时指导输入 | 简短项目说明和入口链接，避免每步注入整库 |
| 定制产物和依赖 | 自定义 schema 与模板 | 只在默认结构持续缺少必要信息时增加，不能把所有知识都变成每次必填产物 |
| 按需了解已有项目 | explore 引导宿主 Agent 发现并读取相关源码、测试、文档、配置；apply 提供具体 contextFiles | 相关资料必须可达；这是读取协议，不是 CLI 已自动检索和理解全项目的证明 |
| 跨仓共用规格与计划 | stores 用独立规划仓共享 specs/changes，提供规范引用索引和读取指引，仍为 beta | 明确实际文档根、代码仓路径和组合版本；不自动同步 checkout，规范索引也不覆盖全部 wiki 或运行数据 |
| 全项目业务导航 | 可引用团队提供的地图；Agent 可探索代码 | 业务能力 → 现行规格、相关变更、代码/API、运行知识的映射 |
| 当前生效的外置配置 | 可以把查询规则写进上下文或操作指导 | 真实只读查询能力、业务锚点、环境及版本信息 |
| 文档持续可信 | 规格变更和归档支持知识演进 | 更新触发、责任人、来源版本、过期与冲突处理；文件存在不证明内容正确 |

因此，“不用 OpenViking 也能先做”与“只执行 OpenSpec 初始化就能得到完整知识库”是两个不同判断：前者可以作为试点方案，后者不能成立。默认工作流之外的导航、操作资料和查询通道是项目自己的上下文建设。

尤其不要把整个知识库复制到 config.context：它用于公共背景，源码设有 UTF-8 50 KiB 限额，超限警告并忽略该字段，并不自动切片检索。适合常驻的是少量事实和导航，详细内容由 Agent 按任务读取。

## 4. 已选路线的组织方式

保留 OpenSpec 原生规格/变更结构，在现有文档仓建立薄导航。下图是职责与引用关系，不是要立即创建的目录清单：

```text
工作区 AGENTS.md                       短入口：项目目的、仓库、约束、导航
    └─ 研发文档仓 map/                 业务能力和跨仓关系，只存摘要与指针
         ├─ openspec/specs/            现行行为规格
         ├─ openspec/changes/          候选变更、设计、任务及归档历史
         ├─ 产品仓代码 / API / schema  实现和可生成的接口视图
         ├─ 既有架构仓 / ADR           系统边界、数据流和长期决策
         ├─ 操作说明                   可复用启动、验证、排障步骤
         ├─ references / 研究资料      外部来源与未定方案，标明版本和性质
         └─ 只读查询入口               必要时读取运行环境中的实际配置
```

地图可以只从一个 README 起步，内容多了再按业务模块拆分。每个模块只写：**一句话边界、维护责任人、检索别名、权威规格、代码/接口入口、必要操作/动态查询入口**。关联 Change 与发布历史可从 OpenSpec/PR 生成索引，不另填一张进度表。

OpenSpec 已有规格清单、用途摘要及读取命令，直接复用；地图只补业务能力与前端/API/数据/部署等来源之间的跨层关系。现行架构需要有可直接阅读的入口，不能要求每位成员遍历所有历史 design 才拼出全貌。

入口链接应从明确的文档根/仓库根解析，不能依赖作者个人的绝对路径。单仓开始工作的 Agent 也应能找到同一文档根；跨仓不可达时应报告缺失来源，不能自行捏造另一份规格。

一次任务使用的来源和版本，可以放在现有 design 的参考段落及交接/证据记录中。短暂阅读清单由 Agent 生成即可，不要求增加一个长期手写的 context.md。

### 路线对照（A 已选定）

| 选择 | 做法 | 取舍 |
| --- | --- | --- |
| **A：OpenSpec＋薄导航，已选定** | OpenSpec 维护规格/变更；现有地图连到架构、操作资料、参考和动态查询；允许不同成员用不同 Skills 完成相同输入输出 | 先验证 AI 能否找到正确知识，定制量和迁移负担较小 |
| B：用定制 schema 管更多产物，第一版未采用 | 把研究、上下文引用、操作影响等定义为 OpenSpec 的特定 Change 产物 | 在反复漏项时有价值，但 schema、模板和既有存量知识映射都需维护；仍不会自动获得运行环境查询能力 |

第一版从 A 开始；只有试点反复漏掉同一种必要信息时，再讨论是否增加某项规则或产物。所有知识不必物理放入 openspec/specs。

## 5. IoT 示例：一次新会话如何取得完整上下文

以下是“设备上报温度后能查询，其他租户不能读取”的上下文走查示例，延续上一份责任走查；尚未确认为实际试点需求，也不代表已有完整链路。

| 顺序 | AI 需要回答的问题 | 应查的来源及结果 |
| --- | --- | --- |
| 1. 进入项目 | 这是哪个项目，哪些仓库相关？ | 工作区入口 → 研发文档根和产品仓；确认当前任务范围 |
| 2. 定位业务 | 遥测上报、设备查询和租户隔离分别由哪里负责？ | 业务地图连接相关能力，找到现行规格和本次 Change；不只检索“temperature”代码关键词 |
| 3. 确认语义 | 温度类型/单位、非法数据、旧消息兼容、租户隔离如何定义？ | OpenSpec 现行要求及候选差异；尚未定义的语义回到 P 澄清，不从旧代码猜成要求 |
| 4. 串起实现 | 设备入口、消息传递、处理/存储、查询/鉴权在哪里？ | 网关、设备管理、API 的真实代码与接口定义；沿实际配置确认消息路径，不预设某种消息中间件 |
| 5. 补齐动态事实 | 目标环境启用了哪个协议映射或规则版本？ | 先查静态配置；确实外置时按设备/产品/环境等适用锚点只读查询，记环境、版本或摘要及读取时间；没有通道就列为缺口 |
| 6. 理解约束和验证 | 有哪些坑、怎样启动和验证这条路径？ | 与本任务相关的架构决策、runbook、测试命令；外部 API 用法需要时才查固定版本参考 |
| 7. 形成可交接输入 | 下一位成员如何知道所依据的材料？ | 在现有交接中引用规格 revision、各代码 revision、环境/配置版本及未决问题；回到 OpenSpec tasks 推进，由 LoopX 管运行过程 |

共同上下文不要求所有人读完全库或使用相同聊天记录；要求各自作出的判断能追溯到相容的规格、代码和环境版本。Review 时发现版本不同，要重新判断受影响结论，而不是以“我们读过同一个文件名”认定已对齐。

本地已核查：`ming-iot/backend/things/README.md` 有 API、网关、设备管理入口，但自述仅为 L0 兼容基线，不能证明完整遥测链路。未知的消息路径、规则查询通道与端到端验证需要在真实试点中确认，不能由此示例补造。

## 6. 维护规则：只更新发生变化的权威来源

| 内容 | 何时维护 | 责任及验收 |
| --- | --- | --- |
| 业务行为与场景 | 需求语义改变 | D 起草对应 OpenSpec Change，P 决定语义，R 核对实现；旧实现本身不是自动改规格的理由 |
| 一次变更的方案与任务 | 实现发现方案/范围需调整 | 在当前 Change 更新；不在地图再抄计划，范围变化按既有责任规则处理 |
| 地图、入口和归属 | 模块新增、移动、退役或来源地址改变 | D 随变更补指针，R 验证能从入口找到正确来源；纯内部代码修改无需改地图 |
| 架构视图与接口 | 边界/长期决策改变；接口源改变 | 人确认稳定语义和理由；能从代码/schema 生成的部分由工具生成并带来源 revision |
| changelog | 需要发布或回顾变更时 | 从合并的 Change/PR 生成，可补用户可感知影响；不要求逐 commit 人工另写一份时间线 |
| runbook | 操作改变，或出现经验证、值得复用的排障经验 | D 或操作执行者提交，R 检查适用条件及复现入口；普通会话不自动成为团队规则 |
| vendor / 研究 | 引用外部实现、升级依赖、采纳或废弃方案 | 保存必要内容和上游版本/出处；研究标为候选，正式采纳后链接对应 Change，不复制现行规格 |
| 动态事实 | 当前任务确需运行环境信息时 | 从只读接口获取；短期快照进入适当证据位置，避免把易变值手写进常驻 AGENTS |

同一信息只在其权威位置修改，其余位置保留链接或生成视图。自动生成能减少录入，但架构解释、经验结论和规格意图仍需审阅。任何暂时无法验证的来源都应保留“未知/待核实”，而不是补成看似完整的项目介绍。

文档维护接入已有节点：G0 检查本次需要的上下文是否可达；G1 由 D 补受影响来源并交付证据；G2 由独立 R 核对规格、实现及引用；G3 按实际集成版本判断完整业务场景。无需为每份辅助文档新增一个人工关卡。完整业务集成仍按已确认安排放在合并后、发布前。

## 7. 用什么证明知识库有效

试点候选验收方法（尚未执行）：

1. **新会话找路**：不给历史聊天，只给仓库入口和上述需求。Agent 应能指出相关规格/变更、代码/API、运行信息入口和测试入口，每项都有可回读来源。找不到必须明确报告。
2. **当前与历史分辨**：安排一个已过期说明或候选设计，检查 Agent 能否识别其性质，不把历史/研究当现行要求。
3. **跨成员交接**：另一位成员使用自己的工具从相同入口接手，能找回相容版本、未决问题和验证方式；无需第一人重新讲一遍项目。
4. **一次变化的维护量**：做一个接口或模块入口变更，记录人工改了多少权威信息、是否需要重复抄写、损坏链接能否发现。

可机械验证的链接、路径、生成视图源版本可逐步进入现有 CI；语义对齐由独立审阅和业务测试判断。先记录找路耗时、遗漏来源、人工补充和维护耗时，再与相近任务比较，不预设提升比例。

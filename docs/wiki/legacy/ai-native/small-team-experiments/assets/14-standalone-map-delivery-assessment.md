# 独立 map-delivery：是否比 OpenSpec 加业务导航更适合当前团队

2026-10-10。Wayfinder 选型重评，性质为有源码依据的建议，不是已批准的文档迁移、工具重写或完整独立产品验收。

## 结论

针对这支团队的核心目标——以业务 Feature 找全栈上下文、保留唯一现行规格、统一追踪 Patch 与证据、尽量少维护文档——**建议把独立 map-delivery 作为下一轮优先验证的路线**。直接围绕业务功能建立权威目录，吸收 OpenSpec 的规格与变更思想，有机会比“OpenSpec 目录＋catalog＋导航生成＋两者适配”更一致。

用户随后提出参考天猫的六个 collar-* Skill：这与独立路线可以组合。建议方向进一步具体化为：**一个 map-delivery 体系、一套共享文档与校验契约、按知识职责拆分的 Skills**。Skill 数量和工具依赖是不同维度，六个同契约的专职 Skill 可以比两个文档模型的适配更清楚；实际收益仍由试点判断。

这不是“两个 Skill 一定比一个差”的结论。一个 map-delivery 入口也可以在内部调用 OpenSpec；成员入口数和底层依赖数是两回事。真正要比较的是：保留 OpenSpec 能复用多少可靠能力，又要为目标业务模型写多少适配，以及独立后团队必须维护多少代码。

此前薄导航方案已经需要业务分类登记、反向索引、稳定入口、导航区块修复和跨 Feature 聚合补充。它仍有价值，但“只是加一层薄导航”低估了这些接入工作。用户的新问题使此前 OpenSpec 选型值得重新评估；唯一权威、证据验收与独立 Review 的原则继续成立。

## 现有基础：两个 map-delivery 版本不能混为一谈

| 当前材料 | 实际已经具备 | 不能据此声称具备 |
| --- | --- | --- |
| 团队源 `ai-native/skills/map-delivery/` | 业务域 → 模块、完整主规格、FEATURE/PATCH/BUGFIX/SUNSET、一个主 Change 连接多个 affected_modules、Plan/Review/Evidence、真实 Issue/PR 和精确版本规则 | 所有步骤已经自动生成或可脱离项目使用 |
| 项目工具 `ming-iot-rd-docs/tools/map_docs.py` | init 骨架；check 结构、导航、锚点与版本元数据；activate 对准备好的候选进行只读校验；check 对相关 effective 变化复用激活校验 | 自动生成所有业务语义、自动合并 delta、自动更新主规格、自动移动归档，或自动批准/发布 |
| `map-delivery-portable` 草案 | 通用上下文定位、项目规则继承、按需模板、无强制远端 Issue 的轻量使用方式 | 完整复制项目校验器；context.py 明确只做定位与观察 |

本轮只读源码核对；没有重新运行整个项目测试或交付试点。核查时 `ming-iot/`、`ming-iot-rd-docs/`、`ai-native/` 三个主工作树根均未发现 `openspec/`，所以不能把此前讨论中的 OpenSpec 路线当成已经完成的业务迁移。

两个具体限制会影响独立路线的工作量：现有锚点占用检查按主 `target_module + anchor` 建键，并未逐一覆盖所有 affected_modules 的锚点；Review/Evidence 校验核对文档声明的 repository/base/exact_head 对应关系，不查询远端或验证测试执行真实性、Reviewer 身份。它们是可复用的检查基础，不能计作跨模块完整冲突检测或验收事实采集已经完成。

## 三条路线的真实差异

| 路线 | 好处 | 持续成本 | 对当前目标的判断 |
| --- | --- | --- | --- |
| OpenSpec + 独立导航入口 | 尽量保留原生工作方式 | 成员理解多个入口；维护业务映射和链接适配 | 不优先继续扩展这个版本 |
| 一个 map-delivery 入口，内部使用 OpenSpec | 对成员统一；可复用 OpenSpec 的解析、产物依赖、同步/归档机制 | 仍要维护业务模型与原生目录之间的适配、版本兼容和相关测试 | 如果真正依赖这些现成功能，这是合理备选 |
| 独立 map-delivery，吸收 OpenSpec 思想 | 业务模型、文档结构和验收规则围绕同一个功能入口设计；能延续现有模块结构 | 本团队负责工具、模板、规格演进规则、异常恢复与测试 | 建议作为有界试点的首选，尚未实证总成本更低 |

独立并不消除业务归属判断。负责人仍要确认 Feature 的边界、复用关系及跨仓影响；变化是这些信息写入唯一的功能/Change 来源，不再为了接入另一种模型单独维护 catalog 映射。

## 吸收 OpenSpec 的哪些优点

1. **当前完整规格与候选变更分开。** 当前功能能独立读懂；Patch 记录改动意图和范围，不让读者每次叠加全部历史。
2. **行为要求和可观察场景。** 借鉴 Requirement/Scenario 的明确性，结合已有稳定锚点把需求、验证及变更关联起来。
3. **显式差量。** 区分增加、修改、移除、重命名；修改既有要求时保留变更后的完整要求和仍适用场景，避免局部替换丢失行为。
4. **意图、技术方案、执行与验证各有职责。** 借鉴 proposal/spec/design/tasks 的分工，但不强制每个小 Patch 都产生四份新文件；沿用已有 change.md 和 plan.md，复杂设计再按需独立。
5. **结束时维护现行规格。** 纳入的结果反映在完整主规格里，历史保存决策原因、适用基线及证据，而非长期靠互相覆盖的补丁解释现状。
6. **可机械校验的条件交给工具。** Skill 给 Agent 路径与写作指引，脚本/CI 检查结构、关系、版本和缺项。格式正确不等于业务验收通过。

这些是设计借鉴，不要求复制 OpenSpec 的目录、命令名、Markdown 解析器或完整 schema 引擎。固定参考：[默认 schema](https://github.com/Fission-AI/OpenSpec/blob/87c3595ace6a2e22957f39ebe5b74c2f2316e0cb/schemas/spec-driven/schema.yaml)、[规格与变更概念](https://github.com/Fission-AI/OpenSpec/blob/87c3595ace6a2e22957f39ebe5b74c2f2316e0cb/docs/concepts.md)。

## 建议的独立结构

优先延续当前 map-delivery 的目录语义；这里是候选设计，不重命名真实文件：

```text
map/
  README.md                              # 从功能来源生成导航
  data/
    telemetry-ingest/
      README.md                          # 功能入口；索引区块自动生成
      spec.md                            # 唯一完整功能规格
      changes/
        PATCH-<仓库>-<Issue>_<名称>/       # 一个主 Change，保持稳定路径
          README.md                      # Hub，跨仓产物与证据入口
          change.md                      # 意图、差量、影响模块、基线
          plan.md                        # 实施与验证检查点
          review.md                      # 独立 Review 实际发生后建立
          evidence.md                    # 真实验证完成后记录
```

一个 Feature 可以横跨后端、前端和设备侧代码；其规格与上下文入口由该功能统一组织。其他功能拥有的规范仍引用其权威位置，不复制整段。一次跨模块交付保留一个主 Change，由 affected_modules 建反向索引。

地图从真实模块路径、主规格标题和已有元数据派生；业务信息不足时补在其来源中。现有项目的 module 字段承担路径身份，未来如果确有模块移动需求，需要显式稳定 ID/别名迁移方案；不能假装已有工具自动支持任意重命名。

历史首先通过已有生命周期记录在同一稳定路径中呈现，**不必为了“归档”再移动 Change 目录**。这能减少上个样例的归档路径适配。生效、合并、部署仍分别记录；需要正式封存的资料继续遵守项目 archives 不可变规则。

## 仍然必须补齐什么

- **索引生成。** 当前项目工具主要检查导航存在，不能把“检查了双向链接”误称为“已经自动生成链接”。建议扩展现有入口，生成模块索引、跨模块反链和历史视图。
- **主规格更新与过期基线检查。** 第一版可由 Agent 根据选定 Change 准备完整主规格差异，R 独立审查，再按项目规则合入。必须记录所依据的文档版本并对过期/并行修改做检查；不要一开始承诺通用的自动语义合并。
- **候选与证据的一致性。** 延续现有精确版本规则；候选或验收场景变化后重做受影响验证和 Review，不能只改 status 通过门禁。
- **跨模块修改的准确范围。** 当前 affected_modules 表达关联范围；若要自动检查每个受影响模块的并行冲突，需进一步明确每个模块的目标要求/锚点，不能从主模块 target_anchors 推断全部范围。
- **中断与重复执行。** 初始化不覆盖已有内容，生成可重复执行，检查只读；规格更新和来源记录放入同一可审查候选。取消、替代和退役需保持历史可读。
- **通用能力与项目规则的边界。** Gitee Issue、Ming 版本证据和激活规则属于项目治理。复用现有校验，不复制成第二份通用规则，也不因独立化删除严格约束。

“独立实现”因此应当是一个有明确数据约定的 Skill + 小型工具 + 项目校验入口，而不是把所有责任写成长提示词。成员仍可用不同编码 Skills；统一的是产物和可执行验收。

## 最小试点如何判断值不值得

用同一项遥测功能验证：新增 Feature、一个跨模块 Patch、一个无行为变化的修复，再加入一次并行修改或过期基线的退回场景。

通过条件：

1. 新会话只从功能入口即可找到当前规格、选定候选、实现位置和实际证据；不需要理解第二种文档模型。
2. 跨模块 Patch 只写一份，相关功能反向索引自动更新；现行完整规格可独立阅读。
3. 结束、替代或退役后旧入口仍可定位，候选不被误当成已发布行为。
4. 过期导航、遗漏关系、锚点冲突及失效版本证据能被检查退回；语义问题仍交独立审查。
5. 相比已有 OpenSpec 导航样例，记录真实人工字段、编辑文件数、交接失败与返工次数后，维护负担确实减少。

若独立方案开始要求团队重建通用 schema 引擎、完整多宿主适配或复杂的自动合并器，或同等规模交付需要更多人工记录，应缩减范围或回到“单入口封装 OpenSpec”的备选。不能只凭目录更顺眼就宣布成本已降低。

## 责任边界保持不变

- map-delivery：功能规格、Change、文档发现与交付产物组织。
- LoopX：长程任务推进和恢复，不在文档中复制其完整运行状态。
- 可选 Skills：协助编码、测试、审查和研究。
- D/R/P 与 CI：按既定职责对候选、真实证据、最低合并前验证和发布前完整集成作验收。

下一步应先锁定最小文档契约及试点检查点，再实现被该试点证明必要的工具能力。本评估没有修改 Skill、业务规格、现行校验器或远端配置。

### 候选分工

下面是本团队的建议命名与职责，并非已经创建的技能，也不是天猫原始 SKILL.md 的复刻。

| Skill 候选 | 何时使用 | 主要负责的产物 | 关键边界 |
| --- | --- | --- | --- |
| map-specs | 澄清需求、新增 Feature、修改 Patch、退役、核对规格偏移 | 功能 spec、Change 及 Plan；维护与 Review/Evidence 的关联；调用索引工具 | 保存业务意图与已接受的规格演进；代码偏离时提出差异，不能自动把意图改成代码现状 |
| map-architecture | 接口、事件契约、数据模型、跨仓依赖或结构决策变化 | 当前架构/契约导航、必要 ADR、实现定位 | 记录结构与来源；引用业务规格，不复制业务规则，也不覆盖代码/schema 的机器契约 |
| map-runbook | 验证环境、排障步骤、发布恢复流程或可复用经验发生变化 | 可执行 runbook、环境复现入口、经确认的团队经验 | 记录适用版本、命令和验证结果；个人原始对话不默认进入团队资料 |
| map-changelog | 交付形成可核实结果，或准备发布说明 | 从 Change、Git、PR、验收记录派生的历史视图/变更摘要 | commit、合并、验收和部署分别标明；不维护第二份任务状态或擅自宣称上线 |
| map-vendor | 需要引入、更新或理解外部 SDK、协议、示例 | 带来源与版本的外部参考资产及索引 | 原始材料可追溯；同步范围明确；不把第三方建议直接升级为本项目需求 |
| map-wiki | 调研、方案比较、Blueprint、尚未定案的经验整理 | 有来源的探索笔记、比较结论、候选蓝图 | 与现行业务规格区分；选定方案后通过 Change 接纳，不维护另一份正式要求 |

Review/Evidence 仍位于当前 Change 的唯一位置。编码、测试与独立审查可以使用现有 tdd、code-review 或成员自己的方法；它们的结果遵循统一的产物与版本约定。map-specs 连接这些结果，不因此获得替 D/R 自我验收的权力。

map-delivery 可以保留为整套工具与技能包的名称。原 `$map-delivery` 如已有调用方，先保留兼容入口并缩减为定位/选择职责；是否长期保留这一入口由宿主发现和使用测试决定。它不应成为强制按顺序调用六个 Skill 的新调度器。

### 共享什么，独立维护什么

共同契约只保存一份：文档根定位、功能/Change/要求身份、现行与候选的含义、来源引用、候选版本及 Review/Evidence 约定、项目校验入口。具体项目的严格规则继续由项目维护。

每个 Skill 只写自身独有的触发条件、必要输入、产物职责、写入范围和完成标准；共享协议通过可定位的来源引用，不粘贴六份。共同的索引、链接检查和候选校验使用同一工具入口。打包与分发时一起校验依赖可达性，不能假设某个兄弟 Skill 恰好安装在固定相对路径。

一次文档变更只更新它的权威来源；其他 Skill 读取该来源或生成索引。知识之间可以互相引用，写作职责不是文件访问权限隔离，真正的写入范围和审批仍由项目规则及工具执行。

### 用小数温度需求走一次

1. map-specs 找到遥测 Feature，起草小数支持 Patch，写出整数兼容和小数保留等验收场景；业务责任人确认意图。
2. D 使用合适的编码/TDD 方法实现，提交与真实候选版本绑定的 red/green 和验证证据；R 独立审查。无需为了进入下一步换一套规定的编码 Skill。
3. 如果消息 schema 或跨仓契约确实变化，使用 map-architecture 更新对应来源/导航；若无结构变化，该 Skill 不产生文件。
4. 如果复现环境或排障步骤发生变化，使用 map-runbook 更新已验证步骤；没有新知识就不要求写一篇总结。
5. map-changelog 在有真实交付事实后生成相应摘要；最低合并前检查和发布前完整集成沿用既定验收。只有发布证据能支持“已发布”。
6. map-vendor 和 map-wiki 在确有外部资料或调研需要时使用，本需求可以完全不触发它们。

功能页把上述产物连起来，使新会话仍从一个业务入口发现上下文。

### 第一版规模与检验

先声明六类知识职责，优先试点 map-specs、map-runbook、map-changelog；map-architecture 按接口/数据契约变化启用，vendor/wiki 随真实研究需要补齐，不为了数量先搭全六套自动化。

同一需求下检查：Agent 是否能选对 Skill、是否只改目标产物、未触发的 Skill 是否保持无操作、六类知识是否引用同一业务规格、输入版本变化是否使受影响结论失效、索引与门禁是否在不使用特定 Skill 时依然可执行。尤其验证独立 Review 来自另一责任人/Agent，而不是把同一 Agent 调用另一 Skill 当作独立性。

提交时可以运行便宜的确定性检查；知识更新由真实变化触发，语义偏移在候选审查中显式呈现。先验证宿主如何发现和执行这些入口，再考虑 Hook 或 CI 联动，不承诺单靠 Skill 文本会自动执行全部动作。

## Question

根据实际人数、职责与现有交付平台，确定需求验收人、实现责任人、独立评审人与发布责任人的职责及可兼任边界；定义少量关键节点的输入、产物、通过与退回条件。明确个人验收、PR 审查、业务验收各自证明什么，环境/代码/spec 变化如何使证据失效。不得把 Agent 自报完成等同于人工或团队验收。

## Context

本票据确定可复用的责任分配和验收安排；实际姓名在每条 Delivery Issue 认领，真实需求与验证入口在试点票据实例化。本地仓库约定与接入缺口已核查，见走查材料；服务端 CI 启用状态仍需在接入时核实。

## Comments

2026-10-10：用户要求继续此项决策，按一条 IoT 需求从 OpenSpec、PR 到集成验收具体化责任、产物、证据、通过和退回条件，并减少文档维护。已由 root 领取；先形成可审阅的走查草案，具体人员和未确认的验收规则不视为已批准。

已形成 [一条 IoT 需求的责任与验收走查](../assets/04-responsibility-acceptance-walkthrough.md)：三个责任角色、四个关口、一轮退回重交，以及现有文档仓/代码仓的引用顺序。示例与版本均为推演，没有执行真实交付。草案提出时，两项政策等待用户选择，票据保持 claimed；随后得到下述明确答复。

## Answer

2026-10-10，用户对两项政策作出明确选择，本票据解决：

1. **交付与审查由两位成员独立承担。** D 对交付负责，R 对最终 PR 审查负责，两者分离；P 负责业务意图和验收，可以兼 R。成员使用的工具和 Skills 可以不同；具体姓名只在 Delivery Issue 认领。
2. **最低必需验证在合并前，完整业务集成在合并后、发布前。** 现行变更面要求的合并前 integration suite 仍须执行；PR 合并和业务验收分别记录。完整集成未通过，本次交付不据此发布。

责任、产物、证据、通过和退回路径的配套说明保留在 [走查材料](../assets/04-responsibility-acceptance-walkthrough.md)，此处不复制细表。实际候选、环境、人员与业务场景仍需在试点实例化。本次只完成方案决策与文档回填，未实施业务、配置 CI、迁移 OpenSpec 或改变生产授权。

## 在现有仓库上形成完整分层

[AGENTS.md](../../AGENTS.md) 已指定 `skills/map-delivery` 为团队唯一源码，[SDLC 原则](../SDLC/00_目标与设计原则.md) 已要求避免投入重平台。建议增加缺失的执行门禁及证据绑定，继续使用当前 Agent 宿主。以下是待落地的职责安排，不是已存在的全部功能。

[map-delivery 的现有协议](../../skills/map-delivery/references/workflow.md)已支持跨仓 `repository_heads`、完整 40 位 `base/exact_head`、独立 Review/Evidence 和激活校验。PoC 的暂存 tree 是提交前的内容身份，不能冒充该协议要求的 commit SHA；提交后必须读取真实 commit，并将候选 tree 与 commit tree 对账，再产生正式交付证据。

[产品 Makefile](../../../ming-iot/Makefile)已有 `verify-fast VERIFY_SCOPE=...`、`verify-pr`、`verify-integration` 和 `verify-release`。按任务选用已有入口并记录命令、环境、退出码、所测候选和结果摘要，不包装一套同义测试。快速检查不能替代集成验收；存在数据库、并发或公共接口变更时，补相应真实行为测试。

[现有 hooks 配置](../../hooks/hooks.yaml)为 `hooks: []`，且列出的内置生命周期 Hook 被禁用。PoC 的临时 Git Hook 与这份配置不是一回事；本次不据此宣称成员宿主、业务仓或远端已经接入门禁。

## 一项真实任务如何通过五阶段

| 阶段与责任人 | 输入 | 必须交出的证据与通过条件 | 退回条件 |
| --- | --- | --- | --- |
| 1 来源快照：Controller | 精确任务记录/PRD/文字/截图及可访问来源 | 来源包、内容摘要、读取时间；说明事实与候选线索；引用真实交付标识。 | 来源不可读、记录不唯一或来源更新，重新取证。 |
| 2 澄清：开发者与 Controller | 来源包和未知项 | 目标、非目标、逐条 AC、风险理由和实际确认记录；沿用有效的既有授权，不机械重复询问。 | AC 模糊、来源变化或新增范围，回到澄清。 |
| 3 工作区：开发者决策，Controller 固化 | 批准范围及候选仓库 | 仓库清单、identity、base/HEAD、目标分支、允许路径/命令；相关选择有依据。 | 仓库、范围或基线漂移，重新确认受影响选择并使旧回执失效。 |
| 4 实现：Worker | 冻结工作包和验收条件 | 失败用例及 red 结果、范围内最小修改、green 结果；交回待审候选，不自行提交。 | 测试前提不成立、需要扩范围或碰到治理资产，交回 Controller。 |
| 5 验证交付：Controller、Reviewer、开发者 | 精确候选与测试结果 | 必需验证通过；独立 Review 无未解决 P0–P2；输出交付材料和具体动作计划；仅执行已授权动作。 | 证据缺失/过期、候选漂移、授权不匹配或外部回读不符，阻塞对应动作。 |

Controller 最终说明运行终态及证据位置，并分别记录验证、提交/推送、部署、人工验收状态。`ready` 只表示该 Workflow 要求的交付证据齐全；它不自动映射为 `map-delivery` 的 `effective`，后者仍须满足既有激活及远端事实核查规则。

## 本地 PoC 的交付边界

[examples/harness-minimal](../../examples/harness-minimal)承载本次独立实现的最小样例，聚焦 task/source/AC、scope/branch/base/暂存 tree 绑定、自动验证回执、独立 review 声明、commit planDigest 授权、`pre-commit`/`commit-msg` 失败关闭和脱敏 trace。具体命令及行为见该目录 README 和源码；本轮实际验证见文末。

演练仅在临时 Git 仓进行。正常路径应形成“冻结任务→修改及暂存→验证回执→审查回执→动作计划及匹配授权→Hook 复核→本地提交→核对 commit tree”的可重放记录。失败演练至少覆盖缺回执、过期、P0–P2 未解决、任务或分支/base/tree 漂移、计划摘要不匹配、提交信息不匹配，以及解释器/检查器缺失；记录退出码和拒绝原因，确认没有错误提交。

必须保留以下边界：Git 本地 Hook 可被 `--no-verify` 等方式绕过；可写 JSON 回执及自报角色不能认证真人授权或独立身份；摘要绑定检查内容一致性，不建立身份信任。正式强制能力需要可信执行主体、受保护的审查回执和平台合并门禁，不能由本地样例推导出来。

外部写入还需处理并发、幂等与失败恢复。原文写前重读和写后回读可以发现一部分漂移，但不能替代平台的原子条件更新；若平台没有可验证的 compare-and-set，必须明确竞态和人工接管条件。当前没有远端 CI、飞书、部署真实集成，也没有完整 Workflow 状态机。

### 职责与现有资产衔接

沿用 [现有 SDLC](../SDLC/00_目标与设计原则.md) 的“业务地图、正向 delivery、反向 review”分工，先确定职责和数据契约，不立即改动 canonical `map-delivery` 或另装同名 Skill。

| 职责 | 消费与产出 | 决策边界 |
| --- | --- | --- |
| 业务地图 / 领域负责人 | 维护领域入口、业务规则、接口、历史决策和验证条件；检查知识是否仍适用。 | 提供领域事实和约束，不代替具体需求的授权与验收。 |
| delivery / 交付负责人 | 读取批准来源和当前阶段任务；产出候选材料，按 findings 修复，附验证结果与下一步建议。 | 不能自行把候选标为已验收，不能通过修改 AC 消除失败。 |
| review / 独立审查者 | 对照来源与阶段标准检查候选，输出 pass/changes_required、逐项 findings 和证据定位。 | pass 是针对特定内容的回执，不是任意修改阶段的权限。 |
| 薄协调器 / Controller | 检查依赖、摘要、验证回执和必要人工决策；唯一负责持久化状态迁移。 | 按预定义迁移表放行；不自行生成“已审查”事实，也不代替产品验收。 |

两个 Skill 的名称或分工本身不能证明有两个独立 Agent、独立上下文或权限隔离。本地设计建议 Reviewer 使用独立上下文和只读权限，协调器核对其证据后提交状态转换；是否做到隔离仍须用实际运行记录和权限检查验证。

文档仓仍是 Spec、Change、Plan、Review、Evidence 的权威来源。阶段状态只记录已批准文档的仓库 identity、提交、路径/锚点与摘要；候选产物放在对应交付位置，不再复制另一份“最新规格”。未批准的候选可以被审查，但不能当作已批准输入供下游执行。

### 阶段合同与最小试点

| 阶段 | 输入与候选产物 | 审查重点及放行条件 |
| --- | --- | --- |
| 需求澄清 | 已批准来源引用；候选目标、非目标、AC 和未决问题。 | 每条 AC 能追溯来源且可验收；冲突或必要决策未解决时不进入方案。 |
| 方案 | 当前需求版本与业务地图；候选接口/数据/影响范围、风险和验证方案。 | 方案覆盖 AC、边界和失败路径；缺少必要领域事实时记录依赖并阻塞。 |
| 任务拆分 | 已通过审查的方案；候选任务、依赖顺序、仓库/路径范围、验证命令。 | 每项任务可执行可验收，依赖明确；批准后再向实现者发工作包。 |

每个阶段至少保存 `stage_id`、`input_refs`、`input_digest`、`artifact_refs`、`artifact_digest`、`validators`、`findings`、`next_action` 与审查回执。验证项应记录实际命令/检查器版本、退出结果和证据位置；无法自动判断的业务条件应显式列为人工检查，不能用字段齐全冒充语义正确。

协调器依据依赖关系和回执判断是否迁移：缺依赖为 blocked；候选未审查为待审查；审查不通过交回 delivery 修复；只有当前输入、产物摘要和必需验证均匹配、阻塞 findings 已处理、必要决策已完成时才进入后续阶段。`next_action` 是候选建议，不能直接控制状态。

内容变化后重算摘要，使对应审查及所有受影响下游回执失效；保留旧版本供追溯，但不得复用旧 pass。失效范围按实际输入依赖传播，并回到最早受影响阶段。状态记录需要校验预期旧版本并串行更新；文件加 Git 解决持久化，不天然解决并发与授权。

每次修复应说明解决了哪些 finding、修改了哪些产物、重跑了哪些验证；审查者复核后再出新回执。试点开始前固定尝试次数、时间/费用预算和人工停止点；重复失败没有新证据、需要改变需求或超过预算时停止自动推进，留下原因与接手入口，不设置无限重试直至“无 bug”。

### 怎样验收这项补充

先用一条真实小需求演练：审查故意遗漏的 AC、错误影响范围和不可执行任务，确认它们在进入代码实现之前被拒绝；修正后验证能恢复推进。再修改已审查的需求，确认旧方案与任务回执失效；缺少依赖时确认不会跳阶段。记录实际输入、产物、回执与迁移，明确哪些判断来自人、哪些来自 Agent、哪些由脚本执行。

观察每阶段的工作时间、等待时间、返工次数、审查发现和交付验收结果；人工介入区分必要业务决策与环境故障/信息缺失/流程失败。目标是减少可避免等待和重复返工，保留必要决策与责任，不盲目追求零人工；本次不据此调整团队编制或取消岗位。

这一补充目前只有设计与验收建议：没有新增两个生产 Skill、阶段协调器、Zeta 接入或领域知识图谱，也没有完成上述真实需求演练。下文原有阶段计划与验证记录仍按各自实际范围成立。

## 分阶段落地与验收顺序

| 阶段 | 责任与交付 | 验收及进入下一阶段的条件 |
| --- | --- | --- |

| C 正式仓与 CI | 仓库管理员和工具维护者把同一检查器接入本地 Hook、CI 及保护分支；单独验证工具发现和版本。 | 缺少/失败检查实际阻止合并；检出真实候选和正确基线；能够证明回执产生者与被审内容，保留回滚方法。 |

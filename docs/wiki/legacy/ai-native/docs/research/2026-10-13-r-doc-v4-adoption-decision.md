# r-doc v4 复核、独立审查与采用决定

状态：第二阶段的候选复核与采用评估已完成，**退回 v4 正式采用**。继续保留小范围 fork 作为修补验证载体，暂不转向全面自建。下一项已授权工作是依据退回结论完成 GitHub 迁移准备与路线调整；没有安装团队默认技能或执行远端迁移。

## 决定及依据

v4 修复了上一轮的带标题链接缺陷，也实现了项目元数据适配和定点检查入口。但 Kafka 三次同条件运行均超时，独立子仓复核也有一次超时；独立审查又确认两项 P2。正确产物、无越界及预算内正常结束尚未同时得到所需证据，因此不能采用为团队默认流程或审计门禁。

当前工程路线仍是**有边界的小 fork 修补验证**。尚未证明需要长期绕过大部分上游核心流程，也没有自建对照和维护成本证据；不能由 v4 未通过直接推导全面自建更好。同时，不承诺长期维护完整 fork，不自动扩大为六个新 Skill。父仓知识契约、原有项目校验器与唯一权威文档仍是设计基础，工具可替换。

这次“退回”已处置当前候选的采用问题；两项 P2 保持未修复状态，不能靠记录限制转为通过。下一候选若继续推进，先只修复这两项、补受影响回归，再预先澄清评测字段和任务边界。该建议不抹去本轮失败，也不把一轮接一轮的试验预设为必然成功。

## 最终候选和既有回归

候选为 `rdoc-project-v4`，固定上游为 `bc23420d7df5ec1d2c5fb45e066c919790ab9cf9`。64 个源码文件与已有 161 项回归通过时的版本一致；本轮复核了源码和证据指纹，没有重跑这套未变的回归。

相对固定上游，文本差异为 13 文件、+607/−78 行，含测试和治理说明移动。这只是补丁规模，不是长期维护人时。旧 v3、原始失败、v4 输入、判据和候选均保持不变。

项目 profile 消除了原有 110 项字段及 22 项状态不兼容；103 项导航问题和 6 项敏感内容告警仍保留。兼容检查通过不等于全库审计通过。项目原生规则继续负责身份、审批状态与精确 Head 语义；未执行 map 激活的 Git 门禁或产品测试。

全部实际使用 `gpt-6-astra / xhigh`、Codex 0.154.0，串行执行，每条件一次，未自动重试。沿用旧真实历史输入、提示、预算和已修复的冻结判据；本批 case YAML、配置和候选指纹均在首次模型运行前固定。

原始结果为 **4 PASS、1 FAIL、1 ERROR**；全部六次来源、Git 控制文件、实际安装 Skill 和提示核对通过，共核对 14,659 项文件及 Git 控制文件指纹，没有发现额外业务文件。六次均观察到读取 Skill，未出现全库审计调用。已生成的报告没有因为资料缺失而把父仓 HEAD 当成产品版本，也没有把旧历史描述当成当前错误清除。

已同步快照的 FAIL 来自报告字段约定歧义：判据要求 `code_field=firmwareModuleCode`，模型填了 Go 成员名 `FirmwareModuleCode`，同时通过 `code_json_field` 给出正确 JSON 名。三个 schema 的判据差异仅在此字段，提示未明确命名层级。主代理与独立审查均支持这一解释。**保留原始 FAIL；它不能证明业务语义判断错误，也不能改判成完整通过。** 下一版评测应事前分别定义 Go 成员名和 JSON 字段名。

独立子仓超时前完成 14 条命令，没有写出报告；根因未确定，不归因为某个 Skill 缺陷或网络问题，不单独加时重跑。六种条件只有各一次，且旧批次使用 ultra，不能把跨批耗时变化归因为 v4。旧 OTA 定点维护未重复执行，相关变更使用新的 Kafka 真实维护任务检验；也未覆盖网关、前端或旧 revision 但语义未变的完整场景。

## 独立审查及缺口处置

独立只读审查实际使用 `gpt-6-astra / xhigh`，338.018 秒正常结束。核对 64 个候选文件、16 份关键证据及其引用的 110 项证据，审查副本未变。它是独立上下文的模型审查，不等于人类批准或产品验收。

| 发现 | 核实结果 | 当前处置 |
|---|---|---|
| 旧 P2：尖括号链接带标题漏检 | 已修复，有正反回归及源码绑定 | 关闭该旧缺陷；不据此宣称全部链接检查无缺陷 |
| 新 P2：锚点目标读取越过排除/受保护边界 | `safe.md` 链接 `private/.env.review.md#target`，配置排除 private，定点检查仍读取目标且没有 finding | 阻止采用；下一候选须在读取目标前检查边界，并报告锚点未验证 |
| P2：无效 version 类型导致异常 | `version: []` 在 baseline 和 v4 均触发 TypeError，无法形成结构化配置报告 | 阻止采用；下一候选先检查类型并输出配置 finding；它不会假通过，但会中断工具 |
| 已同步快照报告字段歧义 | 业务判断正确，机器字段与判据不一致 | 原始 FAIL 保留；后续事前明确字段，不放宽本轮判据 |
| Kafka 与独立子仓运行未完成 | 原始 ERROR 与产物情况已核实 | 不接受运行验收；未来明确分开定点维护与显式全库审计条件 |
| 全库基线及未覆盖范围 | 导航/敏感告警、网关/前端、完整知识生命周期等仍未验收 | 不启用全库门禁，不宣称六类知识管理已完成 |

主代理用纯内存合成数据复现两项新审查发现，没有读取真实受保护文件，也没有改候选。候选被冻结退回；“审查任务完成”与“发现已修复”分别记录。

## 迁移准备的下一步

继续已授权的内容归属、仓库参数与历史/链接映射准备，产出可审查清单。保留独立产品仓的历史、PR、权限与发布；IoT 专用约定归父仓，可复用工具保留独立来源。OpenSpec 仍是待定方案。

只读盘点发现：当前产品仓干净，文档仓及 ai-native 有已有未提交内容；本地未发现同名 mqtt-gateway，前端仓身份未明确；当前文档入口仍把 iot-doc 声明为正式架构来源。准备清单必须处理这些实际边界，不能默认清理未提交内容、猜测子仓身份或复制出另一份架构权威。

当前 v4 采用条件未通过，目标组织、父仓名称、可见性及权限也未确定。依第二阶段说明，先交付迁移准备和路线调整，不部署未通过候选。若后续改变采用路线或推进实际迁移，须使用新的明确条件与对应证据。

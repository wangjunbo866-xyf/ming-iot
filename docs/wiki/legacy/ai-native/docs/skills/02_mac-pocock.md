# Matt Pocock

mattpocock安装命令： npx skills@latest add mattpocock/skills

# SuperPowers和Matt Pocock怎么选
新手可以使用SuperPowers快速上手，如果想要提升Skills并精细化操作，可以使用Matt Pocock
**共识**：俩家的开发流程是一致的，都焊死 TDD，都先写计划再动手，都信文档落盘。分歧从来不在要不要流程，在流程由谁发起。

**分歧**：Superpowers 是自动接管派：模型每次响应前先查一遍技能表，技能全程可见，brainstorm、写计划、派 subagent 一条龙强制执行。Mack Pocock库是手动调用派：技能完全隐身，你敲名字它才出现。

Matt 有个判断：上下文窗口真正好用的区间只有大约 15 万 token，再长就滑进愚蠢区，马虎、健忘、爱犯错。

## Mack Pocock痛点
开销太大：
一是常驻开销。技能索引一直挂在上下文里，等于往 15 万 token 的聪明区塞了件搬不走的家具，长会话肉眼可见地变笨，就是前面算的那笔自动化账

二是触发不可控。该查技能时它没查，不该接管时它把一个五分钟的改动拉进全套 brainstorm，方向盘说抢就抢

三是日常太重。方法论为大项目设计，中小任务也被推着走完全套仪式，仪式感压过干活本身

四是库太杂。技能越滚越多，索引跟着变长，触发面跟着变乱，质量还参差；这边 25 个精干技能，反而个个得心应手。

# Matt Pocock痛点
技能调教复杂：
Matt 赌判断力必须留在人手里，十多个技能，开发者要凭借自己的认知来自己手动调用。


# Matt Pocock
Matt Pocock 有着比 SuperPowers更多的技能，虽然技能调教复杂，但是利用好这些技能，不仅更加灵活更能达到超越SuperPowers的效果。

## 主流程：
/wayfinder → /to-spec → /to-tickets → /implement → /code-review

# wayfinder
规划本身大到一个会话装不下时，它会先画一张决策地图，上面发的不是实现票，是决策票：技术选型没定，发张票让 prototype 去打样；心里没底，发张票让 research 去查资料

地图上所有子问题闭环，再跑一遍 to-spec，规范落到 GitHub、Linear 或 Jira 这类 issue tracker，拆成工单分给各个会话去啃。几十亿 token 的项目，就是这么一口一口吃完的

它拆的不是做什么，是什么还没想清楚。这不就是产品经理的老手艺，先降不确定性再投入生产，只是头一回被编码成了流程

合并冲突那招更狠，信条是切斯特顿栅栏：不知道一道栅栏为什么立在那，就先别拆，每处改动溯源到最初的变更理由再动手。AI 的默认人格是个自信的实习生，你不给它先问为什么的规矩，它就把代码库当草稿纸

AI 把写代码打到了地板价，于是瓶颈往前挪：判断、决策、把话说明白，这些以前被实现难度掩护着的活，现在全裸奔在最前面。

## diagnosing-bugs
diagnosing-bugs 给疑难 bug 装了严格的反馈循环，AI 诊断问题不再靠猜，这可是模型出了名的弱项。wizard 管只有人能干的配置活，比如开通 AWS，它生成引导脚本，自动打开网页、记下环境变量、提示每步 CLI 命令，你只管跟着点

## improve-codebase-architecture 
定期体检，扫一遍仓库输出可视化报告的html，专攻测试套件和模块隔离这类长期质量

# handoff 
会话快满或要换 agent 时，handoff 把对话压缩成一份 markdown 交接文档传下去。

# to-questionnaire
grill 卡壳时，to-questionnaire 把问不出来的问题打包成问卷，发给唯一能回答的人，带着答案回来接着聊

# wait-what
专治没听懂，让 AI 换种方式重讲一遍，顺手统一领域用语。想学习就用 teach，丢个仓库地址过去，直接生成一套 HTML 入职课程（宝藏技能）。

# writing-for-agents
把 Matt 写文档的手艺编成了技能，专治 AGENTS.md 写不清楚

开局记得跑一次 setup-matt-pocock-skills，issue tracker、分诊标签、文档存放位置一次配好，后面 to-spec 落规范才有地方去。


前面聊的都是认知，这里把一次开发工程各环节该用哪个技能收成一张表

| 阶段     | 敲什么                                                | 它负责什么                                                   | 这么做的好处                                   |
| :------- | :---------------------------------------------------- | :----------------------------------------------------------- | :--------------------------------------------- |
| 想清楚   | /grill-me 或 /grill-with-docs                         | 连环追问对齐需求，后者顺手产出 ADR 和术语表                  | 返工消灭在第一行代码之前，决策还能传给下个会话 |
| 动手写   | /implement                                            | 按对齐结果干活，内嵌 TDD 红绿循环                            | 小步验证，代码天生带测试                       |
| 自动收尾 | code review，implement 写完自动触发                   | 先查仓库编码规范，再查有没有漂移出设计方案                   | 漂移当场被抓，不用人盯                         |
| 拆大活   | /to-spec 加 /to-tickets                               | 前者把拷问结果落成规范存进 issue tracker，后者拆成一串声明了依赖关系的工单 | 超出 15 万 token 的项目也能分窗口接力          |
| 超大规划 | /wayfinder                                            | 先发决策票，让 prototype 打样、research 调研，全闭环再发实现票 | 先清不确定性再投产，躲开方向性返工             |
| 日常保养 | /diagnosing-bugs、/resolving-merge-conflicts、/wizard | 诊断疑难 bug、溯源合并冲突、引导人做配置                     | 补上模型最弱的三块                             |

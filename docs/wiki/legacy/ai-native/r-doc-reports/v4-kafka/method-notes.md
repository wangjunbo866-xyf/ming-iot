# 执行后分析口径

本文件补充结果读取方式，不修改已经冻结的用例、时间预算、候选技能、输入或判据。原始 runner 结果始终保留。

## 完成与正确性分别记录

用例正常退出并通过冻结判据，才计入原始通过数。超时用例即使已经生成正确文档和报告，仍计为 ERROR。对保留工作目录执行相同冻结判据的结果，另存为 `*.posthoc-grade.json`；这只说明超时结束后留下的产物，不代表 Agent 完成，也不覆盖原始判定。

这里的产物补充核对由评测主代理在只读过程内完成。它与原始 runner 判定分别留存，但不替代后续 Todo 要求的独立审查。

原判据将 `.agents/`、`.codex/` 视为运行器安装目录。独立分析额外列出这两个目录中技能安装路径和 `.codex/config.toml` 以外的文件，以核对任务原有的修改范围要求。若出现额外业务笔记等文件，要保留原始判定并单独报告范围问题，不静默改写评测规则。

## 成本数据来源

首个超时用例的 `result.json` 将 input/output Token 记录为 0，但实际 Codex 会话中存在 `token_count`。因此，框架的 0 不解释为无消耗。

分析按每次独立会话读取最后一条 `total_token_usage`，分别列出输入、缓存输入、输出和推理输出。累计输入包含重复上下文，缓存输入是输入的组成部分；推理输出是输出的组成部分，不重复相加。超时用例的最后一次记录可能早于终止时刻，只能称为“最后观测用量”，不能当作精确最终账单。没有价格或计费证据时不换算金额。

耗时使用原始用例 `duration_ms`，外层 launcher 耗时另列。命令数以实际轨迹中的已完成 `command_execution` 计数，和框架 max_turns 不是同一概念。工具是否被执行需结合完整命令核对，不能把读取脚本的命令计为运行了脚本。

第六次运行（无技能 r2）正常完成。框架报告 input_tokens=1,582,623，而实际会话累计输入为 825,503、其中缓存输入 757,120、输出 12,995、累计总量 838,498。框架的输入值刚好等于会话输入再加一次缓存输入。因此，报告使用会话口径并保留框架原值，避免把两种口径混入同一成本比较。

## 推断边界

每组只有三次，属于描述性试验。强任务提示、相同项目适配配置、真实历史快照和截止时间共同定义本次场景；不能据此推断技能对所有任务的普遍收益。v3 不认识适配字段的现象按真实兼容性记录。旧 ultra 运行不纳入本次 xhigh 同条件统计。

首次 v4 样本执行了局部检查和全库审计。任务提示的“显式全库检查结果与局部结果分别报告”可能被理解为要求执行全库检查，而非仅规定执行后的报告方式。因此，出现全库审计可作为本场景的成本事实，尚不足以单独认定 v4 默认路由无效。保持本轮提示不变；后续独立评估应区分提示的影响与技能的影响。

第八次运行（无技能 r3）在读取阶段后长时间没有新的动作输出，最终超时，未更新文档或创建报告。保留原 ERROR，单列无产物及无输出区间；没有服务端或完整引擎错误日志，不能把它归因为技能缺失，也不能认定是网络故障。成本比较中的最后观测 Token 尤其不应解释为完成相同任务所需的 Token。

原冻结清单固定了提示、判据、引擎配置、候选文件及全部来源摘要，但没有另列 case YAML 的整文件摘要。结束时核对三份用例定义相同、约束与配置一致、实际运行提示匹配冻结提示，并如实保留这一审计限制。

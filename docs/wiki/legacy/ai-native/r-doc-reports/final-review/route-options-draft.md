这份草案不作为最终验收。候选 v3、真实任务与原始 FAIL/ERROR 均保留，最终结论应以审查结果更新。

## 决策问题

要选择的是 Ming IoT 长期知识治理的维护边界。试点证明了部分工具和 Agent 行为可用，尚未证明完整 r-doc 工作流在现有项目中有稳定的额外收益。已有补丁共 7 文件、增加 145 行、删除 23 行；其中新增回归测试 90 行。不能把“当前小补丁”夸大成巨大的 fork 负担，也不能忽略尚未实现的适配能力。

| 选项 | 能保留什么 | 仍需解决什么 | 当前证据能支持的判断 |
|---|---|---|---|
| 固定上游加项目配置 | 入口/索引、链接检查、模板、通用安全检查 | 配置不能重定义 `document_kind` 与 `approved/pass`，也没有跨仓 revision 语义模型 | 可作辅助诊断，不能直接作为本项目统一知识门禁 |
| 长期维护完整 fork | 现有脚本、144项回归与全部工作流，当前补丁小 | 需要扩展元数据适配、版本化引用、历史/现行事实区分、低成本结束条件并持续跟进上游 | 技术上可行；三任务尚未证明值得承担完整工作流的维护与接入成本 |
| 逐步自建项目适配层，选择性复用 r-doc | 现有项目权威/元数据校验器；可复用已验证的解析和可达性思路、测试 | 自己维护最小上下文/版本契约和少量任务入口，收益仍需新任务验证 | 候选方向；避免重写通用 Markdown 能力，也不把通用治理模型直接变成业务权威 |

## 拟议的最小边界

1. 父仓维护业务知识、项目约定、版本组合和根 `AGENTS.md`。业务事实只在拥有它的正文中更新；入口和状态表引用它，避免再存一套状态事实。
2. 每条跨仓实现或验证证据至少能定位 `repo/path/revision`；需要离线复制时补原始内容哈希与来源。历史记录不因与当前代码不同而被改写；缺失子仓应返回未知。
3. 沿用现有项目的文档身份、批准、Review/Evidence 与精确 Head 语义。OpenSpec 仍是待定方案，不作为本轮前置依赖，也不另建一套竞争的 Spec 真相。
4. 确定性工具检查路径、链接、所有权、版本绑定和可复核引用；语义核验输出具体冲突与上下文，不把文件存在或日期更新当作事实正确。
5. 先建立“发现—定点更新—失效核验”三个有界入口。六个目录并不要求立即写六个 Skill；只有触发条件、输入、产物和写入边界确实不同才拆分。
6. 项目专用约定留在父仓；跨项目通用工具维持单独的可复用来源，以固定版本接入。保留 r-doc 来源、许可证与可复查补丁；是否贡献上游另行决定。

## 与原文章目录的对应

| 知识目录 | 首先明确的规则 | 本轮覆盖 |
|---|---|---|
| `specs/` | 谁拥有业务事实，批准与实现验证分别记录 | 单个真实 OTA 主题的发现与更新 |
| `changelog/` | 已做与待做可区分，链接到实际变更和证据 | 未单独验证完整时间线维护 |
| `architecture/` | 连接两端、接口与所属仓库/版本明确 | 仅相关接口字段与跨仓版本，不是完整连接地图 |
| `runbook/` | 适用环境、前提、实测步骤和失效条件 | 未验证运行手册执行与恢复 |
| `vendor/` | 选择性来源清单、固定 revision/哈希、更新影响核验 | 真实 OpenAPI 快照失效/对齐回放；不是完整同步工具 |
| `wiki/` | 人工维护边界；AI建议不自动成为正式规范 | 未验证人工协作或自动写入策略 |

- 报告正确并按预算结束才算运行通过。若只增加上下文和审计而无可见收益，应删减步骤或停止该路径。

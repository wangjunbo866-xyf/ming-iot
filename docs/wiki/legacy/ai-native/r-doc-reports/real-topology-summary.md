## 已证明的行为

- 完整父仓：定位正式 Spec、实际 API、历史 Evidence；分别核实父仓 gitlink、产品 HEAD 和历史验证版本，三者一致。
- 子仓未初始化：保留规格预期与 gitlink，但实际字段、产品 HEAD、版本一致性为未知；没有把向上解析得到的父仓 HEAD 当作产品 HEAD。
- 独立产品仓：找到实际接口，明确父仓及本次所需的研发文档不可用。产品仓虽含其它 docs 文件，不能据此认定目标正式规格或历史 Evidence 在场。
- 版本错配：父仓固定新提交，产品实际检出 `a6b28035c577131c1a4b0262af6ddbdc393104c5`；正确报告规格要求 `firmwareModuleCode/string`，在场代码仍为 `moduleCode/int64`，并拒绝沿用新提交的历史 PASS。
- 六份报告均有真实原文引用，未把历史测试称作本次运行；完整现场判据核验已有文件、Git HEAD 和 index 保持原样。

## 证据强度与剩余边界

这是指定 OTA 问题在真实完整树上的上下文发现验收，不是完整迁移、全库知识治理或产品验收。网关与前端仍未提供；文档导入后的全部相对链接、权限、发布和 CI 不在本次范围。父仓包装与故意切换旧版本属于可复现试验条件，业务材料本身来自真实历史。

完整父仓的原版和无技能也答对了，因此本轮没有证明二开带来准确率增益。单次样本、不同执行顺序、并行重叠和宿主网络告警限制耗时解释；不能把表中秒数当成稳定效率排名。本批固定同一 360 秒预算，实际 CLI 均为 0.154.0，沿用宿主默认模型和全局配置；报告未提供解析后的模型名。不同于上一批 240 秒预算，不直接作跨批耗时比较。提示和父仓入口已经给出较明确的读取边界，不能把成功全部归因于技能。

前一批 [切片试验](real-discovery-summary.md) 的原始 9 PASS / 3 ERROR 保留，不因本次成功升级。完整检出的新增维度只在完整父仓做三方对照，另外三种条件仅测试候选；全部条件的公平重复采样留待出现路线争议时决定，当前不作稳定成功率结论。

本轮没有改动候选功能源码。后续先做唯一权威文档更新，处理 `document_kind`、`approved/pass` 与 r-doc 默认元数据模型的不兼容；再做知识失效检测。版本错配识别不能替代任务三的“代码已变、现行文档陈旧、历史基线应保留”验证。最终候选的适用回归、独立审查和 fork/配置/自建选择仍在待办中。

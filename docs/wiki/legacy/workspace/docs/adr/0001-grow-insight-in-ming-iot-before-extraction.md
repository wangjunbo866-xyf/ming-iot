# 保留 ming-iot monorepo，Insight 随项目演进

用户已确认以 ming-iot 为迁移主体：保留其 monorepo，巡检先作为其中的独立业务模块，暂不增设 Git 父仓；MQTT 网关定位为跨平台复用的独立仓，其基本开发独立于共享 Insight。Insight 先在 ming-iot 承载项目知识和跨仓导航，以后按真实复用需求提取；对外交付仍承诺经验证的平台版本组合，服务可独立部署。本决策确认目标架构与资料迁入原则，实际仓库布局、工具入口和文档引用尚未切换。

## 取舍

当前优先把组件文档变更与组件代码变更放入同一仓内协作流程，暂不建设跨仓文档加载、正文同步或统一升级机制；未来提取会产生一次性迁移成本，但可以依据真实共性确定边界。复用的候选是稳定的文档约定、Skills 和检查工具，每个项目仍需维护自己的业务事实，不能因复用体系而省略必要内容。

MQTT 网关保留与组件版本一致的基本接口契约、构建和验证说明，ming-iot 的 Insight 导航到这些权威材料；网关基本开发不以 Insight 可用为前提。

巡检按独立业务模块约束接口与数据归属，同仓协作不等于允许任意跨模块依赖；独立产品交付或源码权限隔离成为明确需求时，再评估拆仓。当前只确定方向，不启动巡检实现。

## 后续提取的判断依据

先验证单仓文档导航与维护的收益，等实际消费仓出现后，再比较重复维护与公共工具版本、路径适配、升级协调和排错的总成本。提取后的工具应通过消费仓中的真实任务验证；仅有目录统一、安装成功或文件数量减少，不足以证明收益。

平台版本组合仍需登记并经过集成验证，不能因暂不设父仓而省略兼容责任；具体发布记录与验证机制留在实施设计中确定。GitHub 实际迁移、文档搬迁、共享工具发布与旧仓删除均未在本轮执行。

## 三个辅助仓的资料定位

用户于 2026-10-13 明确指出三个辅助仓均为多轮实验积累，应作为资料或 wiki 纳入 ming-iot，并在新文档体系完善后逐步退役。此前文件中的“研发权威”“正式架构来源”“唯一团队源码”等表述记录了旧组织方式，不得据此自动继承为目标结构的规范，也不得用来否定本次用户确认的方向。

| 来源 | 用户确认的定位 | 迁入与提炼原则 |
| --- | --- | --- |
| ming-iot-rd-docs | 多次实验形成的研发文档，包含 superpowers 或 Matt 相关流程产物 | 先按来源资料整理；依据当前代码、验证证据及已确认需求，提炼仍有效的规格、决策和操作说明；历史 Review/Evidence 保留原始范围与结论 |
| iot-doc | 早期讨论与设计文档 | 保留有价值的研究、候选设计和取舍；核实后提炼现行架构，不把设想写成已实现能力 |
| ai-native | Skills、Hooks 和公共 AI 工具的试验仓 | 试验记录归资料；仍需使用的工具单独决定保留、替换或停用，保留项通过验证后成为 ming-iot 中的实际工具入口 |

建议资料暂存于 ming-iot 文档体系内明确标注的来源资料区，例如 `docs/wiki/legacy/`，按原仓区分来源；目录名称及导入范围在实施清单中确定，不预先把三个仓完整复制进去。每份导入材料至少记录原仓、原路径、源提交或未提交快照标识，以及“待核对、已提炼、已过时”等状态和对应替代文档。

来源资料中的旧 AGENTS、Skills、Hooks 和安装脚本只作为被引用的材料保存，避免在默认代理发现或 Hook 执行路径内原样激活；采纳哪些约定与工具必须明确表达。每项正式知识保留一个权威正文，来源原文只承担出处和历史作用。

## 退役与清理条件

建议按来源仓分别完成以下条件后退役，不以“所有文档都整理完”为无限期前提：

1. 所需材料已迁入或被新文档替代，并有原路径到现位置的映射；过时、重复和无保留价值的内容有明确处置。
2. 需要保留的 Git 历史及未提交、未跟踪的重要内容已有可恢复备份；仅保存 Git 提交不能覆盖全部本地材料。
3. 产品、CI、Skills、Hooks、LoopX 与定时任务的实际依赖已迁出或停用，并验证从新入口可以完成所需工作。
4. 旧仓先停止日常写入并保留可恢复历史，再逐步删除重复材料与旧工作副本；旧仓退役不意味着必须删除仍有价值的引用依据和历史证据。

本轮只读核查发现六个 `map-delivery` 本机入口仍指向 ai-native，且 `ai-native/.loopx/bin/loopx` 仍存在；ai-native 还包含未提交和未跟踪内容。因此当前尚不满足删除该来源仓的条件。这些事实是实施清单的输入，不是继续保留三套活跃文档体系的理由。

# Raw Log 生产案例比较：先选择要保住的能力，再选择存储链路

研究日期：2026-09-05。状态：候选研究已完成并被 RFC 引用；本文不构成实施授权。

关联：`todo_4c8b90e8d03c`；[候选提案](../../proposals/2026-09-05-raw-log-feasibility-reassessment.md)；[RFC 草案](../../rfcs/2026-09-06-raw-log-deployment-profiles-and-reliable-v1.md)；[工业案例取证明细](2026-09-05-industrial-case-evidence.md)。

## 1. 本轮对上一轮结论的修正

上一轮主要比较产品文档，足以证明能力存在，不足以证明客户为何采用。本轮补充具名部署与参与者的工程说明。

目前不能得出“行业普遍全量保存协议解码前 Raw”，也不能得出“工业平台不需要 Raw”。更有解释力的是四个不同目标：接入故障恢复、数据分析复用、选择性诊断、历史重新解释。它们可能共用基础设施，但不是同一个产品承诺。

因此，上一轮“暂保 72h 双流”只能作为**未获批准变更前维持既有契约**的建议，不能作为商业可行性已经成立的结论。候选架构重新开放比较；当前代码与只读架构基线不在本轮修改范围。

## 2. 证据如何分级

- 第一方工程文章：可用于确认文章发表时的系统设计与作者说明的原因，不自动代表 2026 年仍使用相同参数。
- 客户联合署名、供应商客户案例：可证明具名采用；供应商收益描述不能视为独立评测。
- 企业现场参与者论文：可区分生产系统与实验替代方案，但不是公司正式承诺。
- 产品手册：用于解释机制，不能反推某客户已启用某功能。
- 未公开的数据保留期、故障恢复成功率、运维人数和 Raw 层独立收益，统一保留为未知，不套用产品默认值。

本研究是有边界的案例对照，不是市场采用率调查。公开资料对成功和大规模项目有选择偏差；品牌知名度不等于适合 ming-iot。

## 4. 为什么看起来矛盾的架构都可能合理

以下是对案例的比较推断，而非客户未公开的内部决策记录。

### 4.1 数据湖优先：付费价值来自后续分析，不一定来自协议追溯

BMW、Aker BP 所展现的核心价值是让研发、运维人员能跨系统使用数据。对这类需求，可查询的历史业务数据和正确关联的资产上下文，往往比保留所有传输字节更直接产生收益。

对 ming-iot：如果现场已有可信网关或 Historian 完成协议解释，平台主要做可视化、分析和模型应用，就应认真比较“规范化数据持久化＋有限诊断输入”。代价是无法用未保留的输入纠正网关之前的错误；必须写明责任边界。

### 4.2 事件平台优先：付费价值来自多个消费者独立演进

Bosch、DoorDash 的证据更适合回答“为什么需要可重复消费的稳定数据源”。新增算法、应用或消费者时，不必要求生产者重新提供数据。

但“新消费者从历史事件开始计算”比“按过去的模型、协议及所有权版本精确恢复历史行为”要求少。不能借前者的案例证明后者已被低成本解决。

对 ming-iot：若 ProtocolApplication 经常集中修正私有协议，保留解释前的输入有直接价值；若只是新增下游统计，Canonical 历史也可能够用。应先给出一次具体纠错过程，再选择保存层。

### 4.3 边缘与选择性采集：省的是进入中心前的资源

Siemens 案例提示训练与在线执行可以分开，但并没有披露其完整采集策略。由此可以提出、不能宣称已被该案例验证的候选：常态上传低成本业务点值，故障或调试窗口保留更丰富的输入。

这可能同时减少上行带宽、云存储和人工筛选量；代价是触发条件失误或未知故障发生时，所需输入可能根本没保存。对不可重现的一次性故障，不能把“以后打开调试”当作补救。

### 4.4 存储成本优先：缩短本地保留不必缩短恢复窗口

Uber 的选择揭示原方案比较遗漏的一条轴：本地热数据窗口与逻辑可消费窗口可以分离。另一个选项是归档消费者输出批量对象，但二者在消费者接口、恢复路径及运维责任上不同。

对 ming-iot：先算是否真的因 Raw 容量增加节点，再比较普通 Kafka、分层存储、可靠对象归档的总成本。不能因为对象存储单价低就忽略插件兼容、元数据恢复、远端读取和演练成本；也不应为了减少很少的磁盘创建一整套归档平台。

### 4.5 可用性优先：不是所有数据都值得同一种可靠性成本

Netflix 历史案例不是放松可靠性的通行证，而是“损失预算必须有业务理由”的实例。

对 ming-iot：重复高频趋势点、一次性故障事件、计费记录、控制执行结果，损失后果不同。可以比较分级服务，但降采样、丢弃或降低持久性必须有明确规则、可观测计数和对外边界，不能发生静默损失。

## 5. 必须澄清的术语：这些都可能被叫作 Raw

以下是待确认的工作用语，尚未写入 `CONTEXT.md`，也未取代现有架构定义。

| 数据层 | 包含什么 | 对后续恢复的能力边界 |
| --- | --- | --- |
| 线上协议帧 | 传输层或协议帧的字节与顺序 | 留数开销、权限及捕获位置不同；本轮不默认网络抓包 |
| 平台接纳的应用输入 | payload，加租户、设备、来源、时间、关联信息等必要上下文 | 可用于协议解释前排障；不自动覆盖未接纳或未上传的数据 |
| 来源业务记录 | 已被来源系统解码的点值、事件、工单或数据库行 | 可重做映射与分析，未必能纠正来源之前的解码错误 |
| Canonical | 平台规范化后的业务事实 | 可重做消费者计算，通常不能逆推出丢失的原输入 |

一个具体反例：Cognite 文档的 RAW 是无固定 schema 的暂存表，用于降低抽取耦合和重复转换；它也允许不经过 RAW 的集成路径。这不是“不可变的全部协议字节日志”的同义词。[CDF RAW](https://docs.cognite.com/dev/concepts/resource_types/raw)。

Cognite 的 OPC UA 抽取器将点值和事件写入对应服务，节点层级则可进入暂存区。因此，即使一个平台有叫 RAW 的组件，也不能推断所有遥测值必须经过它。[抽取器路径](https://docs.cognite.com/cdf/integration/concepts/extraction)。这是产品机制证据，不是 Aker BP 具体配置证据。

## 6. ming-iot 的可行路线应重新拆成五条轴

| 决策轴 | 应比较的选项 | 当前不能代替用户决定的内容 |
| --- | --- | --- |
| 保存层 | 接纳输入／来源业务记录／Canonical／必要组合 | 产品负责纠正哪一段错误 |
| 采集覆盖 | 全量／按数据类别／诊断窗口／事件触发 | 哪类未保存输入的损失可以接受 |
| 接管边界 | 内存接收／Broker 确认／持久日志确认／端到端结果确认 | “平台已接收”的外部承诺 |
| 时间与介质 | 普通 Kafka／分层 Kafka／可靠归档／短窗口诊断 | 故障多久被发现、允许多久恢复，以及真实成本 |
| 重算强度 | 故障后续跑／新算法回补／协议纠错／历史版本精确复原 | 首期必须交付哪一种，哪些只是潜在卖点 |

建议比较三类部署形态，而非先锁定唯一方案：

- **解释链优先**：平台负责私有协议且纠错重要，可靠输入日志与 Canonical 分层；保留时长后定，先不承诺完整历史复原平台。
- **分析应用优先**：来源已提供可信点值，规范化持久化为主，输入取证按需；明确网关之前的责任边界。
- **诊断产品优先**：平台对常规数据提供基本恢复，对高价值设备／故障保留丰富上下文；选择性策略必须可审计。

这是候选分类，不是建议首期同时实现三套 Profile。过早支持全部组合，会把存储节省转换成配置、测试和维护成本。

## 7. 性价比与卖点如何证伪

先用最小验证区分“能说的卖点”和“客户会付费的能力”，不靠架构名词定价。

| 候选卖点 | 应做的验证 | 什么结果会削弱建设理由 |
| --- | --- | --- |
| 解码服务宕机不丢已接纳数据 | 有界故障注入，核对输入与最终结果，测积压追赶 | 故障恢复需求可以由更简单的现有队列满足 |
| 协议有错可恢复历史正确点值 | 修一个真实解码缺陷，从留存输入重算，验证不触发命令等副作用 | 大多数错误发生在输入留存之前，或客户不需要历史纠错 |
| 原始输入定位争议 | 从设备／时间／错误定位一份输入及其解释上下文 | 隐私限制禁止留存，或绝大部分诊断只需规范化记录 |
| 长期数据复用 | 用旧数据增加一个真实消费者，验证所需字段仍在 | 新应用使用 Canonical 即可，不需要原始输入 |

成本口径：建设人力＋固定运维＋计算＋存储＋网络＋恢复演练＋多版本制品维护＋安全治理。还应与现场排障工时、业务停机损失及无法恢复的错误数据价值比较；没有真实流量和客户场景前，不给出虚假的 ROI 数字。

上一轮的容量敏感性分析仍可复用，但不决定产品形态。尤其要区分逻辑字节减少、采购容量减少、节点减少与现金支出减少，四者不是同一件事。

## 8. grilling 首轮：先确认独立前提，暂不问保留小时数

1. **首期用户与部署定位**：重点是单厂／企业私有部署，还是平台方集中运营多租户云服务？建议以私有部署成本与维护能力为首轮基准，但需用户确认；这是设计比较基准，不是取消多租户能力。
2. **最重要的可售结果**：首期最不能缺的是稳定采集和故障后继续处理、协议错误后的历史纠正，还是长期追溯审计？建议首期先保证前者，将后两者按真实客户必要性提升，不把它们捆成默认承诺。
3. **数据是否允许分级承诺**：趋势遥测与一次性关键事件能否采用不同留存／恢复标准？建议允许分类，但默认为明确、可检测的边界，不能未经授权静默丢弃。

这三项回答后，下一轮才讨论解码责任边界、错误发现时间、现场补传能力、故障域与成本上限；再决定 24h／72h、归档、是否保留双流以及最小实现。

按 `grill-with-docs` 的 `grilling` 流程停在本轮问题前沿；按 `domain-modeling` 只在术语与决策取得共识后更新词汇表或 ADR。不得将本笔记的建议当作用户已经选择。

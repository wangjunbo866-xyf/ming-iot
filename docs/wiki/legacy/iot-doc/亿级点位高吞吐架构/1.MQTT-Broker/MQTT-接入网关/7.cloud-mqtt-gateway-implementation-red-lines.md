# 云端 MQTT Broker 实现红线清单

> 本文承接 [百万级设备 MQTT 接入层架构设计](./1.cloud-mqtt-gateway-architecture.md)、[云端 MQTT 接入 Broker 与 Raw Log Appender 详细设计](./3.cloud-mqtt-gateway-raw-log-design.md)、[云端 MQTT 接入 Broker CONNECT 认证设计](./5.cloud-mqtt-connect-auth-design.md) 和 [云端 MQTT Broker 压力传播与背压控制设计](./6.cloud-mqtt-gateway-pressure-backpressure-design.md)，总结自研 MQTT Gateway 在实现阶段必须遵守的红线。

---

## 1. 结论

MQTT Gateway 第一阶段不是通用 MQTT Broker，也不是本地队列系统，而是专用设备接入层。

实现红线可以归纳为四类：

```text
1. 协议语义红线：不能提前承诺，不能扩大协议范围。
2. 内存红线：长期 session pointer-poor，短期 payload bounded-memory。
3. 背压红线：任何 queue 都必须有边界，过载必须 fail fast。
4. 运维红线：没有指标、压测和降级策略，不允许上线。
```

最重要的判断：

```text
Broker 可以慢。
Broker 可以拒绝。
Broker 可以断连。
Broker 不能无限缓存。
Broker 不能提前 PUBACK。
Broker 不能悄悄丢 QoS1。
```

---

## 2. 范围红线

第一阶段只做专用 MQTT 接入层。

必须坚持：

```text
CONNECT / CONNACK
PUBLISH QoS0 / QoS1
PUBACK
PINGREQ / PINGRESP
DISCONNECT
CleanSession=true
受限 SUBSCRIBE / SUBACK，前提是设备下行命令需要标准订阅语义
```

禁止在第一阶段加入：

```text
QoS2
Retain Message
通用持久会话
通用 wildcard subscription
通用 shared subscription
Broker 内离线消息长期堆积
Broker 内规则引擎
Broker 内 Modbus 解码
Broker 内写时序库
Broker 本地无限 WAL / spool
```

> **按需启用方案（一阶段默认仍不做）**：上述排除项中，`Retain Message` 有「暂不实现、客户要求时按需启用」的完整设计见 [#16 Retain 语义支持设计](./16.cloud-mqtt-gateway-retain-design.md)；`通用持久会话` 见 [#17 持久会话（CleanSession=false）支持设计](./17.cloud-mqtt-gateway-persistent-session-design.md)；`通用 wildcard subscription` 见 [#14 下行 Topic 路由设计](./14.cloud-mqtt-gateway-downlink-topic-routing-design.md)。

判断标准：

```text
如果一个能力不是百万逆变器 telemetry ingress 与低频定向下行必需能力，
就不应进入第一阶段 Broker。
```

## 3. 协议语义红线

### 3.1 QoS1 不能提前 PUBACK

禁止：

```text
收到 MQTT PUBLISH
  -> 放入 Kafka producer 本地 buffer
  -> 立即返回 PUBACK
```

必须：

```text
收到 MQTT PUBLISH
  -> 校验基础合法性
  -> append durable raw log
  -> Kafka / Redpanda 返回 durable ack
  -> 返回 MQTT PUBACK
```

原因：

```text
producer buffer 不是 durable log。
提前 PUBACK 会把 raw log 写失败变成静默丢数据。
```

### 3.2 QoS1 失败不能伪装成功

Kafka / Redpanda append 超时、不确定或失败时：

```text
不返回 PUBACK。
关闭连接或等待设备超时。
由设备按退避策略重试。
```

下游必须按幂等字段去重。

### 3.3 QoS0 不能承诺可靠

QoS0 可以正常进入 raw log，但不能承诺 100% 持久化。

压力升高时允许：

```text
限额
丢弃
断连
```

如果业务要求 QoS0 不丢，应把它按 QoS1 语义规划。

### 3.4 CONNECT 成功必须包含 Presence 成功

CONNECT 成功不只是认证成功。

生产语义：

```text
认证成功
  -> session_version 分配成功
  -> Presence CAS 写入成功
  -> 本地 session 绑定成功
  -> CONNACK success
```

Presence 写失败时禁止返回成功 CONNACK。

（以上为**默认语义**。唯一例外是运维手动降级开关——Phase 3、默认关闭、打开需审计，见 [Presence 设计 §9.1](./2.cloud-mqtt-presence-registry-design.md)：开关打开时按 NOT_ROUTABLE 模式放行连接，下行由 PENDING_DEVICE_ONLINE 兜底，不会错发只会迟发。）

## 4. Pointer-poor Session 红线

百万长连接场景下，长期存活对象比短期消息更危险。

Go GC 会扫描 live heap 中的指针图。百万 session 如果每个都带 map、channel、timer、logger、interface 和指针链，会形成巨大长期扫描成本。

### 4.1 Session 必须小而固定

推荐方向：

```go
type Session struct {
    ConnID           uint64
    DeviceNumericID uint64
    TenantNumericID uint32
    SessionVersion  uint64

    LastSeenUnix    int64
    KeepAliveSec    uint16
    Flags           uint16

    PendingBytes    int32
    InflightCount   int8

    Downlink        [4]DownlinkSlot

    Filters         string // 受限订阅 filter 合并（\x1f 分隔），见架构 §7.8；上限 512B
}
```

特点：

```text
数字字段为主。
固定小数组替代 map。
不保存复杂对象图。
不保存大 buffer。
Filters 是单 string（非 []string），每 Session +1 指针（string header）。
```

> **pointer-poor 微调（架构 §7.8 引入）**：Filters 字段让每 Session 指针数从 ~4 增加到 ~5（+25%），而非用 `[]string` 的 +3-6（+75-150%）。这是"支持受限 fan-out"的代价——GC mark 成本 +25%，仍在可接受范围（<15% CPU）。详见 [架构 §7.8.5 GC 量化](./1.cloud-mqtt-gateway-architecture.md#785-gc-与容量影响量化) + [容量规划](./11.cloud-mqtt-gateway-capacity-planning.md)。

> **50 万/节点 演进方向（容量规划 §10.3）**：若需单节点从 25 万提到 50 万，Session 须进一步压缩到 ~1 指针：
> - **压缩 A**：`Filters string` → `filterIdx uint8`（索引到全局 filterPool，设备 filter 组合只有几十种），省 1 指针。
> - **压缩 B**：`[4]DownlinkSlot` → `*DownlinkSlots`（惰性指针，99% 时间 nil = 无下行 inflight），省 4 指针。
> - 压缩后 ~1 指针/Session，50 万连接的 GC 成本回到当前 25 万水平。详见 [容量规划 §10.3](./11.cloud-mqtt-gateway-capacity-planning.md#103-提前做-50-万节点可行但需-session-压缩)。

这里刻意不把 message payload 放进 `Session`。

原因：

```text
Session 是长生命周期对象，连接存活多久它就存活多久。
payload 是短生命周期对象，只应从收到 PUBLISH 开始存活到 Kafka / Redpanda ack callback 返回。
```

正确关系：

```text
Session 只记录 pending bytes / inflight count / conn_id / session_version。
payload 放在 AppendRequest / RawEnvelope 中。
AppendRequest 进入 bounded append queue。
Kafka / Redpanda ack 或 failure 后释放 payload 引用和 byte budget。
```

示意：

```go
type AppendRequest struct {
    Payload    []byte
    PayloadLen int32
    PacketID   uint16
    QoS        byte
    SessionRef SessionRef
    Meta       RawEnvelopeMeta
    BudgetCost int32
}
```

因此：

```text
Session 负责“这条连接当前还有多少 pending”。
AppendRequest 负责“这条具体消息的 payload 和 ack 回调状态”。
```

### 4.2 每连接禁止项

每个 session 中禁止常驻：

```text
map
channel
time.Timer
logger
interface{}
动态 subscription tree
完整 auth result
完整 topic string 缓存
完整 MQTT packet
大 byte buffer
离线消息队列
```

### 4.3 推荐替代

| 禁止项 | 替代 |
|---|---|
| 每连接 map | 固定小数组 / 全局 sharded map |
| 每连接 channel | shard worker queue / 直接方法调用 / bounded global queue |
| 每连接 time.Timer | timing wheel / shard 级 deadline heap |
| 每连接 logger | 全局 logger + 结构化字段 |
| string device_id | numeric id / interned id / compact principal |
| map[packet_id]inflight | `[1]` / `[4]` 固定槽位 |
| 每连接订阅树 | 受限命令 topic 校验，不维护通用订阅树 |

### 4.4 Downlink Inflight 红线

如果下行 QoS1 inflight 限制是 1 到 4，不允许使用：

```go
map[uint16]*DownlinkMessage
```

应使用：

```go
[4]DownlinkSlot
```

原因：

```text
少对象。
少指针。
内存布局固定。
GC 扫描成本更低。
```

> **容量规划**：本节的 pointer-poor Session 模型如何量化为"Per-Broker 多少连接、什么机型、几个节点"——见 [容量规划](./11.cloud-mqtt-gateway-capacity-planning.md)。结论：Per-Broker 20-30 万连接（32GB/16 核），百万集群 4-5 节点。

## 5. Bounded-memory Payload 红线

短期 payload 可以进入内存，但必须有明确预算和释放时机。

### 5.1 先预算，后分配

读取 MQTT PUBLISH 时，必须尽早得到 payload_len，并在分配 payload 前申请预算。

推荐流程：

```text
读取 MQTT fixed header
  -> 解析 remaining length
  -> 读取 variable header
  -> 得到 payload_len
  -> 校验 max_payload_size
  -> 申请 session byte budget
  -> 申请 global append byte budget
  -> 分配 exact-size payload []byte
  -> io.ReadFull 读 payload
  -> 入 append queue
  -> Kafka ack / failure 后释放预算
```

禁止：

```text
先分配大 payload。
先读完整 packet。
入队时才发现没有预算。
```

### 5.1.1 payload buffer 的分配来源

§5.1 规定了 payload 必须"先预算、后分配、exact-size"，但没规定字节从哪里来。
百万 QPS 下，每包独立 `make([]byte, remaining)` 是 GC 稳定压力来源。
分配来源必须显式选定，否则实现者会默认走最简单的每包 `make`。

必须：对**大 payload**（> 4KB，且 ≤ §5.3 的 `max_payload_size`）采用分级
`sync.Pool`（建议 4KB / 16KB 两档），`Get` 后切 `[:remaining]`。池化只换分配来源，
不改变任何语义：仍是 exact-size、仍走 per-client + global byte budget 双重预算、
仍满足 §5.1 的"先预算后分配"。

**小 payload（≤ 4KB）直接 `make`，不进池**。理由：Go 运行时对 ≤16B 的 noscan 对象
走 tiny allocator（多对象合并进一个 16B 块、per-P mcache 指针 bump、无锁），对
≤32KB 走 per-P size class span（同样指针 bump、锁-free）；且 `[]byte` 是 noscan，
GC 不扫描其内容。因此小 slice 池化时，pool 的 `Get`/`Put` 开销（procPin + 原子 +
slice 操作，几百 ns）> 它省下的分配成本（几十 ns），而 GC 成本两边几乎相同；
更糟的是 pool entry 算 live heap、每 GC 周期被 `poolCleanup` 清一次——池化小对象
既占内存又没省 GC，净负收益。池化只对大 payload（memclr / mallocgc / live-bytes
成本显著）成立。

分档阈值（4KB）必须由 pprof alloc profile 的真实尺寸分布压测确认，可按真实负载
加中间档（如真实分布集中在 1~3KB 时加一档）。禁止预置 ≤256B 小档。

禁止：

```text
每包独立 make([]byte, remaining)（当前 packet.go 现状，大 payload 下的 GC 压力来源）。
对小 payload（≤ 4KB）走 sync.Pool：tiny allocator + per-P size class + noscan 下
  池化净负收益（pool 开销 > 省下的分配成本，且 pool entry 反而占 live heap）。
仿 NATS 的 per-conn 大读缓冲（64KB）+ 自适应 grow：与 §5.2 直接冲突。
  理由：single-sink → Kafka，payload 要跨 goroutine 驻留
  （read loop → ingest worker → Kafka ack callback），不能别名读缓冲。
  NATS 的 per-conn 不入池哲学只对其读缓冲成立（fan-out + deliver 必然 copy），
  本 broker 拿不到 jump-ahead 收益，反而 64KB × 百万连接 = 64GB 爆 §3/§4 内存。
  详见 nats 报告 §7.1 / §7.2 / §7.3。
零拷贝别名大 read buffer 的 subslice（重申 §5.2）。
```

归还点红线（池化方案唯一的高风险点）：

```text
池化 buffer 被 ingest queue 异步路径 + Kafka producer 持有。
必须等"真正消费完"才能 Put 回池，否则 use-after-Put 写脏数据。

QoS1 同步路径：SubmitAndWait 返回 nil（Kafka 已 durable ack）后归还。
  必须确认 franz-go ProduceSync 在返回时已释放 Record.Value 引用。
QoS0 异步路径：不能在 handlePublish 内归还（fire-and-forget 入队后 read loop
  立刻继续）。归还点必须在 ingest worker 内，即 q.release(cost) 旁
  （ingest/queue.go worker）。
失败 / 超时 / 断连：每个退出分支都要保证 Put 一次且仅一次。
```

建议用 RAII 封装收敛归还点：`payloadPool.Get(n)` 返回 `([]byte, *lease)`，
由真正消费完的那一层调 `lease.Release()`，避免归还点散落各分支造成
"漏 Put"（buffer 永不归还，等同每包 make）或"早 Put"（use-after-Put）。

附：sendfile / splice / io.Copy 等内核零拷贝 syscall 在本 broker 不适用——
sendfile 要文件源、splice 要无检查透传、二者都过不了 TLS；当前 payload 从读到
交 Kafka 已是切片别名零拷贝。性能杠杆在 buffer 池化和 TLS/Kafka batch 调优，
不在零拷贝 syscall。

### 5.2 不引用大 read buffer

禁止：

```go
payload := readBuf[payloadStart:payloadEnd]
queue <- AppendRequest{Payload: payload}
```

如果 `readBuf` 是 64KB，而 payload 是 3KB，queue 中的小 slice 会拖住整个 64KB backing array。

推荐：

```text
解析 payload_len 后，直接读入 exact-size payload buffer。
```

必要时才用 copy 切断大 buffer 生命周期：

```go
payload := make([]byte, payloadLen)
copy(payload, readBuf[payloadStart:payloadEnd])
```

copy 不是为了让 queued payload 更早 GC，而是为了避免小 payload 引用大 backing array。

### 5.3 Queue 必须按 bytes 限制

禁止只按消息条数限制 queue。

必须同时限制：

```text
max_append_queue_bytes
max_append_queue_messages
max_pending_bytes_per_client
max_payload_size
max_inflight_qos1_upstream_per_client
```

建议首版起点：

```text
max_payload_size = 8KB / 16KB，按真实设备协议确定
max_inflight_qos1_upstream_per_client = 1 或 2
max_pending_bytes_per_client = 2 * max_payload_size
max_append_queue_bytes = 512MB / 1GB，按单节点规格压测确定
```

### 5.4 Kafka Producer Buffer 也要计入预算

消息出 append queue 后，不代表内存已经释放。

Kafka producer 可能仍持有：

```text
batch buffer
compression buffer
in-flight request
callback state
payload 或 payload 副本
```

预算释放建议：

```text
直到 Kafka ack callback 或 failure callback 返回后再释放。
```

### 5.5 压力下禁止继续读大包

当 global append budget 不足时：

```text
QoS1：断连，不读 payload，让设备退避重试。
QoS0：drop 或断连。
```

如果为了保持连接而 drain payload，必须使用小 scratch buffer 且有上限。

第一阶段建议高压下直接断连，保持实现简单和内存边界清楚。

## 6. Queue 与背压红线

所有 queue 都必须是 bounded queue。

包括：

```text
accept queue
auth queue
append queue
downlink queue
Kafka producer buffer
metrics / log async queue
```

禁止：

```text
无界 channel
无界 slice append
无界 goroutine spawn
无界 retry loop
无界本地磁盘 spool
```

过载时必须明确动作：

| 场景 | 动作 |
|---|---|
| auth queue 满 | CONNACK Server Unavailable 或 close |
| append queue 满，QoS0 | drop 或 disconnect |
| append queue 满，QoS1 | disconnect，不 PUBACK |
| Presence 写失败 | 拒绝 CONNECT |
| Kafka 不可用 | fail closed，拒绝新连接或断开写入连接 |
| Broker 内存高水位 | 限制新连接，降低读取，主动断连 |

### 6.1 PROXY protocol 热路径红线

若普通设备入口采用"云 TLS LB 终结单向 TLS + PROXY protocol 透传源 IP"，PROXY protocol 解析进入 Broker accept 热路径，必须按红线处理。

必须：

```text
只在专用 LB 后端监听端口启用 PROXY protocol。
只接受来自可信 LB CIDR / 安全组的连接；可信性校验先于 PROXY 源 IP 信任。
accept 后立即设置短 read deadline，解析完成后再进入认证 / MQTT 处理。
PROXY 头读取长度有固定上限；只解析源 IP / 源端口所需字段。
缺失、截断、超长、版本非法、源 IP 字段非法：立即断连并计数。
未验证真实源 IP 时，per-IP 限流和 ip_blacklist 必须关闭。
指标按 top-N / 聚合输出，禁止 device_id / IP 全量作为 label。
```

> **TLS 接入设计**：两种 TLS 拓扑（broker 终结 / NLB 卸载）、PROXY protocol 真实 IP 透传、session resumption 握手风暴防护、ECDSA 强制、mTLS 预留的完整设计见 [TLS 接入设计](./network-defense/13.cloud-mqtt-gateway-tls-design.md)。阿里云 NLB TCPSSL 监听的 PROXY protocol v2 不支持 pp2_ssl_cn，mTLS 必须 broker 终结（拓扑 A）。

禁止：

```text
公网直连接口接受客户端自带 PROXY 头。
非可信来源的 PROXY 源 IP 覆盖 TCP peer address。
PROXY 解析失败后静默退回 LB 内网地址继续认证。
在 PROXY 解析路径做 DNS、数据库、Redis、HTTP 或任何网络调用。
无界读取 PROXY 头、按声明长度分配内存、或等待慢客户端无限占用 fd。
把 PROXY 解析塞进 MQTT codec，导致协议 fuzz 和入口鉴权边界混在一起。
```

压测与验收见压测规划 §4.2.1 / §11.5；攻击面与拓扑决策见网络攻击防范设计 §1 / §6.2。

## 7. 连接与 Goroutine 红线

Go 可以支撑大量长连接，但不能让每个连接携带大量并发对象。

### 7.1 每连接 goroutine 数必须受控

推荐：

```text
每连接 1 个 read loop goroutine。
不要每连接常驻 writer goroutine。
不要每连接 timer goroutine。
不要每连接多个 worker goroutine。
```

下行写入可以通过：

```text
session 方法
短临界区
shard worker
bounded downlink queue
```

明确目标值（红线，压测验收）：

```text
goroutine 总数 ≤ 连接数 × 1.x（理想 ≈ 1.0~1.2，即基本只有 per-conn 的 1 个 read loop）。
worker pool（auth worker / append worker / shard worker）为固定数量，
  与 CPU 核数相关，不随连接数线性增长。
100 万连接时 goroutine 量级应在百万级，而不是数百万级。
```

判定标准：把 goroutine 拆成"随连接数线性增长的"和"固定池"两类。前者每连接只允许 1 个（read loop），后者总数必须是常数级。任何"每连接 N 个 goroutine（writer/timer/worker）"都违反本红线。具体模型由压测确定，但乘数上限不变。

### 7.2 append callback 不允许直接操作 session

Kafka / Redpanda 的 ack callback 跑在 producer 的 ack goroutine 上，而 session 字段由 read loop / shard worker 拥有。

禁止：

```text
ack callback 直接 s.SendPubAck() / 直接改 s.PendingBytes / 直接 s.Close()
```

必须：

```text
ack callback 只产出 AppendResult{ConnID, SessionVersion, PacketID, QoS, BudgetCost, Err}
  -> 投递回该连接 shard 的 bounded 回执队列
  -> 由 session 拥有者执行，并用 ConnID + SessionVersion fencing 校验
  -> version 失配（连接已断开 / 被 takeover）则丢弃回执，只释放全局 byte budget
```

byte budget 的释放与 session 是否存活解耦：预算无条件释放，PUBACK 和 session 字段修改只能由 session 拥有者在 fencing 通过后执行。详见 [raw log 设计 §4.0](./3.cloud-mqtt-gateway-raw-log-design.md)。

### 7.3 不允许 goroutine 泄漏

以下事件必须清理所有引用：

```text
连接关闭
认证失败
Presence 写失败
append timeout
Kafka callback 返回
Broker shutdown
```

必须压测：

```text
连接建立 / 断开循环 100 万次后，goroutine 数是否回落。
```

## 8. 认证红线

CONNECT 热路径必须保护 DB。

禁止：

```text
每个 CONNECT 无保护直打业务主库。
CONNECT 阶段 join 多张业务表。
CONNECT 阶段查询设备档案大 JSON。
CONNECT 阶段同步写登录历史。
CONNECT 阶段调用外部 HTTP 服务。
CONNECT 阶段使用慢哈希处理高频机器凭证。
把"凭证错误"或"设备禁用"按 client_id 写入负向缓存作为认证判决。
```

必须：

```text
本地正向缓存（必须携带 secret_hash，命中时仍逐次 constant-time 校验本次 password）。
本地负向缓存（只缓存"未找到凭证记录"，不得因某次密码错误而拉黑 client_id）。
bounded auth queue。
auth worker pool。
认证只读库 / 只读副本。
DB 查询短超时。
cache miss QPS 预算。
每 device_id 同时认证 inflight 限制。
```

认证系统过载时：

```text
fail fast。
返回 Server Unavailable 或 close。
依赖设备退避重试。
```

## 9. Presence 红线

Presence 是下行路由提示，不是最终事实。

必须：

```text
session_version 由中心化原子序列生成。
Presence 写入携带 broker_id / broker_epoch / conn_id / session_version。
断连删除必须条件匹配。
下行投递到 Broker 后必须二次校验本地 session。
Broker lease 失效时，该 Broker 下的 presence 视为无效。
```

禁止：

```text
断连时无条件删除 presence。
Broker 本地自增 session_version。
下行只信 Redis presence，不校验本地连接。
每条 telemetry 都刷新 presence TTL。
每设备频繁续租 TTL。
```

Presence 写失败时：

```text
CONNECT 不得成功。
```

## 10. 下行命令红线

下行命令必须精准路由到持有设备连接的 Broker。

必须路径（单播 = gRPC 直连，不经 Kafka）：

```text
Command Service
  -> 查询 Presence Registry（device_id -> broker_id / epoch / conn_id / session_version）
  -> 查 Broker Registry 取该 broker 的 gRPC 地址
  -> gRPC 直连目标 Broker（Deliver(envelope + fencing)）
  -> Broker 二次校验 broker_epoch / conn_id / session_version
  -> 本地 MQTT PUBLISH，同步回 PUBACK / NOT_HERE / STALE 驱动命令状态机
```

下行的「可达性」由 Command Service 的 DB 状态机拥有（status / retry / TTL / outbox / lease），不由传输层拥有。投递失败（NOT_HERE / 连接错误 / 超时）→ 重查 presence 重投（fail-fast + re-resolve），因为目标 broker 是 presence 的函数，失败时正确动作是改路由而非在原传输里重试。

禁止：

```text
用 Kafka 做单播下行的定向投递（分区路由或消费组都把"可达性"误放到传输层；
  且 Kafka 的"留存等消费"对一个会过期的路由决策语义错误——目标 broker 已 stale）。
所有 Broker 订阅同一个 cmd.downlink 后随机消费。
用 queue group / shared subscription 做定向下发。
每设备一个内部 Kafka / NATS 订阅。
Broker 之间直接转发下行命令（broker→broker mesh；brokers 必须 share-nothing，
  只经 Command Service + presence + broker registry 路由）。
Broker 内维护订阅树 / scope filter 做组播匹配（fan-out 在 Command Service 拆单播，不在 Broker）。
下行命令无限排队在 Broker 内。
离线命令堆积在 Broker 内。
```

离线命令应由 Command Service 管理 TTL、状态机、幂等和重试。

**广播 / 批量（一对多）= Command Service 拆成 N 条单播**（查设备档案 DB 解析成员 → 逐设备查 presence → gRPC 单播，限速，复用 OTA 编排）。Broker 不感知组/广播，只做单播投递；Kafka 仅承载上行 raw log，下行全程不沾 Kafka。

```text

```

## 13. 压测红线

没有覆盖风暴场景，不允许生产上线。

必须压测：

```text
单节点 5万 / 10万 / 20万连接。
100 万设备 30min / 10min / 5min 上线。
TLS 握手风暴：RSA vs ECDSA 证书、开/关 session resumption 的握手 CPU 与握手速率对比。
payload 1.5KB / 3KB / 5KB / 16KB。
协议 fuzz：Go 原生 fuzz 覆盖 ReadPacket / CONNECT / PUBLISH 解析。
畸形包矩阵：谎报 remaining length、QoS=3、CONNECT 前发包、重复 CONNECT、零长 client_id、保留位非零、QoS1 packet_id=0。
慢读饿死：包中途 1 byte/min，验证 read deadline 覆盖"包读到一半"。
Kafka ack p99 = 20ms / 100ms / 500ms / 2s / 10s。
Kafka 短暂不可用。
Redis Presence 短暂不可用。
认证只读库 failover。
设备无退避 / 固定退避 / jitter 退避对比。
Broker 节点重启。
连接建立断开循环，验证 goroutine / fd / heap 回落。
```

验收必须看：

```text
RSS
heap live
heap objects
GC pause p99
GC CPU fraction
goroutine count
fd count
append_queue_bytes
Kafka ack p99
PUBACK p99
auth queue p99
Presence write p99
重试波形
重复消息比例
恢复时间
```

禁止只用平均吞吐证明系统可用。

## 15. 最高优先级红线摘要

如果只保留十条：

```text
1. QoS1 必须等 durable raw log ack 后才 PUBACK。
2. Session 必须 pointer-poor，禁止每连接 map/channel/timer。
3. Payload 必须 bounded-memory，先预算后分配。
4. 所有 queue 必须有 bytes 上限。
5. append queue 满时，QoS1 断连不 ACK，QoS0 丢弃或断连。
6. CONNECT 成功必须以认证成功和 Presence 写入成功为前提。
7. Presence 删除和下行投递必须带 fencing 校验。
8. 设备重试必须退避并带 jitter。
9. Broker 不做通用订阅、持久会话、离线队列和本地无限 spool。
10. 没有风暴压测、指标和降级开关，不允许上线。
```

这些红线的共同目标：

```text
让系统失败得清楚、可控、可恢复，
而不是用隐藏队列、提前 ACK 和无界内存把故障延后到 OOM 或静默丢数据。
```

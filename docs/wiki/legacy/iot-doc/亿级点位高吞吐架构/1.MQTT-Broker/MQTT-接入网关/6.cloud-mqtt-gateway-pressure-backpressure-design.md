# 云端 MQTT Broker 压力传播与背压控制设计

> 本文承接 [百万级设备 MQTT 接入层架构设计](./1.cloud-mqtt-gateway-architecture.md)、[云端 MQTT 接入 Broker 与 Raw Log Appender 详细设计](./3.cloud-mqtt-gateway-raw-log-design.md) 和 [云端 MQTT 接入 Broker CONNECT 认证设计](./5.cloud-mqtt-connect-auth-design.md)，统一说明 Kafka ack、设备重试、内存 buffer、连接风暴、上报风暴和恢复风暴背后的共同问题：压力如何在系统中传播、排队、放大，以及 Broker 应如何用有界背压保护自身和下游。

---

## 1. 结论

Kafka ack、设备重试、内存 buffer 和连接风暴不是四个孤立问题，而是同一种稳定性问题在不同位置的表现：

```text
压力传播、排队、放大与失控。
```

典型故障闭环：

```text
Kafka / Redpanda ack 变慢
  -> Broker 不能及时返回 MQTT PUBACK
  -> QoS1 pending 消息增加
  -> Broker 内存 buffer 增长
  -> 设备超时重试或重连
  -> CONNECT / AUTH / Presence / PUBLISH 压力增加
  -> Kafka / Redpanda 与 Broker 更慢
```

连接风暴也是同一类问题：

```text
大量设备同时 CONNECT
  -> TLS / 认证 / Presence 写入变慢
  -> Broker 连接排队增加
  -> 设备超时重连
  -> CONNECT 压力继续放大
```

核心原则：

```text
1. Broker 可以变慢。
2. Broker 可以拒绝。
3. Broker 可以断开连接。
4. Broker 不能无限缓存。
5. Broker 不能提前承诺。
6. 设备重试必须退避并带 jitter。
7. 所有队列和 buffer 必须有明确字节上限。
```

第一阶段不把 MQTT Gateway 设计成本地持久队列系统，也不让 Broker 用无限内存吸收后端抖动。

```text
QoS1 的承诺点是 durable raw log ack。
QoS0 是 best effort，压力升高时优先降级、丢弃或断连。
CONNECT 的承诺点是认证成功且 Presence 写入成功。
```

## 2. 压力传播模型

### 2.1 正常上行链路

```text
Device
  -> MQTT PUBLISH QoS0/QoS1
  -> MQTT Gateway
  -> append queue
  -> Kafka / Redpanda producer
  -> durable raw log ack
  -> MQTT PUBACK，QoS1
```

### 2.2 反向压力链路

```text
Kafka / Redpanda ack latency 升高
  -> append queue 排队时间升高
  -> QoS1 PUBACK latency 升高
  -> per-client inflight 被占满
  -> Broker 暂停读取或断连
  -> 设备退避后重试
```

### 2.3 压力放大链路

如果设备没有退避，或退避没有 jitter，压力会被放大：

```text
PUBACK 超时
  -> 设备立即重发
  -> 重复 PUBLISH 增加
  -> raw log 写入更多重复消息
  -> Kafka / Redpanda 更慢
```

如果设备选择断线重连，压力会同时打到连接链路：

```text
PUBACK 超时
  -> 设备断开 TCP
  -> 重新 CONNECT
  -> TLS handshake
  -> CONNECT 认证
  -> Redis Presence 写入
  -> 再次 PUBLISH
```

因此系统必须同时控制：

```text
连接速率
认证并发
Presence 写入
每连接 QoS1 inflight
全局 append queue bytes
Kafka producer buffer
设备重试节奏
```

## 3. 统一问题分类

| 表现 | 压力入口 | 传播路径 | 失控结果 | 控制手段 |
|---|---|---|---|---|
| Kafka ack 变慢 | raw log | Kafka ack -> PUBACK -> pending | Broker 内存增长、设备重试 | 延迟 PUBACK、限制 inflight、有界 append queue |
| 设备重试风暴 | device | retry -> PUBLISH / CONNECT | 重复消息、认证压力、写入压力 | 退避、jitter、去重、fail fast |
| 内存 buffer 增长 | broker | pending message -> heap | GC 压力、OOM | byte budget、per-client limit、QoS0 drop、QoS1 disconnect |
| 连接风暴 | device | CONNECT -> TLS -> auth -> presence | 认证库/Redis/Broker 被打穿 | auth queue、connect rate limit、Server Unavailable |
| 上报风暴 | device | PUBLISH -> append queue -> raw log | Kafka 峰值写入过高 | 设备侧打散、Broker 背压、QoS0 降级 |
| 恢复风暴 | broker / backend | backlog flush -> raw log | 后端刚恢复又被打爆 | 恢复限速、批量节流、分阶段恢复 |

结论：

```text
所有风暴都应被建模为：
  输入速率 > 服务速率
  -> 队列增长
  -> 延迟增长
  -> 客户端重试
  -> 输入速率进一步增长
```

Broker 的职责不是吸收无限差值，而是在差值变大时尽早把压力显式反馈给设备和上游控制面。

## 4. 承诺点设计

### 4.1 QoS1 PUBACK 承诺点

QoS1 不能在写入 Kafka producer 本地 buffer 后立即 PUBACK。

错误语义：

```text
Broker 收到 PUBLISH
  -> 写入 producer 内存 buffer
  -> 立即 PUBACK
```

问题：

```text
producer buffer 不是 durable raw log。
Broker 进程崩溃、producer flush 失败、Kafka leader 切换超时，都可能导致数据未持久化。
```

正确语义：

```text
Broker 收到 PUBLISH
  -> 校验 device / topic / payload
  -> produce Kafka / Redpanda
  -> 等待 durable ack
  -> 返回 MQTT PUBACK
```

Kafka / Redpanda 建议：

```text
acks=all
replication.factor=3
min.insync.replicas=2
enable.idempotence=true
delivery.timeout.ms 明确配置
```

### 4.2 QoS0 承诺点

QoS0 没有 MQTT 层 ACK。正常情况下仍建议进入 raw log，便于统一解码、追溯和重放。

但 QoS0 不应与 QoS1 抢占同等可靠性预算：

```text
正常水位：QoS0 写 raw log。
压力水位：QoS0 限额进入 append queue。
高压水位：QoS0 drop 或 disconnect。
故障水位：QoS0 直接拒绝。
```

### 4.3 CONNECT 承诺点

CONNECT 成功不能只代表 TCP 已建立。

生产语义：

```text
CONNECT 成功 =
  认证成功
  + Presence 写入成功
  + 本地 session 绑定成功
```

如果认证系统过载：

```text
返回 CONNACK Server Unavailable 或直接 close。
```

如果 Presence 写入失败：

```text
拒绝连接。
```

这样可以避免平台认为设备在线，但下行无法可靠路由。

### 4.4 QoS1 执行模型：同步 v1 与异步演进

§4.1 定义了"PUBACK 必须在 durable ack 之后"这个承诺，但没规定 Broker 用什么**执行模型**兑现它。两种模型：

```text
同步（v1 实现）：
  read loop 调 SubmitAndWait，阻塞等 durable ack 返回，再发 PUBACK，再读下一个包。
  per-connection 上行 QoS1 inflight 天然 = 1（未 ack 前不读下一包）。
  单 goroutine 自洽，无需 callback / 回执队列 / fencing。

异步（演进形态，见 raw log 设计 §4.0、红线 §7.2）：
  read loop 提交后继续读（up to inflight>1），Kafka ack 回调产出 AppendResult，
  经 bounded 回执队列 + ConnID/SessionVersion fencing 投回 session 拥有者后发 PUBACK。
```

为什么 v1 选同步：百万长连接下每连接一个 read-loop goroutine，连接 A 阻塞在 SubmitAndWait 不影响 B（独立 goroutine，park 几乎零成本），所以同步**不会"串行拖垮"Broker**；而它省掉跨 goroutine 的 use-after-close 和竞态，不需要 fencing，实现最小。**有界 append 队列 + 满即 fail-fast（红线 §5）保证同步模型在过载下是卸载，不是堆积**——扛不住就断 QoS1 连接，Broker 不 OOM。

同步模型的真实代价是**只有两个挡位**：

```text
ack-fast  或  disconnect。
没有"延迟 PUBACK、留住连接"的中间挡。
```

这把 §9.2 的 L0→L1→L2→L3 梯度塌缩成 L0→L3：Kafka durable ack 一变慢或 QoS1 突发，append 队列填满，直接跳到大批 QoS1 连接同时断开。断连远比 QoS0 丢一条消息贵——每条断连是一次 re-auth（打认证 DB）+ re-presence（打 Redis）的完整重建，于是一次 Kafka 打嗝被放大成 CONNECT 风暴（§2.3 放大链路、§10 恢复风暴）。

异步模型买回的正是**中间挡**：read loop 不再 park，能继续读 PINGREQ 和后续包，于是可以"延迟 PUBACK 但保连接存活"，把 §9.2 的 L1 软压挡装回来——压力下设备被节流而非被踢。

但要写清异步**买不到**什么：

```text
1. 吞吐天花板不变：PUBACK 仍等 durable ack（§4.1），acks=all 的 Kafka 容量仍是上限。
   异步只多缓冲几条在途，代价是更多 payload 占 byte budget（§5.3 字节预算是配套约束）。
2. mass-QoS1 总负载不变：全量消息数 × acks=all 不因执行模型而变小。
```

演进触发条件：当 inflight>1 的吞吐/延迟需求出现，或需要 L1 软压挡吸收 Kafka 延迟抖动（高 QoS1 占比场景）时，切异步。在此之前同步 v1 够用且更安全。mass-QoS1 的防护不靠执行模型，见 §4.5。

### 4.5 QoS1 准入与 mass-QoS1 防护

"一大批设备误设为 QoS1"或 QoS1 突发，是 §4.4 放大链路最容易被触发的入口。它本质是**容量 + 策略**问题，不是执行模型问题——换异步也解决不了。

先问最该问的：**这些遥测真的需要 QoS1 吗？**

```text
逆变器每 5 分钟一条全量快照，下游按 (device, boot_id, seq) 幂等——
丢一条快照，下一条就盖过去。纯遥测 QoS0 才是正确默认值。
QoS1 / telemetry.raw.critical 应留给"丢了有后果"的事件 / 告警
（QoS0→normal、QoS1→critical 的 topic 分流见 raw log 设计 §8.2）。
```

防护杠杆（从根因到兜底）：

```text
1. QoS 准入策略：按产品接入配置声明允许的 QoS，Broker 侧对纯遥测 topic
   拒绝或降级设备请求的 QoS1，别让设备单方面决定烧 durable 容量。
   注意这偏离标准 MQTT 语义（设备等 PUBACK），需与固件约定。
2. per-tenant QoS1 准入配额：与 per-tenant CONNECT 限流（认证设计 §6.1）同源，
   防止单租户误配置吃满全局 durable 预算。
3. Kafka 容量按真实 QoS1 占比 + headroom 规划，不按全量 QoS1 拍。
4. 重连善后兜底：accept 限流 + 设备退避 jitter（§10），
   即使真断了一批，重连不形成二次冲击。
```

记忆点：**同步 v1 不会被拖垮，但它把背压塌缩成断连，而断连比丢消息贵得多**。异步恢复梯度是必要演进，QoS1 准入 + 容量规划是 mass-QoS1 的根治；两者解决不同问题，不可互相替代。

## 5. Kafka Ack 与 PUBACK 背压

### 5.1 延迟组成

QoS1 的服务端延迟大致是：

```text
Broker socket read
+ MQTT decode / validate
+ append queue wait
+ Kafka producer batch / linger
+ Kafka leader append
+ follower replication
+ Kafka ack callback
+ Broker PUBACK write
```

Kafka ack p99 会直接传导到 MQTT PUBACK p99。

示例：

| Kafka ack p99 | Broker 行为 | 设备感知 |
|---:|---|---|
| 20ms | 正常 PUBACK | 正常 |
| 500ms | QoS1 pending 时间变长 | 可能仍可接受 |
| 2s | per-client inflight 更容易占满 | 部分设备可能超时 |
| 10s+ | append queue 快速增长 | 重试 / 重连风险显著升高 |

### 5.2 不提前 ACK

提前 PUBACK 会把可靠性问题隐藏起来：

```text
设备认为成功。
Broker 认为已交付。
Kafka 实际可能失败。
下游无法知道缺失。
```

本设计宁可让设备重试，也不提前 ACK。

```text
at-least-once + dedupe
优先于
提前 ACK + 静默丢失
```

### 5.3 Producer Buffer 也属于内存预算

Broker 内部的 append queue 不是唯一 buffer。

消息可能存在于：

```text
append queue
Kafka producer batch buffer
Kafka in-flight request
compression buffer
callback state
```

因此内存预算不能只看：

```text
append_queue_bytes
```

还要保守估算：

```text
append_queue_bytes
+ kafka_producer_buffer_bytes
+ in_flight_request_bytes
+ socket / read buffer
+ session state
+ Go object overhead
```

### 5.4 Timeout 语义

如果 produce 超时或 ack 不确定：

```text
QoS1：不返回 PUBACK，关闭连接或等待设备超时重试。
QoS0：记录 drop / uncertain 指标，按水位决定是否断连。
```

下游必须按幂等字段去重：

```text
(tenant_id, device_id, boot_id, seq)
```

或者兼容旧固件：

```text
(tenant_id, device_id, sample_ts, payload_crc32)
```

## 6. Broker 内存 Buffer 设计

### 6.1 Buffer 存的是什么

Broker 的内存 buffer 不是抽象概念，它通常保存已经从设备接收、但还没有拿到 durable raw log ack 的消息。

典型内容：

```text
payload []byte
packet_id
qos
tenant_id
device_id
boot_id / seq / sample_ts / payload_crc32
broker_receive_ts
session ref
deadline
callback state
```

示例结构：

```go
type AppendRequest struct {
    Payload  []byte
    Meta     RawEnvelopeMeta
    QoS      byte
    PacketID uint16
    Session  SessionRef
    Deadline time.Time
}
```

### 6.2 不保存完整 MQTT Packet

入队后不应长期保存：

```text
完整 MQTT packet
原始 topic 大字符串
连接读缓冲区 readBuf
解析过程临时对象
```

应保存：

```text
刚好大小的 payload []byte
结构化 metadata
packet_id
session ref
```

topic 解析后应变成结构化字段：

```text
tenant_id
product
device_id
message_type
```

（方案 B"单 topic + payload header 绑定"**未采纳**：自产设备已定为每设备 topic + ACL，见架构设计 §6.5；身份字段一律取自认证主体，Broker 不解析 payload。）

### 6.3 避免小 slice 拖住大 backing array

本节是内存风险模型和实现注意，不表示当前 `mqtt-gateway` 已经使用固定 64KB `readBuf`。

当前 v1 代码的 `ReadPacket` 按 MQTT Remaining Length 精确分配 `pkt.Body`，`Payload` 只别名该 packet body；因此现状主要风险是完整 MQTT packet body 暂存，而不是“小 payload 拖住固定 64KB read buffer”。

真正的强制红线见 [实现红线 §5](./7.cloud-mqtt-gateway-implementation-red-lines.md#5-bounded-memory-payload-%E7%BA%A2%E7%BA%BF)。

如果后续为了性能引入固定读缓冲、buffer pool 或零拷贝 streaming parser，危险写法是：

```go
payload := readBuf[payloadStart:payloadEnd]
queue <- AppendRequest{Payload: payload}
```

如果 `readBuf` 是 64KB，而 payload 只有 3KB，只要 queue 仍引用 payload，整个 64KB backing array 都不能释放或复用。

示例：

```text
100,000 条 pending
每条 payload 3KB
```

如果每条拖住 64KB readBuf：

```text
100,000 * 64KB = 6.4GB
```

如果只保留刚好大小的 3KB payload：

```text
100,000 * 3KB = 300MB
```

### 6.4 推荐读取模型

热路径最终推荐模型：

```text
先读取 MQTT fixed header。
解析 remaining length。
读取 variable header，得到 topic / packet_id。
计算 payload_len。
申请 exact-size payload buffer。
io.ReadFull 直接读入 payload buffer。
入队 AppendRequest。
```

伪代码：

```go
fixed, remainingLen, err := readFixedHeader(conn)
if err != nil {
    return err
}

vh, payloadLen, err := readPublishVariableHeader(conn, remainingLen)
if err != nil {
    return err
}

if payloadLen > maxPayloadSize {
    return ErrPayloadTooLarge
}

payload := make([]byte, payloadLen)
if _, err := io.ReadFull(conn, payload); err != nil {
    return err
}

req := AppendRequest{
    Payload:  payload,
    Meta:     buildMeta(session, vh, payload),
    QoS:      fixed.QoS,
    PacketID: vh.PacketID,
    Session:  session.Ref(),
    Deadline: time.Now().Add(appendTimeout),
}

if !appender.TryAppend(req) {
    handleAppendQueueFull(session, req)
}
```

这种模型避免：

```text
大 readBuf 被小 payload slice 长期引用。
完整 MQTT packet 长期驻留。
队列里保存无用协议头。
```

### 6.5 Copy 不是减少 queued payload，而是切断大 buffer 生命周期

如果某个实现或网络框架已经先读到了大 `readBuf`，再 copy：

```go
payload := make([]byte, payloadLen)
copy(payload, readBuf[payloadStart:payloadEnd])
```

这不会让 queued payload 更早 GC。只要 payload 在 queue 中，它就必须存活。

copy 的价值是：

```text
让 queue 引用刚好大小的 payload buffer，
而不是引用一个更大的 readBuf backing array。
```

因此更推荐从源头避免大 readBuf：

```text
解析出 payload_len 后，直接读入 exact-size payload buffer。
```

### 6.6 Byte Budget

所有 queue 都应按 bytes 控制，而不仅按 message count 控制。

推荐限制：

```text
max_payload_size = 8KB / 16KB，按设备协议确定
max_inflight_qos1_upstream_per_client = 1 或 2
max_pending_bytes_per_client = 2 * max_payload_size
max_append_queue_bytes = 512MB / 1GB，按单节点规格压测确定
max_append_queue_messages = 辅助限制
```

入队前先申请预算：

```go
cost := payloadLen + envelopeOverhead

if !globalBudget.TryAcquire(cost) {
    rejectByQoS(session, qos)
    return
}

if !sessionBudget.TryAcquire(cost) {
    globalBudget.Release(cost)
    rejectByQoS(session, qos)
    return
}

req.BudgetCost = cost
appender.Enqueue(req)
```

Kafka ack 或失败后释放预算：

```go
// Kafka ack goroutine 调用：只释放全局预算 + 投递回执，
// 禁止直接操作 Session（红线 #7，契约见 raw log 设计 §4.0）。
func onAppendDone(req AppendRequest, err error) {
    globalBudget.Release(req.BudgetCost) // 无论 session 是否还在，无条件释放

    res := AppendResult{
        ConnID:         req.Session.ConnID,
        SessionVersion: req.Session.SessionVersion,
        PacketID:       req.PacketID,
        QoS:            req.QoS,
        BudgetCost:     req.BudgetCost,
        Err:            err,
    }
    shardOf(req.Session.ConnID).PostResult(res) // bounded 回执队列
}

// per-session 预算释放、PUBACK、断连均由 session 拥有者
// （read loop / shard worker）在 ConnID+SessionVersion fencing 通过后执行。
```

预算释放时机建议保守：

```text
直到 Kafka ack callback 返回后再释放。
```

原因：

```text
Kafka producer 内部可能仍持有 payload 或其副本。
```

### 6.7 QoS0 与 QoS1 的入队策略

QoS0：

```text
正常：进入 append queue。
轻压：限额进入 append queue。
重压：drop。
高压：disconnect。
```

QoS1：

```text
正常：进入 append queue，等待 durable ack 后 PUBACK。
轻压：延迟 PUBACK，限制 inflight。
重压：不再接受新的 QoS1 pending，必要时断连。
高压：fail closed，由设备退避重试。
```

QoS1 不建议在 Broker 内排很多条。

```text
每连接 max_inflight_qos1_upstream = 1 或 2。
```

## 7. 设备重试与去重

### 7.1 重试是可靠性的一部分

QoS1 的语义是 at-least-once，不是 exactly-once。

以下窗口都会产生重复：

```text
Kafka append 成功，但 PUBACK 前 Broker 崩溃。
Kafka ack 返回超时，设备未收到 PUBACK。
Broker 主动断连，设备重连后重发。
设备固件误判超时，重复发送同一采样。
```

因此系统必须把重复当成正常现象。

### 7.2 设备退避

设备连接失败、PUBACK 超时、TCP 断开后，必须退避重试。

推荐：

```text
首次失败：1s ~ 5s 随机
连续失败：5s ~ 30s 随机
持续失败：30s ~ 300s 随机
```

必须带 jitter：

```text
不要固定 5s。
不要所有设备在整点重试。
不要所有设备按同一指数退避曲线同步恢复。
```

### 7.3 服务端错误语义

认证过载：

```text
CONNACK Server Unavailable 或 close。
```

append queue 满：

```text
QoS0 drop / disconnect。
QoS1 disconnect，不 PUBACK。
```

Kafka 不可用：

```text
拒绝新连接或保留心跳。
QoS1 不 PUBACK。
等待设备退避重试。
```

### 7.4 去重字段

Raw message 必须携带：

```text
tenant_id
device_id
boot_id
seq
sample_ts
schema_id
payload_len
payload_crc32
firmware_version
broker_id
broker_receive_ts
```

推荐去重 key：

```text
(tenant_id, device_id, boot_id, seq)
```

兼容旧固件：

```text
(tenant_id, device_id, sample_ts, payload_crc32)
```

（权威定义与字段来源见 [raw log 设计 §3.3](./3.cloud-mqtt-gateway-raw-log-design.md)：tenant_id / device_id 取自认证 envelope，boot_id / seq 取自设备 payload header，由 Decoder 解析。）

## 8. 连接风暴控制

连接风暴与 PUBLISH 风暴本质相同：

```text
输入速率 > 服务速率。
```

只是压力入口从 PUBLISH 变成 CONNECT。

### 8.1 CONNECT 热路径

```text
TCP accept
  -> TLS handshake
  -> CONNECT read deadline
  -> MQTT CONNECT decode
  -> 基础校验
  -> auth cache
  -> auth queue / auth worker
  -> DB read replica
  -> Redis INCR session_version
  -> CAS write Presence
  -> CONNACK
```

任何一层变慢，都可能触发设备重连，进而放大 CONNECT 压力。

### 8.2 控制点

Broker 应限制：

```text
global_connect_rate
per_tenant_connect_rate
per_ip_connect_rate
auth_queue_depth
auth_inflight
db_auth_miss_qps
presence_write_qps
same_device_auth_inflight
```

冷启动时最危险：

```text
auth cache hit rate ≈ 0
db_qps ≈ connect_rate
```

因此不能假设本地 cache 能挡住日出第一次连接风暴。

### 8.3 失败策略

auth queue 满：

```text
返回 Server Unavailable 或 close。
```

DB 超时：

```text
fail fast，不占用连接等待。
```

Presence 写失败：

```text
拒绝连接。
```

Broker 高水位：

```text
停止接受新连接或只接受健康检查 / 管理连接。
```

## 9. 背压水位

### 9.1 水位定义

| 水位 | 状态 | 典型触发 |
|---|---|---|
| L0 normal | 正常 | append ack p99 正常，queue 低水位 |
| L1 soft pressure | 轻压 | ack p99 升高，append queue > 50% |
| L2 hard pressure | 重压 | append queue > 80%，timeout 增多 |
| L3 fail closed | 故障 | raw log 不可用，queue 满，Broker 内存高水位 |

### 9.2 动作矩阵

| 水位 | CONNECT | QoS0 PUBLISH | QoS1 PUBLISH | Existing Session |
|---|---|---|---|---|
| L0 | 正常 | 正常写 raw log | 正常等待 ack 后 PUBACK | 正常 |
| L1 | 限制新连接速率 | 限额写 raw log | 延迟 PUBACK，限制 inflight | 降低读取速率 |
| L2 | 大量拒绝新连接 | drop / disconnect | 不再接收新 pending，必要时断连 | 只保留心跳或低速读取 |
| L3 | 拒绝新连接 | reject | 不 PUBACK，断连 | fail closed |

> v1 实现口径：L1 的"降低读取速率"由 per-client QoS1 inflight=1 + 等 durable ack 天然形成，不实现独立限速器；L2/L3 的"只保留心跳 / 低速读取"在单 TCP 字节流上意味着仍要逐帧解析再选择性丢弃（不读就连 PINGREQ 也读不到），v1 简化为**直接断连**（红线 §5.5）。
>
> 注意 L1 的"延迟 PUBACK"软压挡同样依赖异步执行模型（read loop 不 park 才能边持有未 ack 的 QoS1 边读 PINGREQ）。同步 v1 暂缺该挡，导致本表梯度对 QoS1 实际塌缩为 **L0→L3**（要么秒 ack、要么断连，无中间挡）——这正是 Kafka 抖动 / mass-QoS1 容易放大成断连风暴的根因。完整论证与演进口径见 §4.4，mass-QoS1 准入防护见 §4.5。

### 9.3 水位信号

进入 L1 / L2 / L3 不应只看单个指标。

推荐综合：

```text
raw_log_ack_latency_p99
append_queue_bytes
append_queue_messages
kafka_producer_inflight_bytes
qos1_inflight_count
per_client_pending_bytes
broker_rss
go_heap_live
gc_cpu_fraction
auth_queue_depth
connect_rate
reconnect_rate
connack_server_unavailable_count
```

## 10. 恢复风暴控制

故障恢复也可能造成二次冲击。

典型场景：

```text
Kafka 短暂不可用
  -> Broker 断开大量设备
  -> Kafka 恢复
  -> 设备同时重连
  -> 同时补发 QoS1
  -> Kafka 再次被打满
```

恢复策略：

```text
1. Broker 恢复接入时限速。
2. 每租户设置 connect ramp-up。
3. 设备必须退避并带 jitter。
4. QoS1 per-client inflight 保持 1 或 2。
5. QoS0 在恢复初期继续限额。
6. Kafka producer batch 与 linger 按压测调整，避免恢复期小包打爆。
```

恢复不是瞬间从 L3 回到 L0，而应分阶段：

```text
L3 -> L2 -> L1 -> L0
```

每个阶段观察：

```text
ack latency
queue bytes
connect success rate
reconnect rate
duplicate rate
broker memory
```

## 13. 设计原则清单

### 13.1 必须做

```text
QoS1 等 durable raw log ack 后再 PUBACK。
append queue 按 bytes 限制。
per-client pending bytes 限制。
per-client QoS1 inflight 限制。
CONNECT 认证队列有界。
Presence 写失败时拒绝连接。
设备重试必须退避并带 jitter。
raw message 必须携带幂等字段。
所有压力水位必须有指标和告警。
```

### 13.2 不应做

```text
不要提前 PUBACK。
不要无限 append queue。
不要只按 message count 限制 queue。
不要让小 payload slice 引用大 read buffer。
不要把完整 MQTT packet 长期放入 queue。
不要在 Broker 内做无限本地 WAL / spool。
不要让所有设备固定周期同时重试。
不要在 CONNECT 热路径做复杂 DB 查询。
```

### 13.3 可以接受

```text
QoS0 在高压时丢弃。
QoS1 在高压时断连并由设备重试。
认证系统过载时返回 Server Unavailable。
Broker 故障时由设备重连恢复。
下游通过 dedupe key 处理重复 raw message。
```

## 14. 最终判断

百万级设备接入的核心不是让 MQTT Gateway 扛住所有压力，而是让压力在每一层都被看见、限制和反馈。

```text
无界缓存会把后端抖动变成 Broker OOM。
提前 ACK 会把后端失败变成静默丢数据。
无退避重试会把局部故障变成全局风暴。
无水位恢复会把系统刚恢复又打回故障。
```

因此第一阶段 Broker 的稳定性目标是：

```text
有界内存。
明确承诺点。
可观测背压。
可控失败语义。
可恢复重试节奏。
```

这比单纯追求单节点最高连接数更重要。

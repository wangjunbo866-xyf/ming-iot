## 1. 结论

滚动升级 / 缩容时，一个 Broker 节点的下线**不是 `kill -9`，也不是直接跑 closer-stack**，而是一个**有序、限速、可观测、带超时上限**的编排。没有这个编排，每次滚动升级都是生产实验。

核心判断：

```text
Broker 可以慢慢退。
Broker 退出前必须先不再被 LB 选中。
Broker 必须限速断连，不能一次性全断。
Broker 的 downlink 消费必须活到 presence 清空之后。
Broker 必须排空在途 QoS1 append 再关 Kafka。
Drain 必须有超时上限，不能无限等待。
```

下线顺序错误会引发三类事故（§2），整个协议就是用**严格的阶段顺序**把这三类事故设计排除。

mqtt-gateway 相比 EMQX 的 drain **更简单**：**没有持久会话**（CleanSession=true，红线 #10），所以**不需要 EMQX 的 session 状态迁移**——设备只需断开后由 NLB 重新分发、在别的节点重建无状态连接即可（上行走 Kafka、下行走 gRPC 直连 + presence（Redis），都与具体节点解耦）。

## 2. 三类事故（drain 要排除的失败）

| 事故 | 根因（顺序错误） | 后果 |
|---|---|---|
| **下行黑洞** | 在 presence 仍指向本节点时，就停了 gRPC 下行 endpoint（或先从 Broker Registry 注销前就拒收） | Command Service 仍 gRPC 直连本节点投递，连接被拒/无人处理 → 命令失败 |
| **重发 / 重连风暴** | 一次性全断所有连接 | 全部设备同时重连 → CONNECT/re-auth/re-presence 尖峰打其他节点（§6 §2.3 放大链路、§10 恢复风暴） |
| **拒连风暴** | 仍是 LB 后端时就停了 accept | NLB 把新连接派到正在拒绝的端口 → 客户端连接报错 → 重试风暴 |

排除手段对应三个顺序约束：

```text
先 LB 摘除，再停 accept        → 排除拒连风暴
限速断连 + 设备退避 jitter      → 排除重连风暴
downlink 消费活到 presence 清空 → 排除下行黑洞
```

## 3. EMQX 参考与裁剪

| 能力 | EMQX | mqtt-gateway 裁剪 |
|---|---|---|
| 撤离代理 | `emqx_eviction_agent`：标记节点 evicting → 拒新连接 + 拒新会话 + 可主动逐出 | 借鉴：drain 状态 + 拒新连 + 限速逐出 |
| 节点再平衡 | `emqx_node_rebalance`：evacuation 模式整机撤离，`conn_evict_rate` 限速 | 借鉴：`conn_evict_rate` 限速断连 |
| 会话迁移 | 迁移持久会话状态到其他节点（takeover/handoff） | **不需要**（无持久会话，设备重连即重建） |
| 等待 takeover | 等在途消息 takeover 完成 | 替换为：等 presence 清空 + ingest 在途 append 排空 |
| 进度反馈 | 连接数 / 会话数下降曲线 | 复用：本地连接数 + presence 残留 + ingest 在途 指标 |

一句话：**借 EMQX 的「限速撤离 + 状态机 + 进度可观测」，砍掉它最重的「会话迁移」——因为我们的会话本来就是无状态的、外置在 Redis（presence + registry/lease）/ Kafka（仅上行 raw log），下行是 gRPC 直连，都与具体节点解耦。**

## 4. 与 mqtt-gateway 现有机制的关系

```text
closer-stack（已实现，main.go）：逆构造序关依赖（srv→redis→ingest→kafka→auth→DB）。
  —— drain 是 closer-stack 之前的"集群/LB/连接"层编排；closer-stack 只是 drain 的最后一步（Phase 6）。
presence fencing（已实现，deleteLua）：断连删 presence 带 broker_id/epoch/conn_id/session_version 条件。
  —— drain 限速断连时，设备已在别处重连(session_version 更高)的话，本节点的删除是 NOT_OWNER no-op，不会误删新 presence。
broker_epoch（已实现）：本次进程代次。drain 退出后新进程换 epoch，任何指向旧 epoch 的下行被 fencing 拒。
gRPC 下行 endpoint + Broker Registry 注册（设计中）：下行定向通道。drain 必须保证 endpoint 活到 presence 清空、且先从 Broker Registry 注销（CmdSvc 不再寻址到本节点）。
NLB 无粘性（拓扑决策）：断开的设备由 NLB 随机重分发到其他节点，drain 不需要自己搬连接。
L1/L2 缓存（§5）：被 drain 的节点 L1 随进程消失；新节点 L1 冷但 L2(Redis)热 → 重连设备走 L2 不打爆 DB。
L0-L3 水位（§6 §9）：drain 引发的重连负载用水位反馈做中止判据（§8）。
```

## 5. Drain 协议（有序阶段）

每个阶段标注它排除哪类事故。`▣` = 已有机制可复用，`▢` = 需新增。

```text
Phase 0  准入检查（capacity gate）▢
  确认 N-1 节点能承载本节点的连接 + 重连 λ（auth DB/L2/Redis 余量）。
  不满足 → 拒绝 drain（避免把一个节点的负载压垮其余节点 → 雪崩）。

Phase 1  LB 摘除  ▢   —— 排除拒连风暴
  从 NLB target group 注销 / 健康检查端点转 fail。
  NLB 停止派新连接到本节点，并启动 NLB 自身的连接 draining。
  等待 lb_drain_wait（让 NLB 收敛）。新连接此刻全部去其他节点。

Phase 2  停 accept  ▣(Server.Stop 的 accept 部分可拆出)
  进程停止 accept 新连接；但已建连接、downlink 消费、ingest 继续工作。
  双保险：即便有连接绕过 LB 直连本节点端口也被拒（量极小，因 Phase 1 已让 LB 不派新连）。

Phase 3  限速断连  ▢   —— 排除重连风暴
  按 conn_evict_rate（条/秒）分批主动断开已建连接，不是一次性全断。
  每断一条：read-loop 退出 → defer 按 fencing 删 presence ▣ → 设备按退避 jitter 重连到其他节点。
  持续到 本地连接数 ≤ drain_low_watermark 或 触发 drain_timeout。
  期间持续看其他节点水位（§8 反馈中止）。

Phase 4  排空在途上行  ▢   —— 防 QoS1 静默丢失
  等 ingest 队列在途 QoS1 append 完成（带 ingest_drain_timeout）。
  保证"已回过 PUBACK 的 QoS1"对应的 Kafka durable 都已落地。
  （Phase 3 断连本身对未完成的 QoS1 是 fail-fast 不 ACK，红线 #1/#5；这里排的是断连前已入队、正在等 Kafka durable ack 的那批。）

Phase 5  停 downlink  ▢   —— 排除下行黑洞
  前置条件：本地已无连接 且 presence 已清空（本节点不再是任何设备的 presence 目标）。
  顺序：先从 Broker Registry 注销 gRPC 地址（CmdSvc 不再寻址到本节点）→ 确认上述前置 → 才停 gRPC 下行 endpoint。
  对仍误投到本节点的下行（CmdSvc 拿到 stale presence/registry 直连进来）：回 NOT_HERE，
  Command Service 据此重查 presence / 走 PENDING_DEVICE_ONLINE 兜底（presence 设计 §9.1），只迟发不错发。

Phase 6  关闭依赖（closer-stack）▣
  逆构造序：srv → redis → ingest → kafka → auth → DB。进程退出。
  新版本进程启动 → 重新注册 LB → L1 冷/L2 热预热 → 再 drain 下一个节点。
```

顺序的因果链（为什么不能换序）：

```text
LB 摘除  必须早于  停 accept    （否则 LB 派新连撞拒绝 = 拒连风暴）
限速     必须替代  一次性全断    （否则同时重连 = 重连风暴）
停 downlink 必须晚于 presence 清空（否则命令投到无人消费的节点 = 下行黑洞）
关 Kafka 必须晚于 ingest 排空    （否则在途 QoS1 丢 = 静默丢数据，红线 #1）
```

## 6. 参数与容量约束

```text
conn_evict_rate        断连速率(条/秒)。上界 = 其余节点能吸收的重连 λ：
                       (N-1) 节点的 auth DB miss 预算 / L2 QPS 余量 / Redis 余量 / accept 限流
                       共同决定（认证设计 §6.2 的 R·(1-h) ≤ B_total；drain 的重连就是一段 R）。
lb_drain_wait          等 NLB 连接 draining 收敛（按云厂商 NLB 配置，通常 30s~300s）。
drain_low_watermark    本地连接数降到此值即认为基本排空（剩余尾部交给超时强断）。
drain_timeout          整个 drain 的硬上限。超时 → 强断剩余 + 继续 Phase 4~6，不无限等。
ingest_drain_timeout   等在途 append 的上限。超时 → 记录丢失风险并继续退出（不挂死）。
```

容量约束（Phase 0 准入）：

```text
N-1 节点必须能承载：本节点的稳态连接数 + drain 期间的重连 λ。
drain 窗口选择（重要）：
  - 最佳：日落~日出（光伏设备离线，本就没连接，drain 近乎零成本）。
  - 次佳：白天稳态低谷。
  - 禁止：日出集中上线窗口（λ 已在峰值，再叠加 drain 重连 = 双重尖峰）。
一次只 drain 一个（或有界比例）节点，等它退出+新版本回到 LB+预热后，再 drain 下一个。
```

## 7. Drain 期间的正确性

```text
presence 一致性：限速断连时，设备可能已在 B 节点重连（INCR session_version 更高、CAS 覆盖）。
  本节点 A 断连后的 fencing 删除读到的是 B 的 presence → conn_id/session_version 不匹配 → NOT_OWNER no-op。
  绝不会误删 B 的 presence。（deleteLua 已实现，红线 #8。）
下行不黑洞：downlink 消费活到 presence 清空（Phase 5 前置条件）。清空后 Command Service
  查 presence 不再指向 A，自然不再投递；残留 stale 映射的下行被 A 回 NOT_HERE 兜底。
epoch 防误用：A 退出后新进程换 broker_epoch；任何携带旧 epoch 的下行/presence 操作被 fencing 拒。
QoS1 不丢：Phase 4 排空在途 append；未完成的在 Phase 3 断连时 fail-fast 不 ACK，设备退避重发到 B，
  下游按 (tenant,device,boot_id,seq) 去重（raw log 设计 §3.3）。
```

注意：**drain 不依赖"踢旧连接"（OK_WITH_OLD kick，仍是 TODO）**——drain 是本节点主动断本地连接，设备正常重连到别处走标准 supersede 流程，不需要跨节点 kick。

## 8. 反馈中止（防 drain 引发雪崩）

drain 不是"不计代价排空"，要看其余节点能不能接住：

```text
监控其余节点（或全局）：auth_queue_depth、auth_db_query_qps、connack_server_unavailable_total、
  reconnect_rate、append_queue_bytes、L2 QPS、Redis op/s。
触发阈值（进入 §6/§9 的 L2/L3 水位）→ 暂停 Phase 3 断连（pause evict），
  待负载回落再继续；持续不回落 → 中止 drain，本节点恢复服务（重新注册 LB）。
```

这对应 EMQX rebalance 的"被撤入节点过载则暂停"反馈，是滚动升级安全的关键闸。

## 9. 指标与验收

新增指标（承接红线 §11、压测规划 doc #8 §6）：

```text
drain_state                 0=normal 1=lb_removed 2=accept_stopped 3=evicting 4=draining_ingest 5=downlink_stopped
drain_conns_remaining       本地剩余连接数（排空进度）
drain_conn_evict_rate       实际断连速率
drain_presence_remaining    本节点仍在 presence 中的映射数（应随断连归零）
drain_ingest_inflight       在途未 durable 的 append 数
drain_downlink_not_here_total  drain 期间回 NOT_HERE 的下行数（应短暂出现后归零）
drain_elapsed_seconds       drain 耗时
drain_forced_close_total    超时强断的连接数（应尽量为 0）
```

压测验收（承接红线 §13/§14）：

```text
单节点 drain：N 节点集群 drain 1 个，验证
  - 其余节点 CONNACK 成功率不掉、DB QPS 不超预算（反馈中止生效）。
  - presence_remaining 随 conn_evict_rate 平滑归零，无 NOT_OWNER 误删。
  - drain 期间无下行黑洞（注入下行，断言不丢、最多迟发）。
  - 在途 QoS1 不丢（注入 QoS1 + 制造 Kafka 慢，验证 Phase 4 排空或 fail-fast 重发去重）。
  - goroutine/fd/heap 在节点退出后归零（红线 §7.3 配合）。
滚动升级全流程：逐个 drain 全集群节点，验证全程 CONNACK 成功率、重连波形平滑、无累积 backlog。
drain_timeout 演练：故意制造排不空（设备不退避），验证超时强断 + 仍能干净退出，不挂死。
```

## 11. 实现落点（Phase 2，依赖 gRPC 下行 endpoint + Broker Registry）

```text
internal/server：拆出"停 accept 但不关连接"与"限速逐出"两个动作（当前 Stop 是一步到位全关）。
  新增 Drain(ctx, conn_evict_rate, low_watermark) → 限速断连 + 进度上报。
internal/（新）drain：drain 状态机 + 各 Phase 编排 + 反馈中止 + 指标。
LB 集成：健康检查端点支持 drain 态返回 unhealthy（让 NLB 摘除）。
downlink（依赖 gRPC 下行 endpoint + Broker Registry 实现）：drain 态先从 registry 注销、对误投的 Deliver 回 NOT_HERE；停 endpoint 的前置条件检查。
依赖顺序：本设计的 Phase 5（停 downlink）依赖 gRPC 下行 endpoint + Broker Registry 已实现；在此之前，
  Phase 1~4 + closer-stack 已可构成"无下行阶段"的可用 drain（上行+presence 的优雅下线）。
```

# mqtt-gateway 容量规划：Per-Broker 连接数估算

> 本文把"硬件资源 → 每连接内存占用 → 单节点承载上限"算清楚，给出 Per-Broker 最佳设备连接数和百万集群拓扑建议。是 [实现红线 §4 Pointer-poor Session](./7.cloud-mqtt-gateway-implementation-red-lines.md#4-pointer-poor-session-红线) 的量化延伸，也是"买什么机型、起几个节点"的运维决策依据。
>
> 前提：Session 必须遵守红线 §4.1/§4.2 的 pointer-poor + bounded-memory 约束。若违反（塞 map/channel/string/buffer），每连接常驻内存翻倍以上，本文估算作废。

## 1. 结论

**Per-Broker 最佳设备连接数 = 20-30 万（标准 32GB / 16 vCPU 机型）。**

```text
这个区间是内存（23KB/连接常驻）、CPU（TLS 握手 + 稳态加密解析）、GC（pointer-poor Session
的百万指针扫描）三个约束交叉出来的最优性价比点：
  - 内存只用了约 1/3，留出充足余量给 GC headroom、Kafka buffer、日出握手风暴。
  - CPU 稳态 40-50%，日出握手峰值 60-70%，无过载风险。
  - GC 周期可控（百万指针级 mark），不影响 p99 延迟。

百万集群推荐：4-5 个 25 万节点 + 跨可用区部署。不建议冲百万/节点——那是内存理论值，
GC 周期和握手风暴会吃掉安全余量。
```

## 2. 每连接内存占用模型

### 2.1 Session 结构体（pointer-poor，定长）

基于红线 §4.1 的目标结构：

```go
type Session struct {
    ConnID          uint64    // 8B
    DeviceNumericID uint64    // 8B
    TenantNumericID uint32    // 4B
    SessionVersion  uint64    // 8B
    LastSeenUnix    int64     // 8B
    KeepAliveSec    uint16    // 2B
    Flags           uint16    // 2B
    PendingBytes    int32     // 4B
    InflightCount   int8      // 1B
    Downlink        [4]DownlinkSlot  // 4 × ~32B = 128B
}
```

结构体总计 ≈ 175B，对齐后 **~192B（0.2KB）**。

**pointer-poor 的 GC 含义**：DownlinkSlot 里的指针是 GC 要扫描的，但只有 4 个。百万 Session = 400 万指针扫描单元，可控。若违反红线（塞 map/channel/string），每个 Session 膨胀到几 KB 且指针密度爆炸，GC mark 成本灾难。

### 2.2 连接运行时开销（Session 之外，常驻）

| 项 | 占用 | 说明 |
|---|---|---|
| net.Conn 内部缓冲 | ~8KB | TCP 读/写缓冲（内核 socket buffer + Go bufio） |
| TLS 状态 | ~4KB | 加密上下文（cipher state + 证书链 session） |
| goroutine 栈 | ~8KB（初始 2KB，会 grow） | readLoop 一个 goroutine/连接 |
| MQTT 读状态 | ~1KB | 读包临时状态（fixed header / remaining-length 解析） |
| **常驻小计** | **~21KB** | |

### 2.3 Payload 临时占用（不常驻，瞬态在途）

payload 是短生命周期（收到 PUBLISH → Kafka durable ack 释放），不进 Session。但"在途"时占内存：

```text
QoS1 inflight=1：最坏一条 maxPayloadLen(32KB) 在途
QoS0 fire-and-forget：瞬时，极少同时在途

稳态平均（设备每 10s 上报一次，绝大部分时间无在途）：~2KB
峰值（恰好一条 32KB 在途）：32KB
```

### 2.4 每连接内存总计

| | 占用 |
|---|---|
| 常驻（Session 0.2KB + 运行时 21KB） | **21KB** |
| 瞬态平均（在途 payload） | ~2KB |
| **稳态每连接** | **~23KB** |
| **峰值每连接**（含一条 32KB 在途） | **~53KB** |

> 这是 pointer-poor Session + bounded-memory payload 的结果。若 Session 违反红线（塞 map/string/buffer），常驻从 21KB → 50KB+，峰值更高，本文估算作废。

## 3. 单节点承载上限

### 3.1 按内存（不同机型）

"可用内存"已扣除 OS（1-2GB）、Go runtime + GC headroom（2-3GB）、Kafka producer buffer（1-2GB）、Redis client、其他常驻。

| 机型 | 可用给连接 | 按稳态 23KB | 按峰值 53KB（保守） |
|---|---|---|---|
| 8GB 小型 | ~5GB | ~21 万 | ~9 万 |
| 16GB 中型 | ~11GB | ~47 万 | ~20 万 |
| **32GB 标准型** | ~24GB | **~100 万** | **~45 万** |
| 64GB 大型 | ~50GB | ~217 万 | ~94 万 |

**注意：内存理论上限不等于最佳连接数**——还有 CPU、GC、fd 三个瓶颈（见 3.2）。

### 3.2 非内存瓶颈

**瓶颈 A：CPU（TLS 握手 + 稳态加密解析）**

```text
日出风暴（100 万设备 10 分钟上线）：
  单节点握手速率 = (100万 / 节点数) / 600s
  每条 CONNECT 含 TLS 握手（ECDSA P-256，~1ms CPU）+ MQTT 解析 + DB 认证
  ≈ 2-3ms CPU/CONNECT

稳态：CPU 主要消耗在 TLS 加解密（每条 PUBLISH 都要）+ MQTT 帧解析 + Kafka produce。
16 核机型稳态跑 20-30 万连接的 CPU ≈ 40-60%。
```

**瓶颈 B：文件描述符**

```text
每连接 = 1 个 TCP fd
100 万连接 = 100 万 fd
Linux 默认 ulimit -n = 1024 → 必须调到目标连接数 × 1.2 倍以上
```

**瓶颈 C：GC 压力（pointer-poor 设计的核心意义）**

```text
百万 Session 是长期存活对象。
pointer-poor（每 Session ~4 指针）：百万连接 GC mark ≈ 400 万指针扫描单元，可控
  GC 周期 ~50-100ms，CPU 占比 5-15%
违反 pointer-poor（每 Session 10+ 指针）：GC mark 成本灾难，GC 周期翻倍，p99 抖动
```

## 4. 推荐方案

### 4.1 生产首选：每 Broker 20-30 万连接（32GB / 16 vCPU）

```text
机型：32GB RAM / 16 vCPU / NVMe SSD
连接数：20-30 万（推荐 25 万为规划基线）

内存：
  常驻 23KB × 25万 = 5.75GB
  峰值余量（含在途 payload + Kafka batch + GC headroom）→ 实用约 10GB
  留 22GB 给 OS / Go runtime / Kafka producer / 突发
CPU：
  稳态 40-50%，日出握手峰值 60-70%
fd：
  30 万连接，ulimit 设 60 万（2 倍余量）
GC：
  百万指针级 mark，可控，不影响 p99
```

**安全余量**：内存/CPU 都有 40%+ 余量，应对 flapper 重连风暴、NLB 故障重分配、临时诊断工具（pprof）。

### 4.2 为什么不是 100 万/节点

虽然 32GB 内存理论上能放 100 万连接（稳态 23KB × 100 万 = 23GB），但：

1. **GC 是硬约束**：百万连接的 Session 池让 GC mark 成本陡增。20-30 万是 GC 还很轻松的区间；超 50 万，GC 周期开始影响 p99 延迟。
2. **日出握手风暴**：百万连接集中 10 分钟上线，单节点握手速率 1000+/s，16 核吃紧。20-30 万节点分摊后每节点 200-500/s 握手，舒适。
3. **故障爆炸半径**：单节点挂掉，20-30 万设备重连分散到其他节点，可控。百万节点挂掉是灾难。
4. **运维裕度**：留出内存/CPU 余量给监控、日志、压测、紧急扩容。

### 4.3 备选方案对比

| 方案 | 连接数/节点 | 百万集群节点数 | 内存利用率 | CPU 稳态 | GC 压力 | 适用 |
|---|---|---|---|---|---|---|
| **保守稳定**（推荐） | 20-25 万 | 4-5 个 | ~30% | 40-50% | 低 | **生产首选** |
| 激进紧凑 | 40-50 万 | 2-3 个 | ~60% | 60-70% | 中 | 硬件成本敏感，可接受较高风险 |
| 极限（不推荐） | 80-100 万 | 1-2 个 | ~90% | 85%+ | 高 | 仅压测验证上限，flapper 风暴即雪崩 |

## 5. 百万集群拓扑建议

```text
100 万设备 / 25 万每节点 = 4 个 broker 节点（+ 1 备用）

机型：32GB / 16 vCPU / NVMe SSD
部署：跨可用区分布（2 AZ × 2 节点 + 1 跨区备用）
NLB：最少 4 个目标，单节点故障不影响（NLB 健康检查摘除故障节点，设备重连分散）
Redis L2（认证缓存）：独立 1 主 1 从（不与 broker 共置，避免争抢内存）
PostgreSQL 只读副本：2 个（L2 miss 兜底，主从分担读）
Kafka：独立集群（不与 broker 共置）
```

**为什么 4-5 个节点而不是 2 个大节点**：

- 故障隔离：挂 1 个节点影响 25 万（4 选 1），挂 1 个 50 万节点影响 50 万
- 日出分摊：握手负载分散到更多 CPU
- 滚动升级：逐节点 drain + 重启，每次只影响 25 万设备的 1/4
- 成本：4×(32GB) vs 2×(64GB)，云厂商定价通常前者更便宜（标准机型折扣多）

## 6. 会改变结论的变量

以下任一变化，最佳连接数显著移动：

| 变量 | 影响 | 调整方向 |
|---|---|---|
| **Session 违反 pointer-poor**（塞 map/string/buffer） | 常驻 21KB → 50KB+ | 最佳连接数腰斩到 10-15 万 |
| **设备上报频率高**（每秒多次 vs 每 10s） | 在途 payload 内存上升 | 保守连接数下调 |
| **TLS session resumption 稳态命中** | 日出握手 CPU 降 | 可适当上调连接数 |
| **maxPayloadLen 调到 64KB** | 峰值占用翻倍 | 保守连接数下调 |
| **Kafka batch 做大** | producer buffer 占内存 | 连接数略降但吞吐升 |
| **机型内存密度提升**（如 64GB 降价） | 内存不再是首选约束 | 上限受 CPU/GC 约束，不会线性提升 |

## 7. 验证方法

本文估算是基于红线 §4 设计目标的理论推导，**实际数字必须靠压测验证**（[压测方案 §13](./8.cloud-mqtt-gateway-load-test-plan.md)）：

```text
压测梯度：10 万 → 25 万 → 50 万 → 100 万连接
观测指标（对齐红线 §13 验收项）：
  - go_heap_live_bytes：应 < 可用内存的 50%
  - go_gc_pause_p99：应 < 100ms
  - go_gc_cpu_fraction：应 < 15%
  - mqtt_connect_p99：日出窗口应 < 5s
  - uplink_ack_p99（QoS1）：稳态应 < 50ms
  - fd 使用：应 < ulimit 的 50%

判定标准：
  - 25 万连接：所有指标在红线内 → 该机型可生产
  - 50 万连接：GC/CPU 开始吃紧 → 需更大机型或降连接数
  - 100 万连接：多指标超红线 → 仅作上限参考，不生产
```

## 8. 配套配置（对齐本估算）

基于 25 万连接规划基线，`etc/gateway.yaml` 关键项：

```yaml
server:
  maxConnections: 250000       # 单节点规划基线（不是机型上限，是安全运行值）
  maxPacketSize: 65536
  maxInflightRAM: 8589934592   # 8GB；25万×65536=16GB，需大机型或调低 maxConnections
  # 注意：25万×65536=16GB > 8GB 示例值 → 生产实际应设 maxInflightRAM ≥ 16GB，
  # 或 maxConnections 调到 maxInflightRAM 允许的范围（见红线 §5.1.1 RAM 核算）
ingest:
  maxQueueBytes: 268435456     # 256MiB append 队列（全局，不随连接数增长）
  maxPendingBytesPerClient: 65536  # 单设备在途上限
```

> **注意 maxInflightRAM 与 maxConnections 的核算关系**（红线 §5.1.1）：`maxConnections × maxPacketSize ≤ maxInflightRAM`。25 万 × 65536 = 16GB，所以 32GB 机型的 maxInflightRAM 应设 ≥ 16GB（留 OS/Kafka/Go 余量）。上文"可用 24GB 给连接"的推导与此一致——24GB 容纳 23KB 稳态占用（5.75GB）绰绰有余，maxInflightRAM 约束的是峰值最坏情况（每连接一个 64KB 在途整包）。

## 9. 集群级容量评估：依托 Kafka + Redis 的最大支撑目标

> §1-§8 只算了单节点。本节把 Kafka/Redis/NLB 集群级约束与单节点约束交叉，取最短板，给出 mqtt-gateway 框架的最大支撑连接数。
>
> 前提：下行单播走 gRPC 直连（不进 Kafka，Kafka 仅上行 raw log）、broker registry/lease 复用 Redis（见 [架构 §19 原则 12](./1.cloud-mqtt-gateway-architecture.md)）。

### 9.1 集群级约束逐层核算

集群最大连接数 = 单节点连接数 × 节点数。但节点数和总连接数受三个集群级中间件约束。

**约束 A：Kafka 吞吐（上行 raw log + 下行控制）**

```text
上行 QPS = 连接数 / 上报间隔
  逆变器每 5 分钟（300s）上报一次 700 点位 Modbus 二进制（~1KB/条）
  100 万连接 → 3333 msg/s（~3.3MB/s）
  300 万连接 → 10000 msg/s（~10MB/s）
  1000 万连接 → 33333 msg/s（~33MB/s）

Kafka 单分区吞吐 ~50-200MB/s（视磁盘）
  → 3 broker 集群轻松扛千万级连接的上行
下行控制指令低频（调频/OTA），QPS << 上行，不构成约束

结论：Kafka 不是瓶颈，>1000 万连接的上行都扛得住
```

**约束 B：Redis QPS（presence + 认证 L2 + broker lease）**

Redis 承担三个职责，QPS 特征不同：

```text
1. presence 写（CONNECT 时）：= 连接建立频率
   日出 10 分钟百万上线 = 1667 writes/s（瞬时尖峰，稳态为 0）
2. 认证缓存 L2（L1 miss 时查）：= L1 miss 率 × CONNECT 频率
   日出冷启动 L1 全空 → 全量查 L2 = 1667 reads/s（瞬时尖峰）
3. broker lease 续约（稳态持续）：= 连接数 / lease TTL
   lease TTL=30s 时：100 万 → 33000/s；300 万 → 100000/s；500 万 → 167000/s
4. presence 查（下行投递时）：= 下行指令频率（低频），可忽略

Redis 单实例吞吐 ~10 万 ops/s
Redis Cluster 3 主 3 从 ~30 万 ops/s
```

**稳态 broker lease 心跳是 Redis 的主要负载**。lease TTL=30s 时：

| 集群连接数 | lease QPS | 单 Redis（10万 ops/s） | Cluster 3主（30万 ops/s） |
|---|---|---|---|
| 100 万 | 33000 | ✅ 余量 67% | ✅ 余量 89% |
| 300 万 | 100000 | ⚠️ 打满 | ✅ 余量 67% |
| 500 万 | 167000 | ❌ 超限 | ⚠️ 余量 44% |
| 900 万 | 300000 | ❌ | ❌ 打满 |

**调大 lease TTL（如 60s 或 120s）可线性降低 Redis QPS**——TTL 翻倍，QPS 减半。代价是设备感知 broker 下线变慢（lease 过期才更新 presence）。

**约束 C：NLB 连接数 + 握手速率**

```text
阿里云 NLB 单实例：百万级并发 + 数万 cps（按规格）
日出窗口新建连接速率 = 上线设备数 / 窗口时长
  百万设备 10 分钟 → 1667 cps（NLB 轻松）
  百万设备 1 分钟 → 16667 cps（单实例吃紧，需多实例）

NLB 多实例 + 共享带宽可线性扩展，非硬瓶颈
```

### 9.2 最短板交叉

| 约束 | 扩展方式 | 最大支撑连接数 |
|---|---|---|
| 单节点内存/GC（25 万/节点） | 加节点 | 线性（节点数 × 25 万） |
| Kafka 吞吐（上行） | 加分区/broker | **>1000 万**（不是瓶颈） |
| Redis lease 心跳（TTL=30s） | Redis Cluster + 调大 TTL | **~900 万**（Cluster 3 主极限） |
| Redis lease 心跳（TTL=120s） | 同上 | **~3600 万**（TTL 翻 4 倍） |
| NLB 连接 | 多 NLB 实例 | 线性 |

**最短板是 Redis broker lease 心跳**——这是唯一一个不能靠"加 Broker 节点"线性扩展的约束（Redis Cluster 分片数有上限）。

### 9.3 推荐目标

| 规模 | 连接数 | Broker 节点（25万/节点） | Redis | Kafka | NLB | 适用 |
|---|---|---|---|---|---|---|
| **Phase 1 目标** | **100 万** | 4-5（32GB/16核） | 1 主 1 从（单实例，TTL=30s） | 3 broker | 1 NLB | 当前规划 |
| **扩展目标** | **300 万** | 12-15 | 3 主 3 从 Cluster（TTL=30s） | 3-5 broker | 2-3 NLB | 区域扩张 |
| **极限目标** | **500 万** | 20-25 | 3 主 3 从 + 调大 TTL（60s） | 5+ broker | 3+ NLB | 接近 Cluster 余量下限 |
| **理论上限** | ~900 万 | 36+ | Cluster 3 主极限（TTL=30s） | 不是瓶颈 | 多 NLB | lease 心跳打满 Redis |

```text
突破 500 万的杠杆：
  1. 调大 lease TTL（30s→120s）：Redis lease QPS 降 4 倍，支撑 ~3600 万
  2. Redis Cluster 扩分片（3主→6主→9主）：lease QPS 线性扩展
  3. 两者叠加：理论上限远超千万
```

### 9.4 结论

```text
依托 Kafka + Redis，mqtt-gateway 框架目标最大支撑 300-500 万设备连接：
  Phase 1 目标 100 万（4-5 节点 + 单 Redis + TTL=30s）
  扩展目标 300 万（12-15 节点 + Redis Cluster 3 主 + TTL=30s）
  极限目标 500 万（20-25 节点 + Redis Cluster + 调大 TTL=60s）

Kafka 不是瓶颈（千万级上行都扛得住）。
Redis broker lease 心跳是集群级最短板——稳态每连接每 30s 一次续约，
Cluster 3 主（30 万 ops/s）在 ~900 万连接打满。
突破 500 万需调大 lease TTL 或 Redis Cluster 扩分片。
```

## 10. 演进路径：从百万到千万

> §9 的结论是当前架构支撑 300-500 万。本节给出从百万走到千万的改造方向，以及"提前做 50 万/节点"的可行性评估。

### 10.1 千万级的三个瓶颈

```text
瓶颈 1（集群级）：Redis broker lease 心跳 —— 500 万打满 Cluster 3 主（§9.1 约束 B）
瓶颈 2（单节点级）：GC mark 成本 —— 千万连接 = 千万 Session，pointer 扫描量翻倍
瓶颈 3（运维级）：节点数 × 25 万 = 千万 → 40+ 节点，滚动升级/故障爆炸半径失控
```

### 10.2 千万级改造方向

**方向 1（决定性）：去掉 Redis broker lease，改 presence TTL + fencing 兜底**

当前最短板是 Redis lease 心跳（每连接每 30s 一次 Redis ops）。去中心化后集群扩展不再受 Redis 吞吐约束。

```text
方案 1B（推荐）：lease 退化成 presence TTL + fencing 兜底
  去掉 broker lease 概念，下行投递只查 presence（broker_id + session_version）
  Broker 二次校验（四元组 fencing）兜底——presence 指向已下线 broker 时 fencing 拒绝
  presence 的 TTL 本身隐含 lease 语义（broker 下线 → TTL 过期 → 自然清除）
  
  收益：Redis 回归单一职责（presence + 认证缓存），千万级 presence 写 = 日出窗口 1667/s
  代价：presence TTL 期间（如 12h）下行可能投到死 broker → fencing 拒绝 → CS 重试
        （CS 本来就有重试状态机，架构 §9.4，代价可接受）
```

不推荐方案 1C（gossip 传播，仿 mria）——引入 gossip 违背"极简接入层"定位，过度工程。

**方向 2（单节点）：Session 压缩 + GC 调优**（详见 §10.3）

**方向 3（运维）：K8s 自动扩缩容 + 分集群**

40+ 节点单集群太大（故障爆炸半径、滚动升级窗口）。分多个小集群（如 5 个 × 10 节点），按区域/租户分片。K8s HPA 按连接数/CPU 自动扩缩容，NLB target group 自动注册。

### 10.3 提前做 50 万/节点：可行，但需 Session 压缩

用户提出：在阶段 1 就做 50 万/节点（而非等千万级），让 100 万连接只需 2-3 节点。评估如下。

**50 万/节点的三个约束量化**：

```text
内存（稳态）：50万 × 23KB = 11.5GB → 64GB 机型够（32GB 稳态也够，但 maxInflightRAM 核算需 32GB）
GC mark：50万 × 5 指针 = 250 万指针 → GC 周期 ~200ms，CPU ~18%（超过 15% 舒适线）⚠️ 瓶颈
CPU 稳态：50万连接 → 16 核 70-90%（接近满载）⚠️ 需 32 核
日出握手：50万/节点，2 节点支撑百万 → 每节点 4167 握手/s → 16 核吃紧，32 核安全
```

**结论：50 万/节点 可行，但 GC 和 CPU 是真实瓶颈，必须配套三件事。**

**必做 1：Session 结构体压缩（降 GC mark 成本）**

当前 Session ~5 指针（[4]DownlinkSlot + Filters string）。两个压缩方向：

```text
压缩 A：Filters 改全局索引（省 1 指针）
  设备的 filter 组合实际只有几十种（按产品型号 + 区域），不需每 Session 存 string 本体。
  Filters string → filterIdx uint8（索引到全局 filterPool）
  每 Session 省 1 指针，50 万 Session 省 50 万指针扫描单元。

压缩 B：DownlinkSlot 惰性化（省 4 指针，99% 时间）
  [4]DownlinkSlot → *DownlinkSlots（nil = 无 inflight）
  50 万设备里同时有下行 inflight 的可能只有几千 → 99% 时间 downlinkPtr = nil
  每 Session 省 4 指针（空闲时），50 万 Session 省 ~198 万指针扫描单元。

压缩后：~8 指针/Session（downlinkPtr 99% nil + filterIdx 无指针 + 背景 ~7 指针不变）
  → 50 万 × 8 指针 = 400 万指针（vs 当前 600 万含背景）
  → GC 成本降 ~33%，约等于当前 35-40 万连接的水平（不是 25 万）
  → 详见 [GC mark 计算模型](./reference/go-gc-mark-cost-model.md)
```

压缩 B 的代价：下行投递时检查 downlinkPtr 是否 nil 并按需分配（增加一次分支判断），但下行是低频的（控制指令），开销可忽略。

**必做 2：机型升级 64GB / 32 核**

```text
内存：50万×23KB=11.5GB 常驻 + maxInflightRAM 32GB 预算 → 64GB 够
CPU：32 核稳态 ~45%（50万连接），日出握手 ~30%（32 核分摊）
GC：32 核 mark 并行度更高，周期可降到 ~100ms
```

**必做 3：GC 调优**

```bash
GOGC=200          # 默认 100，调到 200 减少 GC 频率（容忍 2x live heap 才触发）
GOMEMLIMIT=48GiB  # 软内存上限，64GB 机型设 48GB，防 OOM 且让 GC 接近上限时更积极
```

#### 10.3.1 50 万/节点 的可信性评估：是可信目标，不是极限挑战

> 50 万/节点 不是一个"改个 maxConnections 配置就能用"的目标。它是有条件的可信——4 个前提做齐才可信，少一个就滑向极限。

**五维余量核算（Session 压缩后，64GB/32 核）**：

| 维度 | 50 万/节点 余量 | 判定 |
|---|---|---|
| 内存（常驻 16.5GB / 64GB） | 74% | ✅ 充裕 |
| GC mark（压缩后 ~50 万指针 vs 当前 25 万的 125 万） | CPU ~10-13%（<15% 舒适线） | ✅ 可信（前提：压缩 A+B 到位） |
| CPU 稳态（32 核，中低上报频率） | ~10-12%，余量 85-90% | ✅ 充裕 |
| 日出握手（32 核 + session resumption） | ~17-24%，余量 76-83% | ✅ 可信（前提：resumption 生效） |
| **故障爆炸半径（2-3 节点支撑百万）** | **单节点故障 → 剩余节点 75 万连接，超 50 万上限** | **⚠️ 风险** |

**4 个前提（缺一不可）**：

```text
前提 1：Session 压缩（A: filterIdx + B: downlinkPtr 惰性）实现到位
  → 不压缩 = 50万×5指针 = 250万指针，GC CPU ~18%，超 15% 舒适线 → 不可信
  → 压缩 = 50万×1指针 = 50万指针，GC CPU ~10-13% → 可信
  → 压缩是分水岭，不做压缩的 50 万/节点 是极限挑战

前提 2：机型 64GB / 32 核
  → 16 核稳态 70-90%（接近满载）→ 不可信
  → 32 核稳态 ~12%，日出 ~24% → 可信

前提 3：集群至少 3 节点（N+1 冗余）
  → 2 节点：单节点故障 → 剩余 1 节点承受 100 万连接 → 雪崩
  → 3 节点：单节点故障 → 剩余 2 节点各承受 75 万 → 短时可承受（~150% 负载）
  → 设备退避重连 + NLB 健康检查 → 几分钟恢复

前提 4：session resumption 生效（TLS ticket，T1 已修）
  → 不生效 = 每个握手全量 ECDSA，日出 CPU 翻倍 → 32 核也吃紧
  → 生效 = 重复握手走 1-RTT resumption，省 ECDSA → 日出可控
```

**故障爆炸半径的对策**：

```text
对策 1：至少 3 节点（N+1），单节点故障的 50 万重连分散到 2 节点 → 各 75 万（短时可承受）

对策 2：故障时主动降级——节点连接数超 50 万软上限时：
  - 拒绝新连接（返回 Server Unavailable，NLB 健康检查摘除）
  - 对已连接设备降级（QoS0 drop，QoS1 延迟 PUBACK）
  - 等故障节点恢复或 K8s 自动扩容新节点

对策 3：50 万是"安全运行值"，硬上限更高
  压缩后 GC 成本回到 25 万水平 → 内存塞满前的硬极限 ~70-80 万
  50 万设为安全运行值，70-80 万是故障时短时可承受的缓冲
```

**结论**：

```text
50 万/节点 是可信的生产级目标，前提是 4 个条件全做齐：
  Session 压缩 + 64GB/32核 + 3 节点 N+1 + session resumption

正常稳态余量充足（内存 74%、GC 10-13%、CPU 85-90%、日出 76-83%）。
唯一风险是单节点故障的爆炸半径，用 3 节点 + 故障降级兜住。

做不到 4 个前提（尤其 Session 压缩），50 万/节点 退化为极限挑战。
建议：要么配套做齐后上 50 万/节点，要么先用 25 万/节点（4-5 节点）上线，
      后续做压缩升级——两条路都可行，取决于团队对压缩改造的消化能力。
```

### 10.4 调整后的演进路线图

| 阶段 | 目标 | 改造项 | 节点数 | 机型 |
|---|---|---|---|---|
| **阶段 1（提前做 50万/节点）** | **100 万** | **Session 压缩（A+B）+ 64GB/32核** | **2-3（50万/节点）** | **64GB/32核** |
| 阶段 2 | 300 万 | Redis Cluster 3 主 | 6-8 | 64GB/32核 |
| 阶段 3 | 500 万 | Cluster + lease TTL 调大（60s） | 10-12 | 64GB/32核 |
| 阶段 4 | 1000 万 | 方向 1B（去 lease）+ K8s 自动扩缩容 | 20-25 | 64GB/32核 |
| 阶段 5 | 2000 万 | 分集群（federation） | 40（50万/节点） | 64GB/32核 |

**阶段 1 核心收益**：100 万连接只需 2-3 节点（vs 当前 4-5 节点），节点数减半——运维成本、NLB 复杂度、故障爆炸半径都降低。

**千万级的关键改造是阶段 4 的方向 1B（去掉 broker lease）**——这是唯一"不改架构就到不了千万"的硬约束。阶段 1-3 都是加硬件/调参/Session 压缩。

### 10.5 风险提示

```text
压缩 B（downlinkPtr 惰性）改变下行 inflight 内存模型：
  从 [4]DownlinkSlot 固定数组 → *DownlinkSlots 惰性指针
  下行投递时检查 nil 并按需分配 → 增加一次分支 + 偶发堆分配
  下行是低频（控制指令），开销可忽略，但需压测验证

maxInflightRAM 核算（50万×64KB=32GB）需 64GB 机型：
  或调低 maxPacketSize 到 32KB（逆变器 payload 最大 32KB，64KB 本是冗余）
  50万×32KB=16GB，64GB 机型 maxInflightRAM 设 16GB 即可
```

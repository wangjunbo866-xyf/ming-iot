# 云端 MQTT Gateway 下行 Topic 路由设计（可选能力）

> 本文从 [架构设计 §7.9](./1.cloud-mqtt-gateway-architecture.md) 抽出并展开：如何在**不破坏 Broker 的 pointer-poor 与百万容量**的前提下，支持「通用 MQTT 订阅式下发」（设备/应用 SUBSCRIBE 任意声明允许的 topic，平台 publish 一个 topic，匹配的订阅者收到）。
>
> 承接：[架构 §7（南向路由）](./1.cloud-mqtt-gateway-architecture.md)、[Presence Registry 设计](./2.cloud-mqtt-presence-registry-design.md)、[实现红线 §10（下行命令）](./7.cloud-mqtt-gateway-implementation-red-lines.md)。
>
> 参考实现（源码均在本地）：EMQX `apps/emqx/src/emqx_router.erl`、`emqx_topic_index`；NATS `server/sublist.go`、`server/mqtt.go`；MqttWk `mqtt-store`（反面教材）。

---

## 1. 结论

下行 topic 路由**可行，且是干净的加法**——前提是把它做成**下行路由器层的能力，而不是 Broker 的能力**。

```text
默认（逆变器）：身份路由 + 设备档案 DB 解析成员（§7.8）。
可选（其它部门）：topic 路由 —— 订阅外置 Redis 索引 + 匹配在下行路由器 + 喂给身份投递。
红线：匹配器和订阅态永远不上 1M Broker；Broker 收「显式设备清单」，永不匹配 topic。
```

一句话：**借 EMQX 的「定向路由 + 按目标去重」，借 NATS 的「缓存 sublist trie + 订阅外置」，再用三条红线绕开两家各自的扩展性天花板。**

## 2. 目标、非目标与适用边界

### 2.1 目标

```text
支持通用 MQTT 订阅式下发：设备 SUBSCRIBE 声明允许的 topic（含有限通配），平台按 topic 匹配投递。
不引入 Broker 侧订阅树 / topic 匹配 / 每连接订阅态。
不破坏 1M pointer-poor 容量（容量规划 #11）与南向 share-nothing。
复用既有身份投递（§7.8 拆单播）与命令状态机（§9）。
```

### 2.2 非目标

```text
不在 Broker 内做 topic 匹配 / 订阅树 / $share。
不做 retain / 持久会话 / QoS2（沿用架构 §10 范围）。
不为「逆变器」启用——逆变器用 §7.8 的 DB-成员即可，不付订阅索引成本。
```

### 2.3 适用边界（opt-in）

topic 路由是 **per-product / per-tenant opt-in** 的：只有在产品接入配置里声明了「动态订阅能力」的接入，才允许设备 SUBSCRIBE 共享/通配 topic、才付订阅索引成本。逆变器接入默认关闭。

### 2.4 上下行不对称：D2D 与遥测订阅不在范围（含云中转模式）

> 承接 [架构 §1.2](./1.cloud-mqtt-gateway-architecture.md) 的系统定位，在此展开。

一个常见疑问：「下行路由（含本文的 topic 路由）由 Command Service 做，相当于把 Broker 该做的消息路由拆了出来；而上行只进 Kafka——那设备 A publish 的消息，设备 B 收不到，这算缺陷吗？」

**结论：不算缺陷，是与领域匹配的刻意不对称设计**，前提是「device-to-device / MQTT 客户端订阅设备遥测」不在需求内（逆变器域确实不在）。且该设计自洽，不存在「承诺了却做不到」。

#### 2.4.1 本就是两条独立的边，不是对称 pub/sub

```text
上行 = 遥测管道：设备 publish → Broker → Kafka。消费者是后端/Kafka，不是 MQTT 订阅者。
下行 = 定向投递：云发起 → Command Service 路由 → 目标设备。
```

Broker 从不把上行 fan-out 给其它设备订阅者，所以「设备发的消息其它设备收不到」是**预期行为**，不是丢消息。

#### 2.4.2 设计自洽：ACL 本就禁止跨设备订阅

红线规定「受限 SUBSCRIBE：仅设备自己的命令 topic，禁跨设备」。即**没有任何客户端被允许订阅另一台设备的 topic**，因此不存在「我订了 A 的数据却收不到」的破契约。**功能不提供 + 契约一致 = 不是缺陷**；缺陷是「承诺了却做不到」，而这里从未承诺。

#### 2.4.3 这是标准托管 IoT 平台形态

- **Azure IoT Hub** 明确不支持 device-to-device，D2D 必须经云中转。
- **AWS IoT** 设备数据走 Rules Engine 进后端，而非让别的 MQTT 客户端订阅设备遥测做 fan-out。

把路由拆到有 DB/状态机的 Command Service、Broker 保持 lean/无状态——正是这些平台的做法：**用密度换通用性、用云中转换可控**。这不是「拆坏了 Broker」，是换了范式（遥测管道 + 命令通道，而非通用 pub/sub 总线）。

#### 2.4.4 关键澄清：本文的 topic 路由 = egress（云→设备），不含 D2D

本文支持的是「平台 publish 一个 topic → 匹配的设备订阅者收到」，即**云 → 多设备的 egress fan-out**。它**不**支持「设备 A → 设备 B」。**做完本文的能力，D2D 仍然不通**——两者在不同的轴上，别混淆。

#### 2.4.5 什么时候才真的算缺陷（按需求自查）

```text
若需求出现：
  ① 设备 A 的消息要到达设备 B（真 peer D2D）
  ② 某 MQTT 客户端（看板/网关）要订阅设备的实时遥测
→ 当前无 Broker-native 路径，只能：
  (a) 云中转：A → Kafka → 后端消费判断 → Command Service → B（有延迟、需后端逻辑）
  (b) 退回去建 Broker pub/sub（红线 §10 排除、且会破 1M 密度）
```

但 (a) 云中转**往往是 feature 不是 bug**：云可在中间做鉴权 / 审计 / 转换 / 限流，通常本就不该让设备直连互发。即便出现少量「设备协调」需求，云中转常是更优解。

#### 2.4.6 要管理的真实风险：命名与心智模型

叫它「MQTT broker」会让人默认对称 pub/sub，进而惊讶 D2D 不通。它本质是**接入/出口网关**。务必在对接文档显式声明：**上下行不对称、非 pub/sub、跨设备 SUBSCRIBE 禁止、Command Service / 本文 topic 路由 = egress-only（不含 D2D）**。

## 3. 为什么这是个真问题：两块成本必须分开

公司其它部门也想用这套 Gateway，而「topic 路由更通用」。但 topic 路由的成本有两块，性质完全不同：

| 成本 | 随什么增长 | 下行低频能否省 |
|---|---|---|
| **① 每条 publish 的匹配 + fan-out** | 消息速率 | **能省**——下行低频，匹配跑得起 |
| **② 每连接订阅态 + 长寿命匹配结构（trie）** | **连接数**，不是消息速率 | **省不了**——1M 连接就有 1M 份订阅 interest + 一棵长寿命 trie |

下行低频精准杀掉 ①，但 ② 是**连接级**成本：要按 topic 投递，就得知道每个连接订了啥、并维护能匹配的结构——这正是 [pointer-poor 红线（§4）](./7.cloud-mqtt-gateway-implementation-red-lines.md) 要防的长寿命指针图。**低下行量救不了 ②**，这是 EMQX/NATS/MqttWk 都扛不了「百万 pointer-poor 单节点」的根因。

所以可行性 = **能不能把 ② 挪出那台 1M 连接的 Broker。** 能，就可行。

## 4. 三个参考实现剖析（源码核实）

### 4.1 EMQX：`topic→node` 复制路由表 + trie + 定向 + 按节点去重

EMQX 5.x 是**两级路由**，核心是一张全局路由表（`emqx_router.erl`）：

```erlang
#route{topic = <<"foo/bar/baz">>, dest = 'emqx@node1'}   % route 的 dest 是「节点」，不是订阅者
mria:create_table(?ROUTE_TAB_V3,        ...)              % 精确 topic 表
mria:create_table(?ROUTE_TAB_FILTERS_V3, ...)             % 通配 filter 表（emqx_topic_index trie）
{rlog_shard, ?ROUTE_SHARD_V3}                             % ← Mria 复制，全集群一致
```

四个关键点：

1. **路由单位是节点，不是订阅者**：一个节点上 10 万设备订同一 topic，路由表只有 **1 条**（filter→node）；本地订阅者另存本地 ETS。**按 (topic, node) 去重**——比 MqttWk（按订阅者存）省得多。
2. **精确表 + 通配 trie 分开**：精确直查；通配走 `emqx_topic_index`。
3. **定向转发，不广播**：publish 时 `match_routes(Topic)` → 命中的**目标节点集合** → 只转发给这些节点；每节点收到后本地 dispatch。
4. **路由表在 Mria（`rlog_shard`）= 全集群强一致复制**。

**EMQX 的天花板就在第 4 点**：每个 topic 在某节点上「首个订阅者上线 / 末个下线」都要写/删全局路由表 → 跨集群 RLOG 复制。百万设备日出日落 = 路由表 churn 风暴。而且**每设备唯一 topic（`cmd/{device_id}`）= 百万条路由全复制**——这正是开源版建议 ~3 节点的根因（见 [emqx-5.8 集群说明](../emqx-5.8-open-source-cluster-note-2026-04-14.md)）。

### 4.2 NATS：per-server sublist + interest 传播 + JetStream 外置

NATS MQTT（`server/mqtt.go`）**强制依赖 JetStream**（`errMQTTStandaloneNeedsJetStream`）：

```text
匹配引擎：复用 NATS 核心的 sublist（server/sublist.go）——带缓存的 subject trie，
          通配 token *（=MQTT +）/ >（=MQTT #），热 subject 有结果缓存。
订阅态：  MQTT SUBSCRIBE 映射为 NATS 订阅进入 sublist；每 session 有 subs map[string]byte。
持久化：  session / subscription / QoS 消息存 JetStream 流（$MQTT_sess 等）——外置、可跨重连恢复。
跨节点：  interest 传播（server 间只把「有兴趣的 subject」告诉对方）→ 定向，不广播。
```

NATS 是个完整通用 pub/sub 引擎，MQTT 只是协议适配层插在 sublist + JetStream 上。它的特征成本 = **每 server 的 interest 态 + sublist**（所以单 server 连接数中等，非 1M pointer-poor）。

### 4.3 MqttWk：广播 + 通配线性全扫（反面教材）

MqttWk（Java/Netty，`mqtt-store`）：

```text
订阅存 Redis（按订阅者）：subwildcard:{filter} 哈希 + 一个装「所有通配 filter」的 SET。
匹配：    每条 publish 调 search(topic)——精确直查 Redis；
          通配则把【全集群所有通配订阅】从 Redis 全捞出（SMEMBERS + N×HGETALL）逐条线性匹配，无 trie。
跨节点：  收到 publish 后【广播给所有节点】（Kafka/Redis pub-sub），每节点各自 search 投本地订阅者。
```

代价：**O(N) 消息放大**（每消息播所有节点）+ **O(全部通配订阅) 每条匹配** + 每 publish Redis 风暴。中小规模可用，百万 ×3333 msg/s 会瞬间熔毁。它证明的不是「专用设计多虑」，而是「通用 topic 路由要用广播 + 每消息订阅查找换来，封死百万单集群」。

### 4.4 三方对比

| 维度 | MqttWk | NATS | EMQX |
|---|---|---|---|
| 匹配结构 | 无 trie，通配线性全扫 | sublist（缓存 subject trie） | `emqx_topic_index` trie + 精确表 |
| 订阅态存哪 | Redis（按订阅者） | server 内存 sublist + JetStream 持久 | Mria 复制表（topic→node，按节点去重） |
| 跨节点路由 | **广播所有节点** | interest 传播（定向） | match→目标节点（定向） |
| churn 成本 | 每订阅写 Redis | server 间 interest 传播 | **Mria RLOG 全集群复制（最重）** |
| 唯一 topic 高基数 | Redis 膨胀 | 每 server interest 膨胀 | 路由表百万条全复制 |
| 规模定位 | 中小（几千~低万） | 中（十万级/server） | 中大（单集群百万，开源 ~3 节点） |

**共识（也是对 MqttWk 的纠正）**：定向路由，绝不广播。**分歧**在订阅态放哪——EMQX 放强一致复制表（一致但 churn 贵），NATS 放 server 内存 + JetStream（轻但每 server 有 interest 态）。两者在「百万 pointer-poor 单节点 + 每设备唯一 topic」下都会被订阅态/路由态压垮。

## 5. 本设计：借两家之长，绕两家天花板

### 5.1 核心原则：topic 匹配在下行路由器，不在 Broker

把连接级成本 ②（§3）整块挪出 1M Broker：**订阅外置 Redis，匹配在下行路由器（Command Service 层）。Broker 永远不匹配 topic，只按身份投递「显式设备清单」。**

### 5.2 借鉴映射

| 借鉴 | 来自 | 用法 |
|---|---|---|
| 定向路由 + 按目标节点去重（不广播） | EMQX `emqx_router`（topic→node） | 路由器 match 后**按 broker 分组**，每 broker 一条批量投递 |
| 精确表 / 通配 trie 分开 | EMQX（route 表 + filters 表） | 精确共享 topic Redis hash 直查；通配走 trie |
| 带缓存的内存 subject trie | NATS `sublist` | 路由器内匹配器，热 topic 有 cache |
| 订阅态外置持久化 | NATS（sub/session 存 JetStream） | 用 Redis 订阅索引替 JetStream |

### 5.3 绕开两家天花板的三个动作

```text
绕开 EMQX①：订阅索引放 Redis 分片 KV（presence 式），不放 Mria 强一致复制表 → 无 RLOG churn 风暴。
绕开 EMQX②：每设备唯一 cmd topic 不进索引（走身份路由）→ 不产生百万条路由，只索引共享/通配 filter。
绕开 NATS ：匹配器在下行路由器节点，不在 Broker → 1M Broker 上零订阅态，pointer-poor 不破。
```

## 6. 架构与数据流

### 6.1 组件

```text
Broker（接入层，pointer-poor 不变）：
  - SUBSCRIBE 校验 ACL → 写 Redis 订阅索引（只非身份 filter）→ SUBACK；断连/UNSUB 清索引。
  - 暴露 DeliverBatch endpoint：收「显式 device 清单」→ 逐个身份投递。Broker 不匹配 topic。
下行路由器（Command Service 层，things/，不握 1M 连接）：
  - 内存匹配器（sublist 式缓存 trie），数据来自 Redis 订阅索引（增量更新）。
  - publish → match → device_ids → 查 presence 按 broker 分组 → DeliverBatch。
Redis：
  - 订阅索引（精确 hash + 通配 filter 集）+ 既有 presence + broker registry。
```

### 6.2 SUBSCRIBE 流程

```text
设备 SUBSCRIBE(cmd/region/zhejiang/#)
  Broker：
    ① ACL 校验：该 product 接入配置是否声明允许此 filter（含有限通配）—— O(1) / 固定模式比对
    ② 是「身份 topic」（自己的 cmd topic）？是 → 不写索引（走身份路由）；否 → 写订阅索引
    ③ SUBACK
  订阅索引写（Redis，presence 式）：
    精确 filter：HSET subidx:exact:{filter} {device_id} {meta}
    通配 filter：HSET subidx:wild:{filter}  {device_id} {meta}；SADD subidx:wildset {filter}
  Broker session 不变（pointer-poor）；filter 不进 session。
```

### 6.3 下行 publish 流程

```text
平台/业务 publish topic = cmd/region/zhejiang/freq
  下行路由器：
    ① 精确命中：HGETALL subidx:exact:{topic}
    ② 通配命中：在内存缓存 trie 匹配 topic → 命中的 filter → 各自订阅者集合
    ③ 合并 → device_ids → 查 presence → 按 broker 分组（EMQX「按节点去重」借鉴）
    ④ 每 broker：DeliverBatch([device_ids], topic, payload, qos)（限速）
  Broker：
    对 batch 内每个 device_id 身份 lookup 本地连接 → MQTT PUBLISH（+ fencing 校验）
    QoS1 逐设备回执，复用命令状态机（§9）。Broker 不匹配 topic。
```

**与 EMQX 的关键分野**：EMQX `match → 目标 node → 节点本地再 topic 匹配 fan-out`（节点要存订阅 + 匹配 = 破 pointer-poor）；本方案 `match → device_ids 按 broker 分组 → broker 收显式设备清单直接投`——Broker 收的是设备清单不是 topic，**永不匹配**。这是保住 pointer-poor 的精髓。

### 6.4 接口：DeliverBatch

```text
Deliver(device_id, topic, payload, fencing)               // §7.4 单播，身份路由
DeliverBatch([device_id...], topic, payload, fencing[])   // 本文：一 broker 一批，broker 逐个身份投
```

`DeliverBatch` 只是把「路由器已解析好、同一 broker 的多个 device_id」批量投递省往返；Broker 对每个 device_id 仍是身份 lookup + fencing，**不引入任何 topic 匹配**。

## 7. 订阅索引（Redis）设计

### 7.1 只索引「非身份」filter

每设备自己的 cmd topic（`v1/{tenant}/{product}/{device_id}/cmd`）是**身份路由**，不进索引——这避免了 EMQX 式的「百万唯一 topic 全进路由表」膨胀。只有**共享/通配** filter（region/group/产品级/其它部门动态 topic）进索引。

### 7.2 精确 / 通配 分表（呼应 EMQX 双表）

```text
subidx:exact:{filter}  → Hash(device_id → meta)         # 精确共享 topic，O(1) 直查
subidx:wild:{filter}   → Hash(device_id → meta)         # 通配 filter 的订阅者
subidx:wildset         → Set(所有通配 filter)            # 供路由器拉取/构建 trie
subidx:client:{device} → Set(该设备所有 filter)          # 断连清理用（presence 式）
```

### 7.3 生命周期与一致性

```text
写：SUBSCRIBE 时写（presence 式，日出与 presence 同量级；只非身份 filter → 写量大减）。
删：UNSUBSCRIBE / 断连时按 subidx:client:{device} 清理（与 presence delete 同一断连钩子，带 fencing）。
stale：订阅索引可能短暂滞后真实连接 → 路由器解析到已离线设备 → 查 presence 查不到 → 现有兜底
       （NOT_HERE / PENDING_DEVICE_ONLINE，§9.5）接住，只迟发不错发。
```

## 8. 匹配器（下行路由器内）

### 8.1 sublist 式缓存 trie

借 NATS `sublist`：内存 subject trie + 热 topic 结果缓存。只装**通配 filter**（精确走 Redis hash 直查，不入 trie）。trie 在路由器节点，与 Broker 的 1M 连接容量**解耦**——可独立扩、可多副本。

### 8.2 增量更新

```text
路由器订阅「订阅变更事件」（Redis pub/sub 或 stream）→ 增量更新本地 trie；
或周期性从 subidx:wildset 重建（低频 filter 变更下足够）。
trie 只随「distinct 通配 filter 数」增长，不随订阅者数增长（一个 filter 一个 trie 节点链，订阅者挂在叶子）。
```

---

## 9. 三条红线（让它可行的边界）

```text
1. 匹配器（trie/sublist）只在下行路由器，永不上 1M Broker。
2. 订阅索引放 Redis 分片 KV，不放 Mria / 强一致复制表（躲开 EMQX churn 天花板）。
3. 只索引共享/通配 filter；每设备唯一 topic 走身份路由不进索引；
   Broker 侧收 DeliverBatch 的显式 device 清单，不收 topic、不做匹配。
```

## 10. 成本与容量

```text
订阅索引写：只非身份 filter → 砍掉绝大部分写；真有大量动态订阅时与 presence 同量级，一起规划 Redis。
大 fan-out：一条 topic 命中 10 万订阅者 = 10 万次身份投递（限速，架构 §7.8.3 的账）。
匹配开销：  下行低频 → 每 publish 匹配跑得起；trie 内存在路由器，不占 Broker。
broker 增量：仅 SUBSCRIBE 写 Redis + DeliverBatch 收清单逐个投——均 O(1)/批，无 topic 匹配、无订阅树。
```

## 11. 与其它文档 / 红线的关系

```text
架构 §7.1.5：默认身份路由不变；本文是「动态订阅式下发」的可选扩展，Broker 仍不做 topic 匹配。
架构 §7.6  ：不引入「每设备一个内部订阅 churn」——订阅在 Redis 索引，不是 Broker 内部消息订阅。
架构 §7.7  ：不引入 Broker 内 $share / 通配订阅树——匹配在路由器，Broker 零订阅树。
架构 §7.8  ：复用「拆单播 + 身份投递」，只把成员来源从「DB 查询」扩成「DB 查询 或 订阅索引匹配」。
红线 §10   ：下行身份路由 / 不在 Broker 维护订阅树做组播匹配 —— 本文不突破（匹配在路由器）。
```

## 12. 落地阶段

```text
Phase 4（产品化能力，opt-in）：
  ① Broker：SUBSCRIBE ACL 校验 + 写/清 Redis 订阅索引（只非身份 filter）；DeliverBatch endpoint。
  ② 下行路由器：sublist 式匹配器 + 增量更新 + match→分组→DeliverBatch。
  ③ 订阅索引 schema + 一致性（断连清理、stale 兜底）+ 限速。
依赖：架构 §7.8（拆单播 + 身份投递）、§9（命令状态机）、presence、broker registry 已落地。
逆变器主线（Phase 1-3）不依赖本文——本文是为其它部门通用 topic 路由需求预留的可选层。
```

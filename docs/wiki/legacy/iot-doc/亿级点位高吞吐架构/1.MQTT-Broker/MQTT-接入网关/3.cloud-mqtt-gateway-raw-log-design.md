# 云端 MQTT 接入 Broker 与 Raw Log Appender 详细设计

> 本文承接 [百万级设备 MQTT 接入层架构设计](./1.cloud-mqtt-gateway-architecture.md)，展开云端 MQTT 接入 Broker 内部职责、QoS ACK 语义、raw log append、背压策略，以及 JetStream / Kafka / Redpanda 作为 raw log appender 的选型对比。

---

## 1. 结论

生产主链路建议：

```text
逆变器
  -> 自研云端 MQTT 接入 Broker
  -> Kafka / Redpanda raw log
  -> Decoder / OLAP / 时序库 / 告警
```

NATS / JetStream 建议定位：

```text
PoC / 中等规模 raw log：可用 JetStream
百万级长期 raw telemetry 主干：优先 Kafka / Redpanda
```

> 注：下行控制通道经 NATS → Kafka → **gRPC 直连单播** 收敛（详见架构 §19.12）。Kafka **仅承载上行 raw log**；下行单播走 Command Service → gRPC 直连目标 Broker（可达性归 Command Service DB 状态机）。中间件 = Kafka + Redis 两件，NATS 仅保留 PoC 可选。

核心理由：

```text
raw telemetry 是高吞吐 append-only 日志。
它需要按 device_id 分区、保留 7d/30d、支持 replay、多消费组和下游大数据生态。
Kafka / Redpanda 更贴近这个问题。
JetStream 更适合轻量持久消息、控制面、PoC 和较短保留周期。
```

## 2. 云端 MQTT 接入 Broker 职责

Broker 只负责接入层能力：

```text
TCP accept
TLS / mTLS
MQTT packet codec
CONNECT / CONNACK
PUBLISH QoS0/QoS1
PUBACK
PINGREQ / PINGRESP
DISCONNECT
CleanSession=true
认证
基础 ACL
payload size limit
raw log append
QoS1 PUBACK
keepalive
backpressure
本地下行 PUBLISH
presence 注册
```

Broker 不负责：

```text
解码 700 点位
写时序库
写告警表
复杂规则引擎
长期离线消息
retain
QoS2
通用订阅系统
设备影子持久化
```

### 2.1 每连接状态

每连接状态必须极简，且必须 **pointer-poor**。百万长连接下，Session 是长生命周期对象，每个指针字段都会进入 Go GC 的 live heap 扫描图，详见 [实现红线 §4](./7.cloud-mqtt-gateway-implementation-red-lines.md)。

因此 Session **以数字字段为主，用固定小数组替代 map，不保存复杂对象图**：

```go
type Session struct {
    ConnID          uint64
    DeviceNumericID uint64 // 不存 string device_id，存 numeric/interned id
    TenantNumericID uint32
    SessionVersion  uint64

    LastSeenUnix int64
    KeepAliveSec uint16
    Flags        uint16

    PendingBytes  int32 // 该连接当前 pending 的上行 payload 字节数
    InflightCount int8  // 上行 QoS1 inflight，限制 1~2

    // 下行 QoS1 inflight 限制很小(1~4)，禁止用 map[uint16]*DownlinkMessage，
    // 固定小数组更少对象、更少指针、布局固定、GC 扫描成本更低。
    Downlink [4]DownlinkSlot
}
```

注意：**payload 不放进 `Session`**。Session 是长生命周期对象；payload 是短生命周期对象，只应从收到 PUBLISH 存活到 Kafka/Redpanda ack callback 返回，放在 `AppendRequest` 中。详见 [实现红线 §4.1](./7.cloud-mqtt-gateway-implementation-red-lines.md)。

不要在 Session 中保存：

```text
700 点位解析结果
大 byte buffer
离线队列
复杂订阅树引用
大对象缓存
map / channel / time.Timer / interface{}
string device_id / 完整 topic 缓存 / 完整 MQTT packet
```

### 2.2 协议边界

第一阶段建议实现 MQTT 3.1.1 子集：

```text
CONNECT / CONNACK
PUBLISH QoS0/QoS1
PUBACK
PINGREQ / PINGRESP
DISCONNECT
CleanSession=true
```

下行命令如果使用标准 MQTT 语义，需要支持受限订阅：

```text
SUBSCRIBE / SUBACK
只允许设备订阅自己的命令 topic
禁止 wildcard
禁止任意 topic
```

如果固件允许平台直接通过连接写下行 PUBLISH，则可以不暴露通用订阅能力，但必须在协议兼容性测试中确认设备行为。

### 2.3 共享订阅边界

设备接入 Broker 不实现通用 MQTT 共享订阅：

```text
$share/{group}/{topic_filter}
```

上行遥测的负载均衡由 raw log 后面的 consumer group 承担：

```text
MQTT Broker
  -> Kafka / Redpanda raw log
  -> Decoder consumer group
```

这比在 MQTT 层做共享订阅更适合当前场景：

```text
1. raw log 已经是上行 QoS1 的 durable 承诺点。
2. Kafka / Redpanda consumer group 支持分区、offset、replay 和 lag 观测。
3. Broker 不需要维护通用订阅树、共享组成员、选择器和离线队列。
4. 解码、告警、入库的扩容不影响 MQTT 接入层。
```

下行命令也不使用共享订阅或 queue group：

```text
错误方向：
  所有 Broker 订阅 cmd.downlink
  通过 shared subscription / queue group 随机选一个 Broker
  被选中的 Broker 未必持有目标设备连接

正确方向：
  Command Service 查询 Presence Registry + Broker Registry
  gRPC 直连目标 Broker（Deliver）
  目标 Broker 二次校验本地 session
```

SUBSCRIBE 校验策略：

```text
允许：设备自己的命令 topic
拒绝：$share/...
拒绝：wildcard
拒绝：跨设备 topic
拒绝：业务应用任意订阅
```

如果未来需要标准 MQTT shared subscription，应放到独立 Application MQTT Gateway，而不是放进设备接入 Broker。

## 3. 上行 QoS 与 ACK 语义

### 3.1 QoS1

QoS1 的唯一可靠承诺点是 durable raw log append：

```text
收到 PUBLISH
  -> 校验基础合法性
  -> append 到 durable raw log
  -> append 成功
  -> 返回 PUBACK
```

`append 成功` 必须指后端日志系统确认持久化成功，而不是写入本地 producer buffer 成功。

Kafka / Redpanda：

```text
Produce 到 topic partition
  -> acks=all
  -> 满足 min.insync.replicas
  -> Broker 返回 MQTT PUBACK
```

JetStream：

```text
Publish 到 JetStream subject
  -> Stream 持久化成功
  -> Broker 收到 JetStream PubAck
  -> Broker 返回 MQTT PUBACK
```

### 3.2 QoS0

QoS0 没有 MQTT 层 ACK，但正常情况下仍建议走 raw log：

```text
QoS0:
  设备 PUBLISH
    -> Broker 尝试 append raw log
    -> 成功后进入 Decoder
    -> 失败或过载时可以丢弃 / 断连
```

准确语义：

```text
正常水位：QoS0 进入 raw log，便于统一解码、追溯和重放。
压力水位：QoS0 限额进入 raw log。
高压水位：QoS0 直接丢弃或断连。
故障水位：QoS0 全部拒绝，QoS1 不 ACK 并等待设备退避重试。
```

如果业务要求 QoS0 也 100% 持久化、不允许丢弃，那么它在服务端语义上已经接近 QoS1，应按可靠日志链路规划容量、成本和故障恢复。

### 3.3 幂等字段（去重 key 权威定义）

> 本节是去重 key 的**唯一权威定义**，架构设计 §6.4 与背压设计 §7.4 均引用此处。

幂等字段分两层来源，Broker 不解析 payload（红线）：

```text
envelope（Kafka headers，Broker 按认证主体盖章写入，不取自 topic / payload）：
  tenant_id
  device_id
  broker_id
  broker_receive_ts
  mqtt_topic

payload header（设备自报，Broker 原样透传，Decoder 下游解析）：
  boot_id
  seq
  sample_ts
  schema_id
  payload_len
  payload_crc32
  firmware_version
```

设备**无需**在 payload 中携带 tenant_id，身份一律以认证主体为准；禁止为了在 envelope 中填充 boot_id / seq 而让 Broker 解析 payload。

> **mqtt_topic 的 product 段不可信**：mqtt_topic 虽在 envelope headers 里，但它的 product 段是设备可控的——ACL 只校验 product 非空，不校验与认证主体一致（逆变器挂网关下，单认证可对应多 product）。**下游务必从认证身份/注册表取 product，绝不信 mqtt_topic header 的 product 段做鉴权/路由。** tenant_id / device_id 才是 Broker 盖章的可信身份。

权威去重 key：

```text
(tenant_id, device_id, boot_id, seq)
```

必须含 tenant_id：认证表主键是 `(tenant_id, device_id)`，device_id 不保证跨租户全局唯一，缺 tenant_id 会把两个租户的同名设备数据当作重复互吞。

如果设备侧 `seq` 能保证跨重启单调递增，也可以使用：

```text
(tenant_id, device_id, seq)
```

兼容旧固件时可退化为：

```text
(tenant_id, device_id, sample_ts, payload_crc32)
```

但该方案容易受 RTC 不准、重复采样时间、重启后序号归零影响，不建议作为长期主键。

### 3.4 去重键的对抗性边界（Decoder 侧责任）

> **去重实现属于后端 Decoder / Rule Engine，不在 mqtt-gateway 热路径。** Broker 不解码 payload，只把可信身份（tenant_id / device_id）写入 Kafka headers 并把原始 payload 原样写入 value。本节为 Decoder 设计提供威胁输入假设。

`(tenant_id, device_id, boot_id, seq)` 中：

- `tenant_id` / `device_id`：来自 MQTT 认证主体，Broker 盖章，**可信**。
- `boot_id` / `seq`：设备自报，Broker 原样透传，**对抗性（adversarial）**。

被劫持设备（凭证泄露）可主动构造 `boot_id` / `seq`，影响自身数据流：

#### 攻击 1：seq = MAX 导致静默丢数据

```text
攻击者用被盗凭证连接
  -> 发送一条 payload，seq = uint32_max / uint64_max
  -> Decoder 记录该 device 已见过 (tenant, device, boot_id, MAX)
  -> 之后真设备恢复并发送 seq = 1, 2, 3...
  -> 下游 dedup: "seq <= MAX 已见过" -> 全部丢弃
```

结果：该设备后续真实读数被静默吞掉，看起来像离线或没数据，实则是攻击污染。

#### 攻击 2：频繁切换 boot_id 强制重复

```text
攻击者每条消息使用不同的 boot_id
  -> 去重键变成 (tenant, device, boot_id_1, 1),
                 (tenant, device, boot_id_2, 1), ...
  -> 每个 key 都是新的，dedup 不会丢弃
  -> 同一份数据多次入库 / 触发告警 / 污染时序
```

结果：下游数据重复、存储膨胀、告警误报。

#### 爆炸半径

好消息：身份来自 MQTT 认证主体，`tenant_id` / `device_id` 不由 payload 决定，因此攻击者**只能污染被窃取凭证的那个设备自己的数据流**，无法跨设备污染。

#### Decoder 去重必须遵守的对抗性规则

禁止 naive 实现：

```text
// 错误：把 seq/boot_id 当可信字段
if (key 已存在) drop
else 放行
```

必须增加 sanity 检查：

```text
1. seq 单调性约束
   - 同一 (tenant, device, boot_id) 下，seq 应单调递增。
   - seq 回退、长时间停滞、异常跳变应触发异常指标，不要无条件放行或丢弃。

2. seq 上限 sanity
   - 对 seq 最大值做合理边界检查。
   - 接近类型上限（如 uint32_max / uint64_max）的 seq 应触发异常告警，
     并在确认合法前不要把它作为"已见最大值"写入去重状态。

3. boot_id 重置 sanity
   - boot_id 变化应伴随合理的"重启"语义。
   - 同一连接会话内频繁切换 boot_id、或 boot_id 变化但其他字段（如 firmware_version）
     明显不合法，应触发异常告警。

4. 可疑序列的处理策略
   - 不要静默丢弃：可能丢掉真实数据。
   - 不要无条件放行：可能制造重复。
   - 推荐：放行但打异常标记（如 `_dedup_anomaly=seq_overflow`），
     并单独输出到异常 topic 或触发告警，由运营/算法判定。
```

#### 建议的 Decoder 指标

```text
decoder_dedup_hit_total              -> 正常去重命中
decoder_seq_regression_total         -> seq 回退
decoder_seq_near_max_total           -> seq 接近类型上限
decoder_boot_id_churn_total          -> boot_id 异常切换
decoder_dedup_anomaly_marked_total   -> 可疑但未静默丢弃的消息数
```

## 4. Raw Log Appender 抽象

Broker 内部使用 bounded async appender：

```text
MQTT read loop
  -> validate
  -> build RawEnvelope
  -> TryAppend 到 bounded queue
  -> append worker batch 写 Kafka / Redpanda / JetStream
  -> append callback 回到 session event loop
  -> QoS1 发送 PUBACK
```

### 4.0 append callback 的并发契约（必须显式定义）

`append callback 回到 session event loop` 是整个上行链路里最容易产生 data race 和 use-after-close 的地方：callback 跑在 Kafka producer 的 ack goroutine 上，而 session 状态由 read loop 持有。**必须显式约定，禁止 callback 直接读写 session 字段**。

约定如下：

```text
1. Kafka/Redpanda ack callback 不直接操作 Session。
   它只产出一个 AppendResult{ConnID, SessionVersion, PacketID, QoS, BudgetCost, Err}。

2. AppendResult 通过该连接所属 shard 的 bounded 回执队列，
   投递回“拥有该 session 的执行者”（read loop 或 shard worker）。
   只有这个执行者能读写 Session 字段、发 PUBACK、改 PendingBytes/InflightCount。

3. 投递回执时必须带 fencing：用 ConnID + SessionVersion 校验。
   如果 session 已关闭或 version 不匹配（连接已断开/被新连接 takeover），
   丢弃该回执，只释放全局 byte budget，不触碰任何 session。

4. 连接关闭时：先标记 session 失效（version 失配即可拦截在途回执），
   再释放该连接占用的 PendingBytes 预算；
   在途的 append 仍会回调，但因 fencing 失配而被安全丢弃。
```

要点：**payload 的 byte budget 由全局预算负责释放（无论 session 是否还在），PUBACK 与 session 字段修改只能由 session 拥有者执行**。这样 callback 永远不会 use-after-close，也不会与 read loop 竞态。具体执行模型（read loop 自送 vs shard worker）由压测确定，但这条契约不变。

### 4.1 AppendRequest

```go
type AppendRequest struct {
    Envelope RawEnvelope
    QoS      byte
    PacketID uint16
    Session  SessionRef
    Deadline time.Time
}
```

### 4.2 每连接限制

```text
max_inflight_qos1_upstream = 1 或 2
max_pending_bytes_per_client = 2 * max_payload_size
```

### 4.3 全局限制

```text
max_append_queue_bytes = 固定内存预算，例如 512MB / 1GB
max_append_queue_messages = 辅助限制
append_deadline = 2s ~ 10s，按压测调整
```

关键原则：

```text
Broker 不允许无限缓存。
Broker 不把自己变成第二个日志系统。
raw log 慢时，Broker 应变慢、限流、断连，而不是堆内存硬扛。
```

### 4.4 伪代码

```go
func handlePublish(s *Session, p PublishPacket) {
    // ACL：topic 中的 tenant / device_id 必须等于认证主体（防冒充，
    // 见架构设计 §6.5 方案 A），失败即断连，不读 payload。
    if !authorizePublishTopic(s.Principal(), p.Topic) {
        s.Close("publish topic acl denied")
        return
    }

    env, err := buildRawEnvelope(s, p)
    if err != nil {
        s.Close("bad publish")
        return
    }

    req := AppendRequest{
        Envelope: env,
        QoS:      p.QoS,
        PacketID: p.PacketID,
        Session:  s.Ref(),
        Deadline: time.Now().Add(appendTimeout),
    }

    if !appender.TryAppend(req) {
        if p.QoS == 0 {
            metrics.QoS0Drop.Inc()
            return
        }
        s.Close("raw log overloaded")
        return
    }
}

// Kafka/Redpanda ack goroutine 调用，禁止直接操作 Session。
// 只产出 AppendResult 并投递回 session 拥有者 + 释放全局 byte budget。
func onAppendAck(req AppendRequest, err error) {
    globalBudget.Release(req.BudgetCost) // 无论 session 是否还在，预算都要释放

    res := AppendResult{
        ConnID:         req.Session.ConnID,
        SessionVersion: req.Session.SessionVersion,
        PacketID:       req.PacketID,
        QoS:            req.QoS,
        BudgetCost:     req.BudgetCost,
        Err:            err,
    }
    shardOf(req.Session.ConnID).PostResult(res) // bounded 回执队列
}

// 由 session 拥有者（read loop / shard worker）执行，可安全读写 Session。
func (s *Session) applyAppendResult(res AppendResult) {
    // fencing：连接已断开或被 takeover 时，version 失配，安全丢弃。
    if s.ConnID != res.ConnID || s.SessionVersion != res.SessionVersion {
        return
    }
    s.releasePending(res.BudgetCost)

    if res.Err != nil {
        if res.QoS == 1 {
            s.Close("raw log append failed") // 不 PUBACK，设备退避重试
        } else {
            metrics.QoS0Drop.Inc()
        }
        return
    }
    if res.QoS == 1 {
        s.SendPubAck(res.PacketID)
    }
}
```

## 5. 背压策略

| 层级 | 触发条件 | Broker 行为 |
|---|---|---|
| L0 normal | append p99 正常，队列低水位 | 正常读取 socket，正常 append |
| L1 soft pressure | append p99 升高或队列超过 50% | 降低每连接读取速率，限制新 PUBLISH，QoS1 延迟 PUBACK |
| L2 hard pressure | 队列超过 80%，append timeout 增多 | 暂停读取新 PUBLISH，QoS0 优先丢弃或断连，QoS1 等待 append 或超时断连 |
| L3 log unavailable | raw log 不可用或队列满 | 拒绝新连接，已有连接只保留心跳，QoS1 不 ACK 并按超时断连 |

> v1 实现口径：L1 的"降低每连接读取速率"由 per-client QoS1 inflight=1 + 等 durable ack 天然形成，**不实现独立限速器**；"暂停读取 / 只保留心跳"在单 TCP 字节流上意味着仍要解析帧再选择性丢弃（不读就连 PINGREQ 也读不到），v1 简化为**直接断连**（见红线 §5.5），解析-丢弃机制留待后续需要时评估。

背压按字节计，而不仅按消息数计：

```text
append_queue_bytes
append_queue_messages
per_client_pending_bytes
payload_bytes_per_sec
raw_log_ack_latency
```

QoS0 和 QoS1 使用不同优先级：

```text
L0/L1:
  QoS0 -> async publish raw log
  QoS1 -> wait durable ack

L2:
  QoS0 -> 只允许少量进入 append queue，超出直接 drop
  QoS1 -> 继续等待 append，但受 per-client inflight 限制

L3:
  QoS0 -> drop / disconnect
  QoS1 -> 不 PUBACK，超时断连，由设备退避重试
```

## 6. 故障窗口

raw log append 与 MQTT PUBACK 之间天然是 at-least-once，不是 exactly-once。

| 故障窗口 | raw log | 设备是否收到 PUBACK | 结果 | 策略 |
|---|---|---|---|---|
| append 前 Broker 崩溃 | 无 | 否 | 设备 QoS1 重试 | 正常重试 |
| append 成功但 PUBACK 前 Broker 崩溃 | 有 | 否 | 设备 QoS1 重试后产生重复 raw log | 下游按 dedupe key 去重 |
| 后端 ack 丢失或超时 | 不确定 | 否 | Broker 可能断连，设备重试 | 下游去重 |
| QoS0 append 失败 | 无或不确定 | 无 ACK | 数据可能丢 | 记录 drop 指标 |
| raw log 长时间不可用 | 无法写入 | QoS1 不 ACK | 设备退避重连 | Broker fail closed |

## 7. 本地 WAL / Spool 策略

MVP 不建议 Broker 本地落盘做 WAL / spool。

原因：

```text
1. Broker 会从无状态接入层变成状态存储节点。
2. 需要处理磁盘水位、重放顺序、重复 append、文件损坏、机器丢失等问题。
3. 本地积压过多时，恢复阶段可能再次冲击后端日志系统。
4. 运维复杂度接近再造一个日志系统。
```

推荐第一阶段：

```text
PUBACK 只以远端 durable raw log ack 为准。
Broker 最多保留 bounded memory buffer。
raw log 不可用时 fail closed。
```

如果业务要求 raw log 短暂不可用时仍可持续接入，再单独设计本地 WAL：

```text
磁盘容量上限
落盘 fsync 策略
重放顺序
重复消息处理
节点丢失后的数据风险
水位保护与自动降级
```

## 8. Appender 选型对比

### 8.1 总览

| 维度 | NATS JetStream | Kafka | Redpanda |
|---|---|---|---|
| 定位 | NATS 的持久 stream 能力 | 分布式 commit log / event streaming | Kafka API 兼容的流式日志平台 |
| Broker append 语义 | Publish 后等 JetStream PubAck | Producer 等 record ack | Kafka API producer 等 record ack |
| 可靠配置 | file storage + replicas=3 | replication.factor=3 + acks=all + min.insync.replicas=2 | replication.factor=3 + acks=all |
| 横向扩展 | 需要按多个 stream/shard 设计 | topic partitions 天然扩展 | topic partitions 天然扩展 |
| 大吞吐 raw log | 可做，但要谨慎规划 stream leader、replica、磁盘水位 | 成熟主场 | 成熟主场，运维模型更轻 |
| 长保留 / 大数据量 | 可用 max_age/max_bytes 控制 | 很适合 | 很适合 |
| 消费生态 | NATS consumers，简单直接 | Kafka consumer group、Flink、Spark、Connect、OLAP 生态强 | Kafka 生态兼容 |
| 运维复杂度 | 较轻，尤其已有 NATS 时 | 较重，但经验和工具成熟 | 中等，避免 JVM/ZK，但仍需 Kafka 语义运维 |
| 控制面 / RPC | 很适合 | 不适合 | 不适合 |
| 设备命令路由 | 适合做内部 bus | 不建议 | 不建议 |

### 8.2 Kafka / Redpanda 推荐配置

Topic（Broker 按 QoS 与 topic 后缀分流）：

```text
telemetry.raw.critical   # 上行 QoS1 遥测
telemetry.raw.normal     # 上行 QoS0 遥测
command.ack.raw          # 设备 cmd_ack（按 topic 后缀 .../cmd_ack 分流）
```

`command.ack.raw` 把控制闭环从遥测管道中隔离：命令低频，该 topic 几乎恒空闲，APP ACK 延迟不被遥测洪峰的 consumer lag 拖累——同步等 APP ACK 的 API（wait_for=APP_ACK）才能独立承诺 SLA。消费者未来即 Command Service 自身，无需经过 Decoder。

注意：同一设备的消息分布在多个 topic，**跨 topic 无全序**。全量快照 + `sample_ts`/`seq` 幂等语义下无害，但下游不得假设跨 QoS / 跨消息类型有序。

Partition key：

```text
device_id
```

Producer：

```text
acks=all
enable.idempotence=true
compression=lz4 或 zstd
linger.ms=5~20
batch.size=64KB~512KB，按压测确定
delivery.timeout.ms 明确设置
```

Topic durability：

```text
replication.factor=3
min.insync.replicas=2
retention.ms / retention.bytes 按 raw 保留周期设置
```

Partition count 起步建议：

```text
96 / 128 / 192
```

不要拍脑袋上千分区。分区数需要根据 broker 数、目标吞吐、单分区写入、consumer 并发和 controller 元数据压力压测确定。

### 8.3 JetStream 推荐配置

Stream：

```text
stream: TELEMETRY_RAW
subjects:
  telemetry.raw.bucket.*
storage: file
replicas: 3
retention: limits
max_age: 按 raw binary 保留周期设置，例如 7d / 30d
```

Subject：

```text
telemetry.raw.bucket.000
telemetry.raw.bucket.001
...
telemetry.raw.bucket.127
```

Publish：

```text
bucket = hash(device_id) % 128
subject = telemetry.raw.bucket.{bucket}
JetStream Publish(subject, raw_message)
等待 JetStream PubAck
```

不要把普通 NATS publish 当作 QoS1 承诺点：

```text
nc.Publish("telemetry.raw.bucket.042", data)
```

普通 NATS pub/sub 是内存转发语义，不能作为 MQTT QoS1 PUBACK 的 durable 依据。

### 8.4 选型建议

生产主链路推荐：

```text
Kafka / Redpanda 作为 raw log appender（仅上行）；下行单播走 gRPC 直连（不进 Kafka）。
Redis 作为 device presence + broker registry/lease（含 broker gRPC 地址）+ 认证缓存 L2。
```

JetStream 适合：

```text
PoC
中等规模 raw log
保留周期较短
已有 NATS 运维能力
希望统一控制面和轻量持久流
```

Kafka / Redpanda 适合：

```text
百万设备生产遥测主干
长保留 raw binary
多下游 replay
Flink / Spark / OLAP / Connect 生态
更高吞吐和更清晰的分区扩展模型
```

## 9. 容量模型

按 100 万设备、5 分钟一次、3KB payload：

| 场景 | msg/s | raw 入口流量 | R3 写入量 | 判断 |
|---|---:|---:|---:|---|
| 均匀打散到 300s | 3333/s | 约 10 MB/s | 约 30 MB/s | Kafka/Redpanda/JetStream 都可作为目标 |
| 挤在 1 分钟 | 16667/s | 约 50 MB/s | 约 150 MB/s | Kafka/Redpanda 更稳，JetStream 需专项压测 |
| 挤在 10 秒 | 100000/s | 约 300 MB/s | 约 900 MB/s | Kafka/Redpanda 高吞吐设计，可能需要多集群 |
| 挤在 1 秒 | 1000000/s | 约 3 GB/s | 约 9 GB/s | 不应硬扛，必须设备 jitter、Broker 背压、多区域分摊 |

按 payload 大小估算 msg/s：

```text
3KB payload:
  100 MB/s ≈ 34k msg/s
  300 MB/s ≈ 100k msg/s
  1 GB/s ≈ 341k msg/s
```

结论：

```text
10k ~ 100k msg/s 级别是合理生产目标。
百万 msg/s 级别不是单纯 Kafka 问题，而是接入层、网络、磁盘、consumer、下游存储的整体工程问题。
```

# 云端 MQTT 接入 Broker Presence Registry 详细设计

> 本文承接 [百万级设备 MQTT 接入层架构设计](./1.cloud-mqtt-gateway-architecture.md)，展开 Presence Registry、Broker Registry、连接 fencing、两层 lease、Redis/etcd 选型、下行路由校验和故障处理策略。

---

## 1. 结论

Presence Registry 的定位：

```text
Presence 是下行路由提示，不是最终事实。
最终事实以目标 Broker 本地 session 为准。
```

推荐架构：

```text
Redis Cluster：device presence（高频读写）+ broker lease / registry（低频，和 presence 同库）
DB：命令状态、设备档案、历史在线状态
```

下行路由路径：

```text
Command Service
  -> 查询 Presence Registry
  -> 得到 broker_id / broker_epoch / conn_id / session_version
  -> 查 broker registry 取 gRPC 地址 -> gRPC 直连目标 Broker.Deliver
  -> Broker 二次校验本地连接
  -> 本地下行 MQTT PUBLISH
```

核心原则：

```text
1. Presence 可以短暂不准，但不能导致错发。
2. 写入 presence 必须有 fencing 信息。
3. 删除 presence 必须带条件，不能删掉新连接。
4. 不要每台设备频繁续租 TTL。
5. Broker lease 失效即可判定该 Broker 下的 presence 无效。
```

## 2. 数据模型

### 2.1 Device Presence

Redis key：

```text
presence:{tenant_id}:{device_id}
```

Value：

```json
{
  "device_id": "INV_001",
  "tenant_id": "tenant-a",
  "broker_id": "broker-17",
  "broker_epoch": "2026-05-18T01:23:45Z-7f3a",
  "conn_id": 984231,
  "session_version": 128,
  "region": "cn-east-1",
  "connected_at": 1778800000,
  "last_seen": 1778800300,
  "expires_at": 1778886400
}
```

关键字段：

| 字段 | 作用 |
|---|---|
| tenant_id | 防止跨租户串号 |
| device_id | 设备唯一标识 |
| broker_id | 当前连接所在 Broker |
| broker_epoch | Broker 进程启动代次，防止重启后的旧映射误用 |
| conn_id | Broker 本地连接 ID |
| session_version | 设备重连版本，防止旧连接误发 |
| last_seen | 最近上行或心跳时间 |
| expires_at | presence 自动过期时间 |

### 2.2 Broker Lease

Broker lease 放在 Redis（和 presence 同库），key 带 TTL，不引入额外中间件。

Key：

```text
broker:{region}:{broker_id}
```

Value：

```json
{
  "broker_id": "broker-17",
  "broker_epoch": "2026-05-18T01:23:45Z-7f3a",
  "region": "cn-east-1",
  "status": "alive",
  "updated_at": 1778800300,
  "management_addr": "10.0.1.17:9000",
  "control_subject": "downlink.broker-17"
}
```

TTL：

```text
10s ~ 30s
```

## 3. Session Version 与 Fencing

`session_version` 必须由中心化原子序列产生，不能由各 Broker 本地自增。

推荐 Redis key：

```text
presence_seq:{tenant_id}:{device_id}
```

新连接流程：

```text
1. Broker 完成 CONNECT 认证。
2. Redis INCR presence_seq:{tenant_id}:{device_id}，得到 session_version。
3. Broker 生成本地 conn_id。
4. Broker 写入 presence:{tenant_id}:{device_id}。
5. Broker 开始接受该连接上行与下行。
```

为什么需要中心化版本：

```text
两个 Broker 可能同时接到同一 device_id 的重连。
如果 session_version 在本地生成，可能出现相同版本或倒退版本。
下行命令必须能区分新旧连接。
```

边界说明（Redis 异步复制）：failover 可能丢失已确认的 INCR，使计数回退。由于 `presence_seq` 与 `presence` 通过 hash tag 同槽（见 §7.2），且 INCR 先于 presence 写入（复制流 FIFO），回退的最坏后果是新 CONNECT 撞上 `STALE_CONNECT` 被拒、设备退避重试一次后 INCR 越过旧值即自愈；四元组 fencing（broker_id / broker_epoch / conn_id / session_version）保证不会因此错发。无需为此引入 WAIT / 同步复制。

### 3.1 条件删除

断连时不能直接删除 presence。必须带条件：

```text
delete only if:
  broker_id == current.broker_id
  broker_epoch == current.broker_epoch
  conn_id == current.conn_id
  session_version == current.session_version
```

否则旧连接晚断开，可能删除新连接刚写入的 presence。

### 3.2 条件更新 last_seen

如果要更新 `last_seen`，也必须带 fencing 条件：

```text
update last_seen only if:
  broker_epoch / conn_id / session_version 仍匹配
```

但不要每次上报都写 presence。百万设备每 5 分钟上报一次，平均 3333 write/s；在同步上报或重试风暴下会更高。`last_seen` 更适合进入设备状态流或时序库，presence 只负责实时路由。

## 4. 两层 Lease

不要仅依赖每台设备 TTL 续租，否则百万设备会给 registry 带来大量写压力。

推荐两层：

```text
1. broker lease
2. device presence
```

### 4.1 Broker Lease

每个 Broker 定期续租：

```text
broker:{region}:{broker_id}
TTL = 10s ~ 30s
```

Broker 崩溃时，不要求它删除自己名下所有设备 presence。只要 broker lease 过期，Command Service 就把该 Broker 上的 presence 视为无效。

### 4.2 Device Presence

设备连接成功时写入：

```text
presence:{tenant_id}:{device_id}
  -> broker_id + broker_epoch + conn_id + session_version
```

TTL 可以较长：

```text
6h / 12h / 24h
```

理由：

```text
日出上线后，设备通常会在线数小时。
不需要每条遥测都刷新 presence TTL。
Broker 崩溃用 broker lease 判定。
设备自然下线用 last_seen / 业务状态判定。
```

## 5. 写入流程

### 5.1 CONNECT 成功

```text
Broker 收到 CONNECT
  -> 校验 client_id / device_id / tenant_id / 凭证
  -> INCR presence_seq
  -> 生成 conn_id
  -> CAS 写 presence value + TTL
  -> 可选：根据旧 presence 向旧 broker 发 kick
  -> 返回 CONNACK
```

写 presence 与返回 CONNACK 的顺序建议：

```text
先写 presence，再返回 CONNACK。
```

这样设备刚连上后，平台下行已有路由位置。若写 presence 失败，应拒绝连接或进入只上行不可下行的降级模式；生产建议默认拒绝，避免下行状态不一致。

`CONNECT` 写入不能简单覆盖，必须使用 `session_version` 做 fencing：

```text
connect_write_presence:
  current = GET presence:{tenant_id}:{device_id}

  if current 不存在:
    SET new_presence EX ttl
    return OK

  if current.session_version < new.session_version:
    SET new_presence EX ttl
    return OK_WITH_OLD_PRESENCE

  return STALE_CONNECT
```

`STALE_CONNECT` 表示当前连接已经被更新的连接超越，Broker 应关闭该 TCP 连接，不允许它继续成为有效 session。

成功写入后，如果发现旧 presence 指向其他 Broker，可以发起旧连接清理：

```text
new broker
  -> （经 Command Service 中介，或仅 takeover 一次的 broker→broker gRPC）Kick old broker
  -> kick tenant_id / device_id / old broker_epoch / old conn_id / old session_version
```

旧 Broker 只能关闭完全匹配的本地连接：

```text
local.device_id == kick.device_id
local.broker_epoch == kick.broker_epoch
local.conn_id == kick.conn_id
local.session_version == kick.session_version
```

如果不匹配，说明旧连接已经不存在或已经被新连接替代，必须忽略。

### 5.2 DISCONNECT / TCP Close

```text
Broker 检测连接关闭
  -> 条件删除 presence
  -> 删除成功：设备无在线路由
  -> 删除失败：说明 presence 已被新连接覆盖，忽略
```

断连删除也必须原子执行：

```text
conditional_delete_presence:
  current = GET presence:{tenant_id}:{device_id}

  if current 匹配 broker_id / broker_epoch / conn_id / session_version:
    DEL presence:{tenant_id}:{device_id}
    return DELETED

  return NOT_OWNER
```

`NOT_OWNER` 不是错误，通常说明设备已经在其他 Broker 重连，当前旧连接的迟到关闭不应影响新 presence。

### 5.3 运行期 last_seen 更新

不要每条上行 telemetry 都刷新 presence。百万设备每 5 分钟一次平均约 3333 write/s，但同步上报、重试风暴和连接风暴会让写入瞬间放大。

推荐策略：

```text
1. CONNECT 成功时写 presence。
2. Broker lease 周期续租。
3. last_seen 进入独立设备状态流 / 时序库。
4. 如果必须刷新 presence.last_seen，则每连接限频，例如 60s / 300s 一次。
```

`last_seen` 刷新也必须带 fencing 条件：

```text
conditional_update_last_seen:
  current = GET presence:{tenant_id}:{device_id}

  if current 匹配 broker_id / broker_epoch / conn_id / session_version:
    update last_seen / expires_at
    return UPDATED

  return NOT_OWNER
```

`NOT_OWNER` 时不能重新写 presence，应该让当前连接自检本地 session 是否已过期；如果它已经不是最新 session，应主动断开。

### 3.3 presence_seq 生命周期

`presence_seq:{...}` 设计上**永不清理**：

```text
1. 单调性只需 per-device 成立，计数永远向前即可，无上限问题。
2. 设备退役后的孤儿 key 只是一个 64bit 整数，百万级总量内存可忽略。
3. device_id 复用（换机、重新入网）会继承更高的 seq，反而强化 fencing。
```

如确需回收，做离线清理任务（对照设备档案删除退役设备的 seq + presence），不属于在线路径。

### 5.4 Broker 崩溃

```text
Broker 崩溃
  -> broker lease 停止续租
  -> lease TTL 到期
  -> Command Service 查询到该 broker lease 过期
  -> 该 broker 名下 presence 视为无效
  -> 设备退避重连到其他 Broker
```

不需要批量扫描删除该 Broker 名下所有 presence。批量删除会造成 registry 抖动，也容易和设备重连竞争。

## 6. 下行查询与二次校验

Command Service 查询 presence：

```text
presence:{tenant_id}:{device_id}
  -> broker_id
  -> broker_epoch
  -> conn_id
  -> session_version
```

然后查询 broker lease：

```text
broker:{region}:{broker_id}
  -> status=alive
  -> broker_epoch 匹配
  -> control_subject / management_addr
```

下发给 Broker 的内部结构：

```json
{
  "cmd_id": "cmd_123",
  "tenant_id": "tenant-a",
  "device_id": "INV_001",
  "target_broker_epoch": "2026-05-18T01:23:45Z-7f3a",
  "target_conn_id": 984231,
  "target_session_version": 128,
  "payload": "...",
  "qos": 1,
  "expires_at": 1778800600
}
```

Broker 收到后必须二次校验：

```text
1. 本地是否存在 tenant_id + device_id 连接。
2. broker_epoch 是否一致。
3. conn_id 是否一致。
4. session_version 是否一致。
5. 命令是否过期。
6. 设备 downlink inflight 是否已满。
```

可能返回：

```text
OK
NOT_HERE
STALE_BROKER_EPOCH
STALE_SESSION
DEVICE_OFFLINE
INFLIGHT_FULL
EXPIRED
PUBLISH_FAILED
```

Command Service 收到 `NOT_HERE`、`STALE_BROKER_EPOCH` 或 `STALE_SESSION` 后，可以重新查询 presence 并在 TTL 内重试。

### 6.1 为什么下行不使用共享订阅 / queue group

共享订阅或 queue group 只能解决“多消费者分摊消息”的问题，不能解决“目标设备当前在哪个 Broker”的问题。

不建议：

```text
所有 Broker 订阅 cmd.downlink
所有 Broker 加入同一个 shared subscription / queue group
Command Service publish cmd.downlink
消息被随机一个 Broker 消费
```

问题是：

```text
被选中的 Broker 未必持有目标设备连接。
即使该 Broker 成功消费内部消息，也可能只能返回 NOT_HERE。
在高并发下会产生大量无效投递和二次重试。
```

Presence Registry 的职责就是避免这种随机投递：

```text
Command Service
  -> 查询 presence:{tenant_id}:{device_id}
  -> 校验 broker lease
  -> 查 broker registry 取 gRPC 地址 -> gRPC 直连目标 Broker.Deliver
  -> Broker 用 broker_epoch / conn_id / session_version 二次校验
```

因此下行命令的共享消费边界是：

```text
命令状态机可以横向扩容。
Command Service 实例可以共享处理命令任务。
Broker 下行投递不能随机共享消费，必须按 presence 定向。
```

## 7. Registry 选型

| 选型 | 建议 |
|---|---|
| Redis Cluster | 推荐用于高频 device presence 查询与 TTL；同时承载 broker lease/registry（低频，和 presence 同库） |
| etcd | 不推荐承载百万设备 presence；broker lease 已选定 Redis，不引入 etcd |
| NATS JetStream KV | 可用于 broker registry（低频），但本架构已选定 Redis，不引入 NATS |
| MySQL/PostgreSQL | 不建议做实时路由主路径，可做最终状态落库 |

推荐组合：

```text
Redis Cluster：device presence + broker lease / registry
DB：命令状态、设备档案、历史状态
```

### 7.1 Command Service 服务发现边界

Command Service 可以通过 etcd 做 RPC 服务发现和实例 lease：

```text
/services/command-service/{instance_id}
  -> rpc_addr
  -> zone
  -> version
  -> started_at
  -> updated_at
```

实例启动：

```text
1. Command Service 创建 etcd lease，例如 10s ~ 30s。
2. 写入 /services/command-service/{instance_id}。
3. 定期 keepalive。
4. 进程宕机或网络隔离后 lease 过期，endpoint 自动删除。
```

调用方：

```text
业务系统 / API Gateway
  -> watch /services/command-service/*
  -> 本地维护 endpoint 列表
  -> 选择健康实例发起 RPC
```

这能解决：

```text
1. Command Service 实例宕机后的自动摘除。
2. 多实例负载均衡。
3. 滚动升级时 endpoint 动态变化。
```

但它不解决命令可靠性本身。命令状态仍必须落业务 DB：

```text
command_id 唯一约束
status 状态机
lease_owner / lease_until
retry_count
last_error
outbox / delivery attempt
```

Command Service worker 抢占命令时应使用 DB CAS / row lock：

```text
claim only if:
  status in (CREATED, ROUTING, SENT_TO_BROKER)
  and (lease_until is null or lease_until < now)
```

实例故障时：

```text
Command Service 实例挂掉
  -> etcd lease 过期，RPC endpoint 消失
  -> DB 中未完成命令的 lease_until 到期
  -> 其他 Command Service 实例重新 claim
  -> 继续查询 presence 并下发
```

不要使用 etcd 保存大量命令状态或作为命令队列。etcd 适合服务发现、Broker Registry、lease 和小规模配置；命令状态流转应由 DB / outbox / 任务表承担。

### 7.2 Redis Cluster 注意事项

Key 设计应避免热点。注意：本文其他地方 `{tenant_id}` 的花括号是**占位符**，而 Redis Cluster 中字面花括号是 hash tag 语法——最终 key 规范必须显式区分（实现已采用如下格式）：

```text
presence:{<tenant_id>:<device_id>}
presence_seq:{<tenant_id>:<device_id>}

例（字面 key）：
presence:{tenant-a:INV_001}
presence_seq:{tenant-a:INV_001}
```

字面花括号包住 `tenant:device` 作为 hash tag：同一设备的 presence 与 seq 必然同槽，Lua 才能原子执行 INCR-then-CAS；按 `tenant:device` 整体哈希分片，天然打散租户级热点（hash tag 内容含 device_id 即可保证分布均匀）。

### 7.3 Lua / CAS

建议用 Lua 或 Redis 事务封装：

```text
connect_write_presence
conditional_delete_presence
conditional_update_last_seen
```

这样能保证 fencing 条件与写入/删除是原子的。

`connect_write_presence` 至少返回：

```text
OK
OK_WITH_OLD_PRESENCE
STALE_CONNECT
REDIS_ERROR
```

`conditional_delete_presence` 至少返回：

```text
DELETED
NOT_OWNER
NOT_FOUND
REDIS_ERROR
```

这些结果要直接进入 Broker 的连接状态机：

```text
CONNECT CAS 成功 -> 返回 CONNACK
CONNECT CAS 失败 -> 拒绝连接 / 断开
DISCONNECT NOT_OWNER -> 忽略
last_seen NOT_OWNER -> 检查本地 session，必要时断开
```

### 7.4 日出风暴容量模型与分片

> 回答「1M~10M 设备日出风暴，presence 到 Redis 是否扛得住」。**结论：1M 单实例可扛；10M 必须分片（本就该分），决定变量是「设备量 × 日出窗口 × 分片数」。**

**每连接 Redis 开销**

```text
CONNECT  = INCR seq (1 op) + connect Lua EVALSHA (1 op) = 2 ops
DISCONNECT = delete Lua EVALSHA (1 op)
```

两个 Lua 在命中旧值时执行 `cjson.decode`（Redis 单线程里偏重的 CPU），**不能按裸 GET/SET 估吞吐**——保守按「几万 EVALSHA-with-decode/s 单实例」估。

**日出 λ × Redis 负载**（全网同窗、auth 走 [#15 本地快照](./15.cloud-mqtt-credential-local-snapshot-design.md) → ~2λ；若 auth 用 Redis L2 则 ~3λ）

| 场景 | λ(connect/s) | Redis ops/s≈2λ | 单实例(~3~8万 Lua/s)? |
|---|---:|---:|---|
| 1M, 10min | 1,667 | ~3.3k | ✅ 轻松 |
| 1M, 5min | 3,333 | ~6.7k | ✅ 轻松 |
| 1M, 1min | 16,667 | ~33k | ✅ 单实例可（留余量） |
| 10M, 10min | 16,667 | ~33k | ✅ 单实例可 |
| 10M, 5min | 33,333 | ~67k | ⚠️ 逼近单实例 Lua 上限，需分片 |
| 10M, 1min | 166,667 | ~333k | ❌ 必须 Redis Cluster 多分片 |

**三层结构性扩展（为什么实际扛得住）**

```text
1. 日出地理错峰：10M 按时区依次见光，真实瞬时 λ 是【单时区带】量级，远小于全网 D/W
   ——表里 10M/1min=166k/s 是不会发生的悲观上界。
2. presence key 天生可分片（§7.2 hash tag {tenant:device}）：单 key CAS、同槽，
   Redis Cluster M 分片 = M 倍吞吐，线性扩。
3. cell 分片（可选，非 Redis 容量所需）：一个 Redis Cluster 对 presence 随 shard 线性扩，
   10M 单集群即可（内存 ~7GB / 5~8 shard）；cell 是按【爆炸半径 / 地理 / 集群规模(~100M+)】的
   可选切分，不是因为 Redis 顶不住。凭证用堆外本地缓存（不占 Redis、非 cell 约束，见 #5 §5.7）。
```

**削峰与降级**

- **TTL 隔夜过期削峰**：逆变器日落是**断电**（无优雅 DISCONNECT），presence 不被删、靠 TTL 过期。把 presence TTL 设成**隔夜会过期** → 次晨重连命中「无旧值 → 直接 SET」的廉价 no-decode 路径，避开 `cjson.decode` CPU，顺带清掉离线设备的无用 presence。（与 §4.2 长 TTL 的取舍：在线期靠 §5.3 rate-limited 续租维持 presence，而非依赖超长 TTL 跨夜。）
- **限流自钳**：红线 #6（presence 写成功才 CONNACK）+ #9（退避）→ Redis 压力大时回 ServerUnavailable → 设备退避 → λ 自动被 provision 容量钳住。**降级是节流 + 重试，不是雪崩。**
- **但 §9 的代价仍在**：Redis Cluster 整体故障撞日出 = 百万无法上线（主业务为下行陪葬）→ Redis 高可用 + 分片容量必须按 **admitted 峰值**定。

**内存**：10M 设备 = 10M 个 `presence_seq` INCR key 永驻（§3.3：永不清理、可忽略、确需回收走离线任务）+ presence ~10M×600B ≈ **共 7~8GB**，分片集群承载。

**容量原则与验收**

```text
- 原则：不按「全网 D/W」定容量，按【限流允许的 admitted 速率】定，靠地理错峰 + 退避摊平真实 λ。
- 估算：单分片保守「几万 EVALSHA-with-decode/s」，N 分片 = N 倍，留 2~3 倍余量。
- 验收（§11）：日出风暴下 presence op/s、p99、Redis CPU、Lua 耗时、CONNACK 成功率、退避恢复曲线。
  压测必须覆盖「presence 隔夜未过期(走 decode) vs 已过期(no-decode)」两条路径的吞吐差。
```

## 8. 在线状态与 Presence 的边界

Presence 只解决“当前命令应该尝试投给哪个 Broker”。

它不等同于业务在线状态：

```text
业务在线状态 = last_seen + 地域日出日落 + 电站计划 + 告警策略
Presence = 实时路由提示
```

日落断电不应产生百万级强删除或 LWT offline 风暴。

推荐业务状态判定：

```text
last_seen < now - 15min => suspect_offline
last_seen < now - 30min => offline

如果设备所在地已日落，则 offline 不告警。
```

## 9. 故障场景

| 故障 | 现象 | 策略 |
|---|---|---|
| Presence 过期 | 下行查不到设备 | 设备上报触发 pending command 检查 |
| 查到旧 Broker | 下发失败 | Broker 二次校验，返回 NOT_HERE/STALE_SESSION |
| Broker 崩溃 | 其上连接断开 | broker lease 过期，设备退避重连 |
| 旧连接晚断开 | 可能误删新 presence | 条件删除，必须匹配 conn_id/session_version |
| 并发重连 | 多 Broker 同时写 presence | session_version 由 Redis INCR 产生 |
| Redis 短暂不可用 | 新连接无法注册 presence | 默认拒绝连接（fail closed）；事故预案见 §9.1 手动降级开关 |
| Broker lease 抖动 | 下行误判 broker 不可用 | lease TTL 与续租周期留冗余，Command Service 可短重试 |

### 9.1 Presence 手动降级开关（Phase 3，默认关闭）

红线 #6（presence 写失败则 CONNECT 失败）是**默认语义**。它的代价是：Redis Cluster 故障撞上日出窗口时，百万设备会因"下行路由不可注册"而全部无法上线——主业务（遥测上行）为次要能力（低频下行）陪葬。

为事故日预设计一个**运维手动开关**（不自动触发，避免 Redis 闪断造成降级态震荡、避免静默积累幽灵设备）：

```text
开关打开时：
  认证成功 + presence 写失败
    -> 仍返回 CONNACK success
    -> session 打 NOT_ROUTABLE 标记
    -> 上报 presence_degraded_session_count 指标
    -> 后台对 NOT_ROUTABLE session 限频重试 presence 写入，
       成功后清除标记（写入仍走 CAS + fencing）

开关关闭（默认）：维持红线 #6，拒绝连接。
```

语义闭环：NOT_ROUTABLE 期间下行查不到 presence，命令自然落入 `PENDING_DEVICE_ONLINE`，由 device_seen / 定时扫描兜底——**不会错发，只会迟发**。

开关必须进入红线 §14 的降级开关清单与故障演练；打开/关闭都要有审计日志。

## 12. 组件落点与部署拓扑（实现决策）

> 本节记录实现期决策：Presence / Command Service / Broker 三者的**代码落点**与**部署边界**，避免把状态/重依赖塞进对性能红线敏感的 Broker。

### 12.1 落点

| 组件 | 落点 | 理由 |
|---|---|---|
| Presence 写/删 + `session_version`(Redis INCR) + `broker_epoch` + `conn_id` | **Broker 内**（`mqtt-gateway/internal/presence`） | 写在 CONNECT 热路径（红线 #6：CONNECT 成功 = 认证成功 **且** presence 写成功，且在 CONNACK 之前）；fencing token（`conn_id`/`broker_epoch`/`session_version`）只有 Broker 自己持有；10 万 CONNECT/min 风暴下不容许在最关键路径再加一个 RPC 跳 |
| Presence 读 + broker lease 校验 + 下行定向投递 + 命令状态机 | **Command Service**：`things/` 内的 go-zero 服务（如 `things/service/cmdsvr`） | 普通 CRUD + 状态机服务，复用 `share/`（stores / eventBus / errors / clients）、etcd 服务发现、`goctl`；不背 Broker 的性能红线 |
| 存储 | Redis = device presence + broker registry/lease（含 broker gRPC 地址）；Kafka = 上行 raw log（仅上行）；下行单播 = gRPC 直连；DB = 命令状态 | 见 §7 选型 |

**Command Service 不进 Broker 模块、也不单独建仓库。** Broker 是独立 `go.mod`、独立部署、带极端性能红线（pointer-poor / goroutine 预算 / 自研 MQTT codec / 精简可审计依赖）的模块；把 ORM / etcd / asynq 等重依赖塞进去会污染其依赖树并威胁红线。Command Service 放 `things/` 复用现有基础设施最省最稳。

### 12.2 Broker 的南向边界

Broker 对南向（下行）只暴露**一个入口**：一个 **gRPC 下行 endpoint**（`Deliver/Kick/Query`），外加共享的 Redis（presence + broker registry/lease，含 broker gRPC 地址）与 Kafka（仅上行 raw log）契约。下行单播由 Command Service 查 presence + broker registry 寻址后 gRPC 直连目标 Broker（1×N 调用，非 broker→broker mesh），同步回 PUBACK/NOT_HERE 驱动 attempt 状态机；可达性由 Command Service 的 DB 状态机拥有（status/retry/TTL/outbox/lease），投递失败 → 重查 presence 重投（fail-fast + re-resolve，因目标 Broker 是 presence 的函数）。重复投递的幂等由 attempt 状态机 + 四元组 fencing 二次校验覆盖；`SENT_TO_BROKER` 卡死由 §7.1 的 claim 条件接管。设备上线感知不走新通道：Command Service 消费 Kafka raw log 作为 `device_seen`（见架构设计 §9.5）。**Broker 不被 things import，things 也不 import broker**；两者只通过这些契约耦合。下行**全程不沾 Kafka**（不把会过期的路由决策放进持久 log，避免投到 stale broker）。

### 12.3 direct/grpc 双模 vs gRPC 直连下行

things 单体的 `direct/grpc` 双模（如 apisvr↔SysRpc）解决的是 **things 进程内部服务之间**怎么调——能 `direct` 是因为它们可以编进同一个进程。**Broker 永远是 things 之外的独立进程**，因此：

| 调用 | 方式 |
|---|---|
| 业务 / apisvr ↔ cmdsvr | things 的 `direct/grpc` 双模（与 apisvr↔SysRpc 一致） |
| cmdsvr → broker（下行投递） | **gRPC 直连目标 Broker**（presence 查 broker_id + broker registry 取地址）。**无 direct 档**——cmdsvr 进程里没有目标设备的连接，连接握在某台 Broker 手里，只能 gRPC 直连那台 Broker。这是 1×N 调用（cmdsvr → 各 Broker），不是 broker→broker mesh |

```text
业务 / apisvr
  --direct/grpc--> cmdsvr
                     --查 presence(Redis) / broker registry+lease(Redis 取 gRPC 地址)-->
                   gRPC 直连目标 Broker.Deliver(envelope + fencing)
                     --> 目标 Broker --(broker_epoch/conn_id/session_version 二次校验)-->
                   本地 MQTT PUBLISH --> 设备 --> 同步回 PUBACK/NOT_HERE 驱动状态机
```

广播/批量由 cmdsvr 拆成 N 条单播（查设备档案 DB 解析成员 + 限速，复用 §9.8 OTA 编排），Broker 零组播逻辑。

### 12.4 为什么不用 Kafka-as-state 模型（如 Aklivity Zilla）

本设计的 Registry-as-index（Redis presence + gRPC 直连定向 + 四元组 fencing）与 Zilla 式的 Kafka-as-state（session/下行全进 Kafka compacted topic + 消费组消费）是两种不同的南向转发哲学。区别在于：**本设计的下行单播走 gRPC 直连（不进 Kafka），session/presence 外置在 Redis**（显式查询，不进 Kafka compacted topic），Kafka 只承载上行 raw log。经过量化指标对比，**本场景维持 Registry-as-index**。理由：

```text
1. 寻址准确性（presence 显式查询 + 四元组 fencing）—— session 仍外置 Redis，
   不进 Kafka compacted topic，session 迁移窗口的错发率低于 Zilla 的消费组模型。
2. session 外置 Redis，Kafka 只承载消息流 —— Zilla 把 session 也放 Kafka compacted
   topic，引入僵尸 session 清理问题；本设计的 session 是 Redis presence（设备重连即重建）。
3. 中间件精简（Kafka + Redis 两套）—— 去掉 NATS，运维复杂度降低；代价是下行延迟从
   NATS ~1ms 升到 Kafka ~10-50ms（逆变器控制指令可接受）且 Kafka 故障影响上下行。
```

> **延迟与故障域代价（如实记录）**：下行从 NATS 改为 Kafka 后，延迟从 ~1ms 升到 ~10-50ms（受 linger + fetch 周期主导），不再优于 Zilla 的 Kafka-as-state。Kafka 故障也从"只影响上行"变成"影响上下行"。这是减到 2 中间件（去 NATS）换来的代价——架构简化优先于延迟隔离。完整对比见 [对比报告](../reference/aklivity-zilla-comparison-report.md)。

## 19.1 flapping 是什么业务场景

**flapping（连接抖动）**：设备在短时间内反复「CONNECT 成功 → 断连 → 立即重连 → 再断连」的循环。这是 EMQX Cloud 内置的 [Flapping Detected 告警](https://docs.emqx.com/zh/cloud/latest/deployments/alerts_guide/flapping_detected.html) 所防护的故障模式——「某个客户端在短时间内发生高频、反复的连接与断开」。

flapping 的关键特征（区别于凭证攻击）：

- **认证通常都成功**（设备凭证没错，不是凭证攻击——凭证攻击见 [doc 20](20.cloud-mqtt-gateway-credential-attack-defense.md)）
- 频率高（1 分钟内断连重连 15+ 次）
- 持续（不是偶发，是某种持续故障）

### 19.1.1 逆变器的 flapping 来源

| 来源 | 频率 | 特征 |
|---|---|---|
| **4G 蜂窝信号波动**（主要）| 高 | 区域性，信号弱区设备集体抖动 |
| 固件 bug（重连逻辑无退避/jitter）| 中 | 批量，某固件版本的设备都抖 |
| 网络设备故障（基站/路由重启）| 低 | 区域性，恢复后自愈 |
| takeover（设备漂移到新连接，旧连接被踢）| 持续 | 同一设备的反复重连信号 |

> ⚠️ **§19.1.1 自己埋的矛盾**：固件 bug（无退避/jitter）既是 flapping 来源，又会破坏「设备会善意退避」的假设。后文 §19.3.3 会反复用到这个事实——**最会抖的设备最不会退避**。这是已接受的边界，不是漏洞。

### 19.1.2 flapping 不包含什么（边界澄清，防范围蔓延）

flapping 是**连接级别的抖动**（CONNECT-DISCONNECT 循环），不是**包级别的洪水**。下面两类威胁形态上可能和 flapping 并存（同一设备既抖又灌包），但属于不同的防御域，**不在本文范围**：

| 威胁形态 | 归属 | 现有覆盖 | 诚实边界 |
|---|---|---|---|
| **认证成功后的 PUBLISH 洪水**（被劫持合法设备狂发上行）| [doc 6 背压](../6.cloud-mqtt-gateway-pressure-backpressure-design.md) + [doc 9 §5.4 A6](9.cloud-mqtt-gateway-network-attack-defense.md) | 全局/per-client 字节预算（`max_append_queue_bytes` / `max_pending_bytes_per_client`）+ QoS1 inflight=1 | ⚠️ **broker 不崩（survival 真实），但攻击者实时识别是空白**——热路径只拖慢（per-client budget 耗尽 drop），识别走 §6.3 离线基线（小时级），kick 是 Phase 2。期间恶意设备与合法设备挤在同一条 drop 管道，无法区分 |
| **大规模 SUBSCRIBE/UNSUBSCRIBE** | 第一阶段 SUBSCRIBE 几乎不实现（仅设备自己的 cmd topic，禁 wildcard/跨设备/$share）| 结构性免疫——`dispatch` 不路由 SUB/UNSUB（[doc 18 §18.3.3](../18.cloud-mqtt-gateway-comqtt-packets-extraction.md)），解码后 fall through | v1 是 no-op；但 doc 14 动态路由能力落地后会出现新的攻击面（无 SUBSCRIBE 速率限制），届时需独立设计 |

> 📌 **反面教材：NanoMQ GHSA-v57q-w88m-424r**。该 advisory 的 PoC 含「rapid reconnect + massive SUB/UNSUB」，读细节会发现它本质是 **C 语言 QUIC 传输层的 use-after-free**（`aio->prov_data` 指针生命周期 bug → 堆损坏 → SIGABRT），**不是 flapping 攻击模式**——修复是改代码，不是限流。mqtt-gateway 结构上双重免疫：Go 的 GC 消除 UAF/堆损坏，且第一阶段无 QUIC。但它揭示的「认证后恶意设备」前提确实存在（见上一行 PUBLISH 洪水的诚实边界），由 doc 9 A6 信号 + §6.3 离线判定承接，不在本文 flapping 热路径。**不要把这类包级洪水塞进 flapping 定义**——会重蹈 token-bucket 混在 doc 19 里导致失焦的覆辙。

## 19.2 flapping 的危害（三层）

flapping 之所以必须防御，是因为每一次「连接-断连」循环即使最终被拒绝，都是一次完整的资源分配与释放过程。在 mqtt-gateway 架构下，危害分三层：

### 19.2.1 第 1 层：单节点资源耗尽

这是最直接的危害。每次 CONNECT 都烧掉认证链路 + presence 写入的完整成本：

| 资源 | 每次 CONNECT 的消耗 |
|---|---|
| **auth worker** | 一次完整认证（即使 L1 命中，也要走完校验流程）|
| **Redis presence ×2** | 一次 ConnectWrite（CAS）+ 断连时一次 fencing delete |
| **fd / 临时端口** | 每个连接占用一个文件描述符和临时端口，耗尽后无法服务合法客户端 |
| **连接槽** | 快速建立又断开的连接会挤占 MaxConnections 上限（[doc 21 §21.3.3](21.cloud-mqtt-gateway-accept-rate-limit-design.md)）|

高频 flapping 会迅速耗尽 Broker 所在节点的资源。⚠️ **关键放大效应**：flapping 设备每次重连都重新排队认证 + 重写 presence，把单设备的抖动放大成对 auth worker / Redis 的持续压力（[gnet 走查 §8.7.7 认证洪水四道闸门](../reference/gnet/gnet-source-walkthrough.md)）。

### 19.2.2 第 2 层：后端状态频繁更新与一致性压力

> ⚠️ **架构适配说明**：EMQX 是 mria **core + replicant 紧耦合集群**，客户端连接状态变化需要节点间 RPC 同步——高频 flapping 会形成元数据同步风暴，大量消耗集群内部网络带宽，严重时导致心跳检测失败、网络分区（Network Partition）甚至「脑裂」。**mqtt-gateway 是松耦合多 Broker 架构**（多 Broker + Redis presence + Kafka append，无 mria），**没有 mria 分区/脑裂风险**——对应危害转移到 **Redis presence 写删风暴**：

| 维度 | EMQX（mria 集群）| mqtt-gateway（Redis+Kafka 松耦合）|
|---|---|---|
| 连接状态同步 | 节点间 RPC 元数据同步 | **Redis presence 写删**（每个 Broker 独立写自己的连接条目）|
| 高频 flapping 的第 2 层危害 | 元数据同步风暴 → core 节点瓶颈 → 心跳失败 → 脑裂 | **presence 频繁写/删 → Redis QPS 飙升 → fencing 失败率上升** |
| 一致性风险 | 网络分区、数据无法同步、需人工介入 | presence 脏写（条目存活但连接已死）、下行打到死连接 |

mqtt-gateway 在这一层的具体危害：

- **presence 写删风暴**：每次 flapping 循环 = 1 次 ConnectWrite CAS + 1 次 fencing delete。flapping 设备在达到封禁阈值（~15 次）前要烧 ~15 × 2 = 30 次 presence Redis 写。区域性 flapping 事件（基站恢复影响上万设备）会把 presence Redis QPS 推到容量红线。
- **fencing 失败率上升**：频繁建断连导致 presence 条目频繁写/删，CAS 竞态与 fencing 校验失败率上升（[doc 2 presence fencing](../2.cloud-mqtt-presence-registry-design.md)）。
- **presence 脏写**：快速建断连循环中，条目可能「存活但连接已死」，下行投递会打到死连接（依赖 NOT_HERE 语义兜底）。

### 19.2.3 第 3 层：业务逻辑受损

- **QoS1 PUBACK 循环断裂**：会话的频繁重建导致正在传输的 QoS1 消息无法完成 PUBACK 循环，设备不断重发 PUBLISH（放大上行负载）。
- **离线会话堆积**：若未来开启 Clean Session=false（第一阶段不做，[红线 #10](../7.cloud-mqtt-gateway-implementation-red-lines.md)），每次连接都会创建持久会话，flapping 会导致大量无效离线会话堆积，占用存储。
- **重连雪崩**：一个 Broker 故障时，其上大量客户端同时尝试重连到其他 Broker，引发重连风暴（doc 6 §10），进而拖垮整个集群。
- **监控干扰**：flapping 使连接数虚高、close 事件虚高，干扰运维对真实在线数的判断。

### 19.2.4 flapping 防御的目标

> 快速识别抖动设备，短时封禁，使后续重连被**廉价拒绝**——把单设备对 auth worker / Redis 的放大效应降一个数量级。

⚠️ **关键 framing（容易理解错）**：封禁的价值是**省掉昂贵的认证链路**，**不是指望坏固件设备按 ServerUnavailable 退避**。恰恰相反——§19.1.1 把「无退避/jitter 固件」列为 flapping 来源，最会抖的设备最不会退避（[doc 7 红线 #8](../7.cloud-mqtt-gateway-implementation-red-lines.md) 要求设备 jitter，但对不合规固件不成立）。短时封禁的真实作用是「在 TTL 内把每次重连从『完整认证 + 2 次 Redis』压成『认证前 O(1) 拒（双检查点①命中）』或最差『认证后、presence 写入前拦截（检查点②）』」。

## 19.3 公网场景的核心约束：不可信 key 不聚合

> 📌 **高被引小节**（[doc 20](20.cloud-mqtt-gateway-credential-attack-defense.md) §20.3、TODOS #9 引用本节）。

mqtt-gateway 是公网接入层，设备身份在认证前不可信。这导致 flapping 检测机制本身可能被武器化——这是本文设计不能照搬 EMQX 的根因。

### 19.3.1 攻击 1：逼你 ban IP（自伤攻击）

```
攻击者从一个 CGNAT 出口 IP 发 500 个 CONNECT，每个用不同 clientID
  → 如果 flapping 按 clientID 计数：每个 clientID 只计 1 次，都不命中（阈值 15）
  → 如果 IP 维度计数到 500，命中阈值 → IP 被拉黑
  → ⚠️ 这个 IP 是 CGNAT 出口，上万真实设备被连坐
  → 攻击者用 1 个 IP 牺牲，ban 掉了上万真实设备（DOS 放大）
```

> 📌 **高被引锚点**（[doc 20](20.cloud-mqtt-gateway-credential-attack-defense.md) §20.3.1/§20.8 引用本节「逼你 ban IP 自伤」）。

### 19.3.2 攻击 2：撑爆 flapping 计数表（内存攻击）

```
攻击者控制僵尸网络（10 万 IP），每个 IP 发 1000 个 CONNECT，每个不同 clientID
  → 维度 1（clientID）：10 万 × 1000 = 1 亿个 clientID 计数条目
  → 每个条目 {clientID, started_at, cnt} ≈ 几十字节
  → 计数表从正常的几万条膨胀到 1 亿条 ≈ 几 GB
  → ⚠️ 内存爆炸 + map 查找退化
```

**flapping 计数表（如果按不可信 key 聚合）本身变成内存攻击面**。

### 19.3.3 根因：不可信输入不能聚合计数

攻击面 1/2 的根因是：**认证前的维度（clientID/IP）是攻击者可控的输入**。用它们做 flapping 计数的 key，等于让攻击者控制你的内存结构。

**核心原则**（贯穿 doc 19/20/21 三篇）：

> **认证前（key 不可信）：只做限流（rate limit），不做 flapping 计数。**
> （[doc 21](21.cloud-mqtt-gateway-accept-rate-limit-design.md) 用一个不分 key 的全局令牌桶挡总量洪水）
>
> **认证后（key 可信）：才做 flapping 计数。计数表大小 ≤ 在线设备数，天然有界。**
> （本文 §19.4 用认证后 numeric deviceID 做计数）

## 19.4 mqtt-gateway flapping 设计：认证后 deviceID 计数

遵循 §19.3.3 的核心原则，flapping 计数放在**认证成功之后**，按可信的 numeric deviceID 聚合。

### 19.4.1 计数时机：OnClose + close-reason 分类

**时机**：OnClose（断连时），**只对「认证成功 且 close reason 属于设备行为」的连接计数**。

**close reason 分类（计数语义 = 设备行为引发的连接更替）**：

| close reason | 计数？ | 理由 |
|---|---|---|
| clientClose / readTimeout / netErr（设备侧断连）| ✅ | 设备行为 |
| serverKick（presence OK_WITH_OLD 踢旧连接）| ✅ | takeover 本身就是该设备的重连信号。4G 半开场景下 flapping 周期的断连**大多以 kick 形态出现**（旧连半开挂着、新连顶替、新连存活到下一轮再被踢——整个周期没有任何一次设备侧 close），排除 kick = 对主流 flapping 形态失明。且不会双计：takeover 周期只有 kick 一种 close，自断周期只有 netErr 一种，每周期恰计 1 次 |
| serverOverload（[红线 #5](../7.cloud-mqtt-gateway-implementation-red-lines.md) append 满断连）| ❌ 独立指标 | 根因是后端不是设备。若计数：Kafka 抖动 → 反复过载断连 → 无退避固件 15 次/min 达阈值 → **无辜设备批量进黑名单**，后端恢复后仍被封到 TTL 到期 + 解禁雷鸣群，把故障放大成事故 |
| serverDrain（[doc 12](../12.cloud-mqtt-gateway-drain-rolling-upgrade-design.md) 滚动升级排空）| ❌ 独立指标 | 运维行为，非设备行为 |
| serverPresenceFail / STALE_CONNECT（认证成功但 presence 写失败/CAS 竞态）| ❌ 独立指标 | 后端/竞态根因（同 serverOverload 的误封逻辑）。这些路径已烧掉 auth + Redis 成本，独立指标监控其量级 |

**实现纪律（红线）**：所有服务端主动 Close 的调用点必须**先写 session.closeReason 再 Close**（session 加 1 字节 reason 字段，pointer-poor 兼容）；未标注的缺省 = netErr（计数）。gnet `OnClose(c, err)` 的 err 只有 EOF/nil 级信息量，**不得**用作分类来源——分类唯一来源是业务层关闭前写入的 reason。

### 19.4.2 计数表实现：分片 map + noscan 值语义

```go
// 认证后的 flapping 计数表，key 是可信的 numeric deviceID。
//
// ⚠️ 存储形态（对齐 doc 7 §2 pointer-poor 红线 + doc 15 §5.1「必须 noscan」决策）：
// 50 万在线 = 50 万计数条目。若用 map[int64]*flapCount（每条目一个堆上小对象），
// GC mark 要扫 50 万个 *flapCount 指针图，与「长期数据结构必须 noscan / pointer-poor」
// 的方向冲突（doc 15 §5.1 把这个选型论证为硬约束：map[string]*Record 违反红线 §2，
// 改用 map[uint64]CredRecord 值语义让 bucket 数组 noscan）。本表照搬同一决策：
//   - map 用**值语义** map[int64]flapCount（非 *flapCount），bucket 数组 noscan，
//     GC 只扫 overflow bucket（几万级），不再扫 50 万个堆对象。
//   - flapCount 是 plain struct（int64 + int32，零指针），进一步保证 noscan。
//
// ⚠️ 关于 atomic：本实现**不用** atomic.Int32。理由——detect 的「查→建/重置→累加」
// 全程在分片写锁内（见下），plain int32 的 ++ 由 mutex 保护即可。用 map[int64]flapCount
// 值语义也**无法**用 atomic：map 值不可寻址，fc := counts[id] 是拷贝，不能对拷贝
// 调 atomic.Add（会改到副本）。故「值语义」与「atomic」二选一，这里按 GC 诉求选值语义。
//
// 为不退化为「每次 detect 抢全局锁」，按 deviceID 分片：每条计数只在一个分片的锁内操作，
// 锁竞争 = 全局并发 / numShards。分片自身也是 doc 15 §5.3 Tier 3 的做法。
type flapTracker struct {
    shards [numShards]flapShard
    window time.Duration // 检测窗口，如 1min
    maxCnt int32         // 窗口内阈值，如 15
}

type flapShard struct {
    mu     sync.Mutex
    counts map[int64]flapCount // key = deviceID；值语义，noscan
}

type flapCount struct {
    startedAt int64 // unix nano，窗口起点
    cnt       int32 // 窗口内断连计数（plain，由分片 mu 保护，非 atomic——见上）
}

// numShards 取质数分散 deviceID 哈希；经验值 64-256，按节点连接规模调。
// 50 万连接 / 128 分片 ≈ 4k 条/分片，单分片锁竞争可忽略。
const numShards = 128

func (t *flapTracker) shard(deviceID int64) *flapShard {
    // deviceID 是认证后的 numeric 值，分布足够均匀，直接取模即可（无需再 hash）
    return &t.shards[uint64(deviceID)%numShards]
}

func newFlapTracker(window time.Duration, maxCnt int32) *flapTracker {
    t := &flapTracker{window: window, maxCnt: maxCnt}
    for i := range t.shards {
        t.shards[i].counts = make(map[int64]flapCount)
    }
    return t
}

// detect 在 OnClose 调，返回 true 表示 flapping 命中。
// 「查→(缺失/过期则)建→累加」全程在分片写锁内，故 cnt 用 plain int32 即安全，
// 无 check-then-act 竞态（上版 RLock/Lock 两段式的漏计 bug 在此结构下天然不存在）。
func (t *flapTracker) detect(deviceID int64) bool {
    s := t.shard(deviceID)
    now := time.Now().UnixNano()
    hit := false

    s.mu.Lock()
    fc, ok := s.counts[deviceID]
    if !ok || now-fc.startedAt > int64(t.window) {
        // 新窗口或过期：重置（直接写值，无堆分配）
        fc = flapCount{startedAt: now}
    }
    fc.cnt++
    if fc.cnt >= t.maxCnt {
        // 命中阈值：删条目，触发 ban（delete 幂等；并发同时命中会重复 delete 与重复
        // return true，ban 是短 TTL 幂等写入，无害）
        delete(s.counts, deviceID)
        hit = true
    } else {
        s.counts[deviceID] = fc // 写回更新后的值（map 值语义，必须整体赋值）
    }
    s.mu.Unlock()

    return hit
}
```

**为什么认证后的表不会被撑爆**：

- key 是 numeric deviceID（认证后才赋值），攻击者无法伪造
- 表大小 ≤ 窗口内「认证成功且发生过断连」的 distinct 设备数（≤ 已纳管设备总数；稳定在线设备不断连不进表，已断线设备的残留条目最迟被 OnTick GC 按窗口清掉——上界不是「当前在线数」但同量级，50 万级条目 ≈ 几 MB，结论不变）
- 攻击者用错误凭证 → 认证失败 → 不进这张表（走 [doc 21](21.cloud-mqtt-gateway-accept-rate-limit-design.md) 第 1 层总量桶 + [doc 20](20.cloud-mqtt-gateway-credential-attack-defense.md) 负缓存）

### 19.4.3 命中后：device_blacklist 固定 TTL + jitter

命中阈值后写 `device_blacklist`：

- **固定短 TTL = 5min + per-device jitter**（如 `5min + hash(deviceID)%60s`，jitter 防同批被封设备同步解封形成解禁雷鸣群）。
- **不做指数递增**：它需要跨 ban 生命周期的「案底」状态（本设计里计数与 ban 条目到期即销毁，无处安放）、会放大一切误封、且让「设备何时能上线」对运维不可预测；惯犯处置走 [doc 9 §6.3](9.cloud-mqtt-gateway-network-attack-defense.md) 离线基线 → 人工长封（§19.7 第 5 条本就规定长期封禁只能人工决策）。
- 下次该设备的 CONNECT 被 `device_blacklist` 拦（双检查点见 §19.5）。

## 19.5 黑名单拦截：双检查点

> 📌 **高被引小节**（[doc 9 §5.3](9.cloud-mqtt-gateway-network-attack-defense.md)、[doc 20 §20.4.4](20.cloud-mqtt-gateway-credential-attack-defense.md)、TODOS #9 引用本节）。

> ⚠️ **拦截点 = 双检查点（被封设备仍付 TCP+CONNECT 成本，结构性）**：黑名单 key 是认证后才有的 numeric deviceID，无法在 OnOpen/TCP 建连阶段按 deviceID 拒，拦截发生在 OnTraffic 收到 CONNECT 之后，分两个检查点：

- **检查点①（廉价路径：CONNECT 解码后、认证前）**：用 L1 凭证缓存的 clientID→deviceID 映射（[doc 9 §5.3](9.cloud-mqtt-gateway-network-attack-defense.md)——L1 命中即拿到可信 deviceID，无需触发认证）查本地黑名单副本，命中即拒，**省掉 auth worker 调用 + presence 双写**。flapping 设备本身高频重连，L1 常驻热缓存，这是常见路径。
- **检查点②（权威兜底：认证成功后、presence 写入前）**：L1 miss 时（设备漂移到冷 Broker、Broker 重启、映射被驱逐）认证前拿不到 deviceID，放行完整认证，auth 成功后立即查黑名单副本，命中即拒，**零漏拦，但只省 presence 双写不省 auth**。②不可省——否则 L1 miss 的被封设备整条绕过黑名单。

故「认证前廉价拒」的覆盖率 = L1 命中率（高，但不是 100%），§19.2.4 的价值主张按此口径理解。被拒重连的每轮结构性成本：accept 槽位 + TLS 握手 + CONNECT 解码 + O(1) 查（①路径），L1 miss 时再加一次完整认证（②路径）。

另外**达到封禁阈值前的成本同样结构性存在**：~15 ×（L1 命中认证 + 2 次 presence 写）/设备——由 [doc 21 第 1 层令牌桶](21.cloud-mqtt-gateway-accept-rate-limit-design.md) 与 L1 缓存压低单价，区域性故障下该量级需纳入 presence Redis 容量预估。第 1 层令牌桶（OnOpen）前置挡总量洪水，是对这些结构性开销的上游补偿。

## 19.6 flapping 命中后：device_blacklist 集群共享

> 📌 **高被引小节**（7 处入站链：[doc 20](20.cloud-mqtt-gateway-credential-attack-defense.md) §20.4.4/§20.5.2/§20.9/§20.10、[doc 9 §5.3](9.cloud-mqtt-gateway-network-attack-defense.md)、TODOS #10 引用本节）。

> **立场**：device_blacklist 以**共享 Redis 为 source of truth**（key = 可信 numeric deviceID，带 TTL），每个 Broker 维护一份**本地副本**供热路径 O(1) 查询；**命中封禁的 Broker 对本地副本做同步直写（即时生效）**，跨 Broker 传播才走 Redis。不得是 per-Broker 本地表。**本节结论同样适用于 [doc 20](20.cloud-mqtt-gateway-credential-attack-defense.md) 的凭证爆破封禁——flapping 与爆破共享同一张 device_blacklist。**

### 19.6.1 问题：本地黑名单在多 Broker 下可被绕过

架构（[doc 1](../1.cloud-mqtt-gateway-architecture.md)）是多 Ingress Broker + L4 passthrough LB，设备「主动连入任意 Broker」，且 LB 在认证前看不到 deviceID（无法做 deviceID 粘性）。4G 设备重连时源 IP 随 CGNAT 池变化 → 下次 CONNECT 落到**另一个 Broker**。若 device_blacklist 是 per-Broker 本地表：

```
设备在 Broker A 上 flapping → A 累计到 15 次 → A 的本地表封禁
  → 设备重连，LB 分到 Broker B（B 的本地表里没有该 deviceID）
  → B 从 0 开始重新累计，要再 15 次才封
  → 设备在 N 个 Broker 上分摊制造负载
```

flapping 的本质是「反复重连」——这恰好是最擅长在 Broker 间漂移、最擅长绕过 per-node 封禁的故障模式。聚合防护强度 ≈ 单节点防护强度 / N，远弱于共享封禁。

> ⚠️ **边界如实声明：共享的是 ban 结果，不是计数**。各 Broker 的 flapping 计数表仍是本地的——LB 均匀分发下，单设备的断连事件摊到 N 个节点，**全局有效阈值 ≈ 15×N**（N=5 时设备 flap < 75 次/min 不会在任何节点达阈值，永不触发封禁）。这是**已接受边界**：flapping 的危害本质是 per-node 资源消耗（auth worker / presence 写，§19.2.1），per-node 计数与危害正相关、阈值语义自洽；漏网设备的每次 flap 均为 L1 命中认证 + presence 写，绝对负载可控；低速长期 flapping 由 [doc 9 §6.3](9.cloud-mqtt-gateway-network-attack-defense.md) 离线基线兜底（小时级）。若未来节点数增大后稀释成为实测痛点，升级路径 = 计数改共享 Redis INCR（key 是可信 deviceID、有界，不违反 §19.3.3；可复用 presence 删除的异步 worker 通道）——当前不做。

### 19.6.2 为什么放 Redis 不违反有界原则

- key 是**认证后的 numeric deviceID**（可信，攻击者无法伪造——见 §19.4.2「为什么认证后的表不会被撑爆」）
- 条目数 ≤ 被 flapping 封禁的设备数 ≪ 在线设备数（绝大多数设备不 flapping）
- 带短 TTL（如 5min），过期自动清理
- 这与 §19.3.3 的红线一致——红线禁的是「按**不可信** key 聚合」被撑爆，device_blacklist 的 key 可信

### 19.6.3 为什么不能直接「热路径查 Redis」

[doc 9 §5.3](9.cloud-mqtt-gateway-network-attack-defense.md) 规定三层黑名单「查询必须 O(1) 本地内存结构，零网络调用，在 accept/认证热路径」——目的是不让封禁检查本身成为公网延迟/故障放大点（Redis 抖一下 → 公网设备认证全卡）。直接每次 CONNECT 查 Redis 会违反这条。**解法是两层**：

```
        flapping 命中（OnClose detect）
                    │
        ┌───────────┴────────────┐
        ▼                        ▼
 ① 同步直写本地副本        ② 异步写 Redis（后台 worker，有界重试）
   （检测方即时生效，            │
    O(1)，不走网络）            ▼
        │              ┌─────────────────────┐
        │              │  共享 Redis (SoT)   │  key=numeric deviceID, TTL=5min
        │              │  device_blacklist   │  ← 跨 Broker 聚合的唯一真相源
        │              └─────────────────────┘
        │                        │
        │                        ▼ 其它 Broker 异步订阅/拉取（后台 goroutine）
        ▼              ┌─────────────────────┐
 ┌─────────────────┐   │ 其它 Broker 本地副本 │  otter/内存 map
 │ 检测方本地副本   │   │ deviceID → 禁至 T   │
 │ deviceID → 禁至 T│   └─────────────────────┘
 │ otter/内存 map   │            │
 └─────────────────┘            │
        │                        │
        └───────────┬────────────┘
                    ▼  CONNECT 热路径 O(1) 查（零网络，满足 doc 9 §5.3 红线）
             认证前 device 维度检查（检查点①/②，§19.5）
```

- **热路径（读）**：只查本地副本，O(1)，零网络——满足 [doc 9 §5.3](9.cloud-mqtt-gateway-network-attack-defense.md) 红线。设备落到任意 Broker，副本里若有该 deviceID（且未到解禁时刻 T）就拦。
- **封禁写（两步，缺一不可）**：flapping 命中时 **① 同步直写检测方本地副本**（进程内 O(1)，不走网络，不挡 OnClose 热路径）——保证**检测方 Broker 立即生效**；**② 异步写 Redis**（走后台**有界重试队列**——不是「可丢」：跨 Broker 防护依赖 Redis 可见性，静默丢弃 = 无告警地退化成单节点防护。队列满/重试耗尽才允许丢，且必须计 `blacklist_redis_drop_total` 指标 + 告警）——供跨 Broker 传播。
  - ⚠️ **① 不能省**：若命中只异步写 Redis、等自己的 poller 绕一圈读回来才更新本地副本，则检测方在这个 Redis 往返窗口内对该设备**仍不拦**。而 detect 命中时已把本地计数**删除归零**（§19.4.2），flapping 设备（本质就是立即重连，且常被 LB 亲和回同一 Broker）会重连回来重跑**完整 auth + presence 双写**、再从 0 重新累计——正好打在 flapping「快速本地封禁」的价值上。同步直写本地副本消除这个窗口。
- **跨 Broker 副本同步**：其它 Broker 的后台 goroutine 订阅/轮询 Redis，把新封禁条目刷进各自本地副本。这条延迟（秒级）只影响「已封设备**跨节点**漂移到别的 Broker」时的拦截及时性——检测方自身已由 ① 即时拦截，别的 Broker 也各有本地计数表兜底（最坏退回该节点自行累计），短 TTL 再兜一层，故秒级延迟可接受。
- **本地副本的过期清理**：副本条目存「禁至 T」，热路径按 `now < T` 判定，故 Redis 条目 TTL 到期后即便同步没删到，逻辑上也已自动失效（不会误拦）。死条目的物理回收由 otter 容量驱逐兜底，或复用 OnTick 顺带扫一遍——二选一即可，非正确性问题。
- **本地副本容量按最坏封禁规模校准**：副本条目数上界 = 同时被封设备数，区域性固件/弱网事故下可能接近故障波及设备数（十万级）。若副本容量小于它，热封禁条目被驱逐 → 检查点①失明、退回检查点②每轮完整认证。容量 = 最坏预估同时封禁数 × 安全系数（2-3），并对副本驱逐计 `blacklist_replica_evict_total` 指标（持续非零 = 容量不足告警）。
- **这与 [doc 5 §5.5](../5.cloud-mqtt-connect-auth-design.md) 的 L1/L2 两层模式同构**：认证缓存用「本地 L1（otter）+ 共享 L2（Redis）」解决跨节点复用（doc 5 §5.5.1「无粘性下被 N 稀释，靠共享 L2 收回」），device_blacklist 用同样的两层 + **本地命中直写 L1** 解决跨 Broker 封禁聚合。是同一套既有模式的应用，不是新发明。

**降级语义**：Redis 不可用时——热路径读照常走本地副本（可能漏封刚在别处命中的设备，但 flapping 的本地计数仍在各自节点生效，最坏退化回 per-node 防护），封禁写降级为只写本地副本（待 Redis 恢复后台补写）。即「Redis 挂 → 防护退回单节点级别，不致全失效」。

## 19.7 计数表的 GC（防残留）

flapping 计数表可能有残留（设备认证后稳定在线，没再断连，但计数条目还在表里直到窗口过期）。**在 OnTick 里扫描清理**（复用 gnet 走查 §10.7 的 connRegistry 扫描循环）：

```go
func (t *flapTracker) gc(now int64) {
    // 逐分片清理，每分片独立加锁——不长时间阻塞该分片的 detect（GC 是低频后台任务，
    // 每 10s 一次，单分片扫描几 k 条可忽略）。过期条目直接 delete（值语义，无 free）。
    for i := range t.shards {
        s := &t.shards[i]
        s.mu.Lock()
        for deviceID, fc := range s.counts {
            if now-fc.startedAt > int64(t.window) {
                delete(s.counts, deviceID)
            }
        }
        s.mu.Unlock()
    }
}
```

在 OnTick 里每 10 秒调一次 `flapTracker.gc`。这和 EMQX 的 `garbage_collect` 定时清理（`emqx_flapping.erl` `handle_info({timeout,...,{garbage_collect,Zone}})` → `ets:select_delete`）思路一致。

## 19.8 与 CONNECT 路径三层防御的关系

flapping 防御是 **CONNECT 路径三层防御的第 3 层的 `count_flapping` 一半**（另一半 `check_banned` 在 [doc 20](20.cloud-mqtt-gateway-credential-attack-defense.md)）。三层全景与编排见 [doc 9 §5](9.cloud-mqtt-gateway-network-attack-defense.md)，这里只给 flapping 在其中的定位：

```
┌─ CONNECT 路径（完整三层见 doc 9 §5）──────────────────────────────────┐
│                                                                       │
│  第 1 层 accept 限流（[doc 21]）  ← OnOpen，挡总量洪水                  │
│       ↓                                                               │
│  CONNECT 解码（[doc 18] parseOne）                                    │
│       ↓                                                               │
│  ┌─ 第 3 层 黑名单检查点①（本节 §19.5）─────────────────────────────┐│
│  │  L1 clientID→deviceID 命中 → 查本地副本 → 命中即拒（廉价路径）    ││
│  └────────────────────────────────────────────────────────────────────┘│
│       ↓                                                               │
│  认证（[doc 5]/[doc 15]）                                             │
│       ↓ 认证成功 → deviceID 赋值                                       │
│  ┌─ 第 3 层 黑名单检查点②（本节 §19.5）─────────────────────────────┐│
│  │  L1 miss 时权威兜底：查本地副本 → 命中即拒（零漏拦，省 presence） ││
│  └────────────────────────────────────────────────────────────────────┘│
│       ↓                                                               │
│  presence 写入（[doc 2]）                                             │
│       ↓                                                               │
│  OnClose：                                                            │
│    └─ flapping detect（本节 §19.4，第 3 层的 count_flapping）         │
│         认证成功 且 closeReason ∈ 设备行为 → flapTracker.detect       │
│         命中 → ①同步写本地副本 ②异步写 Redis（§19.6）                 │
│    └─ presence 删除（[doc 2]，异步 worker pool）                      │
└───────────────────────────────────────────────────────────────────────┘
```

**与其他防御的协作**：

- **第 1 层 accept 限流**（[doc 21](21.cloud-mqtt-gateway-accept-rate-limit-design.md)）：flapping 的上游保险——没有它，僵尸网络几万 CONNECT/s 会先打满 auth queue，flapping 判定根本来不及跑
- **check_banned**（[doc 20](20.cloud-mqtt-gateway-credential-attack-defense.md)）：count_flapping 的同胞，共享同一张 device_blacklist（§19.6）。doc 20 管认证**失败**类（爆破/撞库/unknown 洪泛），本文管认证**成功**但抖动类
- **负缓存**（[doc 5 §5.2](../5.cloud-mqtt-connect-auth-design.md)）：认证失败的设备走负缓存，不进 flapping 计数（本文只管认证成功的）
- **离线 flapping 基线**（[doc 9 §6.3](9.cloud-mqtt-gateway-network-attack-defense.md)）：本文是热路径实时封禁（秒级），§6.3 是离线分析输出「该设备长期 flapping 需售后介入」（小时级）。两层互补
- **IP 维度防御**：应用层不做 per-IP 限流（已废弃，见 [doc 21 §21.6](21.cloud-mqtt-gateway-accept-rate-limit-design.md)），交给基础设施（NLB/安全组）

## 19.9 EMQX emqx_flapping 源码对比

### 19.9.1 EMQX 的做法（源码事实）

EMQX 的 flapping detect 在 **CONNECT 流程里、认证之前**做（`emqx_channel.erl:610-636` 的 `process_connect` pipeline）：

process_connect(?CONNECT_PACKET(ConnPkt), Channel) ->

        fun enrich_conninfo/2,            %% 2. 补全连接信息（含 peerhost）
        fun run_conn_hooks/2,             %% 3. CONNECT hook

        fun check_banned/2,               %% 7. 查黑名单（→ doc 20）

```

EMQX 用**未认证的 clientid** 做 flapping key（`emqx_flapping.erl` `detect/1`）：

            %% ⚠️ 真实实现用 ets:take 原子取出 #flapping{} 记录再 cast（不是这里写的直接 cast）：
            %%   case ets:take(?FLAPPING_TAB, ClientId) of

            %%   end

```

> 3. line 号以仓库实际为准。
>
> 实质结论不变：**key = 未认证 clientid、计数达阈值即封、封写入 `emqx_banned` 带 until**。本文的对比论点（§19.9.2：mqtt-gateway 是公网，不能照搬未认证 clientid）不受这些出入影响。

命中后写 `emqx_banned`（带 until 过期，`emqx_flapping.erl` `handle_cast({detected,...})` 内）：

```erlang
ok = emqx_banned:ensure(#banned{
    who = emqx_banned:who(clientid, ClientId),
    by = <<"flapping detector">>,
    reason = <<"flapping is detected">>,
    at = Now,
    until = Until   %% Now + ban_time
})
```

### 19.9.2 EMQX 这样做的前提与局限

EMQX 的定位是**企业内网/可信网络**的 broker，clientid 相对可控。且 EMQX 的 `emqx_banned` 是 4 维检查（clientid/username/peerhost/rules），flapping 命中后 banned 表的多维兜底能缓解伪造问题。

**但 mqtt-gateway 是公网接入**，clientID 是攻击者完全可控的输入，不能照搬。EMQX 的 flapping detect 有效区间很窄：它适合「clientid 相对可信、数量受控，但某个客户端/固件确实在短时间内反复 CONNECT」的半可信环境；它不适合作为开放公网入口的 clientID flood 防线。

### 19.9.3 EMQX flapping 的真实边界

1. **公网场景不应开启作为主防线**
   - EMQX ban 的是**认证前 CONNECT 包里声明的 clientid**，不是认证成功后的设备身份。攻击者换一个 clientid 就绕过该 ban。
   - 反过来，攻击者如果知道某个真实设备的 clientid，也可以反复用它发 CONNECT，把这个 clientid 打进 banned，形成对真实设备的定向 DoS。
   - 更严重的是，`emqx_flapping` 的 ETS 表按未认证 clientid 插入记录，只有按 `window_time` 定时清理，**没有 capacity 上限**。攻击者在一个窗口内制造海量唯一 clientid，会把 flapping 计数表本身变成内存攻击面（正是 §19.3.2 的攻击 2）。

2. **内网/可信网络通常又不太需要它**
   - 如果 clientid 已由内网、接入网、认证规范或运维流程约束，恶意无限 clientid 洪泛的概率低；这时 flapping detect 只能处理少数异常客户端的高频重连。
   - 这种异常在内网里往往也可以通过设备侧 backoff、固件修复、运维踢连接、人工 banned 等方式处理，未必需要开启认证前 clientid 计数。

3. **因此它更像一个兼容性的辅助保护，而不是公网安全边界**
   - EMQX 默认 `flapping_detect.enable = false` 是合理的：公网开它会暴露未认证 clientid 的无界聚合风险；内网开它收益也有限。
   - 若确实开启，必须配合 listener 连接速率限制（[doc 21](21.cloud-mqtt-gateway-accept-rate-limit-design.md)）、overload protection（[doc 9 §5](9.cloud-mqtt-gateway-network-attack-defense.md)）、clientid 与认证身份绑定，以及 flapping 表规模/内存指标告警。否则它会从「防抖」变成攻击者可驱动的计数表。

**mqtt-gateway 的结论与此不同**：公网入口不按未认证 clientID 做 flapping 计数；认证前只做不分 key 的总量削峰（[doc 21](21.cloud-mqtt-gateway-accept-rate-limit-design.md)），认证后才按可信 numeric deviceID 计数并封禁（本文 §19.4）。

### 19.9.4 EMQX vs mqtt-gateway 对比（仅 flapping 维度）

| 维度 | EMQX | mqtt-gateway（本文）|
|---|---|---|
| **flapping 计数 key** | 认证前 clientid（公网可伪造）| **认证后 deviceID**（key 可信）|
| **撑爆风险** | ⚠️ flapping 表有（clientid 空间无限）| ✅ 无（认证前不聚合，认证后 key 可信）|
| **封禁存储** | `emqx_banned`（4 维，集群共享 mria）| device_blacklist（本地副本 + 共享 Redis SoT，§19.6）|
| **多节点聚合** | ✅ 集群共享（mria 复制）| ⚠️ ban 可经 Redis 聚合；计数 per-node（有效阈值 ≈ 15×N，§19.6.1）|
| **默认阈值** | window=1min / max=15 / ban≈5min | 同（对齐 EMQX）|
| **GC** | 定时器扫 ETS 清过期 | OnTick 扫计数表清过期（§19.7）|
| **默认/适用性** | flapping 默认关闭（公网有风险）| 本文设计为公网可用 |

> 三层全景（ranch_limiter + overload_protection + check_banned/count_flapping/auth）的完整对比见 [doc 9 §5](9.cloud-mqtt-gateway-network-attack-defense.md)。本表只列 flapping 维度。

## 19.10 实现约束（红线口径）

延续 [doc 9 §5.3](9.cloud-mqtt-gateway-network-attack-defense.md) 的实现约束，针对 flapping 收口：

```text
1. flapping 计数（认证后）：
   - key 必须是认证后的 numeric deviceID（可信）——不得用认证前的 clientID/IP 聚合
     （防 §19.3 撑爆计数表 + 逼 ban IP 自伤）
   - 计数只认「设备行为」close reason：clientClose/readTimeout/netErr/serverKick 计数
     （kick = takeover 型 flapping 的主要形态，必须计）；serverOverload/serverDrain/
     serverPresenceFail/STALE 不计数、走独立指标（防「后端故障 → 批量误封」，§19.4.1）。
     所有服务端主动 Close 调用点先写 closeReason 再 Close，缺省 = netErr（计数）；
     不得用 gnet OnClose 的 err 做分类
   - 计数表大小 ≤ 窗口内认证成功且断连过的 distinct 设备数（天然有界，OnTick GC 收口，§19.7）
   - 计数表必须 noscan / pointer-poor（对齐 doc 7 §2 红线 + doc 15 §5.1）：用 map[int64]flapCount
     值语义（非 *flapCount），分片锁，flapCount 为零指针 plain struct。50 万在线不得产生
     50 万个堆上小对象拖累 GC mark
   - cnt 用 plain int32（由分片写锁保护），不用 atomic——detect 的查→建→累加全在分片写锁内，
     且 map 值不可寻址无法对副本做 atomic

2. 命中后封禁（device_blacklist）：
   - 命中写 device_blacklist（固定 TTL 5min + per-device jitter 防同步解封雷鸣群；不做指数递增
     ——惯犯走 doc 9 §6.3 离线基线 → 人工，见 §19.4.3）
   - device_blacklist 必须集群共享（§19.6）：以共享 Redis 为 source of truth
     （key=可信 numeric deviceID，TTL 有界），各 Broker 维护本地副本供热路径 O(1) 查询。
     不得用 per-Broker 本地表——多 Broker + L4 LB 无 deviceID 粘性下，flapping 设备会在节点间
     漂移，本地表被逐节点绕过。注意共享的只是 ban 结果，计数仍 per-node（有效阈值 ≈ 15×N，已接受边界）
   - 热路径读只查本地副本（零网络，满足 doc 9 §5.3 红线）；命中封禁时同步直写检测方本地副本
     （即时生效）+ 异步写 Redis 供跨 Broker 传播——Redis 写走有界重试队列，丢弃必须计指标+告警
     （不得静默「可丢」）；不得只异步写 Redis 让检测方绕 Redis 往返才生效（§19.6.3）
   - 本地副本容量按最坏同时封禁数校准（区域性事故十万级）+ 副本驱逐指标告警——
     容量不足 = 检查点①失明（§19.5）

3. 黑名单拦截 = 双检查点（§19.5）：
   - 检查点①：CONNECT 解码后经 L1 clientID→deviceID 映射查副本（廉价路径，省 auth + presence）
   - 检查点②：auth 成功后、presence 写入前权威兜底（零漏拦，省 presence）
   - ②不可省——否则 L1 miss 设备绕过黑名单

4. ip_blacklist 不得因「IP 连接数高」自动触发（防 §19.3.1 自伤攻击）：
   - ip_blacklist 只由人工运维 或 高置信度规则（如 mTLS 握手失败率）触发
   - 纯连接数高 = 日出 + CGNAT 的正常形态，不封（详见 doc 21 §21.6）

5. 自动封禁一律短时 + 自动解封；长期封禁只能人工决策

6. 所有封禁/解封写审计日志 + 指标：指标只打聚合 counter（按防线/close reason 维度），
   per-device / per-IP 明细只进审计日志，禁止高基数 label（防把防御系统做成指标系统的 DoS 入口）
```

## 19.11 验证清单

```text
flapping 计数
[ ] key 是认证后 numeric deviceID，表 ≤ 窗口内断连设备数（有界，§19.4.2）
[ ] detect 并发回归测试：N 个 goroutine 同时对同一 deviceID 调 detect（含首个调用/窗口过期
    两条路径），断言无计数丢失、恰好在累计达 maxCnt 时命中阈值（既不早封也不漏封）。
    go test -race 必须 0 race。触发场景：flapping 设备 + presence connect_with_old 踢旧连接，
    同 deviceID 新旧连接 OnClose 重叠。正确性由「查→建/重置→累加全在分片写锁内」保证
    （map 值语义 + 分片 mutex，无 check-then-act 窗口）
[ ] 计数表 noscan / 无堆对象：断言 flapCount 为零指针 plain struct、counts 是 map[int64]flapCount
    值语义（非 map[int64]*flapCount）。50 万在线压测下用 runtime.ReadMemStats / pprof 验证
    GC mark 扫描单元数 ≈ overflow bucket 级（几万），而非 50 万个堆对象级。
    对齐 doc 7 §2 pointer-poor 红线 + doc 15 §5.1「必须 noscan」
[ ] close-reason 语义（§19.4.1）：kick（takeover）循环 15 次 → 必须触发封禁（防 takeover 型
    flapping 被洗白）；模拟 Kafka 慢 → 过载断连（红线 #5）循环 20 次 → 断言设备不进 device_blacklist
    （防后端故障批量误封）+ overload 独立指标 +20；drain / presenceFail / STALE 同理不计数；
    未写 reason 的 Close 路径缺省按 netErr 计数

device_blacklist 集群共享
[ ] device_blacklist 集群共享：以共享 Redis 为 source of truth（key=可信 numeric deviceID，带 TTL），
    各 Broker 本地只读副本供热路径 O(1) 查询。不得是 per-Broker 本地表——多 Broker + L4 LB 无
    deviceID 粘性下，flapping 设备在节点间漂移会逐节点绕过本地表，聚合防护 ≈ 单节点/N。
    热路径读只查本地副本（零网络，满足 doc 9 §5.3 热路径红线），封禁写与副本同步异步进行（§19.6）
[ ] 跨 Broker 封禁聚合测试：模拟同一 flapping 设备在 N 个 Broker 上轮流 CONNECT（设备源 IP 随
    CGNAT 变化、LB 无 deviceID 粘性）。断言：
    (a) 检测方即时性——设备在 Broker A 命中封禁后，重连回 A 的下一次 CONNECT 立即被 A 的本地副本拦
        （不依赖 Redis 往返、不重新累计 15 次），验证「命中时同步直写本地副本」；
    (b) 跨节点聚合——落到 Broker B 的下一次 CONNECT 被 B 的本地副本拦（B 经 Redis 副本同步获知，秒级延迟内）。
    Redis 不可用时降级为单节点防护，不致全失效
[ ] 黑名单双检查点（§19.5）：
    路径①——L1 命中时被封设备 CONNECT，断言 auth worker 零调用、presence 零写入、O(1) 拒；
    路径②——清空 L1（模拟跨 Broker 漂移/重启）后被封设备 CONNECT，断言完整认证后、presence 写入前被拦（零漏拦）

封禁参数 + GC
[ ] 命中写 device_blacklist（短 TTL），下次 CONNECT 被拦
[ ] 解封 jitter：同批封禁的设备解封时刻分散于 TTL+[0,60s)，不得同秒集中解封（防解禁雷鸣群）
[ ] 本地黑名单副本容量：按最坏同时封禁数校准（§19.6.3）；blacklist_replica_evict_total 持续非零
    触发告警（= 检查点①失明）
[ ] OnTick 定时 GC 过期计数条目（§19.7）

IP 边界（应用层不做 per-IP）
[ ] ip_blacklist 不因「IP 连接数高」自动触发（防 CGNAT 连坐，§19.3.1 + doc 21 §21.6）
[ ] 应用层不做 per-IP 限流（已废弃，IP 维度由 NLB/安全组承担，doc 21）

攻击模拟
[ ] 攻击模拟 1（单 IP 伪造 clientID）：认证 O(1) 判负 + 第 1 层总量削峰（doc 21），不 ban IP
[ ] 攻击模拟 2（多 IP 海量 clientID）：第 1 层总量令牌桶挡住（doc 21），flapping 计数表不膨胀
[ ] 所有封禁/解封有审计日志 + 指标
```

## 19.12 一句话总结

```text
flapping 是设备反复「连接-断连」抖动——认证通常都成功，所以它不是凭证攻击（doc 20），
而是认证成功后的资源放大问题。公网不能照搬 EMQX 的「认证前 clientid 计数」（会被伪造
海量 clientID 撑爆 + 逼你 ban CGNAT IP 自伤），只能在认证后按可信 numeric deviceID
计数：OnClose 上只计设备行为类断连（kick 也算），达阈值写集群共享的 device_blacklist
（Redis SoT + 本地副本 + 命中直写），下次重连被双检查点廉价拒（省 auth + presence）。
危害从单节点资源耗尽、presence 写删风暴到 QoS1 循环断裂逐层放大——封禁的价值是省掉
昂贵的认证链路，不是指望坏固件退避。
```

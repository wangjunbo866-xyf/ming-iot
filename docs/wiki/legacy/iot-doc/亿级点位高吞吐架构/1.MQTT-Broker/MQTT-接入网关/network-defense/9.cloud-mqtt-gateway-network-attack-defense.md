# 云端 MQTT 接入层网络攻击防范设计

> 本文承接 [百万级设备 MQTT 接入层架构设计](../1.cloud-mqtt-gateway-architecture.md)、[CONNECT 认证设计](../5.cloud-mqtt-connect-auth-design.md)、[压力传播与背压控制设计](../6.cloud-mqtt-gateway-pressure-backpressure-design.md)、[实现红线清单](../7.cloud-mqtt-gateway-implementation-red-lines.md) 和 [压测规划](../8.cloud-mqtt-gateway-load-test-plan.md)，定义百万设备公网接入层的威胁模型、防御分层与责任矩阵。
>
> 核心问题只有一个：**每一类攻击，由谁检测、由谁防御**——交给云服务商的、必须 Broker 自己做的、必须平台运营兜底的，三层不能混。

---

## 1. 结论

拓扑决策关系：

```text
本文修订 doc 1 §11.5 的 v1 接入拓扑决策：
不再把全部设备固定为"L4 透传 + Broker 终结 TLS"。
v1 当前决策改为按设备安全等级拆入口：
  普通设备：云 TLS LB 终结单向 TLS，再转发到 Broker。
  高安全设备：L4 透传，Broker 终结 mTLS。
压测环境、故障表和实现红线分别以 doc 8、doc 1 §16、doc 7 的修订口径为准。
```

一句话分工：

```text
云厂商防带宽，Broker 防语义，平台防身份。
```

展开：

```text
1. L3/L4 体积型攻击（SYN flood、UDP 反射、带宽打满）只能交给云厂商。
   自研 Broker 在 100Gbps 流量面前没有任何动作空间，入口带宽被打满时
   包根本到不了 Broker。

2. L7 MQTT 协议语义层攻击（CONNECT flood、畸形包、慢读、PUBLISH flood）
   仍由 Broker 自己防。TLS 在哪里终结只影响 A3 TLS 握手攻击的归属，
   不改变云 LB / WAF 不理解 MQTT 业务语义这一点：
   - 普通设备：单向 TLS 默认由云 LB 终结，A3 TLS 握手耗尽优先交给云侧；
   - 高安全设备：mTLS 需要 Broker 直接看到客户端证书，走 L4 透传，
     A3 mTLS 握手耗尽由 Broker 防；
   - 云 WAF 是 HTTP 语义产品，对 MQTT topic / QoS / CONNECT 凭证无效。

3. 凭证与身份类攻击（暴力破解、凭证填充、被盗凭证滥用、被劫持的合法设备）
   两边都接不住：流量完全合法、协议完全合规。
   只能靠平台侧的凭证体系 + Broker 上的执行点（限流、负缓存、封禁、指标）。
```

已有设计的好消息：doc 5/6/7/8 的认证保护、有界背压、红线和协议健壮性验证，**本身就是大部分 L7 防御**——攻击流量和故障风暴在 Broker 视角是同一个东西（输入速率 > 服务速率）。本文不重复那些机制，只做三件事：

```text
1. 把已有机制放进攻击视角的责任矩阵，标出谁负责哪段。
2. 补齐纯防御视角才会出现的缺口：黑名单/自动封禁、黑洞预案、
   CGNAT 误伤校准、内部横向隔离。
3. 给出攻防演练矩阵（与 doc 8 压测互补：doc 8 压"善意风暴"，
   本文压"恶意流量"）。
```

## 2. 威胁模型与攻击面

接入层暴露面：

```text
公网普通设备： 设备 -> :8883 (MQTT over TLS)
              -> 云 TLS LB 终结单向 TLS -> Broker
公网高安全设备：设备 -> :8883 / dedicated endpoint (MQTT over mTLS)
              -> L4 LB 透传 -> Broker 终结 mTLS
内网：        Broker -> Kafka / Redis / 认证只读库
控制面：      Command Service -> gRPC 直连 Broker 下行 endpoint（内网，1×N）
```

普通设备和高安全设备建议使用不同域名、端口或入口分组，避免把云 LB 终结 TLS 与 Broker 终结 mTLS 的责任混在一条链路里。

攻击分类（按"谁能看到它"分组，这决定了责任归属）：

| # | 攻击类型 | 表现 | 谁能看到 |
|---|---|---|---|
| A1 | 体积型 DDoS | UDP 反射/放大、ICMP flood、带宽耗尽 | 只有云厂商（包到不了 Broker） |
| A2 | TCP 状态耗尽 | SYN flood、连接表打满、半开连接堆积 | 云厂商 + Broker 各见一段 |
| A3a | 普通设备 TLS 握手耗尽 | 海量单向 TLS 握手请求烧非对称运算 CPU | 云 TLS LB（云侧终结 TLS） |
| A3b | 高安全设备 mTLS 握手耗尽 | 海量 mTLS 握手 / 客户端证书校验烧 Broker CPU | Broker（L4 透传，LB 不解 TLS） |
| A4 | MQTT 协议层攻击 | CONNECT flood、畸形包、谎报 remaining length、慢读饿死、PUBLISH flood、超大 payload | 只有 Broker |
| A5 | 凭证攻击 | 暴力破解、凭证填充（撞库）、未知 client_id 洪泛 | Broker 看到流量，平台看到模式 |
| A6 | 被劫持的合法设备 | 凭证有效、协议合规，但行为异常（高频上报、topic 越权探测、并发在线） | Broker 出信号，平台做判定 |
| A7 | 中间人 / 嗅探 | 明文协议截获、降级攻击 | 预防性问题（TLS 策略） |
| A8 | 内部横向 | Broker 被攻破后扩散到 Kafka/Redis/DB | 云厂商网络原语 + 平台配置 |

明确不在本文范围（见 §12）：设备侧固件安全、OTA 供应链、Web/APP 端、合规认证。

## 3. 责任分层总览（核心矩阵）

| 攻击 | 检测方 | 防御方 | 云厂商提供 | Broker 必须做 | 平台/运营必须做 |
|---|---|---|---|---|---|
| A1 体积型 DDoS | 云厂商 | **云厂商** | DDoS 基础防护（带黑洞阈值）；超量上高防/原生防护 | 无动作空间 | 黑洞预案、高防切换 runbook、与云厂商应急通道（§4.2） |
| A2 SYN flood | 云厂商 LB | **共担** | LB/宿主层 SYN 防护、连接速率整形 | bounded accept、accept 限流（doc 7 §6） | — |
| A3a 普通设备 TLS 握手耗尽 | 云 TLS LB | **云厂商** | TLS 终结、握手速率整形、证书托管、连接容量 | 只接受 LB 来源；继续防 CONNECT / 认证 / MQTT 语义攻击 | 证书与信任链管理、源 IP 透传校验（§6.2） |
| A3b 高安全设备 mTLS 握手耗尽 | Broker | **Broker** | L4 透传、SYN 防护 | mTLS 握手层限流、ECDSA、session resumption、禁 renegotiation（§5.2） | 客户端证书生命周期、CA pinning 与轮换（§6.2） |
| A4 协议层攻击 | Broker | **Broker** | — | 畸形包矩阵/fuzz/慢读防护（doc 8 §11.5）、限长、byte budget、有界队列（doc 7） | — |
| A5 凭证攻击 | Broker 流量 / 平台模式 | **共担** | — | 负向缓存、错误凭证限流、per-IP/per-tenant 限流、黑名单执行点（§5.3） | 高熵凭证、轮换、封禁决策、告警响应（§6.1） |
| A6 被劫持设备 | Broker 信号 / 平台判定 | **平台** | — | 行为指标输出：connect_with_old、ACL 拒绝计数、per-device 速率（§5.4） | 行为基线、按 device/tenant 封禁、凭证吊销 + 踢连接（§6.3） |
| A7 中间人 | — | **平台策略** | 证书托管（可选） | 只听 8883，公网禁明文 1883 | TLS 强制策略、固件 CA pinning 与轮换预案（§6.2） |
| A8 内部横向 | 云厂商审计 | **共担** | VPC、安全组、子网隔离、流日志 | 最小权限连接后端（只读认证库等） | 安全组最小化、后端服务鉴权、密钥管理（§6.4） |

记忆方式：**矩阵每行只有一个加粗的"防御方"**。出事时先看这一列，不要在错误的层找解药——带宽打满时调 Broker 参数没有意义，凭证填充时找云厂商也没有意义。

## 4. 云服务商承担的防线

### 4.1 能交出去的

```text
1. L3/L4 DDoS 清洗
   - 各云默认含基础防护（阿里云 DDoS 基础防护 / AWS Shield Standard），
     免费但有黑洞阈值；阈值因地域、账户等级而异，以云厂商当前文档为准。
   - 超过阈值 = IP 进黑洞 = 该入口全部设备不可用（见 §4.2 预案）。
   - 更高防护按需购买：阿里云 DDoS 原生防护/高防 IP、AWS Shield Advanced。
     高防是显著成本项，纳入 doc 4 成本口径单独评估，不默认购买。

2. L4 LB 层的 TCP 防护
   - SYN cookie / SYN 代答、新建连接速率整形、单 IP 并发连接上限（部分产品支持）。
   - 这与架构设计 §11.5 的分流拓扑兼容：普通入口在云 TLS LB 前处理 TCP，
     高安全入口在 L4 透传链路处理 TCP；两者都不依赖 MQTT 语义。

3. 普通设备的单向 TLS 终结
   - 对只依赖 MQTT CONNECT 凭证识别设备身份的普通设备，可由云 TLS LB
     终结单向 TLS，把 TLS 握手耗尽风险前移到云侧。
   - LB 到 Broker 默认走 VPC 内明文 TCP（信任边界取舍与残余暴露见 §5.2）；
     无论明文还是内网 TLS，Broker 安全组必须只允许 LB 安全组访问，
     禁止设备绕过 LB 直连 Broker。
   - 必须验证真实源 IP 透传能力：source IP preservation 或 PROXY protocol。
     如果拿不到真实源 IP，per-IP 限流和 ip_blacklist 必须关闭，
     只能退回 per-device / per-tenant 限流。

4. 网络隔离原语
   - VPC：Kafka / Redis / 认证库 全部不暴露公网。
   - 安全组：普通入口的 Broker 后端端口仅允许云 TLS LB 访问；高安全入口
     只开放 8883 / mTLS；公网禁明文 1883；内网按"源安全组"最小化授权。
   - 流日志 / 云防火墙：内网东西向流量审计的数据来源。

5. 入口弹性
   - 多 EIP / 多地域入口 + DNS 调度，作为黑洞时的流量腾挪手段。

6. 阿里云 NLB 的具体防护能力（购买 NLB 时的预期管理）
   - DDoS 原生防护（基础版）：默认免费，最高 5Gbps，清洗 SYN Flood/UDP Flood/ACK Flood。
   - DDoS 防护增强版 EIP（推荐绑定）：Tbps 级专业防护，业务 IP 直接获得强防护，
     无需额外配置 DDoS 高防。NLB 绑定此类 EIP 即可在网络层抗住大流量攻击。
   - 四层 TCP 防护：SYN cookie / SYN 代答、新建连接速率整形、半连接超时清理。
   - 最大并发连接数限制：按 NLB 规格限制，是基础设施层的连接总量闸门。

   ⚠️ NLB 能防什么 / 防不了什么（核心边界）：

   NLB 是四层负载均衡，只看 TCP 层，看不到 MQTT 协议语义。能防的是
   「网络层 flapping」（SYN 狂发、半连接耗尽、带宽打满），防不了的是
   「应用层 flapping」（合法 TCP 握手 + 合法 CONNECT 高频重连）。

   责任分层矩阵（NLB vs mqtt-gateway，互补不可替代）：
   ┌──────────────────────────────┬──────────┬───────────────┬──────────────┐
   │ 威胁                          │ NLB      │ mqtt-gateway   │ 设计文档      │
   ├──────────────────────────────┼──────────┼───────────────┼──────────────┤
   │ SYN Flood                     │ ✅ 清洗   │ —             │ §4.1-1/4.1-2 │
   │ 体积型 DDoS（带宽/PPS）        │ ✅ Tbps 级│ —             │ §4.1-1       │
   │ 半连接耗尽                     │ ✅ 超时清理│ 补充:OnTick 保活│ §4.1-2/§10.7 │
   │ TCP 连接数总量                 │ ✅ NLB 限制│ ✅ 总量令牌桶  │ §5.0 / doc 21 │
   │ 应用层 CONNECT flood           │ ❌ 看不到 │ ✅ 总量令牌桶  │ §5.0 / doc 21 │
   │ 同一设备 flapping（4G 波动）   │ ❌ 不知道 │ ✅ deviceID计数│ §5.0 / doc 19 │
   │ 凭证爆破                       │ ❌ 不知道 │ ✅ 负缓存+ban  │ doc 5+§5.3   │
   │ CGNAT 下单 IP 高频             │ ✅ NLB限速│ ❌ 应用层不做  │ doc 21 §21.6 │
   │ TLS 握手耗尽                   │ ⚠️ 分入口 │ ⚠️ 分入口      │ §5.2         │
   └──────────────────────────────┴──────────┴───────────────┴──────────────┘

   一句话：NLB 是网络层闸门（防 TCP 层打挂），mqtt-gateway 是应用层闸门
   （防 MQTT 层 flapping/flood/爆破）。两者互补，缺一不可。

   部署建议：NLB 绑定 DDoS 防护增强版 EIP（而非普通 EIP），
   获得网络层的强防护，让 mqtt-gateway 专注应用层防御。
```

### 4.2 黑洞预案（必须提前写好，不能事中发明）

基础防护的黑洞机制意味着：**攻击者不需要打穿你，只需要打到阈值，云厂商就替他完成拒绝服务**。预案要点：

```text
1. 接入用域名而非硬编码 IP：固件以域名连接，DNS TTL 控制在分钟级，
   黑洞时可切换解析到备用入口。
2. 多入口分摊：多 EIP / 多地域，单 IP 被黑洞只损失一个分片的设备。
3. 升级路径预演：基础防护 -> 临时开启高防的切换流程、生效时间、
   计费方式，提前与云厂商确认并演练（§11）。
4. 设备侧配合：退避 + jitter（doc 5 §8）保证入口恢复后不形成
   重连风暴二次冲击（doc 6 §10）。
```

### 4.3 不能交出去的（常见误解）

```text
1. 云 WAF 对 MQTT 无效。WAF 是 HTTP L7 产品；即使普通设备由云 LB
   终结单向 TLS，通用 WAF / LB 也不执行 MQTT topic、QoS、CONNECT
   凭证和设备身份语义。不要把 WAF 当 MQTT Broker 的 L7 防线。
2. 云厂商无法区分 "CONNECT flood 攻击" 和 "日出连接风暴"。
   两者在 TCP/TLS 层高度同构，只有 Broker 能从认证结果分布上区分
   （正常风暴：认证成功率高；攻击：未知 client_id / 错误凭证占比高）。
3. 云厂商无法识别慢读攻击。1 byte/min 的连接在 L4 是"健康的低速连接"。
4. 凭证类攻击对云厂商完全不可见：流量小、协议合法。
```

## 5. Broker 承担的防线

> 大部分机制已有设计载体，本节按攻击视角汇总并补缺口。已有的只给引用，不重复。

### 5.0 CONNECT 路径三层防御体系（总览图，EMQX 对标）

> 本节是「连接生命周期上每层防御由谁、在哪、用什么 key 做」的总览图。每层的深度设计见对应专文，本节只做编排与映射。

EMQX 在 CONNECT 路径上有**三层防御**，从外到内（源码：`emqx_ranch_limiter.erl` + `emqx_channel.erl:610-636`）：

```
┌─ 第 1 层：ranch_limiter（accept 层，TCP 握手后、MQTT 之前）─────────┐
│  allow(Socket, State):                                              │
│    ① allow_capacity：atomics 计数器，检查 max_connections 并发上限    │
│       → 超了：close_connection（拒绝）                               │
│    ② allow_limiter：emqx_limiter_client:try_consume（令牌桶速率限流）│
│       → 超了：close_connections_for(100ms)（暂停 100ms 再接受）       │
│  accepted()：atomics:sub（并发 -1）                                  │
│  retired()：atomics:add（并发 +1，连接断开时）                       │
└──────────────────────────────────────────────────────────────────────┘
                         ↓ 通过的连接进入 MQTT 层
┌─ 第 2 层：overload_protection（CONNECT pipeline 第 1 步）───────────┐
│  emqx_olp:backoff(Zone):                                            │
│    load_ctl:is_overloaded()（run queue 长度检测）                   │
│    → 过载：maydelay(Delay)（CONNECT 延迟处理）                      │
│    → 严重过载：backoff_new_conn 返回 {error, overloaded}（拒绝）     │
│    + backoff_gc/backoff_hibernation（跳过 GC/hibernate 省 CPU）     │
└──────────────────────────────────────────────────────────────────────┘
                         ↓ 通过的连接继续
┌─ 第 3 层：check_banned + count_flapping + authenticate ─────────────┐
│  banned 黑名单检查（clientid/username/peerhost/rules 4 维）          │
│  flapping 计数（clientid 窗口内计数 → 超 threshold → ban）           │
│  认证（ETS / 外部 DB）                                              │
└──────────────────────────────────────────────────────────────────────┘
```

EMQX **既有主动入口限速（第 1 层 ranch_limiter 的令牌桶 + 并发上限），又有反应式过载保护（第 2 层 overload_protection）**。两者互补，不是二选一。

#### 5.0.1 mqtt-gateway 三层映射

mqtt-gateway 把这三层拆成「accept 层限流 / 过载保护 / 黑名单+flapping+认证」三块，分别落在不同设计文档：

| EMQX 层 | 机制 | mqtt-gateway 对应 | 现状 | 深度设计 |
|---|---|---|---|---|
| **第 1 层** ranch_limiter | max_connections（atomics 并发计数）| **MaxConnections**（gnet accept 层）| ✅ 已设计 | [gnet 走查 §8.7.7 闸门 4](../reference/gnet/gnet-source-walkthrough.md) |
| | rate_limiter（令牌桶速率）| **总量令牌桶**（单一全局 `rate.Limiter`，不分 key）| ✅ 已设计 | [doc 21 accept 层限流](21.cloud-mqtt-gateway-accept-rate-limit-design.md) |
| **第 2 层** overload_protection | run queue 检测 → delay/new_conn/gc/hibernation 降级 | ⚠️ **缺口（Phase 2 候选）**——见 §5.0.2 | ❌ 未设计 | — |
| **第 3 层** check_banned | 黑名单（clientid/username/peerhost/rules）| **device_blacklist + ip_blacklist + tenant_freeze**（公网适配：不按未认证 clientid，按认证后可信 deviceID）| ✅ 已设计 | [doc 20 凭证攻击](20.cloud-mqtt-gateway-credential-attack-defense.md)、本节 §5.3 |
| | count_flapping | **认证后 deviceID flapping 计数**（公网不按未认证 clientid）| ✅ 已设计 | [doc 19 flapping](19.cloud-mqtt-gateway-flapping-defense-design.md) |
| | authenticate | L1/L2 凭证缓存 + auth queue 四道闸门 | ✅ 已实现 | [doc 5 认证](../5.cloud-mqtt-connect-auth-design.md)、[doc 15 本地快照](../15.cloud-mqtt-credential-local-snapshot-design.md) |

#### 5.0.2 第 2 层过载保护：现状与诚实声明

⚠️ mqtt-gateway 当前**没有反应式过载保护**（EMQX 第 2 层）。这是真实的 Phase 2 缺口，不在此造设计避免编造。

当前靠什么兜住过载：

- **第 1 层预防式令牌桶**（[doc 21](21.cloud-mqtt-gateway-accept-rate-limit-design.md)）：按预估的 CONNECT 速率上限削峰，是「预测式」而非「反应式」。
- **第 3 层 + auth queue 四道闸门**（[doc 20](20.cloud-mqtt-gateway-credential-attack-defense.md)）：认证资源耗尽时 fail fast。
- **doc 6 背压水位 L0–L3**：append queue / per-client 预算等已有背压梯度，是「输入速率 > 服务速率」时的执行层（§8「攻击与风暴同构」）。

这三者覆盖了「可预测速率」和「后端 append/presence 慢」两类过载。**未覆盖的是「节点自身负载信号驱动的反应式降级」**——即 EMQX overload_protection 的 run queue / CPU 检测 → CONNECT 延迟或拒绝 + 跳过 GC/hibernate 省 CPU。Phase 2 演进路径：补 Go 版的 `runtime` 指标（goroutine 数 / GOMAXPROCS 利用率 / GC 压力）过载检测，作为第 1 层令牌桶的反应式补充。

#### 5.0.3 连接生命周期上的三层执行流

把三层落到 gnet 的 OnOpen/OnTraffic/OnClose 生命周期（单张图，避免散落各文档）：

```
┌─ OnOpen（TCP 建连）─────────────────────────────────────────────────┐
│  第 1 层：总量令牌桶 global.Allow() → 超限 Close（不 ban）          │
│           （MaxConnections 并发上限在 gnet accept 层，闸门 4）       │
└──────────────────────────────────────────────────────────────────────┘
                         ↓
┌─ OnTraffic（收到 CONNECT，parseOne 解码后）[doc 18 §18.3.3]─────────┐
│  ┌─ 第 3 层 黑名单检查点①（doc 19 §19.5，廉价路径）──────────────┐│
│  │  L1 clientID→deviceID 命中 → 查本地副本 → 命中即拒（省 auth）  ││
│  └────────────────────────────────────────────────────────────────┘│
│  认证（L1/L2 凭证缓存 + auth queue 四道闸门，[doc 5]/[doc 20]）     │
│       ↓ 认证成功 → deviceID 赋值                                    │
│  ┌─ 第 3 层 黑名单检查点②（doc 19 §19.5，权威兜底）──────────────┐│
│  │  L1 miss 时：查本地副本 → 命中即拒（零漏拦，省 presence）      ││
│  └────────────────────────────────────────────────────────────────┘│
│  presence 写入（[doc 2]，CONNECT 成功 = 认证 + presence，红线 #6）  │
└──────────────────────────────────────────────────────────────────────┘
                         ↓
┌─ OnClose（断连）────────────────────────────────────────────────────┐
│  第 3 层 flapping detect（doc 19 §19.4）：                          │
│    认证成功 且 closeReason ∈ 设备行为 → flapTracker.detect          │
│    命中 → ①同步写本地副本 ②异步写 Redis（集群共享，doc 19 §19.6）  │
│  presence 删除（[doc 2]，异步 worker pool + fencing）              │
└──────────────────────────────────────────────────────────────────────┘
```

> **第 2 层（过载保护）在这张图里没有独立节点**——它本应在 OnTraffic 收到 CONNECT 后、第 3 层之前做 run-queue 检测，但因当前未实现（§5.0.2），暂缺。Phase 2 补上时插在第 1 层与第 3 层之间。

#### 5.0.4 公网适配的核心分歧：key 可信性

EMQX 三层默认假设 clientid/peerhost 相对可信（企业内网）。mqtt-gateway 是公网，**认证前的 clientID/IP 是攻击者完全可控的输入**——这是贯穿 doc 19/20/21 三篇的红线：

```text
认证前（key 不可信）：只做限流（第 1 层总量桶，doc 21），不按 clientID/IP 聚合计数
                      （否则伪造海量 clientID 撑爆计数表，或逼你 ban CGNAT IP 自伤）。
认证后（key 可信）：才做 flapping 计数与爆破封禁（第 3 层，doc 19/20），表大小 ≤ 在线设备数。
```

这一条决定了 mqtt-gateway 不能照搬 EMQX 第 3 层的「认证前 clientid 做 flapping key」——详见 [doc 19 §19.3](19.cloud-mqtt-gateway-flapping-defense-design.md) 与 [doc 20 §20.3](20.cloud-mqtt-gateway-credential-attack-defense.md)。

#### 5.1.1 MQTT 5.0 MaximumPacketSize 双向协商（A4 超大包防护，借鉴 comqtt）

上面「payload/topic 限长」是 Broker 侧硬限制。除此之外，MQTT 5.0 提供了**协议级**的包大小双向协商（comqtt 在 `clients.go:442/582` 实现参考），对逆变器场景有实际价值：

```text
1. 客户端声明：CONNECT 的 MaximumPacketSize 属性声明「我能接受的最大包」。
   Broker 下行（PUBLISH/PUBACK 等）超过该值时截断或拆包，防设备 OOM。

2. Broker 声明：CONNACK 的 MaximumPacketSize 属性声明「服务端能接受的最大包」。
   客户端后续上行超过该值时，Broker 返回 PacketTooLarge 拒绝。
   这是 payload 限长的协议化表达——客户端可以在发包前自查，减少被拒。
```

**实现要点**（两处检查，对应 comqtt 的读写路径）：

```text
读路径（OnTraffic 解码 fixed header 后）：
  if brokerMaxPacketSize > 0 && remaining > brokerMaxPacketSize {
      // [MQTT-3.2.2-15] 客户端发了超 broker 声明上限的包
      断连（或返回 PacketTooLarge，视协议版本）
  }

写路径（AsyncWrite 前检查目标 conn 声明的 max）：
  if clientMaxPacketSize > 0 && len(out) > clientMaxPacketSize {
      // [MQTT-3.1.2-24] 要发给设备的包超设备声明上限
      截断 / 拆包 / 改发（视业务）
  }
```

**第一阶段决策**：逆变器多为 MQTT 3.1.1（ProtocolVersion=4），3.1.1 无此属性，靠 Broker 硬限制（红线 §12 限长）兜底即可。**MQTT 5.0 MaximumPacketSize 协商作为 Phase 2 能力**，当设备升级到 5.0 固件后启用。但** Broker 侧的硬限制（brokerMaxPacketSize）Phase 1 必须有**——它是 A4 超大包攻击的第一道闸门，不依赖客户端协议版本。

> 借鉴来源：comqtt `clients.go:442`（读）和 `clients.go:582`（写）的判断逻辑。comqtt 的实现耦合在 Client 结构里，mqtt-gateway 不抽取 comqtt 的 Client，自己在 gnet 的 parseOne + AsyncWrite 前各加 2 行即可。

#### 5.1.2 CONNECT 字段校验清单（A4 畸形 CONNECT，借鉴 comqtt validateConnect）

doc 8 §11.5 的 fuzz/畸形包矩阵需要一份具体的「CONNECT 合规检查清单」。comqtt 的 `validateConnect`（server.go:488）提供参考，结合 mqtt-gateway 红线（尤其 #10 第一阶段不做 QoS2/retain）整理如下：

```text
CONNECT 必须校验的字段（在认证前执行，拒绝即返回对应 CONNACK 拒绝码）：

A. 字段级验证（packets.ConnectValidate 已覆盖，抽取 comqtt packets 后自动获得）
   - protocol_name == "MQTT" 或 "MQIsdp"（3.1）
   - protocol_version ∈ {4, 5}（3.1.1 / 5.0；拒绝更低）
   - client_id 长度 ≤ ServerCap.MaxClientIDSize（红线 §12 限长）
   - keepalive ∈ [0, 65535]（0 = 不做应用层保活，走兜底窗口）
   - will topic/payload 有效（如果 will flag 置位）
   - username/password 与 will 的 UTF-8 有效性

B. 能力边界校验（mqtt-gateway 自己加，对齐红线 #10）
   - protocol_version < MinimumProtocolVersion（=4）→ 拒绝，返回 UnsupportedProtocolVersion
     （第一阶段只支持 3.1.1=4，拒绝 3.1=3 和未声明版本）
   - will.QoS > MaximumQos（=1）→ 拒绝，返回 QosNotSupported
     ⭐ 对齐红线 #10：第一阶段不做 QoS2，Will 带 QoS2 的 CONNECT 直接拒
   - will.Retain == true 且 RetainAvailable == 0 → 拒绝，返回 RetainNotSupported
     ⭐ 对齐红线 #10：第一阶段不做 retain，带 retain will 的 CONNECT 直接拒
   - clean_session == false 且 client_id == ""（3.1.1）→ 拒绝，返回 UnspecifiedError
     （无 client_id 不能做持久会话，而第一阶段不做持久会话）
```

**关键对齐**：B 组的「Will QoS2 拒绝」和「Will Retain 拒绝」**直接由红线 #10 决定**——第一阶段不做 QoS2 和 retain，所以这两类 CONNECT 必须在认证前就拒绝，不能放进来后再处理。这是个容易漏的点（CONNECT 带的遗嘱消息如果带 QoS2，设备断连时会触发 QoS2 流程，但你第一阶段不支持）。

**实现位置**：doc 18 §18.3.3 的 `parseOne` 解码出 `pk.ConnectParams` 后、`dispatch` 调 `handleConnect` 前，先跑 A+B 校验，不通过直接发拒绝 CONNACK + Close。

### 5.2 TLS 握手层（A3）

先按设备安全等级拆拓扑：

| 设备类型 | TLS 终结位置 | A3 防御主责 | Broker 额外约束 |
|---|---|---|---|
| 普通设备 | 云 TLS LB 终结单向 TLS | 云厂商 / LB | Broker 只接受 LB 来源；校验真实源 IP 透传；继续执行 CONNECT 认证和 MQTT 语义防御 |
| 高安全设备 | L4 透传，Broker 终结 mTLS | Broker | 握手限流、客户端证书校验、证书吊销/轮换、mTLS 指标 |

普通设备的核心判断：

```text
设备身份 = MQTT CONNECT 凭证 / token / secret
TLS 作用 = 加密传输 + 服务端身份校验
```

这种情况下，可以让云 LB 终结单向 TLS，把海量 TLS 握手攻击挡在云侧。
Broker 不再承担普通设备的 TLS 握手 CPU，但必须保证：

```text
1. Broker 入口只允许云 LB 安全组访问。
2. 源 IP 必须可靠传入 Broker；否则禁用 per-IP 限流和 ip_blacklist。
3. LB idle timeout 必须大于 Broker keepalive 判死窗口。
4. LB 长连接容量、TLS 握手容量和计费模型必须进入压测与成本评估。
5. LB 到 Broker 的内网链路默认 VPC 明文（见下方信任边界说明）。
```

**信任边界说明（普通设备 LB 终结 TLS 的有意取舍）**：普通设备身份是
MQTT CONNECT 里的 bearer secret，云 LB 终结 TLS 的那一刻，LB 数据面就已经
看到明文 secret——选择 LB 终结本身已经把信任边界划到「VPC + 云账号 + 云厂商
基础设施」上。在这个前提下再给 LB→Broker 加内网 TLS，并不能收回已经做出的
信任让步，只会换来两遍 TLS 的 CPU 成本；很多云的 L4 TLS 卸载产品后端也只支持
明文 TCP，叠加后端加密本不在产品能力内。因此默认 **VPC 明文**，并显式接受其
残余暴露：

```text
残余暴露（VPC 明文跳）：
  - LB 数据面可见明文凭证（选择 LB 终结的固有代价，不可消除）。
  - 云账号失陷后可对 Broker 后端开「流量镜像 / 镜像会话」做无痕被动截获
    （云 SDN 下邻居节点嗅探无效，截获只剩此向量 + 中间盒 + 运维抓包）。
  - 运维排障 tcpdump 抓到的包内含可复用设备凭证，抓包文件随工单/对象存储
    /聊天工具扩散。
补偿控制见 §6.4（流量镜像纳入云账号高危操作审计、抓包文件按凭证密级处理）。
内网 TLS 只在合规（等保类传输加密要求）驱动时启用；若要付两遍 TLS 成本，
应重新评估直接回「L4 透传 + Broker 终结」端到端一遍 TLS，而不是叠加。
```

高安全设备的核心判断：

```text
设备身份 = TLS 客户端证书
TLS 作用 = 加密传输 + 服务端身份校验 + 设备证书身份
```

这种情况下，Broker 必须直接看到并校验客户端证书，不能被普通 TLS LB
终结链路挡住；因此高安全入口走 L4 透传，由 Broker 终结 mTLS。

```text
Broker 终结 TLS / mTLS 时的要求：
1. ECDSA 证书、session resumption / ticket、握手层与 accept 层分别限流
   （doc 1 §16、红线 §13）。
2. 禁用 TLS renegotiation（Go crypto/tls 服务端默认不支持，显式确认配置）。
3. 握手超时独立设置：TCP 建连后 N 秒内未完成 TLS 握手即断开，
   不进入 MQTT 层任何队列。
4. 握手失败率按源 IP 聚合：高失败率 IP 进入黑名单候选（§5.3）；
   如果源 IP 来自 PROXY protocol，必须先校验连接确实来自可信 LB。
5. session ticket 轮换密钥，避免长期固定 ticket key 形成解密风险。
6. mTLS 客户端证书校验失败要单独计数，不能与普通 bad credential 混淆。
```

### 5.3 凭证攻击执行点（A5）——本文新增的主要机制

> 完整攻击面分析 + 分层防线 + EMQX banned 对比 + 识别指纹 + 验证清单见
> [doc 20 凭证攻击 / 认证洪水防御设计](20.cloud-mqtt-gateway-credential-attack-defense.md)。
> 本节保留责任矩阵口径与黑名单执行点摘要；doc 20 是深入版（与 doc 19 flapping 并列——
> 两者分别是 EMQX 认证前 `check_banned` 与 `count_flapping` 两道闸的拆分）。

已有基础：负向缓存（doc 5 §5.2）、错误凭证速率限制、每 device 认证 inflight=1、per-tenant / per-IP CONNECT 限流（doc 5 §6.1）。在此之上补**分层黑名单与自动封禁**：

```text
黑名单分三层，粒度从粗到细。三层各自独立，触发条件不同：

  ip_blacklist      ：源 IP 级。Broker 本地 O(1) 黑名单是基线执行点，
                      两种入口都必须生效：
                      - 普通 TLS LB 终结入口：完成真实源 IP 可信化
                        （source IP preservation 或可信 LB 的 PROXY header）
                        后、MQTT CONNECT 解析 / 认证前断开。该路径在
                        Broker 侧没有"TLS 握手前"执行点。
                      - 高安全 L4 透传入口：TCP accept 后、TLS / mTLS
                        握手前断开。
                      LB / 安全组 ACL 只承接人工长期封禁或高危固定来源，
                      不承接短 TTL、指数递增、自动解封的自动封禁语义。

  device_blacklist  ：device_id 级（认证后 numeric ID）。认证前置检查，
                      命中返回 Not Authorized 并写长 TTL 负缓存。

  tenant_freeze     ：租户级熔断。该租户凭证大面积泄露时一键冻结。

⚠️ ip_blacklist 的触发规则（关键，和 doc 19 对齐）：

  ip_blacklist 的自动触发条件必须收窄，只限高置信度规则：
    - 人工运维手动加（长期高危固定来源）
    - 高安全入口的 mTLS 握手失败率超阈值（Broker 本地指标，高置信度）

  ⚠️ ip_blacklist 不得因以下原因自动触发（防 CGNAT 连坐 + 防自伤攻击）：
    - "IP 连接数高"（日出 + CGNAT 的正常形态，不封——doc 21 §21.6）
    - "unknown client_id 洪泛"（同一 IP 伪造大量 clientID，改用第 1 层
      总量令牌桶限流（doc 21），不 ban IP——否则攻击者故意逼你 ban CGNAT 出口自伤）
    - "认证失败多"（CGNAT 下大量真实设备偶尔认证失败是正常的）

  这些"连接数高/认证失败多"的场景改用第 1 层的总量令牌桶限流处理（doc 21）：
  超限只拒当前连接（gnet.Close），不写 ip_blacklist，不 ban IP。
  ⚠️ 应用层不做 per-IP 限流（已废弃，详见 doc 21 §21.6），IP 维度交给基础设施（NLB/安全组）。
  这和 §5.3 的 CGNAT 校准第 2 条（"纯粹的高连接数不封"）一致。

device_blacklist 的触发规则（和 doc 19 一致，key 可信）：

  错误凭证爆破：同一 device_id 连续 N 次 bad credential
    -> 封 device（短时）+ 告警（区别于固件 bug：爆破常伴随字典分布）。
    （注意：这里的 key 是认证前 L1 缓存里 clientID 对应的 device_id，如果
     该 clientID 未纳管则走负缓存，不进 device_blacklist）

  flapping 命中：详见 [doc 19 flapping 防御设计](19.cloud-mqtt-gateway-flapping-defense-design.md)。
    认证后 deviceID 在窗口内断连超阈值（doc 19 §19.4 flapping 计数）
    -> 写 device_blacklist（固定短 TTL 5min + per-device jitter 防同步解封雷鸣群；
       不做指数递增——惯犯走 §6.3 离线基线 -> 人工，见 doc 19 §19.4.3 / §19.5 / §19.6）

tenant_freeze 的触发规则：
  人工决策（运维确认该租户凭证大面积泄露），一键冻结该租户所有设备。
  不自动触发（误伤代价 = 整租户停摆）。

握手异常（ip_blacklist 的特殊触发条件）：
  - 普通入口看云 LB TLS 握手失败率。该数据来自云监控慢路径，
    只能做事后封禁候选或人工处置输入，不能当实时热路径封禁依据。
  - 高安全入口看 Broker mTLS 握手失败率。该数据来自 Broker 本地指标，
    可触发短时 ip_blacklist，后续连接在 mTLS 握手前被本地拦截。

flapping 抖动检测（热路径实时，区别于 §6.3 离线行为基线）：
  详见 [doc 19 flapping 防御设计](19.cloud-mqtt-gateway-flapping-defense-design.md)。
  核心要点（完整业务场景 + 危害分析 + 公网约束 + 设计见 doc 19）：
  - 认证前只用第 1 层总量令牌桶限流（doc 21，不分 key），不按 clientID 聚合计数
    （防伪造海量 clientID 撑爆计数表），不因连接数高自动 ban IP（防 CGNAT 连坐）
  - 认证后（deviceID 可信）才做 flapping 计数（只计设备行为类 close reason，
    服务端过载/drain 断连不计——防后端故障批量误封），窗口内断连超阈值写 device_blacklist
  - 与 §6.3 离线 flapping 基线互补：本文热路径秒级封禁，§6.3 离线小时级分析

实现约束（红线口径）：
  黑名单查询必须 O(1) 本地内存结构，零网络调用，在 accept/认证热路径。
  黑名单条目有界（bytes 上限），满时按到期时间淘汰——
  黑名单自身不能成为内存攻击面。
  自动封禁一律短时 + 自动解封；长期封禁只能人工决策。
  自动封禁不得依赖云安全组 / LB ACL API 下发；这些 API 有条目上限和
  限速，只能作为人工长期封禁慢路径。
  所有封禁/解封写审计日志 + 指标。
  ⚠️ ip_blacklist 的自动触发只限高置信度规则（如 mTLS 失败率）；
     CONNECT flood / 认证失败改用第 1 层的总量令牌桶限流（doc 21），不自动 ban IP。
```

**CGNAT 误伤校准（关键，容易出事故）**：逆变器走 4G 蜂窝网或家宽时，运营商 CGNAT 会把成千上万台设备收敛到极少数出口 IP。

```text
1. per-IP 阈值必须按"正常 NAT 池密度"压测校准（doc 8 数据准备中
   增加按运营商出口聚合的 IP 分布模型），不能照搬 Web 业务的低阈值。
2. 自动封 IP 的规则要求"未知 client_id / 错误凭证占比高"作为前提条件，
   纯粹的高连接数不封——日出 + CGNAT 下高连接数是正常形态。
3. 误封的爆炸半径 = 整个 NAT 池的设备，封 IP 动作必须有独立指标和告警。
```

### 5.4 被劫持设备的信号输出（A6）

Broker 不做判定（判定需要业务上下文），只保证**信号可观测**：

```text
presence_connect_with_old_count   -> 并发在线 / 凭证泄露信号（doc 1 §13.2）
acl_reject_total（按 device 聚合） -> 越权探测信号（连了之后乱发 topic）
per-device publish 速率分布        -> 异常高频上报（固件被改 / 数据轰炸）
oversize_payload_reject_total     -> payload 攻击尝试
```

执行点：平台判定后通过既有通道执行——禁用凭证（认证层生效，受缓存 TTL 延迟约束，doc 5 §5.3）+ 主动踢连接（kick，Phase 2 控制通道能力）。

### 5.5 Broker 明确不做的

```text
不做 DPI / 流量清洗（云厂商职责）。
不做 payload 内容安全扫描（Broker 不解析 payload，红线）。
不做复杂行为分析引擎（平台侧离线/近线任务，§6.3）。
不为攻击流量保留任何降级通道——攻击流量与过载流量同等待遇：
  fail fast、断连、不缓存（doc 6 原则的直接推论）。
```

## 6. 平台 / 运营承担的防线

### 6.1 凭证生命周期（A5 的根治在这里）

```text
1. 出厂凭证：每设备唯一高熵 secret（doc 5 §4.3），禁止批次共享凭证——
   一台被攻破不等于一批被攻破。这是自产设备最大的安全杠杆。
2. 算法固定：服务端只存 SHA-256(secret)（doc 5 §4.3），不添加 salt、不使用 HMAC、
   不在 Broker 热路径使用慢哈希。算法明确后轮换和兼容逻辑才能落地。
3. 轮换：支持单设备 / 批次凭证轮换，credential_version 已在认证表（doc 5 §4.1）。
   轮换流程：
     a. 生成新 device_secret（≥128 bit CSPRNG）。
     b. 计算新 secret_hash = SHA-256(new_secret)。
     c. 原子更新 device_credential 表：secret_hash = 新值，credential_version++，
        updated_at = now。
     d. （Phase 2）通过凭证变更事件或短 TTL 让 Broker 缓存尽快失效。
     e. 旧 secret 在设备端更新后立即失效；若需平滑过渡，可允许新旧 secret
        在短暂窗口内同时有效（需在认证表中显式支持多版本，并设过期时间）。
4. 吊销：禁用设备 = DB status 置位 + （Phase 2）主动 kick；
   缓存 TTL 期间的禁用延迟是已接受边界（doc 5 §5.3），
   高危场景用"短 TTL + kick"组合压缩窗口。
5. 凭证存储：服务端只存 hash（doc 5 §4.3），泄库不直接泄凭证。
   由于 secret 本身是高熵随机值且 hash 为 SHA-256，离线暴力破解不可行。
```

### 6.2 传输安全策略（A7）

```text
1. 公网只开 8883（MQTT over TLS）；1883 明文仅限内网调试环境，
   安全组层面保证公网不可达。
2. 普通设备默认走"云 LB 终结单向 TLS + MQTT 凭证认证"：
   - 普通设备域名如 mqtt.example.com；
   - 云 LB 承担 TLS 握手容量、证书托管和基础 TLS 防护；
   - Broker 只接受 LB 来源，不能暴露可被设备绕过的内网明文端口；
   - 源 IP 透传是 per-IP 限流和封禁的前置条件。
3. 高安全设备走"L4 透传 + Broker 终结 mTLS"：
   - 高安全域名如 secure-mqtt.example.com，或独立端口 / 独立入口；
   - Broker 直接校验客户端证书，并把证书身份绑定到认证主体；
   - mTLS 证书吊销、轮换和 kick 需要进入平台凭证生命周期。
4. 服务端证书：用公共 CA 或私有 CA 均可，但固件信任锚（CA pinning）
   必须与证书轮换预案一起设计——pin 了具体证书而非 CA 的固件，
   换证书等于全量设备掉线。pin CA、留双 CA 过渡窗口。
5. TLS 版本与套件：TLS 1.2 起步、优先 1.3；只保留 AEAD 套件。
```

### 6.3 行为基线与判定（A6）

```text
数据源：Broker 信号（§5.4）+ raw log（Kafka）+ 设备档案。
形态：离线/近线分析任务（不在 Broker 内，红线），输出封禁建议或自动工单。
首版规则建议（简单规则先行，不上模型）：
  - 上报频率偏离该型号基线 N 倍且持续
  - ACL 拒绝计数 > 0（正常固件不该有任何越权 publish/subscribe）
  - connect_with_old 持续 flapping
  - 同一 device 从地理/运营商特征突变的 IP 上线（弱信号，只参与组合判定）
响应 runbook：观察 -> 限速 -> 禁用凭证 + kick -> 通知售后换机。
```

### 6.4 内部横向隔离（A8）

假设 Broker 节点可能被攻破（公网暴面 + 自研解析器），限制爆炸半径：

```text
1. 网络：后端组件（Kafka/Redis/PG）仅内网，按源安全组授权到
   Broker 安全组，不开网段级大白名单。
2. 最小权限：
   Broker 的 PG 账号只读、且只能读 device_credential（实现已是 read-only）。
   Kafka ACL：Broker 凭证只允许 produce 到 telemetry.raw.* / command.ack.raw，
   不允许 consume、不允许操作其他 topic（下行不走 Kafka）。
   下行 gRPC endpoint：仅接受来自 Command Service 的内网调用（mTLS / 内网 ACL），拒绝公网。
   Redis：仅 presence/registry/lease 相关 key 模式。
3. 所有后端启用认证（Kafka SASL、Redis AUTH），
   凭证按节点签发、可单独吊销。
4. Broker 进程非 root 运行、最小镜像、只读根文件系统（CI/CD 管线
   设计时落实，见 TODOS #4）。
5. 凭证截获面补偿控制（对应 §5.2 普通入口 VPC 明文跳的残余暴露）：
   - 云账号高危操作审计必须覆盖「创建/启用流量镜像、镜像会话」——
     §4.1 的流日志只审计东西向流量内容，不审计「开镜像」这个动作本身，
     而开镜像是凭证无痕被动截获的唯一云原生向量，必须单独盯。
   - LB 后端抓包文件（tcpdump / 镜像导出）一律按凭证密级处理：
     禁止进对象存储/工单/聊天工具明文留存，抓完即焚或加密隔离。
   - 运维 runbook 注明：LB 后端是明文链路，排障抓包等同接触设备凭证。
```

## 7. 典型攻击场景推演

每个场景走一遍责任链，验证矩阵闭环：

```text
场景 1：300Gbps UDP 反射打到接入 IP
  云厂商清洗 -> 超阈值进黑洞 -> 触发 §4.2 预案：DNS 切备用入口 /
  临时上高防 -> 设备按退避 + jitter 迁移 -> Broker 全程无动作。
  事后：评估是否常态化高防（成本进 doc 4 口径）。

场景 2：僵尸网络 CONNECT flood（随机伪造 client_id）
  普通设备入口：云 TLS LB 先承接 TLS 握手压力 ->
  Broker 从 MQTT CONNECT 开始防御：认证全部 cache miss ->
  负向缓存 + auth queue 保护 DB（doc 5）-> unknown client_id 洪泛
  规则触发，按 IP 短时封禁（§5.3）-> 指标区分攻击与日出风暴
  （认证成功率断崖 = 攻击）。
  注意：未知 client_id 在认证前无法归属租户，封禁生效前会消耗全局
  CONNECT rate / auth queue（doc 5 §6.1），合法设备可能一起收到
  Server Unavailable。当前保证是"伤害有界 + 封禁收敛"；
  若要隔离合法设备影响，需要单独设计租户预留容量。
  高安全 mTLS 入口：L4 透传到 Broker，先由 Broker mTLS 握手限流削峰，
  再进入同样的 CONNECT / 认证防线。

场景 3：凭证填充（拿泄露的真实凭证字典撞库）
  流量小、协议合法，云厂商不可见 -> Broker：bad credential 按
  client_id 聚合触发 device 短封 + 告警 -> 平台：确认泄露范围 ->
  批次凭证轮换（§6.1）+ tenant 级观察。
  根治依赖"每设备唯一凭证"——撞对一个只损失一个。

场景 4：被劫持的合法设备 QoS1 高频轰炸
  协议合规、凭证有效 -> Broker 视角等同过载：per-client inflight=1 +
  byte budget 限住单设备伤害（doc 6）-> per-device 速率指标偏离基线 ->
  平台判定（§6.3）-> 禁用凭证 + kick。
  Broker 的有界设计保证单设备无论如何打不穿全局预算。

场景 5：1 万条慢读连接（CONNECT 后半包挂起）
  云厂商视角：健康低速连接，不可见 -> Broker：read deadline 覆盖
  包中途（doc 8 §11.5.3）+ 半开连接在 keepalive 判死窗口回收 ->
  fd / 预算释放 -> 攻击成本远高于收益。
```

## 8. 攻击与风暴的同构与差异

doc 6 的结论在攻击场景下依然成立：一切都是"输入速率 > 服务速率"。因此**背压水位机制（L0~L3）天然是 DoS 缓解的执行层**，无需为攻击另建一套限流。

差异只有一个维度：

```text
故障风暴：参与者善意 -> 正确响应是"反馈压力，等待退避"（doc 6）。
攻击流量：参与者恶意 -> 退避假设不成立，正确响应是"识别 + 封禁"，
         把攻击者从输入端摘除，而不是与之进行退避博弈。
```

识别靠的是攻击独有的指纹：认证成功率断崖、未知 client_id 占比、错误凭证字典分布、LB / mTLS 握手失败率、ACL 拒绝——这些指标正常风暴下都接近零。**水位告警触发时，第一个判断动作就是看这组指纹，区分"扩容/等待"还是"封禁"。**

## 9. 指标与告警

在既有指标（doc 5 §12、doc 6 §11、红线 §11）之上，攻击识别专用：

```text
blacklist_ip_count / blacklist_device_count        # 当前封禁量
blacklist_hit_total（按层分）                       # 命中即攻击仍在持续
auto_ban_triggered_total（按规则分）                # 自动封禁动作
auto_ban_release_total                             # 自动解封
unknown_clientid_auth_fail_rate（按源 IP top-N）    # 凭证填充/洪泛指纹
bad_credential_rate（按 tenant / 按 IP）            # 爆破指纹
lb_tls_handshake_fail_rate（普通入口，云监控 API，按源 IP top-N）
                                                     # 分钟级粒度/延迟，只用于事后封禁候选
broker_mtls_handshake_fail_rate（高安全入口，本地近实时）
                                                     # Broker 终结 mTLS 场景
acl_reject_total（按 device top-N）                 # 越权探测
oversize_payload_reject_total                      # payload 攻击尝试
half_open_conn_reaped_total                        # 慢读/半开回收量
auth_success_rate                                  # 断崖 = 攻击 vs 风暴的分界指标
```

指标时效分层：

```text
Broker 本地指标（unknown_clientid_auth_fail_rate、bad_credential_rate、
broker_mtls_handshake_fail_rate 等）可以驱动短 TTL 自动封禁。

云 LB TLS 握手失败率只能从云监控 API 获取，通常是分钟级粒度且有采集 /
查询延迟。普通入口的"握手异常 -> 封 IP"只能作为事后封禁候选或人工处置
输入，不能承诺实时拦截；普通入口的实时保护仍依赖云 LB 自身握手容量 /
限速，以及 Broker 在源 IP 可信化后、CONNECT 处理前的本地 ip_blacklist。
```

告警建议：

```text
auth_success_rate 断崖式下跌（连接量同时上涨）      -> 疑似 CONNECT flood
unknown_clientid_auth_fail_rate top-N IP 突增      -> 疑似洪泛，关注自动封禁是否生效
bad_credential_rate 按 tenant 聚集                 -> 疑似该租户凭证泄露
blacklist_hit_total 持续高位                       -> 攻击未停，评估升级高防
auto_ban_triggered_total 突增且命中同一 CGNAT 段    -> 检查误伤（§5.3 校准）
acl_reject_total 单 device > 0 持续                -> 进入 §6.3 判定流程
```

红线口径不变：禁止 device_id / IP 全量作为指标 label（红线 §11），top-N 聚合输出。

## 11. 攻防演练矩阵

与 doc 8 压测互补，按"恶意流量"口径：

```text
凭证填充：10 万条错误凭证字典，分布在 100 / 1000 个源 IP，

TLS 握手耗尽：普通入口压云 TLS LB，高安全入口压 Broker mTLS，

内部横向演练：以 Broker 节点凭证尝试越权访问 Kafka 其他 topic /
         Redis 其他 key / PG 写操作，验证最小权限配置生效。
```

验收口径沿用 doc 8：看曲线不只看结果，封禁/解封/恢复全程指标可解释。

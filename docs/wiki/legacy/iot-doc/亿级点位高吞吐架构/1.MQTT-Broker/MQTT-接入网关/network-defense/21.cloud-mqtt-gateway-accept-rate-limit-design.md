# 21. mqtt-gateway accept 层限流设计（CONNECT 路径第 1 层）

## 21.1 为什么单独成文

mqtt-gateway 是公网接入层，每条 CONNECT 都要烧「auth worker + Redis presence ×2 + 连接槽 + fd」。在 TCP 握手完成后、MQTT CONNECT 解码前这个**最早的廉价拒绝点**做总准入控制，能把总量洪水（僵尸网络、伪造 clientID 扫描、区域性雷鸣群）在烧掉昂贵链路之前挡掉。

本文是 **CONNECT 路径三层防御的第 1 层**（对应 EMQX 的 `ranch_limiter`）。第 3 层的 flapping 计数与黑名单在 doc 19/doc 20，三层全景与编排在 doc 9 §5。本文只管「accept 层怎么限流」这一件事。

## 21.2 EMQX ranch_limiter 源码事实

EMQX 在 accept 层（TCP 握手后、MQTT 协议之前）由 `ranch_limiter` 做两道检查（`emqx_ranch_limiter.erl`）：

```text
allow(Socket, State):
  ① allow_capacity：atomics 计数器，检查 max_connections 并发上限
     → 超了：close_connection（拒绝当前连接）
  ② allow_limiter：emqx_limiter_client:try_consume（令牌桶速率限流）
     → 超了：close_connections_for(100ms)（暂停 100ms 再接受）
accepted()：atomics:sub（并发计数 -1）
retired()：atomics:add（连接断开时并发计数 +1，与 accepted 配对）
```

两道子检查职责分明：

| 子检查 | 维度 | 拒绝动作 | 防什么 |
|---|---|---|---|
| `allow_capacity` | 并发连接数上限 | 立即 close | 内存/fd/连接槽耗尽 |
| `allow_limiter` | 新建连接速率（令牌桶）| 暂停 accept | CPU/认证链路速率被 CONNECT flood 打穿 |

EMQX 用 atomics（无锁原子计数器）实现并发上限，令牌桶做速率限流，二者在 accept 层组合，**都发生在 MQTT 协议层之前**——拒绝成本只有一次 TCP 握手，不烧认证/会话/路由。

## 21.3 mqtt-gateway 设计：单一全局令牌桶

### 21.3.1 选型：golang.org/x/time/rate，不自研、不分片

```go
import "golang.org/x/time/rate"

// 一个全局 rate.Limiter（golang.org/x/time/rate），不分 key，内存恒定。
//
// ⚠️ 选型（不自研、不分片）：
//  - 不自研令牌桶：x/time/rate 是准标准库（零传递依赖，不违反 gateway 依赖极简
//    红线），内部纳秒精度 lazy refill。自研版本极易踩的生产级 bug——
//    「int(elapsed*rate) 向下取整补 0 个令牌 + lastRefill 无条件推进永久丢弃小数
//    → 高频调用（到达间隔 < 1/rate）下 burst 耗尽后桶永远补不回来、持续全拒」
//    ——在它那里结构上不存在。
//  - 不分片：曾按「1M CONNECT/s」论证 64 分片，该数字把「1M 在线连接总数」
//    误当「每秒 1M 次 CONNECT」。真实 CONNECT 速率：日出稳态 ~1667/s、雷鸣群
//    瞬时数千/s（§21.5 校准），距单 mutex 极限（~10M lock/s）3 个量级，
//    单 Limiter 锁占用率 <0.1%，分片是无负载支撑的复杂度。若未来单节点速率
//    量级上升，[]rate.Limiter 值嵌入分片即可，仍无需自研。
var global = rate.NewLimiter(rate.Limit(cfg.Rate), cfg.Burst) // rate/burst 校准见 §21.5
```

### 21.3.2 接入点：OnOpen

```go
// OnOpen 准入。令牌桶在 TCP 建连后、MQTT CONNECT 解码前执行（最早的廉价拒绝点）。
func onOpenAdmit() bool {
    return global.Allow() // 超限：return gnet.Close，不写黑名单
}
```

**特性**：

- **内存恒定**：单个 Limiter（常数，不随连接/攻击规模增长），无法撑爆——这是「不可信 key 不做聚合计数」原则的直接体现（详见 doc 9 §5 三层全景）
- **热路径锁开销可忽略**：真实 CONNECT 速率（日出 ~1667/s、雷鸣群瞬时数千/s）距单 mutex 极限 3 个量级；pprof mutex profile 出现热点即实现 bug（§21.7）
- **不写黑名单**：超限只拒当前连接（`return gnet.Close`），不触发 ban——避免「逼你 ban IP 自伤」（详见 doc 19「公网场景的核心约束」）
- **不区分来源**：无论攻击者用多少 clientID/IP，总量被限定

### 21.3.3 并发上限 MaxConnections（capacity 闸）

EMQX `allow_capacity` 的并发上限对应 mqtt-gateway 的 **MaxConnections**——这不在本表（令牌桶）实现，而在 gnet accept 层实现，详见 [gnet 走查 §8.7.7 闸门 4](../reference/gnet/gnet-source-walkthrough.md)：

```text
MaxConnections 必须 > auth queue + presence queue + 活跃连接数之和，
否则正常连接会被洪泛连接在内存里挤掉（gnet §8.7.7）。
```

**两闸关系**：MaxConnections 是「同时在内存里的连接数」上限（防 fd/内存耗尽），令牌桶是「新建连接速率」上限（防 CONNECT flood 烧认证链路）。两者互补，对应 EMQX 的 `allow_capacity` + `allow_limiter`，缺一不可。

## 21.4 与第 3 层（flapping / 黑名单）的分工

令牌桶（本文，第 1 层）和 flapping 计数 / 黑名单（doc 19/doc 20，第 3 层）都在拒绝连接，但职责完全不同：

| 维度 | 第 1 层 总量令牌桶（本文） | 第 3 层 flapping / 黑名单（doc 19/20） |
|---|---|---|
| 时机 | OnOpen（认证前） | CONNECT 解码后 / 认证后 / OnClose |
| 维度 | 不分 key，全局总量 | 认证后可信 deviceID |
| 拒绝原因 | 总量超限（不区分善意恶意） | 该设备/来源被识别为坏 |
| 写黑名单？ | ❌ 只 Close 当前连接 | ✅ 命中写 device_blacklist |
| key 可信？ | N/A（不分 key） | ✅ 认证后 deviceID |

一句话：**第 1 层挡「总量洪水」（不知道谁坏，先削峰），第 3 层挡「已识别的坏设备」（知道是谁，廉价拒）**。第 1 层是第 3 层的上游保险——没有第 1 层，僵尸网络的几万 CONNECT/s 会先打满 auth queue，第 3 层的判定根本来不及跑。

## 21.5 参数校准（refillRate / burst）

两个参数都要校准，缺一不可：

### 21.5.1 refillRate（稳态补充速率）

`refillRate` = 正常日出峰值 × 2（比如日出 1667 CONNECT/s → 设 3000/s）。攻击者的 500/s 远低于此，但万级僵尸网络的几万/s 会被挡。

### 21.5.2 burst（突发容量）—— 最容易误伤合法场景

`maxTokens`（**突发容量 burst**）必须能吸收**合法的雷鸣群**——这是第 1 层最容易误伤的场景：基站/路由重启恢复瞬间，一个区域内成千上万设备**同时**重连。在总量维度上它与僵尸洪水**不可区分**（都是短时间内海量 CONNECT），第 1 层没有设备身份信息可用来区分。故 burst 不能只按「缓变日出」设，必须覆盖「突发集体恢复」峰值：

```text
推导：maxTokens = 一次基站恢复影响设备数 × 单设备瞬时重连次数（典型 1-3，含首次失败重试）× 安全系数（2-3）
例：一个基站下 2 万设备，恢复后多数在 30s 内重连、平均重试 1.5 次
   → 瞬时总量 ≈ 3 万 → burst 设 6-9 万
```

⚠️ **burst 设小了会误杀合法重连**：基站恢复时设备被第 1 层拒 → 需要退避重试才能进。而这恰是最需要重连的场景（设备刚恢复信号）。

### 21.5.3 误拒后的自愈：依赖设备侧 backoff+jitter（doc 7 红线 #8）

⚠️ **此假设有一个内部矛盾点**：flapping 来源之一就是「固件 bug（重连逻辑无退避/jitter）」——也就是说**最需要重连的设备恰恰可能不退避**（doc 19「业务场景」）。第 1 层拒一个无 jitter 的固件设备，它会立即同步重连，反复撞墙直到 burst 被 refillRate 慢慢补上（几秒~几十秒），期间该设备完全上不了线。

这是**已接受的边界**，不是漏洞——第 1 层是总量兜底，不可能对无 jitter 设备既挡洪水又零误伤。缓解：

- (a) burst 按 §21.5.2 校准到覆盖 P95 基站恢复规模；
- (b) 红线 #8 落地强制固件 jitter（出厂准入），缩小「无 jitter 设备」群体；
- (c) 监控第 1 层拒绝率，基站恢复时段的拒绝尖峰与运维告警关联（可辨识的合法突发 vs 攻击——见 doc 9 §8「攻击 vs 风暴的识别指纹」）。

这三条都要有对应压测/监控项（§21.7）。

## 21.6 per-IP 限流废弃决策（应用层不做 per-IP，交给基础设施）

> 本节记录 per-IP 令牌桶从设计到废弃的完整讨论，作为决策依据。原方案曾作为「第 1 层的第二道子闸」与总量桶并列，现已废弃。

### 21.6.1 初版设计

初版设想在总量令牌桶之外再加一道 per-IP 令牌桶（otter/S3-FIFO 固定容量，抗扫描），执行顺序为「per-IP 先砍 → 总量桶兜底」，目的是防单 IP 挤占全局令牌。

### 21.6.2 废弃理由 1：GC 成本 > 收益

per-IP 限流的实现需要维护一个 `map[IP]*tokenBucket`（或 otter Cache），1 万个 IP 条目 × 每条目含 string key + 指针 value = 约 2-3 万 GC 扫描单元。在百万连接的 GC 压力下，这是真实的 mark 成本（每轮 GC 增加几毫秒）。

对比它保护的东西：per-IP 限流保护的是 **presence Redis 写**（网络 I/O）。但如果认证系统（[doc 15 本地快照](../15.cloud-mqtt-credential-local-snapshot-design.md)）足够快，presence 写真的需要这层保护吗？

### 21.6.3 废弃理由 2：presence 只在认证成功后写（收益 ≈ 0）

关键洞察：presence 写的触发条件是**认证成功**（红线 #6：CONNECT 成功 = 认证 + presence）。认证失败的连接不碰 presence。

| 场景 | presence Redis QPS | 原因 |
|---|---|---|
| 正常 CGNAT 上线（5000 设备/日出窗口）| ~8/s | 5000 次 presence 写分散在 600s 窗口 |
| 攻击（伪造凭证）| **0** | 认证在本地快照 O(1) 判负，不碰 presence |
| 大规模凭证泄露 | 高 | ⚠️ 安全事故，不是限流能解决的 |

**结论**：per-IP 限流保护 presence 的收益 ≈ 0——正常场景 Redis 无压力，攻击场景认证阶段就挡住了（不碰 presence），凭证泄露是安全事故（解法是 [doc 9 §6.1](9.cloud-mqtt-gateway-network-attack-defense.md) 凭证轮换 + tenant_freeze + kick，不是 per-IP 限流）。

### 21.6.4 大规模凭证泄露也不是限流问题

如果攻击者拿到了成千上万的真实凭证，per-IP 限流根本拦不住（因为认证成功 → 写 presence → 正常流程）。这种场景的正确响应是：

- 凭证轮换（[doc 5 §6.1](../5.cloud-mqtt-connect-auth-design.md) / [doc 9 §6.1](9.cloud-mqtt-gateway-network-attack-defense.md)）
- tenant_freeze（[doc 9 §5.3](9.cloud-mqtt-gateway-network-attack-defense.md)）
- 主动 kick 连接（Phase 2 控制通道）
- 安全事件响应流程

**不是 per-IP 限流**。per-IP 限流挡的是「同一 IP 高频连接」，但凭证泄露的攻击者可以用多个 IP、正常速率连接，per-IP 限流完全失效。

### 21.6.5 IP 维度防御由基础设施承担

| IP 层威胁 | 由谁防 | 机制 |
|---|---|---|
| SYN Flood | **NLB**（DDoS 原生防护 + 增强版 EIP）| SYN cookie / 清洗 |
| 体积型 DDoS（带宽/PPS）| **NLB** | Tbps 级清洗 |
| 半连接耗尽 | **NLB** | TCP 超时清理 |
| 已知恶意 IP（人工判定）| **安全组 ACL / ip_blacklist** | 人工加，不自动 |
| 单 IP 高频 CONNECT | **总量令牌桶（本文第 1 层）** | 不分 IP，总量削峰 |

**应用层（mqtt-gateway）不做 per-IP 速率限流**。这与 EMQX 的哲学一致（IP 层交给基础设施，应用层用认证 + flapping）。详见 [doc 9 §4.1 NLB 责任矩阵](9.cloud-mqtt-gateway-network-attack-defense.md)。

### 21.6.6 废弃结论

| 维度 | 废弃前 | 废弃后 |
|---|---|---|
| 认证前限流 | 总量令牌桶 + per-IP 令牌桶 | **只有总量令牌桶** |
| IP 维度 | 应用层 per-IP 限流 | **交给基础设施**（NLB/安全组/云 DDoS）|
| GC 成本 | per-IP map 2-3 万扫描单元 | **零**（总量桶是 1 个计数器）|
| presence 保护 | per-IP 限流削峰 | **不需要**（认证挡住攻击，presence 不受威胁）|

**核心原则**：

> **认证前（key 不可信）：只做总量限流（1 个计数器，零 GC），不做 per-IP 聚合。**
> **认证后（key 可信）：才做 flapping 计数（doc 19）。**
> **IP 维度：交给基础设施（NLB SYN 防护 + 安全组 ACL）。**

> ⚠️ 与 ip_blacklist 的关系：ip_blacklist **不得**因「IP 连接数高 / unknown client_id 洪泛 / 认证失败多」自动触发——这些是日出 + CGNAT 的正常形态，自动 ban 会连坐 CGNAT 下上万真实设备（详见 doc 19「公网场景的核心约束：逼你 ban IP 自伤攻击」+ [doc 9 §5.3](9.cloud-mqtt-gateway-network-attack-defense.md)）。ip_blacklist 只由人工运维 或 高置信度规则（如 mTLS 握手失败率）触发。

## 21.7 实现约束（红线口径）

```text
1. accept 层令牌桶：
   - 不得按不可信 key（clientID/IP）聚合计数（防撑爆，详见 doc 19「不可信 key 不聚合」）
   - 令牌桶 = golang.org/x/time/rate，不自研、不分片：准标准库、零传递依赖、纳秒精度
     lazy refill，自研常见的「int 截断小数令牌 + lastRefill 无条件推进 → 桶漏空永拒」
     bug 结构上不存在。真实 CONNECT 速率距单 mutex 极限 3 个量级，单 Limiter 足够
     （曾以「1M CONNECT/s」论证分片，该数字混淆了在线连接总数与每秒 CONNECT 速率，作废）
   - 超限只拒当前连接（gnet.Close），不写黑名单（防 CGNAT 连坐）

2. MaxConnections（capacity 闸，gnet §8.7.7）：
   - 必须 > auth queue + presence queue + 活跃连接数之和
   - 与令牌桶互补：并发上限防 fd/内存耗尽，令牌桶防 CONNECT flood 烧认证链路

3. burst 校准：
   - maxTokens 必须覆盖「基站/路由恢复 → 区域性集体重连」的雷鸣群（doc 19 业务场景），
     不能只按缓变日出设。推导：基站影响设备数 × 单设备瞬时重连次数（1-3）× 安全系数（2-3）
   - burst 设小了会误杀合法重连——基站恢复是最需要重连的场景

4. 应用层不做 per-IP 限流（已废弃，§21.6）；IP 维度由 NLB/安全组承担
5. ip_blacklist 不因「IP 连接数高」自动触发（防 CGNAT 连坐，详见 doc 19 + doc 9 §5.3）
6. 指标只打聚合 counter，per-IP 明细只进审计日志，禁止高基数 label（红线 §11）
```

## 21.8 验证清单

```text
令牌桶（第 1 层）
[ ] 单 Limiter 内存恒定，超限只 Close 不 ban
[ ] accept 热路径锁开销验证：按真实峰值（雷鸣群瞬时数千 CONNECT/s）压测，pprof mutex profile
    中 global rate.Limiter 不得成为热点（真实量级距锁极限 3 个量级，出现热点即实现 bug）
[ ] burst 校准：maxTokens 覆盖基站/路由恢复的雷鸣群（§21.5.2 推导），不得只按缓变日出设
[ ] 基站恢复式突发重连不被总量桶大面积拒：压测模拟「单基站 2 万设备在 30s 内集体重连
    （平均重试 1.5 次）」的雷鸣群，断言第 1 层拒绝率在可接受范围（如 < 5%，剩余靠设备
    backoff+jitter 自愈）。同时验证第 3 层 flapping 不误判（每设备各自重连次数 < 阈值，
    不触发 deviceID 封禁）。区分判据：拒绝率与基站恢复告警时间相关 → 合法突发；
    拒绝率与告警无关且持续 → 疑似攻击（doc 9 §8）
[ ] 无 jitter 设备退化场景：模拟 burst 耗尽后拒一个不带 backoff/jitter 的设备（doc 19 业务场景），
    断言该设备在 burst 被 refillRate 补上后能恢复上线（误伤是暂时的、自愈的，不是永久拒）
[ ] 限流器集成回归测试：以 10000 次/秒持续调 Allow() 5 秒，通过率 ≈ 配置 rate（如 3000/s →
    约 15000 通过，±5%）。卡住 rate/burst 配置接线错误（单位换算、rate.Limit 类型误用）

MaxConnections（capacity 闸）
[ ] MaxConnections 边界：MaxConnections < auth+presence queue+活跃 时，正常连接被洪泛挤掉
    → 断言配置校验拦住（gnet §8.7.7）

per-IP 废弃边界
[ ] 应用层不做 per-IP 限流（已废弃，§21.6）；IP 维度由 NLB/安全组承担
[ ] ip_blacklist 不因「IP 连接数高」自动触发（防 CGNAT 连坐）

攻击模拟（与 doc 9 §11 攻防演练矩阵互补）
[ ] 攻击模拟 1（单 IP 伪造 clientID）：认证 O(1) 判负 + 第 1 层总量削峰，不 ban IP
[ ] 攻击模拟 2（多 IP 海量 clientID）：第 1 层总量令牌桶挡住
[ ] 所有拒绝有指标 + 审计日志
```

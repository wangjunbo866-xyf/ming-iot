## 20.1 为什么单独成文

doc 9 把接入层攻击分成三类分工：**云厂商防带宽、Broker 防语义、平台防身份**。前两类（A1–A4）云 LB 或 Broker 的有界设计已覆盖大半；唯独**凭证与身份类攻击（A5）两边都接不住**——

```text
流量完全合法（几百个 CONNECT/s，量级远低于洪水阈值）
协议完全合规（标准 MQTT 3.1.1 CONNECT，没有畸形包）
       ↓
云厂商看不见（DDoS 清洗/WAF 对它无效，doc 9 §4.3）
纯协议健壮性也挡不住（包本身合法，doc 9 §5.1 的限长/fuzz 无从触发）
       ↓
只能靠「平台的凭证体系 + Broker 上的执行点」这一条线防
```

这条线不是一个开关，而是一套多层机制：负向缓存的抗扫描、bounded auth queue 的四道闸门、错误凭证 throttle、device 级自动封禁、租户级熔断、CGNAT 误伤校准。它已经在 `internal/auth` 落地了核心件（负缓存 `cache.go`、认证队列 `queue.go`、常量时间校验 `auth.go`），但**防御视角的完整攻击面分析、封禁执行点、CGNAT 校准散落在 doc 9 §5.3 + doc 5 §5.2 + gnet 走查 §8.7.7 + EMQX review 三四处**，没有一篇把它们按「攻击 → 防线 → 红线 → 验证」串起来。

**和 flapping（doc 19）的关系**：EMQX 在 CONNECT 认证**之前**串了两道闸——`check_banned`（黑名单）+ `count_flapping`（抖动计数）（`emqx_channel.erl:623-624`，review §2.3）。我们把这两件事拆成两篇：

| EMQX 认证前的闸 | 我们的文档 | 针对 |
|---|---|---|
| `count_flapping` 抖动计数 | **doc 19** | 认证**成功**但反复建断连（4G 抖动 / 无退避固件 / takeover）|
| `check_banned` 黑名单 + 认证资源保护 | **本文（doc 20）** | 认证**失败**为主（爆破 / 撞库 / unknown 洪泛 / 被盗凭证重放）|

两篇共享同一套 `device_blacklist`（共享 Redis SoT + 本地副本，doc 19 §19.6），但触发条件、key 语义、误伤模型不同，值得各自成文。

## 20.2 凭证攻击的本质与逆变器场景

### 20.2.1 五种形态

| # | 形态 | 认证结果 | 云可见？ | 核心危害 |
|---|---|---|---|---|
| C1 | **unknown client_id 洪泛** | 失败（not found）| 否 | 打穿认证只读库 / 撑爆负缓存 |
| C2 | **错误凭证爆破**（字典撞单设备密码）| 失败（bad credential）| 否 | 烧 auth worker + DB；被反用来 DoS 真实设备 |
| C3 | **凭证填充 / 撞库**（拿泄露的真实凭证）| **成功** | 否 | 冒充真实设备，云和协议层完全无感 |
| C4 | **被盗凭证重放**（截获静态 secret 复用）| **成功** | 否 | 同 C3，但源于 secret 被动截获（doc 9 §5.2 残余暴露）|
| C5 | **时序侧信道枚举**（用响应时间探设备是否存在）| 失败 | 否 | 为 C1/C2 提供有效 client_id 字典 |

**与 flapping 的分界**：flapping 的认证「通常都成功」（密码没错，doc 19 §19.1），本文的 C1/C2/C5 认证「基本都失败」，C3/C4 认证成功但**行为异常**（走 doc 9 §5.4 A6 信号 + §6.3 离线判定，不在本文热路径）。一句话：**flapping 防"合法设备抖"，本文防"非法者试凭证"。**

### 20.2.2 逆变器场景的放大器

```text
1. client_id 可枚举：格式如 tenant-a:INV_001（doc 5 §5.2），攻击者不需要任何
   泄露就能生成海量候选 client_id 做 C1 洪泛，或对已知 client_id 做 C2 爆破。
2. 凭证一旦泄露即长期有效：静态 bearer secret，无 nonce/challenge，被截获
   （LB 后端明文抓包、中间盒，doc 9 §5.2）后可无限重放到轮换为止（C4）。
3. 固件 bug 与攻击同构：坏固件反复用错密码重连，表现和 C2 爆破几乎一致，
   靠「字典分布 vs 单一错误」区分（§20.6）。
```

## 20.3 攻击面分析（核心难点：认证是可信边界）

和 doc 19 §19.3 同一根因：**认证前的 key（client_id / IP）是攻击者可控输入**。凭证攻击把这个难点玩到极致——它的目标恰恰就是认证系统本身。

### 20.3.1 攻击 1：unknown client_id 洪泛 → 打穿 DB / 撑爆负缓存

```
攻击者生成 100 万个不存在的 client_id，每个发一次 CONNECT
  → 每个都 cache miss → 穿透到认证只读库 select where client_id=?
  → DB QPS 飙到 connect_rate（doc 5 §7 冷启动同构：hit_rate≈0）
  → 若负缓存用「map + 随机/顺序驱逐」：缓存填满且条目未过期时，
     每次 miss-insert 要 O(n) 扫描找过期项 → 每个 CONNECT 一次全表扫描 → CPU 耗尽
```

**防御 = 负向缓存 + 抗扫描存储**。负缓存把「not found」这一事实缓存 30~120s（`cache.go` `NegativeTTL`），挡住重复的 unknown。但负缓存本身若用朴素结构就是新的攻击面：

> ⭐ **这正是 accept 层 per-IP 限流同款问题的认证版**：`internal/auth/cache.go:29-37` 已把负缓存底层从手写 map 换成 **otter（S3-FIFO）**——O(1) 驱逐 + 抗扫描（海量一次性 unknown key 洪泛不冲刷反复命中的热凭证）。已有回归测试 `TestCachingStore_ScanResistanceKeepsHotEntry` / `TestCachingStore_BoundedUnderFlood` 卡住。本文的负缓存、doc 5 §5.4 的正缓存、（已废弃的）accept 层 per-IP 桶，**三处是同一个决策的三次应用**：不可信 key 的有界结构必须按频率淘汰，不能按最近访问淘汰。（per-IP 桶废弃记录见 [doc 21 §21.6](21.cloud-mqtt-gateway-accept-rate-limit-design.md)。）

### 20.3.2 攻击 2：错误凭证反用来 DoS 真实设备（自伤攻击）

这是凭证防御最容易踩的坑，和 doc 19 §19.3.1「逼你 ban IP」同构，但落在 client_id 维度：

```
client_id 可枚举（tenant-a:INV_001）
  → 攻击者对某真实设备的 client_id 发一次错误密码
  → 如果把「bad credential」写成按 client_id 的负缓存 / 直接封 client_id：
     该 client_id 被全局拉黑 10s~60s
  → ⚠️ 真实设备拿正确密码来也被拒 → 定向 DoS，攻击成本≈1 个包
```

> ⚠️ **doc 5 §5.2 红线（本文重申并归因）**：
> - **禁止把 bad credential 作为按 client_id 的负缓存条目**——负缓存只缓存「not found」，不缓存「密码错」。`cache.go` 的负缓存只在 `found=false` 时写入，`Authenticate` 里 bad credential 走的是 `found=true` 分支（`auth.go:110`），根本不进负缓存，实现上已经对齐。
> - **禁止把「设备禁用」作为按 client_id 的负缓存条目**——`status` 是正缓存记录的字段（`CredentialRecord.Status`），随记录一起过期，不单独拉黑。
> - **错误凭证的限流必须独立于 auth cache**，key = `(client_id, IP)`（至少含二者），只降频不拉黑，**命中 throttle 时正确密码仍必须被校验放行**（doc 5 §5.2）。

### 20.3.3 攻击 3/4：凭证填充与重放 → 认证成功，热路径无从分辨

```
攻击者拿泄露的真实 (client_id, secret) 撞库（C3），或复用截获的 secret（C4）
  → 认证成功、协议合规、流量小 → Broker 热路径与合法设备完全一致
  → 无法在 CONNECT 那一刻判定（判定需要业务上下文：该设备是否本就在别处在线、
     地理/运营商是否突变、上报是否偏离基线）
```

**热路径不做判定**（同 doc 9 §5.4）：Broker 只输出信号（`presence_connect_with_old_count` 并发在线、per-device 速率偏离），判定交平台离线基线（doc 9 §6.3）。**根治靠凭证体系**（§20.7）——每设备唯一高熵凭证，撞对一个只损失一个。C4 额外要靠「用即疑 → 轮换 + kick」压缩重放窗口。

### 20.3.4 攻击 5：时序侧信道枚举有效 client_id

```
「查到设备才比较密码、查不到直接返回」→ 响应时间泄露 client_id 是否存在
  → 攻击者据此筛出有效 client_id 字典，喂给 C2 爆破
```

**防御已在 `auth.go` 落地**：not-found 分支仍对 `dummyHash` 做一次等长 constant-time 比较（`auth.go:68-70,105`）抹平时间差；且**先验 secret 再看 status**（`auth.go:109-115`），错误 secret 一律返回 `0x04`，不向无凭证者暴露设备「存在 / 禁用」状态。这两点是防 C5 的实现级红线，不能在后续重构中被「优化」掉。

## 20.4 分层防线

按 CONNECT 生命周期排列，从认证前到认证后，粒度从粗到细：

| 防线 | 时机 | 机制 | key 可信？ | 针对 | 载体 |
|---|---|---|---|---|---|
| **0. 认证前黑名单** | CONNECT 解码后、认证前 | ip_blacklist + device_blacklist（经 L1 clientID→deviceID）| 部分 | 已识别的坏来源/设备 | doc 9 §5.3、doc 19 §19.5 |
| **1. 负向缓存** | cache 查询 | not-found 抗扫描缓存 | ❌（client_id 可伪造）| C1 unknown 洪泛 | `cache.go` |
| **2. bounded auth queue 四道闸门** | 入队认证 | 有界队列+固定 worker+inflight=1+超时踢 | N/A | C1/C2 认证资源耗尽 | `queue.go`、gnet §8.7.7 |
| **3. bad-credential throttle** | 校验失败后 | `(client_id,IP)` 降频，不拉黑 | ❌ | C2 爆破（防自伤）| doc 5 §5.2（待落地）|
| **4. device_blacklist（爆破封禁）** | 校验失败累计 | 可信 deviceID 累计 N 次 bad credential→短封 | ✅（L1 映射得到）| C2 定向爆破 | doc 9 §5.3、共享 doc 19 §19.6 |
| **5. tenant_freeze** | 人工 | 租户级熔断 | ✅ | 大面积凭证泄露 | doc 9 §5.3 |

### 20.4.1 防线 1：负向缓存（认证前，抗扫描）

```text
key:   client_id（负缓存与正缓存共用一个 otter 实例，cache.go）
value: found=false
TTL:   NegativeTTL 30~120s（短——便于设备真正纳管后尽快能登录）
```

纪律（对应 §20.3.1 / §20.3.2）：
- **只缓存 not-found**，绝不缓存 bad-credential / disabled（否则退化成 §20.3.2 自伤攻击）。
- **DB 错误不缓存**（`cache.go:75-77`）——瞬时故障不应毒化缓存，否则一次 DB 抖动会让一批设备被负缓存拒到 TTL。
- **必须 otter/S3-FIFO 抗扫描**，不得用朴素 LRU/随机驱逐（§20.3.1）。
- **TTL 在包装层判定**（`cache.go:70` 用 `c.now` 比 `expiresAt`），不用 otter 原生 TTL——正负 TTL 不同，且可注入假时钟做确定性单测。
- **容量有界但异步驱逐**：otter 突发期 `Size()` 可瞬时 ~2~3× `MaxEntries`，稳态收敛（doc 5 §5.4）。容量规划留 3× 余量。

### 20.4.2 防线 2：bounded auth queue 四道闸门（gnet §8.7.7）

`internal/auth/queue.go` 已实现前三闸，第四闸在 accept 层（gnet 走查 §8.7.7）：

```text
闸① bounded auth queue：满即 fail fast（ErrAuthOverloaded → CONNACK ServerUnavailable），
    不无限排队（queue.go:125-128）。建议容量 1000~5000（doc 5 §6.1）。
闸② 固定 worker pool：goroutine 数不随连接数增长（红线 §7；queue.go Workers）。
闸③ per-client inflight=1：同一 client_id 同时只允许一个在途认证
    （queue.go acquireInflight/releaseInflight），挡住单设备/单 client_id 重连风暴
    在 DB 卡住时堆叠多个 job。⚠️ 释放权归 worker：即使调用方超时放弃，也要等真正
    处理完才释放（queue.go:100-103），否则同 client_id 会绕过 inflight=1。
闸④ 认证超时踢除 + MaxConnections：queue 里的 job 用 submit 时刻的 deadline
    （queue.go:95-98），积压 job 被捞起时 ctx 已过期→Authenticate 快速返回，不为已
    放弃的请求白打 DB。accept 层 MaxConnections > auth queue + presence queue + 活跃数
    （gnet §8.7.7），防无界 accept 把洪泛 conn 堆进内存。
```

**攻击视角的关键**：这四闸对「善意日出风暴」和「恶意 unknown/bad 洪泛」是**同一套机制**（doc 6：一切都是输入速率 > 服务速率）。差异只在识别指纹（§20.6），不在限流机制本身。

### 20.4.3 防线 3：bad-credential throttle（防自伤，待落地）

doc 5 §5.2 定义、review §3.5 标注「未落地」的独立 throttle：

```text
key:    (client_id, IP)     —— 禁止仅用 client_id（否则 §20.3.2 自伤）
        ⚠️ CGNAT 下 IP 是大出口，(client_id, IP) 仍可能覆盖同 NAT 池多设备，
           但因带了 client_id，误伤半径 = 同 client_id（单设备），可接受。
action: 限制尝试频率（如 1 次/s），命中只降频/延迟，不返回硬拒
语义:   命中 throttle 时，若该 client_id 存在有效凭证，正确密码仍必须校验并放行
        —— throttle 永不覆盖正缓存里的正确 secret_hash
```

throttle 是「防线 4 自动封禁」之前的软闸：先降频消耗攻击者，累计到阈值再升级到 device_blacklist。

### 20.4.4 防线 4：device_blacklist（爆破自动封禁，key 可信）

来自 doc 9 §5.3，**与 flapping 共享同一张 device_blacklist**（共享 Redis SoT + 本地副本 + 命中直写，doc 19 §19.6），但触发条件不同：

```text
触发：同一 device_id 连续 N 次 bad credential → 封 device（短 TTL）+ 告警
      （区别于固件 bug：爆破常伴随「字典分布」——多个不同的错误 secret；
        固件 bug 通常是「同一个错误 secret 反复重试」，§20.6）

⚠️ key 来源（易错，和 doc 9 §5.3:403-406 对齐）：
   device_id 取自认证前 L1 正缓存里 clientID→device_id 的映射——即被爆破的是一台
   「已纳管的真实设备」，其 client_id 能在 L1 命中解析出可信 numeric deviceID。
   如果该 clientID 未纳管（不存在）→ 走负缓存（防线 1），永不进 device_blacklist。
   ⇒ 攻击者用海量伪造 clientID 撑不爆 device_blacklist（它们进负缓存，不进封禁表），
     这与 §20.3.1 / doc 19 §19.3.3「不可信 key 不聚合」一致。
```

封禁参数对齐 doc 19：**固定短 TTL（如 5min）+ per-device jitter**，不做指数递增（惯犯走 doc 9 §6.3 离线基线 → 人工长封）。拦截点 = doc 19 §19.5 的双检查点（认证前 L1 廉价拒 + 认证后权威兜底）。

### 20.4.5 防线 5：tenant_freeze（租户级熔断）

人工决策（运维确认该租户凭证大面积泄露，多见于 C3 撞库命中一批），一键冻结该租户所有设备。**不自动触发**——误伤代价 = 整租户停摆（doc 9 §5.3）。

## 20.5 EMQX 对比

### 20.5.1 EMQX 的做法（源码事实，review §2.3）

```text
CONNECT pipeline（emqx_channel.erl:610-636）：
  overload_protection → enrich → check_connect → enrich_client
    → check_banned      %% emqx_banned.erl：clientid/username/peerhost/CIDR/正则 多维封禁
    → count_flapping    %% emqx_flapping.erl（→ 我们的 doc 19）
    → authenticate      %% 认证在最后
```

要点：**封禁在认证之前** → 恶意设备命中黑名单时不消耗认证资源；且 EMQX **根本不缓存认证失败结果**，靠 banned + flapping 间接防（review §3.5）。

### 20.5.2 我们的差异与理由

| 维度 | EMQX | mqtt-gateway（本文）|
|---|---|---|
| 认证失败是否缓存 | 不缓存（靠 banned/flapping）| **只缓存 not-found（unknown）**，不缓存 bad-credential |
| 为何敢缓存 not-found | — | unknown 是「查无此记录」的**事实**，可安全缓存挡 C1；bad-credential 是「密码错」的**判决**，缓存即自伤（§20.3.2）|
| unknown 洪泛防护 | ETS + overload_protection | **负缓存 + otter 抗扫描**（cache.go）+ auth queue 四道闸门 |
| 爆破封禁 key | clientid（企业内网可控）| **L1 映射得到的可信 numeric deviceID**（公网 clientID 不可信，未纳管走负缓存）|
| banned 维度 | clientid/username/peerhost/CIDR/正则 | ip_blacklist（人工/高置信）+ device_blacklist（可信 deviceID）+ tenant_freeze；**不因 unknown/bad 自动 ban IP**（防 CGNAT 自伤）|
| 封禁存储 | `emqx_banned` 集群共享表 | device_blacklist 共享 Redis SoT + 本地副本（doc 19 §19.6）|

**核心分歧**：EMQX 定位企业内网，clientid/peerhost 相对可信，敢用多维 banned + 不缓存失败。mqtt-gateway 是公网，client_id/IP 攻击者可控 → **失败结果只缓存「事实型」的 unknown，判决型的 bad-credential/disabled 绝不缓存**；自动封禁只落在认证后可信的 deviceID 上，IP 维度只做限流不自动封（review §3.2 把 banned 标为 Phase 2 缺口，本文给出公网适配后的落地口径）。

## 20.6 攻击 vs 风暴的识别指纹（区分「封禁」还是「扩容」）

doc 9 §8 的结论在凭证场景的具体化：水位告警触发时，第一个动作是看这组指纹区分成因，再决定「封禁」还是「等待/扩容」。

| 指纹 | 正常日出风暴 | 凭证攻击 |
|---|---|---|
| `auth_success_rate`（认证成功率）| 高（>95%）| **断崖**（unknown/bad 占比高）|
| unknown client_id 占比 | 低 | **高**（C1 洪泛）|
| bad credential 的 secret 分布 | 单一错误反复（固件 bug）| **字典分布**（多个不同错误 secret = 爆破）|
| 同一 device_id 的 bad 连续次数 | 偶发 | **持续累计**（C2 定向）|
| 认证成功但 `connect_with_old` 高 | 罕见 | **升高**（C3/C4 冒充，与合法设备并发在线）|

```text
识别原则（doc 9 §8）：
  善意风暴 → 反馈压力 + 等退避（背压水位 L0~L3 天然是执行层）
  凭证攻击 → 识别 + 摘除（负缓存吸收 unknown、throttle+device_blacklist 收敛爆破、
            tenant_freeze 兜大面积泄露），不与攻击者做退避博弈
```

## 20.7 凭证生命周期 = 根治（平台侧，A5 的釜底抽薪）

热路径的防线只是「让攻击变贵、把伤害限有界」；C3/C4 这类认证成功的攻击**只能靠凭证体系根治**（doc 9 §6.1、doc 5 §4.3）：

```text
1. 每设备唯一高熵 secret（≥128 bit CSPRNG，doc 5 §4.3）：撞对/盗到一个只损失一个，
   禁止批次共享凭证——这是自产设备最大的安全杠杆（doc 9 §6.1）。
2. 只存 SHA-256(secret)（auth.go SHA256Verifier + constant-time）：泄库不直接泄凭证；
   secret 高熵 + 快哈希，离线暴力破解在计算上不可行，故无需 salt/慢哈希（doc 5 §4.3）。
3. 轮换：credential_version 已在认证表（doc 5 §4.1）。C4 重放的压制 = 用即疑 → 轮换：
   生成新 secret → 更新 secret_hash + version++ →（Phase 2）凭证变更事件让缓存尽快失效。
4. 吊销：status 置位 +（Phase 2）主动 kick；缓存 TTL 期间的禁用延迟是已接受边界
   （doc 5 §5.3），高危场景用「短 TTL + kick」压缩窗口。
5. 静态 bearer 的固有短板（C4）：无 nonce/challenge，截获即可重放到轮换为止。
   接受此边界的前提是「截获面已由 doc 9 §5.2/§6.4 补偿控制收口」（LB 后端明文抓包
   按凭证密级处理、流量镜像纳入云账号高危审计）。若未来要消除重放窗口，才评估
   challenge-response 或 mTLS（高安全设备已走 mTLS，doc 9 §5.2）。
```

## 20.8 实现约束（红线口径）

延续 doc 9 §5.3 与 doc 5 的约束，针对凭证攻击收口：

```text
1. 负向缓存：
   - 只缓存 not-found；禁缓存 bad-credential / disabled（否则 §20.3.2 自伤 DoS）
   - DB 错误不缓存（瞬时故障不毒化缓存，cache.go:75-77）
   - 抗扫描存储（otter/S3-FIFO），禁朴素 LRU/随机驱逐（否则 unknown 洪泛→热凭证被冲刷 +
     满表 O(n) 驱逐→CPU 耗尽）
   - 有界 MaxEntries，异步驱逐瞬时超额按 3× 预留内存
   - TTL 在包装层判（正负 TTL 不同 + 可测），不用 otter 原生 TTL

2. 认证队列（queue.go）：
   - bounded 队列满即 fail fast → CONNACK ServerUnavailable，禁无限排队
   - 固定 worker pool（不随连接数增长，红线 §7）
   - per-client inflight=1；释放权归 worker（处理完才放），禁调用方超时即释放
   - job 用 submit 时刻 deadline，积压 job 被捞起时 ctx 已过期即快速返回（不白打 DB）
   - MaxConnections > auth queue + presence queue + 活跃数（gnet §8.7.7）

3. 错误凭证 throttle：
   - key = (client_id, IP)，禁止仅用 client_id
   - 只降频不硬拒；命中 throttle 时正确密码仍必须校验放行

4. device_blacklist（爆破封禁）：
   - key = 认证前 L1 clientID→deviceID 映射得到的可信 numeric deviceID
   - 未纳管 clientID 走负缓存，禁进 device_blacklist（防伪造 clientID 撑爆封禁表）
   - 固定短 TTL + per-device jitter，不指数递增；集群共享（doc 19 §19.6）
   - 触发要求「字典分布」前提，非单纯高计数（区别固件 bug 单一错误重试）

5. ip_blacklist：不因「unknown 洪泛 / bad credential 多」自动触发（防 §20.3.2 自伤 +
   CGNAT 连坐，doc 19 §19.3.1）；只由人工或高置信规则（如 mTLS 握手失败率）触发

6. 时序侧信道（auth.go）：not-found 仍对 dummyHash 做等长 constant-time 比较；
   先验 secret 再看 status（错误 secret 一律 0x04，不泄露设备存在/禁用）——禁在重构中移除

7. fail-closed：DB 错误 → ServerUnavailable（不放行未知设备）；未知设备 fail closed（doc 5 §9）

8. 指标只打聚合 counter（按防线/CONNACK 码维度），per-client/per-IP 明细只进审计日志，
   禁高基数 label（红线 §11）
```

## 20.10 验证清单

```text
负向缓存
[ ] 抗扫描回归：预热热凭证 → 海量唯一 unknown client_id 洪泛 → 断言热凭证未被冲刷
    （已有 TestCachingStore_ScanResistanceKeepsHotEntry，本文纳入攻击口径复用）
[ ] 有界回归：unknown flood 下 Size() 收敛，不随洪泛规模线性增长
    （已有 TestCachingStore_BoundedUnderFlood）
[ ] bad-credential 不进负缓存：对已纳管 client_id 发错误密码 N 次，断言该 client_id
    仍走正缓存/DB，正确密码立即可登录（不被负缓存全局拉黑，防 §20.3.2 自伤）
[ ] disabled 不进负缓存：禁用设备的 status 随正缓存记录过期，不单独拉黑 client_id
[ ] DB 错误不缓存：注入 DB 超时，断言不写缓存；DB 恢复后立即正常认证

认证队列（四道闸门）
[ ] 队列满 fail fast：灌满 auth queue → 新 CONNECT 立即 ServerUnavailable，不阻塞
[ ] per-client inflight=1：同一 client_id 并发 CONNECT，断言只有一个在途；DB 卡住时
    不堆叠多个 job；worker 处理完才释放 inflight（-race 0 竞态）
[ ] 超时踢除：慢 DB 下积压 job 被捞起时 ctx 已过期，Authenticate 快速返回不白打 DB
[ ] MaxConnections 边界：MaxConnections < auth+presence queue+活跃 时，正常连接被洪泛挤掉
    → 断言配置校验拦住（gnet §8.7.7）

爆破 / 封禁
[ ] throttle key：对 (client_id, IP) 高频错误降频；换 IP 同 client_id 不共享额度；
    命中 throttle 时正确密码仍放行
[ ] device_blacklist 触发：同一已纳管 device_id 连续 N 次字典型 bad credential → 短封 + 告警；
    单一错误重试（固件 bug 形态）不触发字典判据
[ ] 伪造 clientID 不进封禁表：海量未纳管 clientID 爆破 → 全进负缓存，device_blacklist 不膨胀
[ ] 封禁参数：固定短 TTL + per-device jitter，无指数递增；跨 Broker 共享（复用 doc 19 用例）

时序侧信道
[ ] not-found 与 found-bad-password 的响应时延无显著差异（dummyHash 生效）
[ ] 错误 secret 对「enabled 设备」与「disabled 设备」均返回 0x04（不泄露 status）

识别指纹 / 攻防演练（与 doc 8 互补，恶意口径）
[ ] auth_success_rate 断崖 + unknown 占比升 → 告警区分「攻击」vs「日出风暴」
[ ] 凭证填充演练：10 万条泄露字典分布在 100/1000 IP → device 封禁触发、DB QPS 不超预算、
    合法设备影响可观测且有界（doc 9 §11）
[ ] unknown 洪泛：单 IP / 多 IP 两形态 → 负缓存吸收、DB QPS 有界、缓存表不膨胀、不 ban IP
[ ] CGNAT：单出口 IP 后挂大量真实设备 + 少量爆破流 → 不误封 NAT 池（占比前提，§20.6）

根治
[ ] 每设备唯一凭证：撞库命中一个不影响同租户其它设备（隔离验证）
[ ] 轮换即时性（Phase 2）：轮换后旧 secret 在缓存 TTL/事件失效窗口内失效，kick 压缩窗口
```

## 20.11 一句话总结

```text
凭证攻击云和协议层都接不住——流量合法、协议合规，只能靠「负缓存吸 unknown、
四道闸门保认证资源、(client_id,IP) throttle 防自伤、可信 deviceID 才自动封、
每设备唯一凭证釜底抽薪」这条线。红线是：失败结果只缓存事实型的 unknown，
判决型的 bad-credential/disabled 绝不缓存，自动封禁只落在认证后可信的 deviceID 上。
```

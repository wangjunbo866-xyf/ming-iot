# mqtt-gateway TLS 接入设计

> 本文统一设计 mqtt-gateway 的 TLS 接入层，覆盖两种部署拓扑（broker 终结 TLS / NLB 卸载 TLS）、PROXY protocol 真实 IP 透传、session resumption 握手风暴防护，以及当前实现的缺口与 TODO。
>
> 配套：[实现红线 §13 压测](../7.cloud-mqtt-gateway-implementation-red-lines.md#13-压测验收项)、[网络攻防 §TLS](./9.cloud-mqtt-gateway-network-attack-defense.md)、[EMQX 对比 §模块8 性能优化](../reference/emqx/emqx-design-comparison.md)。

---

## 1. 结论

mqtt-gateway 的 TLS 接入**不硬编码终结位置**（学 EMQX 的设计哲学：两种拓扑都支持，配置决定）。当前实现（`internal/tlsconf`）已支持拓扑 A（broker 终结），但有三处缺口需补：

```text
缺口 1（bug，P0）：tlsconf.go 的 SessionTicketsDisabled: true 禁用了 session resumption，
                   与"防握手风暴"目标冲突。需改为 false。
缺口 2（缺，P0）：无 PROXY protocol 支持。拓扑 B（NLB 卸载 TLS）下拿不到设备真实 IP。
                   需引入 go-proxyproto + config 开关。
缺口 3（缺，P2）：无 mTLS（双向认证）。下阶段开发计划，本文仅预留设计位置。
```

阿里云 NLB 约束：**TCPSSL 监听的 PROXY protocol v2 不支持传递 SSL TLV（pp2_ssl_cn）**，因此 mTLS 不能走"NLB 卸载 + PROXY protocol 传证书"路径——mTLS 必须 mqtt-gateway 自己终结 TLS（拓扑 A）。

---

## 2. 两种 TLS 拓扑

### 2.1 拓扑 A：NLB TCP 透传，mqtt-gateway 终结 TLS

```text
设备 ──TLS(8883)──> 阿里云NLB(TCP监听,透传) ──TLS──> mqtt-gateway(终结TLS)
```

| 维度 | 说明 |
|---|---|
| NLB 监听器 | TCP 监听（前端 8883 / 后端 8883），不解 TLS |
| 真实 IP | TCP 监听 + 客户端地址保持 → `conn.RemoteAddr()` 直接是设备真实 IP |
| TLS 策略 | mqtt-gateway 完全控制（ECDSA / TLS1.3 / session ticket / cipher） |
| 握手风暴防护 | mqtt-gateway 侧 session resumption（**缺口 1 需修**） |
| 握手 CPU | mqtt-gateway 承受（百万 PUBLISH 稳态加密） |
| 证书管理 | mqtt-gateway 侧（滚动重启更新） |
| mTLS | ✅ 天然支持（mqtt-gateway 持有 CA，校验客户端证书） |

### 2.2 拓扑 B：NLB TCPSSL 卸载 TLS，mqtt-gateway 收明文

```text
设备 ──TLS(8883)──> 阿里云NLB(TCPSSL监听,卸载TLS) ──明文+PROXY头(1883)──> mqtt-gateway
```

| 维度 | 说明 |
|---|---|
| NLB 监听器 | TCPSSL 监听（前端 8883 卸载 TLS / 后端 1883 明文） |
| 真实 IP | **必须开 Proxy Protocol**（TCPSSL 默认不保留源地址）→ go-proxyproto 解析（**缺口 2 需补**） |
| TLS 策略 | NLB 侧控制，mqtt-gateway 的 tls.Config 不生效（留空） |
| 握手风暴防护 | NLB 侧（mqtt-gateway 侧无 TLS） |
| 握手 CPU | NLB 承受（mqtt-gateway CPU 全用于业务） |
| 证书管理 | NLB 控制台（mqtt-gateway 不动） |
| mTLS | ❌ **不支持**（阿里云 NLB pp2 不传 pp2_ssl_cn，见 §4） |

### 2.3 对照与选型建议

| 维度 | 拓扑 A（broker 终结） | 拓扑 B（NLB 卸载） |
|---|---|---|
| 真实 IP | ✅ 原生（TCP 源地址） | ⚠️ 需 PROXY protocol |
| TLS 策略控制 | ✅ broker 完全控制 | ❌ NLB 侧 |
| 握手 CPU | broker 承受 | NLB 承受（broker 减负） |
| 证书更新 | broker 滚动重启 | NLB 控制台热更新 |
| mTLS | ✅ 支持 | ❌ 不支持（阿里云约束） |
| 复杂度 | 低（原生 TLS） | 中（PROXY protocol 依赖） |
| 红线 §13 原设计 | ✅ 对齐 | 需调整（TLS 责任上移） |

**选型建议**：

- **如果 mTLS 是近期需求** → 选拓扑 A（broker 终结）。mTLS 必须 broker 持有 CA 校验客户端证书，NLB 卸载后做不到（阿里云约束）。
- **如果近期不做 mTLS 且 TLS CPU 是显著瓶颈** → 可选拓扑 B（NLB 卸载），省 broker CPU，但要接受 PROXY protocol 依赖 + 证书管理上移。
- **默认推荐拓扑 A**——与红线 §13 原设计对齐，mTLS 路径畅通，复杂度最低。

## 3. PROXY protocol 真实 IP 透传（拓扑 B 必需）

### 3.1 为什么需要

阿里云 NLB 的 TCPSSL 监听（TLS 卸载）**默认不保留客户端源地址**——后端看到的源 IP 是 NLB 内网 IP。这会让以下能力失效：

- 认证 Review 的 `(client_id, source_ip)` throttle（防暴破）——源 IP 全是 NLB IP
- banned 黑名单的 peerhost 维度
- 安全审计日志的真实源 IP

### 3.2 方案：PROXY protocol v2 + go-proxyproto

阿里云 NLB 支持 PROXY protocol v2（TCPSSL 监听可开启）。开启后 NLB 在 TCP 握手后将客户端真实 IP/端口附加到数据流头部。后端需解析这个头。

**Go 实现方案**（学 EMQX 的 ranch_proxy_header，Go 对应 `github.com/pires/go-proxyproto`）：

```go
// main.go：用 proxyproto.Listener 包装 net.Listener
import proxyproto "github.com/pires/go-proxyproto"

ln, _ := net.Listen("tcp", addr)
if cfg.Server.ProxyProtocol {
    ln = &proxyproto.Listener{Listener: ln}
}
// 之后 srv.Serve(ln) 不变，Accept 返回的 conn.RemoteAddr() = 设备真实 IP
```

**配置**：

```yaml
server:
  proxyProtocol: false   # 拓扑 A 不开（原生有真实 IP）；拓扑 B 开
```

### 3.3 注意事项

- **双向匹配**：NLB 监听开了 PROXY protocol，mqtt-gateway 必须开 proxyProtocol 解析，否则所有连接失败（前 N 字节被当 MQTT 解析报错）。
- **畸形输入防护**：红线 §13 要求"PROXY 畸形输入验证通过"。go-proxyproto 库有 `ReadHeader` 超时 + 校验，需配置合理的 `proxy_protocol_timeout`（EMQX 默认 3s）。
- **性能**：PROXY protocol 解析在 accept 热路径（红线 §13 提及），但只解析一次（连接建立时），不在每条消息上，开销可接受。

## 4. mTLS（下阶段，预留设计）

### 4.1 阿里云 NLB 的 mTLS 约束

阿里云 NLB TCPSSL 监听的 PROXY protocol v2 **不支持传递 SSL TLV**（`pp2_ssl_cn` 等证书字段）。这意味着：

```text
拓扑 B（NLB 卸载 TLS）下：
  NLB 终结 TLS → 拿到客户端证书 → 但无法通过 PROXY protocol 传给 mqtt-gateway
  → mqtt-gateway 拿不到客户端证书 → 无法做 mTLS 认证

结论：mTLS 必须 mqtt-gateway 自己终结 TLS（拓扑 A）。
```

对比 EMQX：EMQX 能从 PROXY protocol v2 的 TLV 提取 `pp2_ssl_cn`（`emqx_channel.erl:373`），但那要求前端 LB/代理支持传递 pp2 SSL TLV。阿里云 NLB 不支持，所以这条路径对 mqtt-gateway 不通。

### 4.2 mTLS 设计预留（拓扑 A 下）

```text
设备 ──mTLS──> NLB(TCP透传) ──mTLS──> mqtt-gateway(终结TLS + 校验客户端证书)

tlsconf.Config 扩展：
  ClientAuth:        tls.RequireAndVerifyClientCert
  ClientCAs:         *x509.CertPool（设备 CA 证书池）
  // 认证时从 TLS 连接取客户端证书 CN/SN 作为设备身份辅助校验
```

mTLS 下阶段开发，本文只预留 `tlsconf.Config` 的扩展位置和拓扑约束（必须拓扑 A）。

## 5. Session Resumption（握手风暴防护）

### 5.1 问题

百万设备日出窗口集中 CONNECT，TLS 握手（ECDSA P-256 签名验证 ~1ms CPU）是 CPU 峰值的主要来源。session resumption 让已握过手的设备用缓存的 session 恢复连接（1-RTT 甚至 0-RTT），省掉完整握手的非对称运算。

### 5.2 当前 bug（缺口 1）

`internal/tlsconf/tlsconf.go:37`：

```go
SessionTicketsDisabled: true,  // 注释写"用 TLS1.3 无状态 resumption"
```

**这是错的**。TLS 1.3 的 session resumption **依赖 session ticket**——Go 的 `crypto/tls` 在 TLS 1.3 下通过 NewSessionTicket 握手后下发 ticket 实现复用。`SessionTicketsDisabled: true` 会同时禁掉 TLS 1.3 的 ticket-based resumption。原注释把"不维护服务端有状态 session cache"误当成了"启用无状态 resumption"。

### 5.3 修正

```go
// tlsconf.go 修正
return &tls.Config{
    Certificates:           []tls.Certificate{cert},
    MinVersion:             tls.VersionTLS13,
    SessionTicketsDisabled: false,   // ← 修正：启用 ticket-based resumption（Go 自动管理 ticket key ring，无需服务端 session cache）
    NextProtos:             []string{"mqtt"},
}, nil
```

`SessionTicketsDisabled: false`（Go 零值也是 false，显式写出来表意）让 Go 自动管理 ticket key ring——这是**无状态的**（ticket 加密 key 周期轮转，不维护 per-session 服务端状态），正是"防握手风暴"需要的。

### 5.4 拓扑差异

| 拓扑 | session resumption 配置位置 |
|---|---|
| A（broker 终结） | mqtt-gateway 侧（tlsconf.go，本节修正） |
| B（NLB 卸载） | 阿里云 NLB 控制台（mqtt-gateway 侧无 TLS） |

## 6. ECDSA 强制

红线 §13 和 tlsconf 注释都说"建议 ECDSA 证书"，但当前代码**不强制**——如果部署方给了 RSA 证书，tlsconf 照单全收，握手 CPU 比 ECDSA 高一个量级。

### 6.1 修正

在 `tlsconf.New` 里加载证书后校验公钥类型：

```go
cert, err := tls.LoadX509KeyPair(cfg.CertFile, cfg.KeyFile)
// ...
if !isECDSA(cert) {
    return nil, fmt.Errorf("tlsconf: certificate must be ECDSA (got %s), 红线 §13", keyType(cert))
}
```

ECDSA P-256 签名验证 ~1ms，RSA-2048 ~5ms——百万握手下差 5 倍 CPU。强制 ECDSA 是握手风暴防护的必要项。

拓扑 B（NLB 卸载）下此项不适用（证书在 NLB 侧）。

## 7. ECDSA 校验与实现

```go
// tlsconf.go
func isECDSA(cert tls.Certificate) bool {
    if cert.Leaf == nil {
        // LoadX509KeyPair 不填充 Leaf，需手动解析
        parsed, err := x509.ParseCertificate(cert.Certificate[0])
        if err != nil {
            return false
        }
        cert.Leaf = parsed
    }
    _, ok := cert.Leaf.PublicKey.(*ecdsa.PublicKey)
    return ok
}
```

测试覆盖：`TestNew_RejectsNonECDSA`（用 RSA 自签证书 → 期望 error）。

### 8.3 T3 PROXY protocol 实现细节

```go
// config.go Server 段新增
type Server struct {
    // ...
    ProxyProtocol bool `yaml:"proxyProtocol"` // 拓扑B(NLB卸载TLS)时开启，解析真实客户端IP
}

// main.go run() listener 构造
ln, err := net.Listen("tcp", cfg.Server.Addr)
if err != nil { ... }
if cfg.Server.ProxyProtocol {
    ln = &proxyproto.Listener{
        Listener: ln,
        ReadHeaderTimeout: 3 * time.Second,  // PROXY 头解析超时（EMQX 默认 3s）
    }
}
// srv.Serve(ln) 不变
```

**注意**：server.go 当前在 `New()` 内部 `net.Listen`。引入 PROXY protocol 后，要么把 listener 构造上移到 main.go（传入 server.New），要么在 server.New 内根据 cfg 开关包装。前者更清晰（listener 生命周期由 main 管），但改动 server.New 签名。

## 9. 配置示例

### 9.1 拓扑 A（broker 终结 TLS，默认推荐）

```yaml
server:
  addr: "0.0.0.0:8883"
  tls:
    certFile: "${GATEWAY_TLS_CERT}"
    keyFile: "${GATEWAY_TLS_KEY}"
  # proxyProtocol: false   # 不需要，TCP 监听原生有真实 IP
```

### 9.2 拓扑 B（NLB 卸载 TLS）

```yaml
server:
  addr: "0.0.0.0:1883"      # 收明文（NLB 已卸载 TLS）
  # tls:                    # 留空，NLB 侧终结 TLS
  proxyProtocol: true        # 必须开，否则拿不到设备真实 IP
```

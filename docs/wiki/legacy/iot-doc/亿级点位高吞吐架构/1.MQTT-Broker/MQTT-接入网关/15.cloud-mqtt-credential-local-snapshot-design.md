# 云端 MQTT 接入 CONNECT 凭证本地快照存储设计

> 本文承接 [CONNECT 认证设计](./5.cloud-mqtt-connect-auth-design.md)，把其 §11 Phase 3 的「Broker 本地 credential snapshot」从远期演进提前为**首选落地形态**：在 cell 分片前提下，每个 Broker 节点持有本 cell **全量凭证的进程内只读副本**，由 **log-compacted Kafka changelog** 实时喂新，CONNECT 认证退化为**纯本地查找 + 本地 secret 校验**，热路径不再有 Redis/DB 跳。
>
> 设计依据与约束：
> - GC 成本：[Go GC mark 耗时模型](./reference/go-gc-mark-cost-model.md)（5M 条凭证必须 noscan，否则 mark 爆）
> - 红线：[实现红线 §2 pointer-poor / §4 bounded / goroutine 红线](./7.cloud-mqtt-gateway-implementation-red-lines.md)
> - 对标：[CONNECT 认证设计 Review（对标 EMQX）](./reference/emqx/connect-auth-design-review.md)（EMQX built-in-database 模式 = 每节点全量 mria 副本；本文是其解耦、可突破 RAM 上限的等价物）
> - 关联：[架构设计](./1.cloud-mqtt-gateway-architecture.md) · [Presence 注册表](./2.cloud-mqtt-presence-registry-design.md) · [raw log / Kafka](./3.cloud-mqtt-gateway-raw-log-design.md) · [容量规划](./11.cloud-mqtt-gateway-capacity-planning.md)

## 1. 结论

在 **cell 分片**（单 cell 凭证 ≤ ~5M）前提下，CONNECT 凭证的最佳存储形态是：

```text
每个 Broker 节点 = 本 cell 全量凭证的进程内 noscan 只读副本（全量本地快照）
喂新           = log-compacted Kafka changelog（CDC from PG）
冷启动         = 对象存储 cell 级快照文件 seed + 重放 changelog 增量
CONNECT 认证    = 纯本地查找 + 本地 constant-time secret 校验（零网络跳）
```

它一次性消解了 [认证设计](./5.cloud-mqtt-connect-auth-design.md) L1+L2+PG 穿透模型的多处难题：

```text
日出冷启动打爆 DB        → 消失（热路径无 DB，λ 多大都是本地内存查）
无粘性稀释 L1 正向命中    → 消失（每节点全量，落哪个节点都命中）
L2 给 Redis 加 ≈λ 负载   → 消失（auth 不碰 Redis，Redis 只留给 Presence）
禁用/轮换延迟 5~30min     → 反转为亚秒（changelog 事件驱动失效，非 TTL 过期）
负向洪泛 / unknown 风暴   → 本地判负，零 DB
```

核心原则：

```text
1. 5M 条凭证必须 noscan（零指针），否则 GC mark 阶段爆（红线 §2 + GC 模型）。
2. correctness 来自 changelog 事件，不来自 TTL 过期；TTL 不再是失效手段。
3. 全量本地快照的前提是 cell 内凭证装得下单节点；装不下的 cell 退回 L2 共享缓存。
4. 本地 store / Kafka / PG 任一不可用时，按 bounded auth queue 限流 + 设备退避降级，
   绝不让 DB 直面 λ（红线 §4）。
5. Presence 仍强依赖 Redis（红线 §6）——本设计只改 auth，不动 Presence。
```

本设计是 [认证设计](./5.cloud-mqtt-connect-auth-design.md) 的**演进**而非推翻：L1（otter）退化为可选的进程内热路径微优化，L2（共享 Redis 认证缓存）仅在「单 cell 凭证 > 节点内存」时才需要。

## 2. 目标与非目标

### 2.1 目标

```text
CONNECT 认证热路径零网络跳（不查 DB、不查 Redis）。
日出 / 重连风暴下 DB 与 Redis 认证负载恒为 0。
凭证禁用 / 轮换亚秒级在全 cell 节点生效。
5M 条凭证常驻内存而 GC mark 成本可忽略（noscan）。
节点冷启动 / 重启秒级恢复全量快照，不全表扫 PG。
本地 store / Kafka / PG 故障有明确降级语义，不放大为雪崩。
```

### 2.2 非目标

```text
不在单 cell 内承载 > 节点内存容量的凭证（那是 L2 共享缓存的职责，§3.2）。
不改 Presence 设计（仍 Redis CAS + fencing，见 doc #2）。
不在本地 store 落持久会话 / 消息（红线 §10：一阶段不做）。
不在 CONNECT 热路径做慢哈希（沿用认证设计 §4.3：SHA-256 + constant-time）。
不依赖 Kafka changelog 做认证「判决」——它只同步「凭证记录」，判决仍在本地。
```

## 3. 适用前提：cell 分片

### 3.1 为什么必须先分 cell

单集群连接数受**共享协调面吞吐 + 故障爆炸半径**约束，通用 broker 实践多在 100 万 ~ 1000 万/集群，超过即分片联邦。全量本地快照额外要求**单 cell 凭证装得下单节点内存**：

```text
单 cell 凭证数 ≤ ~5M  → 每节点全量快照 ~600MB（§7），可行，本文方案成立。
单 cell 凭证数 > 节点内存  → 全量快照不可行，退回 L2 共享缓存（§3.2）。
```

全 fleet（所有租户合计）若达数千万级，**必须先按 cell 切分**，使单 cell ≤ ~5M，本文方案才在每个 cell 内成立。

> **状态（已变更）**：连接凭证已决定采用 **本地 L1 + 堆外本地 L2 缓存（不用 Redis，miss 回 PG）**，见 [#5 §5.7](./5.cloud-mqtt-connect-auth-design.md)。它是**有界缓存、不持全量**，因此**凭证不再是 cell 容量的约束项**——上面的「≤5M」只属于本文这种「每节点全量快照」形态，而该形态**当前未采用**（保留为备选）。即：cell 是否切、切多大，由【爆炸半径 / 地理 / Redis 集群规模(~100M+)】决定，**与凭证无关**。

### 3.2 cell 分片规则（shared-nothing）

```text
分片键（二选一）：
  - 地理 / 时区：光伏设备天然分布；顺带把「全网同步日出」打散为各时区错峰，
    单 cell 的 λ 自动降一个量级。
  - device-id 一致性哈希：设备固件配置接入域名映射到 cell，无需 broker 间粘性。

cell 边界：每 cell 独立 Broker 池 + 独立 Redis(Presence) + 独立 Kafka topic。
          cell 间零共享，故障互不传染。
```

> 若一个 cell 暂时放不下全量（5M~50M 区间），可在该 cell 内**保留 L2 共享缓存**（认证设计 §5.6）作为过渡，本文 §13 给出共存策略。

## 4. 总体架构

```text
                  ┌─────────────────────────────────────────┐
                  │  device_credential (PG，权威写库)         │
                  └───────────────┬─────────────────────────┘
                                  │ CDC（逻辑复制 / Debezium）
                                  │ 或应用层在凭证变更时双写
                                  ▼
              ┌───────────────────────────────────────────────┐
              │  Kafka topic: cred-changelog.<cell>            │
              │  log-compacted，key = client_id                │
              │  value = CredRecord | tombstone                │
              └───────┬───────────────────────────┬───────────┘
   每节点独立 group.id │ (广播，消费全部分区)        │ (可选) L2 writer 单写者
   消费全量 → 应用本地  ▼                           ▼
        ┌──────────────────────┐         ┌──────────────────────┐
        │ Broker A 本地快照      │  ...    │  Redis L2（仅 §3.2    │
        │ (noscan store, §5)    │         │  过渡 cell 才需要)     │
        └──────────────────────┘         └──────────────────────┘

CONNECT 热路径（命中本地快照即终结，无网络跳）：
  TCP accept → 读 CONNECT → 基础校验 → 本地快照 Lookup(client_id)
    → 命中: constant-time 校验 secret + 查 status → 认证判决
    → 未命中: 见 §6.4（unknown 判负 / 新纳管 race 兜底）
    → 认证成功 → Redis 写 Presence（红线 #6）→ CONNACK
```

要点：
- **CDC 优先于应用层双写**：CDC 保证「PG 提交了 = changelog 必有」，无双写漏发风险；应用层双写需自己保证原子性（outbox 模式）。
- **每节点是自己独立的 consumer group**（独立 `group.id`，消费全部分区）——这是**广播 fan-out**，不是负载均衡消费组。凭证变更低频（§6.2），每节点读全量无压力。
- **changelog 只搬运凭证记录，不搬运判决**：节点拿到记录后，仍按 [认证设计 §3](./5.cloud-mqtt-connect-auth-design.md) 本地校验 secret / status，命中不等于放行。

## 5. 本地存储引擎选型

### 5.1 第一约束：必须 noscan

[GC 模型](./reference/go-gc-mark-cost-model.md) 已定性：`map` = 大量内部指针，`string` / `*T` 各 1 个扫描单元。5M 条凭证若用 `map[string]*Record`，扫描单元达 1500 万~2500 万，按 ~100ns/指针，每轮 mark 直接爆，违反红线 §2。

**因此 5M 条数据集必须是 noscan（零指针）**——这是选型的硬约束，不是优化偏好。

### 5.2 数据模型（权威记录）

```go
// 全 noscan：无 string、无指针、无 slice 元素指针
type CredRecord struct {
    SecretHash  [32]byte // SHA-256(device_secret)，定长数组，noscan
    TenantID    uint32   // interned tenant id
    DeviceID    uint64   // numeric device id
    CredVersion uint32   // 单调递增，用于 changelog 去重 / fencing
    ACLVersion  uint32
    Status      uint8    // 0=disabled / 1=enabled / ...
    _           [3]byte  // 对齐
}
```

`client_id` 不进 `CredRecord`（避免 string 指针），单独列存原文用于碰撞校验（§5.3）。

### 5.3 三档实现（按工程量递增，收益递增）

#### Tier 3｜MVP：`map[uint64]CredRecord`

```go
var table map[uint64]CredRecord // key = xxhash64(client_id)
```

```text
key/value 均 noscan → bucket 数组 noscan，GC 只扫 overflow bucket（几万级，几 ms）。
比 map[string]*Record 好几个数量级，足够 Phase 1。
```

- **必须校验 client_id 防 hash 碰撞**（碰撞 = 冒充他人认证，是安全问题，不能赌概率）：value 旁存定长/偏移 client_id 原文，命中后逐字节比对；不等则判未命中。
- 写入（changelog apply）：分片 RWMutex 或整表 atomic swap。
- 冷启动：重放 compacted Kafka（5M ~ 秒~十几秒级）。

#### Tier 2｜推荐：列式 SoA + 开放寻址索引（in-heap，近零扫描）

```go
type Store struct {
    // 索引：开放寻址，全 noscan
    hashes []uint64 // xxhash64(client_id)，~7M 槽（load factor ~0.7）
    slots  []uint32 // → 数据行号

    // 数据列（struct-of-arrays），全 noscan
    secretHash []byte   // 行 i = secretHash[i*32 : i*32+32]
    cidBytes   []byte   // client_id 原文（防碰撞校验）
    cidOff     []uint32 // client_id 偏移
    tenantID   []uint32
    deviceID   []uint64
    status     []uint8
    credVer    []uint32
    aclVer     []uint32
}
```

```text
每个 slice 仅 1 个 header 指针，底层数组 noscan →
整个 5M 数据集 GC 扫描单元 ≈ 10 个，与条数无关。最贴红线 §2 的形态。
纯 Go，不用 unsafe/mmap，比 Tier 3 多一个开放寻址表。
```

#### Tier 1｜终局：mmap 不可变快照（堆外，零 GC + 秒级冷启动）

```text
把 Tier 2 的列序列化成文件，启动 syscall.Mmap 映射成 []byte，unsafe 切出各列：
  - mmap 内存不在 Go 堆 → GC 永不触碰，扫描单元 = 0，且不占 heap 预算。
  - 冷启动 = mmap 文件（瞬时，页按需 fault-in），不重放 5M Kafka。
  - 代价：unsafe + mmap，工程量最大。
```

### 5.4 并发模型（三档通用）

```text
base    : 不可变，atomic.Pointer[Store] 持有；热路径读无锁。
overlay : 自上次重建以来的 changelog 增量，小 noscan map + RWMutex（写极少）。
查找    : 先查 overlay（小），再查 base（大、无锁）。
重建    : 周期 / 增量达阈值时，把 overlay 折进 base 生成新不可变快照，atomic swap，
          清空 overlay。重建在固定 worker（不随连接数增长，goroutine 红线）。
```

### 5.5 选型路线与排除项

```text
路线：Tier 3 起步（先跑通功能 + 验证失效语义）
   → 收敛到 Tier 2（满足 pointer-poor，压测看 gctrace mark 曲线平）
   → 仅当冷启动重放时间 / heap 预算成为实测瓶颈，再上 Tier 1 mmap。

排除：
  ✗ map[string]*Record / 任何含指针大 map —— GC 雪崩（GC 模型已判死刑）。
  ✗ badger / pebble（LSM）—— 写优化 + 后台 compaction goroutine 撞 goroutine 红线，
    read-mostly 且能装进 RAM 时杀鸡用牛刀。
  ✗ SQLite —— 单 key 查找过 SQL 层，无必要。
  ⚠ bbolt —— 若就是要落盘 + 堆外 + 少写代码，是唯一像样现成选项（mmap B+tree、
    无 compaction goroutine、读优化）；但单 key 查找延迟与简洁度不如 Tier 1 自定义 mmap。
```

## 6. Changelog topic 与节点消费

### 6.1 topic 设计

```text
topic         : cred-changelog.<cell>
cleanup.policy: compact（log compaction，每 key 保留最新值）
key           : client_id（与查询键一致）
value         : protobuf/json 编码的 CredRecord；删除用 tombstone（value=null）
分区          : 按 client_id hash 分区；分区数决定重放并行度
```

语义区分（对齐认证设计 §5.2 / §9）：

```text
纳管 / 轮换 : value = 新 CredRecord（status=enabled，CredVersion 递增）→ 本地 upsert
禁用       : value = CredRecord（status=disabled）→ 本地 upsert，认证返回 0x05
注销 / 删除 : value = null（tombstone）→ 本地 delete，认证返回 0x04（变 unknown）
```

### 6.2 changelog 流量（低频，可忽略）

```text
设备凭证变更是低频事件：日变更量千~万级。
即便全量 5M 一周轮换一遍 ≈ 1.6/s。对 Kafka 与节点应用均可忽略。
```

### 6.3 应用幂等与有序

```text
1. 单调 CredVersion 去重：apply 时若 incoming.CredVersion <= 本地.CredVersion 则忽略，
   防乱序 / 重放把旧值盖新值。
2. 同 client_id 落同分区 → 分区内有序，配合 CredVersion 双保险。
3. tombstone 也带删除时刻的 CredVersion（或单调删除标记），防「删除被旧 upsert 复活」。
4. apply 必须幂等：重启后从上次 commit offset 续读，重复 apply 结果一致。
```

### 6.4 未命中（local miss）语义

全量快照下，已纳管设备恒在本地；miss 只有两种来源：

```text
A. 真 unknown client_id（攻击 / 错误固件）：
   本地直接判负 → 0x04，零 DB、零 Redis。天然吸收 unknown 洪泛（认证设计 §5.2 的负向缓存职责被本地全量覆盖）。
B. 刚纳管、changelog 尚未传播的 race 窗口（亚秒级）：
   可选「bounded PG 兜底查询」一次（受 §10 auth queue 预算保护）；
   或直接 0x03/0x04 让设备退避重连（亚秒后 changelog 到达即成功）。
   首版建议 B 直接退避，不开 PG 兜底，保持热路径纯本地；race 窗口由设备退避吸收。
```

## 7. 冷启动、重建与新节点上线

### 7.1 启动序列（避免全表扫 PG / 惊群）

```text
1. 拉 cell 级快照文件（对象存储，§7.2）→ mmap / 反序列化为初始 base。
2. 从快照记录的 Kafka offset 起重放 changelog 增量到 base。
3. 追平到 topic 末端（lag≈0）后，节点标记 ready，才开始 accept 连接（§10 未 ready 拒连）。
```

```text
新节点不从 offset 0 重放全量 changelog（compacted 后仍可能很大），
也不全表扫 PG（N 节点同启会惊群打爆只读库）——靠对象存储共享快照 seed。
```

### 7.2 cell 级快照文件

```text
产出：一个后台 job（或 leader 节点）周期把全量凭证 dump 成快照文件，
      连同截止 Kafka offset，上传对象存储（cell 维度一份）。
作用：① 新节点 / 重启秒级 seed；② changelog compaction 的基线；③ 灾备。
格式：与 Tier 1 mmap 布局一致最佳（落盘即可直接 mmap，零反序列化）。
```

### 7.3 就绪门槛

```text
节点未追平 changelog（lag 高于阈值）→ 不进入 accept，对 LB 表现为未就绪。
防止「快照不全 / 滞后」时放行错误认证（如已禁用设备因本地未更新被放行）。
```

## 8. 一致性与即时失效

```text
失效模型：事件驱动（changelog），非 TTL 过期。
传播延迟：禁用 / 轮换 = 一条 changelog 事件 → 各节点 overlay 即时 apply → 亚秒生效。
对比认证设计 §5.3：从「TTL 内（5~30min）仍可登录」改善为亚秒，且 review 缺口3
        「凭证轮换无即时失效手段」直接解决（轮换 = upsert 新 hash，无锁定）。
紧急吊销：发一条 tombstone / disabled upsert 即可，无需「多节点清缓存 API」。
fencing ：CredVersion 单调，旧版本事件被忽略（§6.3），杜绝「轮换被旧值复活」。
```

> 注意：即时失效依赖节点**已就绪且 changelog lag≈0**（§7.3）。lag 高时按未就绪处理，宁可拒连不可放行陈旧凭证。

## 9. 故障与降级语义

| 故障 | 节点行为 | 结果 |
|---|---|---|
| 本地快照命中且有效 | 本地校验放行 | 后续写 Presence |
| 本地未命中（真 unknown） | 返回 0x04 | 零 DB / 零 Redis |
| 本地未命中（新纳管 race） | 首版：0x03/0x04 让退避（不开 PG 兜底） | 亚秒后 changelog 到达即成功 |
| changelog 短暂滞后（lag 小） | 仍服务（接受亚秒陈旧） | 禁用/轮换延迟到 lag 收敛 |
| changelog 中断 / lag 持续高 | 超阈值 → 节点标记未就绪，停止 accept | 防放行陈旧凭证；LB 摘除 |
| 快照文件 / 对象存储不可用 | 退回从 Kafka offset 0 重放（慢）或拒绝就绪 | 启动变慢，不放行错误认证 |
| PG 不可用 | **认证不受影响**（快照是本地权威，热路径不碰 PG） | 仅新纳管暂停传播；存量设备照常 |
| Kafka 不可用 | 存量快照继续服务（只读），变更暂停传播 | 接受变更延迟；恢复后续读追平 |
| 本地 store 未就绪（启动中） | 拒绝 accept（§7.3） | 设备退避重连 |
| 内存 / heap 逼近水位 | 降级开关：拒新连 + 告警（红线上线门槛） | 保护节点不 OOM |

降级总原则（红线 §4）：

```text
任何「本地不可用 / 不确定」状态，一律拒连 + 设备退避（fail closed / fail fast），
绝不回退到「DB 直面 λ」。bounded auth queue（§10）是 race 兜底与限流的唯一闸门。
```

## 10. 与负载剪切的衔接

```text
本地查找命中是 O(1) 内存访问，本身不需要队列保护。
仅 §6.4-B 的可选 PG 兜底（若启用）走 bounded auth queue：
  - 复用认证设计 §6 的 max_auth_inflight / max_auth_queue / auth_timeout。
  - 兜底 QPS 钳在 §6.2 的 per-broker DB miss 预算内，超出 → 0x03 + 退避。
首版不开 PG 兜底时，CONNECT 热路径无 DB 依赖，队列只用于 accept/TLS 层限流。
```

## 11. 安全

```text
1. secret_hash 全量驻留每节点 → 爆炸半径扩大：单节点被攻陷可读全 cell hash。
   缓解：secret_hash 是 SHA-256(高熵≥128bit 机器凭证)，离线暴破不可行（认证设计 §4.3）；
        快照文件落受限权限 / 加密卷；mmap 区不可写、不导出。
2. 绝不记录明文 secret / secret_hash 到日志、指标、快照以外的任何地方（认证设计 §4.3）。
3. hash key 必须校验 client_id 原文防碰撞冒充（§5.3）。
4. changelog 通道鉴权 + 传输加密（凭证记录在途）；CDC 账号最小权限只读 device_credential。
5. 快照文件分发链路（对象存储）鉴权；下载校验完整性（防投毒伪造凭证）。
```

## 12. 容量与 GC 成本

### 12.1 单节点内存（5M 凭证）

```text
secret_hash 32B×5M           = 160MB
client_id  ~30B×5M           = 150MB（+ 偏移 uint32×5M = 20MB）
tenant/device/status/ver 各列 ≈ 105MB
开放寻址索引（hashes+slots）   ≈ 84MB
─────────────────────────────────────
合计 ≈ 600MB / 节点
```

```text
Tier 1（mmap）：~600MB 在堆外，不占 heap、零 GC 扫描。
Tier 2（in-heap）：~600MB 在堆，但 noscan，GC 扫描单元 ≈ 10。
Tier 3（map）：~1~1.5GB 在堆，GC 仅扫 overflow bucket（几 ms）。
对比 50 万连接 ~10GB 堆（GC 模型 §4），凭证全集内存可忽略。
```

### 12.2 GC mark 增量（按 GC 模型估算）

```text
T_mark 增量 ≈ 新增扫描指针 × ~100ns / W_workers × F
Tier 1/2：新增扫描指针 ≈ 0（堆外 / noscan）→ T_mark 增量 ≈ 0。
Tier 3  ：新增 ≈ overflow bucket 指针（万级）→ T_mark 增量 ms 级。
验收：GODEBUG=gctrace=1 压测，确认引入快照后 mark 曲线无显著抬升（§15）。
```

## 13. 与现有 L1+L2 设计的关系与迁移

### 13.0 凭证存储的两种方式 / 三个位置

凭证存储对应 EMQX 的两种认证后端；「本地化」按彻底程度有三个递进位置：

| 形态 | 文档 | 对应 EMQX | L2 在哪 | PG 角色 |
|---|---|---|---|---|
| L1 + 共享 Redis L2 + PG 穿透 | [#5](./5.cloud-mqtt-connect-auth-design.md) | 外部 PG 模式（模式B）+ EMQX 没有的共享 L2 | 共享 Redis | 热路径兜底 |
| L1 + **本地 L2** + PG 穿透 | [#5 §5.7](./5.cloud-mqtt-connect-auth-design.md) | 介于两者之间的过渡 | 本地存储（changelog 喂新） | 热路径兜底 |
| **完全本地存储**（全量快照） | 本文 #15 | 内建库模式（模式A），mria → Kafka changelog | 无需 L2（本地即全量） | 仅 CDC 源 + 冷启动 |

```text
两条「本地化」路径替代的都只是「认证侧的凭证缓存 / 查询」（L2 / PG）。
Presence 的 Redis（CAS + fencing，红线 #6/#8，doc #2）是跨节点协调态，
per-node 本地存储结构上无法承担，三种形态下都必须保留。
```

### 13.1 关系与迁移

```text
关系：本设计是认证设计 §11 Phase 3「本地 snapshot」的提前落地。
  - L1（otter）：退化为可选的进程内热路径微优化（命中本地快照后通常无需）。
  - L2（共享 Redis 认证缓存）：cell 内全量装得下时不再需要（最大化简化）；
    仅「单 cell 凭证 > 节点内存」的过渡 cell 才保留 L2。
  - PG：从认证热路径退到「CDC 源 + 快照基线 + (可选)race 兜底」。
  - Presence：完全不变，仍 Redis CAS + fencing（红线 #6/#8，doc #2）。

灰度迁移：
  1. 先建 changelog（CDC + compacted topic）+ 节点消费，构建本地快照，但仍以
     L1+L2+PG 为认证权威，本地快照只做「影子校验」对账（双读比对，记录差异）。
  2. 影子对账命中率 / 一致性达标后，切换认证权威到本地快照，L2 降级为兜底。
  3. cell 内验证稳定后，关停该 cell 的 L2（认证侧），仅保留 Presence 的 Redis。
```

## 14. 指标

```text
# 本地快照
cred_snapshot_entries              # 本地条目数（应 ≈ cell 全量）
cred_snapshot_ready                # 是否就绪（lag≈0 且 seed 完成）
cred_snapshot_rebuild_seconds      # 重建（折 overlay）耗时
cred_snapshot_overlay_size         # overlay 增量条目数
cred_snapshot_mem_bytes            # 快照内存占用（堆内/堆外分别）

# changelog 消费
cred_changelog_lag                 # 消费滞后（关键：决定失效及时性与就绪）
cred_changelog_apply_total{op}     # upsert / delete / ignored(版本旧)
cred_changelog_apply_errors

# 冷启动
cred_seed_source{file|kafka}       # seed 来源
cred_seed_seconds                  # seed + 追平耗时

# 认证（承接认证设计 §12，热路径口径变化）
auth_local_hit_total               # 本地命中（应 ≈ 全部 CONNECT）
auth_local_miss_total{unknown|race}
auth_pg_fallback_total             # race 兜底（若启用，应极小）
auth_success / auth_bad_credential / auth_not_authorized
connack_success / connack_server_unavailable

# GC（承接 GC 模型）
go_gc_mark_seconds                 # 引入快照后应无显著抬升
```

告警：

```text
cred_changelog_lag 持续高 → 失效不及时 / 节点应被摘除
cred_snapshot_ready=0 持续 → seed / 追平异常
auth_local_miss_total{race} 突增 → changelog 传播异常 / 纳管风暴
auth_pg_fallback_total 突增 → 本地快照不全或 race 兜底被滥用
go_gc_mark_seconds 抬升 → 快照结构退化为含指针（违反 noscan）
```

## 15. 压测矩阵与上线门槛

承接 [实现红线上线门槛](./7.cloud-mqtt-gateway-implementation-red-lines.md) 与 [压测规划](./8.cloud-mqtt-gateway-load-test-plan.md)。

```text
功能 / 失效：
  - 禁用事件传播延迟 p99（目标亚秒，跨全 cell 节点）。
  - 轮换后旧 secret 立即失败、新 secret 立即成功（无锁定窗口）。
  - tombstone 删除后变 unknown（0x04）；版本旧事件被忽略（不复活）。
  - 新纳管 race：changelog 到达前后认证行为符合 §6.4。

容量 / 性能：
  - 5M 凭证全量加载内存 = §12.1 预算内；GODEBUG=gctrace=1 确认 mark 不抬升。
  - 日出 100 万设备 5min 集中上线（单 cell）：DB QPS = 0、Redis 认证 op/s = 0、
    本地查找 p99 在 SLA 内。
  - bad / unknown flood：本地判负，零 DB / 零 Redis，无 GC 抖动。

冷启动 / 故障：
  - 节点重启：从对象存储快照 seed + 追平 changelog 的总恢复时间。
  - N 节点同启不惊群打 PG（验证走快照而非全表扫库）。
  - Kafka 中断：存量快照继续服务、变更暂停、恢复后追平。
  - changelog lag 高：节点正确转未就绪、被 LB 摘除、不放行陈旧凭证。
  - 对象存储不可用：seed 退化路径可控，不放行错误认证。

上线门槛（任一不满足不上线）：
  - 无上述失效 / 冷启动 / 故障压测，不上线。
  - 无 cred_changelog_lag / snapshot_ready / gc_mark dashboard，不上线。
  - 无「本地 store 未就绪 → 拒连」与「lag 高 → 摘除」降级开关，不上线。
```

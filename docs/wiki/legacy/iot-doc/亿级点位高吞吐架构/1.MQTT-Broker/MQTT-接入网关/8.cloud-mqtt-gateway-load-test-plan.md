# 云端 MQTT Broker 压测规划

> 本文承接 [百万级设备 MQTT 接入层架构设计](./1.cloud-mqtt-gateway-architecture.md)、[云端 MQTT Broker 压力传播与背压控制设计](./6.cloud-mqtt-gateway-pressure-backpressure-design.md) 和 [云端 MQTT Broker 实现红线清单](./7.cloud-mqtt-gateway-implementation-red-lines.md)，定义自研 MQTT Gateway 的压测目标、环境、工具、场景、指标、验收线和报告模板。

---

## 1. 结论

压测目标不是证明 Broker 在某个瞬间能连上 100 万设备，而是证明系统在真实压力和故障下具备以下能力：

```text
1. 连接能稳住。
2. 上行能进入 durable raw log。
3. Kafka / Redpanda 变慢时，Broker 内存不会无界增长。
4. 设备重试不会放大成全局风暴。
5. 认证、Presence、Kafka 任一依赖抖动时，Broker 能 fail fast。
6. 故障恢复不会形成二次冲击。
7. 连接断开后 goroutine / fd / heap 能回落。
```

压测按阶段推进：

```text
Phase 0：压测工具和观测体系准备。
Phase 1：单节点 idle 连接和内存基线。
Phase 2：单节点稳态 PUBLISH。
Phase 3：单节点压力、背压和故障注入。
Phase 4：多节点集群与百万连接。
Phase 5：长稳、恢复风暴和上线前演练。
```

第一阶段建议先证明：

```text
单 Broker 10 万长连接。
payload 3KB。
QoS1 每 5 分钟上报。
Kafka ack 正常和 p99=2s 抖动两种模式。
append_queue_bytes 不持续增长。
RSS、heap、goroutine、fd 稳定。
断连后资源能回落。
```

不要一开始追求百万集群，否则问题会混在一起，很难判断瓶颈来自 Broker、压测客户端、Kafka、Redis、DB、LB、网络还是 OS 参数。

## 2. 压测原则

### 2.1 分层验证

必须分层压测：

```text
单节点 Broker
  -> 多节点 Broker 集群
  -> Broker + Kafka / Redpanda
  -> Broker + Redis Presence
  -> Broker + Auth DB
  -> 完整链路
```

先把单节点模型压清楚，再扩集群。

### 2.2 先基线，后风暴

每一类压测都先跑基线：

```text
idle 连接基线
稳态上报基线
CONNECT 基线
Kafka ack 基线
内存基线
```

再做风暴：

```text
CONNECT 风暴
上报风暴
重试风暴
恢复风暴
依赖故障风暴
```

### 2.3 看曲线，不只看结果

压测不能只看最终是否成功。

必须看：

```text
连接数曲线
吞吐曲线
PUBACK p99 曲线
Kafka ack p99 曲线
append_queue_bytes 曲线
RSS / heap 曲线
goroutine / fd 曲线
reconnect_rate 曲线
错误码曲线
```

### 2.4 失败也要压测

必须主动制造失败：

```text
Kafka ack 变慢。
Kafka 短暂不可用。
Redis Presence 超时。
Auth DB 超时。
Broker 节点重启。
LB 摘除节点。
设备无退避重试。
```

系统在失败时的行为比正常吞吐更重要。

## 3. 被测系统范围

### 3.1 核心链路

```text
Load Generator
  -> 普通设备入口：云 TLS LB 终结单向 TLS
       -> MQTT Gateway
  -> 高安全设备入口：L4 LB 透传 mTLS
       -> MQTT Gateway

MQTT Gateway
  -> Redis Presence
  -> Auth DB / Auth Mock
  -> Kafka / Redpanda raw log
```

### 3.2 可选链路

```text
Command Service
  -> Presence lookup
  -> Broker private channel
  -> Broker local MQTT PUBLISH
```

第一阶段可以先不压下行命令；第二阶段再加入低频下行。

### 3.3 不纳入首轮压测

首轮不重点压：

```text
Modbus Decoder
时序库
OLAP
告警系统
报表系统
业务大表
```

这些组件可以在 raw log 之后独立压测。

## 4. 压测环境规划

### 4.1 环境分层

建议准备三套环境：

| 环境 | 目标 | 规模 |
|---|---|---|
| dev-load | 开发调参 | 1 到 2 台 Broker，1 到 10 万连接 |
| staging-load | 预生产压测 | 3 到 10 台 Broker，10 到 100 万连接 |
| production-drill | 上线前演练 | 接近生产规格，控制窗口执行 |

### 4.2 Broker 节点规格记录

每次压测必须记录：

```text
CPU 型号和核数
内存
网卡带宽
磁盘类型，若本机有日志或 profiling
OS 版本
Go 版本
GOMAXPROCS
GOGC
GOMEMLIMIT
ulimit -n
内核网络参数
Broker 配置版本
Git commit
```

`GOMEMLIMIT` 建议起点：节点内存的 70%~80%，与 `max_append_queue_bytes` 等字节预算联动解释——红线 §14 要求能解释 append queue 最大内存，GOMEMLIMIT 是 RSS 侧的最后闸门，两者必须能在压测报告中互相印证。

### 4.2.1 接入入口与 LB 规格记录

压测环境必须按架构设计 §11.5 的分流拓扑搭建，并记录每个入口的 TLS 终结位置。

每次压测必须记录：

```text
普通设备入口域名 / 端口 / LB 产品与规格。
普通设备入口 TLS 终结位置：云 TLS LB 终结单向 TLS。
普通入口 LB 到 Broker 的后端协议：默认 VPC 明文 TCP（内网 TLS 仅合规驱动，见 doc 9 §5.2）。
普通入口真实源 IP 透传方式：source IP preservation / PROXY protocol / 无。
若使用 PROXY protocol：版本、可信 LB CIDR / 安全组、Broker 解析开关、失败策略。
高安全入口域名 / 端口 / L4 LB 产品与规格。
高安全入口 TLS 终结位置：Broker 终结 mTLS。
LB idle timeout 与 Broker keepalive 判死窗口。
LB 长连接容量、TLS 握手容量、计费模型。
per-IP 限流 / ip_blacklist 是否启用及其源 IP 可信依据。
```

验收口径：

```text
源 IP 未验证可信时，不得启用 per-IP 限流和 ip_blacklist。
PROXY protocol 解析必须通过红线 §6 的有界热路径要求后，才能进入压测主链路。
普通入口压云 TLS LB 的握手容量；高安全入口压 Broker mTLS 握手容量。
```

### 4.3 Kafka / Redpanda 规格记录

必须记录：

```text
broker 节点数
CPU / 内存 / 磁盘 / 网卡
topic
partition count
replication.factor
min.insync.replicas
acks
compression
linger.ms
batch.size
delivery.timeout.ms
retention
```

### 4.4 Redis / DB 规格记录

必须记录：

```text
Redis / Tair / ElastiCache 节点规格
Redis cluster shard 数
auth DB 类型和规格
auth DB 只读副本数
连接池大小
查询超时
cache TTL
```

### 4.5 压测客户端规格

压测客户端机器必须独立规划。

需要记录：

```text
客户端机器数量
每台机器连接数
每台机器源 IP 数
CPU / 内存 / 网卡
ulimit -n
ephemeral port 范围
TLS 是否开启
payload 生成方式
```

百万连接通常需要多台压测客户端机器。不能让客户端先成为瓶颈。

## 5. 压测客户端能力要求

不要只依赖通用 MQTT benchmark 工具。建议实现公司自用的设备模拟器。

```text

DISCONNECT

```

可选支持：

```text
SUBSCRIBE 自己的 command topic
接收下行 PUBLISH
下行 PUBACK
```

### 5.2 设备身份模拟

必须支持：

```text
tenant_id
device_id
client_id
username
password / secret
firmware_version
product
region
```

压测客户端应能从文件或规则生成设备身份：

```text

tenant-a/INV_000000002
...
```

### 5.3 Payload 模拟

必须支持：

```text

binary payload
boot_id
seq
sample_ts
schema_id
payload_crc32
firmware_version
```

payload 可以是随机二进制，也可以是固定模板加 header。

要求：

```text
同一 device_id 的 seq 单调递增。
重连后 boot_id 可配置为保持不变或重置。
重复发送时保持同一 dedupe key。
```

### 5.4 行为模型

必须支持：

```text

按时间窗口上线

带 jitter 的周期上报
同步上报

断线重连

退避 jitter 开关
```

```text
无退避
固定 5s
指数退避无 jitter
指数退避带 jitter
生产推荐退避
```

生产推荐退避：

```text
首次失败：1s ~ 5s 随机
连续失败：5s ~ 30s 随机
持续失败：30s ~ 300s 随机
```

## 7. 验收指标建议

以下是首版建议值，最终应按真实机器规格和业务 SLA 调整。

### 7.1 单节点资源

| 指标 | 建议验收 |
|---|---:|
| 单节点连接数 Phase 1 | 50k |
| 单节点连接数 Phase 2 | 100k |
| 单节点连接数 Phase 3 | 200k |
| Broker RSS | 不超过机器内存 70% |
| append_queue_bytes | 不持续增长，且低于上限 80% |
| goroutine count | 与连接数线性可解释，断连后回落 |
| fd count | 与连接数线性可解释，断连后回落 |
| GC pause p99 | 稳态不出现持续尖峰 |
| GC CPU fraction | 稳态可接受，压测报告中解释 |

### 7.2 延迟

| 指标 | 正常水位建议 |
|---|---:|
| raw_log_ack_latency_p99 | < 100ms，按 Kafka 规格调整 |
| mqtt_puback_latency_p99 | < 200ms ~ 500ms，按业务调整 |
| auth_queue_wait_latency_p99 | < 100ms ~ 500ms |
| presence_write_latency_p99 | < 50ms ~ 200ms |
| connect_to_connack_latency_p99 | < 1s，日出风暴可放宽 |

### 7.3 故障水位

故障场景不要求所有请求成功，但要求：

```text
Broker 不 OOM。
append_queue_bytes 有上限。
RSS 不持续无界增长。
恢复后连接、goroutine、fd、heap 能回落。
QoS1 不提前 ACK。
QoS0 drop 有指标。
Server Unavailable 有指标。
设备重试带 jitter 时流量能逐步恢复。
```

## 9. Phase 1：单节点 Idle 连接压测

### 9.1 目标

验证单 Broker 在大量 idle 长连接下的基础成本：

```text
每连接内存。
每连接 fd。
goroutine 数。
GC 扫描成本。
keepalive 成本。
断连资源回收。
```

### 9.2 场景

| 场景 | 连接数 | 上报 | 持续时间 |
|---|---:|---|---:|
| idle-10k | 10k | 无 | 30min |
| idle-50k | 50k | 无 | 1h |
| idle-100k | 100k | 无 | 2h |
| idle-200k | 200k | 无 | 2h |

每轮都要测：

```text
连接建立阶段。
稳定 idle 阶段。
批量断开阶段。
断开后 10min / 30min 资源回落。
```

### 9.3 验收

```text
RSS 与连接数线性增长，可解释。
heap live 与连接数线性增长，可解释。
goroutine 与连接数线性增长，可解释。
fd 与连接数基本一致，可解释。
断连后 goroutine / fd / heap 回落。
无明显 goroutine leak。
无 session registry leak。
```

输出：

```text
单连接 RSS 成本估算。
单连接 heap 成本估算。
单连接 goroutine 成本估算。
单节点最大建议连接数。
```

## 11.5 协议健壮性验证（对抗输入）

前面所有 Phase 压的都是"行为良好的客户端在高压下"；本节压"恶意或故障设备发什么都不能打穿 Broker"。自研 codec 直面公网，固件 bug 与扫段攻击都会制造畸形流量（架构设计 §2.2 的"设备固件异常"挑战由本节承接）。本节为**上线门槛**（红线 §13/§14），Phase 1 之后任意时间可执行，与负载压测无依赖。

### 11.5.1 Fuzz

```text
Go 原生 fuzz（go test -fuzz）覆盖：
  ReadPacket / remaining length 解析
  CONNECT 解析（client_id / username / password 各种长度与编码）
  PUBLISH 解析（topic / packet_id / payload_len 边界）
语料：合法包种子 + 压测客户端录制流量
验收：无 panic、无 OOM，错误路径全部走断连/拒绝
节奏：CI 短跑（每次提交数十秒）+ 周期长跑（夜间数小时）
```

### 11.5.2 畸形包矩阵（表驱动单测）

```text
谎报 remaining length（如声明 256MB）
QoS=3 / 保留位非零
CONNECT 之前发送 PUBLISH / SUBSCRIBE
同一连接重复 CONNECT
零长 client_id / 超长 client_id / 非法 UTF-8 topic
QoS1 packet_id = 0
payload_len 超过 max_payload_size
启用 PROXY protocol 时：PROXY 头缺失 / 截断 / 超长 / 版本非法 /
  来自非可信来源 / 源 IP 字段非法

验收："先预算后分配"不被任何畸形输入绕过；
     统一断连 + 计数指标，无 fd / 预算泄漏；
     PROXY protocol 失败必须在进入认证和 MQTT 解析前断开。
```

### 11.5.3 慢读饿死

```text
包中途停顿：发送 PUBLISH 前半段后改为 1 byte/min
半开连接：CONNECT 后不发任何字节

验收：read deadline 覆盖"包读到一半"（不只覆盖包与包之间），
     连接在 keepalive 判死窗口内被回收，fd / pending bytes 随之释放。
```

### 11.5.4 验收汇总

```text
fuzz 跑满约定时长无 crash。
畸形包矩阵 100% 通过并入回归套件。
慢读场景 fd / goroutine / pending bytes 全部回落。
以上结果进入上线判定清单（§20）。
```

## 12. Phase 4：Kafka Ack 抖动压测

### 12.1 目标

### 12.2 方法


## 20. 上线判定

满足以下条件后，才能进入生产灰度：

```text
单节点目标连接数通过。
百万集群稳态通过。
CONNECT 风暴通过。
上报风暴通过。
Kafka ack 抖动通过。
Redis / DB 故障通过。
Broker 节点故障通过。
长稳测试通过。
设备退避策略验证通过。
协议健壮性验证通过（§11.5：fuzz / 畸形包矩阵 / 慢读饿死）。
QoS1 不提前 ACK 验证通过。
append queue / auth queue / downlink queue 均有界。
核心 dashboard 与告警已上线。
降级开关已验证。
回滚流程已验证。
```

不满足以下任一项，不能上线：

```text
无法解释单连接内存成本。
无法解释 append queue 最大内存。
无法解释 Kafka ack p99 对 PUBACK p99 的影响。
无法证明连接断开后资源回落。
无法证明设备重试带 jitter。
无法证明故障恢复不会形成二次风暴。
```

## 21. 建议执行顺序

推荐实际执行顺序：

```text
1. 完成压测客户端和指标。
2. 跑单节点 10k idle，验证工具链。
3. 跑单节点 50k idle，估算单连接成本。
4. 跑单节点 100k idle，确认 goroutine / fd / heap。
5. 跑单节点 50k QoS1 稳态上报。
6. 跑单节点 100k QoS1 稳态上报。
7. 注入 Kafka ack p99=2s。
8. 做 100k CONNECT 风暴。
9. 做 100k 上报风暴。
10. 做故障恢复和资源回落验证。
11. 扩到 300k 集群。
12. 扩到 500k 集群。
13. 扩到 100 万集群。
14. 做 12h / 24h 长稳。
15. 整理容量报告和上线阈值。
```

协议健壮性验证（§11.5）与负载压测无依赖，可在第 5~10 步之间穿插执行；fuzz 短跑应尽早进 CI。

每一步都必须产出报告。没有报告的压测不作为容量依据。

## 22. 最终目标

这套压测最终要回答三个问题：

```text
1. 这个 Broker 单节点到底适合承载多少连接？
2. 百万设备集群在正常、风暴和故障下是否可控？
3. 哪些配置、指标和降级动作必须作为生产上线红线？
```

如果压测只能证明平均吞吐，不能证明故障下的边界，那还不能支撑生产决策。

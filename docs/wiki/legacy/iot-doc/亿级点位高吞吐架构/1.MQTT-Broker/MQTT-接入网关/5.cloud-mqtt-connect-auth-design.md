# 云端 MQTT 接入 Broker CONNECT 认证设计

> 本文承接 [百万级设备 MQTT 接入层架构设计](./1.cloud-mqtt-gateway-architecture.md)，展开 MQTT CONNECT 认证的首版方案：直连数据库认证、认证队列、本地缓存、只读库隔离、上线风暴限流、失败语义和压测指标。
>
> **Review 记录**：本文档已经过对标 EMQX 的 review，识别出 2 个防爆盲区（flapping / banned）、2 个落地缺口（即时失效 / 极端窗口容量）及 L2 必要性论证。详见 [CONNECT 认证设计 Review（对标 EMQX）](./reference/connect-auth-design-review.md)。

## 1. 结论

首版可以采用直连数据库认证，但不能让每个 `CONNECT` 无保护地打到 DB。

推荐链路：

```text
MQTT CONNECT
  -> Broker 基础校验
  -> Broker 本地认证缓存
  -> bounded auth queue
  -> auth worker pool
  -> 认证只读库 / 只读副本
  -> 认证成功
  -> 写 Presence
  -> 返回 CONNACK
```

核心原则：

```text
1. DB 在认证队列、worker pool、超时和限流后面。
2. 认证只做最小单点索引查询，不查复杂业务表。
3. Broker 必须有进程内正向缓存和负向缓存。
4. auth queue 满时拒绝连接，让设备退避重连。
5. 认证成功后先写 Presence，再返回 CONNACK。
```

这不是最终形态。后续可以演进到独立 Auth Service、共享缓存、凭证变更事件和本地快照，但 Phase 1 不需要先把认证服务化。

> **方案定位（凭证存储的两种方式）**：本文（L1 + L2 + PG 穿透）≈ EMQX 的**外部 PG 认证模式**（EMQX 仅作 PG 客户端 + per-node ETS；本文额外补了 EMQX 没有的共享 L2）。凭证「本地化」有两种方式，按彻底程度递增：
> 1. **本地 L2**——把 §5.6 的 L2 后端从共享 Redis 换成**本地存储**（per-node，changelog 喂新），仍是「缓存 + PG 兜底」语义，见 §5.7。
> 2. **完全本地存储**——每节点持本 cell 全量凭证只读副本，PG 退出热路径，≈ EMQX **内建库模式**，见 [#15 CONNECT 凭证本地快照存储设计](./15.cloud-mqtt-credential-local-snapshot-design.md)。
>
> 两种方式替代的都只是**认证侧的凭证缓存/查询**；**Presence 的 Redis（CAS + fencing，§3.1 + doc #2）不在替代范围**，必须保留。

## 2. 目标与非目标

### 2.1 目标

```text
支撑日出大量设备同时 CONNECT。
保护业务主库不被认证风暴打穿。
认证结果与 tenant_id / device_id 绑定。
认证成功后才能写 Presence。
认证失败、超时、过载都有明确语义。
```

### 2.2 非目标

```text
不在首版建设独立 Auth Service。
不在每条 PUBLISH 时查 DB 做 ACL。
不在 CONNECT 阶段查询电站、用户、组织、报表配置等业务大对象。
不支持复杂动态 ACL 表达式。
不依赖数据库慢哈希扛高频机器认证。
```

## 3. CONNECT 认证流程

### 3.1 主流程

```text
TCP accept
  -> 设置 CONNECT read deadline
  -> 读取 MQTT CONNECT packet
  -> 校验协议版本 / client_id / username / payload 长度
  -> 解析 tenant_id / device_id
  -> 查 Broker 本地 auth cache
  -> cache hit: 本地校验 secret / status / acl_version
  -> cache miss: 进入 bounded auth queue
  -> auth worker 查询认证只读库
  -> 校验 secret
  -> 写正向或负向缓存
  -> 认证成功后写 Presence
  -> 返回 CONNACK
```

认证与 Presence 的顺序：

```text
认证成功
  -> Redis INCR session_version
  -> CAS 写 presence
  -> presence 写成功
  -> CONNACK success
```

如果认证成功但 Presence 写失败，生产默认拒绝连接或断开连接。否则平台会认为设备在线但下行无法可靠路由。

### 3.2 伪代码

```go
func handleConnect(c *Conn, pkt ConnectPacket) {
    principal, err := parseAndValidateConnect(pkt)
    if err != nil {
        c.SendConnAck(BadUsernameOrPassword)
        c.Close()
        return
    }

    result, ok := authCache.Get(principal.CacheKey())
    if ok {
        // 命中只是免 DB 查询：仍须用缓存的 secret_hash 做
        // constant-time 校验，并检查 status / 缓存过期
        result = verifyAgainstCachedCredential(principal, result)
    }
    if !ok {
        req := AuthRequest{
            Principal: principal,
            Deadline:  time.Now().Add(authTimeout),
        }
        result, err = authQueue.SubmitAndWait(req)
        if err != nil {
            c.SendConnAck(ServerUnavailable)
            c.Close()
            return
        }
    }

    if !result.Allowed {
        c.SendConnAck(result.ConnAckCode)
        c.Close()
        return
    }

    if err := presence.ConnectWrite(result.TenantID, result.DeviceID, c.ConnID); err != nil {
        c.SendConnAck(ServerUnavailable)
        c.Close()
        return
    }

    c.BindPrincipal(result.TenantID, result.DeviceID, result.ACLVersion)
    c.SendConnAck(Success)
}
```

## 4. 数据库认证模型

### 4.1 认证表

认证路径只查一张轻量表：

```sql
create table device_credential (
  tenant_id           varchar(64)  not null,
  device_id           varchar(128) not null,
  client_id           varchar(128) not null,
  secret_hash         varchar(256) not null,
  status              varchar(32)  not null,
  credential_version  bigint       not null,
  acl_version         bigint       not null,
  created_at          timestamp    not null,
  updated_at          timestamp    not null,
  primary key (tenant_id, device_id),
  unique key uk_client_id (client_id)
);
```

认证查询：

```sql
select tenant_id,
       device_id,
       client_id,
       secret_hash,
       status,
       credential_version,
       acl_version
from device_credential
where client_id = ?
limit 1;
```

如果 `tenant_id` 能从 username 或 client_id 中稳定解析，也可以使用：

```sql
where tenant_id = ? and device_id = ?
```

### 4.2 查询约束

CONNECT 热路径禁止：

```text
join 多张业务表
查询设备档案大 JSON
查询电站 / 用户 / 组织权限树
写登录历史明细
同步调用外部 HTTP 服务
慢哈希校验低熵密码
```

认证成功后的审计、登录历史、设备状态更新应异步写入日志或事件流。

### 4.3 密码与机器凭证

逆变器是机器身份，不是人类密码登录。设备 secret 必须是**高熵随机值**，禁止用低熵字符串、批次共享口令或与设备标识相关的可预测值。

#### 凭证格式规范（首版）

```text
device_secret: 高熵随机字节串，长度 ≥128 bit（推荐 256 bit）
               生成源必须是加密安全随机数生成器（CSPRNG）。
secret_hash:   服务端仅存储 SHA-256(device_secret) 的 hex 或 base64 编码。
               不添加 salt，不添加 server key，不使用 HMAC。
验证方式:      Broker 对 CONNECT 中的 password 做一次 SHA-256，
               与存储的 secret_hash 做 constant-time compare。
```

示例（Go 伪代码）：

```go
// 服务端预计算（出厂或轮换时）
secretHash := sha256.Sum256(deviceSecret)
store(hex.EncodeToString(secretHash[:]))

// Broker CONNECT 热路径
func Verify(password, storedHash []byte) bool {
    sum := sha256.Sum256(password)
    return subtle.ConstantTimeCompare(sum[:], storedHash) == 1
}
```

#### 为什么无 salt / 无慢哈希可接受

- 设备 secret 是机器生成的**高熵随机值**（≥128 bit），不是人类可记忆的密码。
- 128 bit 随机空间已使离线暴力破解和彩虹表在计算上不可行，salt 不再提供额外安全增益。
- 慢哈希（bcrypt / argon2 / PBKDF2）会把 CONNECT 热路径的认证吞吐压到极低，不适合百万级设备高频接入。
- 不添加 server key / HMAC，是为了避免引入 key 管理、key 轮换和双 key 过渡窗口等额外复杂度； secret 本身即完整凭证。

#### 强制要求

```text
✓ 必须使用 SHA-256。
✓ 必须 constant-time compare（subtle.ConstantTimeCompare 或等价实现）。
✓ device_secret 必须 ≥128 bit 加密安全随机值。
✗ 禁止用 MD5 / SHA-1。
✗ 禁止用 bcrypt / argon2 / PBKDF2 作为首版默认算法。
✗ 禁止在 Broker 热路径做慢哈希。
✗ 禁止记录明文 password / secret / secret_hash 到日志或指标。
```

#### 历史系统兼容

如果历史系统已经使用其他算法（如 bcrypt、加盐 hash、HMAC 等），需要专项评估：

```text
1. 明确迁移目标算法（推荐统一为本节 SHA-256 方案）。
2. 设计兼容期：允许同时存储旧 hash 和新 hash，按 credential_version 或 algorithm 字段区分。
3. 压测认证吞吐，确保迁移期间 Broker 热路径性能可接受。
4. 禁止在未经压测的情况下直接把慢哈希接入 CONNECT 热路径。
```

## 5. Broker 本地缓存

### 5.1 正向缓存

缓存 key：

```text
auth:{client_id}
```

缓存 value：

```json
{
  "tenant_id": "tenant-a",
  "device_id": "INV_001",
  "client_id": "tenant-a:INV_001",
  "secret_hash": "...",
  "status": "enabled",
  "credential_version": 12,
  "acl_version": 4,
  "expires_at": 1779233600
}
```

建议 TTL：

```text
5min ~ 30min
```

正向缓存命中只是避免 DB 查询，**不是认证通过**。每次命中都必须：

```text
1. 用缓存的 secret_hash 对本次 CONNECT 出示的 password 做 constant-time 比较。
2. 检查 status 是否为 enabled。
3. 检查缓存是否过期。
```

任何一步失败都按对应 CONNACK 码拒绝；缓存命中不能跳过 secret 校验，也不能因为某次密码错误就把该 client_id 拉黑。

### 5.2 负向缓存

**缓存 key 与语义（安全强制）**

负向缓存只缓存"按 client_id 未查到凭证记录"这一事实，用于挡住未知 client_id 的风暴：

```text
key:   auth:missing:{client_id}
value: not found
TTL:   30s ~ 120s
```

**禁止事项**

- **禁止把"凭证错误"（bad credential）作为按 client_id 的负向缓存条目。** 若攻击者用某 client_id 发送一次错误密码，该 client_id 就会被全局拉黑 10s~60s，真实设备会被定向 DoS。client_id 通常是可枚举的（如 `tenant-a:INV_001`），该攻击协议合法、无需正确密码，且表现与固件 bug 高度相似。
- **禁止把"设备禁用"作为按 client_id 的负向缓存条目。** 设备状态应属于正向缓存中的记录字段（`status`），并随凭证记录一起过期。
- 负向缓存条目**不能**替代认证判决。

**如需对错误凭证做限流**

如果需要在 bad credential 场景下做限流/防暴破，该机制必须是**独立于 auth cache 的 throttle**，并且：

```text
key:    {client_id}|{source_ip}  （至少同时包含二者，禁止仅用 client_id）
action: 限制尝试频率（如 1 次/秒），而不是直接返回 Bad Username or Password
语义:   即使命中 throttle，当该 client_id 存在有效凭证时，正确密码仍必须被校验并允许通过
```

throttle 只能延迟或拒绝"高频错误尝试"，不能成为"该 client_id 当前密码错误"的缓存，更不能覆盖正向缓存中的正确 secret_hash。

### 5.3 缓存失效边界

本地缓存会带来短暂的禁用延迟：

```text
后台禁用设备
  -> Broker 本地缓存尚未过期
  -> 设备可能在 TTL 内继续认证成功
```

首版可以接受该边界。若业务要求秒级禁用，后续需要增加：

```text
credential_version 推送
auth cache invalidation event
共享缓存
短 TTL + 后台强制踢连接
```

### 5.4 缓存实现与容量边界（实现说明 + 压测/运维关注点）

**实现选型**：本地缓存底层用 [otter](https://github.com/maypok86/otter)（S3-FIFO 驱逐），正负缓存共用一个实例。选它解决两件事：

```text
1. O(1) 驱逐：替换早期"map + 随机驱逐"——后者在缓存填满且条目未过期时，
   每次插入都要 O(n) 扫描找过期项。冷启动唯一-client_id 洪泛（§7 冷启动 +
   §9 bad/disabled flood）下，这正好退化成每个 CONNECT 一次全表扫描 → CPU 耗尽。
2. 抗扫描：海量"只出现一次"的 unknown client_id 洪泛不会冲刷掉反复命中的热凭证。
   朴素 LRU / 随机驱逐会在洪泛下淘汰热设备，导致热设备每次重连都重打认证只读库。
```

**TTL 归属**：正负 TTL 不同（§5.1 5~30min / §5.2 30~120s），且要随凭证过期重新穿透，
因此 TTL 判定保留在缓存包装层（按记录的 `expires_at` 比对），不交给 otter 原生 TTL。
otter 只承担"有界 + 并发安全 + 抗扫描"的存储职责。

**容量边界（⚠️ 压测和运维必须关注）**：otter 的驱逐是**异步**的——突发批量写入时，
内部 write buffer 会短暂积压，`cache size` 可**瞬时超过 `MaxEntries`**，维护协程清空后**稳态收敛到 `MaxEntries`**。

```text
稳态：cache_entries == MaxEntries
瞬时：cache_entries 可短暂 > MaxEntries
  - 大容量（生产 MaxEntries 数万~十万级）：实测瞬时峰值约 2~3 倍。
  - 小容量 + 高并发突发：相对超额更大（cap=16 压测下曾瞬时冲到数千），
    但与"洪泛总 key 数"无关（受 write buffer 约束），不会无界增长。
```

含义与要求：

```text
1. 红线"缓存必须有界"仍满足：是"收敛到有界"，不是"任意时刻精确 == MaxEntries"。
   不会把海量 unknown key 全量留在内存 → 不会 OOM。
2. 容量规划：为 cache 估算内存时，按 MaxEntries × ~3 倍 + 单条目大小 预留余量，
   不要按 MaxEntries × 1 倍掐死，否则突发期可能逼近内存水位。
3. 压测验收：观察 cache_entries 的瞬时峰值与回落（收敛）曲线，而不是只看稳态值；
   在 bad/disabled/unknown flood 场景下确认它收敛、不随洪泛规模线性增长。
4. 运维告警：cache_entries 持续高于 ~3×MaxEntries 不回落，说明维护协程被拖住或异常，应排查。
```

### 5.5 本地缓存（L1）的职责定位与容量口径

百万设备 + 多节点 + 无 LB 粘性（接入拓扑见架构设计；设备每次重连可能落到任意节点）下，
最容易产生两个误解：① "每个节点要 L1 缓存大部分设备 → L1 过大"；② "无粘性下同设备落到不同节点
→ L1 没意义"。两者都把 L1 错当成"全量在线设备的本地副本"。**L1 不是设备在线表，是一个短窗口前置闸。**

#### 5.5.1 L1 的主要职责（以及明确不是它的职责）

L1 的定位不是"记住每一台设备的凭证"，而是用进程内零网络跳的代价，承担四件事：

```text
1. 负向洪泛 / 扫描的第一道闸（最重要，且与粘性无关）。
   unknown / bad client_id 洪泛在单节点上天然产生重复，L1 负向缓存就地吸收，
   不让它们穿透到 L2 / DB。otter 的 S3-FIFO 抗扫描保证这些"一次性 key"不会
   冲刷掉热凭证（§5.4）。这条是每节点独立成立的，多开节点不削弱它。
2. 吸收高频 flapper。移动网络最差的那批设备会在短时间内反复重连，
   单节点内就形成高频重复 → L1 命中，省掉 L2/DB 往返。
3. 省一次 L2 / Redis 网络跳。L1 命中的请求根本不出网，是 CONNECT 热路径最快的一档。
4. DB（认证只读库）故障时的降级兜底。DB 不可用但 L1 正向条目未过期时，
   已缓存设备仍可本地通过认证（§9 的"DB 不可用但正向缓存未过期 → 允许已缓存设备登录"）。
   注意：这条兜底是针对 DB 故障，不是 Redis 故障——presence 写强依赖 Redis（红线 #6），
   Redis 挂时新连接无论如何拒连，L1 命中救不了。
```

**明确不是 L1 的职责**（这些是 L2 的活，§5.6）：

```text
× 跨节点正向复用（无粘性下被 N 稀释，靠共享 L2 收回，不靠 L1）。
× 隔夜保温、扛日出冷启动（L1 隔夜过期，靠长 TTL 的 L2）。
× 当"全量设备凭证的本地全集"（那会把 L1 撑到 fleet 大小，违背窗口有界）。
```

一句话：**L1 管"就地高频重复 + 负向洪泛 + 省网络跳 + DB 故障兜底"，L2 管"跨节点复用 + 隔夜保温"。**

#### 5.5.2 L1 容量口径：由"连接速率 × 短 TTL"决定，不由设备总数决定

关键机制：**稳定在线的设备会从 L1 过期掉。** 一台设备日出连一次 → 进 L1 → 之后一整天稳定长连、
不再被查 → 一个 PositiveTTL 后其 L1 条目过期被驱逐，**哪怕连接还活着**。所以 L1 在任意时刻只持有
"最近一个 TTL 窗口内发生过认证查询"的设备（正在 churn + 刚连上的那批），不是"当前所有在线连接"。

```text
L1 条目数 ≈ min( 单节点 CONNECT 速率 × PositiveTTL , 设备总数 )
                  ↑ 由重连/上线速率驱动，不是 fleet
```

两个量级（示例：D=100万设备，N=20 节点，PositiveTTL=10min）：

```text
日出峰值（最坏）：1M 设备集中连一次，每节点摊 D/N = 5万。
  若日出窗口 ≈ TTL，L1 峰值 ≈ 5万条/节点 ≈ 17MB（按 ~350B/条），
  叠加 otter 异步瞬时超额 2~3 倍也就 ~40MB 一闪而过。
白天稳态：设每设备每小时重连 ~3 次 → 全网 R≈833/s，每节点 42/s，
  × TTL 600s ≈ 2.5万条 ≈ 9MB。
要把 L1 装到接近 fleet(1M)，需 (R/N)×T ≈ 1M，即 R≈3.3万次重连/秒
  （每台设备每 30s 重连一次）——病态 flap 风暴，非正常 churn。
```

容量结论：

```text
MaxEntries ≈ fleet/N + headroom（本例 ~6万~12万），不是 fleet(1M)。
内存几十 MB/节点，可忽略。L1 不会过大。
```

**短 TTL 纪律（重要）**：想用"长 TTL 隔夜保温扛日出"的那个长 TTL **只能放 L2，绝不能放 L1**。
若给 L1 设 24h TTL：日出全部 1M 连上后 24h 内谁都不过期 → L1 真的累积到 ~fleet/节点 → 这才"过大"。
L1 必须保持短 TTL（分钟级）以维持窗口有界。

#### 5.5.3 L1 / L2 大小与副本数对照

| | TTL | 单节点大小 | 全集群副本数 | 由谁决定大小 |
|---|---|---|---|---|
| **L1（otter，本地）** | 短（分钟级） | 窗口有界 ≈ fleet/N 峰值 | ×N 份，每份小 | 单节点 connect 速率 × TTL |
| **L2（Redis/Tair，共享）** | 长（≥隔夜空窗，24h+） | —— | **1 份**，全网存一次 | fleet（全量凭证） |

要点：L2 是**一份**共享存储装全量、保温隔夜；L1 是每节点的短窗口前置，永远小。
这样既不让每个节点复制全量，又能用 L2 扛日出。**size（本节）和 hit-rate（§5.6）是两个轴：
无粘性不会让 L1 变大，只会让 L1 正向复用变差——前者本节解决，后者靠 L2。**

### 5.6 L1 / L2 分层与日出集中上线洪峰的 L2 承接（指标分析）

光伏逆变器日出集体上线 = 全量设备在一个窗口内集中 CONNECT（容量见 §7）。这是认证 DB 最危险的时刻，
而 §7.2 指出"不能假设本地缓存挡得住日出风暴"——因为 **L1 隔夜过期，日出时是冷的，命中率 ≈ 0**。
引入 **持久 L2（长 TTL，跨隔夜空窗保温）** 正是为了把这道冷启动洪峰从 DB 移到 L2。

#### 5.6.1 承接链路

```text
CONNECT
  -> L1（本地）：日出时冷，几乎必 miss
  -> L2（共享 Redis/Tair）：长 TTL，隔夜仍 warm → 命中即返回凭证，回填 L1
  -> （仅 L2 miss 才）认证只读库 DB
  -> 校验 secret -> 写 presence -> CONNACK
```

前提（缺一不可）：

```text
1. L2 TTL > 隔夜空窗（夜间 8~16h），否则次晨 L2 也凉了。建议 L2 TTL ≥ 24h。
2. L2 容量 ≥ fleet，否则容量驱逐会在日出制造 L2 miss → 打 DB。
3. 凭证变更走事件失效（§5.3 / §11 Phase 2 "凭证变更事件推送"），
   否则长 TTL 会让轮换 / 禁用的凭证长时间生效。
```

#### 5.6.2 指标推导（符号 + 示例）

```text
符号：D=设备总数  N=节点数  W=日出集中窗口(s)  h1=L1命中率  h2=L2命中率
日出全网 CONNECT 峰值速率   λ ≈ D / W          （窗口内均匀的下界；真实更尖，需按最密集区域）
单节点 CONNECT 速率          λ / N
打到 L2 的 QPS               λ × (1 - h1) ≈ λ    （日出 h1≈0，L1 冷，几乎全透到 L2）
打到 DB 的 QPS               λ × (1 - h1) × (1 - h2) ≈ λ × (1 - h2)
Redis 总 op/s（日出）        ≈ λ × (L2_GET 1 + presence_INCR 1 + presence_CAS 1) ≈ 3λ
```

示例（D=1M，N=20，W=600s，h2=99%）：

| 指标 | 有持久 L2 | 无 L2（仅 L1） |
|---|---:|---:|
| 全网 CONNECT 峰值 λ | ~1,667/s | ~1,667/s |
| 打到 L2 的 QPS | ~1,667/s（Redis 轻松，单实例 ~10万 op/s） | — |
| **打到 DB 的 QPS** | **~17/s** | **~1,667/s（≈λ，L1 冷）** |
| Redis 总 op/s（含 presence） | ~5,000/s（仍 trivial） | ~3,333/s（presence 本就有） |
| L2 内存（一份） | D×~600B ≈ 600MB | — |

核心结论：**持久 L2 把日出 DB QPS 从 ≈λ 砍到 λ×(1-h2)（本例 1667→17，降两个数量级），
代价是给共享 Redis/Tair 增加 ≈λ 的 GET 负载——而 Redis 的 op/s 余量远大于 DB，是划算的负载搬移。**
注意 presence 写本就强依赖 Redis（红线 #6），即 Redis 早已在 CONNECT 关键路径上，
L2 复用同一 Redis 不引入新的硬依赖维度，只是加 GET 负载，按总和扩容即可。

#### 5.6.3 验收指标（压测，承接 §13 / 压测规划 doc #8）

```text
L2 命中率 @ 日出峰值          ≥ 99%（验证 L2 TTL 跨空窗 + L2 容量 ≥ fleet + 凭证变更失效正确）
DB query QPS @ 日出峰值        ≤ §6.2 的 per-broker DB miss 预算 × N（即 λ×(1-h2) ≤ B_total）
Redis op/s @ 日出峰值          ≤ Redis/Tair 容量 × 安全水位（含 auth L2 GET + presence INCR/CAS）
CONNACK success latency p99    在 SLA 内（L1 miss→L2 GET 多一个 RTT，~0.5~2ms）
L2 eviction rate @ 日出         ≈ 0（非 0 说明 L2 容量 < fleet，会漏到 DB）
冷 L2 退化演练                  L2 被清空 / 不可用时，DB 直面 λ，回落到 §7 防线
                               （只读副本 headroom + auth queue + 固件首连 jitter），
                               验证 L2 是优化层、能优雅退化，不是新增硬性 single point。
```

#### 5.6.4 关键纪律

```text
1. L2 是优化层，不是正确性依赖：L2 冷 / 挂时必须能退回 §7 的非缓存防线（replica+queue+jitter），
   日出方案不能假设 L2 永远 warm。
2. L1 短 TTL / L2 长 TTL：保温职责在 L2；L1 一旦设长 TTL 就会被日出撑大（§5.5.2）。
3. 日出尖峰仍需固件首连 jitter + 地理错峰兜底：L2 降的是"DB 被打穿"，
   但 λ 本身（连接建立速率、presence 写速率、TLS 握手速率）不因 L2 而变小，
   仍要靠 jitter / 按最密集区域定容量来削峰（详见业务负载画像与 §7）。
```

### 5.7 L2 缓存的存储后端：共享 Redis vs 本地存储（本地 L2 变体）

> **决策（已定）**：连接凭证采用 **本地 L1 + 堆外本地 L2**（off-heap，fastcache/freecache 风格或 mmap），**不使用 Redis**；miss 回 PG 只读副本。凭证因此是 **per-node 有界缓存**——不在 CONNECT 热路径依赖 Redis，也**不是 cell / Redis 的容量约束项**（「每节点全量、≤5M」那种约束只属于 [#15 完全本地快照](./15.cloud-mqtt-credential-local-snapshot-design.md)，#15 是未采用的备选）。下文「本地 L2 变体」即本决策的方案描述。

§5.6 的 L2 默认用共享 Redis/Tair，但 L2 的职责（跨节点复用 + 隔夜保温）也可以由**每节点的本地存储**承担，构成「本地 L2」变体：

```text
共享 Redis L2（默认）：全网一份，跨节点天然复用；多一跳网络 RTT；CONNECT 路径硬依赖 Redis。
本地 L2（变体）      ：每节点一份本地缓存（disk / noscan 内存），零网络跳；
                     但无粘性下「自身流量」喂不暖 → 必须由 Kafka changelog 广播喂新
                     （否则退回无粘性稀释，见 §5.5 / review §4）。
```

本地 L2 仍是**缓存**（有界、可 miss、PG 兜底），与 [#15](./15.cloud-mqtt-credential-local-snapshot-design.md)「完全本地存储」的区别在于**是否权威**：

| | 本地 L2（本变体） | 完全本地快照（#15） |
|---|---|---|
| 持有量 | 有界子集（可驱逐） | 本 cell 全量 |
| miss 时 | 回 PG 兜底 | 已纳管设备不会 miss；PG 仅冷启动源 |
| 适用场景 | 单 cell 凭证 > 节点内存，想去掉共享 Redis 但容忍部分 PG | 单 cell 凭证 ≤ ~5M，装得下全量 |
| 存储引擎 | 同 #15 §5（noscan 三档：map → 列式 SoA → mmap） | 同 #15 §5 |

不论哪种本地化，喂新通道都建议统一为 **compacted Kafka changelog**（#15 §6），失效从「TTL 过期」升级为「事件驱动」（亚秒）。**边界**：本地 L2 替代的只是 Redis 的**认证缓存**用途；**Presence 的 Redis 不在替代范围**（§3.1 + doc #2）。

## 6. 认证队列与 DB 保护

### 6.1 Broker 侧限制

每个 Broker 配置：

```text
max_auth_inflight = 100 ~ 500
max_auth_queue = 1000 ~ 5000
auth_timeout = 1s ~ 3s
connect_read_timeout = 3s ~ 10s
```

限制项：

```text
全局 CONNECT rate
全局 auth queue bytes / messages
每租户 CONNECT rate
每 IP CONNECT rate
每 device_id 同时认证 inflight = 1
错误凭证速率
```

队列满或超过认证预算时：

```text
优先返回 CONNACK Server Unavailable
如果连接已不可靠或无法及时响应，则直接 close
设备必须按退避策略重连
```

MQTT 3.1.1 可用返回码：

| 场景 | CONNACK 返回码 |
|---|---|
| 成功 | 0x00 Connection Accepted |
| 协议不支持 | 0x01 Unacceptable Protocol Version |
| client_id 不合法 | 0x02 Identifier Rejected |
| 认证系统过载 / DB 超时 | 0x03 Server Unavailable |
| 用户名密码错误 | 0x04 Bad Username or Password |
| 设备禁用 / 无权限 | 0x05 Not Authorized |

### 6.2 DB 侧保护

推荐：

```text
Broker 只连接认证只读库 / 只读副本。
认证库与业务主库隔离连接池。
认证查询设置短超时。
慢查询直接失败，不拖住连接。
所有查询命中索引。
```

DB 连接池上限必须与全局认证预算匹配，而不是每个 Broker 随意开大：

```text
db_auth_budget_qps = 认证库可承受 QPS
broker_count = Broker 实例数
per_broker_db_miss_qps <= db_auth_budget_qps / broker_count
```

示例：

```text
认证只读库安全预算：4000 query/s
Broker 数量：20
每 Broker cache miss 查询预算：<= 200 query/s
```

超过预算后，Broker 应在 auth queue 前限流，而不是继续扩大 DB 连接池。

## 7. 上线风暴容量模型

百万设备集中上线的 CONNECT 速率：

| 上线窗口 | CONNECT/s |
|---|---:|
| 30 分钟 | 约 556/s |
| 10 分钟 | 约 1667/s |
| 5 分钟 | 约 3333/s |
| 1 分钟 | 约 16667/s |

DB 查询压力：

```text
db_qps = connect_rate * (1 - auth_cache_hit_rate)
```

冷启动早晨如果 Broker 本地缓存为空：

```text
auth_cache_hit_rate ≈ 0
db_qps ≈ connect_rate
```

因此必须依赖：

```text
设备上线 jitter
多 Broker 分摊
认证只读库扩容
auth queue 限流
失败退避
```

不能假设本地缓存一定能挡住第一次日出上线风暴。

## 8. 设备退避要求

Broker 过载保护要与设备退避配合才有效。

设备连接失败后建议：

```text
首次失败：1s ~ 5s 随机
连续失败：5s ~ 30s 随机
持续失败：30s ~ 300s 随机
```

要求：

```text
退避必须加入 jitter。
不要所有设备在整点或日出瞬间同时重连。
收到 Server Unavailable 后必须退避。
TLS / TCP 失败也必须退避。
```

如果固件暂时无法调整，平台侧只能更保守地限制 auth queue，并准备更高的只读库和 Broker 冗余。

## 9. 故障语义

| 故障 | Broker 行为 | 结果 |
|---|---|---|
| cache hit 且凭证有效 | 允许认证 | 后续写 Presence |
| cache miss 且 DB 正常 | 查 DB 后缓存结果 | 正常认证 |
| cache miss 且 DB 超时 | 返回 Server Unavailable / close | 设备退避重连 |
| auth queue 满 | 返回 Server Unavailable / close | 保护 DB 与 Broker 内存 |
| DB 不可用但正向缓存未过期 | 可允许已缓存设备登录 | 接受短暂禁用延迟 |
| DB 不可用且 cache miss | fail closed | 不允许未知设备登录 |
| 凭证错误 | 返回 Bad Username or Password | 不写入按 client_id 的负向缓存；可触发 (client_id,IP) 级 throttle |
| 设备禁用 | 返回 Not Authorized | 不写入按 client_id 的负向缓存；状态作为正向缓存记录字段随记录一起过期 |
| Presence 写失败 | 返回 Server Unavailable / close | 避免在线路由不一致 |

生产默认：

```text
未知设备 fail closed。
认证系统过载 fail fast。
已缓存且未过期的设备可以继续登录。
```

## 10. ACL 边界

CONNECT 认证只确定：

```text
tenant_id
device_id
client_id
credential_version
acl_version
```

Broker 本地根据这些字段做基础 ACL：

```text
上行 PUBLISH 只能发布自己的 telemetry topic。
下行 SUBSCRIBE 只允许订阅自己的 command topic。
禁止 wildcard。
禁止跨 tenant / 跨 device topic。
```

不要在每条 PUBLISH / SUBSCRIBE 时查 DB。ACL 策略应在认证结果中携带 `acl_version`，由 Broker 本地规则执行。

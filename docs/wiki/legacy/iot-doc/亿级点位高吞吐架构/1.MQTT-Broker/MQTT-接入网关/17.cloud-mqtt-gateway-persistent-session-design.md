# 云端 MQTT Gateway 持久会话（CleanSession=false）支持设计（可选能力，暂不实现）

> 现状：[实现红线 §10](./7.cloud-mqtt-gateway-implementation-red-lines.md) 一阶段不做持久会话，[协议范围](./1.cloud-mqtt-gateway-architecture.md)**强制 CleanSession=true**。
>
> 本文用途：**暂不实现**；但若客户要求持久会话 / CleanSession=false，用本文（a）先澄清他真正要的是什么，（b）给出按需启用的实现方案。可直接用于向客户介绍。
>
> 关联：[架构 §1.2 系统定位](./1.cloud-mqtt-gateway-architecture.md)、[#14 下行 Topic 路由 §2.4](./14.cloud-mqtt-gateway-downlink-topic-routing-design.md)、[#16 Retain 设计](./16.cloud-mqtt-gateway-retain-design.md)、[Presence 设计](./2.cloud-mqtt-presence-registry-design.md)。

## 1. 结论（TL;DR）

```text
1. 90% 的「要持久会话」其实是「发给离线设备的命令不能丢」——
   这由【Command Service 的 DB 状态机 / outbox】承担，已在架构里，且比 broker 持久会话更可靠
   （跨重启、带业务 TTL、可审计）。先用它满足。
2. 「不想每次重订阅」→ 设备只订自己 1 个 cmd topic，重订极廉价；或服务端按身份 auto-subscribe，免订。
3. 只有当客户【确实需要 CleanSession=false 的线协议语义】（现成 MQTT 设备/App 依赖它，如迁移既有方案）
   时，才实现真持久会话。它比 retain 更难——本质是在 MQTT 层重造一遍 outbox + EMQX 式会话迁移。
4. 真要做：会话态/离线队列【外置】且【bounded】，离线投递【复用 Command Service outbox】，不在 broker 排队。
```

## 2. 先澄清需求：客户要的多半不是持久会话，是「离线命令不丢」

持久会话（CleanSession=false）提供三件事，定义性价值是第 ②：

```text
① 订阅持久：broker 记住订阅，重连不用重订。
② 离线消息队列：QoS1/2 订阅，客户端离线时把发往它的消息排队，重连补发。 ← 核心
③ inflight 持久：未确认的 QoS1/2 消息跨重连保留、重传。
```

在 IoT 里这几乎总是「**发给临时离线设备的下行不能丢**」，而这正是 **Command Service** 的职责。

| 客户的真实诉求 | 持久会话的做法 | 本架构的答案（更好） |
|---|---|---|
| 离线设备的命令重连补发 | broker 每客户端离线队列 | **Command Service outbox**：presence 感知，设备上线即重投待发命令 |
| 不要补发「过期的」命令 | MQTT 离线队列**无业务 TTL**，盲投 | outbox **带 TTL / 状态机**，丢弃或重评估陈旧命令 |
| 跨 broker 重启不丢 | broker 内存队列，**重启即丢** | outbox 在 **DB，跨重启 / 跨 broker 都在** |
| 重试 / 审计可见 | MQTT 队列黑盒 | 状态机有 status / retry / 审计 |
| 免重订阅 | 订阅持久 | 设备只订**自己 1 个 cmd topic**，重订极廉价；或服务端 **auto-subscribe**（免订） |

> **对逆变器域致命的一点**：MQTT 离线队列没有业务 TTL。一条 14:00 下发的「关机」命令，设备傍晚断电离线 → 队列压到次日 6:00 日出重连才投递 → 投了一条 16 小时前的过期危险命令。outbox + TTL 会丢弃 / 重评估它。**这就是 broker 离线队列对本域错误、outbox 正确的根因。**

### 决策树（向客户介绍时用）

```text
客户说「要持久会话 / CleanSession=false」
  ├─ 想要「离线设备的命令重连不丢」？   → Command Service outbox（已有，且带 TTL/审计/跨重启）
  ├─ 想要「离线设备上线拿到目标配置」？ → 设备影子 desired 态（见 #16）
  ├─ 不想每次重订阅？                   → 设备只订自己 1 个 topic，或服务端 auto-subscribe（免订）
  └─ 现成 MQTT 设备/App 真依赖线语义？  → §4 真持久会话（成本高，基本重造 outbox）
```

## 3. MQTT 持久会话语义（实现前先对齐定义）

真要做，必须支持这些，否则不算"支持持久会话"：

```text
1. CONNECT CleanSession=false：复用 client_id 的既有会话（订阅 + 未投递 QoS1/2 + inflight）。
2. 断开后保留会话：MQTT3.1.1 无限期保留；MQTT5 按 Session Expiry Interval 到期清除。
3. 离线期间：发往其订阅 topic 的 QoS1/2 消息入会话队列，重连后投递。
4. 重连：CONNACK 的 Session Present=1 表示沿用旧会话；恢复订阅、重传 inflight、清空离线队列。
5. CleanSession=true 连接到同一 client_id：清除旧会话。
6. 队列必须有上限（参考 EMQX max_offline_messages），溢出按策略丢弃。
```

## 4. 真持久会话实现设计（外置 + 复用 outbox，不破红线）

### 4.1 设计原则

```text
- 会话态 / 离线队列 / inflight 【外置】（Redis/DB，键 client_id），不进 broker（broker 仍 pointer-poor）。
- 离线队列必须【bounded】（max msgs / max bytes，溢出按策略丢，红线 §4）。
- 离线【投递】复用 Command Service outbox，不在 broker 层重建一套队列。
- 无粘性下重连可能落到别的 broker → 会话态从【共享外置存储】取，不依赖 broker 内存（这是会话迁移）。
- opt-in，逆变器默认不开。
```

### 4.2 把持久会话拆成两半，分别解决

```text
A. 订阅持久（便宜）：
   - 方案①（推荐）：服务端按身份 auto-subscribe —— 设备 CONNECT 后 broker 自动绑定其 cmd topic，
     设备根本不发 SUBSCRIBE，"持久"与否都无所谓。
   - 方案②：外置订阅表 sub:{client_id} → filters，重连按 client_id 恢复。
B. 离线消息（贵，= outbox，别重建）：
   - 下行经 Command Service：设备离线时命令进 outbox（DB，带 TTL/重试）；
     presence 感知设备上线 → outbox flush 待发命令。
   - 即「持久会话的离线队列」由 outbox 承担，broker 不持每客户端队列。
```

> 关键：**A 便宜可单独做；B 不要在 broker 重造，直接接 outbox。** 多数"持久会话"需求 = A + 已有的 B。

### 4.3 仅当需要完整线语义（Phase 3）才补的部分

```text
- Session Present / Session Expiry：外置会话存储记录会话存在性与到期时间。
- inflight 持久 + 重传：外置 inflight 状态（client_id → 未确认包），重连重传。
- 会话迁移：重连落到别的 broker，新 broker 从外置存储取会话态接管（含旧连接 fencing 清理，
  类比 EMQX takeover）。这是成本大头。
```

### 4.4 数据流（Phase 1+2，推荐形态）

```text
设备离线期间下行：
  cloud --命令--> Command Service --presence: 离线--> outbox(DB, 带 TTL)

设备重连：
  device --CONNECT(CleanSession=false)--> broker --auto-subscribe/恢复订阅-->
     broker 写 presence 在线 --> Command Service 感知上线 --> outbox flush 未过期命令 --> device
```

## 5. 与红线 / 容量的关系

| 红线 / 约束 | 本方案如何满足 |
|---|---|
| §10 不做持久会话 | 本文是**可选能力**，默认关闭；启用是 opt-in 加法 |
| §2 Broker pointer-poor | 会话态 / 队列外置；broker 无每会话状态 |
| §4 bounded | 离线队列有 max msgs/bytes 上限；溢出有策略 |
| §8 下行 fencing | 离线投递走 outbox + 现有下行写 + fencing |
| 1M 容量 | broker 不持离线队列；离线态在外置存储 |
| 业务正确性 | outbox 带 TTL，避免补发过期命令（§2 逆变器场景） |

## 6. 分阶段交付

```text
Phase 0（现状）：CleanSession=true。离线命令不丢用 outbox；订阅用 auto-subscribe / 廉价重订。
Phase 1（订阅持久）：服务端 auto-subscribe（推荐）或外置订阅表。覆盖"不想重订阅"。
Phase 2（离线投递）：下行接 Command Service outbox，presence 上线即 flush（bounded + TTL）。覆盖"命令不丢"。
Phase 3（完整线语义）：外置会话/inflight/expiry + 会话迁移（EMQX takeover 式）。
        仅在迁移依赖 CleanSession=false 的现成 MQTT 固件/App 时做，成本最高。
不做：broker 内存每客户端离线队列；无界队列；无 TTL 的盲目补发。
```

## 7. 向客户介绍的要点小结

```text
1. 「离线设备的命令不丢」我们用云侧【持久投递队列 outbox】实现，比 MQTT 持久会话更可靠：
   状态在 DB、跨 broker 重启不丢、带重试与【业务 TTL】（不会盲补几小时前的过期命令）、可审计。
2. 「不想每次重订阅」：设备只需订自己的命令 topic，或我们按身份自动绑定（免订），无需 CleanSession=false。
3. 若您的设备固件确实依赖 MQTT 持久会话线语义，可单独评估按需实现（含会话迁移），
   但「不丢命令」这个目标，云侧 outbox 已覆盖且更强。
```

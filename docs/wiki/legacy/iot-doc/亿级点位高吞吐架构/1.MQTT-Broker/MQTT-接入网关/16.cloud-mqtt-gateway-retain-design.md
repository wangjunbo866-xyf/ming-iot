# 云端 MQTT Gateway Retain 语义支持设计（可选能力，暂不实现）

> 现状：[实现红线 §10](./7.cloud-mqtt-gateway-implementation-red-lines.md) 一阶段不做 retain，`retain=true` 标志当前是 **no-op**（消息照常进 Kafka，不产生 retain 行为）。
>
> 本文用途：**暂不实现**；但若客户要求 retain，用本文（a）先澄清他真正要的是什么，（b）给出按需启用的实现方案。可直接用于向客户介绍。
>
> 关联：[架构 §1.2 系统定位](./1.cloud-mqtt-gateway-architecture.md)、[#14 下行 Topic 路由 §2.4 上下行不对称](./14.cloud-mqtt-gateway-downlink-topic-routing-design.md)、[Presence 设计](./2.cloud-mqtt-presence-registry-design.md)。

---

## 1. 结论（TL;DR）

```text
1. 90% 的「要 retain」其实是「要设备的当前/最新状态」或「下发的目标配置」——
   这由【设备影子 device shadow】承担，已在架构下游，零 Broker 改动，最便宜。先用它满足。
2. 只有当客户【确实需要 MQTT retain 的线协议语义】（现成 MQTT 设备/应用用 retain 位、
   期望 SUBSCRIBE 时通过 MQTT 收到 retained 消息，如迁移既有 MQTT 方案）时，才实现真 retain。
3. 真 retain 按本文做：retain 存储【外置】（不进 Broker），更新走 Kafka 消费者，
   订阅时投递精确 topic 走点查、通配复用 #14 匹配器。分阶段、opt-in，不破红线。
4. per-device 状态的 retain ≈ 设备影子，不要建并行存储——直接用影子。
```

---

## 2. 先澄清需求：客户要的多半不是 retain，是「当前状态」

MQTT retain 的**实际用途**是：「一个订阅者**刚连上/刚订阅**就立刻知道某 topic 的**当前值**，不用等下一条」。在 IoT 里这几乎总是两件事之一，而它们都对应**设备影子**：

| 客户的真实诉求 | MQTT 里的体现 | 本架构的答案 |
|---|---|---|
| 「立刻知道设备**当前状态/最后上报值**」 | 设备 publish 遥测 retain=true | **设备影子 reported 态**（影子存最新解码值，可查/可推） |
| 「给离线设备留一份**目标配置**，它上线就拿到」 | 云 publish 配置 retain=true | **设备影子 desired 态**（AWS IoT shadow 的经典模式：云写 desired，设备连上即得） |
| 「我的现成 MQTT 设备/App **就是用 retain 位**，要线协议兼容」 | 真·MQTT retain 语义 | → 走 §4 真 retain 实现 |

### 决策树（向客户介绍时用）

```text
客户说「要 retain」
  ├─ 想要「设备当前状态 / 最后值」？        → 设备影子 reported（已有，推荐）
  ├─ 想要「离线设备上线拿到目标配置」？     → 设备影子 desired（已有，推荐）
  └─ 现成 MQTT 设备/App 依赖 retain 线语义？ → §4 真 retain（opt-in，按本文实现）
```

> **话术**：「我们提供比 retain 更适合 IoT 的能力——设备影子，既有当前状态查询、也有目标配置下发，且带版本与审计。若您的设备固件/应用确实依赖 MQTT retain 位，我们也支持按需开启标准 retain，见下。」

## 3. MQTT retain 协议语义（实现前先对齐定义）

真要做，必须完整支持这些语义，否则不算"支持 retain"：

```text
1. PUBLISH retain=true：Broker 存【该 topic 的最后一条】retained 消息（覆盖旧的）。
2. PUBLISH retain=true 且 payload 为空：清除该 topic 的 retained 消息（删除）。
3. SUBSCRIBE：对每个匹配的 topic，立即把当前 retained 消息投给订阅者，
   投递的 PUBLISH 带 retain 标志；QoS 取 min(存储 QoS, 订阅 QoS)。
4. 通配订阅：投递所有匹配该 filter 的 retained 消息。
5. 跨重启持久：retained 消息独立于任何会话，Broker 重启后仍在。
6. （MQTT5）Retain Handling 订阅选项：0 总是发 / 1 仅新订阅发 / 2 不发；Retain As Published。
```

## 4. 真 retain 实现设计（外置，不破红线）

### 4.1 设计原则

```text
- retain 存储【外置】（Redis/Tair），不进 Broker（Broker 仍 pointer-poor、无每-topic 状态）。
  —— 沿用 presence/auth 的"状态外置"模式。
- 订阅时投递走【bounded 查询 + 现有下行写】，不阻塞 read loop（像 auth 用 worker/queue）。
- 通配匹配【复用 #14 下行路由器的匹配器】，不在 Broker 做 topic 匹配。
- opt-in（per-product/tenant），逆变器默认不开。
```

### 4.2 retain 存储

```text
键：retain:{topic}
值：{ payload, qos, ts, props(MQTT5), publisher_id }
写：retain=true 且非空 → 覆盖写；retain=true 且空 payload → DEL
容量：= 不同 retained topic 数 × 消息大小（在 Redis，不在 Broker）
```

> **容量红线**：若是 **per-device 状态**的 retain（1M 设备各留一份 → 1M × 1~2KB ≈ 1~2GB），这就是设备影子的规模和职责——**改用影子，别建并行 retain 存储**。retain 存储只适合**少量 topic**（配置、广播、组级命令）。

### 4.3 更新路径（两种，推荐 A）

```text
A.（推荐）Kafka 消费者「retain-updater」服务：消费 raw log，对 retain=true 的消息 upsert/删 Redis。
   Broker 只在 Kafka header 保留 retain 位，【热路径零改动】，最契合 pointer-poor。
B. Broker 直写：retain=true → 投到 bounded "retain 更新" worker 队列 → 写 Redis。
   多一个 Broker 出向依赖，仅在不便加消费者服务时用。
```

### 4.4 订阅时投递

```text
SUBSCRIBE(filter) 到达 Broker：
  ├─ 精确 topic：Broker → bounded worker → Redis GET retain:{topic}
  │     命中 → 组 retained PUBLISH（retain 位置 1，QoS=min）→ 写该订阅者 conn（持有 fd，直接写）
  └─ 通配 filter（opt-in，仅 #14 已启用的产品）：
        → 调下行路由器：用 #14 匹配器把 filter 匹配 retain 存储的 topic 集 → 返回命中的 retained 消息
        → Broker 逐条写该订阅者 conn
```

要点：**匹配（通配）下放下行路由器，投递（写 conn）是 Broker 的活**——和 [#14 §2.4.4 egress 模型](./14.cloud-mqtt-gateway-downlink-topic-routing-design.md) 一致；投递复用现有下行写 + fencing。

### 4.5 数据流

```text
发布侧：
  device/cloud --PUBLISH retain=true--> Broker --Kafka--> retain-updater --upsert/DEL--> Redis(retain:{topic})

订阅侧：
  device --SUBSCRIBE--> Broker --(bounded)--> Redis GET / #14 匹配器
                          └── 命中 retained --写 conn(retain=1)--> device
```

## 5. 与红线 / 容量的关系

| 红线 / 约束 | 本方案如何满足 |
|---|---|
| §10 一阶段不做 retain | 本文是**可选能力**，默认关闭；启用是 opt-in 加法 |
| §2 Broker pointer-poor | retain 存储外置 Redis；Broker 无每-topic 状态 |
| §4 bounded | 订阅查询走 bounded worker/队列（同 auth）；retain 存储有 topic 数量上限 |
| §8 下行 fencing | 投递复用现有下行写路径 + fencing |
| 1M 容量 | retain 仅少量 topic；per-device 规模请用设备影子 |

---

## 6. 分阶段交付（按客户需求逐级启用）

```text
Phase 0（现状）：retain=true = no-op。先用设备影子满足"当前状态/目标配置"（§2）。
Phase 1（真 retain·精确 topic）：retain 存储(Redis) + retain-updater(Kafka 消费者)
        + Broker 订阅精确 topic GET 投递。覆盖"设备订自己的 retained 配置/命令"。
Phase 2（真 retain·通配）：复用 #14 匹配器做通配 retained 投递。仅对已开 #14 的产品。
不做：把 retained 消息存进 Broker 内存；为 per-device 状态建并行 retain 存储（用影子）；
      对未开 opt-in 的接入启用 retain。
```

## 7. 向客户介绍的要点小结

```text
1. 我们默认提供【设备影子】——当前状态查询 + 目标配置下发，带版本/审计，比 retain 更适合 IoT。
   您要的"连上就知道状态/拿到配置"，影子直接满足，无需开 retain。
2. 若您的设备固件/应用确实依赖 MQTT retain 线协议位，我们支持按需开启标准 retain
   （精确 topic 优先，通配按产品 opt-in），语义完整（覆盖/空载荷清除/订阅投递/重启持久/MQTT5 Retain Handling）。
3. retain 适合少量配置/广播类 topic；海量"每设备一份状态"的场景，我们建议用影子承载，
   二者可并存：影子管状态，retain 管少量需要线协议兼容的 topic。
```

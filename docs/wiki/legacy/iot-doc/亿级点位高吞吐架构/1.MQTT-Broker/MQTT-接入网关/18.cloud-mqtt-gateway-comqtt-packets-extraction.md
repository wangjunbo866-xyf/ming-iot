# 18. 基于 comqtt packets 的协议解析抽取方案

> 状态：决策记录 + 可执行计划
> 关联：[doc 7 红线](7.cloud-mqtt-gateway-implementation-red-lines.md)（pointer-poor）、[doc 15 本地快照认证](15.cloud-mqtt-credential-local-snapshot-design.md)
> 配套：[gnet 源码走查](reference/gnet/gnet-source-walkthrough.md)（§10.3 改造 1 流式解析、§8.5 socket、§8.7 worker pool）

## 18.1 背景与决策

### 18.1.1 为什么不深度定制 comqtt，而是「抽取 packets 当库」

曾评估「基于 comqtt 深度定制接入层」（换 gnet 网络层、重写认证、加 presence、pointer-poor 化）。评估结论：**不推荐深度定制 comqtt，推荐 mqtt-gateway 继续自身设计 + 抽取 comqtt 的 `mqtt/packets/` 协议解析库**。理由：

| 维度 | 深度定制 comqtt | mqtt-gateway + 抽取 packets |
|---|---|---|
| 网络模型 | ❌ comqtt 是 goroutine-per-conn（net.Conn 阻塞），换 gnet = 范式冲突，5-8 周 | ✅ mqtt-gateway 原生 gnet reactor（已研究透）|
| 内存/GC（50 万连接）| ❌ comqtt `Client` 含 string/map/net.Conn，pointer-rich，GC 每轮 100-200ms | ✅ pointer-poor session（红线 #2），GC 可控 |
| 协议解析 | ✅ 复用 comqtt packets | ✅ **抽取 comqtt packets 当库**（同等收益，零 comqtt 核心耦合）|
| 5 节点 200 万连接 | ❌ comqtt cluster 用 Raft 复制订阅树，写瓶颈 + 全量内存 ×5 | ✅ mqtt-gateway 无状态 + Redis presence，扩容加机器 |
| 总工作量 | 10-16 周（含 gnet 改造 + pointer-poor 重写）| 7-11 周（含抽取 packets 3-4 天）|

**核心洞察**：comqtt 的价值集中在 `mqtt/packets/`（协议编解码），这部分**几乎零耦合** comqtt 的 Client/Server/cluster（仅依赖一个 81 行的 `mempool` buffer 池）。把它当库抽取到 mqtt-gateway，**用 3-4 天获得 3-4 周的自写协议解析收益**，且不引入 comqtt 的网络模型/pointer-rich/Raft cluster 负担。

### 18.1.2 安全模块为什么不在抽取范围

「网络安全」是分层的，packets 只管协议字节流解析，不涉安全：

| 安全层 | 内容 | 归属 | 在抽取范围吗 |
|---|---|---|---|
| 传输安全（TLS）| 证书/加密握手 | NLB 卸载（[doc 13](network-defense/13.cloud-mqtt-gateway-tls-design.md)），不进 mqtt-gateway 进程 | ❌ |
| 连接认证 | client_id + secret 校验 | mqtt-gateway [doc 15 本地快照](15.cloud-mqtt-credential-local-snapshot-design.md) | ❌（独立模块）|
| 发布授权（ACL）| 设备能否 PUBLISH 某 topic | mqtt-gateway `internal/server/acl.go` | ❌（独立模块）|
| **协议解析** | MQTT 字节流 ↔ Packet 结构 | **comqtt packets 抽取** | ✅ **本方案** |

**packets 是纯协议库**：输入字节流输出 Packet 结构（反之亦然），不含 TLS/认证/ACL 任何安全逻辑。安全各层在 mqtt-gateway 的其他模块，各自独立演进。

## 18.2 可行性评估（基于源码核对）

### 18.2.1 依赖耦合：几乎零耦合

| 维度 | 评估结果 |
|---|---|
| 依赖 comqtt 的 Client/Server？ | ❌ **零依赖**。`grep comqtt` 确认 packets/ 不引用任何 Client/Server/cluster |
| 依赖 comqtt 其他包？ | ⚠️ 仅 1 个：`mqtt/mempool`（81 行 bytes.Buffer 池）|
| 依赖外部库？ | ❌ 零（纯标准库 bytes/encoding/binary/io）|
| mempool 能否一并抽取/替换？ | ✅ 81 行，连同抽取或用标准库 sync.Pool 替换 |

### 18.2.2 API 设计：Encode/Decode 是 buffer 模式

comqtt 的协议 API 是「给定完整 buffer，解码出 Packet」：

```go
// 编码：Packet → bytes.Buffer
func (pk *Packet) ConnectEncode(buf *bytes.Buffer) error
func (pk *Packet) PublishEncode(buf *bytes.Buffer) error

// 解码：[]byte → Packet（buf 是去掉固定头的 payload）
func (pk *Packet) ConnectDecode(buf []byte) error
func (pk *Packet) PublishDecode(buf []byte) error
```

**关键**：`Decode(buf []byte)` 接收的是**去掉固定头后的完整 payload buffer**，它**不处理**「读固定头 + 算 remaining length + 读 payload」这个流式过程——这部分由 mqtt-gateway 在 gnet 层做（§18.3.3）。

comqtt 提供两个可复用积木：
- `FixedHeader.Decode(hb byte)`：从 1 字节解码 type/qos/dup/retain
- `DecodeLength(b io.ByteReader)`：接收 `io.ByteReader`，逐字节读变长 remaining length（可用 `io.ByteReader` 适配 gnet，或自己写 5 行的 []byte 版）

### 18.2.3 与 gnet 流式解析（Peek/Discard）的契合度

gnet 的 OnTraffic 需要「Peek 探测 → 判断半包 → Discard 推进」的流式解析。comqtt 的 Decode 是 buffer 模式（给完整 buffer）。两者**可以配合**，需要一层适配：

```
gnet OnTraffic（流式）              comqtt Decode（buffer 模式）
─────────────────────────           ──────────────────────────
c.Peek(2) → 读固定头                
  ↓ 算 remaining length              FixedHeader.Decode(header[0])
  ↓ 判断整包是否到齐                 
c.Peek(totalLen) ───────────────────→ pk.PublishDecode(payload[headerLen:])
c.Discard(totalLen)                  ↓
                                     返回 Packet 结构
```

**适配点**：comqtt 的 `DecodeLength` 用 `io.ByteReader`，gnet 的 `c.Peek` 返回 `[]byte`。解法是自己写一个从 `[]byte` 解码变长整数的函数（5 行），不用 `DecodeLength`。

### 18.2.5 潜在问题

| 问题 | 严重度 | 说明 |
|---|---|---|
| Packet 结构含 string/slice | ⚠️ 中 | `TopicName string`、`Payload []byte` 等。但 Decode 后立即用完（解析+投递），不长期持有在 session 里，GC 影响可控 |
| **mempool 撑大缺陷** | **🔴 高** | comott 默认 `NewBuffer(0)` 无上限，`bytes.Buffer.Reset()` 不释放底层数组，一个大包永久撑大 buffer。**抽取时必须替换成 bsPool（见 §18.3.2）**，详见 §18.4.1 |
| Decode 假设 buffer 完整 | 🟡 中 | 需要在 gnet 层做半包判断（Peek + InboundBuffered），调 Decode 前确保 buffer 是整包 |
| **Decode 出的 []byte 仍是 inboundBuffer 切片** | **🔴 高** | `pk.Payload`/`pk.TopicName` 指向 Peek 返回的 inboundBuffer 内存，**不能跨 OnTraffic 持有**（红线 #3）。详见 §18.4.2 |
| MQTT 5.0 属性 | 🟢 低 | 第一阶段用 3.1.1，`Properties.Decode` 不调（ProtocolVersion=4 跳过）|
| License | 🟢 低 | comqtt 是 MIT，允许抽取，保留版权声明即可 |

**替换 mempool 引用**：packets 包里有对 comqtt mempool 的引用（`GetBuffer`/`PutBuffer` 用于 Encode）。要替换成 bspool：

```go
// 在 mqttpkt 包里新增一个 buffer.go，用 bspool 包装 *bytes.Buffer
package mqttpkt

import (
    "bytes"
    "mqtt-gateway/internal/bspool"
)

// GetBuffer 从 bspool 取一块 []byte，包装成 *bytes.Buffer 返回
func GetBuffer() *bytes.Buffer {
    // ⚠️ 不能直接复用 inboundBuffer 的 []byte（见 §18.4.2）
    b := bspool.Get(256)  // 初始 256，按需 grow
    return bytes.NewBuffer(b[:0])
}

// PutBuffer 归还（⚠️ bytes.Buffer 底层 []byte 必须是 bspool 来的才能归还）
func PutBuffer(buf *bytes.Buffer) {
    bspool.Put(buf.Bytes())
}
```

⚠️ **注意**：`bytes.NewBuffer(b[:0])` 后，buffer 的 grow 可能 `make` 新的底层数组（当 b 不够大时），那时 `buf.Bytes()` 的 cap ≠ 原始 b。Put 时 `bspool.Put` 会按当前 cap 分桶——**这其实规避了 comott mempool 的撑大问题**（grow 出来的大 buffer 归还到对应大桶，下次小请求取小桶，互不污染）。但如果 buffer 被 grow 到很大（比如几 MB），Put 后会占着大桶。**生产建议给 Encode 产物大小设上限**（比如 64KB，超过说明包异常）。

### 18.3.3 阶段 3：gnet OnTraffic 适配层（核心，1-2 天）

这是唯一需要动脑的部分——把 gnet 的流式 Peek/Discard 和 comqtt 的 buffer-mode Decode 衔接。

#### 步骤 3.1 变长整数解码（从 []byte）

```go
// internal/server/mqttread.go
package server

var ErrShortBuffer = errors.New("short buffer")

// decodeVarInt 从 buf 解码 MQTT 变长整数（remaining length）
// 返回 value + 编码占用的字节数（1-4）
func decodeVarInt(buf []byte) (value int, n int, err error) {
    var multiplier uint32
    for i := 0; i < len(buf); i++ {
        if multiplier >= 28 {
            return 0, 0, errors.New("malformed var int")
        }
        b := buf[i]
        value |= int(uint32(b&127) << multiplier)
        if value > 268435455 {
            return 0, 0, errors.New("var int overflow")
        }
        if b&128 == 0 {
            return value, i + 1, nil
        }
        multiplier += 7
    }
    return 0, len(buf), ErrShortBuffer  // buffer 不够，等下次
}
```

#### 步骤 3.2 gnet OnTraffic 的完整解析流程

```go
// internal/server/ontaffic.go（在 gnet 的 OnTraffic 里调）
func (h *handler) OnTraffic(c gnet.Conn) (action gnet.Action) {
    defer func() {
        if r := recover(); r != nil {   // §10.5 recover
            h.log.Error("OnTraffic panic", "err", r)
            action = gnet.Close
        }
    }()
    s := c.Context().(*session)
    atomic.StoreInt64(&s.lastActive, time.Now().UnixNano())   // §10.7 保活

    for {  // 一次 OnTraffic 可能含多个包，循环处理
        act, err := h.parseOne(c, s)
        if err == ErrShortBuffer {
            return gnet.None  // 半包，等下次 OnTraffic
        }
        if err != nil {
            return gnet.Close  // 协议错误，断连
        }
        if act == gnet.Close {
            return gnet.Close
        }
        // act == gnet.None：继续循环处理下一个包
    }
}

func (h *handler) parseOne(c gnet.Conn, s *session) (gnet.Action, error) {
    // 1. Peek 至少 2 字节（1 type + 1 remaining length 起始）
    header, err := c.Peek(2)
    if err != nil {
        return gnet.None, ErrShortBuffer
    }

    // 2. 解码固定头 type 字节
    var fh mqttpkt.FixedHeader
    if err := fh.Decode(header[0]); err != nil {
        return gnet.Close, err
    }

    // 3. 解码变长 remaining length（从 []byte，不用 ByteReader）
    remaining, varLen, err := decodeVarInt(header[1:])
    if err != nil {
        return gnet.None, err
    }
    headerLen := 1 + varLen

    // 4. 判断整包是否到齐
    totalLen := headerLen + remaining
    if c.InboundBuffered() < totalLen {
        return gnet.None, ErrShortBuffer  // 半包
    }

    // 5. Peek 整包（⚠️ comqtt Decode 假设 buffer 完整，这里保证）
    full, err := c.Peek(totalLen)
    if err != nil {
        return gnet.None, ErrShortBuffer
    }
    payload := full[headerLen:]  // 去掉固定头

    // 6. 用 comqtt 的 Decode 解码 payload
    var pk mqttpkt.Packet
    pk.FixedHeader = fh
    pk.ProtocolVersion = s.protoVersion  // 4=3.1.1
    switch fh.Type {
    case mqttpkt.Connect:
        err = pk.ConnectDecode(payload)
    case mqttpkt.Publish:
        err = pk.PublishDecode(payload)
    case mqttpkt.Puback:
        err = pk.PubackDecode(payload)
    case mqttpkt.Subscribe:
        err = pk.SubscribeDecode(payload)
    case mqttpkt.Unsubscribe:
        err = pk.UnsubscribeDecode(payload)
    case mqttpkt.Pingreq, mqttpkt.Pingresp:
        // 无 payload
    case mqttpkt.Disconnect:
        err = pk.DisconnectDecode(payload)
    default:
        return gnet.Close, fmt.Errorf("unknown packet type %d", fh.Type)
    }
    if err != nil {
        return gnet.Close, err
    }

    // 7. 推进缓冲区（消费这个包）⚠️ 必须在 Decode 之后
    c.Discard(totalLen)

    // 8. 处理（分发到业务）
    return h.dispatch(c, s, &pk), nil
}
```

#### 步骤 3.3 dispatch 到业务

```go
// internal/server/dispatch.go
func (h *handler) dispatch(c gnet.Conn, s *session, pk *mqttpkt.Packet) gnet.Action {
    switch pk.FixedHeader.Type {
    case mqttpkt.Connect:
        return h.handleConnect(c, s, pk)   // §10.8 doc 15 认证 + presence
    case mqttpkt.Publish:
        return h.handlePublish(c, s, pk)   // ACL + raw log 投递（§10.6）
    case mqttpkt.Pingreq:
        return h.writePingresp(c)          // PINGRESP
    case mqttpkt.Disconnect:
        return gnet.Close
    }
    return gnet.None
}
```

### 18.3.4 阶段 4：编码响应（用 comqtt 的 Encode）

```go
// internal/server/encode.go
func (h *handler) writeConnack(c gnet.Conn, sessionPresent bool, code byte) error {
    buf := mqttpkt.GetBuffer()
    defer mqttpkt.PutBuffer(buf)

    var resp mqttpkt.Packet
    resp.ProtocolVersion = 4
    resp.FixedHeader.Type = mqttpkt.Connack
    resp.SessionPresent = sessionPresent
    resp.ReasonCode = code
    if err := resp.ConnackEncode(buf); err != nil {
        return err
    }

    // ⚠️ AsyncWrite 异步：buf.Bytes() 是池的切片，不能立即 PutBuffer
    //    解法：copy 一份给 AsyncWrite（多一次拷贝但安全）
    out := make([]byte, buf.Len())
    copy(out, buf.Bytes())
    return c.AsyncWrite(out, nil)
}

func (h *handler) writePingresp(c gnet.Conn) gnet.Action {
    // PINGRESP 固定 2 字节 {0xD0, 0x00}，直接发，不用池
    _ = c.AsyncWrite([]byte{0xD0, 0x00}, nil)
    return gnet.None
}
```

**⚠️ buffer 池 + AsyncWrite 的陷阱**：comqtt 的 Encode 写到 buffer 池的 buffer，`buf.Bytes()` 是池的切片。`c.AsyncWrite` 是异步（投递到 reactor 后才真正发），**不能立即 `PutBuffer`**——否则池复用会覆盖数据。两个解法：

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A（推荐）** | `copy` 一份给 AsyncWrite | 多一次拷贝（CONNACK/PUBACK 几十字节，可忽略），简单安全 |
| B | AsyncWrite 的 callback 里 PutBuffer | 在 reactor 回调里释放，省拷贝但要管理生命周期 |

## 18.4 ⚠️ buffer 生命周期陷阱（抽取时最易踩的坑）

抽取 comqtt packets 后会遇到两个 buffer 相关的陷阱，都是高频踩坑点。

### 18.4.1 comqtt mempool 的撑大缺陷（必须替换）

comqtt 的 `mqtt/mempool`（bufpool.go）用 `sync.Pool` 包 `*bytes.Buffer`，默认 `NewBuffer(0)`（无上限）：

```go
// comqtt mempool 的缺陷根源
var bufPool = NewBuffer(0)   // max=0，无容量上限

func (b *Buffer) Put(x *bytes.Buffer) {
    x.Reset()    // ⚠️ bytes.Buffer.Reset() 只清读写指针，不释放底层数组！
    b.pool.Put(x)
}
```

`bytes.Buffer.Reset()` 的行为（标准库）：**只把读写位置归零，底层的 `buf []byte` 数组保留不动**。所以：

```
一个 buffer 写入 1MB 数据 → 底层 buf 扩到 1MB
Put → Reset（buf 仍 1MB）→ 归还 pool
Get → 拿到这个 1MB 的 buffer
写 100 字节 → 底层 buf 还是 1MB（没缩）→ 归还
下一个 Get → 又拿到 1MB buffer
```

**只要出现过一次大包，那个 buffer 就永久 1MB，之后所有复用它的小操作都占着 1MB**。sync.Pool 里会积累「被撑大的胖 buffer」，内存随大包数量单调增长。

**gnet bsPool 为什么不会撑大**：gnet 的 `pkg/pool/byteslice`（byteslice.go）用 **32 个 sync.Pool 按容量分桶**（2 的幂），请求大小映射到对应桶：

```go
// gnet bsPool 的分桶（不会污染）
请求 100 字节 → idx=7（桶容量 128）→ 取桶 7
请求 500 字节 → idx=9（桶容量 512）→ 取桶 9
请求 1MB     → idx=20（桶容量 1<<20）→ 取桶 20
// 各桶独立，大 []byte 进大桶，小请求取小桶，互不污染
```

**替换方案**（§18.3.2 已落地）：不抽取 comqtt mempool，改抽 gnet 的 `pkg/pool/byteslice`（56 行，零依赖）到 `mqtt-gateway/internal/bspool/`。用 `bspool.Get(size)` / `bspool.Put(buf)` 代替 comqtt 的 `GetBuffer`/`PutBuffer`。

**性能对比**：

| 维度 | comqtt mempool（sync.Pool 包 `*bytes.Buffer`）| gnet bsPool（32 桶，存 `*byte`）|
|---|---|---|
| 复用粒度 | 整个 `*bytes.Buffer` 结构体 | 裸 `[]byte` 底层数组指针 |
| 大小匹配 | ❌ 无分桶，大小错配 | ✅ 32 桶按 2 的幂 |
| 撑大问题 | ⚠️ 会撑大 | ✅ 不会（各桶独立）|
| 装箱开销 | ❌ 零（存的是指针，指针进 any 不装箱）| ❌ 零（`unsafe.SliceData` 取裸指针）|
| GC 扫描 | 扫 1 个指针（指向 Buffer，需递归扫其内部 slice header）| 扫 1 个裸指针（直接到底层数组，无中间结构）|
| 额外堆分配 | 0（指针复用）| **0**（指针复用，无装箱）|

> ⚠️ **纠正一个常见误解**：之前文档说「comqtt mempool sync.Pool 存 any 会装箱」——**这是错的**。comqtt 存的是 `*bytes.Buffer`（指针），指针塞进 `any` **不装箱**（指针本身是 uintptr，能直接放进 interface.val）。comqtt mempool 的真正缺陷是**撑大问题**（Reset 不释放底层数组），不是装箱。下面详解「装箱」和 gnet 为什么用 `unsafe.SliceData`。

#### 「零装箱」是什么意思（unsafe.SliceData 为什么用）

##### 背景知识 1：slice 在内存里是 24 字节的 header

Go 的 `[]byte`（slice）不是裸内存，是运行时的三字段结构：

```
[]byte = struct {
    data *byte   // 8 字节：指向底层数组的指针
    len  int     // 8 字节：当前长度
    cap  int     // 8 字节：容量
}
// 总共 24 字节
```

##### 背景知识 2：sync.Pool 存取用 any

`sync.Pool` 的 `Get()/Put()` 签名是 `any`（即 `interface{}`）：

```go
type Pool struct {
    New func() any
}
func (p *Pool) Get() any
func (p *Pool) Put(x any)
```

`interface{}` 内部是「类型指针 + 数据指针」的结构。把一个**非指针类型**（比如 `[]byte`、`int`、`struct`）塞进 `any`，Go 编译器要做**装箱（boxing）**：在堆上分配临时对象拷贝值，用完后等 GC 回收。

##### 三种存法对比（含反例）

| 存法 | 存什么 | 装箱？ | GC 扫描 | 额外堆分配 |
|---|---|---|---|---|
| **comqtt mempool** | `*bytes.Buffer`（指针）| ❌ 零装箱 | 扫 1 指针（指向 Buffer，需递归扫其内部 slice）| 0 |
| ❌ **朴素存 []byte（反例）** | `[]byte`（24 字节 slice header）| ✅ **装箱**（堆分配 slice header 副本）| 扫 slice header 的 data 指针 | **1 次**（装箱的 header 副本）|
| **gnet bsPool** | `unsafe.SliceData(buf)` 返回的 `*byte`（8 字节裸指针）| ❌ **零装箱** | 扫 1 裸指针（直接到底层数组，无中间结构）| **0** |

##### 为什么「存 []byte 会装箱，存 *byte 不装箱」

**反例：直接存 []byte（gnet 没这么写，演示用）**

```go
// ❌ 反例：把 slice 直接塞进 any
pool.Put(buf)   // buf 是 []byte（24 字节的 slice header）
```

把 `[]byte` 塞进 `any` 会装箱：
1. 编译器在堆上分配一个 24 字节对象，把 slice header（data/len/cap）拷进去
2. `interface.val` 指向这个堆对象
3. Get 时从这个堆对象再拷贝出来
4. 这个 24 字节堆对象要 GC 扫描（它含 `data *byte`，GC 要追踪）

→ **多一次堆分配 + GC 跟踪负担**。

**gnet bsPool：存 *byte 裸指针**

```go
// gnet byteslice.go:71（存）
p.pools[idx].Put(unsafe.SliceData(buf))   // unsafe.SliceData 返回 *byte

// gnet byteslice.go:52（取）
ptr, _ := p.pools[idx].Get().(*byte)      // 取 *byte
return unsafe.Slice(ptr, 1<<idx)[:size]   // 指针还原成 []byte
```

`unsafe.SliceData(buf)` 返回 slice 底层数组的首元素指针（就是 slice header 里的 `data` 字段，8 字节）。

把 `*byte` 塞进 `any` **零装箱**：指针本身是 uintptr，能直接放进 `interface.val`，无需堆分配。

取出来时是 `*byte`，`unsafe.Slice(ptr, cap)` 把指针还原成 `[]byte`（在栈上构造 slice header，不逃逸）。

**关键**：gnet 只存「底层数组的首地址」（8 字节裸指针），**丢弃了 slice 的 len/cap**（Get 时按桶约定重新还原）。这样不存 slice header（省 16 字节 + 避免装箱），GC 只看到一个裸指针，扫描成本最低。

##### 存丢 len/cap，取靠「分桶约定」还原

`unsafe.SliceData(buf)` 存的时候**只留首地址，丢掉 len/cap**——那取出来怎么还原成完整的 `[]byte`？答案是**靠分桶约定**：同一个桶里的所有 slice 容量都是 `1<<idx`，所以 cap 由桶编号隐含，不需要存。

**存的路径**（Put，byteslice.go:60-72）：

```go
func (p *Pool) Put(buf []byte) {
    size := cap(buf)
    idx := index(uint32(size))           // ① 算 buf 属于哪个桶
    if size != 1<<idx { idx-- }          // ② 非 2 的幂降桶（安全保证，见下）
    p.pools[idx].Put(unsafe.SliceData(buf))  // ③ 只存首地址，丢掉 len/cap
}
```

**取的路径**（Get，byteslice.go:44-56）：

```go
func (p *Pool) Get(size int) []byte {
    idx := index(uint32(size))           // ① 算请求大小属于哪个桶
    ptr, _ := p.pools[idx].Get().(*byte) // ② 取出裸指针
    if ptr == nil {
        return make([]byte, size, 1<<idx) // pool 空，新建（cap = 桶容量）
    }
    return unsafe.Slice(ptr, 1<<idx)[:size]  // ③ 用桶约定还原 cap，截到请求 size
}
```

**「丢-还原」时序**：

```
Put([]byte{cap=512}):
  idx = index(512) = 9              ← 算桶
  ptr = SliceData(buf)              ← 取首地址，丢掉 len=?? cap=512
  pools[9].Put(ptr)                 ← 存进桶 9
  （桶 9 的约定容量 = 1<<9 = 512）

Get(size=400):
  idx = index(400) = 9              ← 算桶（400 → 桶 9，因为 1<<9=512 ≥ 400）
  ptr = pools[9].Get()              ← 取出指针
  unsafe.Slice(ptr, 512)            ← ⭐ 用桶约定 512 重建 {data:ptr, len:512, cap:512}
  [:400]                            ← 截到请求 400 → {data:ptr, len:400, cap:512}
```

**核心洞察**：len/cap 全程靠「桶约定」还原，不需要存。存只有 `*byte`（8 字节），取时用 `1<<idx` 在栈上重建 slice header（24 字节，不逃逸到堆）。

##### 安全保证：非 2 的幂降桶（防越界）

存的时候有个关键检查（Put 第 66-68 行）：

```go
idx := index(uint32(size))
if size != 1<<idx {   // 不是 2 的幂
    idx--              // 往下降一桶
}
```

为什么？假设存一个 `make([]byte, 0, 300)`（cap=300，不是 2 的幂）：

- `index(300) = 9`（2^9=512 ≥ 300）
- 如果存进桶 9（约定 512），取出时 `unsafe.Slice(ptr, 512)` 会访问 ptr 后 **512 字节**
- 但实际底层数组只分配了 **300 字节**，多出的 212 字节是**越界内存**（读到别人的数据，写则 corruption）

**降到桶 8（256 ≤ 300）**，保证 `unsafe.Slice(ptr, 256)` 只访问 ptr 后 256 字节，在 300 字节的实际分配范围内，安全。

**这是 bsPool 的安全保证**：存进桶 idx 的 slice，保证它的实际 cap ≥ `1<<idx`。Put 时「非 2 的幂降桶」就是这个目的。代价是浪费一点空间（300 字节的 slice 只能用 256），但换来零越界。

##### 对比标准库 net/http 的 buffer 池

Go 标准库 `net/http` 也用 sync.Pool 复用 buffer，但更简单：

```go
// net/http/server.go
var bufPool = sync.Pool{
    New: func() interface{} {
        return make([]byte, 0, initialBufferSize)  // 固定 4KB
    },
}
buf := bufPool.Get().([]byte)   // 存取都是 []byte（会装箱）
```

对比：

| 维度 | 标准库 net/http | gnet bsPool |
|---|---|---|
| 存什么 | `[]byte`（slice header，**会装箱**）| `*byte` 裸指针（**零装箱**）|
| 容量匹配 | 固定 4KB（小请求浪费，大请求要 grow）| 32 桶按 2 的幂（大小匹配，不浪费）|
| 还原 len/cap | 容量固定，取出来 cap 就是 4KB | 靠桶约定 `1<<idx` 还原 |

**gnet bsPool 是标准库 sync.Pool 的「高性能 + 多大小」增强版**：零装箱（存裸指针）+ 分桶（不同大小不浪费）+ 桶约定还原（不用存 len/cap）。三点组合是 gnet 字节池的设计精髓。

##### 源码注释印证

gnet byteslice.go:69-70 的注释：

```
// Store the pointer to the underlying array instead of the pointer to the slice itself,
// which circumvents the escape of buf from the stack to the heap.
```

「escape from the stack to the heap」（从栈逃逸到堆）和「装箱」是相关概念：`pool.Put(buf)` 把 slice 塞进 any → 装箱 → buf 逃逸到堆（any 持有它）；而 `pool.Put(unsafe.SliceData(buf))` 只存裸指针，buf 本身不逃逸，少一次堆分配。

##### 小结：gnet bsPool 三重优势

gnet bsPool 相比 comqtt mempool 的优势是**三点叠加**，不止「装箱」一项：

1. **分桶不撑大**（32 桶按 2 的幂，大小隔离）——comqtt 单 pool 会撑大
2. **零装箱**（存 `*byte` 裸指针，不存 slice header）——朴素存 `[]byte` 会装箱
3. **最少 GC 扫描**（裸指针直达底层数组，无中间结构递归扫）

comqtt mempool 的真正缺陷是第 1 点（撑大），第 2 点它也是零装箱（存的是 `*bytes.Buffer` 指针）。gnet bsPool 三点全优，是更先进的字节池设计。

##### mqtt-gateway 的 bspool 为什么独立于 gnet 的 builtinPool

gnet 进程内有一个**全局唯一**的 `builtinPool`（`pkg/pool/byteslice` 的包级 `var builtinPool Pool`，:26）。inboundBuffer 的 ring.buf（grow/new 时）、outboundBuffer 的 listBuffer node.buf，都从它取还。doc 18 §18.3.2 设计的是 mqtt-gateway **复制一份** byteslice 包到 `internal/bspool/`，独立于 gnet 的 builtinPool。为什么独立而不是共用？

**直觉上以为**：「两者大小不同（gnet 几 KB，业务几百字节），复用率低」——**这个理由是错的**。实际上两者大小高度重叠：

```
gnet inboundBuffer 读的 PUBLISH 包 ≈ 1-3KB（遥测数据主体）
mqtt-gateway 的 Kafka payload copy ≈ 1-2KB（同一个 PUBLISH 的 payload）
→ 两者都落在 bsPool 桶 11（容量 2KB）
```

**真正的理由**：gnet **频繁进出 bsPool 的热路径（inboundBuffer）实际绕开了 bsPool**。inboundBuffer 的 ring.Buffer 在「读完即归还」时归还的是 **rbPool**（复用整个 ring.Buffer 对象，含 buf），不是 bsPool。只有 ring.grow（扩容）和 ring.New（rbPool 空时新建）才直接进出 bsPool。所以：

| 路径 | 频率 | 用 bsPool 吗 |
|---|---|---|
| inboundBuffer 读 PUBLISH（热路径）| 极高（每包一次）| ❌ 走 **rbPool**（ring 对象复用），buf 跟着 ring 走，不单独进 bsPool |
| inboundBuffer grow 扩容 | 低（包大小稳定后不再 grow）| ✅ 但低频 |
| outboundBuffer listBuffer 积压 | 低（EAGAIN 异常路径才进）| ✅ 但低频 |
| **mqtt-gateway Kafka payload copy** | **高（每 PUBLISH 一次）** | ✅ **这是 bsPool 的主要使用者** |

**结论**：gnet 的 bsPool 主要被 outboundBuffer 积压（低频异常路径）和 inboundBuffer grow（低频）使用，**不是热路径**。mqtt-gateway 的 Kafka payload copy 才是 bsPool 的真正高频使用者。两者共用一个池，gnet 那边贡献的 buf 极少，**复用率提升几乎为零**。

**独立 bspool 的收益**（解耦优先）：

1. **不依赖 gnet 内部 API**：`byteslice.Get/Put` 虽然导出，但属于 gnet 内部实现细节，未来版本可能改（去导出/改行为）。独立一份零耦合风险。
2. **可控**：mqtt-gateway 的 bspool 容量/桶配比可独立调（比如针对 payload 大小分布优化），不影响 gnet。
3. **复用损失极小**：如上分析，gnet 那边 bsPool 本来就不忙，共用收益≈0。

**一句话**：独立 bspool 不是因为「大小不同」（两者都是 1-2KB，高度重叠），而是因为「gnet 的热路径走 rbPool 不走 bsPool」，所以共用对复用率贡献极小，独立的解耦收益更实在。

### 18.4.2 ⚠️ Decode 出的 []byte 是 inboundBuffer 切片，不能跨 OnTraffic 持有（红线 #3）

这是最隐蔽的陷阱。comqtt 的 `Decode(buf []byte)` 从你传入的 buffer 里**取切片**（不 copy）：

```go
// comqtt PublishDecode（简化）
func (pk *Packet) PublishDecode(buf []byte) error {
    // ...
    pk.Payload = buf[offset:offset+payloadLen]   // ⚠️ 指向 buf 的子切片！
    return nil
}
```

而你传给 Decode 的 `payload` 来自 `c.Peek(totalLen)[headerLen:]`——**c.Peek 返回的是 inboundBuffer 内部 rb.buf 的子切片**（gnet ring_buffer.go:71-104，[walkthrough §10.6] 讲过）。

**所以 pk.Payload / pk.TopicName 等所有 []byte/string 字段，都指向 inboundBuffer 的临时内存**。这块内存的生命周期：

```
OnTraffic:
  full, _ := c.Peek(totalLen)       // full 指向 inboundBuffer 的 buf
  pk.PublishDecode(full[headerLen:]) // pk.Payload 指向同一块内存
  c.Discard(totalLen)                // 推进读指针（buf 数据还在，但"可被覆盖"）

OnTraffic 返回后，reactor 继续处理：
  下一个包的 unix.Read → 覆盖 inboundBuffer 的 buf
  → pk.Payload 指向的内存被新数据覆盖！
  或 conn 关闭 → inboundBuffer 归还 rbPool → buf 被 bsPool 复用给别的 conn
```

**这是 doc 7 红线 #3「禁止 queue 里引用大 read buffer 的 subslice」的物理根源**。

#### 正确做法：跨 OnTraffic 使用前必须 copy

##### 场景 1：PUBLISH payload 异步发 Kafka（最常见的踩坑点）

```go
func (h *handler) handlePublish(c gnet.Conn, s *session, pk *mqttpkt.Packet) gnet.Action {
    // ❌ 错误：直接持有 pk.Payload 异步发送
    // h.kafkaClient.SendAsync(pk.Payload)   // pk.Payload 是 inboundBuffer 切片！
    // c.Discard(totalLen)                    // 推进后 pk.Payload 内存被覆盖

    // ✅ 正确：copy 到独立 buffer（方案 A）
    data := make([]byte, len(pk.Payload))
    copy(data, pk.Payload)
    h.kafkaClient.SendAsync(data)   // data 是独立内存，安全
    return gnet.None
}
```

##### 场景 2：用 bspool 复用，减少 make 开销（方案 B，更优）

```go
func (h *handler) handlePublish(c gnet.Conn, s *session, pk *mqttpkt.Packet) gnet.Action {
    // 从 bspool 取一块（按 payload 大小分桶）
    data := bspool.Get(len(pk.Payload))
    copy(data, pk.Payload)   // copy 进去

    // 异步发送 Kafka，回调里归还 pool
    h.kafkaClient.SendAsync(data, func() {
        bspool.Put(data)   // Kafka 发送完成（含重试）后才归还
    })
    return gnet.None
}
```

⚠️ **Kafka 回调的约束**：`bspool.Put(data)` 必须在「Kafka 完全处理完（含重试成功或最终失败）之后」调，否则重发时数据已被覆盖。如果 Kafka 客户端不支持完成回调，用方案 A（make + 让 GC 管）更安全。

#### 不能复用 inboundBuffer 的底层 []byte

注意：**不能**直接把 `pk.Payload`（指向 inboundBuffer）丢给 Kafka 不 copy。即使你想「Kafka 发完再归还 inboundBuffer」，也不行——因为：
1. inboundBuffer 的归还时机由 reactor 控制（OnTraffic 返回后可能立刻被复用），你无法保证 Kafka 先于 reactor 的下一次 read 完成
2. inboundBuffer 的 buf 来自 gnet 内部的 rbPool，跨 goroutine 归还会破坏 gnet 的内存管理

**唯一安全的方式：copy 到独立内存（make 或 bspool），让 copy 出来的内存跟随 Kafka 的生命周期**。

### 18.4.3 Encode 的 buffer 也要注意 AsyncWrite 异步

§18.3.4 的 writeConnack 用 bspool 取 buffer encode，然后 copy 给 AsyncWrite。同样的陷阱：

```go
buf := bspool.Get(64)           // bspool 来的
resp.ConnackEncode(bytes.NewBuffer(buf[:0]))  // encode 进 buf
out := make([]byte, buf.Len())  // ⚠️ 必须 copy
copy(out, buf)
bspool.Put(buf)                 // 归还后 out 仍安全
c.AsyncWrite(out, nil)          // 异步发 copy 出来的
```

如果直接 `c.AsyncWrite(buf, nil)` 然后 `bspool.Put(buf)`，AsyncWrite 还没真正发（在 reactor 队列里），buf 已归还池被复用 → 数据被覆盖。**Encode 产物 copy 后再 AsyncWrite，是安全范式**。

## 18.8 与 mqtt-gateway 其他模块的关系

```
┌─ mqtt-gateway 进程 ────────────────────────────────────────────┐
│                                                                 │
│  gnet reactor（OnTraffic）                                      │
│    ↓ Peek/Discard 流式                                          │
│  mqttpkt（本方案抽取）                                          │
│    ├─ ConnectDecode/PublishDecode → Packet 结构                 │
│    └─ ConnackEncode/PubackEncode → bytes                        │
│    ↓ dispatch                                                   │
│  业务模块（mqtt-gateway 自有，不抽取 comqtt）                    │
│    ├─ 认证（doc 15 本地快照，pointer-poor）                     │
│    ├─ ACL（internal/server/acl.go）                             │
│    ├─ presence（doc 2 Redis CAS + fencing）                     │
│    ├─ raw log 投递（doc 3 → Kafka）                             │
│    └─ session（pointer-poor，红线 #2）                          │
│                                                                 │
│  不引入：comqtt Client / Server / hook / cluster / topics 树    │
└─────────────────────────────────────────────────────────────────┘
```

**抽取 packets 是高收益低风险的操作**：3-4 天获得完整 MQTT 协议解析（含 5.0 属性），不引入 comqtt 的网络模型/pointer-rich/Raft cluster 负担。mqtt-gateway 保留全部设计优势（gnet、pointer-poor、本地快照认证、Redis presence、raw log 直转 Kafka）。

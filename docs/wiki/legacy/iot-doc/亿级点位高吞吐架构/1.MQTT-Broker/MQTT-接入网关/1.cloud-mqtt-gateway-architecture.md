# 百万级设备 MQTT 接入层架构设计

> 目标：支撑公司自产百万级逆变器设备接入。设备白天上线、夜间断电离线，每 5 分钟上传一次 Modbus 二进制全量数据，约 700 个点位。  
> 核心思路：不要实现一个通用 MQTT Broker 集群，而是实现一个面向逆变器遥测与控制的 **极简 MQTT 接入集群**。

---

## 1. 结论摘要

当前场景适合自研，但边界必须收敛：

```text
目标：百万逆变器 telemetry ingress + 低频南向控制
不是：通用 MQTT Broker 替代品
```

推荐架构：

```text
逆变器设备
  |
MQTT Gateway 集群
  |
Durable Raw Log，例如 Kafka / Redpanda / JetStream
  |
Modbus Decoder
  |
时序库 / OLAP / 告警 / 设备影子 / 报表
```

### 1.1 与 NATS MQTT 的关系

本设计中的 `MQTT Gateway` 是一层公司自研的专用 MQTT 接入层，不建议生产环境让百万设备直接连接 NATS Server 的 MQTT listener。

推荐关系是：

```text
设备
  -> 自研 MQTT Gateway
  -> Durable Raw Log Appender
  -> Decoder 消费 raw log
```

即：

```text
MQTT Gateway 负责设备接入语义。
Kafka / Redpanda 负责 durable raw log（**仅上行遥测**；下行不走 Kafka）。
Redis 负责 device presence + broker registry/lease（含 Broker 的 gRPC 地址）+ 认证缓存（L2）。
下行单播走 Command Service → gRPC 直连目标 Broker（查 presence + broker registry 寻址），可达性由 Command Service 的 DB 状态机拥有。
NATS 仅用于 PoC（自带 MQTT listener 可快速验证设备行为，不用于生产接入）。
```

NATS 自带 MQTT 支持可以用于 PoC，例如快速验证设备 MQTT 行为、topic、QoS 与 JetStream 消费链路。但生产架构不建议基于 NATS MQTT 组件二开，也不建议 fork nats-server。

详细设计见：

- [云端 MQTT 接入 Broker 与 Raw Log Appender 详细设计](./3.cloud-mqtt-gateway-raw-log-design.md)
- [云端 MQTT 接入 Broker CONNECT 认证设计](./5.cloud-mqtt-connect-auth-design.md)
- [云端 MQTT 接入 Broker 成本分析](./4.cloud-mqtt-gateway-cost-analysis.md)
- [云端 MQTT 接入层网络攻击防范设计](./network-defense/9.cloud-mqtt-gateway-network-attack-defense.md)

南向控制不依赖 Broker 之间广播，也不依赖 MQTT 集群内部转发，而是使用：

```text
device_id -> 当前所在 broker_id
```

即：

```text
Command Service
  -> 查询 Presence Registry
  -> 找到设备当前连接在哪个 MQTT Gateway
  -> gRPC 直连目标 Broker 精准投递（不经 Kafka/NATS）
  -> Broker 通过本地 MQTT 连接下发给设备
```

### 1.2 系统定位：接入网关，不是 pub/sub 总线（上下行不对称）

本系统是**逆变器遥测接入网关**，不是通用 pub/sub 消息总线。上行与下行是**两条独立、不对称的边**：

- **上行**：设备 publish 遥测 → Broker → Kafka raw log。消费者是**后端 / Kafka 管道，不是 MQTT 订阅者**——Broker 不把上行 fan-out 给其它客户端。
- **下行**：云端发起 → Command Service 路由 → 定向投递到目标设备。

由此有三条必须明确的边界：

```text
1. 不支持 device-to-device：设备 A 的消息不经 Broker 直达设备 B；设备间联动走云中转
   （A → Kafka → 后端 → Command Service → B）。
2. 跨设备 SUBSCRIBE 被 ACL 禁止：客户端只能订自己的命令 topic →
   不存在「订了别人的数据却收不到」的破契约（设计自洽，非缺陷）。
3. 遥测的「订阅者」是 Kafka：看板/集成方消费实时遥测应订 Kafka，而非用 MQTT 订阅设备 topic。
```

这与 Azure IoT Hub（明确不支持 D2D）、AWS IoT（设备数据走 Rules Engine 进后端，而非 MQTT 订阅 fan-out）的托管 IoT 平台形态一致，是刻意取舍。

> 详细说明（为什么不是缺陷、云中转模式、与下行 topic 路由的关系、命名风险）见 [#14 下行 Topic 路由设计](./14.cloud-mqtt-gateway-downlink-topic-routing-design.md) §2.4。

## 2. 业务背景

### 2.1 设备特征

- 设备类型：光伏逆变器。
- 在线模式：太阳出来后上线，太阳下山后断电离线。
- 上报周期：每 5 分钟一次。
- 上报内容：Modbus 二进制全量数据。
- 点位数量：约 700 个点位。
- 上行特征：周期性、全量快照、可幂等、可容忍少量延迟。
- 下行特征：低频控制命令，需要投递到当前在线设备。

### 2.2 核心挑战

真正困难的不是单纯的 MQTT 协议，而是：

1. 日出连接风暴。
2. 5 分钟周期上报风暴。
3. 日落断连风暴。
4. 百万连接下的内存与 FD 管理。
5. QoS1 的重复消息与幂等。
6. 南向命令如何路由到持有设备连接的 Broker。
7. Broker、日志系统、解码器、时序库之间的削峰与解耦。
8. 设备固件异常导致的突发流量。

## 3. 设计目标与非目标

### 3.1 设计目标

| 目标 | 描述 |
|---|---|
| 百万级连接 | 支撑 100 万级设备在线连接 |
| 高可用接入 | 任意 Ingress Broker 故障不影响整体接入能力 |
| 高吞吐上行 | 支撑周期性 Modbus 二进制全量数据上传 |
| QoS0/QoS1 | 上行支持 QoS0 和 QoS1 |
| 南向定向下发 | 支持平台命令下发到指定在线设备 |
| 可削峰 | Broker 与解码、存储、告警解耦 |
| 可幂等 | 上行与下行都允许重试、去重 |
| 易扩容 | 接入节点可横向扩容 |
| 易运维 | 明确限流、熔断、观测指标和故障边界 |

### 3.2 非目标

第一阶段不做：

| 非目标 | 原因 |
|---|---|
| 通用 MQTT Broker | 场景是逆变器专用，不需要完整通用能力 |
| QoS2 | 实现复杂，业务不需要 exactly-once |
| Retain Message | 遥测全量快照不应使用 retain |
| MQTT 持久会话 | 百万设备日夜上下线会造成巨大状态负担 |
| 离线消息堆积在 Broker | 离线命令应由 Command Service 管理 |
| 通用 wildcard subscription | 上行遥测不依赖通用订阅模型 |
| 每设备内部动态订阅 | 日出日落会造成百万级 subscribe/unsubscribe 抖动 |
| Broker 内解码 700 点位 | Broker 只做协议与转发，解码异步化 |
| Broker 内写时序库 | 避免 DB 抖动反向拖垮接入层 |
| 生产环境直接使用 NATS MQTT 接设备 | 需要自定义 ACK、presence、限流、鉴权和背压语义 |
| 基于 NATS MQTT 组件二开 | nats-server MQTT 模块不是业务 Broker SDK，fork 维护成本高 |

## 4. 容量粗算

假设：

```text
设备数：1,000,000
上报周期：300 秒
payload：按 1.5KB / 3KB / 5KB 三档估算
白天在线窗口：12 小时
```

平均上报速率：

```text
1,000,000 / 300 ≈ 3333 条/秒
```

峰值取决于设备是否打散上报。

| 场景 | 消息速率 | 3KB payload 下入口流量 |
|---|---:|---:|
| 均匀打散到 5 分钟 | 3333 msg/s | 约 10 MB/s |
| 全部挤在 1 分钟 | 16667 msg/s | 约 50 MB/s |
| 全部挤在 10 秒 | 100000 msg/s | 约 300 MB/s |
| 全部挤在 1 秒 | 1000000 msg/s | 约 3 GB/s |

如果 raw log 使用 JetStream / Kafka / Redpanda 三副本持久化，后端日志集群实际写入压力约为入口 raw 流量的 3 倍，不含协议头、索引、batch、压缩和副本复制开销：

| 场景 | raw 入口流量 | 三副本日志写入量 | 判断 |
|---|---:|---:|---|
| 均匀打散到 5 分钟 | 约 10 MB/s | 约 30 MB/s | 正常规划下可承载 |
| 全部挤在 1 分钟 | 约 50 MB/s | 约 150 MB/s | 需要认真规划 NVMe、网络、batch、分区 |
| 全部挤在 10 秒 | 约 300 MB/s | 约 900 MB/s | 需要多 stream / 多集群 / 多区域分摊 |
| 全部挤在 1 秒 | 约 3 GB/s | 约 9 GB/s | 不应依赖日志集群硬扛，必须设备侧打散和 Broker 背压 |

按 12 小时白天窗口估算原始数据量：

| 单条 payload | 原始日写入量 | 三副本日志写入量 |
|---:|---:|---:|
| 1.5KB | 约 216 GB/day | 约 648 GB/day |
| 3KB | 约 432 GB/day | 约 1.3 TB/day |
| 5KB | 约 720 GB/day | 约 2.2 TB/day |

结论：

```text
百万连接本身不是最大问题。
最大问题是：
1. 连接风暴
2. 同步上报风暴
3. 存储削峰
4. 重试风暴
```

| 组件 | 职责 |
|---|---|
| MQTT Gateway | 接入 TCP/TLS/MQTT，认证，QoS0/QoS1，上行写 raw log，南向本地投递 |

## 6. 上行数据链路设计

### 6.1 上行路径

```text
逆变器
  |
  | MQTT PUBLISH QoS0/QoS1
  ▼
MQTT Gateway
  |
  | 校验 device_id / topic / payload_len / crc
  ▼
Durable Raw Log
  |
  | append 成功
  ▼
Broker 返回 PUBACK，QoS1 场景
  |
  ▼
Decoder 异步消费 raw log
  |
  ▼
时序库 / OLAP / 告警
```

### 6.2 QoS1 ACK 时机

QoS1 的核心原则：

```text
收到 PUBLISH
  -> 校验基础合法性
  -> append 到 durable raw log
  -> append 成功
  -> 返回 PUBACK
```

`append 成功` 必须指后端日志系统确认持久化成功，而不是写入本地 producer buffer 成功。

Kafka / Redpanda / JetStream 的具体 ACK 语义、故障窗口和 appender 实现见 [云端 MQTT 接入 Broker 与 Raw Log Appender 详细设计](./3.cloud-mqtt-gateway-raw-log-design.md)。

### 6.3 QoS0 与 Raw Log

QoS0 没有 MQTT 层 ACK。正常情况下，QoS0 也建议进入 raw log，便于统一解码、追溯和重放；但压力升高时，QoS0 应先降级、先丢弃、先断连，避免拖垮 QoS1 和接入层。

```text
正常水位：QoS0 进入 raw log。
压力水位：QoS0 限额进入 raw log。
高压水位：QoS0 直接丢弃或断连。
故障水位：QoS0 全部拒绝，QoS1 不 ACK 并等待设备退避重试。
```

如果业务要求 QoS0 也 100% 持久化，那么它在服务端语义上已经接近 QoS1，应按可靠日志链路规划容量、成本和故障恢复。详细策略见 [云端 MQTT 接入 Broker 与 Raw Log Appender 详细设计](./3.cloud-mqtt-gateway-raw-log-design.md)。

### 6.4 上行幂等字段

设备 payload header 建议包含：

```text
device_id
sample_ts        // 采样时间，不是服务端接收时间
seq              // 设备侧递增序号
boot_id          // 每次上电生成
schema_id        // 点位表版本
payload_len
payload_crc32
firmware_version
```

服务端去重 key（**权威定义在 [raw log 设计 §3.3](./3.cloud-mqtt-gateway-raw-log-design.md)，本节为引用**）：

```text
(tenant_id, device_id, boot_id, seq)
```

字段来源分两层：`tenant_id` / `device_id` 取自**认证主体写入的 envelope**（Kafka headers），设备无需在 payload 中携带，固件零改动；`boot_id` / `seq` 在设备 payload header 中，由 Decoder 下游解析（Broker 不解析 payload）。key 必须含 tenant_id——认证表主键是 `(tenant_id, device_id)`，device_id 不保证跨租户全局唯一。

如果设备侧 `seq` 能保证跨重启单调递增，也可以使用：

```text
(tenant_id, device_id, seq)
```

如果历史固件暂时没有可靠 `boot_id` 或单调 `seq`，可以退化为：

```text
(tenant_id, device_id, sample_ts, payload_crc32)
```

但 `(tenant_id, device_id, sample_ts, payload_crc32)` 更适合做兼容方案，不应作为长期主键。因为设备 RTC 不准、重启后序号归零、重复采样时间都可能造成误去重或漏去重。

**强制要求（设备为公司自产，这是最大杠杆）**：第一版固件起就**强制实现 `boot_id` + 跨重启单调递增 `seq`**，把 `(tenant_id, device_id, boot_id, seq)` 作为唯一长期去重主键。具体约束：

```text
boot_id：每次上电生成一次（随机/递增均可），同一 boot 周期内不变。
seq：单调递增，掉电不回退（建议落 flash / 由 boot_id 隔离归零）。
两者组合保证：重启后 seq 即使归零，也因 boot_id 变化而不冲突。
```

不要把 `(tenant_id, device_id, sample_ts, payload_crc32)` 兼容方案当成"反正能用"而省掉固件侧实现 —— 自产设备能在出厂固件里一次做对，远比上线后在服务端打补丁兜底便宜。`(tenant_id, device_id, sample_ts, payload_crc32)` 只用于纳管历史存量固件，且应有明确的退役计划。

固件能力要有**显式准入登记**：产品接入配置（access profile）声明该型号/固件版本支持的去重能力级别（`boot_id+seq` 或仅兼容 key），Decoder 按此选择去重 key；纳管存量固件时同步登记退役计划，避免兼容 key 静默变成长期方案。

### 6.5 Topic 设计

不建议每个点位一个 topic：

```text
bad:
inverter/{device_id}/pv_voltage_1
inverter/{device_id}/pv_voltage_2
...
inverter/{device_id}/point_700
```

建议每次上传一条全量快照。

**自产设备默认采用「每设备 topic + ACL」（方案 A）。** 设备发布到带自身身份的 topic：

```text
v1/{tenant}/{product}/{device_id}/telemetry/raw
```

Broker 对自产设备每个 PUBLISH 做 ACL 校验：**topic 中的 `tenant` / `device_id` 必须等于 CONNECT 认证得到的可信主体**，否则拒绝/断连。

```text
PUBLISH topic 中的 tenant / device_id
  必须等于 CONNECT 认证得到的 tenant_id / device_id
否则拒绝（防止已连接设备冒充其他设备上报）。
```

要点：

- Broker **只比对 topic 字符串与认证主体**，不解析 payload 来识别设备（payload 全程不透明二进制，贴合 §5.2「broker 不解码 payload」）。
- 写入 raw log 的 `tenant_id` / `device_id` 一律取自**认证主体**（DB 权威），不取自 topic、更不取自 payload —— topic 只用于 ACL 比对。
- ACL 检查是一次 O(1) 字符串比较，无订阅树 / 通配匹配开销。

第三方厂家设备不强制改成自产 topic。第三方设备的 topic / payload 保持厂家协议原样，由产品接入配置定义允许的发布/订阅 topic，由规则引擎或 Adapter 在 Broker 之外完成协议转换。

**未作为全局默认的备选：单 topic + payload header 绑定（方案 B）。** 即所有设备发布到固定 `v1/telemetry/raw`，`device_id` 放在 payload header，Broker 拆 payload 头取出 `device_id` 与认证主体绑定校验。该方案能省几十字节 topic、减少 topic 解析成本，但代价是 **Broker 必须拆 payload 头**、与 payload 格式耦合；而本设计上行没有订阅树（遥测直接进 raw log），所谓「减少通配匹配成本」并不适用，3KB 全量快照下 topic 多几十字节也可忽略。因此不作为自产设备默认方案。

> 注：无论哪种方案，核心安全要求一致 —— 必须把**认证主体**和**上报身份**绑定校验，否则设备只要能连接，就可能伪造其他设备的数据。自产方案 A 把上报身份放在 topic（无需拆 payload）即可完成绑定；第三方厂家协议则由产品接入配置声明身份绑定方式。

### 6.6 原始数据保留

建议至少保留两份数据：

| 数据 | 用途 |
|---|---|
| raw binary | 追溯、重新解码、点表修正、故障回放 |
| decoded data | 查询、告警、报表、AI 分析 |

点表版本变更后，raw binary 可以重新按新 schema 解码。

## 7. 南向 / 下行命令路由设计

### 7.0 上行与下行边界

Broker 不通过 payload 猜测消息方向，而是通过 **消息来源和协议方向** 判断上行/下行，再通过产品接入配置做 topic ACL。

上行消息：

```text
设备 TCP/MQTT 连接
  -> Broker 收到 MQTT PUBLISH
```

只要是在设备连接上收到的 `PUBLISH`，就按设备上行处理。业务类型不由 Broker 写死，而由产品接入配置、规则引擎或下游 Adapter 归类：

```text
自产设备：
  v1/{tenant}/{product}/{device_id}/telemetry/raw
  v1/{tenant}/{product}/{device_id}/cmd_ack

第三方厂家设备：
  /sys/{product_key}/{device_name}/thing/event/property/post
  /sys/{product_key}/{device_name}/thing/service/+/reply
  devices/{device_id}/messages/events/
```

下行消息：

```text
Command Service
  -> 查 presence + broker registry → gRPC 直连目标 Broker（Deliver）
  -> Broker 本地 session lookup（fencing 校验）
  -> Broker 向设备 MQTT 连接写 PUBLISH
```

因此判断规则是：

```text
设备连接上收到 PUBLISH：上行。
Broker 往设备连接写 PUBLISH：下行。
Broker 的 gRPC 下行 endpoint 收到 Deliver：下行投递任务。
```

设备侧 topic 权限必须收口，但不能写死为自产 topic。认证结果应携带 `product_id` / `access_profile_id` / `acl_version`，Broker 使用本地缓存的产品接入配置执行轻量 ACL：

```text
publish_allowlist:
  - 自产遥测 topic
  - 自产 cmd_ack topic
  - 第三方厂家上行 / reply topic

subscribe_allowlist:
  - 自产 cmd topic
  - 第三方厂家命令 / service topic

identity_bind:
  - topic 中的 tenant / device_id
  - topic 中的 product_key / device_name
  - CONNECT 认证主体映射出的厂家设备标识
```

v1 范围澄清：自产设备的 ACL 是**静态规则**（topic 形状与认证主体的 O(1) 比对，已在 Broker 内实现），不需要任何配置分发。`access_profile_id` / `acl_version` 对应的产品级 ACL 配置加载、缓存失效与回滚属于第三方设备接入能力（Phase 4），不在第一阶段范围。

设备如果需要接收命令，只允许订阅该产品接入配置中属于自己的命令 topic，例如：

```text
v1/{tenant}/{product}/{device_id}/cmd
/sys/{product_key}/{device_name}/thing/service/+/set
```

禁止订阅其他设备 topic、跨 tenant topic 和 `$share`。是否允许 `+` 这类厂家协议必需的有限 wildcard，由产品接入配置显式声明；不允许设备任意 wildcard。

### 7.1 问题本质

上行可以无状态，因为设备主动连入任意 Broker 都可以上传数据。

但下行不一样：

```text
设备的 TCP/MQTT 连接只存在于某一个 MQTT Gateway 本地。
```

因此，平台要给指定设备下发命令，必须知道：

```text
device_id 当前连接在哪个 broker
```

### 7.1.5 路由模型：身份路由，不是 topic 路由

下行路由的根本选择：**按设备身份路由，不按 topic 路由。** 通用 MQTT broker 的下行是 topic 路由（publish topic X → 订阅树匹配 → 投给所有订阅 X 的人）；本设计是身份路由（命令 target `device_id` → 找它在哪 → 投过去）。**topic 只是设备期望的信封，不参与"投给谁"的决策**——这是 Broker 能保持极简（无订阅树、无通配匹配）的根因。

下行没有"一张 topic 路由表"，只有三层 lookup，每层 key 都是身份：

| 层 | 决策 | 坐在哪 | 数据源 | 复杂度 |
|---|---|---|---|---|
| ① 成员解析 | 逻辑命令 → 目标设备集合（含组/租户/区域） | Command Service | 设备档案 DB（`WHERE tenant_id/region/product/firmware`） | 一次 DB 查询 |
| ② 位置 | 设备 → 哪个 broker | Command Service | presence（Redis） | 一次 KV 查询 |
| ③ 本地投递 | 设备 → 哪条连接 | Broker 进程内 | 全局 sharded `map[device_numeric_id]→*conn` | O(1) |

`topic` 不是路由 key：它在 Deliver envelope 里（规则引擎编码出的 `mqtt_topic`，见 §9.3.4），Broker 收到后做一次 O(1) ACL 校验（是不是这台设备自己的 cmd topic / 声明允许的模式），然后原样 PUBLISH。Broker 从不拿 topic 去匹配"谁该收"。

> 注：设备 SUBSCRIBE 自己的 cmd topic 是**给设备自己的 MQTT 客户端库用的**（标准库只把订阅过的 topic 交给应用层），不是给 Broker 路由用的；Broker 校验合法（O(1)）即可，**订阅记录不是路由输入**。

#### 通配路由：不做

通配路由 = `+` / `#` + 订阅树 trie 匹配。身份路由不需要 trie（没有"拿消息去匹配通配订阅"这一步），且红线 §7.7/§10 禁止通用 wildcard 订阅与订阅树（pointer-heavy + 日出日落百万订阅 churn）。设备只订**一个固定 cmd topic**，O(1) 字符串校验，不建 trie。

唯一例外、但它不是路由：第三方厂家协议必需的有限 `+`（如 `/sys/{pk}/{dn}/thing/service/+/set`），由产品接入配置**显式声明**，Broker 在 SUBSCRIBE 时校验"是否匹配声明的固定模式"——这是对固定声明模式的 ACL 校验，不是通配订阅树匹配。下行投递仍是身份路由。

#### 组 / 租户级"topic 路由到设备"：Broker 侧不做，Command Service 拆单播

不在 Broker 侧做"发到组/租户 topic → fan-out 到成员"（这正是已删除的旧 §7.8 broker 广播方案）。组/租户 fan-out 全在 Command Service：查设备档案 DB 解析成员（`WHERE region=... / tenant_id=...`）→ 逐设备查 presence → gRPC 单播 → 限速（复用 §9.8 OTA 编排，详见 §7.8）。

为什么放 Command Service + DB 而非 Broker + topic：

```text
成员来源：设备档案 DB（region/product/firmware/tenant 的权威源），不是"设备碰巧订阅了什么"。
租户隔离：WHERE tenant_id 在查询层强隔离，不靠"topic ACL 不出错"兜底（约定性弱隔离）。
Broker 状态：零——Broker 只认单播投递，不存 filters / 不做 scope 匹配。
per-device ACK：天然有（每条都是被跟踪的命令，复用命令状态机）。
```

代价"一条逻辑命令 → N 次单播"在低频、秒级容忍的逆变器下行下可接受（论证见 §7.8.3）。

> 若其它业务需要通用**订阅式**下发（设备 SUBSCRIBE 任意声明允许的 topic、平台按 topic 匹配投递），见 §7.9——topic 路由作为 opt-in 可选能力，匹配器外置在下行路由器、**Broker 仍不做 topic 匹配**（借鉴 EMQX 定向去重 + NATS sublist，绕开两家的扩展性天花板）。

### 7.2 核心方案

建立在线位置索引：

```text
device_id -> broker_id / broker_epoch / conn_id / session_version
```

南向消息路径：

```text
业务系统
  |
Command Service
  |
Presence Registry 查询 device_id
  |
找到 broker_id + broker registry 取 gRPC 地址
  |
gRPC 直连目标 broker（Deliver(envelope + fencing)）
  |
目标 MQTT Gateway
  |
本地 MQTT PUBLISH 到设备
```

### 7.3 南向架构图

```text
Business API
    |
    | create command
    ▼
Command Service
    |
    | persist command
    ▼
Command Store
    |
    | lookup device location
    ▼
Presence Registry
    |
    | broker-17, addr=10.0.0.17:9eX, conn_id=984231, session_version=128
    ▼
gRPC 直连（Command Service → Broker）
    |
    | Deliver(envelope + fencing) → broker-17
    ▼
MQTT Gateway-17
    |
    | local session lookup（fencing 校验）
    ▼
Inverter MQTT Connection
```

### 7.4 每个 Broker 的 gRPC 下行 endpoint

每个 Broker 暴露一个 gRPC 下行服务（不订阅任何消息队列通道）：

```text
Deliver(envelope + fencing)   // 下发一条命令到本地设备连接
Kick(device_id + fencing)     // 强制关闭一条本地连接（takeover，见 §13；简化模式可不用）
Query(device_id)              // 校验本地是否仍持有该连接（presence 复核）
```

Broker 启动时把自己的 `broker_id → gRPC 地址` 写入 Broker Registry（Redis，随 lease 续租）。Command Service 据此寻址：

```text
device_id = INV_001
Presence Registry -> broker-17
Broker Registry  -> broker-17 = 10.0.0.17:9eX
Command Service  -> gRPC broker-17.Deliver(envelope)
Broker-17        -> 找本地连接（fencing 校验）-> MQTT PUBLISH -> 回 PUBACK/NOT_HERE
```

注意：这是 **Command Service → Broker 的 1×N 调用**（和 things 内部服务 etcd+gRPC 互调同构），不是 broker→broker mesh——Broker 之间永不直接通信（share-nothing）。

### 7.5 不要用 queue group 做定向下发

不建议：

```text
所有 Broker 订阅 cmd.downlink，并加入同一个 queue group。
Command Service publish cmd.downlink。
某一个 Broker 被随机选中消费。
```

原因：

```text
被选中的 Broker 未必持有目标设备连接。
```

正确做法：

```text
Command Service 查询 Presence Registry。
然后 gRPC 直连指定 Broker 的下行 endpoint（Deliver）。
```

### 7.6 不建议每设备一个内部订阅

不建议让 Broker 为每台在线设备动态订阅：

```text
cmd.{device_id}
```

原因：

```text
1. 内部订阅数会接近在线设备数。
2. 日出日落会产生百万级订阅变更。
3. Broker 重启后要重建大量订阅。
4. 内部消息系统会承受巨大订阅 churn。
```

更推荐：

```text
每个 Broker 只维护少量固定控制通道。
Command Service 负责查 presence 并精准路由。
```

### 7.7 共享订阅边界

本设计不建议在设备接入 Broker 内实现通用 MQTT 共享订阅：

```text
$share/{group}/{topic_filter}
```

原因是共享订阅解决的是“多个消费者共同消费一个 topic”的负载均衡问题，而不是“某台设备当前连接在哪个 Broker”的定位问题。

上行 telemetry 的共享消费应放在 raw log 之后：

```text
设备
  -> MQTT Gateway
  -> Kafka / Redpanda raw log
  -> Decoder consumer group
```

此时 Kafka / Redpanda 的 consumer group 已经提供了共享订阅想要的效果：

```text
同一个 consumer group 内，多个 Decoder 实例分摊 partition。
每条 raw message 在该 group 内只被一个 Decoder 实例处理。
支持 offset、replay、consumer lag 和背压观测。
```

下行命令不能使用 MQTT 共享订阅或内部 queue group 随机投递：

```text
Command Service -> cmd.downlink
所有 Broker 以 shared subscription / queue group 方式消费
随机 Broker 收到命令
```

问题是：

```text
被选中的 Broker 未必持有目标设备连接。
即使命令消息被某个 Broker 消费成功，也不代表设备可达。
```

下行命令仍必须走：

```text
Command Service
  -> Presence Registry 查询 device_id
  -> gRPC 直连指定 Broker 的下行 endpoint
  -> 目标 Broker 二次校验本地 session
  -> MQTT PUBLISH 给设备
```

因此第一阶段策略：

```text
设备接入 Broker 不支持 $share 共享订阅。
设备 SUBSCRIBE 只允许订阅自己的命令 topic。
禁止 wildcard。
禁止任意 topic。
禁止把下行命令投递到 shared subscription / queue group。
```

如果未来需要给业务应用提供标准 MQTT shared subscription，应单独建设 Application MQTT Gateway，不要把该能力放进设备接入 Broker。

### 7.8 下行 fan-out：Command Service 拆单播（不进 Broker、不进 Kafka）

> 当平台要给一批设备发同一条命令（区域调频限功率、批量配置、OTA），需要"一条逻辑命令 → 多设备"。本设计**不在 Broker 侧做组播/广播**，而是由 Command Service 把它拆成 N 条单播，逐设备走 §7.2 的 gRPC 直连路径。**Broker 永远只认"单播投递"一件事**，下行只有一种机制。

#### 7.8.1 单一下行机制：拆单播

```text
广播/批量（如"浙江省所有逆变器限功率 50%"）：
  Command Service
    → 查设备档案 DB（member_rule：region=zhejiang / product / firmware ...）→ 目标设备集合
    → 对每个设备：查 presence(device_id) → gRPC 单播到其所在 Broker（§7.2）
    → 限速下发（复用 §9.8 OTA 的 group / rate 编排）
  Broker 侧：与单播完全相同——收 gRPC Deliver → 本地连接 → MQTT PUBLISH。Broker 不感知"广播"。
```

成员关系由 **Command Service 查设备档案 DB 解析**（region / product / firmware 的权威源），不靠 Broker 侧订阅 filter。设备**只 SUBSCRIBE 自己的命令 topic**（`v1/{tenant}/{product}/{device_id}/cmd`），不订区域/组 topic。

#### 7.8.2 为什么不在 Broker 做广播（保住极简 Broker）

把 fan-out 放回 Command Service，Broker 侧**不需要**任何组播机制：

```text
✗ Session 里不存 filters（省掉每 Session +1 指针，pointer-poor 更纯）
✗ 不需要 Kafka broadcast topic + all-broker 消费
✗ 不需要 Broker 侧 scope 过滤 / topic 前缀匹配
✗ 设备不需要 SUBSCRIBE 区域/组 topic
```

Broker 的下行复杂度与"是不是广播"无关，永远是 O(1) 单播投递。这与 [§9.8 OTA 编排](#98-ota-分组编排group-级-barrier)（拆成 per-device 命令、Broker 不感知 group）是**同一个模型**，两处一致——之前 §7.8 的"Broker 侧 Kafka 广播 + filter"与 §9.8 的"Command Service 拆单播"是互相矛盾的两套做法，本次统一为后者。

#### 7.8.3 代价与为什么可接受

拆单播的成本是"一条逻辑命令 → N 次 presence 查 + N 次 gRPC"，而非"1 条 Kafka 消息"。本场景可接受：

```text
1. 真广播是低频事件（区域调频、批量配置——偶发电网指令，不是持续流）。
2. MQTT 下行秒级容忍（要毫秒同步该走 IEC 61850 GOOSE / Modbus 直连，不是 MQTT）；
   秒级容忍 → 限速拆 N 条来得及（10 万设备 / 10s = 1 万 gRPC/s，纳秒级负担）。
3. 复用 §9.8 OTA 限速编排，零新增机制。
4. 电网命令多半要知道"哪些设备真应用了"→ 本就要 per-device ACK
   → 拆单播天然带 ACK（复用命令状态机），比 fire-and-forget 广播更可控。
```

唯一值得保留 Broker 广播的场景是"打全量大机群 + 完全不需要 per-device 确认 + 要紧同步"——对"要确认 + 秒级容忍"的逆变器，这个场景几乎不存在。故默认拆单播。

#### 7.8.4 与 §7.6 / §7.7 的关系

```text
§7.6 否定"每设备一个内部订阅"（百万订阅 churn）——本方案不引入。
§7.7 否定"$share 共享订阅 + 通配符"（设备间竞争消费）——本方案不引入。
本方案：fan-out 全在 Command Service（查 DB 解析成员 + 拆单播 + 限速），Broker 零组播逻辑。
```

### 7.9 下行 topic 路由（可选能力，详见独立设计 doc 14）

> §7.8 的 fan-out 用「设备档案 DB 解析成员」，适合逆变器。其它业务/部门若要**通用 MQTT 订阅式下发**（设备 SUBSCRIBE 任意声明允许的 topic、平台按 topic 匹配投递），作为 **per-product / tenant opt-in** 的可选能力支持。这是一个独立的较大主题，完整设计（EMQX/NATS/MqttWk 剖析、订阅索引 schema、匹配器、一致性、落地阶段）见：
>
> **→ [云端 MQTT Gateway 下行 Topic 路由设计](./14.cloud-mqtt-gateway-downlink-topic-routing-design.md)**

一句话口径（细节见 doc 14）：

```text
原则：topic 匹配在【下行路由器】，Broker 永不匹配 topic、只按身份投「显式设备清单」。
借鉴：EMQX（定向 + 按目标节点去重 + 精确/通配分表）+ NATS（缓存 sublist trie + 订阅外置）。
绕坑：订阅索引放 Redis 分片 KV（非 Mria 共识）；每设备唯一 topic 不索引（走身份路由）；
      匹配器永不上 1M Broker。
接口：DeliverBatch([device_id...], topic, payload)——一 broker 一批，broker 逐个身份投。
复用：§7.8 的「拆单播 + 身份投递」，只把成员来源从「DB 查询」扩成「DB 查询 或 订阅索引匹配」。
```

## 8. Presence Registry 设计

Presence Registry 维护设备当前连接所在 Broker，是下行命令路由的提示信息，不是最终事实。

```text
device_id -> broker_id / broker_epoch / conn_id / session_version
```

核心原则：

1. Presence 可以短暂不准，但不能导致错发。
2. Command Service 下发时携带 presence fencing 信息。
3. Broker 必须二次校验本地连接。
4. Broker 崩溃时依赖 broker lease 过期，而不是批量删除设备 presence。
5. 不要每台设备频繁续租 TTL，避免百万级写压力。

推荐选型：

| 数据 | 推荐 |
|---|---|
| device presence | Redis Cluster |
| broker registry / broker lease | Redis（和 presence 同库，key 带 TTL） |
| 命令状态、设备档案、历史在线状态 | DB |

presence 写风暴粗算（日出上线时，CONNECT 主路径每次至少 1 次 `INCR` + 1 次 `CAS`，都是写操作）：

| 上线打散窗口 | presence 写 QPS（INCR+CAS，约 2×连接速率） | 判断 |
|---|---:|---|
| 100 万均匀打散到 30min | 约 555 conn/s ≈ 1.1k 写/s | Redis Cluster 轻松承载 |
| 100 万挤在 10min | 约 1666 conn/s ≈ 3.3k 写/s | 需规划分片，正常可承载 |
| 100 万挤在 5min | 约 3333 conn/s ≈ 6.7k 写/s | 必须分片 + 控制 accept 速率 |
| 日落断连 + 设备无退避重连叠加 | 写 QPS 翻倍并可能尖峰 | 必须连接 jitter + accept 限流，否则写风暴放大 |

关键：**presence key 必须按 `device_id` 哈希分片打散，避免 tenant 级或 broker 级热点**；断连删除是条件删除（带 fencing），不是无条件 `DEL`；RUNNING 期不按每条 telemetry 刷新，避免把 3333 msg/s 变成 3333 presence 写/s。分片键设计、热点规避和压测矩阵见下文详细设计。

详细的数据模型、session_version 原子生成、条件删除、两层 lease、Redis/etcd 选型、故障场景和压测矩阵见：

- [云端 MQTT 接入 Broker Presence Registry 详细设计](./2.cloud-mqtt-presence-registry-design.md)

Presence 更新的主路径：

```text
CONNECT:
  认证成功
  -> Redis INCR presence_seq:{tenant_id}:{device_id}
  -> Broker 生成 conn_id
  -> CAS 写 presence:{tenant_id}:{device_id}
  -> CAS 成功后返回 CONNACK

DISCONNECT / TCP Close:
  -> 按 broker_id / broker_epoch / conn_id / session_version 条件删除

RUNNING:
  -> 不按每条 telemetry 刷新 presence
  -> last_seen 如需更新，按连接限频并带 fencing 条件
```

Presence 更新失败时，生产默认 fail closed：拒绝连接或断开当前连接，避免平台认为设备可下行但找不到可靠路由。

## 9. Command Service 设计

### 9.1 为什么需要 Command Service

不要让业务系统直接调用 Broker：

```text
bad:
业务系统 -> Broker -> 设备
```

应该：

```text
good:
业务系统 -> Command Service -> 命令持久化 -> presence 路由 -> Broker -> 设备
```

Command Service 负责：

```text
命令持久化
命令 TTL
命令幂等
重试策略
状态机
设备离线等待
业务 ACK 关联
审计日志
权限校验
```

### 9.2 RPC 服务发现与高可用

Command Service 可以注册成 RPC 服务到 etcd，实现服务入口层面的高可用：

```text
Command Service 实例 A/B/C
  -> 启动时向 etcd 注册 endpoint
  -> 绑定 etcd lease
  -> 定期续租
  -> 实例宕机后 lease 过期，endpoint 自动消失
```

调用方通过 etcd watch 服务列表：

```text
业务系统 / API Gateway
  -> watch /services/command-service/*
  -> 本地维护健康 endpoint 列表
  -> round-robin / least-load 调用任一 Command Service 实例
```

etcd 只负责：

```text
服务发现
实例 lease
健康 endpoint 列表
小规模控制面配置
```

不要把 etcd 当作命令队列或命令数据库。命令状态必须持久化到业务 DB：

```text
command_id
tenant_id
device_id
payload
ttl
status
retry_count
lease_owner
lease_until
last_error
created_at
updated_at
```

完整高可用还需要：

```text
1. Command Service 无状态多副本。
2. command_id 唯一键，重复提交返回同一命令状态。
3. worker 处理命令时使用 DB CAS / row lock / lease_owner 抢占。
4. 实例挂掉后，lease_until 超时，其他实例接管未完成命令。
5. 下发 Broker 前写 outbox 或明确状态转换，避免进程崩溃后命令丢失。
```

推荐流程：

```text
业务系统
  -> etcd 发现 Command Service endpoint
  -> RPC CreateCommand(command_id, device_id, payload, ttl)
  -> Command Service 写 DB，状态 CREATED / ENCODING
  -> outbox 发布 command.encode.request 到 Kafka
  -> 规则引擎消费 Kafka，编码为厂商 MQTT topic / payload
  -> Command Service / Dispatch Worker 消费 command.encoded
  -> 更新 DB，状态 ENCODED
  -> worker 抢占命令
  -> 查询 Presence Registry
  -> 发送 gRPC Deliver(目标 Broker)
  -> 更新命令状态
```

因此：

```text
etcd 解决“调用哪个 Command Service 实例”。
DB 状态机解决“命令是否可靠保存、是否重复执行、实例挂掉后谁接管”。
Kafka 解决“编码请求、编码结果、命令事件、审计日志的异步解耦”。
Presence Registry 解决“目标设备当前在哪个 Broker”。
```

### 9.3 命令状态机

#### 9.3.1 主状态与投递尝试分离

Command Service 不应只靠一个状态字段承载所有细节。推荐分成两层：

```text
iot_command          // 命令业务状态，供 API / 业务系统查询
iot_command_attempt  // 每次实际下发尝试，供重试、审计和排障使用
```

`iot_command.status` 只表达命令主生命周期：

```text
CREATED
ENCODING
ENCODED
ENCODE_FAILED
PENDING_DEVICE_ONLINE
ROUTING
SENT_TO_BROKER
MQTT_PUBACK_RECEIVED
WAITING_APP_ACK
APP_ACK_RECEIVED
EXPIRED
FAILED
CANCELED
```

状态含义：

| 状态 | 含义 |
|---|---|
| CREATED | 命令已持久化，还未开始路由 |
| ENCODING | 已发起规则引擎编码，等待厂商 MQTT topic / payload |
| ENCODED | 已得到厂商 MQTT topic / payload，可进入路由 |
| ENCODE_FAILED | 编码失败，可按重试策略重新编码，超过重试或过期后转 FAILED / EXPIRED |
| PENDING_DEVICE_ONLINE | 设备当前不在线，命令未过期，等待上线 |
| ROUTING | worker 已抢占命令，正在查询 presence、校验 broker lease、准备投递 |
| SENT_TO_BROKER | 命令已投递到目标 Broker，Broker 已接受处理或进入本地有界下行队列 |
| MQTT_PUBACK_RECEIVED | 设备 MQTT 协议栈已返回 PUBACK，只代表设备 MQTT 客户端收到消息 |
| WAITING_APP_ACK | 命令要求业务 ACK，已收到 MQTT PUBACK，正在等待设备上报 `cmd_ack` |
| APP_ACK_RECEIVED | 设备业务 ACK 已收到，命令业务闭环完成 |
| EXPIRED | 超过 `expires_at`，不再下发或等待 |
| FAILED | 不可恢复失败，例如参数非法、超过最大重试、设备明确返回业务失败 |
| CANCELED | 云端主动取消 |

`iot_command_attempt.status` 记录单次投递结果：

```text
PENDING
ACCEPTED
PUBACK
NOT_HERE
STALE_BROKER_EPOCH
STALE_SESSION
DOWNLINK_QUEUE_FULL
TIMEOUT
FAILED
```

attempt 中必须记录 fencing 信息：

```text
broker_id
broker_epoch
conn_id
session_version
mqtt_packet_id
started_at
sent_to_broker_at
mqtt_puback_at
finished_at
error_code
```

注意区分：

| ACK | 含义 |
|---|---|
| MQTT PUBACK | 设备 MQTT 协议栈收到了消息 |
| APP ACK | 逆变器业务逻辑执行完成 |

控制类命令不能把 MQTT PUBACK 当作业务执行成功。

#### 9.3.2 典型流转

在线设备，只等待 MQTT ACK：

```text
CREATED
  -> ENCODING
  -> ENCODED
  -> ROUTING
  -> SENT_TO_BROKER
  -> MQTT_PUBACK_RECEIVED
```

在线设备，要求业务 ACK：

```text
CREATED
  -> ENCODING
  -> ENCODED
  -> ROUTING
  -> SENT_TO_BROKER
  -> MQTT_PUBACK_RECEIVED
  -> WAITING_APP_ACK
  -> APP_ACK_RECEIVED
```

设备离线：

```text
CREATED
  -> ENCODING
  -> ENCODED
  -> PENDING_DEVICE_ONLINE
  -> ROUTING              // 设备上线、上报或定时扫描触发
  -> SENT_TO_BROKER
  -> MQTT_PUBACK_RECEIVED
  -> WAITING_APP_ACK
  -> APP_ACK_RECEIVED
```

路由到旧 session：

```text
ROUTING
  -> Broker 返回 NOT_HERE / STALE_BROKER_EPOCH / STALE_SESSION
  -> Command Service 重新查询 presence
  -> ROUTING 或 PENDING_DEVICE_ONLINE
```

超时：

```text
任意非终态
  -> now >= expires_at
  -> EXPIRED
```

编码失败：

```text
ENCODING
  -> ENCODE_FAILED
  -> ENCODING              // 未过期且未超过重试次数时重新编码
  -> FAILED / EXPIRED      // 不可恢复或过期
```

终态不可回退：

```text
APP_ACK_RECEIVED / FAILED / EXPIRED / CANCELED
  不能再变回 ENCODING / ROUTING / SENT_TO_BROKER
```

#### 9.3.3 同步等待与异步等待

同步和异步不应设计成两套状态机，只是 API 等待同一套状态机的不同状态。

异步：

```text
CreateCommand
  -> 落库
  -> 返回 command_id
  -> 调用方轮询 / 回调 / 订阅 command event
```

同步等待 MQTT ACK：

```text
CreateCommand(wait_for=MQTT_PUBACK, timeout=5s)
  -> 等状态到 MQTT_PUBACK_RECEIVED / FAILED / EXPIRED / CANCELED
  -> 超时返回 command_id + 当前状态
```

同步等待业务 ACK：

```text
CreateCommand(wait_for=APP_ACK, timeout=30s)
  -> 等状态到 APP_ACK_RECEIVED / FAILED / EXPIRED / CANCELED
  -> 超时返回 command_id + 当前状态
```

API 等待超时不等于命令失败。命令是否失败只能由状态机根据 `expires_at`、最大重试、Broker 返回码和设备业务 ACK 判断。

#### 9.3.4 DB 状态机 + Kafka 编码事件流

平台南向命令使用统一格式，不能要求 MQTT Broker 理解每个厂商的 topic 和 payload。规则引擎负责把平台统一命令编码为厂商 MQTT 消息：

```text
平台统一 command
  -> 规则引擎编码
  -> 厂商 mqtt_topic / mqtt_payload / qos / ack_policy
```

Command Service 仍然先写 DB 状态机，Kafka 用于异步编码、事件通知、审计和解耦：

```text
Business API
  -> Command Service
  -> DB transaction:
       iot_command.status = CREATED / ENCODING
       iot_command.canonical_payload = 平台统一命令
       iot_command_outbox.event_type = ENCODE_REQUESTED
  -> Outbox Publisher
  -> Kafka: command.encode.request
  -> Rule Engine 消费 command.encode.request
  -> Rule Engine 编码厂商 MQTT topic / payload
  -> Kafka: command.encoded 或 command.encode_failed
  -> Command Service / Dispatch Worker 消费编码结果
  -> DB CAS:
       ENCODING -> ENCODED / ENCODE_FAILED
  -> ENCODED 后再查 Presence 并定向投递到 gRPC Deliver(目标 Broker)
```

不要把 Command Service 的 DB 状态机替换成“只发 Kafka”。Kafka 是事件流，不是命令当前状态的权威存储。命令仍需要：

```text
command_id 幂等
状态查询
同步等待 MQTT ACK / APP ACK
TTL / 过期
取消
重试次数
失败原因
实例挂掉后接管
终态不可回退
```

这些能力由 DB 状态机提供，Kafka 只负责把编码和后续事件异步化。

规则引擎边界：

```text
输入：tenant_id / product_id / device_id / cmd_type / canonical_payload / rule_version
输出：mqtt_topic / mqtt_payload / qos / ack_policy / expected_ack_rule
```

Broker 边界：

```text
Broker 不执行规则引擎。
Broker 不理解厂商 payload。
Broker 不改写 mqtt_topic / mqtt_payload。
Broker 只校验下行 envelope、session fencing、过期时间和本地连接。
Broker 按已编码的 topic / payload 原样 MQTT PUBLISH 给设备。
```

#### 9.3.5 同设备并发命令策略

`cmd_id` 幂等只防"同一条命令重复"，不防"两条不同命令并发"。逆变器是物理设备：限功率 80% 和停机同时在途，谁先谁后决定设备终态。

默认策略：**per-device 串行**。

```text
同一 (tenant_id, device_id) 同时只允许 1 条非终态命令在途
（CREATED ~ WAITING_APP_ACK 之间均算在途）。

后到命令按策略二选一：
  queue  ：排队等待前一条进入终态（默认，按 created_at 顺序）
  reject ：立即拒绝并返回冲突错误（适合幂等性强的运维脚本）
```

实现落点：worker 抢占命令（DB CAS / lease）时，claim 条件追加"该 device 无其他在途命令"的互斥校验。互斥粒度第一版只做 device 级；cmd_type 级互斥（如升级期间禁止参数写入）与紧急命令抢占留作扩展，表结构预留 `mutex_group` 字段即可，不实现。

> **group 级串行**（device 串行的上一层编排）见 [§9.8 OTA 分组编排](#98-ota-分组编排group-级-barrier)：一组设备全部成功（或达成功率阈值）才执行下一组，典型用于 OTA 灰度升级。`mutex_group` 字段在那里复用为 batch 间设备互斥。

### 9.4 下行完整流程

```text
1. 业务系统创建命令
   command_id = cmd_123
   device_id = INV_001
   ttl = 5min

2. Command Service 持久化命令
   状态 = CREATED
   payload = 平台统一命令

3. Command Service 通过 outbox / Kafka 发起编码
   状态 = ENCODING
   topic = command.encode.request

4. 规则引擎消费编码请求
   输入平台统一命令
   输出厂商 mqtt_topic / mqtt_payload / qos / ack_policy

5. Command Service / Dispatch Worker 消费编码结果
   状态 = ENCODED

6. Command Service 查询 Presence Registry
   INV_001 -> broker-17, conn_id=984231, session_version=128

7. Command Service gRPC 直连目标 Broker
   broker-17.Deliver(envelope + fencing)（地址取自 Broker Registry）

8. Broker-17 收到命令
   检查本地连接是否仍然存在

9. Broker-17 MQTT PUBLISH QoS1 到逆变器
   topic / payload 使用规则引擎编码结果，Broker 不改写

10. 逆变器返回 PUBACK

11. Broker-17 回复 Command Service
   状态 = MQTT_PUBACK_RECEIVED

12. 如果 require_app_ack=true
   状态 = WAITING_APP_ACK

13. 逆变器执行业务命令

14. 逆变器上报 cmd_ack
    该消息属于设备上行 MQTT PUBLISH，Broker 按 topic 后缀分流
    进入独立的 command.ack.raw topic，不与遥测共队
    （控制闭环不被遥测洪峰的 consumer lag 拖累，见 raw log 设计 §8.2）

15. 规则引擎 / 上行 Adapter 解码厂商 ACK
    转换为统一 APP ACK

16. Command Service 消费统一 APP ACK 后更新状态
    状态 = APP_ACK_RECEIVED
```

### 9.5 离线命令

不建议把离线命令堆在 MQTT Broker 里。

应由 Command Service 管理：

```text
设备不在线
  -> 命令状态 = PENDING_DEVICE_ONLINE
```

设备上线的感知**不需要 Broker 通知任何人**（Broker 南向契约面不增长，见 [Presence Registry 设计 §12.2](./2.cloud-mqtt-presence-registry-design.md)）。设备连上后 ≤1 个上报周期内必有首条遥测进入 Kafka raw log，Command Service 直接消费 raw log 作为 `device_seen` 信号：

```text
设备 CONNECT 后首次上报遥测
  -> Kafka raw log（既有契约，无新通道）
  -> Command Service 消费到该 device 的消息（device_seen）
  -> 查询 pending commands
  -> 查询 Presence Registry
  -> 投递 gRPC Deliver(目标 Broker)
```

离线命令本来已等待数小时，再等一个上报周期（≤300s）无感；日出百万 online 信号被 Kafka 分区天然削峰。定时扫描 `PENDING_DEVICE_ONLINE` 作为兜底。

### 9.6 推 + 拉混合模式

推荐同时支持：

```text
在线时：平台主动 push 到当前 Broker。
不确定在线时：设备上报后 pull pending commands。
```

兜底路径（**Broker 全程不调用 Command Service**，遥测热路径不接业务 RPC）：

```text
Device telemetry
  -> Broker -> Kafka raw log
  -> Command Service 消费（device_seen）
  -> 查询是否有 pending commands
  -> 查 presence -> gRPC Deliver(目标 Broker) -> Broker 推送给设备
```

这能覆盖：

```text
presence 过期
设备刚重连
Broker 刚重启
网络抖动
平台查到旧 Broker
设备 NAT 漂移
```

### 9.8 OTA 分组编排：group 级 barrier

> 本节填补 §9.3.5（per-device 串行）之上的「多设备 group 级串行」缺口。典型场景：OTA 升级按组推进，**一组设备全部成功（或达成功率阈值）才执行下一组**。这是 device 串行 → group 串行的两级编排闭环。

#### 9.8.1 设计原则：Broker 不感知 group

```text
核心约束：group 编排全部在 Command Service 内完成，Broker 永远只做单条命令定向投递。
```

Broker 不感知 batch / group 存在。group 调度、成员解析、barrier 判定、组间推进都是 Command Service 的事。这保住了南向路由的 O(1) 特性（Broker 路由复杂度与在线设备数无关，见 [§7](#7-南向-下行命令路由) + [Presence §6](./2.cloud-mqtt-presence-registry-design.md)）。突破此约束会引入百万级订阅 churn（[§7.6](#76-不推荐每设备一个内部订阅) 已否定）。

#### 9.8.2 数据模型：command_batch + command_batch_item

复用现有 command 表和它的完整状态机（编码 → presence 查询 → 定向投递 → cmd_ack 闭环 → 重试 → TTL），外层套两张编排表：

```text
command_batch（批次表，一次 OTA = 一个 batch，含多个 group）
  batch_id          PK
  tenant_id
  cmd_type          (OTA_UPGRADE)
  total_groups      (如 2000 组)
  current_group     (当前进行到第几组)
  status            (PENDING / RUNNING / COMPLETED / FAILED / PAUSED)
  group_policy      (ALL_SUCCESS_NEXT / MAJORITY_NEXT / SKIP_FAILED_NEXT / MANUAL_REVIEW)
  group_threshold   (MAJORITY_NEXT 时的阈值，如 0.95)
  group_size        (每组设备数上限，如 500)
  failure_policy    (组失败时的动作：ABORT / CONTINUE / PAUSE)
  member_rule       (成员规则 JSON：product_id / region / firmware_version 等)
  payload_template  (OTA 包定位、目标版本号等)
  group_timeout     (单组超时窗口，如 1800s；超时后未决 item 转 FAILED)
  created_at / updated_at

command_batch_item（批次项表，每台设备每组一行）
  item_id           PK
  batch_id          FK → command_batch
  group_no          (属于第几组)
  device_id
  cmd_id            FK → command（复用现有命令状态机）
  item_status       (PENDING / SENT / SUCCESS / FAILED / SKIPPED / RETRY)
  app_ack_code      (设备返回的结果码)
  retry_count       (重试次数)
  updated_at
  UNIQUE(batch_id, device_id)   -- 同一设备在同一 batch 内只出现一次
```

关键设计点：

- `command_batch_item.cmd_id` 指向现有 command 表，**复用 §9.3-9.5 的全部能力**，不重写命令生命周期。
- `(batch_id, group_no)` 是 barrier 的聚合粒度。
- `mutex_group` 字段（§9.3.5 已预留）复用为 batch 互斥：同一 device 不允许跨 batch 并发，避免两批 OTA 抢同一设备。
- 成员规则 `member_rule` 是结构化规则（见 9.8.4），不是写死的设备列表。

#### 9.8.3 编排流程：group 串行 barrier

```text
1. 业务创建 OTA batch（command_batch 写入，status=PENDING）

2. Batch Scheduler（Command Service 内的 worker）抢占 batch：
   CAS status PENDING → RUNNING，记录 owner（worker 实例）+ lease

3. 启动 group N（current_group=N）：
   a. 成员解析（见 9.8.4）：按 member_rule 查设备档案 DB → 候选 device 列表
   b. 按 group_size 切分，取第 N 组的设备
   c. 对每个设备：
      - 查 presence（Redis）判断在线
      - 创建 command（走 §9.4 完整流程）+ command_batch_item
      - 在线 → command 正常投递 gRPC Deliver(目标 Broker)，item_status=SENT
      - 离线 → command.status=PENDING_DEVICE_ONLINE（复用 §9.5），item_status=PENDING

4. 设备升级完成，上报 cmd_ack：
   - 现有 cmd_ack 闭环更新 command 状态 = APP_ACK_RECEIVED
   - 【新增】Batch Scheduler 消费 cmd_ack（独立 consumer，不与遥测共队，
     见 raw log §8.2 command.ack.raw topic）：
       成功 → item_status=SUCCESS
       失败 → item_status=FAILED + app_ack_code
   - 超时（group_timeout 到期未收到 ACK）→ item_status=FAILED

5. 【barrier 判定】Batch Scheduler 聚合 group_no=N 的所有 item：
   if group_policy == ALL_SUCCESS_NEXT:
     全部 SUCCESS → group N 完成
     任一 FAILED → group N 失败 → 按 failure_policy 处理
   if group_policy == MAJORITY_NEXT:
     SUCCESS 数 / 已决总数 ≥ group_threshold（如 0.95）→ group N 完成
     （未决 item 不计入分母，避免离线设备阻塞判定；超时后转 FAILED 才计入）

6. group N 完成 → current_group=N+1 → 回到步骤 3 启动下一组
   group N 失败 → 按 batch.failure_policy：
     ABORT    → batch.status=FAILED，停止
     CONTINUE → 失败 item 进 RETRY 队列，组间继续推进
     PAUSE    → batch.status=PAUSED，等人工介入

7. 所有 group 完成 → batch.status=COMPLETED（或 FAILED，取决于 failure_policy）
```

#### 9.8.4 group 成员解析：规则化定义

group 成员不是写死的设备列表，而是**规则计算**的结果。两个层次：

```text
规则定义（batch 创建时，member_rule JSON）：
  {
    "filters": [
      {"field": "product_id",     "op": "=",   "value": "INV-3000"},
      {"field": "region",         "op": "=",   "value": "zhejiang"},
      {"field": "firmware_version","op": "<",  "value": "1.5.0"},
      {"field": "status",         "op": "!=",  "value": "DECOMMISSIONED"}
    ],
    "group_size": 500,
    "sort": [{"field": "firmware_version", "order": "asc"}],
    "group_strategy": "SEQUENCE"   // SEQUENCE=按 sort 顺序切组，HASH=按 device_id hash 散列
  }
```

成员解析时机（Batch Scheduler 启动 group N 时）：

```text
1. 查设备档案 DB（按 filters 过滤）→ 候选 device 列表
   重要：这一步查的是设备档案 DB（如 firmware_version / region），不是 Redis presence。
        presence 是「当前在线位置」，不是「设备集合」。两者不能混用。
2. 按 sort 排序（如 firmware_version 升序——低版本先升级，便于灰度）
3. 按 group_strategy 切分，取第 N 组
```

**`firmware_version < target` 过滤**是 OTA 场景的核心规则——已升级到目标版本的设备自动跳过，使 OTA 可重复执行（幂等的批次级语义）。

#### 9.8.5 失败策略（生产必读）

「一组全部成功才下一组」在真实 OTA 里几乎不可行——**500 台设备里 1 台网络抖动失败，整组卡死，剩下所有组全部停摆**。这是 OTA 场景最常见的陷阱。生产里必须支持降级：

| 策略 | 语义 | 适用场景 |
|---|---|---|
| `ALL_SUCCESS_NEXT` | 全部成功才下一组 | **不建议做默认**。单台故障阻塞整批。只在组内设备数极小（<10）且强一致要求高时用 |
| `MAJORITY_NEXT`（**推荐默认**） | 成功率达阈值（如 95%）即下一组 | OTA 主流策略。容忍个别设备失败，失败设备进 RETRY 队列不阻塞主流程 |
| `SKIP_FAILED_NEXT` | 跳过失败设备继续下一组 | 设备间无依赖、失败可容忍的场景（如配置广播） |
| `MANUAL_REVIEW` | 失败后挂起等人审 | 高危升级（涉及断电/停机风险） |

**建议**：`group_policy` 默认 `MAJORITY_NEXT`，每个 batch 可配。失败设备进 `item_status=RETRY` 的独立重试队列（独立 worker、独立节奏，不阻塞 barrier）。重试上限到达后转 `FAILED`，进入人工补升流程。

#### 9.8.6 离线设备处理

OTA 必然有离线设备（网络故障、未开机）。复用 §9.5 的离线命令机制：

```text
group 启动时对每个设备查 presence：
  在线 → 正常投递，等 cmd_ack
  离线 → command.status=PENDING_DEVICE_ONLINE，item_status=PENDING

barrier 判定中的离线语义：
  - MAJORITY_NEXT 下，离线（PENDING）算「未决」不算「失败」，不计入分母
  - group_timeout 到期后，PENDING → FAILED（计入分母）
  - 离线设备上线后（device_seen，§9.5）补投递；
    若已在后续 group 窗口 → 不打断当前组，进 RETRY 队列随下一轮补升
```

**不搞「等待离线设备上线」**——OTA 不应被个别离线设备无限阻塞。group_timeout 是兜底，超时即转 FAILED。

#### 9.8.7 容量与承载（百万级 OTA）

| 维度 | 数量级 | 承载点 |
|---|---|---|
| 单 batch 设备数 | 百万级 | command_batch_item 表（DB 存储，按 batch_id 索引） |
| group 数 | 百万 / 500 = 2000 组 | 串行执行，Batch Scheduler 内存只持当前 group 的计数器 |
| 单 group 投递 | 500 次 presence 查询 + 500 次 downlink 投递 | 分散到多台 Broker（按 device 的 broker_id 自然分布），轻量 |
| cmd_ack 回流 | 500 台 ACK 集中返回 | 独立 command.ack.raw topic，Kafka 分区削峰，Batch Scheduler 作为 consumer group |
| barrier 聚合 | count(group_no=N) | **不每次扫表**——Batch Scheduler 在内存维护当前 group 的 (success/failed/pending) 计数器，cmd_ack 回来时 O(1) 自增。group 切换时落 DB 一次 |

**关键**：串行 group 把「百万 OTA」降成「2000 个 500 规模的小批」，每批处理都是轻量。百万级压力全在 DB 表存储和 cmd_ack Kafka topic，不在 Broker 路由（Broker 仍然是单播定向投递）。

#### 9.8.8 不改什么（现有架构红线不侵入）

```text
不改 Broker 路由模型：
  Broker 仍只收 gRPC Deliver(目标 Broker) 单条命令 → 二次校验 → PUBLISH。Broker 不知道 group 存在。
不改 presence 设计：
  presence 仍是单设备 key，O(1) 查询。group 成员来自设备档案 DB，不查 presence 集合。
不改命令状态机：
  command 表和 §9.3-9.5 状态流转完全复用，外层套 batch_item + batch 两层编排。
不引入 Broker 侧组播/广播：
  §7.6「不做每设备内部订阅」红线不被突破。
不改南向契约面：
  Presence §12.2「Broker 南向契约面不增长」原则不被破坏——group 是 Command Service 内部概念。
```

group 编排是 Command Service 的内部能力，落点在 [Presence §12.1](./2.cloud-mqtt-presence-registry-design.md) 既定的 Command Service（`things/` 模块内），不进 mqtt-gateway 进程，不污染 Broker 性能红线（§3-§5）。

#### 9.8.9 落地阶段

```text
Phase 1-3：先把单条命令状态机（§9.3）、presence（§9.5）、cmd_ack 闭环（§9.4）、
           规则引擎编码跑通。这些是 group 编排的依赖。
Phase 4  ：加 command_batch + command_batch_item 两表 + Batch Scheduler worker
           + group barrier 逻辑 + 失败策略 + RETRY 队列。
           复用 §9.3.5 预留的 mutex_group 字段做 batch 间设备互斥。
```

## 10. QoS 与会话策略

### 10.1 上行 QoS

| 场景 | 建议 |
|---|---|
| 普通遥测 | QoS0 或 QoS1 |
| 结算、质保、故障追溯 | QoS1 |
| 可补传数据 | QoS0 + 设备本地缓存 + 下次补传 |
| 关键事件 | QoS1 + 幂等 key |

QoS1 不等于 exactly-once。服务端和设备侧都必须支持重复消息处理。

### 10.2 下行 QoS

控制命令建议：

```text
MQTT QoS1 + cmd_id 幂等 + APP ACK
```

设备侧应维护近期已处理命令：

```text
cmd_id -> executed / failed / expired
```

重复收到同一个 `cmd_id` 时：

```text
已执行：返回同样的 APP ACK
未执行：执行
已过期：拒绝
```

### 10.3 Session 策略

建议：

```text
CleanSession = true
不支持 Broker 侧离线会话
不支持 Broker 侧离线消息
不支持 retain 遥测数据
不支持 QoS2
```

理由：

```text
逆变器每天自然上下线。
百万级持久会话会使 Broker 变成巨大状态存储系统。
离线命令应由 Command Service 管理。
```

## 11. 连接管理与流量打散

### 11.1 设备上报抖动

必须避免所有设备在整点或 5 分钟边界同时上报。

固件建议：

```text
slot = hash(device_id) % 300
next_publish_time = floor(now / 300) * 300 + slot
```

效果：

```text
100 万设备均匀打散到 300 秒。
平均约 3333 msg/s。
```

### 11.2 连接抖动

设备上电后首次连接：

```text
initial_delay = hash(device_id) % 300s
```

重连退避：

```text
1s, 2s, 4s, 8s, 16s ... max 300s
每次重试增加 full jitter
```

### 11.3 KeepAlive

由于设备每 5 分钟上报一次，业务数据本身可以维持连接活跃。

建议：

```text
遥测为主：KeepAlive = 600s
需要较实时控制：KeepAlive = 240s ~ 300s
```

注意：

```text
LB / NAT / 防火墙 idle timeout 应大于 Broker 判死窗口。
```

### 11.4 LWT 策略

不建议把日落断电作为 LWT offline 事件处理。

建议：

```text
在线状态 = last_seen 推导。
超过 2~3 个上报周期未上报，标记为疑似离线。
结合设备地域、日出日落、电站计划判断是否异常。
```

例如：

```text
last_seen < now - 15min => suspect_offline
last_seen < now - 30min => offline

但如果设备所在地区已日落，则 offline 不告警。
```

### 11.5 接入拓扑与源 IP（v1 修订决策）

> 修订说明：本文原 v1 决策曾把全部设备固定为"L4 透传 + Broker 终结 TLS"，并把"LB 终结 TLS + PROXY protocol"记录为备选。网络攻击防范设计（doc 9）引入普通设备 / 高安全设备分流后，正式修订该决策：普通设备默认由云 TLS LB 终结单向 TLS，高安全设备继续 L4 透传到 Broker 终结 mTLS。

v1 接入拓扑：**普通设备云 TLS LB 终结单向 TLS；高安全设备 L4 透传 + Broker 终结 mTLS**。

```text
普通设备
  -> 云 TLS LB（终结单向 TLS）
  -> Broker（只接受 LB 来源；继续执行 CONNECT 认证和 MQTT 语义防御）

高安全设备
  -> L4 LB（透传模式，如 LVS / NLB TCP 透传）
  -> Broker 终结 mTLS（ECDSA 证书 + session resumption）
```

理由与边界：

```text
1. 普通设备身份来自 MQTT CONNECT 凭证 / token / secret。
   TLS 只承担传输加密和服务端身份校验，因此可以让云 TLS LB 承接单向 TLS
   握手容量、证书托管和基础 TLS 防护。
2. 高安全设备身份来自 TLS 客户端证书。
   Broker 必须直接看到并校验证书，因此高安全入口不能被云 TLS LB 终结，
   必须走 L4 透传，由 Broker 终结 mTLS。
3. 源 IP 仍是 per-IP CONNECT 限流、黑名单（§16）的前置条件。
   普通入口必须验证 source IP preservation 或 PROXY protocol；
   若拿不到可信真实源 IP，必须关闭 per-IP 限流和 ip_blacklist，
   退回 per-device / per-tenant 限流，不能拿 LB 内网地址当设备 IP。
4. 如果普通入口使用 PROXY protocol，Broker 只能在可信 LB 来源连接上解析，
   且解析必须发生在 accept 后、认证 / MQTT 处理前的有界热路径中；
   具体实现红线见 doc 7。
5. LB idle timeout 必须大于 Broker keepalive 判死窗口。
   LB 长连接容量、TLS 握手容量和计费模型必须进入压测与成本评估。
```

旧决策记录（已被 doc 9 修订）：全部设备使用"L4 透传 + Broker 终结 TLS"。该形态保留为高安全 / mTLS 入口的要求，不再作为普通设备默认入口。

压测环境必须按本节分流拓扑搭建并记录 LB 形态、TLS 终结位置和源 IP 透传方式（压测规划 §4）。

## 12. MQTT Gateway 内部设计

Broker 是专用接入层，不是通用 MQTT Broker。它只保留逆变器遥测与低频下行控制需要的能力：

```text
TCP accept
TLS / mTLS
MQTT packet codec
认证
基础 ACL
payload size limit
QoS0/QoS1
keepalive
backpressure
写 raw log
本地下行 PUBLISH
presence 注册
```

Broker 不负责：

```text
解码 700 点位
写时序库
写告警表
复杂规则引擎
长期离线消息
retain
通用订阅系统
```

连接认证首版采用直连数据库方案，但 DB 必须放在缓存、认证队列、worker pool、超时和限流后面：

```text
CONNECT
  -> 基础校验
  -> Broker 本地 auth cache
  -> bounded auth queue
  -> auth worker 查询认证只读库
  -> 认证成功
  -> 写 Presence
  -> CONNACK
```

认证系统过载时返回 `Server Unavailable` 或直接断开，让设备退避重连；不要无限堆积 CONNECT 或扩大 DB 连接池硬扛。

详细认证设计见：

- [云端 MQTT 接入 Broker CONNECT 认证设计](./5.cloud-mqtt-connect-auth-design.md)

每连接状态、协议子集、QoS inflight、下行订阅边界和 raw log appender 伪代码见：

- [云端 MQTT 接入 Broker 与 Raw Log Appender 详细设计](./3.cloud-mqtt-gateway-raw-log-design.md)

## 13. ClientID 冲突与重连

### 13.1 严格模式

新连接踢旧连接：

```text
1. broker-23 收到 INV_001 新 CONNECT。
2. broker-23 查询 presence，发现旧连接在 broker-17。
3. broker-23 写入新 presence（session_version 增加，覆盖旧映射）。
4. 触发对 broker-17 的 Kick(INV_001 + 旧 fencing)。
5. broker-17 校验 fencing 后关闭旧连接。
```

注意 step 4 的 Kick 路径：为保住 broker share-nothing（broker 间不直接通信），不让 broker-23 直连 broker-17。两种可选实现——(a) broker-23 把 takeover 信号交给 Command Service，由其 gRPC `Kick` 目标 broker；(b) 仅 takeover 这一条低频控制调用允许 broker→broker gRPC。但 CONNECT 热路径不应同步调 Command Service（红线：认证热路径不接业务 RPC），所以严格模式的主动 kick 仍是**未决 TODO**。**逆变器场景推荐 §13.2 简化模式**——不主动 kick，靠 session_version + fencing 让旧连接失效、keepalive 超时自然回收，从根上绕开这个跨 broker 难题。

内部消息：

```json
{
  "device_id": "INV_001",
  "old_conn_id": 984231,
  "reason": "client_takeover"
}
```

### 13.2 简化模式

允许短时间双连接，按最新 `session_version` 路由。

流程：

```text
1. 新连接写入 presence，session_version 增加。
2. Command Service 总是路由到最新 session_version。
3. 旧 Broker 即使还没断开，也不会收到新命令。
4. 上行遥测靠 tenant_id + device_id + boot_id + seq 去重。
```

对逆变器遥测场景，推荐简化模式。  
因为上行可幂等，短暂双连接通常可以接受。

安全边界：简化模式默认"两个连接都是真设备的重连"。凭证泄露或异常固件造成的**持续并发在线**（同一 device 的 presence 反复 OK_WITH_OLD、两条连接交替存活）必须可观测：上报 `presence_connect_with_old_count` 并按 device 聚合做 flapping 检测，异常升高时告警并人工介入（踢连接 / 轮换凭证）。这是凭证泄露的早期信号，不是普通重连噪音。

## 14. Raw Log 与解码链路

Raw log 是 Broker 与后续解码、存储、告警之间的削峰和重放边界。

推荐生产主链路：

```text
MQTT Gateway
  -> Kafka / Redpanda raw log
  -> Decoder
  -> 时序库 / OLAP / 告警
```

JetStream 可以用于 PoC、中等规模 raw log 或较短保留周期。生产百万级长期 raw telemetry 主干，优先 Kafka / Redpanda。

详细的 appender 抽象、JetStream / Kafka / Redpanda 选型对比、容量模型、背压策略、故障窗口和压测矩阵见：

- [云端 MQTT 接入 Broker 与 Raw Log Appender 详细设计](./3.cloud-mqtt-gateway-raw-log-design.md)

### 14.1 Raw Message 结构

```json
{
  "device_id": "INV_001",
  "tenant_id": "tenant-a",
  "sample_ts": 1778800000,
  "seq": 1024,
  "boot_id": "boot_abc",
  "schema_id": "modbus_schema_v3",
  "firmware_version": "1.2.7",
  "broker_id": "broker-17",
  "broker_receive_ts": 1778800005,
  "payload_crc32": "0x12345678",
  "payload_binary": "<binary>"
}
```

> 注：本 JSON 是**逻辑视图**。物理上分两层：`tenant_id` / `device_id` / `broker_id` / `broker_receive_ts` 在 envelope（Kafka headers，Broker 按认证主体盖章）；`boot_id` / `seq` / `sample_ts` / `schema_id` / `payload_crc32` / `firmware_version` 在设备 payload header 内，由 Decoder 解析——Broker 不解析 payload（红线）。字段来源权威定义见 [raw log 设计 §3.3](./3.cloud-mqtt-gateway-raw-log-design.md)。

### 14.2 Decoder 职责

Decoder 消费 raw log：

```text
按 schema_id 找点表
解析 700 点位
校验范围
生成宽表或列式数据
写入时序库 / OLAP
触发告警
```

Decoder 堵塞不应影响 Broker。  
Broker 只关心 raw log append 是否成功。

## 16. 故障场景与处理策略

| 故障 | 现象 | 处理策略 |
|---|---|---|
| 日出连接风暴 | 大量 CONNECT 同时到达 | 设备 jitter、Broker accept 限流、认证本地化、LB 扩容 |
| 日出 TLS 握手风暴 | 大量 TLS 握手同时进行，CPU 被非对称运算打满（真正瓶颈往往不是 MQTT 解析） | 普通设备入口由云 TLS LB 承接单向 TLS 握手压力；高安全 mTLS 入口在 Broker 侧使用 ECDSA、session resumption / ticket 复用、accept 层与握手层分别限流（v1 修订拓扑见 §11.5 与 doc 9） |
| 整点上报风暴 | 5 分钟边界瞬时流量高 | hash(device_id) % 300s 打散 |
| 日落断连风暴 | 大量连接关闭、offline 事件暴涨 | 不用 LWT 表示正常日落离线，last_seen 推导 |
| Raw Log 变慢 | QoS1 PUBACK 延迟升高 | 入站限流、日志分区扩容、设备退避 |
| Decoder 堵塞 | 解码延迟升高 | raw log 解耦，decoder consumer 横向扩容 |
| 时序库变慢 | 写入延迟、积压 | Broker 不直接写 DB，raw log 堆积保护 |
| Presence 过期 | 下行查不到设备 | 设备上报触发 pending command 检查 |
| 查到旧 Broker | 下发失败 | Broker 二次校验，返回 NOT_HERE/STALE_SESSION |
| Broker 崩溃 | 其上连接断开 | 设备退避重连，broker lease 过期 |
| 固件 Bug | 设备高频上报或 payload 异常 | firmware 限流、device 熔断、payload limit |
| 重复数据 | QoS1 重试、网络抖动 | tenant_id + device_id + boot_id + seq 幂等 |
| 重复命令 | Broker 重试或设备重连 | cmd_id 幂等、APP ACK 去重 |

## 19. 推荐最终架构原则

1. **Broker 极简化**  
   Broker 只做协议、认证、路由、QoS、raw log append 和本地下行投递。

2. **上行与下行解耦**  
   上行是数据入口，下行是命令状态机，不要混成一个 Broker 内部状态问题。

3. **状态外置**  
   在线位置在 Presence Registry，命令状态在 Command Service，原始数据在 Raw Log。

4. **ACK 前只做最小可靠操作**  
   QoS1 PUBACK 前只保证 raw log append 成功，不等待解码和入库。

5. **所有链路都要幂等**  
   上行按 `(tenant_id, device_id, boot_id, seq)` 去重，下行按 `cmd_id` 去重。

6. **设备侧必须参与削峰**  
   上报与重连都必须基于 device_id 做确定性 jitter。

7. **离线命令不放 Broker**  
   设备离线时，命令由 Command Service 等待，设备上线后再下发。

8. **Presence 可以不准，但 Broker 必须校验**  
   presence 是路由提示，不是最终事实；最终以 Broker 本地 session 为准。

9. **避免每设备内部订阅**  
   Broker 暴露固定的 gRPC 下行 endpoint，Command Service 负责查表（presence + registry）路由直连。

10. **保留 raw binary**  
    点表版本变化、故障排查、历史重算都依赖原始二进制数据。

11. **组件落点：Broker 极简，Command Service 入 things**
    Presence 写在 Broker 内（CONNECT 热路径 + fencing）；Presence 读、下行投递、命令状态机由 `things/` 内的 Command Service 承担——不进 Broker 模块、不单独建仓库，以保住 Broker 的性能红线。Broker 南向只暴露 **gRPC 下行 endpoint** + 共享 **Redis(presence + broker registry/lease，含 gRPC 地址) / Kafka(raw log，仅上行)** 契约。详见 [Presence Registry 设计 §12](./2.cloud-mqtt-presence-registry-design.md)。

12. **下行通道选型：NATS → gRPC 单播（2026-06-20 收敛）**
    下行通道经历了 NATS → Kafka → **gRPC 直连单播** 两次迭代，最终收敛为：**单播走 Command Service → gRPC 直连目标 Broker，广播拆成 N 条单播，Kafka 只承载上行 raw log（下行全程不沾 Kafka）**，中间件为 **Kafka + Redis 两件**（去掉 NATS）。
    - **为什么不是 Kafka 下行**：下行的「可达性」由 Command Service 的 DB 状态机拥有（status/retry/TTL/outbox/lease），Kafka 的 at-least-once 与之冗余；且目标 Broker 是 presence 的函数，投递失败时正确动作是「重查 presence 重投」（fail-fast + re-resolve），而 Kafka「留存等消费」对一个会过期的路由决策语义错误（目标已 stale）。把 Kafka 用于单播定向投递还会撞 §7.5/红线 §10（消费组随机消费 / 分区路由把可达性误放到传输层）。
    - **为什么不是 broker→broker 转发**：会重新引入 broker 间 mesh（违反 share-nothing），且单 group 下 (N-1)/N 的命令都要转发，是常态开销；produce 时已从 presence 知道目标，应直接投对，不该盲投再转发。
    - **消费/寻址模型**：Command Service 查 presence(device_id) → 查 Broker Registry(Redis) 取目标 Broker 的 gRPC 地址 → gRPC `Deliver(envelope + fencing)` → Broker 二次校验本地 session → MQTT PUBLISH → 同步回 PUBACK/NOT_HERE 驱动状态机。这是 1×N 调用（Command Service → 各 Broker），不是 broker→broker mesh。
    - **广播/批量**：Command Service 查设备档案 DB 解析成员 → 拆成 N 条单播 → 限速下发（复用 §9.8 OTA 编排）。Broker 零组播逻辑（删掉早期 §7.8 的 Session.filters + Kafka 广播 topic + scope 匹配）。
    - **收益**：中间件 3→2（去 NATS，且未引入 Kafka 下行）；下行延迟 ~1-5ms（gRPC，优于 Kafka ~10-50ms）；下行与上行 raw log 解耦，无爆炸半径混叠；零新增中间件（gRPC + broker registry 都已有，与 things 服务 etcd+gRPC 互调同构）。
    - **仍优于 Zilla 的点**：session 外置 Redis（不进 Kafka compacted topic），寻址准确性 + 僵尸 session 清理优势保留。详见 [Zilla 对比报告](./reference/aklivity-zilla-comparison-report.md)。

## 20. 一句话总结

```text
你不需要实现一个完整 MQTT Broker 集群。
你需要实现一个极简、无状态、可削峰、可幂等的逆变器 MQTT 接入层。

上行：
设备 -> 任意 Broker -> raw log -> 异步解码。

下行：
Command Service -> Presence Registry -> gRPC 直连指定 Broker -> 本地 MQTT 连接 -> 设备。
```

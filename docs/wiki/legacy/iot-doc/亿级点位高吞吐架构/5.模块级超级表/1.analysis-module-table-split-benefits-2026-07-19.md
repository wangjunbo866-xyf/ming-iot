# 设备按模块切分多表：收益分析与切分判据

> 场景：百万设备 × 500 测点，产品按模块组合（公共/混逆/储能/召测等），回答"设备数据该一设备一张表，还是按模块切多表"。
> 配套文档：[模块级超级表设计](./design-module-level-supertable-2026-04-15.md.md)、[模块级超级表优化](./design-module-level-supertable-optimization-2026-04-23.md%20(1).md)、[TDengine 高效写入（第五章源码分析）](../TDengine时序库/high-throughput-writing.md)
> 版本前提：TDengine ≥ 3.3.6.0（超级表 KEEP 特性），当前集群 3.3.6.34 满足。

---

## 一、结论速览

**满足以下任一条件即应切分，满足越多越该果断切：**

| # | 切分判据 | 判据背后的 TDengine 机制 |
|---|---|---|
| 1 | 模块间**保留期/数据价值**不同 | 超级表级 KEEP（3.3.6.0+），库内直接差异化，无需拆库 |
| 2 | 存在**按需召测/异频采集**模块 | 宽表一行一 ts，异频共表 = NULL 填充吃掉宽表红利 |
| 3 | 模块被**多个子产品共享且持续演进** | 超级表 = schema 管理单元，共享模块只应有一份定义 |
| 4 | 有**跨产品 fleet 级聚合**查询需求 | TDengine 聚合以超级表为单位，模块表一条 SQL，合并表需 M 路 union |
| 5 | **SKU 持续增加**、新模块横向推广 | 模块化 = 组合零 schema 工作；合并表 = 每 SKU 一张新超级表 |

**反面条件（全部成立则不切，一设备一表更优）**：全部点位同频同保留期同价值、子产品少且封闭、公共字段基本冻结、查询以单设备详情页为主。

## 二、决策的物理基础：TDengine 成本模型

切分讨论的每一步都落在以下四个机制上（源码证据见 [高效写入第五章](../TDengine时序库/high-throughput-writing.md)）：

1. **写入按"行"和"表"计费，不按"点位"计费**：每行一次 memtable 跳表插入（`tsdbMemTable.c:718`）、每行一份 ts key；每表一次 meta 校验 + 独立 `STbData` 结构。一行塞 200 列与塞 10 列成本几乎相同——这是"宽表红利"，也是切分成本的来源。
2. **超级表是 schema 管理单元**：列定义、ALTER、子表继承都以超级表为边界；ALTER 使该表全部子表 sver 升版，客户端缓存 meta 失效、下次写入被拒后刷新重试（`vnodeSvr.c:2479`）。
3. **保留策略三级**：
   - **DB KEEP**：文件组级整文件裁剪（`tsdbRetention.c:281`），最便宜但是全库统一；
   - **超级表 KEEP**（3.3.6.0 新增）：`CREATE/ALTER STABLE ... KEEP Nd`，**compaction 时按行物理清除**（官方 [release notes](https://docs.tdengine.com/releases/notes/3.3.6.0/)；测试 `test/cases/04-SuperTables/01-Create/test_stable_keep_compact.py`）；
   - **表级 TTL**：整表寿命到期自动 drop（`metaTtl.c`），是"表寿命"不是行级过期，不适用本场景。
4. **行宽/列数上限**：单行 ≤ 64KB（`TSDB_MAX_BYTES_PER_ROW = 65531`）、非虚拟列 ≤ 4096（`tdef.h:280-281, 357`）。500 点位远未触顶，不构成切分理由。

## 三、切分的收益（按强度分级）

### 强理由（结构性，不随运维努力消失）

**1. 保留期/价值等级按模块差异化 —— 超级表 KEEP（本场景最有分量的一条）**

- 机制：单库 `KEEP 3650` 兜底（高价值数据长期归档），低价值模块超级表 `KEEP 90d`，到期由 compaction 物理清除。
- 相比两个旧方案全面占优：
  - ~~拆库~~：无需多 DB、无跨库查询受限、无 vnode/内存规划复杂化；
  - ~~手工 DELETE 作业~~：无 tombstone、无 raft 写放大、零作业运维（DELETE 走 `TDMT_VND_DELETE` raft 复制 + memtable 写删除标记，`tsdbMemTable.c:155`，空间要等 compaction 间接回收——STB KEEP 直接借 compact 清除，是原生路径）。
- 约束（必须接受）：
  - **回收滞后于 compaction**：过期行在 compact 前仍占空间、仍可查；容量规划按"短 KEEP + 一个 compact 周期"留余量；可 `COMPACT DATABASE` 手动触发；
  - **只能缩短、不能延长**：DB KEEP 是硬上限，写入超出 DB KEEP 的历史数据被拒（"Timestamp data out of range"）；归档期必须设在 DB 上。
- 模块恰好是价值等级的天然边界，切分后此收益自动获得——这是"按模块切"区别于"按子产品合并"的独有优势。

**2. Schema 单一事实来源，公共字段零漂移**

公共模块字段只定义一次、ALTER 一次。按子产品合并的方案中公共字段存在 M 份定义，每次演进需同步 M 张超级表，漏同步即产生同名字段类型/单位漂移——数据债务在跨产品分析时集中爆发。子产品数 M > 3 且公共模块仍演进时，此理由为强。

**3. 跨产品 fleet 级聚合是原生路径**

"全部在运设备的电网电压"：模块方案 = 公共模块超级表 + tag 过滤一条 SQL；合并方案 = M 张超级表分别查再应用层 union。BI 报表、fleet 监控、跨产品对标越多，此理由越重。

**4. 新 SKU / 新模块的 schema 成本趋零**

- 新子产品 = 选模块组合直接建子表，无新超级表、无 ALTER、无字段复制；
- 新模块推广到 K 个子产品 = 建 1 张超级表（合并方案 = ALTER K 张且需保证 K 份定义一致）；
- 超级表数量 = 模块数（个位数），而非 SKU 数（可能几十上百）——schema 治理对象最小化。

### 中理由（工程性，可用工具对冲但切了更省）

**5. 差异化策略的天然落点**

- **按需召测模块**：不常规上报，合入主表则每行整段 NULL（bitmap + 存储浪费），**必须切出**；与 [优化文档](./design-module-level-supertable-optimization-2026-04-23.md%20(1).md) 的冷热分层（`property_tsdb` / `property_no_store`）天然对齐；
- **异频采集模块**：宽表一行一 ts，异频共表只能按高频写（低频列 NULL 填充）或按低频写（丢高频数据）；也可同表列子集写（`INSERT INTO tb (ts, c1, c5) ...`）作为中间路线，拆表换来的是查询语义清晰（每表自己的 ts 序列、`last()` 缓存按表生效）；
- **权限/数据开放**：表是权限与 TMQ 订阅的自然单元，"公共模块开放给第三方、储能模块不开放"只有切表能做到。

**6. schema 变更的写入抖动面更小**

ALTER 使该超级表全部子表 sver 升版、客户端 meta 失效重刷。模块表变更只抖动该模块的写入流；合并大表任何字段变更都让整张 500 列大表升版，全部点位写入流一起刷新。字段变更越频繁此收益越大。

### 弱理由（真实但不该主导决策）

**7.** 设备物模型与云端 schema 同构（固件按功能模块组织，SDK/边缘代码按模块复用）；**8.** 多固件版本字段微差异由模块表加列统一承载，避免 SKU × 固件版本组合爆炸。

## 四、切分的成本（必须正视）

每多切一张表，每设备每上报窗口多付：

| 成本项 | 机制 | 量级 |
|---|---|---|
| +1 行写入 | 1 次跳表插入 + 1 份 ts key + 1 个 SQL 表子句解析 | 小（3~6 张可忽略） |
| +1 子表元数据 | meta entry、`sEntryCache`、memtable `STbData`、catalog 缓存 | 小（百万级设备下每表 ~百字节级） |
| 单设备全点位查询变 join | N 张表按 ts 对齐（前值填充/窗口拼接） | **中——切分的主要代价** |
| 宽表红利稀释 | 行数 ×N，WAL/memtable 按行计费的部分同步 ×N | 小~中 |

**对照方案（按子产品合并成一表）**：写入最优（一设备一行）、单设备查询最优，但公共字段 M 份定义 + fleet 聚合 M 路 union + 丧失 STB KEEP 差异化落点。判据见第五节反面条件。

## 五、切分判据决策矩阵

| 判据 | 成立 | 不成立 |
|---|---|---|
| 模块间保留期/价值不同 | **果断切**：STB KEEP 库内差异化 | 保留期统一 → 此条不构成理由 |
| 存在按需召测模块 | **必须切出**（否则 NULL 填充吃宽表红利） | 全量常规上报 → 不切 |
| 模块间采集频率差异大 | 切，或同表列子集写（看查询语义偏好） | 全同频 → 不切 |
| 模块被多子产品共享且演进 | **果断切**（schema 单一来源 + ALTER 1 次） | 模块=子产品独占且稳定 → 可合并 |
| 跨产品 fleet 聚合需求 | 切（原生聚合路径） | 查询全是单设备详情 → 倾向合并 |
| SKU 持续增加 | 切（新 SKU 零 schema 工作） | 产品线封闭 → 可合并 |
| 数据开放/权限按模块 | 切 | 无此需求 → 不构成理由 |

**静态元数据（版本号、名称、固件）不参与切分讨论**：应放 TAGS（存元数据、每子表一份、写入零成本）；需变化历史的慢变点位才考虑独立慢变表，且常量列压缩率极高，收益有限。

## 六、量化估算（本场景）

**写入成本**：每设备每 5 分钟窗口，切 3 表 = 3 行 vs 合并 1 行——多 2 次跳表插入 + 2 份 ts key + 2 个表子句，相对 500 列的行内解析成本可忽略（<5%）。

**存储节省（STB KEEP 差异化）**：设低价值点位数据占比 `p`、低价值保留 `t1` 天、高价值保留 `t2` 天（DB KEEP），则相对"全量留 t2"节省空间约：

```
p × (t2 − t1) / t2
例：p=80%、t1=90、t2=3650 → 省 ≈ 78%
```

**schema 变更成本**：公共模块加 1 列，切分方案 = ALTER 1 张超级表（全部子产品继承）；按子产品合并 = ALTER M 张超级表 + 保证 M 份定义一致。

## 七、落地检查清单

- 切分维度只对准三个判据：**schema 组成/变更节奏**（超级表边界）、**保留期**（STB KEEP）、**采集/上报方式**（常规 vs 召测/异频）；
- 静态元数据一律 TAGS，不为"变化频率低"单独切表；
- 召测/冷点位模块独立成表（或 `property_no_store` 不入 TDengine），常规热点位合并成模块主表；
- 容量规划按"短 KEEP + 一个 compact 周期"估算低价值数据的空间峰值；
- 产品线演进路线确认：SKU 增长、模块共享度、公共模块变更频率——三者任一走高，模块化切分长期收益越大。

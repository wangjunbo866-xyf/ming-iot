# Kafka 原生消息架构设计：从 NATS 代码基线重建 ming-iot

- 日期：2026-07-27
- 状态：架构方向已确认，书面设计评审中
- 适用范围：`ming-iot` 新平台的数据面、领域事件面，以及 Scene Runtime 的 Kafka 接入与物理边界；Scene wire、业务状态/求值与 Action Outbox 由[场景主规格总纲](../6.规则引擎与场景联动/场景联动 Runtime 主规格总纲.md)定义，partition ownership、Manager/Actor、completion、restore、rebalance 与 Zombie 由[Runtime 调度分章](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-scope)定义

## 0. 结论先行

本项目虽沿用“NATS 迁移至 Kafka”的说法，实际执行的是 **Kafka-only 绿地重建**，不是运行中间件平滑迁移：

- 不兼容 NATS Core、JetStream、NATS subject、queue group 或旧 `MsgHead`；
- 不实现 NATS/Kafka 适配层、桥接、双写、灰度切换或历史消息搬运；
- 不保留可切换 `EventConf.Mode` 和最小公分母式 `Publish/Subscribe` 接口；
- 新业务从第一天只写 Kafka 原生契约；旧代码只作为业务语义盘点材料；
- Kafka 只承载需要持久日志、分区顺序、消费进度或重放的事实，不把缓存通知、WebSocket 广播和进程内回调一律伪装成 Kafka 消息；
- 场景联动不是“新增一个 Kafka consumer”这么简单；Topic/wire、current Binding/SubjectContext、状态业务语义与 Action Outbox/producer 失败窗口服从场景主规格总纲，动态 partition ownership、Manager/Actor 执行、completion、restore、rebalance 与 Zombie 服从[Runtime 调度分章](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-scope)，不能从 Kafka 通用能力反推另一套 Runtime 正确性模型。

生产数据主链路冻结为：

```text
Device
  │ MQTT
  ▼
EMQX / Access Adapter
  │ 原始 payload，acks=all
  ▼
Kafka Durable Raw
  │ ProtocolApplication：consume → transform → produce
  │ 同一 Kafka transaction 提交 outputs + Raw next-offset
  ▼
Kafka Durable Canonical / lifecycle / schedule facts
  ├─ Timeseries Materializer
  ├─ Reducer / Projection
  ├─ Flink（需要高级流计算时）
  └─ Scene admission / normalization
                          │ scene_event
                          ▼
                 Go Scene Runtime
                 ├─ partition-local Actor 内存状态
                 ├─ 异步 best-effort scene_state 完整状态
                 ├─ PostgreSQL Action Outbox + deterministic effectId
                 └─ 无 RocksDB、Kafka EOS 或跨 Topic transaction
```

低频 saas/things 领域状态继续以 PostgreSQL 为事实来源：

```text
业务事务：domain row + outbox row
                    │ 至少一次 relay
                    ▼
             Kafka Domain Event
                    │
       consumer inbox + projection transaction
```

这里的 Kafka transaction 指 Raw → Canonical 等本文明确标注的非 Scene 流程，只在 **同一 Kafka 集群内**提供原子性，不能覆盖 PostgreSQL、TDengine、设备命令、Webhook 或第三方系统。Scene V1 不使用 Kafka transaction 提交 state/input offsets；外部副作用统一使用稳定幂等键收敛。

### 0.1 新手先记住的术语

| 术语 | 本文中的含义 |
| --- | --- |
| record | Kafka 中的一条记录，由 topic、partition、offset、key、headers、value、timestamp 组成 |
| partition | topic 内的有序追加日志；Kafka 只保证同一 partition 内的顺序 |
| key | producer 用来选择 partition 的稳定 bytes；相同 key 在 partition 数不变时进入同一 partition |
| consumer group | 一个业务投影的稳定消费身份；组内多实例竞争 partitions，不是“所有实例广播” |
| next-offset | consumer 下一条要读的位置；若已处理 offset 9，提交值是 10 |
| LSO / `read_committed` | LSO 是受未决 transaction 影响的当前可见边界；`read_committed` 只返回已提交记录 |
| Kafka transaction | 将同一 Kafka 集群内的多条输出与 consumer group offsets 原子提交 |
| `transactional.id` | Kafka 用来识别并 fence 旧 producer 的稳定身份 |
| RF / minISR / `acks=all` | RF 是副本数；minISR 是允许成功写入的最少同步副本；`acks=all` 要求所有当前 ISR 确认 |
| compaction | 每个 key 最终只需保留最新 value 的日志清理方式；不是传统数据库快照 |
| tombstone | value 为 null 的删除记录；它自身也可能在 `delete.retention.ms` 后被清理 |
| Outbox / Inbox | 用数据库本地事务记录待发布事件 / 已消费事件，以稳定 ID 收敛跨系统重复 |
| lane | 同一 `(tenantCode, subjectKey)` 经 `routeKeyBytes` 路由后，在一个 `scene_event` partition 中形成的串行处理序列 |

## 1. 背景与设计依据

### 1.1 当前代码是需求清单，不是迁移目标

联犀基线中的事件实现暴露了需要重新设计的语义：

| 当前实现 | 代码证据 | 问题 | 新平台结论 |
| --- | --- | --- | --- |
| 消息到达后先 `Ack()`，再开 goroutine 反序列化和执行业务 | [`share/events/nats.go`](../../../share/events/nats.go) | 业务失败时消息已经确认，无法可靠重投；goroutine 还绕开了分区顺序和背压 | Kafka consumer 在业务效果完成后推进 next-offset；瞬时错误暂停 partition 并重试 |
| `FastEvent` 是进程级单例，handler 再开 goroutine | [`share/eventBus/fastEvent.go`](../../../share/eventBus/fastEvent.go) | 不表达 consumer group、offset、rebalance、顺序与错误策略 | 不移植 `FastEvent`，各 runtime 直接拥有 Kafka 处理循环 |
| JetStream 启动时删除 durable consumer，并从 `DeliverLast` 开始 | [`share/clients/nats.go`](../../../share/clients/nats.go) | 重启语义会丢历史；consumer 名与 IP、节点、subject 耦合 | consumer group ID 是稳定业务投影身份，不包含 Pod IP |
| `server.>`、`device.>`、`application.>` 使用 `InterestPolicy`，最长仅保留 2 分钟 | [`share/clients/nats.go`](../../../share/clients/nats.go) | 不能承担 72 小时 Raw、停机追赶和可控重放 | Kafka topic 按事实类型冻结 retention、compaction 和副本策略 |
| `MsgHead` 携带 `Trace/Timestamp/Data/UserCtx` | [`share/events/events.go`](../../../share/events/events.go) | 缺少稳定 event ID、事件类型和契约版本；把请求权限上下文传播成异步事实 | 使用版本化领域/自动化契约；只传播最小 actor/audit 引用，不传播 `UserCtx` |
| NATS wildcard、临时 request/reply subject、动态数据库订阅 | `things` 与 `ming-iot` 的订阅启动代码 | Kafka topic 不是 subject，临时订阅也不是 Kafka 的强项 | 使用受管 topic catalog、RPC、CommandExecution 和类型化 action registry |

因此，本设计不追求“NATS API 在 Kafka 上还能运行”。业务能力必须先归类，再选择 Kafka、数据库事务、RPC、Redis 或进程内调用。

### 1.2 与总体架构的关系

本文是 [`enterprise-iot-platform-architecture-design.md`](../enterprise-iot-platform-architecture-design.md) 的 Kafka 物理与运行语义补充。发生冲突时采用以下规则：

1. 总体架构定义平台边界、容量锚点和最终产品承诺；
2. 本文定义 Raw、Canonical、领域事件等非 Scene 流程的 Kafka topic、客户端、事务、恢复和 NATS 代码替换规则；
3. [场景主规格总纲](../6.规则引擎与场景联动/场景联动 Runtime 主规格总纲.md)定义 Scene 的 Topic/wire、Binding/状态业务语义、matching/evaluation、Action Outbox 事务、route/hash 与 producer 交付窗口；
4. [Runtime 调度分章](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-scope)定义 Scene 的动态 partition ownership、Manager/Actor 执行、PartitionRuntimeContext、completion、restore、rebalance 与 Zombie；本文只细化与两章一致的 Kafka 物理接入；
5. 四份文档出现冲突时必须在同一次变更中显式修订全部受影响的规范性段落，不能依靠权威排序或“后写文档自动覆盖前文”；同步完成前，冲突部分不得作为已冻结实施契约。

本次联合修订已经完成以下范围收敛：

- 撤销本文旧 §5.3/§8 对 Scene Runtime 的 RocksDB、Kafka EOS、事务 checkpoint、commit attestation 和远端 snapshot/manifest 方案；
- Scene V1 改用主规格总纲定义的 `scene_event`、异步 best-effort `scene_state`、PG Action Outbox 与 current `SubjectContext`，并由 Runtime 调度分章定义其 partition-local 执行与接管；
- Scene Admission/Runtime 全链路执行必填 `ProcessingContext` 与 `SCENE_ID_V2` 门禁；`BACKFILL` 在 matching 前旁路，Scene V1 不执行 `REPLAY` 求值；
- 父架构旧“state/timer/AlarmSignal/ActionIntent 与 Outbox 同一 PG 本地事务”不再适用于 Scene；PG 原子边界只有 Action Outbox，state/timer 与 producer 交付顺序服从主规格总纲，partition completion 与 offset 推进服从[Runtime 调度分章 §5](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-normal-completion)；
- `automation.input.live` 等旧 Topic 与新契约不是 wire-compatible 改名，完整处置矩阵见 §5.3；
- Raw → Canonical Kafka transaction、Domain Outbox，以及 protocol/model/ownership 自身需要的 cutover 不受撤销范围影响。

后续发现同一 Runtime 的新冲突时仍适用上述同次修订门禁；任何一份文档都不能单方面宣布另一份规范失效。

### 1.3 设计目标

- 100 万逻辑设备、每报告 500 points 的容量模型下，数据面可水平扩展；
- Raw 先持久化，协议修复后可重放；
- 对同一 `subjectKey` 的场景 `LIVE` 输入形成唯一、可恢复的 processing-order lane；
- 任何 offset 推进都有明确的“处理完成”定义；
- 外部副作用允许重试但不会因重放重复生效；
- broker、consumer、数据库或进程在关键提交点崩溃后，结果可解释、可恢复；
- topic、group、principal、quota、retention 和 schema 均受版本控制；
- 本地开发保持足够简单，生产基线不以单机配置冒充高可用。

### 1.4 明确不做

- NATS 历史消息导入；
- NATS 与 Kafka 双写比对；
- NATS subject 到 Kafka topic 的一一机械映射；
- 每设备、每场景或每租户创建 topic/consumer group；
- 跨 Kafka 与 PostgreSQL 的“全局 exactly-once”宣传；
- 运行时任意创建 topic、任意订阅正则或由数据库直接配置 topic 名；
- 使用 Kafka 替代同步 RPC；
- 让设备 `deviceTime` 决定 V1 场景联动的分区处理顺序；
- 在生产使用 PLAINTEXT、自动建 topic、单 broker 或 RF=1；
- V1 云端同时维护 Kafka Streams/JVM 和 Go 两套场景运行时。

## 2. 方案比较与最终选择

| 方案 | 描述 | 优点 | 代价/风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. Kafka 原生双平面 | 数据面 Raw/Canonical 使用 Kafka 原生契约；领域面使用 PostgreSQL Outbox；Scene Runtime 按主规格总纲与 Runtime 调度分章使用 `scene_event/scene_state` best-effort 协议 | 各链路的 durability、offset 与失败窗口明确；不会被 NATS API 限制，也不把 Kafka EOS 强加给 Scene | 需要分别掌握 Raw transaction、普通 consumer 与 Scene best-effort 恢复边界 | **采用** |
| B. 保留 `FastEvent`，增加 Kafka adapter | 继续暴露 `Publish/Subscribe/QueueSubscribe` | 初期改动看似较小 | 无法表达 read-committed、事务 offset、partition revoke、DLQ 与广播差异；长期形成错误抽象 | 拒绝 |
| C. 场景直接采用 Kafka Streams | JVM Kafka Streams + RocksDB/changelog/EOS | 状态底座成熟 | 团队当前主栈是 Go；动态规则、倒排索引、领域 timer/outbox 仍需自建；引入双运行时 | 仅作为实现对照，不进入 V1 |
| D. 所有消息均走 PostgreSQL/Redis | Kafka 只存设备 Raw | 技术种类少 | 高吞吐、回放、分区状态和停机追赶成本高 | 拒绝 |

Go Kafka 客户端选择 `github.com/twmb/franz-go`。版本基线为 2026-07-01 发布的 `v1.21.5`；它公开标明支持到 Kafka 4.2+，因此 Phase 0 必须用 Kafka 4.3.1 实测事务、rebalance、故障注入和性能后才能进入 Phase 1。业务代码直接依赖项目内按职责封装的 producer/consumer runtime，不复刻通用 EventBus。

## 3. Kafka 的职责边界

### 3.1 两个逻辑平面

V1 默认使用一个物理 Kafka 集群，但配置上从第一天区分：

| 平面 | 内容 | 配置入口 | topic prefix | principal / group namespace |
| --- | --- | --- | --- | --- |
| Data Plane | Raw、Canonical、quarantine、`scene_event/scene_state`、replay | `DataKafkaBootstrapServers` | `iot.data.*`、`scene_*`、`iot.replay.*` | `data-*` / `iot.data.*` |
| Domain Plane | saas/things 领域事件、发布快照、集成事件 | `DomainKafkaBootstrapServers` | `platform.*` | `domain-*` / `platform.*` |

两个 bootstrap 配置在 V1 可以指向同一集群，但必须使用不同 principal、ACL、quota、client ID、consumer group 前缀和告警。未来将 Domain Kafka 拆出时，Raw 与 Canonical 仍留在同一 Data Kafka，以保留 consume-transform-produce transaction。

### 3.2 Kafka 不承担的能力

| 需求 | 正确实现 | 不使用 Kafka 的原因 |
| --- | --- | --- |
| 同进程无状态回调 | 直接函数调用或有界 worker queue | 不需要持久、重放或跨进程 |
| 同步查询/命令受理 | gRPC/HTTP + PostgreSQL transaction | 请求方需要即时业务结果，不是日志消费 |
| 本地缓存失效 | 版本化 projection + 短 TTL；必要时 Redis version | 单 consumer group 会漏掉其他副本，多个 group 又难治理 |
| WebSocket 连接投递 | session registry + edge fanout；Kafka 只记录 durable notification fact | 每个 API Pod 都消费广播会放大流量，单 group 又无法覆盖全部本地连接 |
| 设备命令结果等待 | `CommandExecution` 状态机 + correlation ID + 查询/推送 | 不创建临时 reply topic 或临时 consumer group |
| 任意脚本订阅消息 | 类型化 trigger/action registry | 任意 topic/正则破坏 ACL、容量和 schema 治理 |

## 4. 版本与部署基线

### 4.1 版本

| 组件 | 基线 | 约束 |
| --- | --- | --- |
| Apache Kafka | `4.3.1`，KRaft | Phase 0 验证通过后锁定镜像 digest；升级必须重复事务与兼容测试 |
| Go | 与平台 Go Workspace 一致 | 不为 Kafka 单独引入 JVM 业务服务 |
| franz-go | `v1.21.5` | Kafka 4.3.1 兼容性由 Phase 0 验证报告签字 |
| 协议契约 | repository-managed `.proto`/descriptor + compatibility check | V1 不依赖外部 Schema Registry 可用性 |

Kafka 4.x 不再使用 ZooKeeper。开发、测试与生产使用同一大版本，避免教程环境与生产语义脱节。

### 4.2 环境拓扑

| 环境 | 拓扑 | 可接受用途 | 禁止误解 |
| --- | --- | --- | --- |
| 本地开发 | 1 个 combined broker/controller，单副本 | 学习、单元/集成测试、手工观察 | 不代表 HA、ISR 或 broker 故障能力 |
| CI | 1 节点快速套件 + 3 节点故障套件 | 契约、事务、rebalance、故障注入 | 不能只跑 happy path |
| Phase 1 生产试点 | 至少 3 broker，RF=3、minISR=2；若使用 3 个 combined 节点必须披露风险 | 单客户生产试点 | 不能降为单 broker |
| Enterprise GA | 3 个独立 controller + 至少 3 broker，跨故障域部署 | 正式 HA 承诺 | controller 与 broker 同宿主不是最终形态 |

生产基础配置：

```text
process.roles                         = broker 或 controller
auto.create.topics.enable             = false
unclean.leader.election.enable        = false
default.replication.factor            = 3
offsets.topic.replication.factor      = 3
transaction.state.log.replication.factor = 3
transaction.state.log.min.isr         = 2
```

broker / topic 级耐久基线：

```text
replication.factor      = 3
min.insync.replicas     = 2
```

producer 级耐久基线：

```text
producer acks           = all
producer idempotence    = true
```

无法满足 minISR 时，写入必须失败并触发背压或入口保护，不能降级为不耐久成功。

### 4.3 生产安全基线

- 集群内外链路启用 TLS；
- 默认使用 SASL/SCRAM-SHA-512 的独立服务 principal；需要双向证书的交付环境可切换 mTLS profile；
- secret 由部署平台注入，不写入仓库、镜像、日志或 metric label；
- `allow.everyone.if.no.acl.found=false`；
- topic、group、transactional ID 分别授权，producer 不自动获得 consumer group 权限；
- 本地开发可使用 PLAINTEXT，但 compose 文件必须显著标注 `LOCAL_ONLY`，且该 listener 不进入生产 values；
- Raw payload、quarantine 和 replay 可能含敏感设备数据，其 ACL、审计、加密和删除策略至少与 Canonical 同级。

## 5. Topic Catalog

### 5.1 命名规则

逻辑名称使用：

```text
<domain>.<plane>.<fact>.<major-version>
```

需要冻结分区数和 key 映射的物理 topic 增加 generation：

```text
<logical-topic>.gNN
```

例如：

```text
iot.data.raw.v1.modbus-tcp.g01
iot.data.canonical.telemetry.v1.g01
scene_event.g01
scene_state.g01
```

`gNN` 是 topic 代，不是 schema 版本。任何会改变同 key 分区映射的扩容都创建下一代 topic 并执行有边界的 cutover；禁止直接给有序/有状态 topic 增加 partition。topic catalog 记录逻辑名、物理名、partition 数、key codec、partitioner、retention、schema major、owner、ACL 和生效位置。

### 5.2 数据面 topic

下表中的 retention 是逻辑基线；毫秒值由部署生成器统一计算，禁止手填多个互相矛盾的单位。

| 逻辑 topic | Key | Value | cleanup / retention | 生产者 | 消费者 |
| --- | --- | --- | --- | --- | --- |
| `iot.data.raw.v1.<protocolKey>` | 可信 transport identity bytes | 原始 MQTT payload bytes | `delete` / 72h / `LogAppendTime` | Access Adapter/Gateway | 对应 ProtocolApplication production group |
| `iot.data.canonical.telemetry.v1` | 可信 canonical device key bytes | 完整 `PropertyReport` batch | `delete` / 24、48、72h 中经 Phase 0 冻结一档 | ProtocolApplication | Materializer、审计摘要、未来 Flink、Scene admission |
| `iot.data.canonical.device-event.v1` | 可信 canonical device key bytes | append-only `DeviceEvent` | 同 Canonical 档位 | ProtocolApplication | reducer、审计、未来 Flink、Scene admission |
| `iot.data.canonical.lifecycle-observation.v1` | 可信 canonical device key bytes | 连接/会话 observation | 同 Canonical 档位 | Adapter/Gateway/ProtocolApplication | presence reducer |
| `iot.data.canonical.command-reply-observation.v1` | 可信 canonical device key bytes | 命令回复 observation | 同 Canonical 档位 | ProtocolApplication | command reducer |
| `iot.data.canonical.outcome.v1` | source identity | `NO_OUTPUT`、受控处理 outcome | `delete` / 至少与 Canonical 相同 | ProtocolApplication | audit/ops |
| `iot.data.quarantine.ingress.v1` | raw identity | 非法 transport/topic/raw metadata | `delete` / 7d 起，按合规调整 | Adapter/Gateway | ops |
| `iot.data.quarantine.protocol.v1` | raw identity | decode/schema/budget error + payload ref | `delete` / 7d 起，按合规调整 | ProtocolApplication | ops/reprocess tool |
| `iot.data.quarantine.automation.v1` | automation input identity | 非法契约、超预算、不可恢复求值错误 | `delete` / 7d 起 | Automation Runtime | ops |

Raw topic 冻结 `message.timestamp.type=LogAppendTime`，72 小时从 broker durable append timestamp 起算，不信任 Adapter 主机时钟。`retention.bytes` 默认 `-1`。若部署必须设置 size limit，其每 partition 下限必须覆盖最热 partition 在已接纳容量内 72 小时的实测压缩写入、segment/index 和安全余量，不能早于 72 小时时间承诺淘汰。

所有受管 Kafka topic 都显式设置 `message.timestamp.type=LogAppendTime`，禁止静默继承 broker 默认值。Kafka record timestamp 只用于 retention、日志年龄和运维；业务 `occurredAt/observedAt/deviceTime` 始终放在 value 中，replay 保留原业务时间但由目标 broker 生成新的 append timestamp。这样历史业务时间不会让新写入的 replay/Domain record 被立即按 retention 淘汰。

Canonical retention 使用：

```text
Tcanonical >= 最大允许停机时间
             + 故障发现与修复时间
             + 积压追赶时间
             + 安全余量
```

产品基线不得低于 24 小时。Canonical 超期后的重算回到 Raw 或合规对象归档。

### 5.3 场景联动 topic

本节只登记 Kafka 物理角色。SceneEvent/SceneBindingState wire、Topic/key/route、Action Outbox 与 Producer 交付窗口以[场景主规格总纲 §§5、8、12–14](../6.规则引擎与场景联动/场景联动 Runtime 主规格总纲.md)为准；动态 partition ownership、completion、restore 与 rebalance 以[Runtime 调度分章 §§5–10](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-normal-completion)为准。本文不复制两章算法。

| 逻辑角色 | 物理契约 | cleanup / retention | 作用与交付语义 |
| --- | --- | --- | --- |
| Scene data lane | `scene_event` | `delete`；按 Scene 停机、追赶与安全余量冻结 | 唯一物理入口，以 `oneof` 承载 SOURCE、LINKED、Schedule、SubjectLifecycle 和 LifecycleTarget；普通 producer 至少一次发送 |

| Binding 配置传播 | `scene_binding_lifecycle` | catalog 按配置收敛与审计窗口冻结 | PG current Binding + lifecycle Outbox 的至少一次广播，只驱动 ProjectIndex 收敛，不承载运行时 state |

`scene_event` 与 `scene_state` 使用相同固定 partition count 和 §14.1 的共享 route 函数，但共置不等于跨 Topic 原子性。`scene_state` send failure 进入日志、指标和告警，不建立 checkpoint Topic 补偿。Schedule 进入同一 `scene_event`，不另建 durable schedule lane。

生产 Scene data lane 的语义门禁固定为 `processingNamespace=production && processingMode=LIVE`。公共 `SceneEvent` envelope 必须保留必填 `ProcessingContext { processingNamespace, processingMode }` 与 `identityAlgorithmVersion=SCENE_ID_V2`；不得从 Topic 名、时间戳、到达延迟或设备 payload 推断/补齐。`production + BACKFILL`（在线补传/历史 output）与 `backfill/<jobId> + BACKFILL`（显式 job）均在 Scene matching 前旁路且不产生 Scene record。生产 `scene_event`、生产 `scene_state` 与 Action Outbox 的写入权限只授予经验证的 production+LIVE+SCENE_ID_V2 路径；`replay/<id> + REPLAY` 与 `shadow/<id>` 只能停留在允许的隔离边界，缺失/未知/表外组合则 quarantine/fail closed。

旧契约处置如下。旧、新记录的 key、envelope、状态后端和提交语义均不兼容；禁止把下表理解为 broker alias、wire-compatible 改名或双写迁移：

| 旧契约 | Scene V1 处置 |
| --- | --- |
| `automation.input.live` | 由 `scene_event` 取代；key、envelope、事件分类和处理语义全部以场景主规格为准 |

### 5.4 领域事件 topic

| Topic | 典型事实 | cleanup / retention | Producer transaction | Consumer identity |
| --- | --- | --- | --- | --- |
| `platform.saas.event.v1` | tenant/user/project/area/work-order 等领域事实 | `delete` / `Tdomain` | saas PostgreSQL row + outbox | 每个独立 projection 一个稳定 group |
| `platform.things.event.v1` | product/device/model/ownership/command 等领域事实 | `delete` / `Tdomain` | things PostgreSQL row + outbox | 每个独立 projection 一个稳定 group |

领域 topic 不按每个事件类型拆 topic。事件类型由受控 `eventType` 标识，消费者在代码中声明 allowlist。高吞吐设备报告不得发布到领域 topic。

`Tdomain >= 最大允许 projection 停机 + 故障发现与修复 + 积压追赶 + 安全余量`，由 Phase 0 在 catalog 中冻结成明确毫秒值；禁止沿用 broker 默认 7 天而不评审。确需长期保留的 Domain compacted topic 逐项冻结 retention 和受引用分析保护的 GC，不能从已撤销的 Scene release/active-pointer 方案继承默认值。

领域 record key 固定为 `DomainAggregateKeyV1(aggregateType, aggregateId)`；同一 aggregate 的所有版本进入同一 partition。Envelope 携带单调递增 `aggregateVersion`，event ID 只用于幂等，不参与分区。Outbox relay 不得让同 aggregate 的后序版本越过尚未成功发布的前序版本；consumer 仍以 inbox + aggregate version/CAS 拒绝重复或陈旧事件。不同 aggregate 之间不承诺全序。

### 5.5 Replay namespace

生产 Raw/Canonical replay 不能 reset/seek 正式 consumer group；它继续使用独立 consumer group、processing namespace、ACL、quota 与输出目的地，不能写正式 TDengine latest、PG projection、设备命令或其他 LIVE 副作用。

Scene V1 不创建 `iot.replay.*.automation.input/state`，也不承诺由 Canonical 历史重放复原 Scene 状态。LIVE 的 state 业务有效性、缺失/损坏与类型化冷启动语义由场景主规格总纲 §9 拥有；assignment 后的 state-before-event restore、固定恢复切面与 activation gate 只见[Runtime 调度分章 §7](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-restore)。通用 Raw/Canonical replay 不能代替该协议。

任何未来 Scene 隔离重算、virtual clock 或“用新规则模拟历史 processing-time timer”能力都必须另立 ADR；隔离结果不得晋升为 LIVE。通用 Raw/Canonical replay namespace 不能被误写成 Scene 当前恢复协议。

## 6. Key、分区与消息契约

### 6.1 Scene route key

Scene key 不复用 Canonical key 的偶然编码。V1 逐字继承场景主规格 §14.1：

```text
routeKeyBytes(tenantCode, subjectKey) =
  unsigned-varint(len(NFC_UTF8(tenantCode))) || NFC_UTF8(tenantCode) ||
  unsigned-varint(len(NFC_UTF8(subjectKey)))  || NFC_UTF8(subjectKey)

partition = (kafkaMurmur2(routeKeyBytes) & 0x7fffffff) % partitionCount
```

SOURCE/SubjectLifecycle 的 `subjectKey=sourceSubjectKey`；Linked/Schedule/LifecycleTarget 的 `subjectKey=evaluationSubjectKey`。`scene_event` message key 就是上述 route bytes。所有 producer 使用共享 codec 与 golden vectors，禁止 delimiter 拼接或 client 默认复合 key 解释。V1 固定 partition count；改变映射必须另立迁移设计。

### 6.2 `scene_state` key 与完整状态

```text
stateKeyBytes =
  encode(tenantCode) || encode(bindingId) || encode(evaluationSubjectKey)
```

`scene_state` 以完整复合 key 支持 compaction；state partitioner 从 key 中解析 tenant/evaluation subject，重建与对应 `scene_event` 完全相同的 `routeKeyBytes`。每条非 tombstone value 是场景主规格 §8.1 定义的完整 `SceneBindingState`，不保存 release-map control record、不可变 affiliation snapshot、checkpoint 或 transaction manifest。

每条生产 `scene_state` 的非 tombstone value 必须保存且校验 `processingNamespace=production && processingMode=LIVE && identityAlgorithmVersion=SCENE_ID_V2`，并且只能由 Scene Runtime 专用 `state-writer` principal 写入；producer identity、build 与 contract version 写入有界 audit headers。restore 仍对 payload 中的 context/version 做二次验证；缺失、未知、组合不一致、非 `SCENE_ID_V2` 或来源不可信的 state 必须 quarantine/fail closed，不得加载 live state、注册 timer、求值或产生副作用。ACL 和 audit 是持久来源的信任边界，不引入 commit-attestation。

状态换版沿用稳定 `bindingId` key；current Binding 的 `configRevision/semanticHash`、preserve/close+tombstone、next-live bootstrap 与 current-scope reconciliation 属于场景主规格总纲 §§8–9 的业务有效性契约。assignment 后如何扫描、staging、安装 timer、开放 gate，以及 timer callback 如何回 lane，只由[Runtime 调度分章 §§5、7](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-restore)定义；本文不复制恢复/激活算法。旧 payload 中不存在可用于恢复历史 area/group membership 的 `affiliationBindingId`。

state append 是异步 best-effort。同一处理轮可以折叠成一个最终完整 value，但不能据此推导它与 `scene_event` offset 原子提交。Binding 禁用/删除、scope exit、entity 删除和显式 reset 使用主规格定义的 tombstone。

### 6.3 Raw record

Raw 没有业务 Envelope：

```text
Kafka topic      = catalog(protocolKey).rawPhysicalTopic
Kafka key        = transport identity codec 的稳定 bytes
Kafka value      = 原始 MQTT payload bytes
required header  = message-kind
optional header  = mqtt-qos, mqtt-retain, broker-received-at, traceparent
source identity  = sourceClusterId + Kafka topicId + partition + offset
record timestamp = broker LogAppendTime
```

Adapter 不解析 tenant、内部 device ID、物模型或业务 schema。`rawRef = sourceClusterId/topicId/partition/offset` 是后续事实的稳定因果来源；topic name 只作诊断，不能替代 topic ID。归档与 replay 必须保存原 `rawRef` 和 LogAppendTime。

Adapter 重复 append 会得到新 rawRef。只有 transport 契约同时提供稳定 source ID 与 source epoch/boot ID 时，平台才承诺跨 Raw append 去重；否则只能收敛同一 rawRef 的 redelivery。

### 6.4 Canonical / Domain Envelope

Canonical 与 Domain 事实共享以下逻辑头的适用子集，但每类 value 有自己的强类型 payload。Scene 不继承这个通用头；`SceneEvent/SceneBindingState` 的 wire 与业务字段以场景主规格总纲为唯一契约：

```text
eventId/outputId       继承总体架构的稳定事实身份
eventType              allowlist 中的完整类型名
contractVersion        逻辑契约版本
semanticReleaseSetHash 严格覆盖 protocolReleaseId/modelReleaseId/processingModePolicyReleaseId/contractVersion
occurredAt             领域事实发生时间
observedAt             首次进入可信 durable boundary 的冻结时间
producer               service + build + contract release
processingNamespace    production / backfill/<jobId> / replay/<id> / shadow/<id>
processingMode         LIVE / BACKFILL / REPLAY
ownerTenantId          直接 owner，用于隔离与状态 key，不用于 partition
ownershipBindingId     不可变 owner-tenure snapshot ID
ownershipGeneration    同 subject owner cutover 的单调代
canonicalSubjectKey    Canonical/Domain 自身的稳定实体 identity；不是 Scene route key
sourceRef              raw/topicId-partition-offset、上游 outputId 或 DB outbox ID
causationId            直接上游事实 ID
correlationId          一次命令/请求/业务流程关联 ID
aggregateVersion       领域事件使用的单调 aggregate 版本
traceparent            W3C trace context；只用于观测，不参与幂等
actorRef               可选的最小 user/service ID 与 tenant ID，用于审计
payload                强类型消息，不允许 Any/Struct/map[string]any
```

禁止传播完整 `UserCtx`、角色列表、权限计算结果、token 或请求 header。异步消费者必须基于事实中的资源归属和自身权限重新决策。

`observedAt` 的来源冻结为：

| 输入类型 | `observedAt` |
| --- | --- |
| Raw 派生 Canonical | 原 Raw 的 Kafka LogAppendTime；协议重投与归档导入继续沿用原值 |
| PostgreSQL Domain Event | 创建 outbox 的业务 transaction `committedAt` |
| reducer accepted transition | reducer 首次成功提交 transition 的 DB 时间 |
| replay | 原事实的 `observedAt`，另用 namespace/mode 标识重算 |

`observedAt` 用于审计、freshness 和确定性来源说明。Scene 的 `receivedAt`、timer 与 schedule 语义由场景主规格 §5、§10、§11 定义，不能从本通用 Envelope 反推。

高吞吐 Canonical physical encoding 服从总体架构的 Phase 0 benchmark：禁止 JSON、逐点 heap object 和 protobuf `Any/Struct`；在 protobuf packed scalar 与至少一种紧凑格式之间，以 wire B/report、allocs/report、encode/decode MB/s、GC CPU 和 RSS 冻结结果。领域事件默认使用 repository-managed protobuf；Scene protobuf 由场景主规格独立冻结。

兼容规则：

- 同一 major 内只增加 optional 字段或新 enum 值；
- protobuf tag 永不复用；
- 改变字段含义、key 或排序语义必须升级 topic major/generation；
- consumer 在滚动升级窗口同时接受当前与前一兼容 minor；
- CI 对 descriptor 做 backward compatibility check，并用 golden record 做跨版本解码；
- schema 不可解析属于 poison record，进入 quarantine/outcome 后才能推进 offset，不能无限重启。

### 6.5 确定性 ID

本文逐字继承总体架构的 `reportId/outputId` 二元身份，不能把 semantic hash 混进 `outputId`：

```text
若 sourceReportId + sourceEpoch 可证明稳定：
reportId         = H(ownershipBindingId, canonicalDeviceId,
                     sourceEpoch/deviceBootId, sourceReportId,
                     reportIndex, processingNamespace)
否则：
reportId         = H(rawRef, reportIndex, processingNamespace)

PropertyReport.outputId = reportId
其他标准 outputId       = H(rawRef, processingNamespace, outputKind, outputIndex)
outputTransportIdentity = (outputId, semanticReleaseSetHash)
```

`sourceReportId` 不能脱离 source epoch 直接充当平台 ID；无法证明其稳定性时只承诺同一 `rawRef` redelivery 收敛。DecodeManifest 的 output index/count/manifest hash 继续服从总体架构。

Scene identity 不使用旧 `bindingReleaseId/affiliationBindingId/release barrier` 公式。`logicalTimerId/timerFireId`、`scheduleOccurrenceId/scheduleEvaluationId`、`lifecycleEvaluationId`、`transitionId/effectId` 分别由场景主规格 §10、§11、§12 定义；新公式均以 `SCENE_ID_V2` tag 为首个 hash 输入，其中 stable `bindingId` 与 current-context lifecycle identity 收敛 retry/rebalance，不把配置 revision 或 membership snapshot 放入 effect identity。`LEGACY_NO_NAMESPACE_V1` 只用于已接受 pending Outbox 的原 ID 只读投递。

所有 `H` 的算法、字段顺序、长度前缀和输出编码放入对应 contract package，并提供 golden vectors。禁止使用 map 序列化结果、relay 重试时钟或随机 UUID 作为需要重算一致的 ID。

## 7. Kafka 处理语义

### 7.1 Producer 基线

普通 durable producer：

```text
acks=all
enable.idempotence=true
retries 受 delivery timeout 约束，不使用业务层无界循环
max.in.flight.requests.per.connection <= 5
compression 由真实 payload benchmark 冻结
```

producer 必须区分：

- `ProduceSync`：控制面低频事件或需要明确提交结果的路径；
- 有界异步 batch：Raw/Canonical 高吞吐路径，回调错误必须进入整体 backpressure；
- transactional producer：只用于 Raw→Canonical 等本文明确标注的 Kafka 内原子路径；Scene producer 不使用此档。

任何 producer queue 都有 byte 和 record 上限。队列满时向上游施加背压，不能继续创建 goroutine 或丢弃回调错误。

### 7.2 Consumer 基线

```text
isolation.level = read_committed
enable.auto.commit = false
group protocol = classic
assignment strategy = cooperative-sticky
offset reset = NoResetOffset（正式环境）
```

- 每个 consumer group 对应一个独立、可命名的业务 projection；
- group ID 不包含 Pod IP、随机 UUID 或每次部署变化的 release；
- handler 不脱离 partition 生命周期创建不可追踪 goroutine；
- 每个 partition 使用串行状态机或明确的有界并行 + 连续 next-offset barrier；
- 瞬时依赖故障时 pause partition，带抖动退避后重试；
- revoke 时停止取新消息、取消/等待 in-flight、完成或 abort transaction，再交还 partition；
- 处理时间可能超过 group poll 限制的任务必须拆批，不能靠无限放大超时掩盖；
- 所有文档和数据库字段中的消费位置统一表示“下一条要消费的 offset”，不混用 last-processed offset。

正式 group 完成显式 bootstrap 后必须使用 `kgo.ConsumeResetOffset(kgo.NoResetOffset())`。offset 缺失、超出 retention 或被误删时停止 partition 并告警，不能默认跳到 earliest/latest。新 topic generation 的每个 group 起点由 catalog/cutover workflow 显式写入。

`cooperative-sticky` 采用 franz-go 的 classic consumer group 实现。Kafka 4.x 的新 consumer protocol 在 Phase 0 单独验证前不进入生产基线。Kafka-to-Kafka 事务路径使用 `kgo.NewGroupTransactSession`；其 assignment/revoke callback 只负责快速 pause、登记/取消 restore 与短时 lease fencing，完整状态加载在 callback 外执行；callback 不再实现另一套 offset commit。

franz-go `GroupTransactSession.End(kgo.TryCommit)` 会提交当前 poll 产生的全部 uncommitted offsets，因此一个 transaction cycle 必须处理本次 `PollRecords` 返回的**所有**记录。可以按 partition 分桶串行求值，但不能只处理一个桶便提交，也不能在 `End` 前再次 poll。

### 7.3 Raw → Canonical transaction

每个 ProtocolApplication worker slot 持有一个独立 `GroupTransactSession`。一次 transaction cycle 执行：

1. 使用 `PollRecords(ctx, maxPollRecords)` 以 `read_committed` 拉取一个有 records/bytes 上限的 poll；
2. 立即 `Begin()`；之后任一步失败都用 `End(ctx, kgo.TryAbort)`，让 session 回到 broker 已提交 offsets；
3. 处理 poll 返回的全部 records，可按 partition 分桶但不得遗漏；
4. 有界解码并冻结每条 Raw 的 `DecodeManifest`；
5. 每个 expected output 必须产生且只产生以下一种结果：
   - 完整 Canonical record；
   - 对应 quarantine record；
   - 明确的 `NO_OUTPUT` outcome；
6. 写入所有 Canonical/quarantine/outcome；
7. 调用 `End(ctx, kgo.TryCommit)`；session 把本次 poll 的全部 next-offset 与 Canonical/quarantine/outcome 原子提交；
8. 只有返回 `committed=true` 才释放 batch；abort 时全部重算；End 返回 error 时退休该 session，不在未知 producer 状态上继续。

一个 poll 中任一 partition 遇到瞬时错误，整个 Kafka transaction abort；永久单消息错误必须成为同 transaction 的 quarantine/outcome，不能跳过。Phase 0 用 `maxPollRecords`、fetch bytes 与 worker slot 数控制事务大小；同一进程可运行多个 session slot 获得并行度。

Scene admission 是下游契约：它在 existence/relevance 与 current tenant/fact interest filter 之前读取、校验 Canonical 中受信的 `processingNamespace/processingMode`，只把 `production + LIVE` 已接纳事实规范化为生产 `scene_event`。`production + BACKFILL` 与 `backfill/<jobId> + BACKFILL` 均在 interest/candidate matching 前 deterministic bypass，不产生 Scene record；`REPLAY`、shadow 按主规格旁路，而上下文不完整、枚举未知、表外组合或来源不可信时 quarantine/fail closed，任何一种情况都禁止 LIVE fallback。该路径不属于 Raw → Canonical Kafka transaction；Scene V1 不要求 Canonical 与 `scene_event` 的跨 Topic transaction，interest filter 仍允许 false positive，并按场景主规格处理 retry/quarantine。

必须满足：

- transactional ID 在 namespace、input topic ID/generation 和部署槽位上稳定，例如 `prod.data.protocol.<protocolKey>.<rawTopicId>.g01.<statefulsetOrdinal>.<workerSlot>`；
- 新进程初始化 transactional producer 时能 fence 旧进程；
- `cycle p99 + margin < transaction timeout < session timeout`，cycle wall time 还必须小于 `max.poll.interval`；batch 足够小以避免长事务；
- 普通超时不 cancel `End` 的 context；franz-go 明确提示这样可能使 client 进入无效状态，只有进程退出才取消；
- 下游只读 `read_committed`；
- commit 响应不确定时停止 slot，通过稳定 group offset、输出 ID 和读回验证恢复，不能继续使用内存结果；
- transaction 只保证 Kafka 内原子提交，不保证 TDengine/PostgreSQL sink。

### 7.4 外部 sink

Timeseries、latest、领域 reducer 等外部 sink 使用：

```text
Kafka 至少一次输入
→ 稳定 eventId/sourceRef
→ sink 幂等写或 version/CAS comparator
→ 整个 record 的必要效果完成
→ 推进连续 next-offset
```

一个 `PropertyReport` 的所有 module history 与 processing mode 要求的 latest 更新完成前，不能提交该 record。TDengine 不可用时 pause partition，让 Canonical 承接有界积压；禁止无限堆内存。

### 7.5 PostgreSQL Outbox / Inbox

领域生产事务：

```text
BEGIN;
UPDATE/INSERT domain tables;
INSERT outbox(
  event_id UNIQUE, aggregate_type, aggregate_id, aggregate_version,
  event_type, payload, occurred_at
);
COMMIT;
```

relay：

1. 以租约领取未发送 outbox；
2. 同 aggregate 严格按 `aggregate_version` 发布，前序未成功时不越过；
3. Kafka key 使用 `DomainAggregateKeyV1(aggregateType, aggregateId)`，`event_id` 只作幂等；
4. 等待 `acks=all` 成功；
5. 标记已发送；
6. 若“Kafka 已成功、标记前崩溃”，允许再次发送同一个 event ID。

领域 consumer：

```text
BEGIN;
INSERT inbox(consumer_name, event_id) ON CONFLICT DO NOTHING;
若已存在：直接视为完成；
若首次出现：按 aggregateVersion/CAS 更新 projection / 触发后续 outbox；
COMMIT;
提交 Kafka next-offset；
```

这提供“至少一次投递 + 业务幂等效果”，不宣称跨 PostgreSQL/Kafka exactly-once。

## 8. Scene Runtime 与 Kafka 的集成边界

本节只汇总两份 Scene 架构源与 Kafka 的物理接点，不形成第二套业务、completion、恢复或接管 ADR：[场景主规格总纲](../6.规则引擎与场景联动/场景联动 Runtime 主规格总纲.md)拥有 wire、业务状态/求值、Action Outbox 与 producer 交付，[Runtime 调度分章](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-scope)拥有 partition-local 执行、completion、restore、rebalance 与 Zombie。任一边界变化都必须按 §1.2 同次修订。

### 8.1 规范边界与统一入口

`scene_event` 是 V1 唯一物理数据入口。统一 `SceneEvent oneof` 承载 SOURCE_DELTA、LINKED_DELTA、SCHEDULE_EVALUATE、SubjectLifecycle 和 LifecycleTargetDelta；同一 consumer entrypoint 按 kind 分派，不按 SOURCE/LINKED 拆 Topic 或 Runtime。

Scene admission 先从 Canonical/accepted transition 的受信 envelope 读取 `ProcessingContext`，再做 existence/relevance 与 tenant/fact 级无漏接过滤；不得从 Topic 名、event/device time、到达延迟或 payload 推断 mode。生产 Admission 只有在 `processingNamespace=production && processingMode=LIVE` 时才可写一条生产 SOURCE_DELTA；`production + BACKFILL` 与 `backfill/<jobId> + BACKFILL` 都在 candidate matching 前 deterministic bypass，推进 Admission 自身的正常处理前沿但不写任何 Scene record；`replay/<id> + REPLAY`、`shadow/<id>` 不进入生产 Scene。缺失、未知、表外 namespace/mode 组合或来源不可信时 quarantine/fail closed，禁止默认 LIVE。Admission 不在 Raw → Canonical transaction 中写 Scene 输出。

公共 `SceneEvent` envelope 必须携带独立、必填的 `ProcessingContext { processingNamespace, processingMode = LIVE | BACKFILL | REPLAY }` 与 `identityAlgorithmVersion=SCENE_ID_V2`；SOURCE_DELTA 从 Canonical 原样继承 context，Admission 盖章 Scene identity version；LINKED_DELTA、local/remote target bundle、timer fire 与同一因果链派生记录原样复制二者，不能藏在 `lineage` 或重新默认为 LIVE。受信 Scheduler/SubjectLifecycle producer 显式盖章 production+LIVE+SCENE_ID_V2。每个 producer 在 publish 前校验，每个 Actor/handler 在 lookup、argument 构造或 evaluation 前再校验；误路由时 fail closed/quarantine，不改 state/timer/Alarm/Outbox。

SOURCE_DELTA 不冻结 Product/Project/Area/group snapshot；通过 mode gate 后，source lane 才在处理时解析 current `SubjectContext`，不可用时 retry/fail closed。迁区/换组后的 backlog 与 redelivery 按处理时已知的 current affiliation 匹配，这是 V1 明确语义；`SubjectContext` 不得改写、推断或提升 processing mode。

`scene_binding_lifecycle` 只传播 PG current Binding 的配置变化。它不承载 Runtime state，不与 `scene_event` 建立 config/offset barrier；revision gap 通过 ProjectIndex 重建收敛。该 Topic 与 explicit reinit 都只是受信的 no-state-value control：允许安装配置、close/reset 内存、发 tombstone 并标记 next-live bootstrap；close/reset 必须取消已有 timer slot/handle，但禁止读 current facts、构造非 tombstone business state、执行 predicate/FSM、创建/arm/推进/fire timer、产生 Alarm/Action Outbox 或绕过 mode gate 立即求值。

### 8.2 状态与恢复

Scene Runtime 使用 partition-local Actor 内存作为热状态，`scene_state` compacted Topic 保存每个 `(tenantCode,bindingId,evaluationSubjectKey)` 的完整可恢复业务状态。state producer 异步 best-effort 发送：

- 不使用 RocksDB；
- 不使用本地或远端 snapshot/manifest/CAS/GC；
- 不创建 transaction checkpoint、commit attestation 或 release-map control record；
- `scene_state` append 与 `scene_event` offset 没有原子切面；
- state send failure 记录日志、指标和告警，但不阻塞 source offset commit。

生产 `scene_state` 非 tombstone value 只允许专用 Scene Actor/`state-writer` principal 写入，并必须持久化 production+LIVE+SCENE_ID_V2；这些是本文保留的 Topic ACL 与 wire trust 边界。state 的业务有效性、current Binding 兼容、scope reconciliation、类型化冷启动与一次性 `SCENE_ID_V2` rollout 由场景主规格总纲 §§9.2–9.5 拥有；assignment 后的固定恢复切面、staging、timer activation、restore gate 与开放顺序只见[Runtime 调度分章 §7](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-restore)。

异步 state 可能领先或落后于 committed event offset，旧 owner append 也可能迟到成为 compacted latest；其幂等与残余风险边界只见[Runtime 调度分章 §9](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-best-effort)。本文不把 compaction、`effectId` 或 producer idempotence解释成 restore 正确性证明。

### 8.3 Event commit 与动作顺序

动作 transition 的 tentative state → PG Action Outbox transaction/commit → 内存 state/timer → async `scene_state` Producer handoff 顺序与 PG 失败处置，只由场景主规格总纲 §12.3 拥有；Producer callback/retry/quarantine 与 handoff 后失败窗口只由其 §13 拥有。本文只保留物理事实：PG Outbox commit 是动作接纳边界，Scene producer 非 transactional，Kafka transaction 不覆盖 PG，也不原子提交 Scene state/input offsets。

完整 input completion predicate、per-partition sequencer、安全连续 next-offset frontier 与 graceful revoke final commit/handoff 只见[Runtime 调度分章 §§5、8](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-normal-completion)。offset commit 不表示外部 Action 已执行，也不把异步 state 提升为 durable 或跨存储原子；本文不复制这些算法。

每条 Action Outbox row 必须保存 `processingNamespace/processingMode/identityAlgorithmVersion`。新 row 只能为 `SCENE_ID_V2`；只有场景主规格总纲 §9.4 审计迁移的 `LEGACY_NO_NAMESPACE_V1` pending row 可按原 `effectId` 只读兼容投递，任何 Runtime/工具不得用 legacy 版本创建或重算。只有 Scene Actor DB role 可 INSERT；dispatcher role 只能 SELECT 与推进投递状态，无 INSERT、改 payload、context 或 version 权限。dispatcher 在 dequeue 和每次外发前均仅接受受信的 production+LIVE 与允许版本。非法 pending row 必须以 CAS/PG 本地事务原子转为终态 `BLOCKED_CONTEXT`，记录 bounded reason/audit/quarantine reference 并移出 due index；它不重试、不外发、不阻塞无关 row。若是 strict target lane，必须暂停该 target 后继并 page，禁止后序越过被阻塞 row；不得原地修改 context/version 后重回 pending。

无动作 state 更新的校验/发布顺序与 lookup/index 完整性门禁继续由场景主规格总纲 §§6、12.3 拥有，本文不再给出第二份执行步骤。

### 8.4 Rebalance、配置与生命周期

Kafka client/group 的固定选择仍由本文 §7.2 拥有；dynamic assignment、PartitionRuntimeContext、token/effect gate、graceful final commit、硬故障接管与 Zombie 重连只由[Runtime 调度分章 §§6、8–9](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-state-machine)拥有。本文不复制 rebalance 算法，也不新增 DB owner epoch、分布式 lease、durable fencing 或 Scene transactional producer。

配置、current scope/version、SubjectLifecycle 与 Schedule 的业务语义只由场景主规格总纲 §§6、9、11 拥有。本文只保留两个物理事实：配置经 `scene_binding_lifecycle` 传播，Schedule/SubjectLifecycle 的数据面输入进入统一 `scene_event`；不创建 affiliation barrier、独立 schedule Topic 或第二套 matching/lifecycle 算法。

### 8.5 已撤销的旧协议

旧 §8 的 RocksDB + Kafka changelog/EOS、state/checkpoint/input offsets transaction、commit-attestation projector、远端 snapshot、release/affiliation barrier、topic/state-generation migration 与 GC 协议已整体撤销，不得作为实现或验收依据。逐项处置见 §5.3；当前规范性架构算法由场景主规格总纲与[Runtime 调度分章](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-main-spec-index)按职责共同组成，本文只拥有 Kafka 物理接入边界。
## 9. NATS 使用点的语义替换

| NATS 用法 | 不能直接映射的原因 | Kafka-only 设计 |
| --- | --- | --- |
| 普通 `Publish` | 不知道需要持久、顺序还是同步结果 | 先归类为 Raw、Canonical、Domain Event、Outbox 或直接调用 |
| queue subscribe | Kafka group 只保证组内竞争，不代表所有业务消费者 | 每个独立 projection 一个稳定 group；同 projection 多副本共享 group |
| broadcast subscribe | 单 group 只会给一个实例，多 group 又会把每个实例永久化 | durable 业务消费者用独立 group；WebSocket/cache 使用专门 fanout/version 机制 |
| wildcard `device.>` | Kafka 不提供 NATS subject wildcard 语义 | catalog 管理有限 topic 列表；protocolKey workload 显式拥有一或少量 Raw topic |
| 临时 request/reply subject | topic/group 创建与清理成本高，难治理 | 同步 RPC；异步命令用 `CommandExecution + correlationId` |
| JetStream durable | ack 与业务效果边界不正确 | Kafka offset 在业务/事务完成后推进 |
| 动态数据库 subject | 绕开 schema、ACL、quota 和容量评审 | 类型化 trigger/action registry |
| 每 API Pod 收广播 | Kafka group 与连接局部性冲突 | durable notification fact + session registry/edge fanout |
| 定时任务先发 NATS 再由本进程消费 | 无必要跳转，失败边界模糊 | 类型化 handler；Scene 普通 timer 为内存 handle + `scene_state.timerState[]`，可靠 delayed action 只用带 due time 的 PG Action Outbox；不建 PG timer row 或额外 Kafka lane |

### 9.1 具体业务重建

| 现有业务 | 新事实来源 | 新路径 |
| --- | --- | --- |
| tenant/user/project/area 创建、更新、删除 | PostgreSQL domain transaction | row + Outbox → `platform.saas.event.v1` → things inbox/projection |
| 设备解绑、区域重置 | things reducer | 消费领域事件，幂等更新设备归属，再发布 accepted transition |
| 设备上行 | Kafka Raw | MQTT → Raw → Protocol transaction → Canonical |
| 设备下行 | `CommandExecution` | API/Automation 写 execution + outbox → codec → EMQX/Gateway adapter |
| 命令回复 | Canonical observation | reducer 收敛为 accepted transition，再按需进入 Automation input |
| cache invalidation | PostgreSQL/versioned projection | Redis/shared version + local TTL/version compare |
| WebSocket | durable notification + connection registry | Kafka/Outbox 记录事实，edge 按本地连接投递 |
| timed job | DB lease / typed handler | 同服务直接调用；可靠 timer 经 PG outbox 写入 Automation lane |

### 9.2 下行命令明确不建 Kafka command topic

V1 下行命令由 PostgreSQL 状态机驱动，Kafka 只承接设备回复的 Raw/Canonical observation：

1. API 或 Automation dispatcher 在 PG transaction 中创建 `CommandExecution + CommandOutbox`；`commandId/effectId` unique；
2. command runtime 以 lease 领取，冻结 `protocolKey/protocolReleaseId`，生成不可变 `CommandAttempt`、目标 MQTT topic 和 encoded payload；
3. 需要同设备严格顺序的产品在 PG 分配单调 `deviceDispatchSequence`，同一设备只允许一个有序 attempt in-flight；
4. EMQX/Gateway adapter 发布 MQTT；默认 QoS 1；
5. MQTT PUBACK 只把 attempt 标为 `BROKER_ACKED`，表示 broker 接收，不表示设备执行成功；
6. 设备 reply 经 Raw→Canonical→command reducer，以 `commandId/attemptId/correlationId` 收敛为 `DEVICE_ACKED/SUCCEEDED/FAILED/EXPIRED`；
7. 若进程在 publish 成功与保存 PUBACK 之间崩溃，结果是 `OUTCOME_UNKNOWN`：只有命令契约声明幂等或设备支持稳定 command ID 去重时才自动重发，否则等待 reply/超时并交人工决策。

不创建临时 reply topic、临时 consumer group或 `device.down.*` 的 Kafka 仿制品。这样把“受理、编码、broker 接收、设备执行”四个可靠性边界分开，也不虚假承诺设备命令 exactly-once。

```text
principal:

  <env>.<namespaceHash>.<plane>.<component>.<inputTopicId>.<generation>.<statefulsetOrdinal>.<workerSlot>
```

禁止把 tenant ID、device ID、随机 UUID、Pod IP 或 build version 放入 group ID。Scene consumer/producer 不配置 `transactional.id`；上面的模板只用于 ProtocolApplication 等本文明确采用 Kafka transaction 的流程。

### 10.2 最小权限示例

- Adapter：只写其 catalog 授权的 Raw topic，无 Canonical/Domain read；
- ProtocolApplication：只读自己的 Raw topic/group，只写授权 Canonical/quarantine/outcome，使用自己的 transactional ID prefix；
- Scene Admission：只读授权的生产 Canonical/accepted transition，在输入 context 为 production+LIVE 时只发布 `SourceDelta + SCENE_ID_V2` 到生产 `scene_event`，否则只能按契约 bypass 或写 quarantine；
- Scene Scheduler producer：只写生产 `scene_event`，application contract 只允许 `ScheduleEvaluate + production+LIVE+SCENE_ID_V2`；无 `scene_state`/`scene_binding_lifecycle` 写权，无 Action Outbox INSERT 权；
- Things SubjectLifecycle relay：只写生产 `scene_event`，application contract 只允许 `SubjectLifecycle + production+LIVE+SCENE_ID_V2`；无 `scene_state`/`scene_binding_lifecycle` 写权，无 Action Outbox INSERT 权；
- Scene Runtime：读生产 `scene_event` 与 `scene_binding_lifecycle`，其 event-producer principal 只写生产 `scene_event` 内部派生的 `LinkedDelta`/`LifecycleTargetDelta + SCENE_ID_V2` 与 quarantine；Actor 以独立 `state-writer` credential 只写生产 `scene_state`，不共用 event-producer credential。PG 中只有 Actor role 可 INSERT Action Outbox，dispatcher role 只可读取/推进状态；不授予 checkpoint/attestation/lease 表权限；
- Binding lifecycle relay：使用独立 principal，只写 `scene_binding_lifecycle`；
- Replay/shadow/backfill：各自 principal 只读批准的 Raw/Canonical offset range 并写受授权的隔离 namespace；其 principal 与 namespace 不得写生产 `scene_event/scene_state`、Action Outbox 或命令，禁止通过伪造 LIVE 字段获得生产权限；
- saas outbox：只写 `platform.saas.event.v1`；
- things projection：只读指定 Domain topic/group，不能读取 Raw payload。

Kafka ACL 只能限制 Topic/cluster operation，不能识别 Protobuf `oneof` kind。上述“只允许某 kind + production+LIVE+SCENE_ID_V2”由已认证 producer identity 对应的封闭 publish API/application contract/schema guard 在发送前强制，不得提供任意 envelope publish 接口。Runtime consumer 二次验证全局 allowed kind、oneof/payload/key/route 一致性、ProcessingContext 与 identity version；Kafka record 不包含 broker 认证后的 producer principal，producer 自填 header 也不是该证据，因此 consumer 不得声称能按 record 验证 role→kind。若 producer compromise 也必须被独立阻断，只能另立 ADR 采用 broker 可寻址的 per-kind Topic 或可验证签名，V1 单 `scene_event` Topic 不承诺这一层。

Data 与 Domain principal 分别设置 produce/fetch/request quota。受控 replay 使用更低优先级 quota；“设备双峰值 + replay + broker 故障”时 Domain event p99/lag 仍需达标，否则触发物理拆分 ADR。

## 11. 容量与分区冻结方法

### 11.1 单位必须分开

平台容量同时记录：

```text
reports/s
points/s
Kafka records/s
producer MB/s
RF=3 broker replicated MB/s
每个 consumer group fetch MB/s
scene_event records/s 与 bytes/s
scene candidates/evaluations/transitions/s
scene_state append records/s 与 bytes/s
PG Action Outbox rows/s
timer fires/s
state-before-event restore bytes、耗时与 RTO
async state send failure/callback latency
backlog bytes 与 lag age
```

一个含 500 points 的 `PropertyReport` 通常仍是一个 Kafka record；一条 admitted Canonical record 最多形成一条批量 SOURCE_DELTA，不按相关点位数拆 Scene records。`points/s`、Canonical records/s、`scene_event` records/s 和 candidate evaluations/s 必须分别测量。

总体架构容量锚点：

| 档位 | reports/s | points/s |
| --- | ---: | ---: |
| 24h 日均 | 1,667 | 约 83 万 |
| 12h 活跃稳态 | 3,333 | 约 167 万 |
| 60s 集中峰值 | 16,667 | 约 833 万 |
| Phase 1 双峰值压测上限 | 33,334 | 约 1,667 万 |

旧 3K RocksDB checkpoint/s、commit attestation bytes 或 snapshot bytes 不再进入容量签字。当前 Scene POC 必须实测每 report 的相关 fact 数、SOURCE/Linked/lifecycle/Schedule records、candidate evaluations、完整 state bytes、async state append 与 PG Action Outbox 行数。

### 11.2 流量公式

```text
rawProduceMBps        = reportsPerSecond × measuredRawBytesPerReport / 1e6
canonicalProduceMBps  = reportsPerSecond × measuredCanonicalBytesPerReport / 1e6
sceneEventProduceMBps = admittedSceneRecordsPerSecond × measuredSceneEventBytes / 1e6
sceneStateProduceMBps = stateAppendsPerSecond × measuredSceneStateBytes / 1e6
brokerWriteMBps       ≈ Σ(topicProduceMBps × replicationFactor)
consumerFetchMBps     = Σ(eachConsumerGroupReadMBps)
backlogBytes          = ingressBytesPerSecond × outageSeconds
catchupSeconds        = backlogBytes / (consumerCapacityBps - ingressBps)
```

`admittedSceneRecordsPerSecond` 来自场景主规格的 interest filter 与批量 SOURCE_DELTA 规则：允许 false positive，但不能按点位机械放大，也不能假设所有 Canonical report 无条件复制。容量测试必须同时覆盖 Linked、Schedule、SubjectLifecycle 与 timer 路径。

### 11.3 Partition 选择

Phase 0 可测试候选 `24 / 48 / 96 / 192`，选择满足以下全部条件的最小值：

- 在目标硬件上承受 Phase 1 双峰值，broker/consumer steady utilization 不超过 60%；
- 单 broker 故障和受控 Raw/Canonical replay 同时发生时仍满足 Raw append、Domain p99 与 lag SLO；
- 最热 key/topic 的 p99、吞吐和 skew 达标；
- Scene 在 cruise 的 `lag age <= 5min`，声明的 60s 峰值后 `lag age <= 30min`，且追赶能力持续大于入口；
- `scene_state` state-before-event restore 在声明 RTO 内完成；
- ProtocolApplication transaction 的 records、bytes、duration 和 abort rate有充分余量；
- Scene async producer queue/callback、controller、topic、partition、文件句柄和内存成本可接受。

冻结内容包括硬件、payload 分布、压缩、partition 数、每 partition MB/s/records/s、consumer 副本数、batch 参数、恢复时间和成本。Scene V1 生命周期内固定 `scene_event/scene_state` partition count；需要改变时创建新 generation 并另立迁移设计，不能复用已撤销的 barrier/transaction GC 协议。

Phase 0 的 SLO/capacity artifact 至少包含 Raw append p95/p99、Domain publish-to-consume p99/lag、Scene normal latency/lag age、broker/PG 故障窗口、全量 state-before-event restore RTO、catch-up MB/s、Protocol transaction p99/timeout、async state failure 窗口和成本上限。

## 12. 错误、隔离与重放

### 12.1 错误分类

| 类别 | 例子 | 行为 |
| --- | --- | --- |
| 瞬时基础设施错误 | broker timeout、PG/TD/current-context store 暂时不可用 | pause/retry；Scene 按主规格区分可重试 pack、远端 bundle 与 state callback，不伪装成原子事务 |
| 永久单消息错误 | schema 不兼容、非法 payload、预算超限 | 写 quarantine/outcome 后按该链路的明确策略推进；Raw 流程仍可使用同 Kafka transaction |
| Scene ProcessingContext/identity 非法 | 缺失/未知 mode、表外 namespace/mode 组合、SceneEvent 缺失/非 `SCENE_ID_V2`、来源不可信、非 production+LIVE 误路由；合法 `production + BACKFILL` 不属于错误 | Admission/Actor/state restore/timer fail closed/quarantine；不进 matching、不产生生产 state/timer/Alarm/Outbox |
| Action Outbox context/identity 非法 | pending row 缺 context/version、非 production+LIVE、未知 version 或来源不可信；[主规格总纲 §9.4](../6.规则引擎与场景联动/场景联动 Runtime 主规格总纲.md#94-processingcontext-强门禁-rollout-与历史迁移)的 legacy allowlist 除外 | dispatcher 原子转 `BLOCKED_CONTEXT`、不重试、不外发；strict target lane 阻塞后继并 page |
| 代码缺陷/不变量破坏 | Scene route key 落错 partition、ProjectIndex 返回部分结果、state key 无法解析 | fail closed、停止受影响处理、page 告警，不自动跳过 |
| 容量超载 | lag 接近 retention、producer queue 满、磁盘 85% | replay/backfill 限速、扩容、入口保护；不缩短已承诺 retention |
| 外部副作用失败 | Webhook、设备离线、命令 adapter 失败 | Action Outbox/CommandAttempt 独立重试和终态，不阻塞 Kafka consumer transaction |

### 12.2 Quarantine 不是垃圾桶

每条 quarantine 至少包含 error class/reason、source topic/partition/offset 或 Outbox ID、contract/build version、payload digest/ref、first/last failure、attempt count、trace/correlation 和允许的重处理目标。Scene lookup/index 失败不得把部分 bundle 当成功结果；Linked/LifecycleTarget 最终失败与 state send failure按主规格保留可观测的 best-effort 窗口。

运维工具只能把修复后的 Raw/Canonical 消息投入隔离 replay namespace。Scene V1 没有可写回 LIVE 的历史 replay lane；显式 reinit 走 Scene 控制面，不 reset 正式 consumer group。

## 13. 可观测性与 SLO

### 13.1 Kafka 基础设施

必须观测 offline/under-replicated partition、ISR、controller quorum、leader election、request queue、produce/fetch p95/p99、broker disk/network/page cache、transaction begin/commit/abort/fence、producer queue/error/retry/throttle、consumer lag/age/rebalance 和 partition skew。

transaction/LSO 指标属于实际使用 transaction 的 Raw → Canonical 等流程，不能用来宣称 Scene EOS。硬门禁仍为 offline partitions=0、unclean leader election=0、minISR 不满足时 durable write 失败、Raw/Canonical lag age 不越过 retention headroom。

### 13.2 业务 runtime

| Runtime | 核心指标 |
| --- | --- |
| Adapter | MQTT receive、Raw produce MB/s/p99/error/throttle、queue bytes |
| Protocol | Raw lag/age、decode p99、outputs/report、quarantine、transaction abort/fence |
| Materializer | Canonical lag/age、points/s、rows/s、TD/latest p99、retry |
| Scene | `scene_event` lag/age、SOURCE/Linked/Schedule/lifecycle records/bytes、candidate p95/p99/max、evaluation/no-op/transition/action、`scene_state` records/bytes/size p99、async send failure/callback latency、restore ETA、current-context lookup/reconciliation、late old-owner state overwrite；`scene_admission_mode_total{namespace_class,mode,decision}`、`scene_processing_context_invalid_total{reason}`、`scene_state_processing_context_invalid_total{reason}` |
| Timer/Outbox | active/due、due lag、stale no-op、Outbox oldest age、effectId conflict、dispatch retry/terminal；`scene_dispatcher_processing_context_invalid_total{reason}`、`scene_outbox_blocked_context_total{reason}` |
| Domain relay | outbox oldest age、publish retry、duplicate event、inbox conflict |

普通 Prometheus label 不包含 tenantId、deviceId、原始错误文本等无界值。上述 `namespace_class/mode/decision/reason` 只能使用有界 enum/class，`jobId/replayId/effectId` 等高基数 ID 只进受控日志、trace 或审计字段。日志使用 `eventId/sourceEventId/effectId/timerFireId/correlationId` 串起轨迹，但禁止记录完整敏感 payload 和凭证。

## 14. 故障注入与验收

上线前至少通过以下测试：

1. Raw producer 在 broker leader 退出、transaction commit 响应丢失和新实例 fencing 下，Canonical/quarantine/outcome 与 Raw next-offset 仍原子可解释；
2. 一个 `GroupTransactSession` poll 同时返回多个 Raw partitions 时全部处理或全部 abort，不误提交未处理桶；
3. Scene 的 PG Action Outbox/内存 state/Producer handoff 业务失败窗口按场景主规格总纲 §§12.3–13 验证；input completion、连续 offset 与 revoke handoff 按[Runtime 调度分章 §§5、8](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-normal-completion)验证；
4. lookup/index/current-context 故障时不产生部分 SOURCE/Linked/lifecycle bundle；retry/quarantine/最终失败策略可验证；
5. async state send 失败、callback 超时与 producer queue 满时不阻塞 source offset，但日志、指标、告警和后续 state 落后窗口可观测；
6. 删除 Scene Pod 全部进程内状态后，按[Runtime 调度分章 §7](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-restore)验证 state-before-event restore、固定切面与 activation gate；
7. 单条 state 缺失、损坏、超 32 KiB 或 semanticHash 不兼容时，preserve 或 close+tombstone+next-live bootstrap、类型化冷启动、quarantine 与无动作行为正确；
8. 按[Runtime 调度分章 §§6、8–9](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-state-machine)验证 graceful revoke（含 callback 内至多一次 final commit）、hard failover、Zombie、token/effect gate 与旧 owner late state 残余窗口；
9. 相同 trigger 在旧/新 owner 重算得到相同 transitionId/effectId，已 commit Action Outbox 不重复外发；
10. current Binding 更新、revision 乱序/gap、节点短暂配置差异与 PG rebuild 不依赖 config/offset barrier；
11. 设备迁区/换组后的 backlog/redelivery 按处理时 current SubjectContext 匹配；延迟 Linked、恢复 state、重复/乱序 SubjectLifecycle 和 version gap 不能复活旧成员；
12. Schedule current-target 分页、去重、`limit+1` 超限和中间页失败不发送部分 target，重试按 current membership 收敛；
13. poison Raw/Canonical/Scene record 不永久阻塞整个 partition，且 quarantine 信息完整；
14. timer 的业务 identity/current-slot/freshness 与 reliable delayed action 符合场景主规格总纲，partition/token 捕获、callback 回 lane 与 restore activation 符合[Runtime 调度分章 §§5、7](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-restore)；
15. TDengine 停止 30 分钟后内存有界、Canonical 未越 retention、恢复后在 RTO 内追平；
16. Phase 1 双峰值 + 受控 Raw/Canonical replay + 单 broker 故障下 quota 和 Domain SLO 达标；
17. Raw 72h retention 的真实 disk growth、segment rollover 和最热 partition 达标；
18. topic generation 迁移不产生同 subject 双 LIVE 副作用；Scene partition 迁移使用单独评审的方案；
19. Replay principal 无权限写正式 `scene_event/scene_state`、Action Outbox 或 command；
20. Scene event/state key、`SCENE_ID_V2` tag 与全部 ID golden vectors跨 Go/Java 版本一致；
21. 生产安全扫描不存在 PLAINTEXT listener、默认开放 ACL 或 auto-create topic；
22. command publish 后记录 PUBACK 前崩溃时，幂等命令重试与非幂等 `OUTCOME_UNKNOWN` 均可验证。
23. production+LIVE Canonical 经过 ProcessingContext 验证并由 Admission 盖章 `SCENE_ID_V2` 后才进入 relevance/matching，并可产生生产 `scene_event/state/timer/Alarm/Outbox`；`production + BACKFILL` 与显式 job BACKFILL 必须正常 bypass 而非 quarantine，二者及 REPLAY、shadow、缺失/未知/表外 mismatch 和来源不可信用例都必须证明 zero production Scene record/mutation/delivery；
24. 误路由 `scene_event`、非法 `scene_state`/timer slot 与非法 pending Action Outbox 分别被 Actor/restore/timer/dispatcher 二次门禁拦截；`BLOCKED_CONTEXT` 不 hot-loop、不外发、不阻塞无关 row，strict target lane 的后续不得越过；
25. Kafka ACL 证明 replay/shadow/backfill principal 无法写生产 `scene_event/scene_state`、只有 `state-writer` 可写生产 state；PG 权限证明只有 Actor role 可 INSERT Action Outbox，dispatcher 只能读取/推进状态；
26. `SCENE_ID_V2` cutover 先 pause/fence/撤销全部旧 Scene producer，排空 producer input frontier、context-less `scene_event`、callback 与 DB/Kafka in-flight；无法排空者只隔离并经损失审批。identity-bearing state tombstone/cold start；可信 legacy pending Outbox 保留原 `effectId` 只投递；无法证明者转 `BLOCKED_CONTEXT`。任一 Runtime 路径都不得默认 LIVE，同一 pre-cutover trigger 不得跨算法重算或重复外发；
27. `scene_binding_lifecycle` 与 explicit reinit 只做 no-state-value control，必须 close/cancel 已有 timer slot/handle，zero current-fact read/predicate/FSM/timer create|arm|advance|fire/Alarm/Outbox；下一条合格 production+LIVE `SceneEvent` 才可懒 bootstrap 并求值。
28. Admission/Scheduler/Things SubjectLifecycle/Runtime 各使用独立 producer principal 与封闭 publish API；正向分别只发 `SourceDelta`/`ScheduleEvaluate`/`SubjectLifecycle`/内部派生 kind 且只为 production+LIVE+SCENE_ID_V2。反向验证跨 Scene Topic 被 Kafka ACL 拒绝，role→kind/context/version 由 producer contract 拒绝；向 Runtime 注入未知/畸形 kind、oneof/payload/key/route 不一致或非法 context/version 时必须二次 fail closed/quarantine。测试不得用自填 producer-role header 冒充 broker 认证，也不得声称共享 Topic consumer 能识别“合法 foreign kind 来自错误 principal”。

验收报告记录硬件、镜像 digest、Kafka/franz-go 版本、配置、payload 分布、reports/s、points/s、records/s、MB/s、RF3 流量、p95/p99、lag age、恢复时间、best-effort 错误窗口与成本。

## 16. 风险与取舍

| 风险 | 影响 | 控制 |
| --- | --- | --- |
| 团队第一次使用 Kafka | 容易把 offset、transaction、rebalance 用错 | 教程、故障注入、共享客户端封装、代码 review 清单 |
| Scene async state 落后/丢失 | 恢复后可能缺变化或重复计算 | 完整 `scene_state`、类型化冷启动、后续输入/reinit、明确 SLO/告警，不宣传零丢失 |
| Scene revoke 后旧 state 迟到 | compacted 最新值可能回退并在恢复后误触发 | 按[Runtime 调度分章 §§8–9](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-failover)执行 best-effort fencing、幂等与故障注入量化；未来需要更强语义时另立 ADR |
| Scene event/state 写放大 | 增加 broker/network/storage | 批量 SOURCE_DELTA、state 配额、按 records/bytes 实测、固定 partition count |
| current affiliation 处理 backlog | 迁区前积压按新归属求值，与历史归属不同 | 作为明确产品语义记录；SubjectLifecycle/version/current-scope reconciliation 防旧成员复活 |
| Action 在 Outbox commit 前失败 | 可能丢动作 | retry/quarantine/人工最终策略；Outbox commit 后以 effectId 可靠重试 |
| 单物理集群 noisy neighbor | Data 峰值影响 Domain | principal/client quota、独立 namespace/告警；达到门槛物理拆 Domain |
| `scene_state` restore 慢 | partition 开放与 RTO 变差 | 按[Runtime 调度分章 §7](../6.规则引擎与场景联动/Scene%20Runtime%20调度、分片与故障转移.md#runtime-restore)对完整 compacted state 的 restore 做基准、配额和容量门禁 |
| Scene topic generation 迁移复杂 | 错误切换会双触发或乱序 | 固定 V1 partition count；需要扩容时另立迁移 ADR，禁止复用已撤销协议 |
| 外部 sink 不在 Kafka transaction 内 | 可能重复执行 | inbox/effectId、CAS、Outbox、CommandAttempt |
| franz-go 事务会提交整次 poll offsets | Raw 部分处理会永久漏消息 | ProtocolApplication 每次处理全部 polled records，任一桶失败整体 abort |
| 版本选择过新 | 客户端/运维经验不足 | 固定 patch/digest，Phase 0 兼容与故障测试，不跟随 latest 漂移 |

采用本设计的核心取舍是：Kafka-native 不等于所有 Runtime 都使用 Kafka EOS。每条链路分别冻结 durability、order、offset、replay 和 failure contract。

# 场景有状态计算规范

## 1. 文档定位与规范边界

本文是 Scene 有状态计算业务语义的唯一人类可读规范，统一定义状态容器、状态组件、五类
有状态算子、扩展能力、Timer 运行机制和 Reliable Delayed Action 持久效果。实现中的
arm、update、cancel、fire、冷启动、恢复、`NOT_READY`、freshness 与 fail-closed 行为必须以
本文为准。

本文不重新拥有相邻架构契约：

- [《场景联动 Runtime 主规格总纲》](场景联动%20Runtime%20主规格总纲.md)继续拥有 Runtime/产品
  边界、`scene_event`/`scene_state` wire 与物理 Topic、状态身份、事务、容量和总体恢复取舍；
- [《Scene Current Fact 设计》](Scene%20current%20fact设计.md)唯一拥有 Current Fact 写入者、
  投影、统一 comparator 的来源证据、读取 API、coverage、水线和部署档位；
- [《Scene Runtime 调度、分片与故障转移》](Scene%20Runtime%20调度、分片与故障转移.md#runtime-scope)
  唯一拥有 partition lifecycle、Actor lane、assignment/token、completion、restore activation 与
  revoke；
- [《算子语义与术语》](算子语义与术语.md)只维护共享术语、Fact 契约和旧锚点兼容入口；同一
  有状态计算规则若在那里仍有摘要，以本文为准；
- [《水线与读取屏障详解》](水线与读取屏障详解.md)提供 barrier 的完整直观解释，本文只规定
  barrier/coverage 必须先于 freshness 和业务求值。

本文使用“必须”“不得”“仅当”和 fail closed 表示规范性要求。无法证明输入、状态、身份、
读取完整性或配置可信时，不得把错误降级成业务 false、missing 或旧值继续求值。

## 2. 统一术语与分类

| 中文统称 | 英文规范名 | 成员 |
| --- | --- | --- |
| 场景有状态计算 | Scene Stateful Computation | 本规范全部能力 |
| 状态容器 | State Container | `SceneBindingState` |
| 状态组件 | State Component | `latest`、`rolling` |
| 有状态算子 | Stateful Operator | Edge/Change、Duration、Debounce、Cooldown、Hysteresis |
| 扩展能力 | Extension | Script、Alarm/FSM |
| 运行机制 | Runtime Facility | Timer |
| 持久效果 | Durable Effect | Reliable Delayed Action |

上述层次不得混称：`SceneBindingState` 是状态容器，不是算子；`rolling` 是状态组件，不是
算子；Timer 是支撑算子执行与恢复的运行机制，不是业务算子；Reliable Delayed Action 是动作
接受后的持久效果，不是普通 Timer。Script 与 Alarm/FSM 属于扩展能力，不计入五类内建有状态
算子。

本文沿用以下共享术语：

- **Binding**：已编译的场景绑定；`bindingId` 全生命周期不复用。
- **evaluation subject**：参数状态、FSM 和动作归属的计算主体。
- **TRIGGER argument**：其通过身份/顺序门禁的输入可由 Binding input receipt 授予本轮
  `triggerRight`，并因此发起数据求值的参数。
- **CONTEXT_ONLY argument**：只提供当前上下文；自身刷新不得单独发起数据求值。
- **semantic transition**：算子产生、可进一步映射为动作的稳定业务迁移；latest 更新、arm、
  cancel、candidate 替换和 cooldown gate 清除都只是 internal FSM update。
- **action acceptance**：本轮完整 Action Outbox 事务 commit 成功；commit 前的 transition/action
  都只是 tentative candidate。

## 3. SceneBindingState：状态容器、身份与状态层次

`SceneBindingState` 表示“一个 Binding 在一个 evaluation subject 上当前算到哪里”，稳定身份为：

```text
(tenantCode, bindingId, evaluationSubjectKey)
```

一个 `scene_state` record 只保存该身份下一个 Binding 的完整可恢复业务状态，不得序列化整个
Go Actor、mailbox、锁、编译对象、Actor 引用或进程内 Timer handle。逻辑层次如下：

```text
SceneBindingState
├── metadata / trusted ProcessingContext / identity version
├── arguments                 -> latest 状态组件
├── rollingArguments          -> rolling 状态组件
├── inputReceipts             -> 有界、可恢复的数据输入触发回执
├── members                   -> shared target 的有界成员切片与版本 guard
├── operator states           -> Edge/Change、Duration、Debounce、Cooldown、Hysteresis
├── extension states          -> Script、Alarm/FSM
└── timerState[]              -> 可恢复业务计时状态；不含进程内 handle

SceneBindingState 之外
└── PostgreSQL Action Outbox  -> 已接受动作与 Reliable Delayed Action
```

完整业务 schema 至少表达下列信息；实现可以使用等价的强类型布局，但不得丢失这些语义字段：

```text
SceneBindingState {
  schemaVersion
  tenantCode
  bindingId
  evaluationSubjectKey
  metadata {
    processingNamespace
    processingMode
    identityAlgorithmVersion
    configRevision
    semanticHash
    lastEvaluationMetadata
    lastSubjectAggregateVersion
  }

  arguments {
    argId -> latest value / availability / eventTs / observedAt /
             optional factVersion / retained provenance
  }

  members {
    sourceSubjectKey -> {
      active
      lastAggregateVersion
      arguments { argId -> latest state component }
    }
  }

  rollingArguments {
    argId -> bounded samples / sampleIdentityIndex / coverage state /
             retained provenance
  }

  inputReceipts {
    (sourceEventId, factDeltaId | occurrenceId, argId [, operatorId]) -> {
      envelopeHash
      sourcePosition
      bindingSemanticHash
      runtimeTriggerObserved
    }
  }

  scriptState
  alarmState
  fsmState {
    edgeChange
    duration
    debounce
    cooldown
    hysteresis
  }

  timerState[] {
    processingNamespace
    processingMode
    identityAlgorithmVersion
    operatorId
    timerKind
    operatorGeneration
    semanticHash
    timerAnchorPolicy
    anchor
    armedByTriggerId
    armedAt
    dueAt
    logicalTimerId
    timerFireId
    recheckPending
  }
}
```

`inputReceipts` 是 `SceneBindingState` 内的 **Binding input receipt**，不是 Action Outbox 中的
`EffectSetReceipt`。它必须可恢复，不得只放在进程内存。上表中的 key 已受外层
`(tenantCode, bindingId, evaluationSubjectKey)` 限定：LATEST 至少绑定
`sourceEventId + factDeltaId + argId`，OCCURRENCE/rolling 至少绑定
`sourceEventId + occurrenceId + argId`；若触发观察是算子局部的，key 还必须带
`operatorId` 或等价的状态组件作用域。相同稳定身份的 envelope 漂移必须在授予
`triggerRight` 前 fail closed。

当前输入的 latest/rolling merge、sample identity index、算子/FSM/Timer 变更与对应
receipt/`runtimeTriggerObserved` 必须先形成同一个 tentative next state，成功求值后只能作为
同一个序列化 `scene_state` image 一起发布，不得只推进 marker 或只发布业务状态。
有动作时仍须先经过 PostgreSQL Action Outbox 的接受边界；这不声称 Kafka 与 PostgreSQL
跨存储 exactly-once。

receipt 与 marker 必须有受配额的保留策略，但只能在同一 input domain 的受信、单调
minimum-redelivery frontier 已越过 `sourcePosition`，且所有支持的 restore/replay 路径都不会再投递
该 identity 时淘汰。无法证明安全却已达 hard cap 时，必须对该 Binding fail closed，不得
静默淘汰后让旧输入重新取得 `triggerRight`；本约束不引入无界 Inbox。

每个进入 latest 或 rolling 的值/样本必须保留其来源身份、envelope/payload hash、时间与版本域、
source position、FactContract 引用和完整 ProcessingContext 等 `RetainedFactProvenance`；Linked、
timer、transition 与 Outbox 派生路径不得只保留外层 `SCENE_ID_V2` 而丢失 lineage。具体事实字段
字典仍见[《算子语义与术语》§15.2](算子语义与术语.md#152-wire-与身份-hash)。

生产非 tombstone state 只能来自受信的
`processingNamespace=production && processingMode=LIVE && identityAlgorithmVersion=SCENE_ID_V2`。
完整 state 和每个 Timer slot 都必须保存创建它的原始 ProcessingContext 与身份版本。缺失、未知、
组合冲突、来源不可信或旧身份版本一律 fail closed/quarantine，不得加载为 live state，不得补默认
`LIVE`，也不得初始化参数、baseline、FSM、Timer、Alarm 或 Outbox。

`configRevision` 只表示最后一次处理 state 时使用的 current config；revision 改变不产生新 state
key。`semanticHash`/`bindingSemanticHash` 判断状态能否保留：语义不兼容时必须
close+tombstone，并等待下一次合格 live trigger 冷启动；Fact contract、身份、Timer anchor policy
或其时间域依赖变化都必须改变该语义指纹。

shared target 的 `members` 必须保存 active slice 和最近 REMOVE version guard。较旧 operation
不得覆盖较新 guard；版本相等只有在 member 仍 active 时才可应用 Linked；版本更高、inactive 或
guard 缺失时必须回查 Things current context。成员和 inactive guard 都受有界配额约束，淘汰
guard 后只能退化为 current-store validation，不能把迟到 Linked 当作 ADD。

device-target state 从 SOURCE、Schedule、恢复 reconciliation 或数据面 SubjectLifecycle 的
INIT/REINIT 建立时，必须保存已验证 current SubjectContext 的 `lastSubjectAggregateVersion`；后续
INIT/REINIT/DELETE 按 `< / == / >` gate 处理。DELETE 后只保留有界 transient deletion guard；
state/guard 缺失或 operation 版本更高时必须先读取 current SubjectContext，迟到旧 INIT 不得仅因
state 已 tombstone 而复活。transient guard 不进入 `scene_state`，恢复后仍由 current-store guard
兜底。

<a id="scene-state-write-compaction-protocol"></a>

### 3.1 `scene_state` 写入与 Compaction 协议

本节集中解释状态什么时候发布以及 Compaction 解决什么问题；物理 Topic、事务和失败窗口的唯一
完整定义仍在[主规格 §§8、12～13](场景联动%20Runtime%20主规格总纲.md#8-scene_state-逻辑与物理模型)，
本节不得被实现成第二套协议。

`scene_state` 是 compacted Topic 中的异步 best-effort **恢复副本**，不是动作接受边界，也不是
durable 业务真源。Runtime 的当前 accepted `SceneBindingState` 驻留在其 partition owner 的 Actor
lane；每当本轮成功接受的结果实际改变 arguments、rolling、receipt、member、FSM 或 Timer business
state 时，Runtime 才对该 key 执行一次完整 state image 的 Producer handoff。已经处理过且不产生
任何状态变化的 duplicate/stale no-op 不写新 image；Binding 禁用/删除、scope 退出、entity 删除和
显式 reset 写 tombstone。

发布顺序固定为：

```text
基于当前 accepted state 构造 tentative mutation view
  -> freeze + 规范序列化完整 next image + 配额校验
  -> 无动作：接受并发布内存 next state
     有动作：PG Action Outbox commit 成功后才接受并发布内存 next state
  -> 注册/取消进程内 Timer handle
  -> 对已校验 bytes 做一次异步 scene_state Producer handoff
```

序列化或配额校验失败、Action Outbox rollback、求值 fail closed 时都必须丢弃 tentative 结果：不替换
accepted state、不改变 Timer handle，也不发送 state。Producer 接受、broker ACK 或 callback 都不
改变已经完成的动作接受结论，也不进入 input completion 谓词；发送失败只记录日志、指标和告警，
后续恢复可能读到旧 image、缺 state 并执行类型化冷启动。

record key 必须保持完整复合身份；`scene_event` 与 `scene_state` 的 partition count 必须相同，state
partitioner 必须提取 `(tenantCode,evaluationSubjectKey)` 并与对应 target event 共置，不得依赖
client 默认 key hash。只有 Runtime 的 `state-writer` principal 可写完整 state；控制面只能写无
value tombstone，不得构造或覆盖完整 business state。

Kafka Compaction 最终只保留同一 key 的最新 image/tombstone，用于限制稳定存储量和恢复重放量；它
不会省掉 image 已经发生的序列化、Producer 发送、leader append、副本复制和 Cleaner I/O。因此，
“使用 compacted Topic”不能作为忽略实时 state append/s、平均 record bytes、RF 带宽和 Cleaner
headroom 的理由。

## 4. 统一求值顺序与 latest-value join

### 4.1 统一入口、上下文与触发权

四类上下文回答不同问题，不得互相替代：

| 名称 | 回答的问题 | 典型内容 | 明确不包含 |
| --- | --- | --- | --- |
| ProcessingContext | 输入属于哪个 namespace/mode，是否有生产副作用权限 | `processingNamespace`、`processingMode` 与受信契约引用 | current 组织归属、业务时间、算子 state |
| SubjectContext | subject 当前属于哪个 tenant/project/area/product，scope 是否适用 | typed subject identity、组织关系、aggregateVersion | 参数 latest、rolling、FSM、Timer handle |
| SceneBindingState | 某 Binding 在某 evaluation subject 上算到哪里 | 状态组件、算子/扩展业务状态、Timer slot | 全量设备关系、Actor、锁、编译对象 |
| Scene Current Fact | 当前可读取的受信业务事实是什么 | latest value、availability、时间/版本、freshness metadata | edge baseline、duration arm、debounce candidate、cooldown gate |

same-subject complete bundle、cross-subject target-keyed `LINKED_DELTA` bundle、Schedule、数据面
`SubjectLifecycle` 和 Timer fire 最终都进入同一 evaluation-subject lane。数据 bundle 必须先取得
至少一个 TRIGGER argument 的 `triggerRight`；Schedule、SubjectLifecycle 和 Timer 使用各自稳定
evaluation identity。`scene_binding_lifecycle` 与显式 reinit 只做 control-only state management，
不得进入业务求值顺序。

Timer anchor 与 evaluation identity 同样必须来自当前 trigger：DATA trigger 只能使用本轮取得
`triggerRight` 的 TRIGGER deltas；合法非数据 trigger 只能使用其契约显式冻结的稳定
anchor。Current Fact/CONTEXT_ONLY 值只参与当前 predicate，不得被反推成 Timer anchor。
本文所称“取得 `triggerRight`”是 Binding input receipt 的授权结果，与
`compareLatest=ACCEPT` 不是同一概念；projector 抢先造成的 `DUPLICATE_NOOP` 仍可能取得
该 Binding 的首次 `triggerRight`。

<a id="stateful-trigger-dependency-closure"></a>

#### 4.1.1 参数模式与触发依赖闭包

判断一个参数是否必须是 `TRIGGER`，先看它是否位于普通完整条件谓词中，再看它是否会推进、取消
或替换某个可恢复状态。普通“完整条件成立时执行动作”的谓词中，每个动态 argument 的变化都可能
让最终布尔值成立或失效，因此全部必须是 `TRIGGER`；凡位于有状态组件/算子的状态作用域内、且其
变化会改变该状态的动态 argument，也都属于强制触发依赖：

| 能力 | 必须发布为 `TRIGGER` 的动态依赖 | 不这样做会丢失什么 |
| --- | --- | --- |
| 普通完整条件谓词 | 谓词引用的全部动态 argument | 最后使完整谓词成立或失效的变化 |
| rolling | 每个产生窗口样本的 argument | 永久遗漏样本、窗口值与淘汰结果错误 |
| Edge/Change | 被观察谓词或规范化值表达式引用的全部动态 argument | 中间边沿或值变化 |
| Duration/FOR | “持续成立”谓词内引用的全部动态 argument | false 中断、取消和新的持续区间 |
| Debounce | 决定候选值/候选谓词的全部动态 argument | 短暂翻转、候选替换或回到 committed value |
| Hysteresis | 被上下阈值比较的值表达式引用的全部动态 argument | 跨越 HIGH/LOW 阈值及 latch 迁移 |
| Cooldown | 不新增数据 argument | 它由已接受 transition/effect 启动，由 Timer 到期清理 |
| Script、Alarm/FSM | 冻结 ABI 中声明会推进状态迁移的 argument | 当前仍为 DRAFT，发布器不得自行推断 |

发布编译器必须计算上述依赖闭包。闭包内 argument 强制为 `TRIGGER`；只有产品/DSL 显式建模成
`WHEN ... IF ...` 的 IF 外层附加门禁才可以是 `CONTEXT_ONLY`，其变化有意不主动求值。同一
argument 同时属于两类时 `TRIGGER` 优先；若提交配置把闭包内 argument 标为 `CONTEXT_ONLY`，
发布期必须拒绝。编辑器必须在保存前将结果逐 argument 显式写入 Binding，Runtime 不得依赖条件
顺序猜测；完整控制面规则见
[《控制面与匹配契约》§4.2](控制面与匹配契约.md#42-trigger-与-context_only)。

状态作用域由规范化 AST 和括号决定。例如：

```text
WHEN DURATION_2M(A > 30) COMPLETES IF B = CLOSED
  A = TRIGGER；B 可为 CONTEXT_ONLY

WHEN DURATION_2M(A > 30 AND B = CLOSED) COMPLETES
  A = TRIGGER；B = TRIGGER
```

第一条只要求 A 连续成立，B 是完成/求值时读取的外层当前门禁；第二条要求 A 与 B 共同连续成立。
若第二条仍把 B 设为 `CONTEXT_ONLY`，B 可以在两分钟内先 `OPEN` 再 `CLOSED`，Runtime 到期时只看见
最终值，从而错误地把已经中断的区间判为连续。read barrier 只能证明到固定要求水线为止的投影
完整，freshness 只能判断当前事实是否过旧；二者都不能替代对中间状态迁移的触发观察。

<a id="aggregate-predicate-rising-gate"></a>

#### 4.1.2 完整谓词上升沿动作门

多个 argument 都是 `TRIGGER`，表示它们各自的独立消息都可以进入 Binding 求值，并不表示每条消息
都独立执行动作。V1 普通“条件满足则执行动作”必须在完整布尔谓词外编译或复用一个
`Edge(RISING)`；其最小状态就是本规范 §6.1 已定义的 `initialized + previousPredicate`。

```text
P = A > 30 AND B = CLOSED

accepted previousPredicate = false
10:00:01  A = 31℃       -> P=false -> false，无动作
10:00:02  B = CLOSED    -> P=false -> true，产生一次完整 action set
10:00:03  A = 32℃       -> P=true  -> true，无动作
10:00:04  B = OPEN      -> P=true  -> false，只更新 baseline
10:00:05  B = CLOSED    -> P=false -> true，进入新的成立区间，再产生一次 action set
```

这里的“一次”以完整谓词的语义 transition 为单位，不以输入消息数量为单位：

- 同一个 source bundle 命中多个 TRIGGER，先按“每 Binding 每 bundle 最多求值一次”合并；
- 不同 source/设备的独立消息仍各自求值，但都在同一 evaluation-subject lane 串行读取和更新同一份
  `previousPredicate`，所以一个连续 `true` 区间只有第一次 `false -> true` 形成动作候选；
- 不得靠毫秒级等待、批量窗口或“同时到达”合并消息；这些策略既增加延迟，也无法定义可靠边界；
- 不得靠 `effectId` 合并不同 Trigger。`effectId` 只稳定标识同一逻辑 transition 的重试与下游幂等，
  两条不同输入本来就可能具有不同 trigger identity；动作门必须发生在 effect 创建之前。

带动作的 `false -> true` 必须先 commit PostgreSQL Action Outbox，再把
`previousPredicate=true` 随 tentative next state 接受；commit 失败时丢弃 tentative mutation，重试
仍从旧 baseline 开始。同一 lane 中后续 Trigger 不得越过这次接受边界。`true -> true` 不产生
semantic transition、`effectId` 或 Outbox row，但仍可接受本轮必要的 latest、receipt 等状态更新。

这个动作门复用现有 `SceneBindingState.operator states` 和 `scene_state` compacted Topic，不新增
durable gate、Kafka Topic 或 PG 状态行。它提供的是同一 active owner/lane 正常持有 accepted state
期间的单次上升沿语义，不把异步 best-effort 恢复副本升级成严格真源：

普通谓词的布尔计算本身仍可以是无状态代码，只有“是否已进入当前 true 区间”的动作门是最小
有状态部分。普通 latest-value join 本来就要在同一 `SceneBindingState` 中维护 arguments 和
inputReceipts；`previousPredicate` 只随这些字段进入同一份完整 image，通常不会为同一轮处理另发
第二条 state record，但会增加少量 image bytes，实际 append/s 与容量仍按 §3.1、§11 验收。

- 缺 state 或不兼容时按 Edge 的 `BASELINE_ONLY` 以当前 READY 谓词建立 baseline，首轮不补发动作；
- 恢复到滞后的 `previousPredicate=false` 后再次看到当前 `true`，可能重复形成 rising；恢复到滞后的
  `true` 也可能漏掉故障窗口内的新区间；
- 上述极少量重复/漏触发属于 V1 已接受的 crash、rebalance、state-send 残余窗口。若业务要求跨该
  窗口严格一次，必须另立 durable predicate gate；本规范不为此新增持久化写放大。

若未来产品需要“谓词为 true 时每个合法输入都执行动作”，必须新增明确、可见且可验收的动作模式；
V1 不得把它作为普通条件的隐藏默认。

### 4.2 Tentative state：提交隔离，不是完整深拷贝

tentative state 的规范目的，是让当前 accepted state 在本轮校验和动作接受完成前保持不变。文档中
用 `v17 -> tentative v18` 表示旧/新逻辑 image 时，`v17/v18` 只是帮助理解的代号，不是要求新增
schema version，也不表示必须复制整棵 Go 对象图。

推荐实现把 accepted state 当作不可变 base，并在当前 lane 内建立有界 mutation overlay：

```text
StateTxn
├── base: accepted state，只读
└── mutations
    ├── latest / rolling append-and-evict
    ├── receipt / runtimeTriggerObserved
    ├── member / scope guard
    ├── operator / extension FSM
    └── Timer slot final mutation
```

实现可以使用 `base + mutation overlay`、只复制被修改组件的 copy-on-write、结构共享的不可变容器，
或能通过同等故障测试证明精确回滚的等价机制。规范序列化器可以直接遍历 base+overlay 形成完整
next image，不要求先物化第二份完整对象。默认实现不得在每次求值时无条件深拷贝完整
`SceneBindingState` 对象图；若某实现选择完整复制，必须由容量 POC 证明其分配带宽、GC pause 和
heap headroom 满足签字预算。

无论采用何种结构，都必须满足以下不变量：

- tentative 修改不得通过共享 map、slice、rolling index、指针或可变子对象泄漏到 accepted base；
- freeze/序列化/配额失败或 PG rollback 后，accepted state、receipt、FSM、Timer slot 和进程内
  Timer handle 必须与本轮开始前完全一致；
- 成功时以 lane 内一次 publish/指针替换把 frozen next image 变成 accepted state；并发读者不得看到
  半更新的组件组合；
- 异步 Producer 使用的 encoded bytes 在 Producer 接管或完成前必须保持不可变；buffer pool 不得
  提前复用造成已排队 state 漂移；
- 同一 logical input 重试必须从仍被接受的 base 和同一稳定 identity 重算，不能依赖已丢弃
  tentative 对象中的 marker。

每轮求值必须按以下顺序形成 tentative 结果：

1. 在 lookup、参数构造或状态变更前验证 trigger 及现有 state/Timer slot 的完整
   ProcessingContext 与身份版本；非法输入 fail closed/quarantine。
2. 从 current ProjectIndex 取得 BindingCtx，检查 Binding enabled；读取 current SubjectContext，
   检查 tenant/project、scope 和 target applicability。
3. 解析全部必要 Current Fact 与 source route；先完成读取 readiness/coverage/conflict 检查。失败时
   retry 或 fail closed，不得进入 missing/freshness 或 predicate。
4. 取得现有 `SceneBindingState`；缺失、损坏或语义不兼容时按第 10 章冷启动，在 tentative state
   上以 Current Fact 查询结果建立 baseline。
5. 按第 5 章合并完整 argument bundle：latest 使用 `compareLatest`，rolling 使用稳定样本身份；
   当前 bundle 不得无条件覆盖查询到的更新值。
6. value merge 与 `triggerRight` 必须分别计算。身份/order conflict 在任何 grant 前 fail closed；
   BindingState receipt 已记录 `sourceEventId/factDeltaId` 时，redelivery 无触发权；若 Current Fact
   仅因独立 projector 抢先而与当前输入完全相同、但该 BindingState 尚未处理它，当前输入仍保留
   恰好一次触发权。store stale 无触发权，store 较旧或缺失取得一次；纯 CONTEXT_ONLY refresh
   只允许更新并持久化参数。只有本轮取得 `triggerRight` 的 TRIGGER delta 才能参与
   DATA Timer anchor。
7. 数据 bundle 仅当至少一个 TRIGGER argument 取得触发权时进入业务求值，并且每个 Binding 每个
   bundle 最多求值一次；未变化参数从 tentative state 读取。
8. 解析 Argument source，以本轮参数视图执行 latest-value join，再按显式 missing/freshness 策略
   得到 READY、false 或 `NOT_READY`。
9. 仅对 READY 且拥有合法数据或非数据 trigger 的轮次执行 predicate 与对应算子/扩展 FSM。普通
   条件动作先经过 §4.1.2 的完整谓词 `Edge(RISING)`；只有语义 transition 才形成 action candidate。
10. Cooldown 只过滤配置指定的 action candidate，不阻止 latest/rolling 更新或维持正确性所需的
    FSM tentative update。
11. 汇总 tentative next state、transition candidate 和 action set；实现不得依赖 map 遍历顺序决定
    结果。
12. 带动作的 tentative transition 只有在主规格定义的 PostgreSQL Action Outbox 事务 commit 成功
    后才被接受；commit 失败不得发布 FSM、Timer 或 Cooldown 变化。成功完成时必须把对应
    BindingState receipt 与 rolling `runtimeTriggerObserved` marker 随 next state 原子推进，使同一
    logical input 的后续 redelivery 不再取得触发权。

Latest-value join 的语义是“一个 TRIGGER 参数取得本轮 `triggerRight`，加上本轮 state 中其他
参数的当前值，立即
求值”，不要求不同设备参数具有相同 event timestamp：

```text
10:00:01  device:A.temperature = 31.2
          humidityB 缺失 -> NOT_READY

10:00:03  device:B.humidity = 75
          使用 temperature=31.2 与 humidity=75 立即求值
```

需要同一 event-time 切面、严格跨设备 JOIN、session、CEP 或大窗口时必须交给 Flink。

## 5. latest 与 rolling：状态组件

latest 与 rolling 只保存求值输入状态，不自行产生 semantic transition；Edge/Change 等算子消费
这些组件并维护各自 FSM。

<a id="state-component-latest"></a>

### 5.1 latest

latest 是 `LATEST_STATE` SingleValue 参数在本轮 `SceneBindingState` 中的有界输入视图，至少保存
initialized/availability、规范化值或 tombstone、`eventTs`、`observedAt`、可选
`factVersion`、`factDeltaId`、envelope/payload hash 与 retained provenance。它不是 Current Fact
写入槽；Current Fact 的唯一写入者、durable 顺序、barrier 和读取状态只见
[《Scene Current Fact 设计》](Scene%20current%20fact设计.md)。Runtime 对其只读并在 tentative
state 上 overlay 当前 bundle。

Current Fact、bootstrap/evaluation-time overlay 与 Scene latest 必须使用同一
`compareLatest` 契约：

1. 旧值不存在时 `ACCEPT`。
2. `factDeltaId` 相同且完整 envelope 相同为 `DUPLICATE_NOOP`；任一 envelope 字段漂移为
   `FACT_IDENTITY_CONFLICT`。
3. order domain 或 encoding 不兼容为 `ORDER_DOMAIN_CONFLICT`。
4. 先比较 `eventTs`：较新为 `ACCEPT`，较旧为 `STALE_NOOP`。
5. `eventTs` 相同而只有一侧存在 `factVersion` 时为 `VERSION_PRESENCE_CONFLICT`。
6. 双方都有版本时调用来源 FactContract 冻结的 comparator：更高为 `ACCEPT`，更低为
   `STALE_NOOP`；同 order 且 payload 相同为 `DUPLICATE_NOOP`，payload 不同为
   `SAME_ORDER_DIFFERENT_PAYLOAD_CONFLICT`。
7. 双方都无版本时，同 payload 为 `DUPLICATE_NOOP`，不同 payload 为
   `AMBIGUOUS_SAME_TIMESTAMP_CONFLICT`。

value 与 UNAVAILABLE/tombstone 使用相同门控。不得用 Kafka offset、到达顺序、配置 revision 或
“最后写赢”解决冲突。所有 conflict 都必须 fail closed/quarantine；comparator duplicate 不修改
value，也不刷新 freshness。`triggerRight` 另算：BindingState receipt 已处理该
`sourceEventId/factDeltaId` 时 redelivery 无权；Current Fact 仅因独立 projector 抢先而与当前输入
完全相同、但 receipt 尚无记录时，当前输入保留恰好一次触发权；store stale 无权，store 较旧或
缺失取得一次。identity/order conflict 必须在任何 grant 前 fail closed。更高版本即使规范化值相同
仍是来源更新，但是否产生 Change transition 仍由 canonical value equality 决定。

<a id="state-component-rolling"></a>

### 5.2 rolling

rolling 是单 evaluation subject、单参数的有界窗口状态组件。Scene V1 必须按稳定样本/occurrence
身份去重：LATEST 样本主身份是 `factDeltaId`，OCCURRENCE 样本身份是 `occurrenceId`。
`eventTs` 只用于窗口排序和 cutoff；不同 occurrence 即使 timestamp 相同也必须并存，不得互相覆盖。

相同身份且 envelope 相同为 duplicate，不新增样本，也不刷新 freshness；相同身份发生 envelope
漂移为 identity conflict，必须在任何触发权 grant 前 fail closed/quarantine。
`sampleIdentityIndex` 必须有界保存去重索引；`runtimeTriggerObserved` 与 BindingState receipt 单独
裁决触发权：当前 sample 尚未成功求值时保留恰好一次触发权，成功求值时原子标记；后续 redelivery
无权。被替换身份作为 bounded dedupe entry 保留到 cutoff prune；active sample、排序索引、身份
索引与 receipt/observed marker 必须原子更新并分别受发布期 hard cap 约束。

Scene rolling 没有 watermark/allowed lateness，永远不得声称未来不会再到达窗口内的较旧
`eventTs`。coverage 状态固定为：

- `ROLLING_COVERED_AT_BARRIER`：受信 window reader 按同一 FactContract、严格
  `production+LIVE` provenance 与 source frontier/read barrier 返回完整受限窗口；不保证未来
  没有迟到样本；
- `ROLLING_PARTIAL_WARMING`：没有受信历史，从空窗开始；
- `ROLLING_PARTIAL_OBSERVED_WARM`：首个 accepted sample 记录 `warmupStartedAt`，
  `maxAcceptedObservedAt` 单调推进，二者跨度达到 `windowDuration` 后进入该状态。

`rollingBootstrapPolicy=REQUIRE_COVERED_AT_BARRIER` 是默认值。受信 reader 无法证明 coverage
时，业务结果只能为 `NOT_READY`；只有显式策略允许时才可保留 partial warming 状态。没有 coverage
的求值必须 zero-effect，不得形成 transition 或动作。rolling argument 必须是 TRIGGER；
`CONTEXT_ONLY + ROLLING` 必须在发布期拒绝。

窗口跨度、最大点数和最大状态字节必须在发布期声明。只可按声明窗口淘汰 cutoff 外样本；窗口内
样本超出硬配额时必须 fail closed，不得静默裁剪后继续产生动作。Scene 与 Flink 的容量边界见
第 11 章。

#### 例：单设备“5 分钟内平均温度”的一轮处理

该例是单 evaluation subject、单温度参数的 Scene rolling，可以留在 Scene；第 12 章三个设备共同
求平均属于跨设备窗口，必须进入 Flink，两者不要混淆。假设 10:05:00 收到温度 34℃，accepted
state 中已有以下覆盖有效的样本：

```text
10:00:30  28℃
10:02:00  30℃
10:04:00  32℃
```

一轮处理如下：

1. lane 读取当前 accepted state 作为只读 base；warm state 且 coverage 仍有效时不重复查询整个
   历史窗口，cold bootstrap 才按第 10 章经 read barrier 读取受限 5 分钟历史。
2. 以 `factDeltaId` 检查 34℃ 样本身份；duplicate 与 identity conflict 按本节门禁处理。`eventTs`
   只用于排序和 cutoff，窗口内迟到样本不能仅因时间较旧就被当成 stale，也不能只按时间戳去重。
3. 在 mutation overlay 中 append 34℃，删除 `eventTs < 10:00:00` 的样本，并同步更新排序/身份
   索引、coverage、Binding input receipt 与 `runtimeTriggerObserved`；accepted base 尚未改变。
4. 本轮窗口为 `28、30、32、34`，平均值为 31℃。以同一 tentative 参数视图执行 predicate 和
   Edge/Duration 等算子，形成最终 FSM/Timer mutation 与可选 action set。
5. 从 base+overlay 规范序列化完整 next image，校验 rolling 点数、全部状态组件和 32 KiB 配额。
6. 若没有动作，校验成功就是本轮本地 state 接受边界；若产生动作，必须先等完整 Action Outbox
   事务 commit。失败时丢弃 overlay，重试仍从旧 accepted state 开始。
7. 接受后一次性发布 next state、更新 Timer handle，并把步骤 5 的完整 bytes 异步 handoff 到
   `scene_state`。因此可恢复状态的发布触发点是“本轮成功接受且 state 实际变化”，不是周期性
   checkpoint，也不是等窗口结束才上传。

即使只计算平均值，滑动窗口也不能通常只保存 `sum+count`：旧样本到达 cutoff 时必须知道应减去哪
一个值。可以使用有界样本、时间桶/环形桶及其 `sum+count` 等等价可淘汰结构，但必须保持稳定样本
身份、迟到/重复语义、coverage 和精确淘汰能力；改变表示形式不能削弱本节语义。

## 6. 五类有状态算子

五类算子都只在输入 READY 且本轮具有合法 trigger 时运行。`NOT_READY` 不等于 false，不得伪造
edge/change，也不得绕过 Timer fire 的 current-value/freshness 复核。transition 映射为动作时，
对应 next state 只有在动作接受后才能发布。

<a id="stateful-operator-edge-change"></a>

### 6.1 Edge / Change

Edge 检测 predicate 的 rising、falling 或任一边沿；Change 检测规范化值是否真正改变。最小状态
包含 `initialized`，以及 Edge 的 `previousPredicate` 或 Change 的
`previousCanonicalValue`/有界等价 hash。

被观察 predicate/canonical-value 表达式引用的全部动态 argument 都必须是 `TRIGGER`；只位于
Edge/Change 外层动作门禁的参数才可为 `CONTEXT_ONLY`。

- 首次 READY 值只建立 baseline，不产生 transition。
- 后续 READY 值与 baseline 相同只更新必要 metadata；false→true 产生 rising，true→false 产生
  falling，Change 的 canonical value 不等时产生 changed pulse。
- 每轮最多输出一次语义 pulse，随后以 current 值作为新 baseline。
- `NOT_READY` 不更新 baseline，也不伪造 transition。
- transition 带动作时，baseline 必须等 Action Outbox commit 成功后才随 next state 发布。
- Scene V1 的直接 OCCURRENCE 不允许 edge/change 或其它依赖 occurrence 到达先后的 FSM；Kafka
  到达顺序不得冒充业务顺序。

示例：温度首次为 29℃只建立 false baseline；随后 31℃产生 rising；32℃保持 true 不重复；28℃
只在 Binding 配置 falling 输出时产生对应 transition。

<a id="stateful-operator-duration"></a>

### 6.2 Duration / For

Duration/FOR 确认 predicate 连续成立达到固定时长，一轮 true 区间只完成一次。最小状态包含
`IDLE/ARMED/FIRED` phase、predicate、`armedByTriggerId`、Timer anchor、`armedAt`、`dueAt`
和 current logical Timer slot。

持续 predicate 引用的全部动态 argument 都必须是 `TRIGGER`，使其中任一变化都能建立、保持、
取消或重新开始正确区间；Duration 外层只在完成时检查的门禁参数才可为 `CONTEXT_ONLY`。

- false→true：按本算子的 `timerAnchorPolicy` 选择本轮稳定 anchor，设置 `armedAt/dueAt` 并进入
  ARMED。
- true→true：保持原 anchor、`armedAt` 和 `dueAt`，重复 true 绝不重置计时。
- true→false：清除当前 slot、取消内存 handle，进入 IDLE。
- FIRED→true：不重复 arm 或输出；FIRED→false 才回到 IDLE。
- 初始 `NOT_READY` 不得 arm；已有 arm 遇到 `NOT_READY` 时必须按显式策略 CANCEL 或 KEEP_ARMED。

到期 callback 回到原 evaluation-subject lane 后，必须验证 current Binding、current slot/
`timerFireId`、scope/applicability、当前 predicate 和全部必要参数 freshness。身份或适用性失配是
stale callback no-op；predicate=false 时取消；`NOT_READY` 按策略处理。全部通过后才形成一次
duration-complete transition candidate；带动作时，只有 Outbox commit 成功后 phase 才发布为
FIRED。

对 DATA trigger，默认/推荐 `timerAnchorPolicy=OBSERVED_AT`，anchor 只取本轮取得
`triggerRight` 的 TRIGGER deltas 的 `max(observedAt)`，retry 不得重读 wall clock；
`EVENT_TS` 也只取这些 deltas，且仅在时间域可比并有可解析的 `schedulerDeadlinePolicyRef` 能
确定性映射到可信平台 epoch deadline 时允许。合法非数据 trigger 只能使用其契约显式冻结的稳定
anchor，例如 Schedule 的 `plannedFireTs`；没有合格 anchor 时保持 `NOT_READY`，不得 arm。完整
身份约束见第 8 章。

示例：规则要求“温度高于 30℃持续 5 分钟”。10:00 首次由合格 trigger 观察到 31℃并 arm，10:03
再次收到 32℃时保持原 `dueAt=10:05`，不得重置；10:05 callback 复核仍高于 30℃后才形成一次
duration-complete transition。若 10:04 降到 29℃则取消，本轮不产生动作。

<a id="stateful-operator-debounce"></a>

### 6.3 Debounce

Debounce 只提交稳定保持一段时间的候选值，过滤短暂翻转。最小状态包含可选
`committedValue`、`candidateValue`、`candidateSince/armedAt`、`dueAt` 和 current Timer slot。

决定 candidate value/predicate 的全部动态 argument 都必须是 `TRIGGER`；否则 Runtime 无法观察
短暂翻转、候选替换或回到 committed value，防抖语义会退化为稀疏采样。

- current value 等于 committedValue：清除 candidate 并取消 Timer。
- current value 不同且没有 candidate：建立 candidate，并按本算子的 `timerAnchorPolicy` arm。
- current value 等于已有 candidate：保留原 candidateSince 与 dueAt，不重置。
- candidate 变为另一值：替换 candidate，并使用本轮取得 `triggerRight` 的新 TRIGGER 输入的
  稳定 anchor 重置 dueAt。
- candidate 回到 committedValue：取消本轮，不产生 transition。
- `NOT_READY` 不是候选值；KEEP_CANDIDATE 或 CANCEL 必须由显式策略决定。

到期 callback 必须执行与 Duration 相同的身份、Binding、scope、readiness、freshness 和 current-value
复核。仅当 current value 仍等于 candidate 且 candidate 不同于 committedValue 时，才提交新值并
产生一次 transition。Timer 到期本身不证明 candidate 仍成立。Debounce 的 OBSERVED_AT/EVENT_TS
选择与限制完全遵守 §6.2 和第 8 章。

示例：风压上报在 `NORMAL/ALARM` 间抖动，要求 `ALARM` 稳定 30 秒才提交。第一次看到 `ALARM`
建立 candidate；20 秒后回到 `NORMAL` 就取消；再次进入 `ALARM` 使用新的合格 trigger anchor 重新
计时，只有到期复核仍为 `ALARM` 才产生 transition。

<a id="stateful-operator-cooldown"></a>

### 6.4 Cooldown

Cooldown 是动作 gate，不是 predicate、Edge 或 Duration 的替代品。最小状态包含 active gate、
`startedByTransition/effect` identity、不可变 `acceptedAt`、`cooldownUntil` 与可选清理 Timer slot。

Cooldown 不要求额外数据 argument 成为 `TRIGGER`：它由上游 semantic transition/action acceptance
启动并由 Timer 清理。上游 Rolling、Edge、Duration 等自身的触发依赖仍必须照常推进，不能因为
动作处于冷却期而降为 `CONTEXT_ONLY`。

- 只能在当前动作/transition 被 PostgreSQL Action Outbox 事务成功接受后开始；predicate=true、
  tentative transition、insert/commit 失败都不得开始。
- `cooldownUntil = acceptedAt + configuredDuration`；相同 effect 重试必须复用首次 acceptance，不能
  按重试时间延长。
- 冷却期间仍更新 latest、rolling 和维持正确性所需的 FSM，只抑制配置明确指定的 action candidate。
- 被抑制事件不重置或延长 fixed cooldown；V1 不得暗中实现 sliding cooldown。
- 到期只清除 gate，不产生 transition 或补发动作；state close 取消 handle，但不撤销已 commit 输出。
- 缺失 Cooldown state 时恢复为“不在冷却期”，明确接受极少量重复风险。

示例：高温告警动作成功接受后进入 10 分钟 fixed cooldown。期间温度继续更新，Duration/Edge 等
正确性状态也继续推进，但新的同类告警 action candidate 被抑制；这些输入不把 cooldown 延长到
“最后一次高温之后 10 分钟”。

<a id="stateful-operator-hysteresis"></a>

### 6.5 Hysteresis

Hysteresis 用上下阈值形成中间带，防止数值在单阈值附近反复切换。发布时必须满足 `low < high`。
最小状态为 `initialized`、`currentBand` 和 `latchedSide`：`value <= low` 为 LOW，
`low < value < high` 为 MIDDLE，`value >= high` 为 HIGH。

用于计算被监控 value 的全部动态 argument 都必须是 `TRIGGER`；只有 Hysteresis 外层附加门禁才可
为 `CONTEXT_ONLY`，否则跨阈值与 latch 迁移可能被漏掉。

- 首次 READY 值只确定 band/latch，不触发；首次在 MIDDLE 时 `latchedSide=UNKNOWN`。
- 进入 HIGH 且 latch 不是 HIGH：锁存 HIGH，产生 high transition。
- 进入 LOW 且 latch 不是 LOW：锁存 LOW，产生 low transition。
- 进入 MIDDLE：更新 currentBand，但保持 latchedSide；MIDDLE 内变化不产生 transition。
- `NOT_READY` 不改变 band 或 latch；本算子没有 Timer 或待取消 handle。

HIGH/LOW 到 active/inactive 的映射必须在 Binding 中显式配置，不得由数值正负或阈值名称猜测。

示例：风机控制使用 `high=30℃`、`low=27℃`。温度首次到 31℃锁存 HIGH 并触发开启；之后在
29℃、28℃之间波动仍保持 HIGH，不反复切换；降到 27℃才锁存 LOW 并触发关闭。

## 7. Script 与 Alarm/FSM 扩展边界

Script 与 Alarm/FSM 属于场景有状态计算，但不是五类内建算子。它们可以占用
`SceneBindingState` 中的有界扩展状态并使用统一求值/恢复门禁；尚未冻结的配置、状态迁移或 ABI
不得由实现自行补齐，也不得因出现 state 字段就宣称已实现。

<a id="extension-script"></a>

### 7.1 Script

Script 必须无外部 I/O、无随机数、不直接读取 wall clock，并受 CPU、内存、执行时长和结果大小
限制。它只能操作当前 `SceneBindingState` 中的有界参数，不允许递归、无界数组或动态扩张状态。
复杂事件时间、跨实体计算和大状态必须转入 Flink。

Script 的 sandbox ABI、状态 schema/version migration、确定性 API 和具体资源配额尚未在本阶段
冻结，因此只能视为扩展边界，不能据此生成或实现未定义的运行时行为。

<a id="extension-alarm-fsm"></a>

### 7.2 Alarm/FSM

Alarm/FSM 状态随完整 `SceneBindingState` 恢复；Alarm duration 可以使用普通 Timer，但 Alarm/FSM
本身仍是扩展而不是 Timer。当前 active Alarm 可以从 Alarm 业务库懒加载；duration 遵守本文
Timer anchor 与到期复核规则；缺失 repeating count 时重置。scope state 删除或退出不自动 clear
既有 active Alarm，只有场景显式产生补偿/clear transition 时才形成新的 Action Outbox row。

Alarm/FSM 的状态层级、确认/恢复协议、并发事件仲裁和版本迁移尚未完整冻结。AlarmSignal 是动作
kind/payload，不得被建模成与 state/Timer 同事务提交的另一套 Scene 状态表。

<a id="runtime-facility-timer"></a>

## 8. Timer：运行机制

普通 Timer 支撑 Duration、Debounce、Cooldown gate 清理和 Alarm duration 等能力；它不是业务
算子。进程内 ScheduledFuture/Go handle 只是可重建的调度加速对象，不得序列化，也不得作为恢复
事实来源。`SceneBindingState.timerState[]` 保存业务 timing state；普通 Timer 不建立 PostgreSQL
`scene_timer` 事实表。

每个 slot 必须保存创建它的完整 ProcessingContext、`SCENE_ID_V2`、operator/timer kind、
operator generation、semanticHash、Timer anchor policy/anchor、`armedByTriggerId`、`armedAt`、
`dueAt`、`logicalTimerId`、`timerFireId` 和 recheck 状态。只有受信
`production + LIVE + SCENE_ID_V2` trigger 才能创建、推进或恢复 live Timer。

Timer 身份必须满足：

- `logicalTimerId` 稳定标识 processing namespace、tenant、Binding、evaluation subject、operator、
  timer kind 与当前 operator generation/semanticHash 下的逻辑 slot；
- `timerFireId` 稳定标识该 slot 的当前 arm，必须覆盖 `armedByTriggerId`、选定 anchor 及 policy、
  operator generation、semanticHash、`armedAt` 和 `dueAt`；
- anchor policy 及其时间域依赖必须进入 semanticHash；配置改变后旧 state/slot 不得 preserve；
- retry、redelivery、rebalance 或 restore 必须复用已保存字段，不得移动 `dueAt` 或生成新的
  `timerFireId`。

`timerAnchorPolicy` 按算子配置：

- DATA trigger 的 `OBSERVED_AT` 是默认且推荐策略，只取本轮真正取得 `triggerRight` 的
  TRIGGER deltas 的 `max(observedAt)`；不得在重试或 callback 时重新读取 wall clock。
- DATA trigger 的 `EVENT_TS` 也只取上述 deltas，且仅在时间域可比、
  `schedulerDeadlinePolicyRef` 能把该域确定性校验/映射到可信平台 epoch deadline 时允许；
  boot-relative、仅设备局部单调或无法映射的时间不得 arm。
- 合法非数据 trigger 只能使用其 trigger contract 显式冻结的稳定 anchor；例如 Schedule 使用
  `plannedFireTs`。不得从任意 CONTEXT_ONLY 或 Current Fact/latest 值推断、回填或回溯 anchor。
- 当前 trigger 没有合格的冻结 anchor 时，Duration/Debounce 必须保持 `NOT_READY`，不得 arm。

callback/Timer fire 必须原样继承 slot context/version，先通过 Runtime 当前 assignment/token 与
lane gate，再回到对应 evaluation-subject lane。业务求值前必须检查 current Binding enabled、
`logicalTimerId/timerFireId/current-slot`、scope/applicability、current predicate/candidate、读取
readiness 与 freshness。任何身份或 slot 不匹配都是 stale callback no-op；非法 context/version
必须 fail closed/quarantine。Timer fire 不是新的 `SceneEvent` record。

恢复发现 dueAt 已过时，只能把当前 fire 排回 lane 并执行完整复核；恢复线程不得直接产生
transition/action。state close 会使 slot 失效并取消 handle，之后到达的旧 callback 按 current-slot
检查 no-op。具体 handle 安装、activation queue、partition revoke 和 callback token gate 只见
[Runtime 调度分章 §§5～8](Scene%20Runtime%20调度、分片与故障转移.md#runtime-normal-completion)。

<a id="durable-effect-reliable-delayed-action"></a>

## 9. Reliable Delayed Action：持久效果

Reliable Delayed Action 表示“动作已经被业务接受，只是要求以后可靠投递”。它与等待条件是否
成立的普通 Timer 是两类责任：Duration/Debounce 到期仍需回 lane 复核；Delayed Action 在接受时
已经冻结不可变动作意图。

动作仅当来自受信 `production + LIVE + SCENE_ID_V2` 求值且 PostgreSQL Action Outbox 本地事务
commit 成功时才被接受。Outbox row 必须保存稳定 effect identity、不可变 payload、原
ProcessingContext/身份版本及 `executeAfter`/`available_at`；dispatcher 只在到期后领取，并在
dequeue 和每次外发前二次验证允许的 context/version。

已 commit row 不依赖 `SceneBindingState`、普通 Timer slot 或进程内 handle 保证投递。V1 默认
`CONTINUE_AFTER_ACCEPT`：state close、Binding disable、scope exit 或 entity delete 都不自动取消，
也不得扫描并回滚旧 transition。业务需要撤销时必须显式建模新的补偿/取消动作。

不得把 Delayed Action 塞入 Duration/Debounce slot，不得为它额外创建 PG state/timer row，也不得
把普通条件 Timer 伪装成已接受动作。dispatcher 的至少一次物理投递仍必须携带同一 `effectId`
作为下游幂等键；唯一 Outbox row 不等于目标端 exactly-once。

<a id="stateful-not-ready-freshness-fail-closed"></a>

## 10. 冷启动、恢复、NOT_READY、新鲜度与 fail-closed

**NOT_READY。** `NOT_READY` 表示当前不足以作出业务判断，常见原因是必要参数缺失、明确
UNAVAILABLE/tombstone、类型非法，或通过 readiness 后按显式 freshness 策略判定 stale。它不是
false，也不是 edge/change；不得产生 transition/action。已通过身份和更新门控的参数仍可保存。

每个必要参数必须显式配置 missing/freshness 策略，至少说明：

- missing/UNAVAILABLE/tombstone 是否直接 `NOT_READY`；
- 是否允许保持最后值直到反向输入；
- 最大 freshness；
- stale 时把 predicate 视为 false 并取消 arm，还是 KEEP_ARMED 但禁止 fire；
- accepted offline fact/state 是否使参数失效或取消 Duration；
- Timer fire 时必须重读和复核哪些 Current Fact。

没有策略时不得猜测“缺数等于 false”或“最后值永远有效”。freshness 使用 Current Fact 的
`observedAt`/接收状态元数据；`eventTs` 仍用于 latest 排序、rolling cutoff 和显式 EVENT_TS anchor，
两者不得混成一个字段。duplicate 不刷新 freshness。

**读取完整性先于 freshness。** 每次 data、Schedule、Timer 或 SubjectLifecycle 业务求值都必须先
验证 Current Fact readiness/coverage/conflict，之后才检查 freshness，再进入 predicate/FSM：

```text
readiness / coverage / conflict
    -> freshness / missing policy
        -> predicate / operator / Timer / action
```

`PROJECTION_NOT_READY/BEHIND`、`LOOKUP_FAILED` 或 `PROJECTION_CONFLICT` 是投影/读取失败，不是
业务 missing；必须 bounded retry，耗尽后 fail closed，不得用 state/store 中旧值降级。FULL 档
要求固定 read barrier 与 coverage 证明；DIRECT_TD 只有其明确声明的软 lag 门和较弱保障。完整
barrier 捕获、route vector、retry 与档位差异只见
[《水线与读取屏障详解》](水线与读取屏障详解.md)，本文不复制该协议。

缺少共享 expiry signal 时，Scene 只承诺在下一次输入或已有 Timer fire 时发现 stale，不承诺在
stale 的精确时刻唤醒全部 state。KEEP_ARMED 的 callback 若被 freshness/`NOT_READY` 阻止，必须
保留原 slot、dueAt、timerFireId 并标记 `recheckPending`，不得忙循环或更换 identity；后续 freshness
恢复信号或 accepted input 到达时，predicate/candidate 仍成立且 dueAt 已到，才把原 fire 排回 lane；
predicate=false 或策略要求 CANCEL 时清除。

**冷启动。** `SceneBindingState` 缺失、损坏或不可用时，只能由已经通过
`production + LIVE + SCENE_ID_V2` 门禁的首个 SOURCE/LINKED、Schedule 或数据面
SubjectLifecycle trigger 在 handler 内惰性初始化；不得全租户/全实体扫描、回放历史
`scene_event`/Canonical、补演历史 transition 或以控制面立即求值。

冷启动固定顺序为：

1. 按 current BindingCtx 建立空 tentative state。
2. 并行读取全部必要 Current Fact 和受限 rolling history，并先验证 readiness/coverage。
3. 以查询结果为 baseline，再按 §5 comparator/identity 规则合并当前 bundle；当前 Delta 不得
   无条件覆盖更新的查询值。
4. 执行类型化 `init(false)`；必要参数不足则保留已有参数并进入 `NOT_READY`。
5. READY 时使用到达 trigger 的稳定 identity 及其合格冻结 anchor 求值；没有合格 anchor 的
   Duration/Debounce 保持 `NOT_READY`，不补发 bootstrap 之前的历史 edge/action。
6. 按动作接受边界发布内存 state/Timer，并异步写完整 `scene_state`。

类型化行为如下：

| 状态类型 | 缺 state 时的行为 |
| --- | --- |
| latest | 从 Current Fact 读取当前值，再用 `compareLatest` 合并当前 bundle |
| rolling / Script | 只读取业务存储能证明 coverage 的受限窗口；不回放缺失历史；无证明时按策略 `NOT_READY`/partial warming |
| Edge/Change | 当前 READY 值只建立 baseline，首轮不触发 |
| Hysteresis | 当前 READY 值确定 band/latch，首轮不触发 |
| Duration | predicate=true 且当前 trigger 有合格冻结 anchor 时才 arm：DATA 只取本轮取得 `triggerRight` 的 TRIGGER deltas，非数据 trigger 只取其 contract time；没有 anchor 即 `NOT_READY`。dueAt 可已过，但仍须回 lane 复核 |
| Debounce | 仅以当前 trigger 的同一合格 anchor 建候选稳定期；不得从任意 CONTEXT_ONLY/current-latest 回推。没有 anchor 即 `NOT_READY`，不 arm |
| Cooldown | 无法由输入恢复，重置为不在冷却期，接受极少量重复 |
| Alarm/FSM | active Alarm 可从 Alarm 业务库懒加载；duration 同上；缺失 repeating count 重置；不自动 clear |
| Reliable Delayed Action | 从 PG Action Outbox 恢复，不依赖 `scene_state` |

Debounce 的 committedValue 缺失时，不得把当前 candidate 直接当作已提交值；仍须等待稳定期到期并
回 lane 确认后才能 commit。没有后续合格 trigger 时，缺失或 `NOT_READY` state 可以长期不重建或
不继续推进，Runtime 不得为此虚构全量扫描或主动唤醒。

主规格另有 Geofence 当前坐标/围栏只建 baseline、历史 ENTER/LEAVE 不补的冷启动结论；Geofence
不在本规范本次能力分类内，其完整语义仍由主规格拥有，不得借本表推测新能力。

**control-only reset。** `scene_binding_lifecycle` 与显式 reinit 只能 close/reset 内存、发送
tombstone、取消已有 Timer slot/handle，并标记 next-live bootstrap；不得立即读取 Current Fact、
执行业务求值，或创建/arm/推进/fire Timer、Alarm、transition、Action Outbox。异步 tombstone 的
既有 best-effort 残余窗口仍按主规格处理，不能用 effectId 冒充 state reset authority。

**恢复。** 有效 state 必须恢复 arguments、rolling、五类算子、扩展与 Timer business state，并
绑定到 ProjectIndex 中 current enabled BindingCtx。schema/context/version 不可信时隔离该 key，
按缺失 state 等待冷启动；semanticHash 不兼容时 close+tombstone+next-live bootstrap。恢复依赖
membership 的 state/Timer 必须在首次合格 data trigger 或恢复 Timer fire 求值前，用 current
SubjectContext 懒 reconciliation；失配则 close/cancel，lookup 失败则 retry/fail closed。恢复线程
不得绕过 lane 与 effect gate 直接求值。

**fail closed。** 下列情况都不得进入业务 missing/false 分支：ProcessingContext/身份/来源不可信，
FactContract/type/order/identity conflict，读取 readiness/coverage 失败，state 超限，或 current
Binding/scope 无法确认。失败必须可观测并按所属协议 retry、quarantine 或完成批准的最终失败处置；
本轮不得产生业务副作用。

## 11. Scene 小状态与 Flink 大状态的边界

Scene Runtime 只保存 per-Binding、per-evaluation-subject 的小而有界状态：latest-value join、
单参数 rolling、五类 FSM、扩展状态和轻量 Timer。V1 硬上限为：

- 每个序列化 `SceneBindingState` 最大 32 KiB；
- 每个 rolling argument 最大 1000 个 active samples；
- 每 Binding 的 arguments、rolling arguments、operator/FSM、Timer slots 和有界 members 数量必须
  有发布期上限；
- 超限的 `(bindingId,evaluationSubjectKey)` 必须 fail closed，不产生动作，记录配额告警并要求
  缩小状态或迁移到 Flink；不得静默裁剪窗口内样本后继续求值。

以下能力必须进入共享 Computed Metric/Flink：跨设备/区域聚合、严格 event-time 对齐 JOIN、CEP、
session、watermark/allowed lateness、迟到修正/retraction、复杂窗口或超过 Scene 硬配额的大状态。
控制面以语义 fingerprint 相同的不可变 ComputationPlan 共享计算，不得把每条 Scene 变成独立
Flink Job。Flink 输出最终 `ComputedMetricUpdated`，再作为新的 LATEST_STATE Current Fact 和
Scene trigger 回到统一求值入口；Scene 不保存其窗口样本。

判断原则不是“是否用了 rolling”而是状态和时间语义：单主体、单参数、受限且不要求完整事件时间
终局的窗口可留在 Scene；跨主体、严格时间对齐、可修正或超限窗口必须放入 Flink。

## 12. 完整案例

案例规则：R1 区域的 `temp-01/02/03` 计算 5 分钟平均温度；`平均值超过 30℃ AND
door-01=CLOSED` 共同持续 2 分钟后，启动 `fan-01/02`。本节只展开有状态计算边界；完整上报、
Canonical、投影、动作投递与命令回复链路见
[《15 分钟读懂场景联动》§5](00-15分钟读懂场景联动.md#complete-case-sequence-diagram)和
[大字版完整端到端时序图](场景联动完整案例端到端时序图.html)。

1. 三个温度点的 5 分钟聚合是跨设备 time-window，由共享 Flink ComputationPlan 维护；
   `SceneBindingState` 不保存三个点的窗口样本。
2. Flink 的 FINAL `ComputedMetricUpdated` 投影为 R1 平均温度 Current Fact；平均温度与门状态都
   位于“共同持续 2 分钟”的 Duration predicate 内，因此二者都作为 `TRIGGER`。任一精确事实变化
   都可经 matching/fanout 要求同一 R1 Binding 求值，但同一完整 bundle 内仍只求值一次。
3. Runtime 先验证平均温度和门状态所需来源的 readiness/coverage，再检查 freshness；任何读取
   失败都 fail closed，不以旧门状态继续。
4. 本轮至少一个参数取得 `triggerRight` 后，tentative state overlay 当前平均温度和门状态。任一参数
   不可用或 stale 时为 `NOT_READY`；否则计算 `avg>30 && door=CLOSED`。
5. predicate 首次为 true 时，Duration 以默认 OBSERVED_AT 策略取本轮取得 `triggerRight` 的
   TRIGGER deltas 的稳定 anchor，保存 ARMED、dueAt 与 Timer identity；重复 true 不重置两分钟。
6. 平均温度或门状态的后续合格 trigger 只要看到 predicate=false，就立即取消当前区间；两分钟到期
   时 callback 回同一 lane，重新读取二者并再次执行 readiness、freshness、predicate 与 current-slot
   检查。
7. 复核仍为 true 才形成 duration-complete transition candidate。启动两台风机是两个独立 action
   effects，必须在同一动作接受事务中按稳定 effect identity 写入 Outbox；commit 前不得发布
   FIRED/Timer next state，commit 后即不因 scope exit 自动撤销。

因此本例的 Scene 小状态只有平均温度/门状态 latest 视图、Duration FSM 和普通 Timer slot；Flink
拥有温度窗口，Current Fact 拥有受信当前值，Action Outbox 拥有已接受的两台风机效果。

- [ ] 有状态算子目录恰好包含 Edge/Change、Duration、Debounce、Cooldown、Hysteresis 五类。
- [ ] Script 与 Alarm/FSM 保持扩展边界，不推测未冻结 ABI、配置或迁移协议。
- [ ] 所有 state、Timer、transition 与 Outbox 路径先验证完整 ProcessingContext 和
  `SCENE_ID_V2`；非法输入 fail closed，绝不默认 `LIVE`。
- [ ] latest 全链路使用 §5.1 `compareLatest`；duplicate 不修改 value 或刷新 freshness；
  `triggerRight` 由 BindingState receipt 与 projector race 单独裁决，最多授予一次。
- [ ] rolling 以稳定 sample/occurrence identity 去重；distinct same-timestamp occurrences 可并存，
  identity drift 在 grant 前 fail closed，receipt/`runtimeTriggerObserved` 只允许首次成功求值。
- [ ] 发布编译器计算有状态算子依赖闭包：rolling、Edge/Change、Duration、Debounce、Hysteresis 的状态
  输入全部强制 `TRIGGER`，Cooldown 不新增数据 trigger；冲突的 `CONTEXT_ONLY` 配置发布期拒绝。
- [ ] 普通完整条件谓词引用的动态参数全部为 `TRIGGER`；各 Trigger 可独立求值，但共享完整谓词
  `Edge(RISING)`，同一 active owner/lane 内连续 true 区间只创建一次 action set。
- [ ] rolling coverage 未满足时 zero-effect；硬配额超限不静默裁剪。
- [ ] Duration/Debounce 默认使用 OBSERVED_AT；EVENT_TS 只有在 deadline policy 可确定性映射时允许。
- [ ] Timer anchor/policy/operator generation/semanticHash 进入 state 与 fire identity；retry、restore
  不移动 dueAt/timerFireId。
- [ ] `NOT_READY`、投影失败和 predicate=false 三者分别处理；readiness/coverage 先于 freshness。
- [ ] Timer 只作为可恢复运行机制；Reliable Delayed Action 只由 durable Action Outbox 承担。
- [ ] action candidate 只有在 PostgreSQL Outbox commit 成功后才接受并发布关联 FSM/Timer/Cooldown
  状态。
- [ ] tentative state 只表达提交隔离，不要求完整深拷贝；共享 map/slice/index 不得让失败 mutation
  污染 accepted state，rollback 后 state/receipt/Timer handle 必须保持原样。
- [ ] `scene_state` 只在成功接受且 state 实际变化后异步发送完整 image；duplicate/stale 无变化不写，
  Compaction 不得被当作实时写入、复制和 Cleaner 容量的替代品。
- [ ] Scene 状态满足 32 KiB/1000 samples 等硬上限；跨主体、严格事件时间或大状态迁移到 Flink。
- [ ] POC 同时测量 accepted state 常驻内存、tentative allocation bytes/eval、Producer in-flight bytes、
  GC pause 与 heap headroom；32 KiB 不能当作平均内存预算。
- [ ] 第 14 章只保留一组生成 marker，目录中的版本、hash、能力集合与 `things` 生成物一致。
- [ ] 当前没有 `IMPLEMENTED` 能力；生成类型与注册项不得被表述为 Runtime/FSM 已实现。

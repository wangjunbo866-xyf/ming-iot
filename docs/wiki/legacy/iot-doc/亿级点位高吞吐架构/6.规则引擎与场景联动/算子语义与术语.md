## 2. 共享术语

**ProcessingContext。** ProcessingContext（处理上下文）是 `SceneEvent` 公共
envelope 中的必填受信字段，包含 `processingNamespace` 与
`processingMode=LIVE|BACKFILL|REPLAY`。生产 Scene 数据面只接受
`processingNamespace=production && processingMode=LIVE`；`production + BACKFILL`
与 `backfill/<jobId> + BACKFILL` 都在候选匹配前正常 bypass，`REPLAY` 与 shadow
namespace 均不进入 Scene V1 生产求值。缺失、
未知、表外 namespace/mode 组合或来源不可信时 fail closed/quarantine，
禁止默认为 `LIVE`。普通 redelivery、same-subject complete bundle、
cross-subject target-keyed `LINKED_DELTA` bundle 与 timer fire 必须
原样保留 context；已经进入 Scene 数据面的记录/回调还必须原样保留下述身份版本。

**Scene identity version。** `identityAlgorithmVersion` 是 `SceneEvent`、完整 state、
timer slot 和 Action Outbox 的必填身份编码版本。切换后的新数据只能使用
`SCENE_ID_V2`，所有 Scene 派生 hash 都以该 tag 为首项；
`LEGACY_NO_NAMESPACE_V1` 只允许标记 cutover 前已接受且保留原 `effectId` 的 pending
Outbox，由 dispatcher 只投递、不重算，Runtime 不得用它创建新 state/timer/effect。

`processingMode` 回答“这条输入为何被处理、拥有什么副作用权限”；
processing time 是 Runtime 观察、串行处理或执行 callback 的时间；
event time 是业务事实的 `eventTs`；device time 是设备生成/上报的时间
（如存在）。四者不得互相推导；迟到、重试或回调时刻不能把
`BACKFILL`/`REPLAY` 重分类为 `LIVE`。

该 Processing Mode 是平台 Raw/Canonical provenance 与生产副作用隔离契约。
ThingsBoard Queue 的 `ProcessingStrategy` 解决失败消息重试/跳过，CF reprocessing 是
独立历史任务能力；现有 TB 研究没有证明其公共消息 envelope 存在等价的
`LIVE/BACKFILL/REPLAY` 权限字段，不能把两者当成同一设计。

**Reducer（状态收敛器）。** Reducer 不是“收到消息就调用一次业务 handler”，也不是 Kafka
Streams 某个具体 `reduce()` API。它是领域状态的唯一裁决者：把可能重复、迟到、乱序或互相
冲突的 observation，与已经提交的当前状态按确定性规则收敛，产生新状态或明确的 no-op/conflict
outcome；只有被接受的领域变化才发布 `AcceptedStateTransition`：

```text
Reduce(currentDomainState, observation)
  -> nextDomainState | unchanged
  + accepted | duplicate | stale | conflict | unmatched outcome
  + optional AcceptedStateTransition
```

observation 只表示“上游观察到了什么”，不自动等于平台已经接受的领域事实。两个正式 reducer
的目标边界如下；输入 Topic 是已给出的逻辑基线，输出 Topic、consumer-group 名及完整 outcome
枚举仍须由后续 ADR 冻结：

| reducer | Canonical observation 输入 | 权威状态与裁决规则 | 被接受时的输出 |
| --- | --- | --- | --- |
| Presence reducer | `iot.data.canonical.lifecycle-observation.v1` | `sessionGeneration + lifecycleSequence + current presence`；有可信序列时 CAS，无可比序列时由 EMQX snapshot reconciliation 裁决 | 表示 `ONLINE → OFFLINE` 等已接受变化的 `AcceptedStateTransition`；具体 transitionType 待冻结 |
| Command reducer | `iot.data.canonical.command-reply-observation.v1` | `CommandExecution/CommandAttempt/Outbox + reducer outcome`；按 `commandId + attemptNo` 幂等执行单调状态迁移，无法关联的回复进入诊断流 | 表示命令状态推进到 `RESULT_SUCCEEDED` 等已接受变化的 `AcceptedStateTransition`；具体 transitionType 待冻结 |

例如设备当前为 `ONLINE(sessionGeneration=10,lifecycleSequence=8)`：再次收到同一
`CONNECT(10,8)` 是 duplicate；迟到的 `DISCONNECT(9,99)` 属于旧 session，是 stale；只有
`DISCONNECT(10,9)` 才把状态推进为 `OFFLINE` 并发布一次 accepted transition。类似地，命令
已由 `attemptNo=2` 的成功回复推进到 `RESULT_SUCCEEDED` 后，相同回复重投是 duplicate，旧
`attemptNo=1` 的失败回复不能把终态倒退。

职责必须分开：ProtocolApplication 负责把厂家 payload 解码为标准 observation；Reducer 决定
该 observation 是否改变领域事实，并在状态/outcome 的本地事务中登记 accepted transition
Outbox；Projector 把已经接受的事实写成查询投影；Scene 只消费 accepted transition，不重新
裁决原始 Lifecycle/CommandReply。目标代码边界是 `things/runtime/presence` 与
`things/runtime/command`，`things/service/dmsvr` 只作为 facade。本文修订时当前 `things`
仓库尚无这两个 runtime package，也无完整 `AcceptedStateTransition` contract，因此该名称
表示目标架构 role，不能用现有直接更新 `is_online` 或直接处理 reply 的旧逻辑冒充实现。

**ComputationPlan（共享计算计划）。** ComputationPlan 是控制面把窗口、聚合等表达式规范化后
发布的不可变计算计划，不是一条 Scene Binding、一个 Go Scene 算子实例，也不是“每条规则一个
Flink Job”。它把可共享的计算语义与各 Scene 自己的阈值、动作分开：

```text
Scene 窗口/聚合表达式
  -> 控制面规范化并计算 fingerprint
  -> immutable planId + planReleaseId + outputs[]
  -> 共享 Flink Computed Metric Runtime
  -> ComputedMetricUpdated
       |- ComputedMetricCurrentFactProjector -> Scene Current Fact
       `- Scene Admission                    -> scene_event -> Scene Runtime
```

fingerprint 必须覆盖所有会改变计算结果的语义：source selector/filter、schema/model release、
field 与单位归一化、keyBy、函数及参数、窗口类型/大小/滑动/对齐/时区、timestamp/time
semantics/allowed lateness、NULL/INVALID/quality、去重/retraction 与 emission/finality。
阈值、告警或命令动作，以及“哪个 Scene 使用该指标”不进入 fingerprint。只有 fingerprint
完全相同的 Binding 才能共享一份 plan 和 keyed window state；控制面负责引用计数、版本
barrier 与安全 GC，Flink 不会自动识别并合并两条看起来相似的业务规则。

例如 Scene A 使用“R1 区域全部温度点的 5 分钟 TUMBLE AVG > 30℃”触发告警，Scene B 对同一
平均值使用 `> 35℃` 下发命令：两者 selector、field/unit、keyBy、AVG、窗口、时间及质量语义
完全相同时共享一个 ComputationPlan；`30/35` 阈值与各自动作留在 Binding 中。Flink 每个窗口
只计算一次并发布一个版本化 `ComputedMetricUpdated`，两个 Binding 在 Scene 侧分别判断阈值。
若任一 Scene 改成 1 分钟滑窗、不同 area selector 或不同迟到/质量策略，就必须得到不同 plan。

以属性窗口为例，Flink 的已知上游基线是 `iot.data.canonical.telemetry.v1`；生产 Job 只消费
`LIVE` 并输出 `LIVE`。`ComputedMetricUpdated` 通过 `planReleaseId + outputOrdinal` 解析
`metricOutputSemanticId/FactContract`，Scene V1 只接纳 `finality=FINAL + production+LIVE`。
Current Fact projector 与 Scene Admission 是同一计算结果流的不同逻辑 consumer group：前者是
COMPUTED_METRIC 当前值的唯一 writer，后者负责规范化触发输入，二者不能互相代替。

ComputationPlan 的业务配置在目标架构中逻辑归属 things IoT 控制面，实际窗口状态和聚合执行归
未来共享 Flink runtime；Scene Runtime 不保存这些窗口样本。本文修订时当前 `things` 仓库没有
ComputationPlan 的 Go/Proto/DDL、plan manager 或 `ComputedMetricUpdated` producer，Flink
Job 的代码位置、计算结果物理 Topic 及相关 consumer-group 名也尚未冻结。因此它是已经确定边界
的目标能力，而不是当前 `things` 已经实现的共享计算层。

**Scope selector。** Scope selector（作用范围选择器）回答“这个 Binding 当前适用于
哪些设备”。它基于 project、area、product、fixed device 等当前组织关系做匹配，
不决定状态 key 或动作归属；同一宽 scope 可以有多个 evaluation subject。scope
不再适用时 state 可以 close，但已接受输出不回滚。

**Source subject。** Source subject（来源主体）是本次事实来自谁，由 sourceSubjectKey 标识。
例如 device:A.temperature 的 source subject 是 device:A。
source subject 决定 SOURCE 输入所在的 source lane，但不必等于状态归属主体。

**Evaluation subject。** Evaluation subject（计算主体）是参数状态、FSM 和动作归属的主体，由
evaluationSubjectKey 标识。
例如 device:A 和 device:B 的房间参数可以共同求值到 area:R1；
此时两个设备分别是 source subject，area:R1 是 evaluation subject。

**Actor lane。** Actor lane 是借用 Actor 思想、以
`(tenantCode, evaluationSubjectKey)` 为键的 subject-keyed 串行执行通道；同一计算主体的求值任务
串行进入统一入口。它不是 Kafka partition，也不承诺一 Actor 一 goroutine 或采用现成 Actor 框架；
状态层级与执行边界见
[Runtime 调度分章 §§2～3](Scene%20Runtime%20调度、分片与故障转移.md#runtime-model)。

**Argument source。** Argument source（参数来源）说明每个参数从哪个 subject 的哪个 fact 取得。
SELF 从触发来源自身读取，EVALUATION_SUBJECT 从计算主体读取，FIXED_SUBJECT 从固定
主体读取。Argument source 是参数映射，不是 Scope selector、参数触发模式或状态 key。

**Argument mode / trigger dependency closure。** `TRIGGER` 参数变化可以发起求值，
`CONTEXT_ONLY` 只在其他合法 trigger 已经要求求值时提供当前上下文。普通“完整条件成立时执行
动作”的规则，其谓词引用的全部动态 argument 都必须是 `TRIGGER`；不能按第一个条件或字段顺序
选择一个主触发参数。只有显式 `WHEN ... IF ...` 中的 IF 附加门禁才可为 `CONTEXT_ONLY`，且其
变化有意不主动求值。保存后的 Binding 必须逐参数显式记录模式。rolling 样本依赖，以及
Edge/Change 被观察表达式、Duration 持续 predicate、Debounce candidate 和 Hysteresis value 表达式
中的全部动态依赖也必须是 `TRIGGER`；Cooldown 不新增数据 trigger。同一参数同时命中普通门禁和
有状态依赖时 `TRIGGER` 优先。`AND`/`OR` 本身不能推导显式上下文，必须按规范化 AST、触发表达式
和算子状态作用域计算依赖闭包。完整发布规则见
[控制面与匹配契约 §4.2](控制面与匹配契约.md#42-trigger-与-context_only)，完整算子矩阵见
[场景有状态计算规范 §4.1.1](场景有状态计算规范.md#stateful-trigger-dependency-closure)。

按 matching 契约，SOURCE/LINKED reverse path 不为纯 CONTEXT_ONLY 依赖建立 posting；
纯 CONTEXT_ONLY refresh 只能更新当前参数，不能单独成为数据触发。

**Aggregate predicate rising gate（完整谓词上升沿动作门）。** 多个 `TRIGGER` 各自到达都会发起
求值，但 V1 普通条件动作共享完整布尔谓词的 `Edge(RISING)` 状态：`false -> true` 产生一次完整
action set，`true -> true` 只求值而不重复创建 Outbox，`true -> false` 更新 baseline。它发生在
effect 创建之前，不能用 `effectId` 合并不同 Trigger 代替。该门复用现有 `SceneBindingState` 与
异步 best-effort `scene_state`，只保证 active owner/lane 正常持有 accepted state 期间的单次上升
沿；不新增 durable gate，也不承诺跨 crash/rebalance 严格一次。完整定义见
[场景有状态计算规范 §4.1.2](场景有状态计算规范.md#aggregate-predicate-rising-gate)。

**Latest-value join。** Latest-value join 是“一个 TRIGGER 参数取得本轮 `triggerRight`，加上 state 中其他参数的
最新值，
立即求值”的语义。
它不要求来自不同设备的参数具有相同 event timestamp。
需要同一 event-time 切面、严格跨设备 JOIN、session、CEP 或超大窗口时，交给 Flink。

**Semantic trigger time。** Semantic trigger time（语义触发时间）是本轮业务状态变化使用的稳定时间，不是回调
实际运行时临时读取的 wall-clock，也不是 `processingMode`。

- DATA bundle 默认采用 `OBSERVED_AT`：只取本轮取得 `triggerRight` 的 TRIGGER deltas 的
  `max(observedAt)`；选择 `EVENT_TS` 时也只取这些 deltas，并且必须有可解析的
  `schedulerDeadlinePolicyRef` 把可比时间域确定性映射到可信平台 epoch deadline；
- 同一 bundle 没有取得 `triggerRight` 的 TRIGGER delta 时，不伪造数据时间，
  Duration/Debounce 保持 `NOT_READY`、不得 arm；
- 合法非数据 trigger 只使用其契约显式冻结的稳定时间；Schedule 使用 scheduleEvaluationId 与
  `plannedFireTs`。数据面 `SubjectLifecycle` 使用 lifecycleEvaluationId，但只有其 trigger contract
  明确冻结 anchor 时才可 arm，不得从任意 CONTEXT_ONLY/current-latest 值回推；
- control-only 的 `scene_binding_lifecycle` 与显式 reinit 不是语义求值触发器；
- timer fire 使用 timerFireId，并延续 arm 时保存的 armedAt、dueAt；
- cooldown 单独以动作首次被事务性接受的时刻作为开始点。

同一 logical trigger 的 retry、rebalance 与 restore 必须复用冻结的语义时间，不能向后漂移。

**NOT_READY。** NOT_READY 表示当前不足以作出业务判断。
常见原因包括必要参数缺失、tombstone、类型不合法，或按显式 freshness 策略已经 stale。
NOT_READY 不是 false，也不是一次 edge/change。
它不产生 transition 或动作，但已通过版本门控的参数更新仍可保存在 state 中。

**Transition。** Transition 是算子输出的、可映射为动作或告警的语义 pulse/状态迁移，
由 trigger identity、operatorId 和 transition kind 稳定识别，才生成 transitionId；映射为动作或告警时才进一步生成 effectId。
IDLE→ARMED、cancel、candidate 替换、latest 更新和 gate 清除只是 internal FSM update；
重复 logical trigger 不得用进程内序号创造新 transition。

**Action acceptance。** Action acceptance（动作接受）发生在本轮全部目标 Action Outbox 写入成功并且 PG
事务 commit 之后。
commit 前只是 tentative transition；commit 失败不推进 FSM、注册 timer 或开始
cooldown。同一 effect 的幂等重试不得重定义更晚的开始点，commit 后由 Outbox 可靠投递。

**Cold bootstrap。** Cold bootstrap（冷启动）是 SceneBindingState 缺失、损坏或不可用时，
从 current BindingCtx 与业务 current latest store 懒建当前状态。
它只能在已通过门禁的 `production + LIVE` `SceneEvent` handler 中，
由首个数据输入、Schedule 或 SubjectLifecycle evaluation trigger 惰性触发。
`scene_binding_lifecycle` 与显式 reinit 只能 close/reset、发 tombstone 和标记
next-live bootstrap；close/reset 必须取消已有 timer slot/handle，但它们不立即读
current facts、不执行业务求值，也不创建、arm、推进或 fire timer。
它不扫描全量实体，也不补演历史 transition。

## 3. 四类上下文不得混用

| 名称 | 回答的问题 | 典型内容 | 明确不包含 |
| --- | --- | --- | --- |
| ProcessingContext | 输入属于哪个处理 namespace/mode，是否允许生产副作用 | `processingNamespace`、`processingMode` | current 组织归属、业务时间、算子 state |
| SubjectContext | subject 当前属于哪个 tenant/project/area/product，scope 现在是否适用 | typed subject identity、projectId、area path、productId、aggregateVersion | 参数 latest、rolling、FSM、timer handle |
| SceneBindingState | 某 Binding 在某 evaluation subject 上当前算到哪里 | arguments、bounded rolling、script/Alarm/FSM、timer business state | 全量设备关系、Go Actor、锁、编译对象 |
| current latest store | 冷启动和复核时当前能读到哪些业务事实 | latest/attribute、timestamp、optional version、freshness metadata、受限 rolling | Scene 的 edge baseline、duration arm、debounce candidate、cooldown gate |

SceneBindingState 的稳定身份是：

    (tenantCode, bindingId, evaluationSubjectKey)

ProcessingContext 决定处理隔离和副作用权限；SubjectContext 只用于
current applicability guard，不得把非 `LIVE` 输入升级为 `LIVE`。生产
SceneBindingState 及其 timer slot metadata 必须保存原始
`processingNamespace/processingMode` 与 `identityAlgorithmVersion`，且非 tombstone
state 只能是受信的 `production + LIVE + SCENE_ID_V2`。
current latest store 是业务当前值投影，可能落后于正在处理的 Kafka Delta；
因此冷启动必须先读取 store，再按统一更新规则合并当前 Delta。

## 15. Canonical→Scene Fact 投影契约术语

> 本节术语来自《Canonical → Scene Fact 投影契约补充修订设计》（2026-08-04，
> `docs/superpowers/specs/2026-08-04-scene-canonical-fact-projection-contract-reconciliation-design.md`）。
> 该设计方向已确认、书面规格待联合修订；转正前本节为预备术语，与任一架构源冲突时必须联合修订，
> 未收敛前不得据此覆盖架构决策；
> §2 中两字段 ProcessingContext 等既有定义随联合修订升级。

### 15.1 事实身份与来源

**factType / factKey。** Scene 正式参数引用的二元组。factType 取
`PROPERTY | DEVICE_EVENT | COMPUTED_METRIC | STATE_TRANSITION`；factKey 是来源域
生成的稳定语义 ID：平台生成、普通用户不可编辑、全生命周期永不复用，正常编辑或发布下一
版本自动继承，新建/复制/确认语义变化自动生成新 ID。display name、Identifier、Modbus
地址、TDengine 列名、数据库行 ID、pointOrdinal 均不得充当 factKey。

**稳定语义 ID。** 按来源类型分别为 `propertySemanticId`（属性）、`eventSemanticId`
（事件类型）、`metricOutputSemanticId`（计算指标输出）、`transitionSemanticId`
（accepted transition）；事件参数另有 `eventParamSemanticId`（Binding 以
fieldSemanticId 引用）。同一 ID 的 canonical contract 不得发生不兼容改变，且必须进入
不可变发布物及其 hash，不能只留在 current 数据库行中。

**temporalKind。** “事实如何随时间演进”的来源契约，不是时间戳字段，也不是 Scene timer
使用哪种时钟。平台按来源类型自动推导并在发布快照中显式固化，普通物模型/Scene 配置人员
不直接编辑。`LATEST_STATE`：同一 subject、同一 fact identity 的更新竞争一个当前槽位，
有 Current Fact，可用于冷启动与 latest-value join；`OCCURRENCE`：每次发生都是独立事实，
以 occurrenceId 去重，不覆盖前一事件，不写 Current Fact。已发布 ID 不允许原地切换。

**FactContract。** 从来源发布物编译出的运行时契约（factType/factKey、temporalKind、
subjectType、canonicalValueType、payloadSchemaRef、quantityKind/canonicalUnit、
availability/timestamp/scheduler-deadline/fact-version/occurrence-order 等策略 ref、
time domain 与 encoding、semanticContractVersion），是编译产物而非独立人工维护的
Registry。`semanticContractHash` 覆盖其全部语义字段；同一 `(factType,factKey)` 跨
active release 必须得到完全相同的 semanticContractHash，否则必须新建稳定语义 ID。
原始映射、raw type、单位换算函数与 ordinal dictionary 另形成随快照冻结的
`snapshotProjectionHash`，允许跨快照不同。所有 `*PolicyRef/*SchemaRef` 都是可按内容
hash 校验的 immutable semantic reference。

**四类受信来源。** `PropertyReport`（由快照 pointOrdinal 解释的类型化点位报告）、
append-only `DeviceEvent`、共享计算层 `ComputedMetricUpdated`（Scene V1 只接纳
`finality=FINAL + production+LIVE`）、reducer 已提交的 `AcceptedStateTransition`。
诊断类 `ProtocolError/UnknownPoint` 不进入业务 Scene Fact；原始 Lifecycle/CommandReply
不得绕过 reducer 冒充 accepted transition。

**DmModuleSchemaSnapshot V3 / DmProductRelease。** 物模型来源发布物，即设计中的逻辑
术语 ModelRelease。V3 快照在 V2 全部字段上新增运行时字典：`itemOrdinal`（快照内冻结，
PROPERTY wire 中即 pointOrdinal）、itemKind、identifier、稳定语义 ID、
factContractRef/semanticContractHash、sourceProjectionRef、eventParams[]（paramOrdinal、
eventParamSemanticId、canonicalFieldOrdinal 等）、snapshotProjectionHash、
automationEligibleBitmap、factOwnerKeyPolicyRef/Hash。V2 快照不具备这些身份字段，
只能经受审计 lineage migration 升级后进入新 Admission，运行时不得按 Identifier 猜 ID。

**ComputationPlan.outputs / AcceptedTransitionDictionary。** §2 已定义 ComputationPlan 与
Reducer 的业务职责；本条只约束它们供 Scene 解释输出所需的不可变发布物字典。两类字典分别按
`outputOrdinal`（planRelease-local，发布后冻结）与
`transitionType` 冻结稳定语义 ID、factContractRef/semanticContractHash、owner-key
policy ref/hash、automationEligible 及其 policy ref（transition 另有
allowedCauseKinds/allowedCauseContractHashes）。解释版本分别由现有 `planReleaseId` 与
`reducerVersion` 标识，不另造 PlanRelease/ReducerRelease 实体。

**FactSelector。** Scene Binding 的正式参数引用：
`(factType, factKey, optional fieldSemanticId)`。scalar 事实不得带 field；结构化
DEVICE_EVENT/transition 参数必须保存稳定 fieldSemanticId，不得保存展示名、数组下标或
临时 ParamKind。TriggerPosting 只按 root `(factType,factKey)` 建索引。

**factOwnerKey。** 来源冻结并在 SourceDelta/LinkedDelta 中传播的通用 subject
incarnation，wire 为 FACT_OWNER_KEY_V1 typed canonical bytes，非冒号拼接字符串：
oneof `deviceTenure(canonicalDeviceId, ownershipBindingId)` 与
`entityIncarnation(subjectType, canonicalSubjectId, subjectIncarnationId)`；其
policy ref/hash 纳入 sourceSemanticSetHash。ownershipBindingId/subjectIncarnationId
防止 owner tenure/实体重建后旧事实与新槽位碰撞；来源域证明 typed subject ID 永不复用时，
incarnation 由 `H(PERMANENT_SUBJECT_INCARNATION_V1, ...)` 确定性生成并冻结。
planReleaseId、routing provenance、current affiliation 不得充当 owner/incarnation；
OCCURRENCE 虽不写 Current Fact 也必须携带 factOwnerKey。

**不可变发布物 / artifact retention。** 来源发布物（快照、ComputationPlan、
AcceptedTransitionDictionary、ProcessingContextContract、owner-key policy 等）按内容
hash 寻址、发布后不可变。只要 Raw/replay archive、Current Fact、Scene state/timer、
Action Outbox、quarantine 或 cutover manifest 仍有一个引用，就必须保留可解析内容；
最后一个 dependent reference 清除且审计保留期结束后才可 GC。

### 15.2 wire 与身份 hash

**SceneEvent / SourceDelta / FactDelta。** Scene 数据面 wire。SceneEvent 是公共
envelope：eventId + 必填 ProcessingContext + `identityAlgorithmVersion=SCENE_ID_V2` +
oneof payload（SourceDelta/LinkedDelta/ScheduleEvaluate/SubjectLifecycle/
LifecycleTargetDelta）。SourceDelta 是一条来源输入至多一条的批量 Delta：tenantCode、
sourceKind、sourceSubjectKey、factOwnerKey 及 policy ref/hash、sourceOutputId、
sourceSemanticSetHash、sourceEventId、sourcePosition、sourceContractRefs[]、
factDeltas[]。FactDelta 是单个事实的 Delta：factType/factKey/temporalKind、
availability、payload（IDL oneof：scalarValue | structuredValue，不得压成不可校验的
`map<string,any>`）、eventTs 及时间域字段、observedAt、可选 factVersion、OCCURRENCE
必填的 occurrenceId/可选 occurrenceOrder、sourceContractRefIndex 与 sourceLocation。

**ProcessingContext 扩展字段。** 在 §2 两字段基础上，data-origin wire 还必须携带
`processingContextContractRef`（platformProcessingContextArtifactId +
platformArtifactContentHash）、`processingModePolicyReleaseId` +
processingModePolicyArtifactHash、
`processingContextContractVersion=PROCESSING_CONTEXT_CONTRACT_V1`、
`processingContextContractHash` 与 `processingProvenanceRef`。Linked/timer fire 等派生
路径逐字段继承，不得分配新 policy release。ref/hash 缺失、未知、过 retention、内容不符
或 producer 计算不一致均 fail closed；同一 direct trigger 的 retry 必须重建相同完整
context，任一漂移为 `DIRECT_TRIGGER_CONTEXT_CONFLICT`。

**sourceEventId / factDeltaId / occurrenceId。** 稳定身份公式：
`sourceEventId = H(SCENE_ID_V2, SCENE_SOURCE_ID_V1, processingNamespace, tenantCode,
sourceKind, factOwnerKey, sourceOutputId, sourceSemanticSetHash)`；
`factDeltaId = H(SCENE_FACT_ID_V1, sourceEventId, factType, factKey)`；
OCCURRENCE 的 occurrenceId 等于 factDeltaId。同一 redelivery、Admission retry、
rebalance、interest generation 变化或语义不变的镜像滚动均不得改变这些 ID；不得使用
进程序号、新 UUID 或裸 outputId。

**sourceSemanticSetHash。** 一条来源输出的 Scene 解释集合 hash，按 source kind 确定性
构造（Canonical 覆盖既有 semanticReleaseSetHash、projection/semantic contract entries；
metric 覆盖 planId/planReleaseId/computationPlanContractHash；transition 覆盖
causationSemanticSetHash 与 acceptedTransitionDictionaryHash；三者均含
factOwnerKeyPolicyHash 与 processingContextContractHash）。多 artifact entry 按
`(artifactKind,artifactId,factType,factKey,contentHash)` 排序后长度前缀编码；集合取完整
source output 引用的 artifact contracts，不取动态 interest 过滤后的子集。

**envelope/payload hash。** `semanticPayloadHash` 覆盖 availability、unavailable
reason、canonical type 与规范化值（structured 还含 schema ref 及按
`(canonicalFieldOrdinal,fieldSemanticId)` 排序的字段状态/值），使用版本化 deterministic
typed encoding。`factExecutionEnvelopeHash` 再覆盖 factDeltaId、temporalKind、
semanticContractHash、eventTs 及时间域、timestampSource/PolicyRef、observedAt、
factVersion 域与 processingContextCanonicalHash；`occurrenceEnvelopeHash` 再加
occurrenceId 与 occurrenceOrder 域。同一 occurrenceId/factDeltaId 只有 envelope hash
也相同才是 duplicate，任一字段漂移即 identity conflict。

**RetainedFactProvenance / SceneSourceLineage。** 每个进入 Current Fact、SingleValue
或 rolling 的值/样本必须保存的完整来源证据：lineage（identity/source/fact 三个版本、
factOwnerKey 及 policy、sourceEventId、sourceSemanticSetHash）、factDeltaId、各
envelope/payload hash、temporalKind、时间与版本域、occurrence 字段、sourcePosition、
sourceContractRef、semanticContractHash 与完整 processingContext。LinkedDelta、timer
slot/fire、transition 与 Action Outbox provenance 复制同一 lineage，不得只留外层
SCENE_ID_V2。

**sourcePosition / sourceStreamId。** 固定为 `(sourceStreamId, partition,
recordOffset)`，不得以“或等价位置”留给实现解释。sourceStreamId 含 logicalKind、
kafkaClusterId、broker immutable topic UUID 与 topicGeneration（delete/recreate 或受控
迁移时递增；跨 generation 的 offset 绝不可比较）。logicalKind 四类：
`CANONICAL_TELEMETRY_V1`、`CANONICAL_DEVICE_EVENT_V1`、`COMPUTED_METRIC_V1`、
`ACCEPTED_TRANSITION_V1`；前两者对应现有 `iot.data.canonical.telemetry.v1` 与
`iot.data.canonical.device-event.v1` 两个独立 offset 域，不得合并。

**eventTs / observedAt。** eventTs 是业务时间，由受信 producer 按版本化
`timestampPolicyRef` 产生，同时携带 `timestampSource` 与
`timeDomainId/eventTsEncoding/eventTsPrecision`；Admission 只验证复制，不按到达延迟
猜测、不在缺失时取当前 wall clock。observedAt 是平台稳定观测时间（来自 Canonical
receivedAt），redelivery 保持不变；用于 freshness 与默认 timer anchor，不参与 LATEST
主排序。

**factVersion / occurrenceOrder。** factVersion 是同一 subject/fact 的来源业务修订或
可信顺序，只在来源 contract 明确定义时存在；wire 值须符合 `factVersionEncoding`，比较
只能调用 `factVersionPolicyRef` 的 canonical comparator。modelReleaseId、
moduleSchemaSnapshotId、schemaHash、Kafka partition/offset、Admission 处理次数、Scene
Binding config revision 均不得冒充 fact version。occurrenceOrder 同理只按来源 contract
冻结的 domain/encoding/wrap policy 与 comparator 比较，Kafka offset 不得充当替代品；
V1 仅用于证据/冲突校验，不构成 ordered-prefix finality。

**scene_event / scene_state。** Scene 数据面两个 Topic：scene_event 承载 SceneEvent
wire，由 Admission 发布、Runtime 消费；scene_state 是 Runtime 内存热状态的异步
best-effort 持久化，不是 durable 真源，落后或丢失后允许按 §11 收敛重算。

### 15.3 Current Fact 投影

> 实现规格（投影、水线、读取 API、双档部署、存储选型）以[《Scene Current Fact 设计》](Scene%20current%20fact设计.md)为准；本节只保留术语定义。

**Scene Current Fact / SceneCurrentFactStore。** Scene 专用的 LATEST_STATE 当前值
投影，逻辑上独立于通用 latest（BACKFILL 可按冻结 CAS policy 改写通用 latest，但不得
创建、推进或删除本槽 value）；key 为
`(tenantCode, factOwnerKey, factType, factKey)`。物理上可复用通用 latest 的 backend，
但必须是独立 table/namespace/column family 和权限（即 Materializer 的 Scene-live 槽）；
它不是 scene_state，也不从 scene_event 反向构建；Scene 查询 API 只能读
`production + LIVE + LATEST_STATE` slot。

**writer owner（唯一写入者）。** 每种 LATEST_STATE 来源有且只有一个 Current Fact 写
入者：PROPERTY 是 Timeseries Materializer（物化器：消费完整 Canonical PropertyReport
并写 history/通用 latest 的既有服务）的 Scene-live 槽；COMPUTED_METRIC 是
`ComputedMetricCurrentFactProjector`（独立 group
`scene-current-fact-computed-metric-v1`）。Admission 与 Runtime 都不是写入者；即使
Admission 为静态 eligible 的 CONTEXT_ONLY 更新发布 SOURCE_DELTA，Runtime 也只能零
fanout，不能借机写 Current Fact。Materializer 沿用其现有唯一逻辑 consumer
group/checkpoint（不新增组）：history、通用 latest 与 Scene-live 槽全部 durable 后，
才推进连续 next-offset。

**completion frontier / readyThroughNextOffset。** 写入者对外发布的应用侧 partition 连续完成水线，
数值采用 next-offset 约定；它与 Kafka committed offset 是不同概念：前者证明投影连续完成，
后者记录 consumer 恢复进度，但两者都不得领先于连续完成事实。
底层 store 必须保证同一 partition 的 current rows 先
durable、frontier 后推进。BACKFILL 等 deterministic bypass 记录 terminal outcome 后
同样推进 frontier（value slot 不变）；暂时性 store/catalog 失败没有 terminal outcome，
必须 retry，frontier 不得越过。`projectionGeneration` 标识一次受控构建的 coverage
lineage，row/frontier/seed 同属一个 generation；读者不得拼接两个 generation。

**无值变更完成（no-value-mutation completion）。** writer 对某个 input 已完成适用性判断，且
所有其他启用目标已经 durable，但按全局静态 eligible、temporal contract 或既有旁路契约不需要
修改 Scene-live value slot。它是 input completion 的逻辑分支，不是新的 wire/lookup/Materializer
状态或逐输入持久化表；普通确定性 no-op 由连续 frontier 汇总证明。只有规范点名的 bypass、
conflict、quarantine、迟到旧 artifact 等分支，才必须先完成 reason-bearing terminal outcome。
尚未解决的 store/catalog/contract 失败不属于该终态，必须 retry，frontier 不得越过。

**availability / UNAVAILABLE。** Canonical state 的投影：ABSENT 不产生 Delta；VALUE 且
quality 被 contract 接受 → `AVAILABLE + typedValue`；NULL/RESET/INVALID/quality 被判
不可用 → `UNAVAILABLE(NULL_VALUE|RESET|INVALID_VALUE|BAD_QUALITY)`。UNAVAILABLE 是
正常 current value，按 comparator 排序后保存，不得用 Kafka/storage tombstone 表示；
tombstone 只用于 subject 删除、ownership tenure 结束或明确投影 GC，否则 compact 后会
丢失“明确不可用”与“从未见过/尚未投影”的区别。

**ProjectionCoverageToken / ProjectionCoverageSeed。** readiness 证据，取代含义不明的
watermark。Token 含 projectionContractVersion、sourceSetHash、readBarrierId 与逐
`(sourceStreamId, partition, projectionGeneration, coverageStartOffset,
readyThroughNextOffset)` entries；每个进入业务求值的 logical trigger 在本轮第一次读取
时，经 CurrentFactBarrierSnapshotProvider 捕获固定 source-end vector 形成
readBarrierId——provider 将并发请求 micro-batch，只有登记完成之后开始的 capture cycle
才能满足这些 trigger，retry 复用同一 barrier，不得逐次追逐新 end，也不得退回登记前的
旧缓存。Seed 是 `READY_NEVER_SEEN` 的 durable 覆盖证明（owner/model activation、metric
plan activation 或受控初始构建产生），并按 key 携带
`projectionObligationStartNextOffset`；已有事实后开 eligibility 时不得把 effective-from
前移，一条迟到的 LIVE row 不能证明压过未投影前缀。

**Current Fact 读取状态。** `READY_AVAILABLE`、`READY_UNAVAILABLE`、`READY_NEVER_SEEN`
（须 seed 背书）、`PROJECTION_CONFLICT`、`PROJECTION_NOT_READY/BEHIND`、
`LOOKUP_FAILED`。投影落后或 lookup 失败不是业务 missing，必须 retry/fail closed，不得
进入 Scene 的 NOT_READY/false 分支后继续产生动作。

**CurrentFactConflictFence。** comparator/identity conflict 时写入者对
SceneCurrentFactKey 写的 durable 封条（projection generation、conflict kind、双方
envelope hash/order-domain 与 source positions）；lookup 必须优先返回
PROJECTION_CONFLICT，不得再暴露旧 row。SAME_ORDER/AMBIGUOUS/VERSION_PRESENCE 类仅在
同一 order domain 出现严格高于整个 conflict order 的 accepted row 时，以“写新 row +
清 fence”一个 durable mutation 清除；FACT_IDENTITY_CONFLICT、ORDER_DOMAIN_CONFLICT 与
source-contract 类只能经受审计 repair/rebuild 产生新 projection generation 清除。晚到
且不再 applicable 的旧-release backlog 记 `SOURCE_ARTIFACT_NO_LONGER_APPLICABLE`
terminal no-write；non-final metric 记 `UNSUPPORTED_FINALITY_BYPASS` terminal
no-write。

### 15.4 排序与冲突裁判

**comparator（compareLatest）。** Current Fact、Scene SingleValue 参数、
bootstrap/evaluation-time overlay 合并共用的同一门控：旧值不存在 → `ACCEPT`；
factDeltaId 相同 → envelope 相同 `DUPLICATE_NOOP`、任一字段漂移
`FACT_IDENTITY_CONFLICT`；order domain/encoding 不兼容 → `ORDER_DOMAIN_CONFLICT`；
先比 eventTs（较新 `ACCEPT`、较旧 `STALE_NOOP`）；eventTs 相同再比 factVersion——仅
一侧存在 → `VERSION_PRESENCE_CONFLICT`，两侧都有则调 policy comparator（更高
`ACCEPT`、更低 `STALE_NOOP`、相等则同 payload `DUPLICATE_NOOP`、不同 payload
`SAME_ORDER_DIFFERENT_PAYLOAD_CONFLICT`），两侧都无则同 payload `DUPLICATE_NOOP`、
不同 payload `AMBIGUOUS_SAME_TIMESTAMP_CONFLICT`。value 与 UNAVAILABLE 使用完全相同
门控；同一 order 的冲突禁止按 Kafka offset 或到达先后“最后写赢”；duplicate 不刷新
freshness、也不产生 value mutation；comparator outcome 不裁决 triggerRight，后者必须按
§15.5 的 BindingState receipt/projector race 规则另算。更高 version 即使规范化值相同仍是被
接受的来源更新。

**OCCURRENCE 门控。** 新 occurrenceId 是独立发生；相同 occurrenceId + 相同
occurrenceEnvelopeHash 是 duplicate，任一 envelope 字段不同是
`OCCURRENCE_IDENTITY_CONFLICT`——只隔离冲突副本并告警，不回滚已接受 state/action。
eventTs 用于审计、semantic trigger time 与 bounded window，不把多个事件折叠为“最后一
个事件”；V1 对所有直接 OCCURRENCE 禁止 sequence/edge/change/依赖先后的 FSM，只允许
occurrence-local predicate/action 与 order-insensitive、occurrence-idempotent 的
bounded aggregation；Kafka 到达顺序只是执行顺序。

**fail closed / quarantine。** 拿不准即按错误处理：缺失/非法/不可信输入、
contract/type/identity/order conflict 一律不产生业务副作用。冲突不能无限毒死
partition：写入者把以 `(sourcePosition,factOwnerKey,factType,factKey)` 幂等的 bounded
conflict/quarantine outcome durable 后计为 terminal no-value-mutation 并推进 frontier；
Runtime 只隔离受影响 bundle，不声称跨 target 回滚。

### 15.5 Admission 与 interest

**Scene Admission。** Canonical→Scene 的规范化入口，固定流程：验证受信
ProcessingContext（BACKFILL 在 source projection/fanout 前 deterministic bypass，
REPLAY/shadow 不进入，缺失/非法 quarantine）→ source-kind gate → 验证来源输出身份、
release/snapshot ref 与 contract version/hash → 按历史来源发布物解析 FactContract（不得
查询 current model）→ 映射 state/quality、规范化类型/单位、验证 eventTs/version/
occurrence 身份 → 校验本条输入的 fact count、bytes 与全部 semantic invariants → 无静态
eligible 更新则记 deterministic no-output，有则按 immutable eligibility dictionary 把
本批全部合格更新装入至多一条 SOURCE_DELTA → publish 回调/失败策略完成后，completion
sequencer 才推进连续 offset。一个静态 eligible 事实的永久 contract/type/identity 错误使
整条 source input quarantine，禁止先发布其余“成功字段”；ACK 不确定或 redelivery 时
必须重建并重发相同 sourceEventId、fact identities、eventTs、observedAt、
factVersion/occurrenceOrder 与 payload，不得把 retry 变成 no-output。

**静态 eligibility / automationEligibleBitmap。** 由同一快照内 `isCanSceneLinkage` 等
静态能力/治理标记编译的“是否允许进入 Automation/Scene”位图，属于快照 hash；它回答
“这个点是否允许进入”，不表示当前已有 Scene。Admission 的输出决定和 payload 集合只由
input 引用的 immutable source artifact 与 Canonical states 决定，不随 Scene interest
generation 漂移。false→true 必须执行受控初始构建/authoritative current rebase 并生成
coverage seed；true→false 必须在激活前撤销 posting 并 fence 对应 Current Fact。

**动态 interest / InterestedOrdinalBitmap。** 控制面根据 enabled Binding 的精确
dependency、当前 `tenantFactInterestGeneration` 与 snapshot dictionary 编译的动态派生
缓存，回答“Runtime 当前应为哪些点建 TRIGGER posting、哪些只作 CONTEXT”。cache key 为
`(tenantCode, moduleSchemaSnapshotId, snapshotProjectionHash,
tenantFactInterestGeneration)`，是 tenant 内 enabled Binding 的保守并集；它不属于快照
hash、不是配置真源、不能决定 Admission 是否发布，也不能充当 emit gate。缺失、
generation 不匹配或无法证明完整时 bounded rebuild/retry，不返回部分结果。角色区分
`TRIGGER_EMIT` 与 `CONTEXT_REQUIRED`：纯 CONTEXT_ONLY 或当前无人引用的事实不取得
triggerRight，也不仅因自身刷新触发 Scene。

**TriggerPosting / fanout / triggerRight。** Runtime 按消费时的 current Binding 对
SOURCE_DELTA 建 0..N fanout（one-target-one-bundle，每 Binding 每 bundle 最多求值一
次）。triggerRight 与 value merge 分离；BindingState 中对 `sourceEventId/factDeltaId` 的
bounded receipt 是判断该 Binding 是否已处理当前输入、从而抑制 redelivery 的依据。receipt 已有
记录 → redelivery 无新触发权；Current Fact/BindingState 的 factDeltaId 与当前相同但 envelope
不同 → `FACT_IDENTITY_CONFLICT`，在任何 exact-ID grant 之前 fail closed；Current Fact
恰好等于当前记录且 envelope 相同、但 receipt 尚无记录 → value 是 comparator duplicate，当前
输入仍保留恰好一次触发权；store 语义严格更新 → 当前 Delta stale 无触发权；store 较旧或不存在
→ 接受并获触发权；同 order 不同 payload/order-domain/版本存在性冲突 → 受影响
ArgumentDeltaBundle fail closed。成功求值必须原子推进对应 receipt，使后续 redelivery 无权。

**evaluation-time overlay。** 每次 data trigger、schedule、timer 或 subject-lifecycle
业务求值前，warm BindingState 也必须批量读取并 overlay 全部必要 LATEST_STATE
SingleValue 参数（不止 CONTEXT_ONLY 与 freshness 参数）；BindingState 中缓存的任何
SingleValue 都只是上次求值视图。合并固定顺序：确定所需 Current Fact → 并行读取并验证
coverage/readiness → 构造 tentative state → 以查询结果为 baseline 按 comparator 合并
当前 bundle（本批值不无条件覆盖）→ 另算 triggerRight → 再执行 missing/freshness、
predicate/FSM 与 timer 逻辑。rolling 参数必须是 TRIGGER，`CONTEXT_ONLY + ROLLING` 在
发布期拒绝。

**bindingSemanticHash。** Binding 的语义指纹；fact contract/identity 变化、timer
anchor policy 及其时间域依赖变化都必须改变它，即使 bindingId 保留。修改后旧
timer/state 不得 preserve，必须 close+tombstone+next-live bootstrap。

### 15.7 动作收敛补充

**EffectSetReceipt。** Action Outbox 中不投递的回执 row：
`effectSetReceiptId = H(SCENE_ID_V2, EFFECT_SET_RECEIPT_V1, processingNamespace,
tenantCode, bindingId, evaluationSubjectKey, triggerIdentity,
bindingSemanticHash)`。产生非空 action set 时，receipt 与全部 action row 在同一 PG
Action Outbox 本地事务插入；唯一键竞争的获胜 insert 由 DB transaction timestamp 生成
一次不可变 `acceptedAt`，acceptance-relative 的 `dispatchNotBefore/cooldownUntil` 由
同一事务冻结，retry/restore 必须读回原值，不得用 wall clock 重新起算。receipt 保存
`canonicalEffectSetHash`（按 effectId 排序的 `(effectId, actionPayloadHash)` 集合）与
`canonicalMutationPlanHash`（effect set + 影响后续业务求值的 operator/FSM state delta
+ 每 logicalTimerId 恰好一个 final operation 的 timer mutation + cooldown mutation）。
首轮空 action set 不写 receipt，仍属异步 best-effort state 边界。

**EFFECT_SET_CONFLICT / EFFECT_PAYLOAD_CONFLICT。** 已有 receipt 但 set hash 或
mutation-plan hash 不同 → 原子写入以
`(effectSetReceiptId, competingSetHash, competingMutationPlanHash)` 唯一的不投递
conflict row，本轮任何新 action 与 tentative state/timer/cooldown 均不提交，既有
effect 不回滚；conflict durable 后该 trigger 对本 target/binding 是 terminal
quarantined，redelivery 读取同一 outcome 并可推进 input completion，下一不同 trigger
可正常求值。相同 effectId、不同 actionPayloadHash 是 row 级第二道门禁
`EFFECT_PAYLOAD_CONFLICT`，按同一 terminal completion 协议处理。dispatcher 每次物理
投递携带相同 effectId 作为 idempotency key；唯一 logical Outbox row 不等于目标端
exactly-once。

### 15.8 身份 cutover

**SceneFactIdentityCutoverManifest（保留名称，未冻结）。** 它是未来 source/fact
身份公式变更时可能使用的业务审计 artifact，而非 V1 Runtime 编排契约。本章最多保留其
审计维度：old/new source/fact identity versions、彼此独立且不得交叉比较的 offset 域、
相关 dictionary/hash，以及受影响 Binding。具体 cutover 协议尚未冻结。

`SCENE_ID_V2` 的一次性 rollout 与 identity point-of-no-return 唯一见
[主规格 §9.4](场景联动%20Runtime%20主规格总纲.md#94-processingcontext-强门禁-rollout-与历史迁移)，
本文不复制该流程。未来如需 durable cutover barrier，必须由主规格与 Runtime 调度分章联合
ADR 冻结；它不是 V1 owner fencing，也不得在本术语章假定 Runtime drain、write generation、
写入令牌或 tombstone ACK barrier。

## 1. 先记住一句话

Scene 把 PropertyReport、DeviceEvent、ComputedMetricUpdated 和 reducer 已接受的 AcceptedStateTransition 规范化为统一 SceneEvent，在同一 evaluation subject lane 串行求值；只有 PostgreSQL Action Outbox 事务 commit 后，命令或 Webhook 才算被业务接受。

## 2. 先看状态标记

| 标记 | 含义 |
| --- | --- |
| `[现有实现]` | 当前仓库可以定位到对应目标契约的代码实现 |
| `[目标设计]` | 架构已经指定职责，但目标 runtime/package 或消息实现尚不存在 |
| `[待 ADR]` | 物理 Topic、Consumer Group 名、完整枚举或事务细节尚未冻结 |

> 本文时序图描述目标链路。当前仓库没有 `things/runtime/{presence,command,automation,timeseries,latest}`、
> `protocol/runtime` 或 `protocol/applications`；现有 `things/service/dmsvr` 只是 facade/旧流程，
> 不能据此把新 reducer、Scene Runtime 或 Computed Metric Runtime 标成已实现。

## 3. 本文唯一示例

R1 区域的 `temp-01/02/03` 共同计算 5 分钟平均温度。平均值超过 30℃并且
`door-01=CLOSED`，两者共同持续 2 分钟后，平台向 `fan-01/02` 下发启动命令并发送 Webhook。两台
风机的回复先由 Command reducer `[目标设计]` 收敛；只有合法状态变化才成为
`AcceptedStateTransition`。

示例中的 30℃、5 分钟和 2 分钟只用于讲解，不是产品默认值或容量承诺。

### 四类受信事实

| Scene factType | 具体输入 | 谁产生 | 时间形态 |
| --- | --- | --- | --- |
| `PROPERTY` | `door-01=CLOSED` 等 PropertyReport 点值 | ProtocolApplication `[目标设计]` | LATEST_STATE；由 Timeseries Materializer `[目标设计]` 投影 Current Fact |
| `DEVICE_EVENT` | 设备一次独立事件 | ProtocolApplication `[目标设计]` | `OCCURRENCE`，不覆盖前一事件 |
| `COMPUTED_METRIC` | R1 三个温度点的 5 分钟 AVG | Flink Computed Metric Runtime `[目标设计]` | LATEST_STATE；由 ComputedMetricCurrentFactProjector `[目标设计]` 投影 Current Fact |
| `STATE_TRANSITION` | Command reducer 接受的命令状态变化 | Presence/Command reducer `[目标设计]` | `OCCURRENCE`，只能触发 |

原始 Lifecycle/CommandReply 只是 observation，不能绕过 reducer 直接冒充 `AcceptedStateTransition`。完整来源身份见[主规格 §3.4](场景联动%20Runtime%20主规格总纲.md#34-输入身份)。

### 本例谁触发、谁只作上下文

`TRIGGER` 回答“该参数变化是否启动本 Binding 的一轮求值”，`CONTEXT_ONLY` 回答“只在其他触发已经
到来时读取其当前值”。二者与条件使用 `AND`/`OR` 无关。本例的准确语义是“平均温度超过 30℃并且
门保持关闭，二者共同持续 2 分钟”，所以平均温度和门状态都在 Duration predicate 内，必须都是
`TRIGGER`：任一参数变为不满足都要及时取消计时。

普通 `A > 30 AND B = CLOSED` 也不能默认只让第一个条件触发：A、B 都可能让完整条件最后成立，
所以完整谓词引用的动态参数都必须是 `TRIGGER`。只有产品明确表达成
`WHEN A changes IF B = CLOSED` 时，B 才是有意不主动求值的 `CONTEXT_ONLY`。rolling、
Edge/Change、Duration、Debounce 或 Hysteresis 状态作用域内的动态依赖同样必须为 `TRIGGER`；发布
的 Binding 必须逐参数显式保存模式，Runtime 不根据条件顺序猜测。

但“两个参数都能触发求值”不等于“两个参数各执行一次动作”。普通条件动作由完整谓词共享的
`Edge(RISING)` 收口：A 到达时若完整条件仍为 false，不动作；B 随后让它从 false 变为 true，只执行
一次；之后 A 再变化但完整条件仍为 true，只求值、不重复动作。这个保证适用于当前 active
owner/lane 的正常串行处理；它复用现有 best-effort `scene_state`，不新增严格持久化去重门，因而不
承诺跨崩溃或滞后恢复副本严格一次。完整规则见
[《控制面与匹配契约》§4.2](控制面与匹配契约.md#42-trigger-与-context_only)和
[《场景有状态计算规范》§§4.1.1～4.1.2](场景有状态计算规范.md#stateful-trigger-dependency-closure)。

## 4. 先认清程序和状态所有者

| 程序节点 | 本例职责 | 唯一写入状态/输出 | 状态 |
| --- | --- | --- | --- |
| Access Adapter | MQTT payload 机械投影到 Raw | Kafka Raw record | `[目标设计]` |
| ProtocolApplication | 解码、校验并事务性产生 Canonical | PropertyReport / CommandReply observation | `[目标设计]` |
| Timeseries Materializer | 一次消费完成 history、latest 和 PROPERTY Scene-live 槽 | TDengine + latest + PROPERTY Current Fact | `[目标设计]` |
| Flink Computed Metric Runtime | 执行 things IoT 控制面按 fingerprint 生成并发布的共享 ComputationPlan，维护 5 分钟窗口 | ComputedMetricUpdated | `[目标设计]` |
| ComputedMetricCurrentFactProjector | 投影最终计算指标 | COMPUTED_METRIC Current Fact | `[目标设计]` |
| Scene Admission | 校验来源契约并规范化为 SceneEvent | `scene_event` SourceDelta | `[目标设计]` |
| Scene Runtime | matching、latest-value join、duration 和动作接受 | 内存 SceneBindingState、异步 `scene_state`、PG Action Outbox | `[目标设计]` |
| Command Runtime | 以 effectId 幂等创建并投递命令 | CommandExecution / Attempt / Outbox | `[目标设计]` |
| Command reducer | 收敛重复、迟到和冲突回复 | command state/outcome + AcceptedStateTransition Outbox | `[目标设计]` |

这里的 `SceneBindingState` 是状态容器，`latest`/`rolling` 是状态组件；只有 Edge/Change、Duration、
Debounce、Cooldown、Hysteresis 才统称“有状态算子”。完整语义与代码生成约束见
[《场景有状态计算规范》](场景有状态计算规范.md)。

> Command reducer 是 Command Runtime（目标包 `things/runtime/command`）内部的回复归并角色；上表按创建/投递与回复收敛拆开讲，不表示存在两个命令状态 writer；这里的 Command Runtime 是 Scene 动作下游的命令领域角色，不计入主规格 §2 所称的两个场景计算 Runtime。

## 6. 为什么水线宁可失败也不用“看起来最新”的值

一句话：**FULL 档的 Runtime 必须先证明所有必要来源都已完整投影，再进行业务求值。** 否则它可能把设备 A 的新值和设备 B 的旧值拼在一起；动作一旦被接受或下发，随后到达的新数据无法撤销错误副作用。

FULL 档首次读取时，Runtime 通过 Kafka `ListOffsets` 捕获固定的要求水线；Current Fact writer 的 `readyThroughNextOffset` 是实际投影水线。两者逐 route 比较：

```text
actual.readyThroughNextOffset(r, generation)
    >= required.capturedEndNextOffset(r)
```

实际水线记录 partition 的连续 input completion，不是某一事实行自身的 source offset。同一
partition 的后续 input 按全局静态 eligible 与 temporal contract 无需修改 Scene-live value slot
时，只要其他适用处理已经完成，水线仍会越过该 input；无需等待原事实再次上报。原事实是否过旧
由 barrier 之后的 freshness 检查决定。

**DIRECT_TD 档不捕获该读取屏障，只使用软 lag 门，因此不具备 FULL 档的投影完整性证明。**

FULL 档未覆盖时，Runtime 复用同一个 `readBarrierId` 做 bounded retry；耗尽后 fail closed。本轮不进入 freshness、predicate 或动作。只有水线和 coverage 都通过后，才检查事实是否过旧。

> 要求水线从哪里来、与谁比较，以及 retry 对 Kafka 其他消息的影响，见
> [《水线与读取屏障详解》](水线与读取屏障详解.md)。规范定义仍见
> [《Scene Current Fact 设计》§5.2](Scene%20current%20fact设计.md#52-水线与-barrier)和
> [《场景有状态计算规范》§10](场景有状态计算规范.md#stateful-not-ready-freshness-fail-closed)。

## 7. 三类状态不要混在一起

| 状态 | 回答的问题 | key/所有者 | 本例内容 |
| --- | --- | --- | --- |
| Scene Current Fact | “现在已知的业务事实是什么？” | `(tenantCode,factOwnerKey,factType,factKey)`；每类来源一个唯一 writer | door=CLOSED、R1 5m AVG temperature |
| SceneBindingState | “这个 Binding 在这个计算主体上算到哪里？” | `(tenantCode,bindingId,evaluationSubjectKey)`；Scene Runtime | 参数快照、duration ARMED/FIRED、dueAt、timer slot/timerFireId |
| CommandExecution/Attempt | “命令创建、编码、投递和回复到哪一步？” | commandId/attemptNo；Command Runtime/reducer | fan-01/02 的两次独立执行和回复结果 |

Current Fact 不是 Scene 状态，SceneBindingState 也不是命令状态。Admission 和 Scene Runtime
都不是 Current Fact writer。完整定义分别见[《Scene Current Fact 设计》](Scene%20current%20fact设计.md)
和[《场景有状态计算规范》§3](场景有状态计算规范.md#state-container-scene-binding-state)。

SceneBindingState 驻留在 Actor lane 内；Actor lane 的状态层级与串行执行边界见
[Runtime 调度分章 §§2～3](Scene%20Runtime%20调度、分片与故障转移.md#runtime-model)，
lane 随 partition ownership 取得或失去时的生命周期见
[同分章 §6](Scene%20Runtime%20调度、分片与故障转移.md#runtime-state-machine)。本文不复制该调度协议。

## 8. 重投为什么不应重复动作

| 失败或重投位置 | 收敛依据 | 结果 |
| --- | --- | --- |
| Raw 被 ProtocolApplication 重读 | Kafka transaction、确定性 outputId、read_committed | 事务 abort 的输出不可见；重试保持同一业务身份 |
| ComputedMetricUpdated 重投 | outputId、planReleaseId、revision/finality、Current Fact comparator | duplicate 不刷新 Current Fact，也不再次取得值更新权 |
| SceneEvent 重投 | sourceEventId/trigger identity、EffectSetReceipt、effectId | 相同 effect set 幂等；不同 payload 形成 conflict，不静默覆盖 |
| Action Outbox commit 前崩溃 | PG transaction | 没有 accepted action；tentative state/timer 丢弃并重算 |
| Action Outbox commit 后崩溃 | durable Outbox row + effectId | dispatcher 可至少一次重试；已接受动作不因 scope exit 自动撤销 |
| CommandReply 重投或迟到 | commandId + attemptNo + 单调状态机 | 合法迟到推进只接受一次并登记一个 AcceptedStateTransition Outbox；duplicate/stale/conflict/unmatched 不登记 |

“唯一 Outbox row”不等于设备或 Webhook exactly-once；外部执行仍必须使用 effectId 作为幂等键。
事务顺序见[主规格 §12.3](场景联动%20Runtime%20主规格总纲.md#123-状态与-outbox-顺序)，
故障承诺见[SLO 文档 §4](SLO故障测试与实施.md#4-外部效果承诺边界)。

## 9. 本例的关键身份怎样传下去

| 身份 | 谁产生 | 用途 |
| --- | --- | --- |
| outputId | ProtocolApplication / Flink / reducer | 稳定识别一条来源输出 |
| sourceEventId → timerFireId | Scene Admission → Scene Runtime | 本例 source trigger 武装本轮 2m timer；fire 使用稳定 timerFireId |
| transitionId → effectId | Scene Runtime | 本例一次 timerFireId 派生一个 transitionId；fan-01、fan-02、Webhook 各一个 effectId |
| commandId → attemptNo | Command Runtime | 两个风机 effect 各建一个 commandId；每个 command 可有多个 attemptNo |
| causationOutputId | reducer | 把 AcceptedStateTransition 追溯到原 CommandReply output |

这些 ID 不是一个字段不断改名，而是不同边界上的稳定身份；完整 hash 和 provenance
见[主规格 §3.4](场景联动%20Runtime%20主规格总纲.md#34-输入身份)和
[《场景有状态计算规范》§3](场景有状态计算规范.md#state-container-scene-binding-state)。

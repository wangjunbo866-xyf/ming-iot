关键结构（③⑤ 与 ⑥a–⑥d）：③ 和 ⑤ 是同一个来源 Topic 上的两个不同 consumer group——Admission 组做 Scene 投影，Materializer 组做存储物化。 Materializer 一次消费、一次解码，写两个必选目标：⑥a 历史库（TDengine）、⑥c Scene-live 槽（Scene 专用当前值，仅 production+LIVE）； ⑥b 通用 latest 是可选模块（虚线），开启时才作为第三写入目标。全部启用目标 durable 之后才推进唯一 checkpoint（⑥d）——这个 checkpoint 就是 ⑧ barrier 使用的 readyThroughNextOffset 水线。 代价：任一启用目标卡住会拖住整个组的遥测写入；关闭 ⑥b 可少一处耦合（R3 落点）。
通用 latest 为什么可以可选：场景联动不读它——Scene 冷启动/求值/timer 复核只读 Scene-live 槽（通用 latest 允许 BACKFILL CAS 改写，本来就必须与 Scene 分槽）； 业务查询（仪表盘/设备详情/latest API）要的就是「最新一行」：BACKFILL 补的老数据 ts 更小、赢不了 last，newest 由 LIVE 路径刷新，且内置 last 按主键 ts 取 max、天然免疫 BACKFILL 乱序到达。 V1 默认不开启独立 latest 投影，通用 latest 作为查询层能力由 TDengine last over history 承载；严格冻结 5 元组 CAS 投影（独立 TDengine 表或 Redis）降级为 deferred option——出现明确的正确性消费者（而非展示消费者）或高读 QPS 需求时再启用。 待确认前提：history 表主键 ts 即写入时已校验的 effectiveTime（含 deviceTime 可信度回退），否则错误的未来设备时间戳会污染 last 视图。 Scene-live 槽不可选、也不能用内置缓存（要 LIVE-only 过滤、fence、coverage、provenance）。 该改动属父架构联合修订事项（设计文档 §8.5 与 §13 第 30 项），且以 Scene 改读 Scene-live 槽落地为前提。
* group 命名为示意：设计中明文命名的只有 metric 投影的 scene-current-fact-computed-metric-v1（§8.2）；Admission 与 Runtime 的组名图中为占位。 完整来源流共四类：iot.data.canonical.telemetry.v1（本场景）/ iot.data.canonical.device-event.v1 / ComputedMetricUpdated / AcceptedStateTransition； 其中 DEVICE_EVENT 与 STATE_TRANSITION 是 OCCURRENCE——没有 Current Fact 写入者，但仍经 Admission 投影进 scene_event。 Runtime 热状态持久化走 scene_state（异步 best-effort）。

水线设计：offset、水线与 barrier（主流程 ⑧ 的展开）

barrier 把"读到的值新不新"从运气问题变成证明问题：求值前，拿 broker 末尾号码当及格线，等写入者的完成承诺过线，再读值。

1. 三个概念

概念一句话类比
offset Kafka 每个 partition 是一条编号传送带，每条消息领一个递增号码（97、98、99…）。它是账本，不是时间。 传送带号码
水线 readyThroughNextOffset 写入者每处理完一条、且结果全部 durable，才把公开计数器拨到"下一条待处理号码"。水线=101 的含义：「101 之前的都处理完并落库了」。它是对外承诺，不是内部状态。 分拣员的公开进度牌
barrier Runtime 求值前的对账动作：先看各传送带 broker 末尾到几号（及格线），再等水线过线，然后才读值。 求值前对账

2. 场景与两条传送带

规则：设备 D1 温度>80 AND 设备 D2 湿度>70。D1 的报告在 partition 3，D2 在 partition 7（不同设备 → 不同传送带，两个独立 offset 域，号码互不可比）。

partition 3 (D1温度):  [97][98][99][100=温度85]          broker 末尾 = 101
partition 7 (D2湿度):      [256][257][258][259=湿度75]      broker 末尾 = 260

3. 时间线（盯住四个计数器）

时刻broker p3 末尾水线 p3broker p7 末尾水线 p7事件

4. barrier 三步（§8.4）

  1. 登记：Runtime 声明本轮求值所需路由（p3 温度、p7 湿度）；并发请求由 CurrentFactBarrierSnapshotProvider micro-batch 合并；
  2. 捕获末尾：provider 对 route 并集批量调 broker ListOffsets，得到及格线（p3=101、p7=260），返回不可变 snapshot；登记完成之后才开始的 capture cycle 才有效，登记前的旧缓存不得充当本轮 barrier；
  3. 等水线：各 partition 水线 ≥ 及格线才放行；随后批量读 Current Fact 行，并复核各 entry 的 projection generation / 水线一致，再求值。同一 logical trigger 的有界 retry 复用同一 snapshot，不追逐新末尾。

5. 三个直觉问题

  • 每次评估都要等吗？只在真有在途数据时等。没有新数据时 broker 末尾 = 水线，第一步就全过，零等待。barrier 的等待 ≈ 写入延迟 × 有数据在途的概率，不是固定开销。
  • 水线追不上怎么办？有界 retry，超时本轮延后；水线 lag 是监控指标、会告警。「等不到」是响亮事件，绝不拿旧值硬算。
  • 为什么不 sleep 2 秒？2 秒是猜，水线是证明：空闲时白等（99% 的情况 100ms 就够），积压时不够（高峰写入延迟 5 秒，sleep 完还是旧值，还自以为安全）。

6. 多节点：水线存在哪

水线不在任何节点的脑子里——它是共享库里每 partition 一行的小记录。节点 A 的 Runtime 与负责湿度 partition 的节点 B 从不直接通信，两边只跟库说话：

共享 Current Fact 库（Redis / PG）
├── 数据行: (T1, D1@B9, P123) → 85.0      ← 谁拥有 partition 谁写
├── 数据行: (T1, D2@B7, P124) → 75.0
├── 水线行: (telemetry, p3) → 101          ← p3 owner 节点写
├── 水线行: (telemetry, p7) → 260          ← p7 owner 节点（B）写
└── seed / fence / conflict outcome 小表 …
  • 谁写哪条水线由 Kafka consumer group 的 partition assignment 决定；写入纪律固定：先数据行 durable，再更新水线行（PG 可同事务——水线可见 ⇒ 数据必可见）。
  • 谁读：任意 Runtime 节点点查那行即可。无节点间 RPC、无锁、无 gossip；节点增减/rebalance 只改 assignment，水线数据不动。
  • rebalance 缝隙：group 协议保证一个 partition 同一时刻只有一个 active consumer（旧 owner 先 revoke）；cutover 显式撤销旧 write token（fencing）。同 generation 内水线单调递增、重复写无害；跨 generation 的值不可比较，读者不得拼接。

7. 为什么用 offset 而不是时间

设备时钟会漂、事件时间与处理时间不一致、机器间时钟不同步——时间是糊涂账；offset 是每条流自己的精确账本。代价是各流号码互不可比：四类来源（telemetry / device-event / computed-metric / transition）各自独立成域，水线只在同域内比较，绝不交叉比较。

出错分支：设计的真正用武之地

系统吸收 不需要人介入 · fail closed 响亮失败、等人修 · 错误前移 暴露在发布期

Admission 发完没收到 ACK 系统吸收

不看任何当前状态，原样重发 SE-1/FD-1/85.0。Runtime：FD-1 已处理 → 不给新触发权；写入者：同 ID 同指纹 → 幂等跳过。什么都不会发生第二次。

10:04:30 回落到 78°C 系统吸收

撤掉定时器（每个定时器只保留一个最终操作）。之后重新超 80°C 时，从新的合法锚点重新计 5 分钟。

乱序旧值：09:59 的 90°C 晚到 系统吸收

裁判判 STALE：不降级当前值、不动定时器、不刷新鲜度。静默丢弃，但有指标计数。

同 eventTs 又来一条 91°C（无版本） fail closed R1

裁判判冲突 → 写入者给这个 key 贴 fence（封条）→ 此后读取一律返回「投影冲突」→ 求值零动作 + 告警。宁可这台设备的场景瘫掉等人修，也不在 85 和 91 之间随便挑一个继续算。

BACKFILL 补历史数据 系统吸收

确定性绕过：不写 Scene-live 槽、不触发场景；但 checkpoint 水线照样推进。补数不会偷摸影响生产动作。

设备 10:03 过户 系统吸收

新 ownershipBindingId → 新 factOwnerKey → 旧事实留在旧槽位，不串到新主人名下；场景范围按当前 SubjectContext 重新匹配。

Runtime 10:02 崩溃 系统吸收

timer 带原 dueAt/timerFireId 原地复活，不重新计时；回执保证同一触发发不出第二套动作；落库前的重算按更新 baseline 来——这是明说的 best-effort 边界，不假装 exactly-once。

模型改版 S2 错误前移

沿用 P123：场景零改动，新老设备进同一场景。若把单位改成 °F → 说明书指纹不同 → 发布直接失败：错误暴露在上架那一刻，而不是运行三个月后。

2. 持久化哲学的四个结构性差异

  1. "最新值"表的成色：TB 的 ts_kv_latest 是与 history 同一次 doSave 里的第二个 DAO 调用（BaseTimeseriesService.java:202-219）；SQL 端有 ts <= ? 旧值保护（SqlLatestInsertTsRepository.java:45），Cassandra 端是裸 INSERT 没有保护；无 mode 区分、无裁判、无 fence、无 coverage。本设计：唯一写入者 + comparator + 水线 + coverage seed 的完整状态机。
  2. 状态持久化（唯一真正相似处）：TB CF state 写 compacted topic tb_cf_state（KafkaCalculatedFieldStateService.java:75）≈ 本设计 scene_state。差异在纪律：本设计明说 best-effort、恢复后允许重算、EffectSetReceipt 收敛；TB 每次处理后 persist、恢复即续，但 CF 队列消费失败只记日志不重投（DefaultTbCalculatedFieldConsumerService.java:169-177，at-most-once 倾向）——状态缺一次输入无人知晓。
  3. 动作收敛粒度：TB 靠 PG 存储过程 create_or_update_active_alarm（schema-functions.sql:17-86）按 (originator, type) 活跃告警唯一去重——挡住重复告警，挡不住「同一触发重算出两套不同动作」；本设计 EffectSetReceipt + actionPayloadHash 管后者。
  4. 成功承诺边界：TB 在 Kafka produce 成功（leader ack）时即回 MQTT PUBACK（DefaultTransportService.java:1157），此刻消息尚未被任何规则处理；RE 队列处理策略允许重试超限后丢弃整批。本设计：Canonical offset 事务提交、各消费者独立书签、conflict 也须 durable outcome 才推 frontier。

TB 的 ts_kv_latest 一张表兼任展示与自动化两职；本设计拆开：展示半 → 通用 latest（可选，TDengine last）；自动化半 → Scene Current Fact。

6. 裁决

TB 用「推送聚合 + compacted state + (originator,type) 告警幂等」三件便宜工具挡住了它规模下最常见的问题，是精明的工程。 它的三个边界恰好是本设计在亿级规模下的三个洞：CF init 现查无证明（= cold bootstrap 问题）、推送可丢无感知（= NOT_READY/fence 问题）、跨 partition 无完整性（= barrier 问题）。 本设计的差异复杂度集中在四处——稳定身份、水线/coverage、裁判/fence、effect-set 回执——每一处都对应 TB 语义边界上一个会在「百万设备 + 多版本 + 多租户」下变成工单的静默错误。

四句话总结：身份稳定（模型改版场景不重配）· 拿不准不动（错误会响不会闷）· 缓存有追平证明（没追上 ≠ 没数据）· 动作整组留回执（崩溃重算不分叉）。
评审保留条件落点： R1 fence/冲突的修复工具链需定义作用域与成本 → 红色卡片； R2 identity/projection 库（Admission 与 Materializer 共用）变更需 shadow-compare 灰度 → Admission 生命线； R3 一个 checkpoint 管全部启用目标，Scene-live 槽（及可选 latest）的可用性耦进遥测写入关键路径，需明文运维应答 → Materializer 生命线； R4 barrier 等待需时延与原因级指标 → 消息 ⑧。

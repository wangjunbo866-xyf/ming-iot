## 0. 竞品研究观察

- 在本次样本与可见证据边界内，未观察到同时保持极轻运行态机制和完整恢复语义的点位级方案；语义取舍、状态外部化和恢复机制之间普遍存在成本交换。
- 运行态实现可横向归为四类常见路线：纯内存/可丢失状态、显式业务库状态、per-key KV 状态，以及 checkpoint/持久 state 与重放组合。§1 用 A—D 路线展开这一归类。
- ThingsBoard、JetLinks 和 Cumulocity 等样本显示，告警实例或可观测终态常落在业务库，用业务唯一性或条件更新吸收部分重复；这不等于各平台对计算状态做出了相同选择。
- OpenRemote 的首轮动作抑制、JetLinks 现查设备最新值和 openHAB 事件携带前态，都是对应平台特定语义与部署条件下的事实，不能单独推导本项目的恢复协议。
- 本项目的现行选择按职责见顶部主规格总纲与 Runtime 调度分章。

## 1. 四条路线总览

| 路线 | 代表平台 | 场景联动状态怎么办 | 代价 |
| --- | --- | --- | --- |
| A. 彻底无状态 | EMQX、AWS IoT Core Rules、阿里云 IoT、Azure IoT Hub 路由 | 语法层砍掉窗口/聚合/duration，状态推给用户或下游流计算 | 表达力残缺，duration/cooldown/edge 缺位 |
| B. 内存状态 + 诚实丢失 | ThingsBoard CE rule chain、JetLinks、Home Assistant、openHAB、Cumulocity、Node-RED、rulego | duration/cooldown/timer 主要在内存；TB CE 仅 deprecated 告警节点有默认关闭的可选 PG 状态 | 默认重启即丢；告警业务库可吸收部分重复 |
| C. per-key 小 KV + TTL + 配额 | Losant、AWS IoT Events（已停售） | 状态缩成每设备一行小记录，节点执行时同步读写，惰性过期 | 无一致性保证；TTL 静默改行为；规模受限 |
| D. 持久 state/checkpoint + 重放或恢复 | eKuiper（轻量形态）、Flink、Azure Stream Analytics、ThingsBoard CF（重量形态） | 快照、checkpoint 或全量 state changelog，配合源重放或 state-first 恢复 | 机制复杂度、恢复时间与写放大受状态大小和变更频率影响 |

## 2. 开源平台档案（源码实证）

### 2.1 eKuiper（LF Edge）——D 路线的最轻形态

- **状态形态**：运行时状态全部在内存 `sync.Map`（`internal/topo/context/default.go:358`）。窗口算子存**全部原始 tuple**（`$$windowInputs`，`internal/topo/node/window_op.go:87-91`）；source offset 存 `$$offset`；另有内置防抖函数 `last_hit_count/last_hit_time`（`internal/binder/function/funcs_global_state.go`）。
- **持久化**：opt-in。rule 级 `qos>=1` 才启用 SQLite KV store（`internal/topo/state/store.go:25`；默认 qos=0 纯内存，`memory_store.go` 全 no-op）。简化版 Chandy-Lamport barrier：每 `checkpointInterval`（默认 **5 分钟**）把整条 rule 的全量状态 gob 序列化后**一行写入 SQLite**，内存最多保留 3 个 checkpoint（`internal/topo/state/kv_store.go`，全文 146 行；`internal/topo/checkpoint/coordinator.go`）。存储后端编译期可换 redis/pebble。
- **恢复**：读最后一个快照 + source `Rewind` 回倒 offset 重放（`source_node.go:225-251`）。崩溃丢最近一个 checkpoint 间隔；qos=1 sink 端重复甩给用户去重；qos=2 只保证内部状态恰好一次，sink 仍可能重复。`kill -9` 时 shutdown 补快照机制无效。
- **配额**：checkpoint 保留 3 份；**无单算子状态大小硬上限**，窗口膨胀只受 channel buffer 间接限制。
- **定性**：**「边缘单机的诚实极简主义——小状态不值得重装备，丢了就靠重放，重放不了就认丢」**。单机 SQLite、全量快照限定了部署形态；内存优先、定时快照与 source 重放构成一套 state+checkpoint 两包合计不足 1500 行的边缘实现。

### 2.2 ThingsBoard CE rule chain——B 路线代表（4.x CF 之前的老方案）

- **状态形态**：95% 节点无状态。dedup/delay/tick 全是 JVM 堆内 Map + 内存 `ScheduledExecutorService`；`DefaultTbContext.java:178` 有作者亲留 `//TODO: add persistence layer`——**从未持久化**。告警 duration 状态 = `PersistedAlarmRuleState{lastEventTs, duration, eventCount}`（每规则 3 个 long），靠每分钟 cron 扫描内存 Map 累加（`AlarmRuleState.evalDuration`）。
- **持久化**：规则链中唯一涉及 `rule_node_state` 的路径属于已 deprecated 的 `TbDeviceProfileNode`；`persistAlarmRulesState` 与 `fetchAlarmRulesStateOnStart` 两个开关默认均为 false。只有开启持久化时，告警规则状态变化才会**同步写 PG `rule_node_state` 表一行 JSON**（`dao/.../RuleNodeStateEntity.java`）。告警实例本身存 DB `alarm` 表，`TbCreateAlarmNode` 查已有活动告警天然去重。
- **恢复**：默认靠 Kafka offset 重投（at-least-once，重复处理是常态），规则节点运行态不恢复；只有已有持久化状态且开启对应加载开关时，deprecated `TbDeviceProfileNode` 的告警状态才以最后一次写盘为准恢复。有状态节点为吞吐会**提前 ack**（`TbMsgDeduplicationNode`），崩溃即消息与状态一起丢——`TbMsgDelayNode` 因此被官方标 `@Deprecated`，注释自认 "does not guarantee that message will be processed"。
- **配额**：dedup 每 originator 默认 100 pending；delay 默认 1000；状态总量无硬限。
- **定性**：**「无状态 actor + Kafka 重投」：把绝大多数状态做成可丢弃的堆内 Map；只有 deprecated 告警节点提供默认关闭的可选 PG 状态路径**。开启后「每变更同步写 PG 一行」会产生与状态变更频率成正比的写放大；本次源码调研没有证明这与 4.x 引入 CF 之间存在直接因果关系。

### 2.3 EMQX——A 路线极端代表

- **语法级无状态**：`rulesql.yrl` 终结符全集无 GROUP BY/WINDOW/INTERVAL——窗口能力不是没实现，是没设计。规则 = `{select, Clauses}` / `{foreach, Clauses}` 纯函数式「消息进、动作出」（`emqx_rule_runtime.erl`）。duration/cooldown/edge/告警实例一概不存在。
- **唯一跨消息原语**：SQL 函数 `kv_store_put/get/del`，一张节点本地 ETS 表（`'@rule_engine_db'`），重启全丢、集群不复制、无配额——escape hatch 而非功能。
- **持久化**：只有规则定义（Mnesia 集群配置 + `cluster.hocon`）；节点启动 `load_rules()` 重新编译。bridge 缓冲用 replayq 但故意配成 `volatile_offload`——重启主动清空磁盘 segment（`emqx_resource_buffer_worker.erl:2537`），宁可丢消息也不承担状态恢复。
- **恢复**：规则执行 fire-and-forget，失败只记 metric；重复 vs 丢失由 MQTT QoS 重传决定，引擎对单次触发零保证零记录。
- **定性**：**「规则无状态，定义才持久」——用彻底放弃状态语义换极致简单与吞吐；有状态计算官方指路 eKuiper**。

### 2.4 Node-RED——B 路线（边缘单机）

- **状态形态**：内建节点状态全内存——trigger 计时器（`89-trigger.js:88` `node.topics` + setTimeout）、delay 队列、rbe edge 状态（`rbe.js:25` `node.previous`）、join 窗口。只有用户显式 `context.set()` 的状态可持久化。
- **持久化**：localfilesystem context 插件 = 内存缓存 + **30 秒写合并** + 整 scope JSON `writeFileAtomic` 覆盖（`@node-red/runtime/lib/nodes/context/localfilesystem.js`）。无 checkpoint/WAL。优雅 shutdown 强制 flush。
- **恢复**：崩溃丢最近 30 秒写入；内建计时器状态**永远丢**——「门开持续 5 分钟才告警」重启后 op2 永远不发，漏触发无任何补偿；rbe 重启后首条消息被当作「变化」重复通过。官方文档直言默认配置「重启 = 状态清零」。
- **配额**：context 无大小/TTL 限制；delay 队列 `nodeMessageBufferMaxLength` 默认 0 = 不限。
- **定性**：**「默认无状态，持久化是用户的显式声明」**——只对显式声明要存活的状态支付持久化成本；JSON 全量刷盘也把实现限定在相应的单机部署规模内。

### 2.5 rulego（本仓库）——B 路线（现状清单）

- **设计宣言**：`api/types/types.go:434` "Components are stateless by design"。核心库无窗口聚合/去重/告警状态机节点。
- **有状态点全内存**：delay 挂起队列 + `TellSelf` 的 `time.AfterFunc`（`components/action/delay_node.go:91`、`engine/rule_context.go:523`）；通用 KV 原语 `types.Cache`（默认 `MemoryCache`，map+RWMutex+TTL，无容量上限）。server 模块写盘的只有链定义 JSON 与运行日志（bbolt），不是运行时状态。
- **恢复**：进程重启 = 一切清零；**热更新同样丢**（`ReloadSelfFromDef` 全量重建，`DelayNode.Destroy()` 空函数，pending 静默丢弃）。补偿设计：`metadata._delayOffsetMs` 把恢复责任推给消息载体。`WithRestoreNodes` 恢复的是执行流程断点，非业务状态。
- **扩展点**：`Config.Cache` 可自实现 Redis 版（接口仅 Set/Get/Has/Delete 等，无 CAS/原子过期）+ 自定义节点 + node_pool。
- **定性**：**诚实的纯内存编排内核，状态平台的位置是留空的**——接口保留了替换 Cache 与增加自定义节点的扩展点，但现成实现并未提供完整状态层。

### 2.6 JetLinks（jetlinks-community）——B 路线，国产原生场景联动

- **状态形态**：场景编译成 Reactor 流，**没有任何 state store 抽象**。duration/防抖 = `ShakeLimitFlux.java:90-124` 的几个 `volatile long` + `Schedulers.parallel()` 定时器；DelayAction = `Mono.delay()`；分支「持续满足才触发」= 内存 `Sinks` + reset 信号（`SceneRule.java:305-349`）。edge/上一次值比较**不留本地状态**，现查 `device.property.recent()`（`DeviceTrigger.java:303-307`，底层是设备档案存储/Redis 缓存）。
- **持久化**：唯一认真持久化的是告警实例——Redis hash + 关系库 `alarm_record` 条件更新判重（`DefaultAlarmHandler.java:101-168`：`UPDATE ... WHERE state='warning'` 返回 0 行才 INSERT）。另有 `TaskSnapshot` 表，但只存调度拓扑（任务在哪个节点跑），无运行数据。
- **恢复**：重启从 `task_snapshot` 表拉起任务——**恢复的只是「任务在跑」，防抖计数/timer 进度/delay 队列全部清零**；编辑/重发布场景 = `dispose` 旧流重建，状态清零。社区版无自动故障迁移（`reBalance` 直接抛 `UnsupportedOperationException`）。诚实缺陷：定时场景在 N 节点集群 N 倍重复触发（单节点调度被注释，`TimerTriggerProvider.java:131-132`）。
- **配额**：无场景数/状态大小配额；防抖分组无上限，分支队列无界（OOM 风险靠 JVM 自担）。
- **集群分区**：设备触发场景用 `justLocal()` 订阅——**分区天然绑定设备接入连接落点**，连接迁移即内存状态作废。
- **定性**：**「规则无状态化、状态流量化」——用重启即失忆换取较低机制复杂度**。其内存计数器、关键业务态外部化与连接落点分区是同一套部署取舍；无恢复语义、无迁移和无配额也是这套取舍的边界。

### 2.7 OpenRemote——B 路线，「数据库即状态后端」

- **状态形态**：单 JVM 单体（K8s `replicaCount: 1`），easy-rules 4.1.0（无 RETE 工作内存）。规则 facts = 全量资产当前值的堆内 HashSet（`RulesFacts.java:82-84`，初始容量 10 万）。duration = `durationMatchTimes`（`JsonRulesBuilder.java:95`，首次匹配记时间戳）；edge 去重 = `previouslyMatchedAssetStates`；cooldown = `nextRecur` 时间戳（per-rule 或 per-asset）；全部 HashMap/HashSet。
- **持久化**：只有 PG 里的资产当前属性值（JSONB，先落库后送规则，`AssetProcessingService.java:342-445`）与告警（`SentAlarm` JPA）。规则运行状态从不写盘，无 checkpoint/snapshot/WAL。
- **恢复（首轮动作抑制）**：重启从 PG **重放所有资产当前值**重建 facts（`RulesService.java:852-861`），然后**首轮点火抑制动作**（`JsonRulesBuilder.java:696-708`：`hasPreviouslyFired()` 为 false 时只记 `previouslyMatchedAssetStates`、不执行动作）——重启后仍满足条件的规则不重复告警，主动选择「宁可漏触发、不可重复触发」。duration 计时清零重计、cooldown 丢失、错过的 cron 不补、延迟动作消失——恢复逻辑总共约 100 行。
- **配额**：`MAX_RULES_TRIGGERED_PER_EXECUTION = 100` 防规则循环；facts/计时 map 无界；点火节流 3s/周期 50s。
- **定性**：**「数据库即状态后端，内存即工作集，重启即重放」**——该平台把 DB 当前值投影、可丢弃易失计时态和首轮抑制组合成一条轻量路线，明确代价是放弃 duration/cooldown 的崩溃精确性。

### 2.8 Home Assistant——B 路线（消费级单机）

- **状态形态**：automation `for:` 持续计时 = 纯 asyncio 定时器 + 闭包 dict（`triggers/state.py` → `async_call_later` → `loop.call_at`，一行见底）；边沿 armed 集合纯内存；运行中脚本（delay/wait_for_trigger 到一半）重启即杀。
- **持久化**：`.storage/core.restore_state` **一个 JSON 文件**，启动后、每 15 分钟、优雅停机时**全量重写**（`helpers/restore_state.py`，全文约 300 行）；存「实体最后状态 + extra_data」，实体删除后保留 7 天。timer 实体可选恢复：用快照里的 `finishes_at` 绝对时间「补响或续跑」。
- **恢复**：`for:` **重启即蒸发且不重新计时**——官方文档明说 "will not survive restart"，静默漏触发；官方 workaround 是让用户把触发时刻写进持久化的 `input_datetime`——**把可靠性从运行时机制降级为数据建模问题**。kill -9 最多回退 15 分钟。
- **定性**：**「内存即真相，磁盘只存最后一张快照；宁可诚实地漏，也不为确定性付工程税」**——哲学（分层诚实性、可靠性显式物化成数据）可借鉴，实现（单文件全量 JSON）不可上云。

### 2.9 openHAB——B 路线，「运行状态可重推导」

- **状态形态**：规则引擎刻意近乎无状态。**边沿信息搭事件便车**——`ItemStateChangedEvent` payload 自带 oldState（`ItemStateTriggerHandler.java:144-154`），引擎零存储。`createTimer` = 纯内存 `ScheduledExecutorService`；expire（无命令超时回位）= 内存 map + 1Hz 全表扫描（`ExpireManager.java:81-123`）。
- **持久化**：与联动运行态完全分离的另一套——Item 状态走插件式 persistence（rrd4j/mapdb/jdbc 等），`restoreOnStartup` 启动回读最后状态且**直写不发事件**（不会误触发规则）；规则定义存 JsonStorage（延迟 500ms 批量整文件覆写 + 5 个滚动备份）。
- **恢复**：关键模式是**运行状态从持久化的设备状态重推导**——`DateTimeTriggerHandler.java:96` 从持久化 Item 状态重建 cron 表达式；`SystemStartlevelTrigger` 提供启动重放钩子，官方教用户用 `System started` 规则重建 timer。`createTimer` 全丢不补、expire 重启后静默失效到下一事件、错过的 cron 跳过——诚实 at-most-once。
- **定性**：**「不存运行状态，而是让运行状态可以被重新算出来」**——事件自带前态 + Item 状态恢复 + 启动重放钩子三件套，是家庭自动化单机场景对 Flink 式状态管理最激进的反向答案。

## 3. 商业平台档案（官方文档）

> 以下结论全部来自官方文档；涉及内部实现处标注「推断」。

### 3.1 AWS——「状态外包」，两条产品线对照

- **IoT Core Rules Engine**：彻底无状态。SQL 只有 SELECT/FROM/WHERE/SET，全部约 80 个内置函数均为标量函数（文档枚举核对），无窗口/聚合/GROUP BY。有状态需求的官方答案：`get_dynamodb()` / `get_thing_shadow()` **同步查外部 KV**（按 action 计费）。错误处理：有限重试 → 诚实丢弃 + error action；无 exactly-once。配额：1000 规则/账户、2 万评估/秒/账户。
- **IoT Events**（按 detector 实例维护状态的托管服务，**截至调研日，2025-05 已停售新客户、2026-05 已整体停服**）：detector model = 状态机（≤20 states），按 input key 自动裂变实例，每实例 = `{stateName, ≤50 variables, ≤5 timers}` 一行小状态，有 DescribeDetector/BatchUpdateDetector 读写 API——状态是一等公民数据。timer 最短 60s，到期主动触发评估；BATCH 评估模式（同组事件看到输入前快照）；**messageId 5 分钟去重窗口**是唯一恰好一次机制。配额：每实例 10 msg/s（固定）、全账户 1000 评估/秒、单模型 10 万实例。
- **官方迁移指南给出的替代架构**（文档明说）：Kinesis 按设备 ID 分区 + Lambda 读改写 **DynamoDB 单行状态** + EventBridge Scheduler **每实例一个 schedule 当 timer**。这是 AWS 建议的迁移实现，不能据此断言 IoT Events 原服务内部采用相同架构；该替代方案没有 checkpoint/watermark。
- **定性**：**「状态外包」——无状态规则引擎 + 按 key 分区的一行小 KV + 5 分钟去重窗口**。公开配额显示其容量边界是每实例 10 msg/s、每账户 1000 次评估/s、每模型 10 万实例；停售事实只能说明该产品线截至调研日的商业状态，不能单独推导某种自研架构或点位级容量结论。
- 资料：[IoT Core SQL 函数](https://docs.aws.amazon.com/iot/latest/developerguide/iot-sql-functions.html)、[rule actions](https://docs.aws.amazon.com/iot/latest/developerguide/iot-rule-actions.html)、[IoT Events Developer Guide](https://docs.aws.amazon.com/pdfs/iotevents/latest/developerguide/iotevents-dg.pdf)、[IoT Events 配额](https://docs.aws.amazon.com/general/latest/gr/iot-events.html)

### 3.2 阿里云 IoT——「平台无状态化」（已停售新用户）

- **数据流转**：规则 SQL 全部标量函数（约 30 个），无聚合/窗口/JOIN；失败重试 1s/3s/10s 三次后**诚实丢弃** + 错误记录；去重甩给消费者按 messageId。服务端订阅 = 纯推送，唯一状态是 MQ 堆积（1 亿条/1 天）。
- **场景联动**（TCA 模型）：触发器 = 属性/事件**变化** + cron；**刻意不做 duration/edge**——「温度连续超阈 5 分钟才动作」无法表达，官方路径转函数计算。唯一计时状态是「延时执行」任务（最长 24h）。后继产品「事件响应」唯一的跨事件持久状态是**静默周期（cooldown）上次触发时间**，最长 1 天。
- **告警**：工单式三态（待处理/已处理/已忽略），人工流转，无自动恢复/聚合。
- **配额**：场景 ≤100~200 条/实例；事件处理 ≤5000 次/小时；每规则触发器 ≤10——定位是**低频运维通知**，不是点位级计算。
- **定性**：规则平台将窗口、duration 和 edge 等有状态语义排除或外部化到函数计算/Flink。无 duration/edge、每实例 100~200 条场景、每小时 5000 次事件处理和每规则最多 10 个触发器，共同限定了其低频运维通知定位；停售只记录截至调研日的商业状态，不作为技术结论的证据。
- 资料：[使用限制](https://help.aliyun.com/zh/iot/product-overview/limits)、[什么是场景联动](https://help.aliyun.com/zh/iot/user-guide/scene-orchestration-1)、[什么是事件响应](https://help.aliyun.com/zh/iot/user-guide/what-is-incident-response)、[云产品流转](https://help.aliyun.com/zh/iot/user-guide/overview-4)

### 3.3 Azure——「分层卸载」

- **IoT Hub 路由/Event Grid**：纯无状态谓词匹配（单消息属性/body/twin），无窗口无 join；at-least-once，状态问题原样推给下游。
- **IoT Central rules**：唯一时间维度状态是 tumbling window 聚合；**无 duration/edge/告警实例**；**用动作限流代替 cooldown 状态机**（email 每规则每分钟 1 封、webhook 每 10 秒 1 次）——「用配额换实现简单」：即使内部状态重建导致重复触发，限流也能兜住用户可见噪声。配额：50 规则/应用、200 msg/s。
- **Azure Stream Analytics**（微软对有状态的正式答案）：全内存 Trill 引擎（状态超内存即作业挂掉，不是降级）+ 内部 checkpoint（每几分钟，用户不可见不可配）+ replay 兜底；用户主动停止再启动 = checkpoint 不可用，**全量 replay**（要求输入保留期 ≥ 最大窗口）；处理 exactly-once、输出 at-least-once。窗口最大 7 天。状态可靠性/恢复速度全部按 SU 折算成钱。
- **定性**：接入层极轻（无状态路由 + 限流式降噪），有状态层不比 Flink 便宜——**微软的选择是把「规则即状态」的中间地带干脆砍掉**。
- 资料：[Message routing](https://learn.microsoft.com/en-us/azure/iot-hub/iot-hub-devguide-messages-d2c)、[IoT Central rules](https://learn.microsoft.com/en-us/azure/iot-central/core/howto-configure-rules)、[Quotas](https://learn.microsoft.com/en-us/azure/iot-central/core/concepts-quotas-limits)、[ASA checkpoint/replay](https://learn.microsoft.com/en-us/azure/stream-analytics/stream-analytics-concepts-checkpoint-replay)、[ASA delivery guarantees](https://learn.microsoft.com/en-us/stream-analytics-query/event-delivery-guarantees-azure-stream-analytics)

### 3.4 Cumulocity——「引擎可弃，状态入库」

- **架构**：Analytics Builder 模型、EPL apps、smart rules 全部注入每租户的 Apama correlator 微服务执行；窗口/duration/listener 状态全在 correlator 堆内存。
- **持久化**：文档明说——**没有**。「all microservices must be stateless」，correlator 无持久文件系统，Apama 原生 persistence 与 MemoryStore persistence 均不可用且官方已 deprecated；官方方向是「要持久就显式写平台库」。**告警实例不下放引擎**：平台告警库按 (source, type) 去重，重复上报只 count+1——用平台语义吸收引擎重启后的重复触发。
- **恢复**：重启 = 状态清零，从 `onload()` 重跑；**Safe mode** 检测崩溃循环后禁用全部用户代码并 raise CRITICAL alarm（宁可不跑也不崩溃循环）；restore 超 60s raise alarm 重试；CEP 队列满时**明确丢旧事件**并告警。
- **配额**：按微服务规格卖（`Apama-ctrl-250mc-1g` = 0.25 vCPU/1GB）；单 correlator 垂直扩展（文档明说 stateful 应用不适合 auto-scaling）。
- **定性**：correlator 是可随意杀掉重建的无状态微服务，K8s 原生运维零状态基础设施；代价是有状态分析重启即失忆。告警实例交业务库去重，是该平台吸收重复触发的一项业务语义选择。
- 资料：[Introduction](https://cumulocity.com/docs/streaming-analytics/introduction-analytics/)、[EPL apps](https://cumulocity.com/docs/streaming-analytics/epl-apps/)、[Troubleshooting](https://cumulocity.com/docs/streaming-analytics/troubleshooting/)

### 3.5 Losant——「引擎无状态，联动状态 KV 化」（C 路线代表）

- **状态形态**：workflow 引擎是纯执行器；跨运行状态全部显式收敛为 **Workflow Storage KV**（Storage: Get/Set 节点）。**latch / on-change / throttle 的 per-device 状态做成节点内置能力**——三个节点都有 identifier 字段（通常填 deviceId）按 key 分桶：On Change 存「上一次值+时间」（7 种变化判定）、Throttle 存「上次放行时间」、Latch 存 latched 布尔。
- **持久化**：云端 = 托管 KV，写立即生效、跨 workflow 版本共享、与部署解耦；无 checkpoint 概念，就是节点执行时同步 KV 读写。**TTL：storage key 跟着组织数据保留策略惰性过期**。Edge 侧 = 挂载卷上一个 `losant-edge-agent-store.db` 单文件（推断 SQLite 类），workflow 定义 + storage KV + 断网缓冲消息一起落盘。
- **恢复**：**On Change 首次运行走「无变化」分支**（文档明说）——状态丢失后恢复的首批数据被静默吞掉，宁可漏报不误报，at-most-once 倾向。单次执行 60s 硬超时，无重试承诺。
- **配额**：workflow storage 单 workflow **16MB / 16384 key**，单值 16KB；globals ≤100；throttle 最快 10 次/秒。
- **定性**：**「per-device identifier 分桶 + 小 KV + TTL + 硬配额」**把跨运行状态显式化，但 16MB / 16384 key 的总配额同时限定了单个 workflow 的适用规模。该形态可作为容量比较样本，不能据此推导本项目的状态后端。
- 资料：[Workflows overview](https://docs.losant.com/workflows/overview/)、[Throttle](https://docs.losant.com/workflows/logic/throttle/)、[Latch](https://docs.losant.com/workflows/logic/latch/)、[On Change](https://docs.losant.com/workflows/logic/on-change/)、[GEA usage](https://docs.losant.com/edge-compute/gateway-edge-agent/usage/)

## 5. 研究观察与使用边界

1. A—D 是对本次样本的研究归类，不是架构成熟度排序。单个产品的实现受部署形态、语义承诺、产品配额和商业边界共同影响，不能从某一案例直接推导本项目应采用的恢复模型。
2. 样本中多次出现「告警实例或可观测终态进入业务库」：ThingsBoard 用 `alarm` 表查询活动告警，JetLinks 用 `alarm_record` 条件更新，Cumulocity 按 `(source, type)` 聚合告警。这说明业务终态可以吸收部分重复，但不代表计算状态、timer 与动作投递可以合并为同一存储问题，也不足以称为全行业共识。
3. OpenRemote 的首轮动作抑制、JetLinks 读取设备最新值、openHAB 事件携带 oldState，以及 Losant/AWS IoT Events 的 per-key KV，均只证明对应平台在其语义边界内的选择；本文不据此提出首轮点火、前值外包或 PG 小 KV 等项目方案。
4. 本项目现行方案仅作定位提示：Scene 使用异步 Kafka compacted full `scene_state` 并执行 state-before-event 恢复，动作写 PG Action Outbox 并以 `effectId` 收敛重复，Runtime 只有 Scene 与 Flink。完整约束、失败窗口和未冻结事项按职责见顶部主规格总纲与 Runtime 调度分章。
5. 早期材料中的 Canonical bounded replay、独立 Go CF、`SourceSeries/stateNode`、RocksDB snapshot+tail 和 PG timer 属于已否决的历史候选，不是本文结论，也不得由这些竞品事实恢复为现行方案。

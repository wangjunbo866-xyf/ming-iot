## 1. 控制面实体与稳定身份

### 1.1 `SceneTemplate` 是可选工件

`SceneTemplate` 只服务于控制面编排、参数化和复用。一个场景可以由模板创建多个 Binding，也可以不经模板直接创建 Binding。

`SceneTemplate` 不具备运行时状态身份：

- 不进入 Scene state key、Actor key、timer identity 或动作幂等身份；
- 不因模板复用而让不同 Binding 共享状态；
- 模板编辑不能隐式把既有 Binding 的 owner、状态或动作身份迁到另一空间。

### 1.2 `SceneBinding` 是稳定的配置与运行时实体

每个可执行场景都必须落为一个 `SceneBinding`，并编译为 enabled `BindingCtx`。其约束如下：

- `bindingId` 是稳定且不可复用的身份；编辑、启停和重新发布不创建新的运行时身份；
- owner `tenantCode` 与 `projectId` 在创建时确定，`projectId` 不允许原地变更；跨 project 迁移必须禁用或删除旧 Binding，再以新 `bindingId` 创建新 Binding；
- `configRevision` 只用于 current 配置收敛、兼容性判断和审计，不进入 state key、partition key、timer identity 或动作身份；
- 不同 Binding 独立持有状态；同一模板派生出的多个 Binding 也不共享状态；
- 运行时状态身份固定为 `(tenantCode, bindingId, evaluationSubjectKey)`。

`BindingCtx` 是某个 enabled `SceneBinding` 的当前编译结果，包含求值、Scope、参数依赖和 target resolver 所需的只读 metadata。它是 ProjectIndex 内存内容，不是新的业务实体。

## 2. 组织轴、Scope 与当前 `SubjectContext`

### 2.1 V1 只承认三条组织轴

```text
tenant -> project -> device
tenant -> project -> area -> device
tenant -> product -> device
```

由此冻结以下边界：

- 跨服务租户身份使用 `tenantCode`；
- `projectId` 是每个 Binding 的必填 owner 和强隔离边界；不存在 tenant-wide Binding anchor；
- area 是 project 内的可选树形选择器；一台设备最多只有一条当前有效 area path；
- product 是 tenant 级目录，与 project 轴正交；product selector 的结果必须再与 Binding owner project 相交；
- device 使用稳定内部 `deviceId` 参与 subject identity；
- V1 不允许 source、evaluation subject、Scope target 或 action target 跨越 Binding owner project。

`ScopeSelector` 只支持 project all、area exact/subtree、product、fixed device，以及这些条件在同一 project 内的有界组合。任何 selector 都先与 `(tenantCode, projectId)` owner 边界相交；不能借 product 或 fixed subject 绕过 project 隔离。

### 2.2 Scope、计算主体与参数来源必须分离

三个解析职责不能互相代替：

```text
ScopeSelector
  决定哪些设备适用该 Binding

EvaluationSubjectResolver
  决定状态与动作归哪个 evaluation subject 所有

ArgumentSource
  决定一个参数允许由哪个 source subject 的事实更新
```

V1 冻结：

- `EvaluationSubjectResolver = MATCHED_DEVICE | FIXED_DEVICE | FIXED_AREA | PROJECT`；
- `ArgumentSource = SELF | EVALUATION_SUBJECT | FIXED_SUBJECT`。

`MATCHED_DEVICE` 从 current Scope 命中的设备得到 target；其余 resolver 从 Binding owner project 内的固定 device、固定 area 或 project 得到 target。解析失败、target 不存在或 target 跨 project 时整条 lookup 失败。

`ArgumentSource` 编译为每个 argument 的 source predicate：

- `SELF` 只接受本次 current Scope 命中的 typed source subject；
- `EVALUATION_SUBJECT` 只接受与已解析 `evaluationSubjectKey` 相同的 source；
- `FIXED_SUBJECT` 只接受 Binding 中已编译的固定 typed source identity。

source identity 校验是 exact fact posting 命中后的独立步骤；`sourceSubjectKey` 不得拼入或替代 `(factType, factKey)`。

### 2.3 area path 语义

`areaPath` 是从 project 内根 area 到当前 area 的有序稳定 area identity 序列。本契约只依赖序列语义，不冻结数据库字符串编码：

- area exact：设备当前 path 的末端 area 等于 selector area；
- area subtree：selector path 是设备当前 `areaPath` 的前缀；
- 不在 area 中的设备没有可用于 area selector 的当前 path，但仍可被同 project 的 project、product 或 fixed-device selector 匹配；
- selector path 与设备 path 必须属于同一 tenant/project，否则控制面拒绝发布，运行时拒绝匹配。

### 2.4 current `SubjectContext`

`SOURCE_DELTA` 不冻结 Product、Project 或 Area 归属。source lane 在处理时从 partition-local 有界 active-subject cache 取得 current `SubjectContext`；首次触达、rebalance 后缺失或 version gap 时，从 Things current store 懒加载或收敛。

下表描述逻辑读取视图，不是 Protobuf 或 DDL 字段定义：

| 逻辑信息 | 语义 |
| --- | --- |
| `sourceSubjectKey` | typed、tenant-local 的稳定 source identity |
| `subjectType` / `entityId` | 当前主体类型及其稳定实体身份 |
| `projectId` | 当前强隔离边界 |
| `deviceId` | device subject 时的稳定内部设备身份 |
| `areaPath` | device/area subject 当前有效的有序 area path（可无） |
| `productId` | device subject 当前产品（可无） |
| `aggregateVersion` | 当前组织/关系记录的单调版本；用于生命周期乱序与 applicability guard，不是配置生效版本 |

`tenantCode` 来自 envelope 外层隔离身份，不在 tenant-local subject key 内重复编码。context 缺失、读取失败或无法验证 tenant/project 时，整条 `SOURCE_DELTA` retry；耗尽有界重试后 fail closed/quarantine，不能依据旧 payload 猜测 Scope，也不能跨 project matching。

`SubjectContext` 只解析处理时的 current scope，与 `SceneEvent.processingContext`
中的 `processingNamespace/processingMode` 正交。当前归属变化可以改变 Scope
匹配结果，但不得推断、替换或把非 `LIVE` 输入升级为 `LIVE`。

## 3. PG、控制流与 ProjectIndex

### 3.1 唯一控制面真源

PG current `SceneBinding` 是配置真源。一次创建、修改、启停或删除必须在同一 PG 事务中：

1. 更新 current Binding，并递增该 Binding 的 `bindingConfigRevision`；
2. 递增 owner `(tenantCode, projectId)` 的 `projectConfigRevision`；
3. 将本次 `projectConfigRevision` 写入该 Binding current row 的 `lastChangedProjectRevision`；
4. 写 Binding lifecycle Outbox，记录稳定 event identity、owner、Binding identity、两级 revision 和操作类型。

以上是逻辑事务契约，不指定表名、列名或 DDL。Outbox 至少一次投递 Kafka `scene_binding_lifecycle` control stream，Kafka key 固定为 `(tenantCode, projectId)`，使同一 project 的事件共置。

```text
PG current SceneBinding + lifecycle Outbox
                    |
                    v
Kafka scene_binding_lifecycle control stream
                    |
                    v
Runtime node: (tenantCode, projectId) -> ProjectIndex
```

每个 Runtime 节点使用自己的配置 consumer group 接收 `scene_binding_lifecycle` 的全部 partitions；不能让多个节点共享一个只把配置事件交给其中一台节点的 consumer group。Kafka key 不足以证明并发 relay 的发送顺序，consumer 必须执行 project revision gate：

- event `projectConfigRevision` 小于或等于本地 `installedProjectRevision` 时，按旧/重复事件忽略；
- event 大于 `installedProjectRevision + 1` 时视为跳号，只 rebuild 对应 ProjectIndex；
- 增量应用前读取并验证 PG current row；若 `lastChangedProjectRevision` 已越过该 event，不能用未来 row 冒充该 revision，必须 rebuild；
- 编译失败、未知 Binding 或周期对账不一致同样只 rebuild 受影响 ProjectIndex。

Kafka control stream 传播“current 配置发生了变化”，不承载不可变执行发布物，也不定义某条 data record 应使用哪个配置版本。

`scene_binding_lifecycle` 与显式 reinit 都是 **no-state-value control**：它们只能
安装配置、close/reset 内存 state、发送 tombstone，并标记
`next-live bootstrap`。close/reset 必须取消已有 timer slot/handle，但它们不得读
current facts、构造 non-tombstone 业务 state、执行 predicate/FSM，或创建、arm、
推进、fire timer/Alarm/Action Outbox。下一条通过
数据面门禁的 `production + LIVE` `SceneEvent` 才可在其 handler 内惰性
bootstrap；控制流本身不是立即业务求值触发器。

### 3.2 ProjectIndex 的可见性契约

ProjectIndex 是按 `(tenantCode, projectId)` 隔离的内存索引。对读取者而言，每个已安装版本都是 project-scoped immutable generation：

- 更新先形成完整新 `BindingCtx`、scope postings 和 trigger dependency postings；
- 安装时在 project 级写锁内完成完整换代或等价的原子更新；
- 一个读取只能看见完整旧 generation 或完整新 generation；
- 从第一个 `factDelta` matching 到全部 evaluation target 分组完成，读取者始终持有同一个完整 generation/read view；
- generation 损坏或没有可验证版本时，该 project retry/fail closed，禁止在线拼接 PG/Redis 查询结果或返回局部 posting。

这里的 generation 只是本节点的完整内存读视图，不是需要持久化、路由或进入 state identity 的控制面发布工件。

当前基线允许每个 Runtime 节点缓存全部 enabled Binding 的编译配置和 matching metadata，但 ProjectIndex 始终按 project 组织。处理某个 data partition/project 不要求该 partition 的 Actor 缓存全租户设备、全量 telemetry、其他 partition 的 Actor state 或 rule × device 展开结果。Actor state/timer 仍按 `scene_event` partition 分片。

本节只冻结 ProjectIndex 与 matching metadata 的组织边界；per-partition active-state registry、
Actor/timer ownership 与关闭范围见
[Runtime 调度分章 §§3～4](Scene%20Runtime%20调度、分片与故障转移.md#runtime-components)。

### 3.3 数据面 `ProcessingContext` 前置门禁

所有 interest filtering、scope/index lookup 和 candidate matching 的前置条件，是输入
已通过受信任 `ProcessingContext` gate。`ProcessingContext` 必填且包含
`processingNamespace` 与 `processingMode=LIVE|BACKFILL|REPLAY`；它只能继承自
主规格列明的受信入口，不得由 topic 名、到达延迟、event/device time
或设备 payload 推断。只有通过该门禁、将要被 Admission 规范化的 production+LIVE
输入才会获得 `SceneEvent.identityAlgorithmVersion=SCENE_ID_V2`；BACKFILL 在此之前
bypass，不要求 Canonical 输入伪造 Scene identity version。普通 redelivery 必须原样
保留其已有 context/version。

生产 Scene matching 的决策顺序冻结为：

1. 在 tenant/fact interest filter 之前验证 ProcessingContext 来源、枚举值和
   namespace/mode 组合；
2. `production + BACKFILL`（在线补传/历史 output）与
   `backfill/<jobId> + BACKFILL`（显式 job）均在 candidate matching 前
   deterministic bypass，不查 ProjectIndex、不写 `scene_event`、不生成逐规则
   skip 或任何 live effect；
3. `replay/<id> + REPLAY` 与任何 `shadow/<id>` 不进入生产
   `scene_event/state/outbox` 或 production matching；
4. 只有 `processingNamespace=production && processingMode=LIVE` 可由 Admission
   盖章 `SCENE_ID_V2`，在 SceneEvent version 二次校验后进入 interest filter 和
   `TriggerPosting` 求交；
5. 缺失、未知、表外 namespace/mode 组合或来源不可信时 fail closed，
   quarantine/告警，禁止默认或降级为 `LIVE`。

Scene V1 不实现隔离 replay evaluator。上述 `REPLAY` 规则是生产副作用
禁令，不是可在当前 Runtime 中执行场景回放的能力声明。

## 4. 冻结的 matching 管线语义

### 4.1 统一 `TriggerPosting` 域上的匹配管线

为避免把 Binding 集合、argument posting 集合和 target 集合直接求交，matching 只在统一逻辑元素域上过滤。`TriggerPosting` 的逻辑形态为：

```text
TriggerPosting = (
  bindingId,
  argId,
  sourcePredicate,  // 编译后的 ArgumentSource
  scopePredicate,   // 编译后的 ScopeSelector
  targetResolver    // 编译后的 EvaluationSubjectResolver
)
```

这不是 Protobuf 或内存 struct 定义，只规定一个 posting 必须能完成哪些判断。reverse-dependency index 固定为：

```text
ExactTriggerIndex[(factType, factKey)] -> set<TriggerPosting>
```

其中 key 只有精确 `(factType, factKey)`。`sourceSubjectKey` 是取得 posting 后交给 `sourcePredicate` 的输入，不是 index key 的第三维。

设 `PC` 为 `S` 公共 envelope 中的 `ProcessingContext`，`IV` 为其
identity algorithm version，`G` 为同一次完整
ProjectIndex read view，`S` 为 `SOURCE_DELTA`，`C` 为 source 的 current
`SubjectContext`，`d` 为其中一个 `factDelta`。可实施的匹配管线固定为：

```text
require Trusted(PC) &&
        IV == SCENE_ID_V2 &&
        PC.processingNamespace == production &&
        PC.processingMode == LIVE

P0 := G.ExactTriggerIndex.lookup(d.factType, d.factKey)

P1 := filter P0 where
      G.BindingCtx[p.bindingId] exists and is enabled

P2 := filter P1 where
      SourceMatches(
        S.sourceSubjectKey,
        p.sourcePredicate,
        C,
        p.targetResolver
      )

P3 := for each p in P2 where current tenant/project is applicable:
      ScopeAndTargetPlan(
        p.scopePredicate,
        p.targetResolver,
        C,
        G.BindingCtx[p.bindingId]
      )
      -> (p, targetPlan)

Matches := for each (p, targetPlan) in P3:
  for each evaluationSubjectKey in ResolveAndValidateTargets(targetPlan):
    emit (p.bindingId, p.argId, evaluationSubjectKey)
```

`require` 失败时不得执行 `P0`。正常 Admission 已只会发布
`production + LIVE` `SOURCE_DELTA`；此处是对错路由、错误 producer 和
quarantine 重投的二次门禁，不能用 Topic 所在位置代替 wire 校验。

`SourceMatches` 按 §2.2 校验 `SELF | EVALUATION_SUBJECT | FIXED_SUBJECT`；对 `EVALUATION_SUBJECT`，它可无副作用地使用同一个 compiled target resolver 验证 source identity，但只有通过 Scope、project 和 target applicability 后才输出 resolved target。普通 target plan 解析为零或一个 target；§4.5 的显式有界特殊路径可以解析为多个 matched-device targets。Scope/target 不适用时该 posting 不产生 match；lookup、planning 或 resolver 本身出错则按 §4.4 处理为整条失败，不能当作“不匹配”。同一个逻辑参数的结果仍以 `(evaluationSubjectKey, bindingId, argId)` 去重。

### 4.2 `TRIGGER` 与 `CONTEXT_ONLY`

- `TRIGGER`：该 argument 的精确事实变化可以启动该 Binding 的本次求值。只有 `TRIGGER` argument 被编译为 `TriggerPosting` 并进入 reverse-dependency index；同一 bundle 内一个或多个 `TRIGGER` 命中仍只让该 Binding 求值一次。
- `CONTEXT_ONLY`：该 argument 不生成 `TriggerPosting`、不进入 reverse-dependency index，也不因自身变化进入候选或主动 fanout。只有其他 `TRIGGER`、Schedule 或数据面 `SubjectLifecycle` 已要求求值时，Actor 才从已维护的 `SceneBindingState` 或 current latest store 读取它；这里不包含 control-only 的 `scene_binding_lifecycle` 或显式 reinit。

控制面必须明确标注每个 argument 的 `argumentMode=TRIGGER|CONTEXT_ONLY`；
缺省或含糊的 argument mode 不得发布。它不是输入的 `processingMode`，
也不能改变 §3.3 的处理模式门禁。不得为 `CONTEXT_ONLY` 建“仅更新不求值”的隐藏 reverse posting，否则仍会制造被禁止的 source-to-target fanout。

#### 4.2.1 完整条件依赖与显式上下文

产品编辑器可以减少普通用户的配置负担，但不得用条件顺序改变规则语义：

- 对普通“当完整条件成立时执行动作”的规则，完整条件谓词引用的每个动态 argument 都默认且必须
  发布为 `TRIGGER`。`A > 30 AND B = CLOSED` 中 A、B 都能让谓词最后成立，不能默认只给第一个
  条件触发权；`OR`、嵌套括号同理；
- `CONTEXT_ONLY` 只用于产品/DSL 已经显式区分“触发表达式”和“求值时附加门禁”的配置，例如
  `WHEN A.temperature changes IF B.door = CLOSED`。此时 B 的变化有意不主动求值；这与
  `WHEN (A.temperature > 30 AND B.door = CLOSED) BECOMES_TRUE` 不是同一种业务语义；
- 若存在 rolling 或有状态算子，还必须按 §4.2.2 计算强制触发依赖闭包。用户不能把强制触发依赖
  降为 `CONTEXT_ONLY`；同一 argument 同时命中触发表达式与上下文门禁时 `TRIGGER` 优先；
- 编辑器保存或 API 发布前必须把最终模式逐 argument 写入 Binding。Runtime、ProjectIndex 编译器和
  restore 路径不得根据“第一个条件”、JSON/map 遍历顺序或表达式文本临时猜测模式。

因此，UI 若要提供“只由某个条件触发”的高级能力，必须把它展示为显式 `WHEN ... IF ...` 语义并说明
IF 条件变化不会触发；不得把普通复合条件悄悄降级为一个 `TRIGGER` 加若干 `CONTEXT_ONLY`。

#### 4.2.2 发布触发依赖闭包

发布编译器必须从规范化表达式 AST 计算：

```text
RequiredTriggerArgs =
    OrdinaryEvaluationPredicateDependencies
  ∪ RollingSampleDependencies
  ∪ EdgeChangeObservedDependencies
  ∪ DurationPredicateDependencies
  ∪ DebounceObservedDependencies
  ∪ HysteresisValueDependencies
  ∪ FrozenExtensionTransitionDependencies
```

`OrdinaryEvaluationPredicateDependencies` 是普通完整条件谓词引用的全部动态 argument；显式
`WHEN ... IF ...` 中只有 WHEN/触发表达式属于该集合，IF 附加门禁只作上下文。其余 dependency 是
算子状态输入表达式引用的动态 argument，不包括阈值、窗口长度等常量配置。Cooldown 由已接受
transition/effect 启动并由 Timer 清理，不新增数据 argument；Timer 本身也不是 argument。
Script、Alarm/FSM 仍处于扩展边界，只有其状态迁移 ABI 冻结后才能填入最后一项，不得由实现自行猜测。

闭包中的每个 argument 都必须以 `TRIGGER` 发布并编译为精确 `TriggerPosting`；外部 API 若提交
`CONTEXT_ONLY` 冲突配置，发布必须拒绝，而不是静默生成错误规则。数据驱动 Binding 必须至少有
一个 `TRIGGER`；只有 Schedule、Timer、数据面 SubjectLifecycle 等已冻结非数据 trigger 的专用
Binding 可以不依赖数据 argument 发起求值。

括号决定状态作用域；是否显式建模为附加门禁决定状态作用域外参数能否是 `CONTEXT_ONLY`：

```text
WHEN DURATION_2M(A > 30) COMPLETES IF B = CLOSED
  A = TRIGGER；B 可为 CONTEXT_ONLY
  含义：只由 A 推进两分钟计时，并在完成时检查 B 当时是否关闭；B 变化不主动求值

WHEN DURATION_2M(A > 30 AND B = CLOSED) COMPLETES
  A = TRIGGER；B = TRIGGER
  含义：A 与 B 必须共同连续满足 2 分钟
```

第二种语义中，B 在计时期间变为 `OPEN` 必须立即进入该 Binding 并取消 Duration；只在到期时读取
B 的最新值，无法证明 B 在整个区间内未发生过中断。完整矩阵及 Edge/Change、Debounce、Hysteresis
约束见[《场景有状态计算规范》§4.1.1](场景有状态计算规范.md#stateful-trigger-dependency-closure)。

#### 4.2.3 完整谓词上升沿动作门

`TRIGGER` 只授予“启动一次求值”的权利，不等于“本条输入独立执行一次动作”。V1 普通的
“条件满足则执行动作”必须把完整条件谓词编译为一个共享的 `Edge(RISING)` 动作门；不得把每个
argument 分别编译成动作入口，也不得用时间窗口把相邻输入猜测为同一批。

以 `P = (A > 30 AND B = CLOSED)` 为例，A、B 都是 `TRIGGER`。它们的独立消息按同一个
`(tenantCode, bindingId, evaluationSubjectKey)` lane 串行求值，并共享 P 的
`previousPredicate`：

| 上一 accepted P | 本轮 P | 结果 |
| --- | --- | --- |
| `false` | `false` | 无 transition、无动作 |
| `false` | `true` | 恰好一个 `RISING` transition，形成一次完整 action set |
| `true` | `true` | 无 transition、无动作 |
| `true` | `false` | 更新 baseline；普通 rising 动作不执行 |

例如 A 先变成 31℃、B 仍为 `OPEN` 时只完成一次 `false -> false` 求值；随后 B 变为 `CLOSED`
完成 `false -> true`，执行一次动作；之后 A 再变成 32℃虽然仍会求值，但只得到 `true -> true`，
不得再次创建 Outbox。若 A、B 位于同一个 source bundle，§4.2 的“每 Binding 每 bundle 最多求值
一次”仍先去重，再执行同一个动作门。

动作门属于既有 `SceneBindingState.operator states`，复用 Edge 的
`initialized + previousPredicate`、冷启动 `BASELINE_ONLY` 和 Action Outbox 接受顺序：带动作的
`false -> true` 必须先成功 commit 完整 Outbox，随后才能接受 `previousPredicate=true`；同一 lane
中的下一条 Trigger 不得越过。`effectId` 只负责同一逻辑 transition 重试及下游幂等，不能把两个
不同 Trigger 输入事后猜成同一次上升沿。

该约束不新增 Kafka Topic、PG 状态表或 durable predicate gate。Edge 状态随现有完整
`scene_state` image 异步 best-effort 发布；V1 只承诺同一 active owner/lane 正常持有 accepted state
期间，一个 `false -> true` 区间产生一次动作。崩溃、rebalance 或恢复副本滞后造成的极少量重复或
漏触发仍属于既有 best-effort 残余窗口；缺 state 时按 `BASELINE_ONLY` 只建立当前 baseline，不补发
历史动作。若未来要求跨上述窗口严格一次，必须另立 durable gate 设计，不能宣称由本协议覆盖。

### 4.3 V1 只允许精确 trigger fact

V1 的 trigger dependency key 只能是精确、强类型的 `(factType, factKey)`。发布时必须拒绝：

- whole-record change、any-property-change 或 any-event；
- 空 key、前缀、正则、glob、通配 product/point/property；
- 运行时才枚举字段的动态 trigger；
- 不能给出有界 payload、类型和基数约束的复合事实。

只有当上游已经把“整条记录/一组字段发生变化”建模为一个显式、有界、强类型事实，并为它分配精确 `(factType, factKey)` 时，Binding 才能依赖该事实；此时 matching 的仍是该精确事实，而不是 whole-record 或 wildcard 特例。

### 4.4 一条 SOURCE 的完整只读匹配

同一条 `SOURCE_DELTA` 的处理顺序固定为：

```text
1. 验证公共 ProcessingContext 的受信来源与 production + LIVE 组合
2. 解析并验证 current SubjectContext、tenantCode 与 projectId
3. 取得该 project 的一个完整 ProjectIndex generation/read view
4. 对 SOURCE_DELTA.factDeltas[] 全部执行 exact (factType, factKey) TriggerPosting lookup
5. 在统一 TriggerPosting 域依次执行 enabled、ArgumentSource/sourceSubjectKey、current Scope/project 与 target resolver 校验
6. 以 (evaluationSubjectKey, bindingId, argId) 去重并合并
7. 按 evaluationSubjectKey 形成完整 target bundle，原样复制 ProcessingContext
8. 释放 read view
9. 以 evaluationSubjectKey 与 sourceSubjectKey 是否相等分类：相等形成 same-subject 完整 bundle；不等形成 target-keyed LINKED_DELTA
```

第 9 步只冻结 matching result 与 payload 分类：
`evaluationSubjectKey == sourceSubjectKey` 才形成 same-subject 完整 bundle；
`evaluationSubjectKey != sourceSubjectKey` 一律形成 target-keyed `LINKED_DELTA` 并经 Kafka，
即使 hash 到同一 partition 或由同一 Runtime 承载，也不得走本地捷径。递交与 completion 的执行协议见
[Runtime 调度分章 §5](Scene%20Runtime%20调度、分片与故障转移.md#runtime-normal-completion)。

“完整 target bundle”指同一 source record 对同一 evaluation target 的全部匹配 argument delta，而不是复制场景全部参数。Actor 应用完整 bundle 后，每个 Binding 最多求值一次；未变化参数继续来自该 Actor 的 `SceneBindingState` 或按主规格从 current latest store 初始化。

lookup timeout、posting/BindingCtx 不一致、generation 损坏或内部不变量失败时：

- 不得返回已经查到的 binding/argument；
- 不得先发送部分 same-subject bundle 或 cross-subject `LINKED_DELTA`；
- 整条 `SOURCE_DELTA` 先有界 retry，耗尽后 fail closed/quarantine 并告警。

bundle entries/bytes 超限时不拆包、不静默裁剪、不让 Actor 对半包求值；按主规格对完整 source 或完整 target bundle fail closed。Kafka producer 最终失败等交付窗口继续服从
[主规格 §13](场景联动%20Runtime%20主规格总纲.md#13-kafka-交付事务与失败窗口)，
不由本契约扩张为跨 target 原子事务。

### 4.5 固定 source 主动展开 matched targets

普通 `SELF` trigger 或固定/area/project 单 target 走 §4.1 的直接 resolve。只有 `ArgumentSource=FIXED_SUBJECT + TRIGGER` 且 `EvaluationSubjectResolver=MATCHED_DEVICE` 可能要求从一个固定 source 主动展开多个 matched devices；这是有界特殊路径，不是 ProjectIndex 常规 posting lookup 的隐式副作用。

处理顺序固定为：

```text
1. 由 exact (factType, factKey) 命中 TriggerPosting
2. 校验 sourceSubjectKey 等于 compiled FIXED_SUBJECT，BindingCtx enabled 且 owner project 一致
3. pin 同一 project 的完整 BindingCtx/ProjectIndex read view
4. 通过 Things current membership API 有界枚举 Scope 内 matched devices
5. 对结果执行 owner project、current Scope、稳定 device key 排序与去重
6. 在发送前形成完整且不超过硬上限的 target list
7. 按 evaluationSubjectKey 形成完整 payload：与 sourceSubjectKey 相等时为 same-subject bundle；不等时为 target-keyed LINKED_DELTA
```

ProjectIndex 不保存设备全集，也不得把 Scope 在发布期展开为 rule × device postings。控制面只有在 Binding 声明显式 fanout limit 且不超过平台硬上限时才允许发布该路径；未声明、估算超限或巨大 fanout 默认拒绝。运行时任何 membership 查询/分页不完整、失败或结果超限，都使整条 `SOURCE_DELTA` retry/fail closed；不允许发送已读到的前 N 个 target。

`FIXED_DEVICE`、`FIXED_AREA` 或 `PROJECT` resolver 都是同 project 的单 target，正常 resolve 后形成一个 target bundle，不调用 matched-device 枚举。要求无界或大群体稳定展开时，应改用 `CONTEXT_ONLY`、缩小 Scope/limit，或交给专用批任务/Flink。

## 5. 物理路由边界

`scene_event` 的 envelope/wire/schema 由
[主规格 §5](场景联动%20Runtime%20主规格总纲.md#5-scene_event-合约)唯一拥有；
本契约只拥有 matching result、payload 分类与 applicability。same-subject/cross-subject 的递交与
completion 执行唯一见
[Runtime 调度分章 §5](Scene%20Runtime%20调度、分片与故障转移.md#runtime-normal-completion)。

场景计算只有一个 Scene Runtime。`SOURCE_DELTA` 与 `LINKED_DELTA` 是同一物理 `scene_event` Topic 中统一 envelope 的两种类型，不是两套 Runtime 或两个 Topic：

```text
Canonical record (trusted ProcessingContext)
  -> Scene Event Admission
       -> mode gate before interest/candidate matching
  -> scene_event / SOURCE_DELTA
  -> Scene Manager + ProjectIndex matching
       -> same-subject complete bundle (evaluationSubjectKey == sourceSubjectKey)
            -> current subject Actor lane
       -> cross-subject target-keyed LINKED_DELTA (evaluationSubjectKey != sourceSubjectKey)
            -> scene_event -> target subject Actor lane
  -> PG Action Outbox
  -> async Kafka compacted scene_state
```

本图只解释 matching result、payload 分类与 applicability，不重新定义 wire；same-subject bundle 与
cross-subject `LINKED_DELTA` 怎样进入当前 owner、何时完成，仍由上述 Runtime 调度分章定义。

约束：

- 生产 `scene_event` 的公共 envelope 必须携带受信任的
  `processingNamespace=production && processingMode=LIVE`；
- 一条 admitted Canonical record 最多形成一条批量 `SOURCE_DELTA`，不按点位拆成多条物理消息；
- `SOURCE_DELTA` 按 `(tenantCode, sourceSubjectKey)` 路由到 source lane；
- `evaluationSubjectKey != sourceSubjectKey` 时，按 evaluation target 汇总为 target-keyed
  `LINKED_DELTA` 并经 Kafka 按 `(tenantCode, evaluationSubjectKey)` 路由；即使 hash 到同一
  partition 或由同一 Runtime 承载，也不得走本地捷径；
- `evaluationSubjectKey == sourceSubjectKey` 时形成 same-subject 完整 bundle，不产生 `LINKED_DELTA`；
- same-subject bundle 与 `LINKED_DELTA` 必须原样传播 SOURCE 的 `ProcessingContext`，
  目标 Actor 在应用 argument、bootstrap state 或注册 timer 前再次校验；
- `LINKED_DELTA` 是终端 bundle：不再次 reverse matching，也不递归产生新的 `LINKED_DELTA`；
- `scene_state` 是 Actor 的异步 Kafka compacted full state；它不是控制面配置，也不是同步 matching 索引。

### 5.1 `LINKED_DELTA` applicability guard

`LINKED_DELTA` 携带 source handler 匹配时读取的 `sourceAggregateVersion`。target handler 不重新 reverse matching，但在应用 bundle 前必须：

1. 校验公共 `ProcessingContext` 仍为受信 `production + LIVE`；失败时整个
   bundle fail closed/quarantine，不得执行以下 lookup；
2. 从 current ProjectIndex 校验每个 Binding 仍 enabled，并校验 source 与 evaluation target 的 tenant/project、current Scope 和 target resolver；
3. 对共享 area/project/fixed target，以 `sourceAggregateVersion` 检查该 source member 的 `lastAggregateVersion` 与 active guard；
4. incoming version 小于 guard 时把该 entry 作为 stale no-op；特别是较新 `REMOVE_MEMBER` 已被处理后，旧 `LINKED_DELTA` 不得复活 member；
5. 只有 incoming version 等于 guard 且 member active 时，才可按该本地 guard 继续应用；
6. guard 缺失、member inactive、incoming version 更高，或 state/member 不存在时，先从 Things current store 读取并验证 source/target current context、version 与 Scope；验证成功前不得应用 argument、推进 state 或 bootstrap member/BindingState，也不得把 `LINKED_DELTA` 本身当作 membership add；
7. 任一所需 index/context lookup 出错时，整个 target bundle retry/fail closed/quarantine，不能先应用其余 entry。

明确验证为 disabled、out-of-scope 或 stale 的 entry 是幂等 no-op；lookup 错误不是 no-op。该 version guard 只用于 current applicability 防护，不改变异步 target-lane 交付模型。

精确 envelope、key bytes、partition/hash 与 state schema 以主规格和后续协议工件为准。

## 6. 发布期正确性与容量门槛

### 6.1 overlap 必须拒绝

overlap comparison group 使用逻辑派生键，不新增持久实体：

```text
bindingFamilyKey =
  templateId  // 由 SceneTemplate 派生
  bindingId   // 不经模板直接创建的独立 SceneBinding

OverlapGroup = (
  tenantCode,
  ownerProjectId,
  bindingFamilyKey,
  evaluationSubjectSpace
)
```

`evaluationSubjectSpace` 是 compiled resolver 所能产生的 typed target 空间；它用于比较，不是新的运行时 identity。发布控制面只在同一 `OverlapGroup` 内比较 enabled Binding：若两个 Scope 可以命中同一 evaluation subject，则拒绝新发布，不能依赖下游 effect 去重容忍同一模板的重复 Binding。

比较至少覆盖 project all 与 area/product/device 组合、area exact/subtree 的包含或相交，以及 fixed/evaluation target 解析后的 subject space。检查所需 current membership 或关系读取失败、无法证明结果完整时，发布 fail closed，不能以 warning 代替拒绝。

直接创建的独立 Binding 以自身 `bindingId` 为 family，且自身只有一个 composite Scope；因此两个不同直接 Binding 属于不同 family，可以作为不同场景合法重叠。同理，不同 template family 可以匹配同一实体；它们保持独立 Binding、独立状态与独立业务效果。

### 6.2 candidate 与 fanout 预算

发布前必须基于编译后的 exact trigger postings、Scope 和 target resolver 估算：

- 每条 `SOURCE_DELTA` 的候选 BindingState 数 `c`；
- distinct cross-subject evaluation target 数，即 target-keyed `LINKED_DELTA` fanout `lambda`；即使 target 与 source hash 到同一 partition 或由同一 Runtime 承载也计入；
- source/target bundle 的 argument entries 与 bytes；
- fixed source 到 matched target、Schedule current-target 枚举和 action target 的最坏有界 fanout；
- project/tenant 累计 enabled Binding、posting 和 compiled `BindingCtx` 内存。

估算值超过产品硬上限时拒绝发布。运行时仍执行 per-tenant/project/event candidate cap、linked target fanout cap 和 bundle cap，防止 current membership 或数据分布变化突破发布期估算；超限 fail closed/quarantine，不返回前 N 个候选，也不发送前 N 个 target。

宽 Scope 只保存 project、area path、product、device 的符号 postings，不在发布时展开 rule × device。Schedule 的 current-target fanout 使用 Things current membership API 做有界查询、排序、去重与硬上限检查；ProjectIndex 不承担设备全集枚举。

## 7. 多点位上报示例

假设 current `SubjectContext` 为：tenant `T1`、project `P1`、device `D7`、area path `[A0, A5]`、product `M1`。一条设备上报在 Admission 过滤后形成一条 `SOURCE_DELTA`：

```text
processingNamespace = production
processingMode = LIVE
sourceSubjectKey = device:D7
factDeltas = [
  (PROPERTY, temperature, 31.2),
  (PROPERTY, humidity,    75),
  (PROPERTY, activePower, 6.2),
  (PROPERTY, voltage,     229)
]
```

当前完整 ProjectIndex generation 中有两个 enabled Binding：

- `B-climate`：owner `P1`，Scope 为 area `[A0]` subtree，evaluation target 为 matched device；`temperature` 与 `humidity` 都是 `ArgumentSource=SELF` 的精确 `TRIGGER`，area `A5` 的 setpoint 是 `ArgumentSource=FIXED_SUBJECT` 的 `CONTEXT_ONLY`；
- `B-load`：owner `P1`，Scope 为 product `M1` 且 area `[A0, A5]` exact，evaluation target 为 fixed area `A5`；`activePower` 与 `voltage` 都是 `ArgumentSource=SELF` 的精确 `TRIGGER`。

Manager 在同一个 read view 内匹配四个 fact delta：

```text
device:D7 same-subject target bundle
  B-climate.temperature = 31.2
  B-climate.humidity    = 75

area:A5 cross-subject target-keyed LINKED_DELTA
  B-load.activePower = 6.2
  B-load.voltage     = 229
```

结果是一个 same-subject 完整 bundle 和一个 cross-subject target-keyed `LINKED_DELTA`，而不是四条 source 消息或四条 linked 消息。`B-climate` 在完整 trigger bundle 应用后只求值一次；setpoint 没有 dependency posting，也不在该 `SOURCE_DELTA` 的 matching/bundle 中，Actor 在此次 trigger 已要求求值后才从 `SceneBindingState` 或 current latest store 读取它。`B-load` 到 area Actor 后也只求值一次。若 `D7` 的 current project 不是 `P1`、任一 trigger dependency 非精确，或四个事实未能在同一完整 generation 中完成 lookup，则不产生上述部分结果。

即使 `device:D7` 上报了与 area setpoint 同名、同类型的事实，也不会为这个 `CONTEXT_ONLY` argument 产生候选；reverse-dependency index 中根本不存在它的 `TriggerPosting`。

## 8. 明确不采纳的旧结论

以下内容不属于本契约，也不得由实现自行恢复：

- 持久化 Binding 发布快照或版本化运行时身份；
- 常驻的 Scope 到全量设备反向展开索引；
- 冻结的设备归属快照、ENTER/STAY/EXIT 归属状态机；
- Binding 配置与 Kafka data offset 对齐的生效屏障；
- group、tag 或其他未列入三条组织轴的 Scope；
- 独立 Go CF Runtime；普通 CF 计算属于同一个 Scene Runtime，高级事件时间计算属于 Flink；
- Canonical 历史回放恢复 Scene state；
- 把 `BACKFILL`/`REPLAY` 接入当前 Scene Runtime，或为 Scene V1 虚构 replay evaluator；
- Scene RocksDB/snapshot/tail 恢复；
- 以 PostgreSQL 普通 timer 行作为 duration/debounce/cooldown 的事实来源。

普通 Scene timer 的 handle 驻进程内，业务 timing state 随 `scene_state`；其业务语义仍由主规格与算子契约定义，partition ownership、执行和 revoke close 见
[Runtime 调度分章 §§3、6、8](Scene%20Runtime%20调度、分片与故障转移.md#runtime-components)。
已经接受且要求可靠延迟投递的动作进入 PG Action Outbox，其事务仍由主规格定义。

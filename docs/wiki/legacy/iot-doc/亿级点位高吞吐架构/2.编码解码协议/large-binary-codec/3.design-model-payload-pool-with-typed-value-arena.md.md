# 基于设备型号的 Typed Payload 预分配池设计
## 1. 背景
设备点表包含 `string`、`int`、`float` 三类值，不能用单一 `[]float64` 表达。新项目尚未上线，可以直接设计一套更适合高频时序写入的内部数据结构：

1. 元数据使用 `ProductID`、`DeviceName`、`ModuleID`、`PointID`、`SchemaRelease` 等轻量字段。
2. 点值不使用 `map[string]any` 长期流转。
3. 不使用 `[]string` 保存点名。
4. 不使用单一 `[]float64` 保存所有值。
5. 使用 `PointValueRef + Ints/Floats/Text arena` 表达混合类型点值。
6. 使用设备型号维度的 pool 复用 slice 底层数组。

这套结构的目标是让解析、校验、路由、写入之间流转的是低指针、低分配、生命周期明确的 payload。

## 2. 设计目标
1. 同时支持 `string`、`int`、`float` 点值。
2. 高频路径不携带点位字符串名，只携带 `PointID`。
3. 高频路径尽量避免 `map[string]any` 和 `[]any`。
4. string 点值写入 batch 局部 `[]byte` arena，使用 offset/length 引用。
5. payload 的所有权明确，避免 `sync.Pool` 提前归还导致数据污染。
6. sink 边界可以通过 schema dictionary 恢复 TDengine 列名和参数顺序。
7. 结构可以自然演进到 value ring buffer。

## 3. 核心数据结构
### 3.1 ValueKind
```go
type ValueKind uint8

const (
    ValueInt ValueKind = iota
    ValueFloat
    ValueString
)
```

`ValueKind` 表达的是 arena 存储形态，不是物模型原始 `DataType` 的一一映射。也就是说，多个物模型类型可以落到同一种存储形态：

1. `ValueInt`：所有整数类、bool、enum、timestamp 归一到 `int64` arena。
2. `ValueFloat`：float/double 归一到 `float64` arena。
3. `ValueString`：普通字符串写入 `Text []byte`，通过 `StringRef` 引用。

当前 module property 发布链路只允许标量类型，`struct` 和 `array` 会被拒绝。因此高频 TDengine property 路径只处理 `ValueInt`、`ValueFloat`、`ValueString`。

`null` 或“当前 decode 分支没有有效值”的点不生成 `PointValueRef`，也不进入任何 value arena。sink 拼 SQL 时只根据 `payload.Values` 拼列名和值，因此跳过该点即可实现“不写该字段”。本设计不引入单独的 null kind。

### 3.1.1 DecodeProperties 类型适配
`DecodeProperties` 中的 `vdata_type` 是二进制编码类型，例如 `U16`、`S16`、`U32`、`S32`、`20 Byte`。它不等于物模型 `Define.Type`。`ValueKind` 应在 schema 校验和归一化之后确定，而不是直接由 `vdata_type` 决定。

兼容路径可以继续沿用当前流程：

1. 二进制 decode 阶段只得到 `identifier -> rawValue`。
2. `VerifyProperties` 根据 `Model.Properties[identifier].Define.Type` 把 rawValue 归一成写入值。
3. typed payload 阶段根据 schema dictionary 中的 `PointMeta.Kind` 写入对应 arena。

高频 PUSH_DATA 路径不建议继续走这套 `map[string]any + VerifyProperties` 流程，而应使用 `PropertyPointPlan + DecodePropertiesIntoPayload + typed verifier`，在 decode 当场直接写入 `ModulePayload`。详细改造见：[属性 Typed Decode 与 Typed Verifier 改造设计](5.design-property-typed-decode-and-verifier.md)。

适配关系：

| 来源 | 当前 decode 输出 | 物模型类型 | ValueKind | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| `U16/S16/U32/S32` | `decimal.Decimal` 或可转数字 | `bool` | `ValueInt` | 按现有 iot 语义转成 `0/1` 或 int64。 |
| `U16/S16/U32/S32` | `decimal.Decimal` 或可转数字 | `tinyInt/smallInt/int/bigInt/*Unsigned` | `ValueInt` | 归一为 `int64`；当前 iot 校验逻辑也是 `cast.ToInt64E`。 |
| `U16/S16/U32/S32` | `decimal.Decimal` 或可转数字 | `enum` | `ValueInt` | 枚举以数字值写入。 |
| `U16/S16/U32/S32` | `decimal.Decimal` 或可转数字 | `timestamp` | `ValueInt` | 归一为毫秒时间戳或 TDengine 可接受的 int64。 |
| `U16/S16/U32/S32` | `decimal.Decimal` 或可转数字 | `float/double` | `ValueFloat` | 归一为 `float64`。 |
| `U32` 特殊版本字段 | `string` | `string` | `ValueString` | 例如版本号拼接出的字符串。 |
| `20 Byte/22 Byte/6 Byte` | `string` | `string` | `ValueString` | 设备型号、序列号、BCD 时间字符串等。 |
| `40 Byte/38 Byte/8 Byte` 当前只校验长度 | `nil` | 无有效写入值 | 不生成 descriptor | 不拼该列，不写该字段。 |
| `struct/array` | `map/slice` | `struct/array` | 不支持 | 当前 module property 发布应拒绝，不进入高频 TDengine property 路径。 |


因此，`ValueKind` 覆盖的是当前需要写入 TDengine 的有效点值。`40 Byte/38 Byte/8 Byte` 这类当前没有赋值的分支应在构造 payload 时跳过点位，后续拼 SQL 时自然不会出现对应字段。

### 3.2 PointValueRef
`PointValueRef` 是一个轻量 descriptor，只描述“哪个点位、什么类型、值在哪里”。

```go
type PointValueRef struct {
    PointID uint16
    Kind    ValueKind
    Index   uint32
}
```

含义：

1. `PointID`：eKuiper 根据 `ProductID + ReleaseID + SchemaBundle` 派生的本地紧凑索引。
2. `Kind`：值类型。
3. `Index`：指向对应 arena 的下标。

示例：

1. `Kind=ValueInt, Index=3`：值在 `payload.Ints[3]`。
2. `Kind=ValueFloat, Index=7`：值在 `payload.Floats[7]`。
3. `Kind=ValueString, Index=2`：字符串引用在 `payload.Strings[2]`。

### 3.3 StringRef
```go
type StringRef struct {
    Off uint32
    Len uint32
}
```

字符串真实字节保存在 `Text []byte` 中，`StringRef` 只记录 offset 和 length。

### 3.4 ModulePayload
```go
type ModulePayload struct {
    ModuleID      int64
    SchemaRelease int64
    Timestamp     int64

    Values []PointValueRef

    Ints    []int64
    Floats  []float64
    Strings []StringRef
    Text    []byte
}
```

`ModulePayload` 是单个 module 的点值容器，不重复保存产品和设备标识。产品和设备标识保存在外层 `ModulePayloadBatch` 中：

1. `ModulePayloadBatch.ProductID`：产品编码，字符串类型，不是产品表的自增主键或数据库主键。
2. `ModulePayloadBatch.DeviceName`：设备编码，字符串类型，对应设备表中的设备编码。
3. `ProductID + DeviceName` 可以确定设备唯一性。单独的 `DeviceName` 不应假设全局唯一。

因此本文中 `ProductID` 的语义统一为“产品编码”。如果后续代码里确实需要产品表主键，应另起名，例如 `ProductPK`、`ProductDBID` 或 `ProductTableID`，不要复用 `ProductID`。

`SchemaRelease` / `ReleaseID` 全链路统一使用 `int64`，与 `PayloadPoolKey.ReleaseID`、`PropertyDict.ReleaseID`、`SchemaBundle.Meta.ReleaseID` 保持一致。它是业务发布版本号，不是位掩码，不使用 `uint64`。

这个结构有几个重要特点：

1. `Values` 是 descriptor 列表，不直接存储任意类型值。
2. `Ints` 和 `Floats` 是无指针连续数组，GC 扫描成本低。
3. `Text` 是无指针连续字节池，所有 string 点值在一个 batch 局部内存块里。
4. `Strings` 是 offset/length 列表，不包含 Go string 指针。
5. 整个 payload 只有 slice header 中有少量指针，点位数量增加时不会制造海量小对象图。

### 3.5 ModulePayloadBatch
`ModulePayloadBatch` 是“一台设备一次上报”的所有权单位。属性 decode 阶段从设备型号 pool 借出一个 batch，把本次上报的所有 module 点值写入 `Modules`，然后把整个 batch 转交给 TDengine sink。sink 写入完成后再归还 pool。

```go
type ModulePayloadBatch struct {
    ProductID     string
    DeviceName    string
    SchemaRelease int64
    Timestamp     int64

    Modules []ModulePayload

    Blocks       []ModbusBlock
    BlockScratch []byte

    pool *ModelPayloadPool // internal, set by PayloadPoolManager.Borrow
}
```

字段分工：

1. `Modules`：最终要写入 TDengine 的 typed 点值。每个 `Modules[i]` 对应一个 module。
2. `Blocks`：本次上报 `DATA` 二进制块的临时索引表，只在 decode 阶段使用。
3. `BlockScratch`：`DATA.VALUE` 解码后的临时 byte arena，供 `Blocks` 用 offset/length 引用。

`Blocks` 和 `BlockScratch` 不属于最终写入数据。属性值一旦 decode 到 `ModulePayload.Values / Ints / Floats / Text` 后，sink 不需要再读取 `Blocks`。

因此 `DecodePropertiesIntoPayload` 返回前可以把 `Blocks` 和 `BlockScratch` 的长度清零，只保留底层 capacity 给 pool 复用。这样 batch 交给 sink 时不会携带原始二进制块内容；sink 只消费 `Modules` 中的 typed 点值。

`pool` 是内部所有权字段，由 `PayloadPoolManager.Borrow` 设置。调用方不直接保存 pool 引用，也不直接调用 `pool.Put(batch)`，而是在最终消费者完成后调用 `batch.Release()` 归还。

### 3.6 ModbusBlock 与 Blocks
`ModulePayloadBatch.Blocks` 不是点值缓存，而是“本次上报有哪些原始 Modbus 数据块”的 descriptor 列表。它的作用是让每个属性根据 `base-addr` 快速找到自己所在的数据块，避免当前 `DecodeProperties` 那种“每个属性都重新遍历 `DATA`，并可能重复 hex decode”的模式。

推荐结构：

```go
type ModbusBlock struct {
    ID      int32
    Offset  int32
    DataOff uint32
    DataLen uint32
}
```

字段含义：

1. `ID`：来自 `DATA[i].ID`，表示数据块覆盖的起始寄存器地址。
2. `Offset`：来自 `DATA[i].OFFSET`，表示数据块覆盖的寄存器数量。当前协议里一个寄存器按 2 字节计算。
3. `DataOff`：该数据块在 `BlockScratch` 中的起始 offset。
4. `DataLen`：该数据块在 `BlockScratch` 中的字节长度。

例如一次上报包含：

```go
DATA = []any{
    map[string]any{"ID": 100, "OFFSET": 20, "VALUE": "01020304..."},
    map[string]any{"ID": 200, "OFFSET": 10, "VALUE": "aabbccdd..."},
}
```

预处理后变成：

```go
batch.BlockScratch = append(decodedBlock100, decodedBlock200...)
batch.Blocks = []ModbusBlock{
    {ID: 100, Offset: 20, DataOff: 0,  DataLen: len(decodedBlock100)},
    {ID: 200, Offset: 10, DataOff: n1, DataLen: len(decodedBlock200)},
}
```

属性 decode 时：

```go
block, ok := findBlock(batch.Blocks, plan.BaseAddr)
if !ok {
    // 本次上报没有覆盖该点位，跳过，不生成 PointValueRef。
}

data := batch.BlockScratch[int(block.DataOff):int(block.DataOff+block.DataLen)]
valueOffset := (plan.BaseAddr - block.ID) * 2
decodeOneProperty(plan, data, valueOffset, modulePayload)
```

这里的 `valueOffset` 乘以 2，是因为当前协议中 `base-addr` 和 `OFFSET` 的单位是寄存器，一个寄存器对应 2 字节。

为什么不直接在 `ModbusBlock` 中保存 `Data []byte`：

1. `[]byte` 是 slice header，里面有指针；`[]ModbusBlock` 放入 pool 后会增加 GC 扫描和引用保留风险。
2. 如果 `Data` 直接引用 `deviceMsgInverter["DATA"]` 里的 `[]byte`，reset 后旧 slice header 可能仍在 `Blocks` 底层数组中，导致原始输入数据生命周期被拉长。
3. `DataOff/DataLen + BlockScratch` 让 `Blocks` 成为无指针 descriptor，reset 时只要把长度清零即可复用。

如果未来为了极致减少复制，确实想让 `ModbusBlock` 持有 `Data []byte`，则 `Reset` 时必须先 `clear(b.Blocks)` 再 `b.Blocks = b.Blocks[:0]`，否则旧元素里的 slice 指针可能继续保留旧数据。本设计默认不走这条路。

## 4. 设备型号预分配池
### 4.1 为什么按设备型号建池
同一设备型号的 module 和点位数量通常稳定。按设备型号预分配，可以避免每次上报都根据点位数量重新分配 slice。

这里的“设备型号”不能只理解为 `ProductID`。物模型是分版本的，同一个产品可能同时存在：

1. 默认当前版本：通过 `GetCurrentSchema` 获取。
2. 指定发布版本：通过 `GetReleaseSchema` 获取，例如设备 runtime meta 中存在 `SchemaReleaseIDOverride`。

因此 pool 的作用域必须和 `PropertyDict` / `SchemaBundle` 的运行时索引一致，推荐按下面的 key 建池：

```go
type PayloadPoolKey struct {
    ProductID string
    ReleaseID int64
    Scope     string
}
```

其中：

1. `ProductID`：产品编码，字符串类型，不是产品表主键。
2. `ReleaseID`：最终命中的 schema release。即使走 `GetCurrentSchema`，也要使用返回的 `bundle.Meta.ReleaseID`，不能使用请求 key 里的 `ReleaseID=0`。
3. `Scope`：当前 lookup scope，例如 `periodic_decode`。如果不同 scope 返回的 SchemaBundle 可能不同，必须纳入 key。

`DeviceRuntimeMeta.SchemaReleaseIDOverride` 只表示“设备是否覆盖产品当前物模型版本”，不能作为最终版本号来源：

1. `SchemaReleaseIDOverride > 0`：用它路由到 `GetReleaseSchema`。
2. `SchemaReleaseIDOverride == 0`：说明设备跟随产品当前版本，路由到 `GetCurrentSchema`。
3. 设备跟随当前版本时，`DeviceRuntimeMeta` 不返回当前 release id。最终 release id 必须从 `SchemaBundle.Meta.ReleaseID` 获取。

如果 `runtime-schema-batch` 返回的 `tsl` 中 `Meta.ReleaseID` 为空或为 `0`，应在 `loadSchemaBundle` 解析外层 response 时用 `entry.ReleaseID` 回填：

```go
if bundle.Meta.ProductID == "" {
    bundle.Meta.ProductID = entry.ProductID
}
if bundle.Meta.ReleaseID == 0 {
    bundle.Meta.ReleaseID = entry.ReleaseID
}
```

`PropertyDict.PoolKey.ReleaseID` 必须在这个回填之后生成。禁止把 `GetCurrentSchema` 请求中的 `ReleaseID=0` 写入 pool key，否则产品当前版本升级后，不同物模型版本会错误复用同一个池。

不要按“设备名”建池。设备数量可能百万级，而池只需要按产品物模型版本建，数量通常远小于设备数。

### 4.2 什么时候建池
推荐懒创建：`SchemaBundle` 进入 L1 otter cache 的 `Fmt` 阶段只负责构建 `PropertyDict` 和计算容量建议，不直接创建全局 pool。

原因：

1. `Fmt` 是 cache 数据格式化入口，适合解析 schema、构建 runtime index。
2. pool 是运行时资源，可能需要独立生命周期、容量上限和统计指标，不适合混进 L2 Redis 数据。
3. L1 cache 淘汰 SchemaBundle 时，如果 pool 和 bundle 强绑定，释放策略会变复杂。

推荐结构：

```go
type PayloadPoolManager struct {
    mu    sync.RWMutex
    pools map[PayloadPoolKey]*ModelPayloadPool
    cfg   PayloadPoolConfig
}

type PayloadPoolConfig struct {
    MaxRetainFactor    float64
    SecureWipeOnRelease bool
}

type ModelPayloadPool struct {
    key             PayloadPoolKey
    moduleCount     int
    maxPoints       int
    maxTextBytes    int
    maxBlocks       int
    maxBlockBytes   int
    maxRetainFactor float64
    secureWipeOnRelease bool
    pool            sync.Pool
}
```

创建时机：

1. `release_schema_cache.go` 的 `Fmt` 中构建 `PropertyDict`。
2. `PropertyDict` 里记录 `PoolKey` 和容量建议，例如 `MaxPoints`、`MaxTextBytes`、`ModuleCount`。
3. 第一次处理命中该 `PropertyDict` 的设备上报时，通过 `PayloadPoolManager.Borrow(dict)` 懒创建池。
4. 后续同一 `ProductID + ReleaseID + Scope` 的设备复用同一个池。

示例：

```go
type PropertyDict struct {
    ProductID string
    ReleaseID int64
    Scope     string

    PoolKey      PayloadPoolKey
    ModuleCount  int
    MaxPoints    int
    MaxTextBytes int
    MaxBlocks     int
    MaxBlockBytes int

    Points  []PropertyPointPlan
    Modules []ModuleMeta
}

// Internal helper. Business code should call Borrow, not this helper.
func (m *PayloadPoolManager) getOrCreate(dict *PropertyDict) *ModelPayloadPool {
    key := dict.PoolKey

    m.mu.RLock()
    p := m.pools[key]
    m.mu.RUnlock()
    if p != nil {
        return p
    }

    m.mu.Lock()
    defer m.mu.Unlock()
    if p = m.pools[key]; p != nil {
        return p
    }

    p = NewModelPayloadPool(key, dict.ModuleCount, dict.MaxPoints, dict.MaxTextBytes, dict.MaxBlocks, dict.MaxBlockBytes, m.cfg)
    m.pools[key] = p
    return p
}
```

### 4.3 Pool 初始化
`ModelPayloadPool` 不应只创建单个 `ModulePayload`，而应创建一整个 `ModulePayloadBatch`。因为一次设备上报会按 module 写入多个 TDengine module 表，batch 是“一台设备一次上报”的所有权单位。

```go
const DefaultMaxRetainFactor = 2.0

func normalizeMaxRetainFactor(v float64) float64 {
    if v <= 0 {
        return DefaultMaxRetainFactor
    }
    if v < 1 {
        return 1
    }
    return v
}

func NewModelPayloadPool(key PayloadPoolKey, moduleCount int, maxPoints int, maxTextBytes int, maxBlocks int, maxBlockBytes int, cfg PayloadPoolConfig) *ModelPayloadPool {
    p := &ModelPayloadPool{
        key:                 key,
        moduleCount:         moduleCount,
        maxPoints:           maxPoints,
        maxTextBytes:        maxTextBytes,
        maxBlocks:           maxBlocks,
        maxBlockBytes:       maxBlockBytes,
        maxRetainFactor:     normalizeMaxRetainFactor(cfg.MaxRetainFactor),
        secureWipeOnRelease: cfg.SecureWipeOnRelease,
    }
    p.pool.New = func() any {
        b := &ModulePayloadBatch{
            ProductID:     key.ProductID,
            SchemaRelease: key.ReleaseID,
            Modules:       make([]ModulePayload, moduleCount),
            Blocks:        make([]ModbusBlock, 0, maxBlocks),
            BlockScratch:  make([]byte, 0, maxBlockBytes),
        }
        for i := range b.Modules {
            b.Modules[i] = ModulePayload{
                Values:  make([]PointValueRef, 0, maxPoints),
                Ints:    make([]int64, 0, maxPoints),
                Floats:  make([]float64, 0, maxPoints),
                Strings: make([]StringRef, 0, maxPoints),
                Text:    make([]byte, 0, maxTextBytes),
            }
        }
        return b
    }
    return p
}
```

容量建议：

1. `moduleCount` 来自 `PropertyDict.Modules`。
2. `maxPoints` 可以先取该产品版本下单个 module 的最大点位数，或保守取总点位数。
3. `maxTextBytes` 根据 string 点位数量和 `Define.Max` 估算，并设置上限，避免异常模型创建巨型池。
4. `maxBlocks` 来自一次上报中 `DATA` 块数量的产品级估算，用于复用 `[]ModbusBlock` descriptor。
5. `maxBlockBytes` 是池的初始 capacity 建议和长期保留上限，不要求从 schema 精算。它对应一次上报中所有 hex string `VALUE` 解码后的字节总量，不是 hex 字符串长度；hex 字符串长度约为它的 2 倍。
6. 如果暂时无法从 schema 精确估算 `maxBlockBytes`，先使用配置默认值。实际解码时根据本次 `DATA.VALUE` 长度临时 grow，保证正确性。
7. pool 侧应另设 `MaxRetainFactor`、`MaxRetainBlockScratchBytes` 和 `HardBlockBytesLimit`：前两者决定超大 batch 是否放回池，后者决定异常大包是否拒绝。
8. 如果某次上报超过预估容量，允许 slice 临时扩容，但 `Put` 时要做容量上限保护，超限 batch 直接丢弃，不放回池。

初始建议值：

```go
const (
    DefaultBlockScratchBytes   = 512
    MaxRetainBlockScratchBytes = 4 * 1024
    HardBlockBytesLimit        = 16 * 1024
    DefaultMaxRetainFactor     = 2.0
)
```

当前设备遥测字符类型很少，通常不会超过 500 个字符。这里的容量都按 hex 解码后的字节数计算，不是 hex 字符串字符数；1000 个 hex 字符约等于 500 bytes。上线后应根据 `needBytes` 的 p95 / p99 / max 调整默认值和硬限制。

### 4.4 借出时怎么判断从哪个池借
借出时不要自己根据 `ProductID` 猜池，也不要根据设备名建池。必须使用当前设备实际命中的 `SchemaBundle` / `PropertyDict`。

在 `ps_lookup.go` 中，设备 schema 的选择逻辑已经存在：

1. 如果 `runtimeMeta.SchemaReleaseIDOverride > 0`，调用 `releaseSchemaCache.GetData(ctx, ProductReleaseKey{ProductID, ReleaseID: override, Scope})`。
2. 否则调用 `currentSchemaCache.GetData(ctx, ProductReleaseKey{ProductID, Scope})`。
3. 取返回的 `bundle.Meta.ReleaseID` 作为最终版本。
4. 从 bundle runtime index 取 `PropertyDict`。

因此 `handlePushData` 借池流程应是：

```go
dict, _ := oneSubsetMap["propertyDict"].(*schema.PropertyDict)
if dict == nil {
    // fallback old path
}

batch := payloadPoolManager.Borrow(dict)
batch.DeviceName = deviceName
batch.Timestamp = nowTs
```

关键点：

1. `dict.PoolKey` 是唯一可信的借池依据。
2. current schema 和 release schema 最终都归一到 `dict.PoolKey{ProductID, bundle.Meta.ReleaseID, Scope}`。
3. 同一产品不同 release 必须使用不同池，因为 module 数、点位数、string 容量和 `PointID` 分配都可能不同。
4. 同一设备如果 runtime meta 切换了 `SchemaReleaseIDOverride`，下一次 lookup 会命中新 bundle，也会自然借到新池。
5. 如果 L1 schema 被 NATS 通知删除，下次 lookup 会重新加载 bundle 和 dict；池不要跟随 schema cache 立即删除，应按 `4.6` 的规则做延迟清理。
6. 产品当前版本升级时，`currentSchemaCache` 失效后会重新加载新的 `SchemaBundle.Meta.ReleaseID`；新 `PropertyDict.PoolKey` 会指向新池，旧池进入候选清理状态。

网关主设备和子设备也按同一规则处理：谁命中了哪个 `SchemaBundle`，就使用该 bundle 的 `PropertyDict.PoolKey` 借池。不要把网关产品的池和子设备产品的池混用。

### 4.5 借出和归还
对外只暴露 `PayloadPoolManager.Borrow` 和 `ModulePayloadBatch.Release`，不要让业务代码直接持有裸 `sync.Pool` 或 `ModelPayloadPool`。这样 batch 跨 goroutine 转移所有权时，只需要传递 batch 本身，最终消费者调用 `batch.Release()` 即可。

推荐调用形态：

```go
batch := payloadPoolManager.Borrow(dict)
defer batch.Release()

decodeInto(batch)
writeOrTransfer(batch)
```

如果 batch 的所有权转移给 sink，decode 阶段不要 `defer batch.Release()`，而是由 sink 在该 batch 的所有 SQL 写入完成后调用 `batch.Release()`。

```go
func retainLimit(base int, factor float64) int {
    if base <= 0 {
        return 0
    }

    factor = normalizeMaxRetainFactor(factor)
    n := int(float64(base) * factor)
    if float64(n) < float64(base)*factor {
        n++
    }
    return n
}

func (b *ModulePayloadBatch) Release() {
    if b == nil {
        return
    }

    p := b.pool
    if p == nil {
        return
    }

    // Break ownership before putting back. Calling Release twice becomes a no-op.
    b.pool = nil
    p.put(b)
}

func (p *ModelPayloadPool) put(batch *ModulePayloadBatch) {
    p.lastReturn.Store(time.Now().UnixNano())
    defer p.inFlight.Add(-1)

    if batch == nil {
        return
    }
    if cap(batch.Modules) != p.moduleCount {
        return
    }

    maxRetainPoints := retainLimit(p.maxPoints, p.maxRetainFactor)
    maxRetainTextBytes := retainLimit(p.maxTextBytes, p.maxRetainFactor)
    maxRetainBlocks := retainLimit(p.maxBlocks, p.maxRetainFactor)
    maxRetainBlockBytes := retainLimit(p.maxBlockBytes, p.maxRetainFactor)

    for i := range batch.Modules {
        payload := &batch.Modules[i]
        if cap(payload.Values) > maxRetainPoints || cap(payload.Text) > maxRetainTextBytes {
            return
        }
    }
    if cap(batch.Blocks) > maxRetainBlocks || cap(batch.BlockScratch) > maxRetainBlockBytes {
        return
    }
    batch.Reset()
    p.pool.Put(batch)
}
```

`put` 前必须做容量上限保护，避免一次异常大报文把巨大底层数组长期留在池里。`Release` 只能由 batch 的当前所有者调用；调用后不得继续读写该 batch 或其内部 slice。

`MaxRetainFactor` 是“归还时最多保留多大 capacity”的配置，默认建议 `2.0`。这个默认值不是业务正确性边界，而是池化复用的折中：Go slice 在容量不足时经常会发生一次接近翻倍的扩容，如果 `maxPoints`、`maxTextBytes`、`maxBlocks` 或 `maxBlockBytes` 的估算基本准确，但某次正常上报刚好略超预估，底层数组可能从 `maxX` 扩到接近 `2*maxX`。默认保留 2 倍可以避免把这种“正常一次扩容”的 batch 每次都丢弃，减少池反复重建。判断条件使用 `cap > retainLimit`，因此刚好等于 `2*maxX` 的 batch 仍会放回池。

注意这个阈值只决定“归还时是否继续留在 pool”，不决定本次上报是否接受。真正拒绝异常大包应由 decode 阶段的 `HardBlockBytesLimit` 等硬限制处理。

配置建议：

1. 内存非常紧张时可取 `1.25` 到 `1.5`，代价是正常波动也更容易触发丢弃和重新分配。
2. 默认先取 `2.0`，适合点位数量稳定、偶发小幅超预估的设备遥测。
3. 如果 schema 估算偏保守且上报波动大，可临时取 `3.0`，但必须观察 retained heap，避免池长期持有过大的底层数组。
4. 上线指标至少包含 `pool_drop_oversize_total`、`pool_retained_cap_points`、`pool_retained_cap_text_bytes`、`pool_retained_cap_blocks`、`pool_retained_cap_block_bytes`，用于判断 factor 是否过小或过大。

### 4.6 旧 release pool 清理
旧 release pool 不能在产品当前版本升级、L1 schema 删除、或发现新 `ReleaseID` 后立即清理。原因是 eKuiper 链路中可能已经有 batch 从旧池借出，并且所有权已经转移到 TDengine sink；只有 sink 写入完成并归还 batch 后，旧池才具备被释放的条件。

推荐把 pool 生命周期拆成两个问题：

1. 是否还会有新借出：由 schema lookup 的命中情况决定。只要某台设备仍然命中旧 `ProductID + ReleaseID + Scope`，就允许继续借旧池。
2. 是否可以释放内存：由 pool 自己的 `inFlight` 和最近使用时间决定。只有所有已借出的 batch 都归还，并且一段时间内没有新借出，才能从 `PayloadPoolManager.pools` 中删除。

因此 `ModelPayloadPool` 需要维护运行时状态，而不是裸用 `sync.Pool`：

```go
type ModelPayloadPool struct {
    key PayloadPoolKey

    moduleCount     int
    maxPoints       int
    maxTextBytes    int
    maxBlocks       int
    maxBlockBytes   int
    maxRetainFactor float64

    pool sync.Pool

    inFlight    atomic.Int64
    lastBorrow  atomic.Int64 // unix nano
    lastReturn  atomic.Int64 // unix nano
    retiredAt   atomic.Int64 // unix nano, 0 means active
}
```

`sync.Pool` 本身不能告诉我们当前借出了多少对象，所以借出必须由 `PayloadPoolManager.Borrow` 封装，归还必须经由 `batch.Release()` 进入内部 `ModelPayloadPool.put`。业务代码不能直接操作裸 pool。为了避免“清理线程看到 `inFlight == 0` 时，另一个 goroutine 刚拿到 pool 指针但还没加计数”的竞态，推荐把借出计数放在 manager 锁内完成：

```go
func (m *PayloadPoolManager) Borrow(dict *PropertyDict) *ModulePayloadBatch {
    key := dict.PoolKey
    now := time.Now().UnixNano()

    m.mu.Lock()
    p := m.pools[key]
    if p == nil {
        p = NewModelPayloadPool(key, dict.ModuleCount, dict.MaxPoints, dict.MaxTextBytes, dict.MaxBlocks, dict.MaxBlockBytes, m.cfg)
        m.pools[key] = p
    }
    p.inFlight.Add(1)
    p.lastBorrow.Store(now)
    m.mu.Unlock()

    batch := p.pool.Get().(*ModulePayloadBatch)
    batch.Reset()
    batch.pool = p
    return batch
}

func (p *ModelPayloadPool) put(batch *ModulePayloadBatch) {
    p.lastReturn.Store(time.Now().UnixNano())
    defer p.inFlight.Add(-1)

    if batch == nil {
        return
    }
    if cap(batch.Modules) != p.moduleCount {
        return
    }

    maxRetainPoints := retainLimit(p.maxPoints, p.maxRetainFactor)
    maxRetainTextBytes := retainLimit(p.maxTextBytes, p.maxRetainFactor)
    maxRetainBlocks := retainLimit(p.maxBlocks, p.maxRetainFactor)
    maxRetainBlockBytes := retainLimit(p.maxBlockBytes, p.maxRetainFactor)

    for i := range batch.Modules {
        payload := &batch.Modules[i]
        if cap(payload.Values) > maxRetainPoints || cap(payload.Text) > maxRetainTextBytes {
            return
        }
    }
    if cap(batch.Blocks) > maxRetainBlocks || cap(batch.BlockScratch) > maxRetainBlockBytes {
        return
    }

    batch.Reset()
    p.pool.Put(batch)
}
```

这里有一个有意设计的边界：`inFlight.Add(1)` 必须发生在 manager 锁内，并且必须早于 `p.pool.Get()`。

原因是 `inFlight` 保护的不只是“已经成功拿到 batch 的对象”，还包括“已经决定从这个 pool 借出、但正在执行 `sync.Pool.Get` 的借用窗口”。`sync.Pool.Get()` 可能很快返回，也可能因为 GC 清理了 `sync.Pool` 本地缓存而触发 `New` 重新分配；`NewModelPayloadPool` 里的 batch 初始化会做多个 `make`，极端情况下这一步可能比较慢。

如果先 `pool.Get()` 再 `inFlight.Add(1)`，就会出现危险窗口：

1. goroutine A 已经从 `m.pools` 取到了旧 release pool 指针，准备 `pool.Get()`。
2. 此时还没有 `inFlight++`。
3. sweeper 看到该 pool `retiredAt > 0` 且 `inFlight == 0`，并且 idle TTL 已到，于是从 `m.pools` 删除。
4. goroutine A 随后才拿到 batch 并开始使用。虽然 Go 指针仍能保持对象存活，但 manager 已经认为旧池可回收，后续统计、生命周期和重新创建逻辑都会变得混乱。

当前顺序避免了这个问题：

1. 在 manager 锁内找到或创建 pool。
2. 在同一把锁内执行 `inFlight++` 和 `lastBorrow = now`。
3. 释放锁后再执行可能较慢的 `p.pool.Get()`。

这样即使 `p.pool.Get()` 触发 GC 后的重建分配，sweeper 也只能看到 `inFlight > 0`，不会删除该 pool。等 batch 最终 `Release()` 后，内部 `put` 才会 `inFlight--`。因此 `inFlight` 覆盖了“借用意图 -> 成功拿到 batch -> 使用中 -> 归还”整个所有权窗口。

旧 release pool 的清理建议采用“事件标记 + 后台 sweep”的方式：

1. 当产品当前版本切换后，新的 current schema 会生成新的 `PayloadPoolKey`。manager 可以把同 `ProductID + Scope` 下非当前 `ReleaseID` 的 pool 标记为 `retiredAt = now`。
2. 当收到设备迁移完成、release 下线、或 schema cache invalidation 事件时，也只标记 retired，不立即删除。
3. 后台 sweeper 定期扫描 pool map。满足 `retiredAt > 0`、`inFlight == 0`、并且 `now - max(lastBorrow, lastReturn, retiredAt) > retireIdleTTL` 时，从 `m.pools` 删除该 pool。
4. 如果没有可靠的“全部设备已迁移”事件，也可以只用被动 idle TTL：旧池长时间没有新借出且 `inFlight == 0` 就删除。

示例：

```go
func (m *PayloadPoolManager) RetireProductOldReleases(productID string, scope string, currentReleaseID int64) {
    now := time.Now().UnixNano()

    m.mu.Lock()
    defer m.mu.Unlock()

    for key, p := range m.pools {
        if key.ProductID == productID && key.Scope == scope && key.ReleaseID != currentReleaseID {
            p.retiredAt.CompareAndSwap(0, now)
        }
    }
}

func (m *PayloadPoolManager) Sweep(now time.Time, retireIdleTTL time.Duration) {
    nowNano := now.UnixNano()

    m.mu.Lock()
    defer m.mu.Unlock()

    for key, p := range m.pools {
        retiredAt := p.retiredAt.Load()
        if retiredAt == 0 {
            continue
        }
        if p.inFlight.Load() != 0 {
            continue
        }

        lastUsed := maxInt64(retiredAt, p.lastBorrow.Load(), p.lastReturn.Load())
        if time.Duration(nowNano-lastUsed) < retireIdleTTL {
            continue
        }

        delete(m.pools, key)
    }
}
```

从 `m.pools` 删除后，只要没有借出的 batch 还引用该 pool，整个 `sync.Pool` 及其中缓存的 batch 就会变成 GC 可回收对象。这里不需要也不能遍历 `sync.Pool` 手动释放内部对象。

清理策略建议：

1. `retireIdleTTL` 不要太短，建议先取 `10m` 到 `30m`，避免刚升级后少量延迟上报导致频繁重建旧池。
2. 如果后续业务要求旧 release 不再接受上报，应在 schema lookup 或设备版本校验层拒绝旧版本，而不是依赖 pool 删除来表达业务禁用。
3. 如果删除后又有设备命中旧 release，`Borrow` 会按 `dict.PoolKey` 重新创建旧池；这说明仍有设备未迁移，应该通过监控暴露出来。
4. 监控指标至少包含 `pool_count`、`pool_inflight`、`pool_last_borrow`、`pool_retired`、`pool_drop_oversize_total`。

### 4.7 Reset
```go
func (b *ModulePayloadBatch) Reset() {
    b.DeviceName = ""
    b.Timestamp = 0
    b.Blocks = b.Blocks[:0]
    b.BlockScratch = b.BlockScratch[:0]

    for i := range b.Modules {
        b.Modules[i].Reset()
    }
}

func (p *ModulePayload) Reset() {
    p.Timestamp = 0

    p.Values = p.Values[:0]
    p.Ints = p.Ints[:0]
    p.Floats = p.Floats[:0]
    p.Strings = p.Strings[:0]
    p.Text = p.Text[:0]
}
```

`Reset` 默认只重置长度，不清空底层数组。因为底层数组会被下一次写入覆盖，这样可以避免归还 pool 时额外扫描大块内存。

这个选择有一个明确 trade-off：`BlockScratch[:0]`、`Text[:0]` 之后，旧数据仍然留在底层数组的 capacity 范围内。正常业务代码不会读取这些区域，但如果后续场景包含敏感数据，例如序列号、密钥片段、认证 token 或隐私字段，归还前应启用安全擦除。

推荐把安全擦除做成 pool 配置，而不是默认行为：

```go
type ModelPayloadPool struct {
    // ...
    secureWipeOnRelease bool
}

func (b *ModulePayloadBatch) Wipe() {
    clear(b.BlockScratch[:cap(b.BlockScratch)])
    for i := range b.Modules {
        clear(b.Modules[i].Text[:cap(b.Modules[i].Text)])
    }
}

func (p *ModelPayloadPool) put(batch *ModulePayloadBatch) {
    // capacity guard ...

    if p.secureWipeOnRelease {
        batch.Wipe()
    }
    batch.Reset()
    p.pool.Put(batch)
}
```

安全擦除会按 `cap(BlockScratch)` 和 `cap(Text)` 扫描整块底层数组，CPU 成本与容量成正比。当前设备遥测场景敏感度不高，建议默认关闭；如果产品线后续把敏感字段放入 `DATA.VALUE` 或 string 点值，再按产品、scope 或全局配置打开。

2. 避免大量小 string 对象散落堆中。
3. payload 归还时整块 `Text` 一起复用。

## 6. Schema Dictionary
### 6.1 必要性
payload 中只有 `PointID`，sink 写 TDengine 时需要恢复列名。因此必须有 schema dictionary。

```go
type PointMeta struct {
    PointID    uint16
    Identifier string
    Kind       ValueKind
    ModuleID   int64
    ModuleCode string
    ColumnSQL  string
}

type SchemaDict struct {
    ProductID      string
    ReleaseID      int64
    Points         []PointMeta
    ByIdentifier   map[string]uint16
}
```

当前 `things/device/auth/runtime-schema-batch` 返回的 `SchemaBundle` 中，`Model.Properties` / `Model.Events` 只有 `Identifier`，`Route` 中也只有 `identifier -> [ModuleID, ModuleCode]`。因此 `PointID` 不应理解为数据库里的 `dm_module_schema_info.id`，而应理解为 eKuiper 在加载发布物模型后派生出的本地紧凑索引。

注意：这里的 `PointID` 只服务 property typed payload。事件链路不进入 property `PointID` 空间，事件应使用独立的 `eventType + alarmCode` lookup cache。详细设计见：[设备事件 Schema Lookup Cache 设计](4.design-event-schema-lookup-cache.md)。

推荐构建规则：

1. 从 `SchemaBundle.Meta.ProductID` 和 `SchemaBundle.Meta.ReleaseID` 确定字典作用域。
2. 遍历 `Model.Properties`，只处理属性点位；事件参数不进入 property `PointID` 空间。
3. 只收录 `Route` 中存在的 `identifier`，因为只有这些点位能写入 TDengine module 表。
4. 按稳定顺序排序后分配 `PointID`。推荐顺序为 `(ModuleID, Identifier)`；如果 `ModuleID` 不可用，则使用 `(ModuleCode, Identifier)`。
5. 分配结果写入 `Points []PointMeta`，并建立 `ByIdentifier map[string]uint16`。
6. 如果点位数量超过 `math.MaxUint16`，启动时直接报错，要求切换为 `uint32` PointID 或拆分模型。

示例：

```go
// 输入来自 SchemaBundle:
// ProductID = "p1", ReleaseID = 42
// Properties = ["Pac", "Uac", "SN"]
// Route = {
//   "Pac": [1001, "inv_runtime"],
//   "Uac": [1001, "inv_runtime"],
//   "SN":  [1002, "inv_profile"]
// }
//
// 稳定排序后:
// PointID 0 -> inv_runtime/Pac
// PointID 1 -> inv_runtime/Uac
// PointID 2 -> inv_profile/SN
```

这个 `PointID` 是内存优化用的本地 ID，不是业务主键，不要求跨环境一致。只要同一个 `ProductID + ReleaseID` 在当前进程内构建规则稳定，decode、verify 和 sink 共享同一份 `SchemaDict` 即可。

### 6.2 构建时机：SchemaBundle 进入 L1 Fmt
`SchemaDict` 不应在每次 `handlePushData`、每次 decode 或每次 sink 写入时临时构建。它只和 `ProductID + ReleaseID + SchemaBundle` 有关，应在 schema release 进入本地 L1 cache 时一次性生成。

当前缓存链路是：

1. L1：进程内 `otter.Cache`。
2. L2：Redis `kv.Store`。
3. L3：HTTP `things/device/auth/runtime-schema-batch`。

`release_schema_cache.go` 中的 `Fmt` 是写入本地 L1 otter cache 前的格式化入口。Redis 命中时，数据从 L2 反序列化后执行 `Fmt`，再写入 L1；HTTP 命中时，原始 `data` 从 L3 返回，`Fmt` 的返回值写入 L1，而原始 `data` 会被异步 marshal 回写 L2 Redis。

因此，property `SchemaDict` 应在 `GetCurrentSchema` / `GetReleaseSchema` 的 `Fmt` 阶段预生成，并挂在 L1 copy 上：

```go
type SchemaRuntimeIndex struct {
    PropertyDict *SchemaDict
    EventLookup  map[EventLookupKey]EventLookupMeta
}

type SchemaBundle struct {
    Model json.RawMessage             `json:"Model"`
    Route map[string]SchemaRouteEntry `json:"Route"`
    Meta  SchemaBundleMeta            `json:"Meta"`

    parsedModel  *Model
    runtimeIndex *SchemaRuntimeIndex
}
```

推荐把 current schema 和 release schema 的 `Fmt` 统一为一个 helper：

```go
func formatSchemaBundleForL1(ctx context.Context, key client.ProductReleaseKey, data *schema.SchemaBundle) *schema.SchemaBundle {
    if data == nil {
        return nil
    }

    copied := *data
    if err := copied.ParseModel(); err != nil {
        // log warn
    }
    if err := copied.BuildRuntimeIndexes(); err != nil {
        // log warn or fail fast
    }
    copied.Model = nil
    return &copied
}
```

`BuildRuntimeIndexes` 至少应完成两件事：

1. 构建 property `SchemaDict`：`identifier -> PointID`、`PointID -> PointMeta`、`ModuleID/ModuleCode`、`ColumnSQL`、`ValueKind`。
2. 构建 event lookup：`eventType + alarmCode -> EventID/Type/ParamKinds`，详见 [设备事件 Schema Lookup Cache 设计](4.design-event-schema-lookup-cache.md)。

实际代码可以把 `SchemaRuntimeIndex` 拆成多个 `json:"-"` 字段，例如 `propertyDict` 和 `eventLookup`。如果放在 `schema` 包内实现，注意不要反向依赖 sink 包；`ColumnSQL` 的生成规则应放在无循环依赖的 runtime index helper 中，或者只存储已校验的列名片段。

property `SchemaDict` 需要继续扩展为 `PropertyPointPlan`，把 `base-addr/scaler/vdata_type/min/max/step/enum/module` 等信息都预解析好，供高频 decode 和 typed verifier 直接使用。详细字段与流程见：[属性 Typed Decode 与 Typed Verifier 改造设计](5.design-property-typed-decode-and-verifier.md)。

这里必须坚持 copy-on-format：

1. `Fmt` 不能直接修改入参 `data`。
2. `copied.Model = nil` 只能发生在 copy 上，用于减少 L1 内存占用，不能清空原始 `data.Model`。
3. runtime index 字段必须是 `json:"-"` 或非导出字段，不能写入 L2 Redis。
4. `Route map` 可以共享，但后续必须只读；如果构建过程需要改写 map，必须深拷贝。
5. 构建字典时如果需要排序，应排序临时 `PointMeta` 切片，不要依赖 map 遍历顺序。

当前代码中，`GetCurrentSchema` 的 `Fmt` 已经采用 `copied := *data` 的模式；`GetReleaseSchema` 的 `Fmt` 也应改成同一个 helper，避免直接 `data.ParseModel()` 和 `data.Model = nil` 污染 L2 回写数据。

### 6.3 L1 容量估算与上限
`SchemaDict` / `PropertyDict` 是高频路径的运行时索引，不写 Redis，但会常驻本地 L1 cache。它节省的是每次上报的 CPU 和小对象分配，代价是每个 `ProductID + ReleaseID + Scope` 占用一份内存。

粗略估算：

1. `PointMeta` 只包含 `Identifier/ModuleCode/ColumnSQL/Kind/ModuleID` 等字段，单点约 `100~180B`。
2. 扩展到 `PropertyPointPlan` 后，还包含 `base-addr/scaler/vdata_type/min/max/step/enum`，单点建议按 `200~300B` 估算。
3. `ByIdentifier map[string]uint16`、enum 数组、`ColumnSQL` 字符串会继续增加内存。

典型容量：

| 产品版本规模 | 单个 runtime index 估算 |
| :--- | :--- |
| 100 点 | 30KB~60KB |
| 500 点 | 150KB~300KB |
| 1000 点 | 300KB~600KB |


如果 L1 同时保留 1000 个产品版本，property runtime index 可能达到 `300MB~600MB`。这还不包含 parsed model、event lookup、otter entry 元数据和 Go allocator 碎片。因此 schema L1 cache 必须设置条目上限或权重上限。

建议：

1. L1 schema cache 按 `ProductID + ReleaseID + Scope` 设置 max entries，初始可按部署内存从 `1000~5000` 个版本评估。
2. 如果 cache 组件支持权重，按 `len(PropertyDict.Points)` 或估算字节数做 weighted cache，而不是单纯按条目数。
3. 当前版本和仍有设备使用的 release 应优先保留；历史 release 依赖 TTL / LRU 淘汰。
4. pool 和 schema L1 不强绑定。schema entry 淘汰不应立即删除 payload pool，payload pool 按 `inFlight + idleTTL` 延迟清理。
5. 监控指标至少包括 `schema_l1_entries`、`schema_l1_evictions_total`、`property_plan_points_total`、`property_plan_estimated_bytes`。
6. 如果内存压力明显，优先优化 `ByIdentifier` 是否按需构建、字符串驻留、`ColumnSQL` 复用，以及 enum 数组共享。

### 6.4 为什么不直接使用 dm_module_schema_info.id
不建议把 `dm_module_schema_info.id` 作为 `PointID`：

1. 它是数据库自增主键，跨环境、导入、重建、测试库不稳定。
2. 当前发布快照 `dm_module_schema_snapshot.schema_json` 保存的是语义字段和 `Identifier`，没有保存原始自增 ID。
3. 高频路径需要的是紧凑数组下标，数据库 ID 往往稀疏，直接作为数组下标会浪费内存。
4. 使用数据库 ID 会把 eKuiper 的运行时内存结构和 iot 内部表结构强绑定，后续迁移成本更高。

如果未来确实需要 iot 和 eKuiper 共享完全一致的 point id，应在发布产物中显式生成 `PointIndex`，而不是直接泄漏 `dm_module_schema_info.id`。例如：

```json
{
  "PointIndex": {
    "Pac": [0, 1001, "inv_runtime", "float"],
    "Uac": [1, 1001, "inv_runtime", "int"]
  }
}
```

### 6.5 ColumnSQL 是什么
`ColumnSQL` 是预生成的 TDengine 列名 SQL 片段，例如：

```go
PointMeta{
    Identifier: "Pac",
    ColumnSQL:  "`Pac`",
}
```

它只表示“列名”，不表示“值”，也不包含 placeholder。写 INSERT 时直接拼到列列表里：

```sql
(`ts`,`Pac`,`Uac`) VALUES (?,?,?)
```

其中：

1. `` `Pac` `` 和 `` `Uac` `` 来自 `ColumnSQL`。
2. `?` 来自 SQL builder 的 placeholder 模板。
3. 真实点值仍走 `db.Exec(sql, args...)` 的参数，不拼进 SQL 字符串。

提前保存 `ColumnSQL` 的收益：

1. sink 写入时无需重复给 identifier 加反引号。
2. 无需每条数据重复做 sanitize / escape / 拼接。
3. module 写入模板可以直接复用 `ColumnSQL` 拼出的列列表。
4. 可以在 schema dictionary 构建阶段集中校验非法列名，失败尽早暴露。

生成规则建议：

1. 优先在发布阶段保证 `Identifier` 符合 TDengine 安全列名规则，例如 `^[A-Za-z][A-Za-z0-9_]{0,63}$`。
2. 构建 `SchemaDict` 时对 identifier 做一次校验。
3. 通过校验后生成 `` "`" + identifier + "`" ``。
4. 如果允许更宽松的 identifier，必须统一调用项目里的 `SanitizeTablePart`，并保证 sanitize 后不会产生列名冲突。

### 6.6 ID 作用域
推荐作用域：

1. `PointID uint16`：只在一个 `ProductID + ReleaseID` 对应的本地 `SchemaDict` 内唯一。
2. `ModuleID int64`：来自当前 `SchemaBundle.Route`，用于 TDengine module 路由。
3. `ProductID string`：产品编码，不是产品表主键。
4. `DeviceName string`：设备编码。设备唯一性由 `ProductID + DeviceName` 确定，不依赖单独的 `DeviceID`。
5. `SchemaRelease/ReleaseID`：产品物模型发布版本。

不要把 `uint16` 用作全局点位 ID。全局点位数量很容易超过 65535。

## 7. Sink 边界转换
SQL builder 或 TDengine sink 读取 payload 时，按 descriptor 顺序恢复列和值。

这一段逻辑必须只实现一份。`BuildPropertySQLFromBatch`、批量 SQL builder 或其他 sink 分支都应调用同一个 helper，避免列名和值恢复规则分叉。

```go
func AppendPayloadColumnsAndArgs(cols []string, args []any, dict *PropertyDict, payload *ModulePayload, timestamp int64) ([]string, []any, error) {
    cols = append(cols, "`ts`")
    args = append(args, timestamp)

    return AppendPayloadValueColumnsAndArgs(cols, args, dict, payload)
}

func AppendPayloadValueColumnsAndArgs(cols []string, args []any, dict *PropertyDict, payload *ModulePayload) ([]string, []any, error) {
    if dict == nil {
        return nil, nil, fmt.Errorf("nil property dict")
    }

    for _, ref := range payload.Values {
        if int(ref.PointID) >= len(dict.Points) {
            return nil, nil, fmt.Errorf("point id %d out of range", ref.PointID)
        }
        meta := dict.Points[ref.PointID]
        cols = append(cols, meta.ColumnSQL)

        switch ref.Kind {
        case ValueInt:
            args = append(args, payload.Ints[ref.Index])
        case ValueFloat:
            args = append(args, payload.Floats[ref.Index])
        case ValueString:
            sref := payload.Strings[ref.Index]
            b := payload.Text[sref.Off : sref.Off+sref.Len]
            args = append(args, string(b))
        default:
            return nil, nil, fmt.Errorf("unknown value kind %d", ref.Kind)
        }
    }

    return cols, args, nil
}
```

注意：`string(b)` 会为 database/sql 生成 Go string。这个分配发生在 sink 边界，数量已经从“上游全链路携带大量 string key/value”收敛到“写入前必要转换”。如果 TDengine driver 支持 `[]byte` 写 BINARY，可以进一步减少这一步转换。

## 8. 所有权与生命周期
### 8.1 基本规则
谁拥有 batch，谁负责最终调用 `batch.Release()`。payload 归还池之前，下游不得继续持有它或持有它内部 slice 的引用。

调用方不直接保存 `ModelPayloadPool`，也不直接调用 `pool.Put(batch)`。`PayloadPoolManager.Borrow(dict)` 会把所属 pool 绑定到 batch 的内部字段，最终消费者只需要调用 `batch.Release()`。

### 8.2 同步链路
如果 decode -> verify -> build SQL -> db.Exec 全部在同一个 goroutine 内同步完成，可以这样使用：

```go
batch := payloadPoolManager.Borrow(dict)
defer batch.Release()

decodeInto(batch)
verify(batch)
writeToTdengine(batch)
```

`writeToTdengine` 必须在返回前完成对 batch 的读取。

### 8.3 跨 goroutine 链路
如果 payload 会进入 eKuiper 下游算子、异步队列或 sink buffer，则不能在 function 返回时 `Release`。

可选方案：

1. 不跨 goroutine 传 pooled payload，只在单个 operator 内部使用，输出时转成普通不可复用对象。
2. 引入引用计数，最后一个消费者释放时 `Release`。
3. 将 payload 所有权转移给 sink，由 sink 在 `Exec` 完成后调用 `batch.Release()`。
4. 异步队列复制必要数据，复制完成后立即归还 payload。

新项目推荐优先选择第 3 种：payload 从 decode 阶段借出，所有权随消息转移到 TDengine sink，sink 同步或异步写入完成后归还。

### 8.4 禁止事项
1. 禁止 function append result 后立即 `batch.Release()`。
2. 禁止把 `payload.Text` 切片转成不复制的 unsafe string 后跨越 `Release`。
3. 禁止多个 goroutine 同时写同一个 payload。
4. 禁止 sink 在 `db.Exec` 未返回时归还 args 或 payload。
5. 禁止把池作为无限队列使用。
6. 禁止调用 `Release` 后继续读写 batch；重复 `Release` 是 no-op，但使用已释放对象仍然是 bug。

## 9. 与 SQL Builder 池的关系
Typed Payload 池解决的是“上游数据结构和生命周期”的问题；SQL Builder 池解决的是“写入侧大 SQL 构造”的问题。两者可以组合：

1. Decode 阶段：通过 `PayloadPoolManager.Borrow(dict)` 获取 `ModulePayloadBatch`。
2. Verify 阶段：按 schema 写入 `PointValueRef + arena`。
3. Sink 阶段：读取 payload，使用 schema dictionary 生成 SQL fragment。
4. SQL Builder 阶段：使用 builder 池拼 batch SQL。
5. Exec 完成：归还 SQL builder，并调用 `batch.Release()` 归还 payload。

推荐落地顺序：

1. 先定义 typed payload 和所有权协议。
2. 再实现 [属性 Typed Decode 与 Typed Verifier](5.design-property-typed-decode-and-verifier.md)，让高频 PUSH_DATA 绕开点级 map、`VerifyProperties` 和 `SplitByModule`。
3. 再接入 SQL builder 池。
4. 最后再评估是否需要 ring buffer。

## 10. 与 Value Ring Buffer 的关系
`PointValueRef + Ints/Floats/Text arena` 本身就是 value ring buffer 的前置形态。后续如果吞吐仍不够，可以把单个 payload 的 arena 扩展为批量 ring：

1. `Payload` 变成 ring 中的一段 descriptor。
2. `Ints/Floats/Text` 从 per-payload arena 变成 per-shard arena。
3. sink 维护 flush cursor 和 retry cursor。
4. ring 满时触发 backpressure。

这种演进不会推翻 typed value 设计，只是把生命周期从“单个 payload”扩大到“一个 shard 或 worker 的连续批次”。

## 11. 测试与验证
### 11.1 单元测试
1. `AddInt` 写入 `Ints`，descriptor 指向正确下标。
2. `AddFloat` 写入 `Floats`，descriptor 指向正确下标。
3. `AddString` 写入 `Text`，`StringRef` offset/length 正确。
4. 无有效值点位不生成 descriptor，sink 不拼对应列。
5. `Reset` 只清空长度，不改变合理容量。
6. `Put` 遇到超大容量 payload 时丢弃，不放回池。
7. sink 按 descriptor 恢复列名和值，args 顺序正确。
8. payload 在 sink `Exec` 完成后才归还。

### 11.2 Benchmark
对比三组：

1. `map[string]any` payload。
2. 简单 `TypedValue{PointID, Kind, I64, F64, Str}` payload。
3. `PointValueRef + Ints/Floats/Text arena` payload。

关键指标：

1. `allocs/op`
2. `B/op`
3. p95/p99 decode + build SQL 耗时
4. GC CPU
5. RSS 和 heap inuse

### 11.3 压测输入
压测必须覆盖：

1. 纯 int/float 点表。
2. 含少量 string 点表。
3. string 点值较长的点表。
4. 500 点位/次。
5. 1000 点位/次。
6. 多设备并发上报。

## 12. 推荐结论
新项目可以直接采用 `PointValueRef + Ints/Floats/Text arena`，它比 `[]float64` 更符合真实设备点表，也比 `map[string]any` 更适合高频路径。

需要坚持两条底线：

1. payload 所有权必须随数据流转到最后一个消费者，不能提前 `Release`。
2. sink 边界必须通过 `SchemaRelease + PointID` 恢复列名和值类型，不能依赖 map 随机遍历顺序。

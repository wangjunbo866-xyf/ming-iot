# 设备事件 Schema Lookup Cache 设计
## 1. 背景
当前 PUSH_DATA 链路中，设备属性和设备事件的写入特征不同：

1. 属性是固定点表，每次全量上传、全量解码、全量校验、全量存储。
2. 事件是固定事件位图，每次全量上传、全量解码，但只在状态变化时存储。
3. 大部分上报周期内，事件没有变化，或者只产生少量变化事件。

因此，事件链路第一阶段不建议做和属性一样的 `PointValueRef + Ints/Floats/Text arena` 预分配池。事件优化的优先级应放在 schema 查找和重复校验上。

当前事件解码中的主要热点是 `getEventIdentifier`：

1. 每次根据 `eventType + alarmCode` 查找事件 ID。
2. 每次都会遍历 `tslEvents`。
3. 遍历过程中还会反复 `json.Unmarshal(tslEvent.ExtendConfig)` 解析 `alarm_code`。

这些工作只和 `ProductID + ReleaseID + SchemaBundle` 有关，和单次设备上报无关，适合在 schema release 进入本地 L1 cache 时一次性预生成。

## 2. 设计目标
1. 运行时事件解码不再遍历 `tslEvents`。
2. 运行时事件解码不再反复解析 `ExtendConfig`。
3. 事件码查找从 `O(len(events))` 变为 `O(1)`。
4. lookup cache 只存在于 eKuiper 本地 L1 otter cache，不写入 Redis。
5. 构建 lookup cache 时不得修改传入的 `data`，避免污染 L2 Redis 回写内容。
6. 事件优化保持轻量，不把 event 参数混入 property typed payload 的 `ValueKind`。

## 3. Cache 分层与 Fmt 定位
当前 `caches.Cache` 是三层结构：

1. L1：进程内 `otter.Cache`。
2. L2：Redis `kv.Store`。
3. L3：HTTP `things/device/auth/runtime-schema-batch`。

`Fmt` 的定位是“把 L2/L3 返回的原始数据格式化成本地运行时对象”，然后写入 L1。

Redis 命中时：

```go
var ret dataT
json.Unmarshal(raw, &ret)
ret = *c.fmt(ctx, key, &ret)
c.cache.Set(keyStr, &ret)
```

HTTP 命中时：

```go
data, err := c.getData(ctx, key)
newData := c.fmt(ctx, key, data)
c.cache.Set(keyStr, newData)

// 注意：这里异步写 Redis 的仍然是 data
json.Marshal(data)
```

所以，事件 schema lookup cache 应该在 `release_schema_cache.go` 的 `Fmt` 中预生成，并挂在返回给 L1 的 copy 上。

## 4. Fmt 必须 Copy-on-Format
`Fmt` 不应该直接修改入参 `data`。原因是：当 L3 HTTP 命中时，`data` 会在 `Fmt` 后异步 marshal 并回写 Redis。如果 `Fmt` 直接修改 `data`，就会把本地运行时字段或被裁剪后的字段写入 L2。

推荐统一 current schema 和 release schema 的格式化逻辑：

```go
func formatSchemaBundleForL1(ctx context.Context, key client.ProductReleaseKey, data *schema.SchemaBundle) *schema.SchemaBundle {
    if data == nil {
        return nil
    }

    copied := *data
    if err := copied.ParseModel(); err != nil {
        // log warn
    }
    copied.BuildRuntimeIndexes()
    copied.Model = nil
    return &copied
}
```

注意：

1. `copied := *data` 足够隔离 `copied.Model = nil` 这类字段替换，不会把原始 `data.Model` 清空。
2. `Route map` 可以共享，只要后续按只读使用。
3. `parsedModel`、event lookup、property dict 这类运行时索引必须是 `json:"-"` 字段或非导出字段，不参与 L2 序列化。
4. 当前 `GetCurrentSchema` 已经采用 copy 后解析的方式；`GetReleaseSchema` 也应改成同样的 helper，避免直接修改 `data`。

## 5. Runtime Index 结构
可以在 `schema.SchemaBundle` 中增加本地运行时字段：

```go
type SchemaBundle struct {
    Model json.RawMessage             `json:"Model"`
    Route map[string]SchemaRouteEntry `json:"Route"`
    Meta  SchemaBundleMeta            `json:"Meta"`

    parsedModel *Model
    eventLookup          map[EventLookupKey]EventLookupMeta
    eventLookupConflicts []EventLookupConflict
}
```

事件 lookup key：

```go
type EventLookupKey struct {
    EventType string
    AlarmCode int
}
```

事件 lookup value：

```go
type EventLookupMeta struct {
    EventID    string
    Type       string
    ParamKinds []EventParamKind
}
```

重复事件码冲突只进入本地运行时字段，不写入 Redis：

```go
type EventLookupConflict struct {
    Key         EventLookupKey
    KeptEventID string
    DropEventID string
}
```

事件参数类型使用独立的轻量枚举，不复用 property typed payload 的 `ValueKind`：

```go
type EventParamKind uint8

const (
    EventParamInt EventParamKind = iota
    EventParamFloat
    EventParamString
)
```

当前逆变器故障/告警事件只有 `params.val`，且值为 `0/1`，因此第一阶段只需要支持 `EventParamInt`。事件路径不引入 JSON value kind；如果未来 event 参数需要 JSON 序列化，应作为 event sink 边界的独立策略处理。

## 6. 构建规则
在 `SchemaBundle` 进入 L1 时构建：

```go
func (b *SchemaBundle) BuildRuntimeIndexes() {
    model := b.GetModel()
    if model == nil {
        return
    }

    b.eventLookup = make(map[EventLookupKey]EventLookupMeta, len(model.Events))
    for i := range model.Events {
        ev := &model.Events[i]

        alarmCode, ok := parseAlarmCode(ev.ExtendConfig)
        if !ok {
            continue
        }

        key := EventLookupKey{
            EventType: ev.Type,
            AlarmCode: alarmCode,
        }

        meta := EventLookupMeta{
            EventID:    ev.Identifier,
            Type:       ev.Type,
            ParamKinds: inferEventParamKinds(ev),
        }

        if old, exists := b.eventLookup[key]; exists {
            b.eventLookupConflicts = append(b.eventLookupConflicts, EventLookupConflict{
                Key:         key,
                KeptEventID: old.EventID,
                DropEventID: meta.EventID,
            })
            continue
        }

        b.eventLookup[key] = meta
    }
}
```

`parseAlarmCode` 只在 L1 构建阶段执行一次：

```go
func parseAlarmCode(extendConfig string) (int, bool) {
    var cfg struct {
        AlarmCode int `json:"alarm_code"`
    }
    if err := json.Unmarshal([]byte(extendConfig), &cfg); err != nil {
        return 0, false
    }
    if cfg.AlarmCode <= 0 {
        return 0, false
    }
    return cfg.AlarmCode, true
}
```

如果同一个 `eventType + alarmCode` 出现重复，不建议让 schema 加载失败。线上已发布 schema 可能因为历史数据或并发发布问题出现重复事件码；如果 L1 schema 加载失败，会导致 eKuiper 侧该产品的所有设备上报都失败，影响面过大。

推荐策略：

1. 继续加载 schema，服务不中断。
2. 保留第一条事件映射，忽略后续重复项，保证运行时行为稳定。
3. 记录 warning 日志，包含 `ProductID`、`ReleaseID`、`eventType`、`alarmCode`、保留的 `EventID` 和被忽略的 `EventID`。
4. 增加监控指标，例如 `schema_event_lookup_conflict_total{product_id, release_id}`。
5. 将冲突明细保存到 L1 runtime 字段 `eventLookupConflicts`，供 debug 或健康检查接口查看。

选择“保留第一条”而不是“后者覆盖前者”，是为了让同一份 schema 在同一进程内的 lookup 结果稳定，也避免 map 构建顺序变化导致语义抖动。重复事件码本质上仍是 schema 数据问题，应通过监控告警推动人工修复，而不是在 eKuiper 侧静默吞掉。

## 7. 运行时使用方式
当前运行时逻辑：

```go
eventID := getEventIdentifier(eventType, alarmCode, tslEvents)
```

优化后：

```go
meta, ok := schemaBundle.LookupEventByCode(eventType, alarmCode)
if !ok {
    return eventMsgEvents
}

eventMsgEvents = append(eventMsgEvents, buildOneEventMsgSubDevieEvent(meta.EventID, timestamp, alarmStatus))
```

`LookupEventByCode` 只读 L1 内存结构：

```go
func (b *SchemaBundle) LookupEventByCode(eventType string, alarmCode int) (EventLookupMeta, bool) {
    if b == nil || b.eventLookup == nil {
        return EventLookupMeta{}, false
    }
    meta, ok := b.eventLookup[EventLookupKey{
        EventType: eventType,
        AlarmCode: alarmCode,
    }]
    return meta, ok
}
```

如果 `handlePushData` 当前只拿到了 `Model.Events`，可以先把 `eventLookup` 挂到 `Model` 上；但更推荐挂到 `SchemaBundle` 上，因为 lookup 的作用域是 `ProductID + ReleaseID`，并且构建时还可以同时生成 property dictionary。

## 8. 与事件存储的关系
事件链路不建议第一阶段做通用预分配池，原因如下：

1. 事件是差异存储，绝大多数周期没有输出或只有少量输出。
2. 当前 TDengine event 表是固定列：`ts`、`event_id`、`event_type`、`param`。
3. event `params` 当前会在 sink 边界 `json.Marshal` 成一个字段，不是多列 typed value 写入模型。
4. property typed payload 解决的是“全量点表高频写入”的对象图问题，事件链路的主要浪费在 schema 查找和重复 verify。

推荐事件链路第一阶段只做：

1. `eventType + alarmCode` 的 L1 lookup cache。
2. 小容量局部 slice，例如 `make([]EventChange, 0, 4)`。
3. 复用同一次 `VerifyEvents` 的结果，避免存储路径和 notify 路径重复校验。

## 9. 测试与验证
### 9.1 单元测试
1. `Fmt` 返回的 `SchemaBundle` 包含 `parsedModel` 和 `eventLookup`。
2. `Fmt` 不修改入参 `data`，尤其不能清空 `data.Model`。
3. `GetCurrentSchema` 和 `GetReleaseSchema` 使用同一个 `formatSchemaBundleForL1` helper。
4. `eventType + alarmCode` 能查到正确 `EventID`、`Type`、`ParamKinds`。
5. 缺失或非法 `alarm_code` 不进入 lookup。
6. 重复 `eventType + alarmCode` 不阻断 schema 加载，保留第一条映射，记录 warning 和冲突指标。
7. 重复冲突明细只存在于 L1 runtime 字段，不会被 marshal 回写 Redis。

### 9.2 Benchmark
对比两组：

1. 原始 `getEventIdentifier`：遍历 `tslEvents` 并反复 `json.Unmarshal(ExtendConfig)`。
2. L1 lookup：`map[EventLookupKey]EventLookupMeta` 直接查询。

关键指标：

1. `allocs/op`
2. `B/op`
3. 单次事件码查找耗时
4. 单次 PUSH_DATA 中事件解码总耗时

## 10. 推荐结论
事件优化应先做 schema lookup cache，而不是事件 payload 池。

落地顺序：

1. 统一 `GetCurrentSchema` / `GetReleaseSchema` 的 `Fmt`，确保 copy-on-format。
2. 在 `SchemaBundle` 或 `Model` 上增加本地 event lookup runtime index。
3. 在 `Fmt` 解析 model 后构建 `eventType + alarmCode` 索引。
4. 替换 `getEventIdentifier` 的遍历查找。
5. 再考虑复用 `VerifyEvents` 结果，减少存储和 notify 双重校验。

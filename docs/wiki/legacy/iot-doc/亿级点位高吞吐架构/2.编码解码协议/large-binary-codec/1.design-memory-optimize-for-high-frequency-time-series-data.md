这是一份整合了从微观数据结构到宏观内存架构的全链路优化方案，可以直接将其作为重构物联网平台的核心参考手册。

# Go 物联网平台高频时序数据内存优化全链路指南
## 1. 背景与痛点
在物联网平台场景中，设备周期性（如每秒）高频上传大量点位数据（如 500~1000 个点位/次）。平台需将二进制报文解析为内存结构。  
如果数据结构设计不当，在 Go 语言非移动式 GC 的机制下，极易导致：

+ **GC CPU 飙升**：STW 毛刺，服务卡顿。
+ **内存碎片化**：RSS 居高不下，甚至 OOM。
+ **吞吐量瓶颈**：内存分配锁竞争严重，并发上不去。

---

## 2. Go 内存核心概念厘清
### 2.1 什么是 Go 中的“大对象”？
+ **定义**：单一连续内存分配 > 32KB (32768 字节) 的对象。
+ **分配路径**：绕过常规的 `mcache/mcentral`，直接向 `mheap` 申请独立的 Span（由多个 8KB Page 组成）。
+ **判定时机**：通常在**运行时**由 `makeslice` 等函数根据动态计算的长度判定，而非编译期（除非硬编码常量）。

### 2.2 各类数据结构成为大对象的概率
| 数据类型 | 是否常为大对象 | 原因分析 |
| :--- | :--- | :--- |
| **Slice** | **极易** | Slice 头部仅 24B，但其**底层数组**极易超过 32KB。 |
| **Map** | **极难** | Map 头部很小，底层由多个独立的 Bucket 组成，单个 Bucket 远小于 32KB。 |
| **Struct** | **罕见** | 除非内部直接内嵌了巨型数组（如 `[4096]float64`），包含 Slice 并不会让 Struct 本身变大。 |


### 2.3 String 的底层本质
+ String 底层是一个**只读的字节切片引用**，结构为 `Data指针(8B) + Len长度(8B) = 16B`。
+ 与 Slice 相比，缺少了 `Cap` 容量字段，因为 String 不可变，无需扩容。
+ **隐患**：String 的真实数据（字符）是独立分配的小块内存，与 String 头部物理分离。

---

## 3. 数据结构演进与内存灾难剖析（微观层）
### 3.1 反模式：`[]map[string]any`
这是最直觉但性能最差的写法。

+ **内存布局**：假设 750 个点位，会产生 1 个 Slice 底层数组 + 750 个 Map + 750 个 String 底层数组 + 750 个 any(Interface) 装箱堆分配。
+ **后果**：约 **2200+ 次微小对象堆分配**。虽无单一 >32KB 大对象，但形成**“对象图灾难”**。GC 需追踪数千个指针，CPU 霸凌。

### 3.2 进阶模式：列式存储的局限
将行式转为列式，是正确的第一步，但如果只按纯数值遥测建模，仍然暗藏杀机。

`[]float64`** —— 只适合纯数值遥测的优等生**

+ 连续内存，整存整取。
+ 无指针，GC 扫描成本为零。
+ 即使超过 32KB 成为独立 Span 大对象，回收时也能整块归还 OS，**无外部碎片**。
+ 由于 Go GC 不移动内存，它死亡后留下的完美连续空洞，正好被下一个同尺寸 Slice 复用。
+ **限制**：真实设备点表同时包含 `string`、`int`、`float`，单一 `[]float64` 无法表达混合类型，只能作为纯数值子集的优化模型。

`Names []string`** —— 披着羊皮的碎纸机**

+ **“盘子”与“菜”分离**：Go 根据 Slice 容量分配“盘子”（存放 StringHeader 的连续数组），根据每个字符串长度分配“菜”（真实的字符内存）。
+ 1000 个点位 = 1 次 16KB 连续分配（盘子） + **1000 次 16B/32B 碎片分配（菜）**。
+ **混居导致外部碎片**：1000 份小菜散落在多个 8KB Span 中，与程序其他对象混居。当 Payload 被回收，只要 Span 里还有一个存活对象，整块 8KB 就无法归还 OS，形成千疮百孔的**外部碎片**。
+ **指针追踪暴击**：GC 必须顺着 1000 个指针逐一跳跃标记，严重破坏 CPU Cache。

## 4. 高频时序场景的微观结构优化（消灭指针）
在物联网时序数据场景，元数据（点名）是稳定的，数据（值）是变化的。绝不能用通用搜索结构承载高频时序数据。

### 🌟 方案一：字典化 + Typed Value Arena（新项目推荐）
将点位的字符串名称在系统启动、设备上线或 schema release 加载时注册到字典。高频流转过程只传递整型 ID，并使用分类型 arena 承载 `string`、`int`、`float` 点值。  
**优化前：**

```go
type DevicePayload struct {
    Names  []string  // 16KB + 1000次小对象分配，1000个指针
    Values []any     // 混合 string/int/float 时会产生装箱和对象图
}
```

**优化后：**

```go
type ValueKind uint8

const (
    ValueInt ValueKind = iota
    ValueFloat
    ValueString
)

type PointValueRef struct {
    PointID uint16
    Kind    ValueKind
    Index   uint32
}

type StringRef struct {
    Off uint32
    Len uint32
}

// 高频流转的最终结构
type ModulePayload struct {
    ModuleID      int64
    SchemaRelease int64
    Timestamp     int64

    Values []PointValueRef

    Ints    []int64
    Floats  []float64
    Strings []StringRef
    Text    []byte
}
```

外层 `ModulePayloadBatch` 保存设备标识：`ProductID string` 表示产品编码，不是产品表主键；`DeviceName string` 表示设备编码。`ProductID + DeviceName` 才能确定设备唯一性。

`SchemaRelease` / `ReleaseID` 统一使用 `int64`，与 `SchemaBundle.Meta.ReleaseID` 和 `PropertyDict.ReleaseID` 保持一致。

**收益**：

+ 点名从 `[]string` 变为 `PointID`，高频路径不再携带大量字符串 key。
+ `int`、`float`、`string` 分 arena 存储，避免 `[]any` 装箱和 map 对象图。
+ `Text []byte` + `StringRef` 让 string 点值的生命周期跟 payload 一致，可整块复用。

### 🌟 方案二：扁平化 Buffer（C 风格，适合无法字典化的场景）
如果必须在内存里保留字符串，将其压入一个连续的字节池，用偏移量切割。

```go
type DevicePayloadFlat struct {
    NamePool []byte   // 所有点位名拼在一起： "temp1\0humi1\0..."
    Offsets  []int32  // 记录每个名字在 NamePool 中的起始偏移量
    Values   []PointValueRef
    Ints     []int64
    Floats   []float64
    Text     []byte
}
```

**收益**：点名和值都收敛到连续 buffer 和 descriptor，依然保持低指针、低碎片的内存形态。

## 5. 宏观架构跃迁：抗住海量高频大对象的冲击（宏观层）
微观结构优化后，纯数值场景下的 `[]float64` 很理想；但真实设备点表通常同时包含 `string`、`int`、`float`，需要使用 typed value arena 表达混合类型点值。面对**大规模（10万+设备）高频（每秒）**上报，每秒仍会产生数以十万计的 8KB~40KB 大对象分配和回收。  
Go 原生的内存分配器和 GC **无法抗住这种级别的原生吞吐**，会引发三大宏观瓶颈：

1. **全局锁竞争**：>32KB 的大对象必须向 `mheap` 申请，而 `mheap` 加了全局锁，高并发下 Goroutine 全部卡在锁上。
2. **GC 位图扫描开销**：即使无指针，GC 每秒仍需扫描数十万个 Span 的元数据以确认“无指针”，耗费大量 CPU。
3. **mmap 疯狂抖动**：每秒数百 MB 的分配与归还，导致内核态与用户态频繁切换。  
**破局思想：从“依赖 GC 回收”转向“手动池化与复用”。破坏对象的创建与销毁循环，让内存常驻。**

### 🌟 宏观方案 1：基于设备型号的 Typed Payload 预分配池
新项目可以直接采用 `PointValueRef + Ints/Floats/Text arena`。它用轻量 descriptor 表达点位，用分类型 arena 存储 `int`、`float`、`string` 点值，避免单一 `[]float64` 无法表达混合类型，也避免 `map[string]any` 和 `[]string` 在高频路径制造大量对象图。

核心思路：

+ `PointID` 替代点位字符串名；它是 `ProductID + ReleaseID` 下由 eKuiper 本地派生的紧凑索引，不是 `dm_module_schema_info.id`。
+ `SchemaRelease + PointID` 在 sink 边界通过 schema dictionary 恢复 TDengine 列名。
+ schema dictionary 在 `release_schema_cache.go` 的 `Fmt` 阶段预生成，只写入本地 L1 otter cache；`Fmt` 必须 copy-on-format，不能修改入参 `data`，避免污染异步回写 L2 Redis 的原始 `SchemaBundle`。
+ `Ints []int64`、`Floats []float64`、`Text []byte` 分别承载不同类型的值。
+ `StringRef{Off, Len}` 引用 `Text` 中的字符串，避免高频路径持有大量 Go string 指针。
+ pool 按设备型号预分配容量，`Reset` 只重置长度，复用底层数组。
+ 高频 PUSH_DATA 使用 `DecodePropertiesIntoPayload + typed verifier`，绕开点级 map、`VerifyProperties`、`SplitByModule`、`decimal.Decimal` 和 `cast` 热路径。
+ 明确所有权：payload 归还池之前，下游不得继续持有它或它内部 slice 的引用；跨 goroutine 时所有权必须转移到最后一个消费者。

详细设计见：[基于设备型号的 Typed Payload 预分配池设计](3.design-model-payload-pool-with-typed-value-arena.md)。

属性 decode 与 verifier 的详细改造见：[属性 Typed Decode 与 Typed Verifier 改造设计](5.design-property-typed-decode-and-verifier.md)。

### 🌟 宏观方案 2：SQL Builder 池批量提交（当前最优先落地）
在当前 TDengine 写入链路中，设备点表主要是 `string`、`int`、`float`，并且 iot 侧采用“多条 TDengine INSERT fragment 拼成一条大 SQL 后集中发送”的方式。因此，第一阶段不应直接跳到 value ring buffer，而应先优化大 SQL 构造过程。

核心思路：

+ 使用 `bytes.Buffer` / `[]any` 池复用批量 SQL 构造过程中的大 buffer 和参数切片。
+ 单条记录只写 TDengine fragment，batch 层只保留一个外层 `INSERT INTO`。
+ 按 `maxBatchRows`、`maxSQLBytes`、`maxArgs` 切分 batch，避免单条 SQL 过大。
+ 缓存 module 写入模板，复用稳定的列名、placeholder、stable 名称和参数顺序。
+ `db.Exec` 返回后才能归还 builder 和 args，避免异步写入场景下提前复用导致数据污染。

详细设计见：[TDengine 批量写入 SQL Builder 池设计](2.design-sql-builder-pool-for-tdengine-batch-write.md)。

### 🌟 宏观方案 3：事件 Schema Lookup Cache（事件链路优先优化）
设备事件和设备属性的写入模型不同：属性是固定点表全量上传、全量解码、全量存储；事件是固定事件位图全量上传、全量解码，但只在状态变化时存储。大部分周期内事件没有存储输出，或者只输出少量变化事件。因此事件链路第一阶段不建议做和属性一样的 typed payload 预分配池。

事件链路更值得优先优化的是 schema 查找：

+ 在 schema release 进入本地 L1 otter cache 的 `Fmt` 阶段，预生成 `eventType + alarmCode -> EventID/Type/ParamKinds` lookup。
+ 运行时事件解码不再遍历 `tslEvents`，也不再反复 `json.Unmarshal(ExtendConfig)`。
+ lookup cache 只属于 L1 本地运行时索引，不写入 Redis。
+ `Fmt` 必须 copy-on-format，不能直接修改入参 `data`，否则 L3 miss 后异步回写 L2 Redis 时会污染原始 schema bundle。

详细设计见：[设备事件 Schema Lookup Cache 设计](4.design-event-schema-lookup-cache.md)。

### 🌟 宏观方案 4：Ring Buffer 批量提交（下一阶段展望）
时序数据最忌讳“来一条写一条”。通常是攒一波（比如 1000 台设备的数据），批量写入底层存储。

```go
// descriptor + value arenas 按环形批量使用
type ValueRingBuffer struct {
    Descriptors []PointValueRef
    Ints        []int64
    Floats      []float64
    Text        []byte
    Head        uint64
    Tail        uint64
}
// 每次设备上报追加 descriptor 和分类型 value arena，flush 成功后推进 Head。
```

**收益**：

+ 全局只有 1 个大 Slice，内存分配极简，无锁竞争。
+ 配合批量写入数据库，磁盘 IO 效率最高。

注意：当前 property 链路并不是纯 `float64` 模型，还需要表达 `string/int/float` 点值、product/device/module、timestamp、tag 和重试边界。真正可落地的 ring buffer 应至少包含 descriptor ring、numeric value arena、text arena、flush cursor、retry cursor 和 backpressure 策略。事件参数如果后续需要 JSON，应作为独立 event 路径设计，不混入当前 property `ValueKind`。因此 ring buffer 更适合作为 SQL builder 池之后的下一阶段演进，而不是第一阶段改造入口。

## 6. 核心结论与避坑指南
1. **大对象并不可怕**：Go 对 >32KB 的连续无指针数组管理极好，整存整取，无外部碎片，GC 扫描零成本。
2. **指针是碎片的万恶之源**：评估一个结构体是否会引发 GC 灾难和内存碎片，**不要看它占了多大内存，而要看它包含多少个指针**。每一个指针，都是一次独立的堆分配，也是未来产生外部碎片的隐患。
3. `[]string`** 是高频场景的禁忌**：它看似是一个数组，实则是成百上千个碎片的集合。
4. **非移动式 GC 的好朋友是“值类型”**：Go GC 不移动内存，因此它最喜欢“生死同穴”的对象（连续分配，连续死亡，留下完美空洞）。`[]uint16`、`[]int64`、`[]float64`、`[]byte` arena 都是典范。
5. **微观优化是宏观优化的前提**：只有把高频结构里的指针和对象图压到最低（例如使用 `PointValueRef + Ints/Floats/Text arena`），才能安全地做池化复用。带指针对象也能使用 pool，但必须清楚所有权和生命周期，否则很容易因为间接引用导致内存无法释放或数据被复用污染。
6. **高频吞吐的终极杀器是“复用”而非“分配”**：当并发规模上去了，`make` 就是毒药，`sync.Pool` 和 `Ring Buffer` 才是解药。

---

**下一步行动建议：**

1. **第一步（数据结构定型）**：新项目优先引入 [Typed Payload 预分配池](3.design-model-payload-pool-with-typed-value-arena.md)，用 `PointValueRef + Ints/Floats/Text arena` 替代高频路径中的 `map[string]any`、`[]string` 和单一 `[]float64`。
2. **第二步（属性热路径改造）**：按 [属性 Typed Decode 与 Typed Verifier 改造设计](5.design-property-typed-decode-and-verifier.md) 落地 `PropertyDict`、`DecodePropertiesIntoPayload`、typed verifier 和 `propertyTypedBatch` sink。
3. **第三步（写入侧提速）**：引入 [SQL Builder 池](2.design-sql-builder-pool-for-tdengine-batch-write.md)，复用批量 SQL buffer、参数切片和 module 写入模板，降低 TDengine 写入前的大字符串构造成本。
4. **第四步（事件查找提速）**：引入 [事件 Schema Lookup Cache](4.design-event-schema-lookup-cache.md)，把 `eventType + alarmCode` 的查找前移到 schema L1 cache 构建阶段。
5. **第五步（所有权固化）**：明确 payload 从 decode 到 sink 的所有权转移，确保 `db.Exec` 或最后一个消费者完成后才归还 pool。
6. **第六步（极限）**：在 SQL builder 池和 typed payload 复用仍不足时，再评估 value ring buffer、text arena 和 descriptor ring，进一步降低 IO 和内存流转频率。

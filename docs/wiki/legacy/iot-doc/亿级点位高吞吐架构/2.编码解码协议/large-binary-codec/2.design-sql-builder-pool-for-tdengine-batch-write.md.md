# TDengine 批量写入 SQL Builder 池设计
## 1. 背景
当前高频时序数据链路中，设备点表主要包含 `string`、`int`、`float` 三类值。写入 TDengine 时，链路并不是直接把值放进一个纯数值环形缓冲区，而是需要生成 TDengine multi-table INSERT：

```sql
INSERT INTO
  device_module__p1__d1__m1 USING model_module__m1 TAGS(...) (`ts`,`Pac`,`Uac`) VALUES (?,?,?)
  device_module__p1__d2__m1 USING model_module__m1 TAGS(...) (`ts`,`Pac`,`Uac`) VALUES (?,?,?)
```

因此，当前阶段的主要内存热点不是单纯的 `[]float64` 分配，而是：

1. 每条记录构造一段 SQL fragment。
2. 每条记录构造 `cols`、`placeholders`、`args` 等临时切片。
3. 批量提交前再把多段 SQL 拼成一条大 SQL。
4. 大 SQL 构造过程中可能发生多次字符串复制和扩容。

SQL Builder 池的目标，是在不改变现有数据契约和 TDengine 写入语义的前提下，先降低 SQL 构造阶段的临时对象数量和大字符串复制次数。

## 2. 设计目标
### 2.1 目标
1. 复用批量 SQL 构建时的大 buffer，减少高频大字符串分配。
2. 复用 `[]any` 参数切片，减少每个 batch 的参数切片扩容。
3. 缓存 module 写入模板，减少列名、placeholder 和稳定 SQL 片段的重复构造。
4. 保留当前 `database/sql` 参数化写入方式，不把值直接拼进 SQL。
5. 继续支持按 `maxBatchRows`、`maxSQLBytes`、`maxArgs` 切分 batch。
6. 保持错误返回和 eKuiper sink node retry/cache 语义一致。

### 2.2 非目标
1. 不在本阶段实现 value ring buffer。
2. 不改变上游 `map[string]any` 的数据契约。
3. 不要求所有点位先字典化为整型 ID。
4. 不实现自定义 TDengine wire protocol。
5. 不在 sink 内部做无限重试。

## 3. 为什么不是“字符串池”
Go 的 `string` 是不可变值。最终传给 `db.Exec(sql, args...)` 的 SQL 字符串一旦生成，就不适合被复用或修改。

真正值得池化的是构建过程中的可变对象：

1. `bytes.Buffer`：复用底层 `[]byte`，承载一条 batch SQL 的构造过程。
2. `[]any`：复用参数列表底层数组。
3. SQL 模板：缓存稳定的列名、placeholder、stable/table 片段生成规则。

最终 SQL 仍然是一次性字符串，只在 `Exec` 调用期间有效。`Exec` 返回后，builder 和 args 才能归还池。

## 4. 当前链路的主要问题
### 4.1 重复构造单条 SQL
当前实现倾向于每条记录先生成一个 `sqlStr`，再收集到 `sqlClauses`。这会产生大量短生命周期字符串。

```go
sqlStr, args, err := BuildPropertySQL(database, record)
sqlClauses = append(sqlClauses, sqlStr)
allArgs = append(allArgs, args...)
```

优化方向：不要为每条记录返回完整 SQL 字符串，改为直接把 fragment 写入 batch builder。

### 4.2 大 SQL 使用字符串累加
如果使用 `fullSQL += " " + clause` 拼接大 SQL，每追加一次都可能复制已有内容。batch 越大，复制成本越明显。

优化方向：使用 `bytes.Buffer` 或 `strings.Builder` 一次性流式写入。

### 4.3 SQL fragment 契约需要统一
TDengine multi-table INSERT 推荐的结构是外层只有一个 `INSERT INTO`，每条记录生成的是 fragment：

```sql
device_module__p1__d1__m1 USING model_module__m1 TAGS(...) (`ts`,`Pac`) VALUES (?,?)
```

因此，property/event SQL 生成函数应该统一为：

1. `WritePropertyClause(builder, record, args)`：只写 fragment，不写外层 `INSERT INTO`。
2. `WriteEventClause(builder, record, args)`：只写 fragment，不写外层 `INSERT INTO`。
3. `FlushBatch`：负责写外层 `INSERT INTO` 并提交完整 SQL。

如果单条 SQL 函数返回完整 `INSERT INTO ...`，批量拼接层又额外加 `INSERT INTO`，会造成 SQL 契约混乱。

## 5. 核心结构
### 5.1 Batch Builder
```go
type tdengineBatchBuilder struct {
    buf         bytes.Buffer
    args        []any
    rows        int
    approxBytes int
}
```

字段说明：

1. `buf`：保存完整 batch SQL，生命周期只覆盖一次构建和一次 `Exec`。
2. `args`：保存 `db.Exec` 参数，顺序必须与 SQL placeholder 一致。
3. `rows`：当前 batch 已写入的记录数。
4. `approxBytes`：用于切分 batch 的估算字节数。

### 5.2 Pool
```go
var tdengineBuilderPool = sync.Pool{
    New: func() any {
        return &tdengineBatchBuilder{
            args: make([]any, 0, 1024),
        }
    },
}
```

借出：

```go
b := tdengineBuilderPool.Get().(*tdengineBatchBuilder)
b.resetForUse()
```

归还：

```go
b.release(maxRetainedSQLBytes, maxRetainedArgsCap)
tdengineBuilderPool.Put(b)
```

释放策略：

```go
func (b *tdengineBatchBuilder) release(maxSQLBytes int, maxArgsCap int) {
    if b.buf.Cap() > maxSQLBytes {
        b.buf = bytes.Buffer{}
    } else {
        b.buf.Reset()
    }

    if cap(b.args) > maxArgsCap {
        b.args = nil
    } else {
        b.args = b.args[:0]
    }

    b.rows = 0
    b.approxBytes = 0
}
```

这里必须设置容量上限。否则一次异常大的 SQL 可能把巨型 buffer 长期留在池里，导致 RSS 难以下降。

## 6. SQL 模板缓存
### 6.1 为什么需要模板缓存
同一个 product/module/schema release 下，属性列集合通常稳定。每次上报都重新生成：

1. 反引号列名：`` `Pac`,`Uac` ``
2. placeholders：`?,?,?`
3. stable 名称：`` `model_module__inv_runtime` ``
4. 参数顺序

这些都是重复劳动。

### 6.2 缓存 Key
建议使用以下维度作为 key：

```go
type moduleWritePlanKey struct {
    database      string
    productID     string
    moduleCode    string
    schemaRelease string
    fieldSetHash  uint64
}
```

说明：

1. `database`：不同库可能有不同命名空间。
2. `productID`：产品下的 schema 和字段集合更稳定。
3. `moduleCode`：module stable 的物理路由 key。
4. `schemaRelease`：避免产品发布后旧模板误用。
5. `fieldSetHash`：如果同一 module 存在稀疏字段上报，用字段集合 hash 区分模板。

如果当前链路暂时拿不到 `schemaRelease`，可以先使用 `productID + moduleCode + sortedIdentifiersHash`，后续再补 release 版本。

### 6.3 缓存 Value
```go
type moduleWritePlan struct {
    stableName   string
    columnsSQL   string
    valuesSQL    string
    identifiers  []string
}
```

示例：

```go
moduleWritePlan{
    stableName:  "`model_module__inv_runtime`",
    columnsSQL:  "(`ts`,`Pac`,`Uac`)",
    valuesSQL:   "VALUES (?,?,?)",
    identifiers: []string{"Pac", "Uac"},
}
```

`identifiers` 的顺序必须稳定。不要直接使用 `map` 遍历顺序作为 SQL 列顺序。推荐顺序：

1. schema 定义顺序。
2. route 中的 module 字段顺序。
3. 如果没有 schema 顺序，使用 identifier 字典序作为兜底。

## 7. 写入流程
### 7.1 CollectList 主流程
```go
func (s *cloudxTdengineSink) collectList(ctx api.StreamContext, records []map[string]any) error {
    b := acquireBatchBuilder()
    defer releaseBatchBuilder(b)

    for _, record := range records {
        if record["sinkType"] != "tdengine" {
            continue
        }

        estimate, argCount, err := estimateRecord(record)
        if err != nil {
            return err
        }

        if b.needFlush(s.cfg, estimate, argCount) {
            if err := s.execBatch(b); err != nil {
                return err
            }
            b.resetForNextBatch()
        }

        if b.rows == 0 {
            b.buf.WriteString("INSERT INTO ")
        } else {
            b.buf.WriteByte(' ')
        }

        if err := writeRecordClause(b, record); err != nil {
            return err
        }
    }

    if b.rows > 0 {
        return s.execBatch(b)
    }
    return nil
}
```

### 7.2 写 property clause
```go
func writePropertyClause(b *tdengineBatchBuilder, record map[string]any) error {
    plan, err := getModuleWritePlan(record)
    if err != nil {
        return err
    }

    b.buf.WriteString(subtableName(record))
    b.buf.WriteString(" USING ")
    b.buf.WriteString(plan.stableName)
    b.buf.WriteString(" TAGS(")
    writeTags(&b.buf, record)
    b.buf.WriteByte(')')
    b.buf.WriteByte(' ')
    b.buf.WriteString(plan.columnsSQL)
    b.buf.WriteByte(' ')
    b.buf.WriteString(plan.valuesSQL)

    b.args = append(b.args, record["timestamp"])
    params := record["params"].(map[string]any)
    for _, id := range plan.identifiers {
        v, err := paramToValue(params[id])
        if err != nil {
            return err
        }
        b.args = append(b.args, v)
    }

    b.rows++
    return nil
}
```

### 7.3 写 event clause
事件写入字段通常稳定，可以使用更简单的固定模板：

```go
const eventColumnsSQL = "(`ts`,`event_id`,`event_type`,`param`)"
const eventValuesSQL = "VALUES (?,?,?,?)"
```

事件 `params` 如果后续进入独立 event 表，可能仍需要序列化为 JSON。当前 property 写入只处理 `string/int/float`，不引入 JSON value，也不把 event 参数混入 property typed payload。

## 8. Flush、Retry 和 Backpressure
### 8.1 Flush 触发条件
一个 batch 应在以下条件触发 flush：

1. `rows >= maxBatchRows`
2. `approxBytes + nextBytes > maxSQLBytes`
3. `len(args) + nextArgCount > maxArgs`
4. `CollectList` 处理完成

### 8.2 Exec 生命周期
builder 和 args 的归还必须发生在 `db.Exec` 返回之后：

```go
sqlText := b.buf.String()
_, err := db.Exec(sqlText, b.args...)
```

如果当前执行是同步的，`Exec` 返回后可以立即复用 builder。

如果后续改成异步队列，则不能把 builder 直接交给队列后立刻归还。异步队列必须拥有自己的 `query string` 和 `args` 副本，或明确由队列负责归还 builder。

### 8.3 错误分类
1. 数据契约错误：缺少 `productID`、`deviceName`、`moduleCode`、`params` 类型错误、字段无法序列化。这类错误直接返回普通 error。
2. IO 错误：连接断开、TDengine timeout、driver Exec 失败。这类错误包装为 `errorx.NewIOErr`，交给 eKuiper sink node 的 retry/cache。

### 8.4 Backpressure
SQL builder 池本身不解决下游写入慢的问题。下游慢时，必须依赖：

1. eKuiper sink node 的 buffer/cache 策略。
2. `database/sql.DB` 连接池限制。
3. `maxBatchRows` 和 `maxSQLBytes` 控制单次请求大小。

不要为了吞吐在 sink 内部无限排队，否则内存优化会变成内存堆积。

## 9. 容量建议
初始建议：

```json
{
  "maxBatchRows": 200,
  "maxSQLBytes": 1048576,
  "maxArgs": 10000,
  "maxRetainedSQLBytes": 2097152,
  "maxRetainedArgsCap": 20000
}
```

说明：

1. `maxSQLBytes` 控制单条 SQL 大小，避免 TDengine 和 driver 层出现超大请求。
2. `maxRetainedSQLBytes` 控制池里保留的 buffer 容量，通常可设为 `2 * maxSQLBytes`。
3. `maxArgs` 需要结合 TDengine driver 参数限制压测确认。
4. 对 500~1000 点位的设备，应使用估算函数提前判断单条 module record 是否已经超限。

## 10. 验证方案
### 10.1 单元测试
先写失败测试，再实现：

1. property SQL clause 不包含外层 `INSERT INTO`。
2. batch SQL 只有一个外层 `INSERT INTO`。
3. 多条 property record 的 args 顺序与 SQL 列顺序一致。
4. `maxBatchRows` 超限时切分为多个 Exec。
5. `maxSQLBytes` 超限时切分为多个 Exec。
6. buffer 容量超过保留阈值时不会放回池。
7. event record 与 property record 可以在同一批次内按 TDengine multi-table INSERT 拼接。

### 10.2 Benchmark
建议对比三组：

1. 当前实现：每条 record 返回 SQL string，再拼大 SQL。
2. Builder 池：直接写 batch SQL，复用 buffer 和 args。
3. Builder 池 + 模板缓存：列名和 placeholder 走缓存。

关键指标：

1. `ns/op`
2. `B/op`
3. `allocs/op`
4. p95/p99 `CollectList` 耗时
5. GC CPU
6. `heap_alloc`、`heap_inuse`、RSS

示例命令：

```bash
go test ./extensions/impl/cloudx -run TestTdengineBatchBuilder -bench BenchmarkTdengineBatchBuilder -benchmem
```

### 10.3 压测指标
压测报告必须记录：

1. 设备数量。
2. 每台设备点位数。
3. 上报频率。
4. property/event 比例。
5. schema release。
6. `maxBatchRows`、`maxSQLBytes`、`maxArgs`。
7. TDengine driver 和服务端版本。
8. eKuiper 规则版本。

没有这些上下文，内存和吞吐数据不可横向比较。

## 11. 风险与边界
### 11.1 map 遍历顺序
如果直接遍历 `params map[string]any` 生成列和值，每次 SQL 列顺序都可能变化。只要 args 顺序同步，语义仍然正确，但模板缓存命中率会变差，也不利于排查问题。

建议使用 schema 顺序或排序后的 identifiers。

### 11.2 string 值仍会分配
SQL builder 池只能降低 SQL 构造过程的分配。设备点位中的 `string` 值本身如果来自解析阶段的新字符串，仍然会有独立分配。这个问题需要在上游解析结构、字典化或字节池阶段解决。

### 11.3 event 参数
当前 property 路径不支持复杂属性 JSON，也不需要 JSON value。后续如果独立 event 写入路径需要 JSON 序列化，`json.Marshal` 仍会产生 `[]byte`，届时再评估 event 参数 buffer 池或更紧凑的事件结构。

事件链路第一阶段更优先的优化不是 event 参数池，而是 schema lookup cache：在 `SchemaBundle` 进入本地 L1 cache 时预生成 `eventType + alarmCode` 索引。详细设计见：[设备事件 Schema Lookup Cache 设计](4.design-event-schema-lookup-cache.md)。

### 11.4 sync.Pool 不保证常驻
`sync.Pool` 中的对象可能在 GC 后被清理。它用于摊薄分配成本，不适合作为严格容量控制队列。实现上必须允许 pool miss 并重新分配。

## 12. 下一阶段展望
### 12.1 Value Ring Buffer
当 SQL builder 池和模板缓存仍无法满足吞吐目标时，再考虑 value ring buffer。它不应是单一 `[]float64`，而应至少包含：

1. descriptor ring：描述每条记录的 product/device/module/timestamp/字段集合。
2. numeric value arena：存放 int/float/bool 等值类型。
3. string arena：存放 string 点值或 tag 字符串快照。
4. 可选 event 参数 arena：仅在后续独立 event 路径需要时引入，不进入当前 property `ValueKind`。
5. flush cursor：标记哪些数据已经成功写入 TDengine。
6. retry cursor：失败后可重放同一批 descriptor。
7. backpressure 策略：ring 满时阻塞、丢弃或交给上游缓存。

这种方案改动面更大，因为它会改变数据在解析、校验、路由、写入之间的所有权模型。只有在 SQL builder 池已经证明不够时，才值得进入。

### 12.2 字典化 Payload
在 schema release 稳定的前提下，可以把高频流转结构从：

```go
map[string]any{"Pac": 123.4, "Uac": 220}
```

逐步收敛为：

```go
type ModulePayload struct {
    ProductID     uint32
    DeviceID      uint64
    ModuleID      uint32
    SchemaRelease uint64
    PointIDs      []uint16
    Values        []TypedValue
}
```

sink 边界再通过 schema release 把 `PointID` 恢复为 TDengine 列名。这样可以减少上游 `map[string]any` 和字符串 key 的对象图压力。

### 12.3 更细粒度的 arena
如果 string 点值占比高，可以引入局部 arena：

1. 每个 batch 一个 string arena。
2. descriptor 中只保存 offset/length。
3. batch flush 完成后整块 arena 归还或丢弃。

这比全局 string 池更安全，因为生命周期和 batch 一致，不容易出现悬挂引用。

## 13. 推荐落地顺序
1. 统一 SQL fragment 契约：单条 record 只生成 fragment，batch 层负责唯一的 `INSERT INTO`。
2. 引入 `tdengineBatchBuilder`，去掉 `[]string sqlClauses` 和 `fullSQL +=`。
3. 池化 builder 和 args，并加容量上限。
4. 为 property/event 写单元测试，覆盖 batch 切分和 args 顺序。
5. 增加 benchmark，记录当前实现与 builder 池的 `allocs/op` 和 `B/op`。
6. 引入 module 写入模板缓存。
7. 压测后再决定是否进入 value ring buffer 或字典化 payload。

# 属性 Typed Decode 与 Typed Verifier 改造设计
## 1. 背景
当前高频 PUSH_DATA 属性链路是：

```latex
DecodeProperties
  -> []map[string]any{ {"params": map[string]any{identifier: val}} }
  -> extractPropertiesParams 合并成 map[string]any
  -> buildPropertyMap 每次上报重建 schema map
  -> VerifyProperties(model, []map[string]any)
  -> SplitByModule 再构造 moduleCode -> params map
  -> BuildPropertySQL 遍历 params map
```

这条链路的主要问题是“每个点位都在制造对象图”：

1. `DecodeProperties` 每个属性都 `json.Unmarshal(ExtendConfig)`。
2. 每个属性都扫描 `deviceMsgInverter["DATA"]`。
3. 同一个 modbus 数据块可能被重复 `hex.DecodeString`。
4. 每个属性创建一个 property map 和一个 params map。
5. `extractPropertiesParams` 再创建一个全量 params map。
6. `buildPropertyMap` 每次上报根据 L1 的 `schema.Properties` 重建 schema map。
7. `VerifyProperties` 再创建 normalized map，并在 `getVal` 中使用 `any/cast/decimal.Decimal` 归一化。
8. `SplitByModule` 再创建 module map。

百万设备周期上报时，点级 map、`any` 装箱、`cast` 和 `decimal.Decimal` 都会变成持续性 CPU 与内存成本。

## 2. 改造目标
高频 PUSH_DATA 属性链路不再调用：

1. `DecodeProperties`
2. `extractPropertiesParams`
3. `buildPropertyMap`
4. `VerifyProperties`
5. `SplitByModule`

这些旧函数保留给兼容路径、低频路径和对比测试使用。

新链路改为：

```latex
SchemaBundle 进入 L1 Fmt
  -> BuildRuntimeIndexes
  -> PropertyDict / PropertyPointPlan

PUSH_DATA
  -> DecodePropertiesIntoPayload
  -> typed verifier
  -> ModulePayloadBatch
  -> propertyTypedBatch record
  -> BuildPropertySQLFromBatch
```

最终目标：

1. 属性热路径不生成点级 `map[string]any`。
2. 属性热路径不重建 schema map。
3. 属性热路径不使用 `decimal.Decimal`。
4. 属性热路径不使用 `cast` 做反射式转换。
5. 每个 modbus 数据块的 `VALUE` 最多 decode 一次。
6. decode、verify、split by module 合并成一次按 plan 写入 typed payload 的过程。

## 3. SchemaRuntimeIndex 与 PropertyDict
`PropertyDict` 应在 `release_schema_cache.go` 的 `Fmt` 阶段预生成，只进入本地 L1 otter cache，不写入 L2 Redis。

推荐结构：

```go
type PropertyDict struct {
    ProductID string
    ReleaseID int64

    Points  []PropertyPointPlan
    Modules []ModuleMeta

    // 兼容和低频路径可用；高频 decode 主路径不依赖这个 map。
    ByIdentifier map[string]uint16
}

type ModuleMeta struct {
    ModuleIndex uint16
    ModuleID    int64
    ModuleCode  string
}
```

这里的 `ProductID` 语义与 `ModulePayloadBatch.ProductID` 一致，表示产品编码字符串，不是产品表主键。设备唯一性在 batch 层由 `ProductID + DeviceName` 表达。

每个属性点位预生成一份 plan：

```go
type PropertyPointPlan struct {
    PointID    uint16
    Identifier string

    ModuleIndex uint16
    ModuleID    int64
    ModuleCode  string
    ColumnSQL   string

    ValueKind ValueKind
    DataType  schema.DataType

    BaseAddr  int32
    VDataType string
    DecodeKind PropertyDecodeKind
    Scaler    int8

    HasMinInt bool
    MinInt    int64
    HasMaxInt bool
    MaxInt    int64
    StepInt   int64

    HasMinFloat bool
    MinFloat    float64
    HasMaxFloat bool
    MaxFloat    float64
    StepFloat   float64

    MaxStringLen int
    EnumAllowed  []int64
}
```

`PropertyDecodeKind` 用来把当前代码里的字符串判断前移到 schema 构建阶段：

```go
type PropertyDecodeKind uint8

const (
    DecodeU16 PropertyDecodeKind = iota
    DecodeS16
    DecodeU32
    DecodeS32
    DecodeU32Version
    DecodeString20
    DecodeString22
    DecodeBCDTime6
    DecodeSkip8
    DecodeSkip38
    DecodeSkip40
)
```

构建 plan 时完成这些工作：

1. 解析 `ExtendConfig`，拿到 `base-addr`、`scaler`、`vdata_type`。
2. 根据 `Define.Type` 推导 `ValueKind`。
3. 根据 `Route[identifier]` 写入 `ModuleID`、`ModuleCode`、`ModuleIndex`。
4. 生成并校验 `ColumnSQL`。
5. 解析 `min/max/step` 为 int 或 float，不在热路径里 `cast`。
6. 把 enum mapping 预解析为 `[]int64`，排序后高频路径二分查找。
7. 把 `U32` 版本号这种特殊逻辑预标记为 `DecodeU32Version`，避免热路径 `strings.ContainsAny(tslName, "版本")`。

### 3.1 容量估算
`PropertyPointPlan` 是为了把热路径上的 `json.Unmarshal`、`map` 查找、`cast`、`decimal.Decimal` 等成本前移到 L1 schema 加载阶段。它不是零成本结构，需要估算 L1 内存占用。

单点 plan 的主要开销：

1. 结构体本体：多个 int、float、bool、enum kind 字段，约 `100~160B`，具体取决于 Go 对齐。
2. `Identifier string`、`ModuleCode string`、`ColumnSQL string`：每个 string header 约 `16B`，底层字节通常与 parsed model 共享或由构建阶段新生成。`ColumnSQL` 通常会新分配。
3. `EnumAllowed []int64`：slice header 约 `24B`；有 enum 时还会有独立的 int64 数组。
4. `ByIdentifier map[string]uint16`：兼容和低频路径使用，按点位数还会带来 map bucket 开销。

保守估算：一个 `PropertyPointPlan` 按 `200~300B` 计比较稳妥。典型规模：

| 点位数 | Points 估算 | 加上 ByIdentifier / enum / 字符串后 |
| :--- | :--- | :--- |
| 100 | 20KB~30KB | 30KB~60KB |
| 500 | 100KB~150KB | 150KB~300KB |
| 1000 | 200KB~300KB | 300KB~600KB |


如果 L1 同时保留 1000 个 `ProductID + ReleaseID + Scope`，仅 property runtime index 就可能达到 `300MB~600MB`。因此需要给 schema L1 cache 设置条目上限或权重上限，不能无限缓存所有历史 release。

建议：

1. `current schema` 和仍有设备使用的 release 优先保留。
2. 旧 release 依赖 L1 cache TTL / max entries 淘汰；淘汰后如果仍有设备命中，可从 L2/L3 重新加载。
3. L1 指标至少暴露 `schema_l1_entries`、`property_plan_points_total`、`property_plan_estimated_bytes`、`schema_l1_evictions_total`。
4. 如果内存压力明显，可把 `Identifier/ModuleCode/ColumnSQL` 做字符串驻留，或把 `ColumnSQL` 延迟到 sink 模板构建阶段生成。
5. 如果 `ByIdentifier` 只服务低频兼容路径，可以按开关构建；高频 typed decode 主路径只需要 `Points` 的顺序数组。

## 4. Fmt 与 copy-on-format
`PropertyDict` 的构建入口应是 `GetCurrentSchema` / `GetReleaseSchema` 的 `Fmt`。

推荐统一 helper：

```go
func formatSchemaBundleForL1(ctx context.Context, key client.ProductReleaseKey, data *schema.SchemaBundle) *schema.SchemaBundle {
    if data == nil {
        return nil
    }

    copied := *data
    if err := copied.ParseModel(); err != nil {
        // log warn
    }
    if err := copied.BuildRuntimeIndexes(); err != nil {
        // log warn or fail fast
    }
    copied.Model = nil
    return &copied
}
```

必须注意：

1. `Fmt` 不能直接修改入参 `data`。
2. L3 HTTP miss 时，原始 `data` 会异步 marshal 回写 Redis。
3. `copied.Model = nil` 只能发生在 copy 上。
4. `PropertyDict`、event lookup 等运行时索引必须是 `json:"-"` 或非导出字段。
5. 当前 `GetReleaseSchema` 的 `Fmt` 直接修改 `data`，应先改成统一 helper。
6. `PropertyDict.PoolKey.ReleaseID` 必须来自最终 `SchemaBundle.Meta.ReleaseID`。如果 `tsl` 内的 `Meta.ReleaseID` 为空，应在 `loadSchemaBundle` 中用外层 `runtime-schema-batch` 返回的 `entry.ReleaseID` 回填后再构建 runtime index。

## 5. ModulePayloadBatch
因为 plan 已经包含 `ModuleIndex`，decode 时不需要再 `SplitByModule`。

```go
type ModulePayloadBatch struct {
    ProductID     string
    DeviceName    string
    SchemaRelease int64
    Timestamp     int64

    Modules      []ModulePayload
    Blocks       []ModbusBlock
    BlockScratch []byte

    pool *ModelPayloadPool // internal, set by PayloadPoolManager.Borrow
}
```

`ModulePayloadBatch` 应从设备型号预分配池借出。池 key 来自当前设备实际命中的 `PropertyDict.PoolKey`，也就是 `ProductID + ReleaseID + Scope`。`DeviceRuntimeMeta.SchemaReleaseIDOverride` 只决定走 `GetReleaseSchema` 还是 `GetCurrentSchema`；即使设备走的是 `GetCurrentSchema`，也要使用返回的 `bundle.Meta.ReleaseID`，不能使用请求 key 中的 `ReleaseID=0`。

调用方不直接保存 `ModelPayloadPool`，也不直接调用 `pool.Put(batch)`。`PayloadPoolManager.Borrow(dict)` 会把所属 pool 绑定到 batch 的内部字段；最终消费者只调用 `batch.Release()`。这样 batch 跨 goroutine 转移到 TDengine sink 时，不需要同时传递 `batch` 和 `pool` 两个引用。

初始化时按 `dict.Modules` 预分配。`Modules[i]` 的下标就是 `ModuleIndex`，稳定模块元数据从 `dict.Modules[i]` 读取，不需要在每个 payload 中重复保存 `ModuleCode` 字符串。

`BlockScratch` 也应预分配，但只预分配 capacity，不预置长度：

1. `BlockScratch` 是本次上报内 `DATA.VALUE` hex decode 后的临时 byte arena。
2. `NewModulePayloadBatch` 中使用 `make([]byte, 0, dict.MaxBlockBytes)`，`len` 必须为 `0`。
3. 每次借出或归还时执行 `b.Blocks = b.Blocks[:0]` 和 `b.BlockScratch = b.BlockScratch[:0]`。
4. `MaxBlockBytes` 更准确地说是“池愿意长期保留的 `BlockScratch` capacity”，不是业务正确性的硬上限。
5. 它对应一次上报中所有 hex string `VALUE` 解码后的字节总量，不是 hex 字符串长度；hex 字符串长度约为它的 2 倍。
6. 如果暂时无法从 schema 精确估算 `MaxBlockBytes`，不阻塞落地：先使用配置默认值，运行时允许临时扩容，并在 `Put` 时对 `cap(BlockScratch)` 做上限保护，超限 batch 不放回池。
7. 真正的异常大包保护应使用独立的 `HardBlockBytesLimit`，避免单次异常报文导致进程内存被打爆。
8. `Blocks` 是 `ModbusBlock` descriptor 切片，也建议放进 batch 中复用，避免每次 `buildModbusBlocks` 都分配一个新的 descriptor slice。
9. 默认 `Reset` 只清长度，不清 `BlockScratch` 底层数组。当前遥测场景优先性能；如果后续 `DATA.VALUE` 包含敏感内容，应按 pool 配置启用安全擦除，详见 [基于设备型号的 Typed Payload 预分配池设计](3.design-model-payload-pool-with-typed-value-arena.md)。

```go
func NewModulePayloadBatch(dict *PropertyDict) *ModulePayloadBatch {
    b := &ModulePayloadBatch{
        ProductID:     dict.ProductID,
        SchemaRelease: dict.ReleaseID,
        Modules:       make([]ModulePayload, len(dict.Modules)),
        Blocks:        make([]ModbusBlock, 0, dict.MaxBlocks),
        BlockScratch:  make([]byte, 0, dict.MaxBlockBytes),
    }
    for i := range dict.Modules {
        b.Modules[i].ModuleID = uint32(dict.Modules[i].ModuleID)
    }
    return b
}
```

实际实现中应按 `ProductID + ReleaseID + Scope` 做 pool，`Reset` 时只清长度，不清底层数组。详细池生命周期见：[基于设备型号的 Typed Payload 预分配池设计](3.design-model-payload-pool-with-typed-value-arena.md)。

### 5.1 无法精算 MaxBlockBytes 时的策略
`MaxBlockBytes` 不要设计成必须精确计算的 schema 字段。它是性能优化参数，不是解码正确性的前提。

推荐策略：

1. `PropertyDict.MaxBlockBytes` 先取配置默认值，例如 `DefaultBlockScratchBytes`。
2. `PayloadPoolManager` 再配置一个 `MaxRetainBlockScratchBytes`，控制池最多长期保留多大的 `BlockScratch`。
3. 解码时根据本次 `DATA.VALUE` 实际长度计算 `needBytes`。hex string 使用 `hex.DecodedLen(len(v))`，`[]byte` 使用 `len(v)`。
4. 如果 `needBytes > cap(batch.BlockScratch)`，允许本次临时 grow，保证正确解码。
5. 如果 `needBytes > HardBlockBytesLimit`，认为报文异常，直接返回错误或丢弃该设备本次上报。
6. 归还 pool 时，如果 `cap(batch.BlockScratch) > MaxRetainBlockScratchBytes`，该 batch 不放回池，让 GC 回收。
7. 通过指标观察 `needBytes` 的 p95 / p99，再回调默认值。

初始建议值：

```go
const (
    DefaultBlockScratchBytes   = 512
    MaxRetainBlockScratchBytes = 4 * 1024
    HardBlockBytesLimit        = 16 * 1024
)
```

说明：

1. 当前设备遥测字符类型很少，通常不会超过 500 个字符；`DefaultBlockScratchBytes = 512` 可以覆盖大多数常规上报。
2. 这些值都按 hex 解码后的字节数计算，不是 hex 字符串字符数。如果 hex string 长度是 1000，则解码后约 500 bytes。
3. `MaxRetainBlockScratchBytes = 4KB` 用来避免偶发较大包污染池，同时允许短期扩容后的 batch 在合理范围内复用。
4. `HardBlockBytesLimit = 16KB` 是异常大包保护的起点，不代表协议上限。上线后应观察 `needBytes` 的 p95 / p99 / max，再按产品模型调整。

示例：

```go
func estimateScratchNeed(dataList []any) (int, error) {
    need := 0
    for _, item := range dataList {
        m := item.(map[string]any)
        switch v := m["VALUE"].(type) {
        case string:
            if v == "" {
                continue
            }
            if len(v)%2 != 0 {
                return 0, fmt.Errorf("invalid hex VALUE length")
            }
            need += hex.DecodedLen(len(v))
        case []byte:
            // Copy into BlockScratch so ModbusBlock stays pointer-free.
            need += len(v)
        }
    }
    return need, nil
}
```

这意味着：即使当前无法从物模型精算 `MaxBlockBytes`，也不会影响方案推进。先用默认 capacity 减少大多数分配，再靠运行时 grow 兜底，最后靠归还限幅防止池被异常大包污染。

## 6. Modbus Block 预处理
当前每个属性都会扫描 `DATA` 并可能重复 `hex.DecodeString`。新链路先把本次上报中的数据块解析成轻量结构：

```go
type ModbusBlock struct {
    ID      int32
    Offset  int32
    DataOff uint32
    DataLen uint32
}
```

`ModulePayloadBatch.Blocks` 是本次设备上报内 `DATA` 块的轻量索引表，不是最终点值缓存。它只回答一个问题：某个属性的 `base-addr` 应该从本次上报的哪段二进制数据里读取。

字段含义：

1. `ID`：`DATA[i].ID`，表示该数据块覆盖的起始寄存器地址。
2. `Offset`：`DATA[i].OFFSET`，表示该数据块覆盖的寄存器数量。当前业务里一个寄存器按 2 字节计算。
3. `DataOff` / `DataLen`：该数据块在 `ModulePayloadBatch.BlockScratch` 中的 offset/length。

推荐不要在 `ModbusBlock` 里保存 `Data []byte`。`[]byte` 是 slice header，内部有指针；如果 `Blocks` 放进 pool 复用，旧元素里的指针可能延长原始数据生命周期。使用 `DataOff/DataLen` 后，`Blocks` 是无指针 descriptor，reset 时只需要 `b.Blocks = b.Blocks[:0]`，不会保留上一轮上报的 `DATA.VALUE` 引用。

预处理规则：

1. 遍历 `deviceMsgInverter["DATA"]` 一次。
2. `VALUE` 是 hex string 时只 decode 一次。
3. 如果 `VALUE` 已经是 `[]byte`，也复制到 `BlockScratch`，换取 `Blocks` descriptor 无指针和生命周期简单。
4. `BlockScratch` 的生命周期不得超过本次 decode；需要写入 payload 的 string 值必须复制到 `payload.Text`。

示例：

```go
func buildModbusBlocks(deviceMsgInverter map[string]any, blocks []ModbusBlock, scratch []byte) ([]ModbusBlock, []byte, error) {
    dataList := deviceMsgInverter["DATA"].([]any)
    blocks = blocks[:0]

    for _, item := range dataList {
        m := item.(map[string]any)
        id := toInt32Fast(m["ID"])
        offset := toInt32Fast(m["OFFSET"])

        raw := m["VALUE"]
        start := len(scratch)
        switch v := raw.(type) {
        case string:
            if v == "" {
                continue
            }
            var err error
            scratch, err = appendHexStringDecoded(scratch, v)
            if err != nil {
                return nil, nil, err
            }
        case []byte:
            if len(v) == 0 {
                continue
            }
            scratch = append(scratch, v...)
        default:
            continue
        }

        blocks = append(blocks, ModbusBlock{
            ID:      id,
            Offset:  offset,
            DataOff: uint32(start),
            DataLen: uint32(len(scratch) - start),
        })
    }
    return blocks, scratch, nil
}
```

`appendHexStringDecoded` 负责把一个 hex string 直接解码并追加到 `BlockScratch`。它不调用 `hex.DecodeString`，也不做 `[]byte(s)` 转换；当 `dst` 的剩余 capacity 足够时，不产生额外分配。

```go
func appendHexStringDecoded(dst []byte, s string) ([]byte, error) {
    if len(s)&1 != 0 {
        return dst, fmt.Errorf("invalid hex VALUE length %d", len(s))
    }

    original := dst
    oldLen := len(dst)
    decodedLen := len(s) / 2
    newLen := oldLen + decodedLen

    if newLen > cap(dst) {
        newCap := cap(dst) * 2
        if newCap < newLen {
            newCap = newLen
        }
        if newCap == 0 {
            newCap = newLen
        }

        grown := make([]byte, newLen, newCap)
        copy(grown, dst)
        dst = grown
    } else {
        dst = dst[:newLen]
    }

    for si, di := 0, oldLen; si < len(s); si, di = si+2, di+1 {
        hi := fromHexChar(s[si])
        lo := fromHexChar(s[si+1])
        if hi > 0x0f || lo > 0x0f {
            return original, fmt.Errorf("invalid hex VALUE at byte %d", si)
        }

        dst[di] = hi<<4 | lo
    }

    return dst, nil
}

func fromHexChar(c byte) byte {
    switch {
    case '0' <= c && c <= '9':
        return c - '0'
    case 'a' <= c && c <= 'f':
        return c - 'a' + 10
    case 'A' <= c && c <= 'F':
        return c - 'A' + 10
    default:
        return 0xff
    }
}
```

说明：

1. `s` 是 `DATA.VALUE` 的十六进制字符串，例如 `"0102030A"`。
2. 每两个字符表示一个字节，`"01"` 解码为 `0x01`，`"0A"` 解码为 `0x0A`。
3. `oldLen := len(dst)` 记录追加前的位置，当前 block 的数据会写入 `dst[oldLen:newLen]`。
4. 如果 `newLen <= cap(dst)`，只做 `dst = dst[:newLen]` 扩展长度，不分配新底层数组。
5. 如果 capacity 不够，才会 `make` 一个更大的底层数组；这属于 `BlockScratch` grow 兜底，不是每次 decode 的固定成本。
6. `fromHexChar` 直接按 string 下标读取字符，避免 `[]byte(s)` 临时分配。
7. 如果遇到奇数长度或非法 hex 字符，函数返回追加前的 `original`，调用方不会看到半截解码结果。

如果 `DATA` 块数量很少，`findBlock` 可以线性查找；如果块数量较多，应按 `ID` 排序并用游标或二分查找。不要为了每个设备上报都构造大 map，除非压测证明 block 数量足够大。

初始阈值建议：

1. `len(blocks) <= 8`：直接线性查找，分支少、实现简单。
2. `len(blocks) > 16`：先按 `ID` 排序，再二分查找。
3. `9~16`：先保持线性查找，后续以 benchmark 决定是否提前切换。

Modbus 寄存器地址通常按连续区间组织，`DATA` block 之间一般不重叠。因此按 `ID` 排序后二分找到最后一个 `ID <= baseAddr` 的 block，再判断 `baseAddr <= ID + Offset - 1` 即可。

```go
func findBlock(blocks []ModbusBlock, baseAddr int32) (ModbusBlock, bool) {
    for _, b := range blocks {
        if b.ID <= baseAddr && baseAddr <= b.ID+b.Offset-1 {
            return b, true
        }
    }
    return ModbusBlock{}, false
}
```

二分版本示例：

```go
func prepareBlocksForLookup(blocks []ModbusBlock) {
    if len(blocks) > 16 {
        sort.Slice(blocks, func(i, j int) bool {
            return blocks[i].ID < blocks[j].ID
        })
    }
}

func findBlockBinary(blocks []ModbusBlock, baseAddr int32) (ModbusBlock, bool) {
    i := sort.Search(len(blocks), func(i int) bool {
        return blocks[i].ID > baseAddr
    }) - 1
    if i < 0 {
        return ModbusBlock{}, false
    }

    b := blocks[i]
    if baseAddr <= b.ID+b.Offset-1 {
        return b, true
    }
    return ModbusBlock{}, false
}
```

如果未来发现同一上报内 `DATA` block 可能重叠，应在 `prepareBlocksForLookup` 中检测并记录 warning；重叠区间会让“baseAddr 属于哪个 block”变得不确定。

## 7. DecodePropertiesIntoPayload
新函数不接收 `schema.Properties`，也不接收 `subDevice map`：

```go
func DecodePropertiesIntoPayload(
    logger api.Logger,
    dict *PropertyDict,
    deviceMsgInverter map[string]any,
    batch *ModulePayloadBatch,
) error
```

核心流程：

```go
func DecodePropertiesIntoPayload(logger api.Logger, dict *PropertyDict, deviceMsgInverter map[string]any, batch *ModulePayloadBatch) error {
    blocks, scratch, err := buildModbusBlocks(deviceMsgInverter, batch.Blocks[:0], batch.BlockScratch[:0])
    if err != nil {
        return err
    }
    batch.Blocks = blocks
    batch.BlockScratch = scratch
    defer func() {
        // Blocks and BlockScratch are only needed during decode.
        // Keep capacity for pool reuse, but do not expose raw block data downstream.
        batch.Blocks = batch.Blocks[:0]
        batch.BlockScratch = batch.BlockScratch[:0]
    }()

    for i := range dict.Points {
        plan := &dict.Points[i]
        block, ok := findBlock(blocks, plan.BaseAddr)
        if !ok {
            continue
        }

        valueOffset := (plan.BaseAddr - block.ID) * 2
        blockData := scratch[int(block.DataOff):int(block.DataOff+block.DataLen)]
        modulePayload := &batch.Modules[plan.ModuleIndex]

        if err := decodeOneProperty(plan, blockData, valueOffset, modulePayload); err != nil {
            return err
        }
    }
    return nil
}
```

`decodeOneProperty` 只产出 typed value，不产出 `any`：

```go
func decodeOneProperty(plan *PropertyPointPlan, data []byte, offset int32, payload *ModulePayload) error {
    switch plan.DecodeKind {
    case DecodeU16:
        raw, ok := readU16(data, offset)
        if !ok {
            return errShortData(plan)
        }
        appendVerifiedIntOrFloat(plan, int64(raw), payload)
    case DecodeS16:
        raw, ok := readS16(data, offset)
        if !ok {
            return errShortData(plan)
        }
        appendVerifiedIntOrFloat(plan, int64(raw), payload)
    case DecodeU32:
        raw, ok := readU32(data, offset)
        if !ok {
            return errShortData(plan)
        }
        appendVerifiedIntOrFloat(plan, int64(raw), payload)
    case DecodeS32:
        raw, ok := readS32(data, offset)
        if !ok {
            return errShortData(plan)
        }
        appendVerifiedIntOrFloat(plan, int64(raw), payload)
    case DecodeU32Version:
        b, ok := decodeVersionBytes(data, offset)
        if ok {
            appendVerifiedBytes(plan, b, payload)
        }
    case DecodeString20:
        b, ok := readBytes(data, offset, 20)
        if ok {
            appendVerifiedBytes(plan, trimZeroSpaceBytes(b), payload)
        }
    case DecodeString22:
        b, ok := readBytes(data, offset, 22)
        if ok {
            appendVerifiedBytes(plan, trimZeroSpaceBytes(b), payload)
        }
    case DecodeBCDTime6:
        b, ok := readBytes(data, offset, 6)
        if ok {
            appendVerifiedBCDTime(plan, b, payload)
        }
    case DecodeSkip8, DecodeSkip38, DecodeSkip40:
        return validateOnly(plan, data, offset)
    }
    return nil
}
```

`DecodeSkip8/38/40` 只校验长度，不写 payload。它们对应“无有效写入值，不拼该字段”。

## 8. Typed Verifier
typed verifier 的输入是 `PropertyPointPlan + raw typed value`，输出直接写入 `ModulePayload`。

它替代的是 `VerifyProperties -> getVal -> cast.ToInt64E/cast.ToFloat64E/decimal.Decimal` 这条热路径。

### 8.1 数值缩放
当前 `scale` 的语义是：

1. `scaler < 0`：除以 `10^-scaler`。
2. `scaler >= 0`：直接返回原始值。

新链路保留这个语义，但不使用 `decimal.Decimal`：

```go
var pow10Float = [...]float64{
    1,
    10,
    100,
    1000,
    10000,
    100000,
    1000000,
}

var pow10Int = [...]int64{
    1,
    10,
    100,
    1000,
    10000,
    100000,
    1000000,
    10000000,
    100000000,
    1000000000,
    10000000000,
    100000000000,
    1000000000000,
    10000000000000,
    100000000000000,
    1000000000000000,
    10000000000000000,
    100000000000000000,
    1000000000000000000,
}

func scaleFloat(raw int64, scaler int8) float64 {
    if scaler >= 0 {
        return float64(raw)
    }
    n := int(-scaler)
    if n >= len(pow10Float) {
        return float64(raw) / math.Pow10(n)
    }
    return float64(raw) / pow10Float[n]
}

func scaleInt(raw int64, scaler int8) int64 {
    if scaler >= 0 {
        return raw
    }
    n := int(-scaler)
    if n >= len(pow10Int) {
        return 0
    }
    return raw / pow10Int[n]
}
```

`scaleFloat` 必须保留 scaler 语义。预计算表只是快路径，不能在表越界时直接返回 `raw`，否则 `scaler=-8` 这类配置会把 `123456789` 错写成 `123456789`，而不是 `1.23456789`。因此越界时用 `math.Pow10(n)` 兜底，性能略差但保证正确。实际代码需要引入 `math` 包。

`scaleInt` 的负 scaler 会做整数除法并截断小数部分。为了避免隐式精度丢失，推荐在构建 `PropertyPointPlan` 时校验：带小数缩放的点位应声明为 `float/double`，否则记录 warning 或拒绝加载 schema。`pow10Int` 扩到 `1e18`；当 `n >= len(pow10Int)` 时，任何 `int64` 原始值除以 `10^n` 都会按整数语义变成 `0`，不能返回原始值。

### 8.2 int/bool/enum/timestamp
```go
func appendVerifiedInt(plan *PropertyPointPlan, raw int64, payload *ModulePayload) bool {
    v := scaleInt(raw, plan.Scaler)

    if plan.HasMinInt && v < plan.MinInt {
        v = plan.MinInt
    }
    if plan.HasMaxInt && v > plan.MaxInt {
        v = plan.MaxInt
    }
    if plan.StepInt != 0 {
        v = v / plan.StepInt * plan.StepInt
    }
    if len(plan.EnumAllowed) > 0 && !containsInt64(plan.EnumAllowed, v) {
        return false
    }

    payload.AddInt(plan.PointID, v)
    return true
}
```

说明：

1. bool 当前兼容旧语义，可按 int64 写入；如果业务要求严格 `0/1`，应在 plan 构建阶段配置独立 bool 策略。
2. enum mapping 在 L1 构建阶段解析为排序后的 `[]int64`。
3. timestamp 归一为 `int64`。

### 8.3 float/double
```go
func appendVerifiedFloat(plan *PropertyPointPlan, raw int64, payload *ModulePayload) bool {
    v := scaleFloat(raw, plan.Scaler)

    if plan.HasMinFloat && v < plan.MinFloat {
        v = plan.MinFloat
    }
    if plan.HasMaxFloat && v > plan.MaxFloat {
        v = plan.MaxFloat
    }
    if plan.StepFloat != 0 {
        v = stepFloatTyped(v, plan.StepFloat)
    }

    payload.AddFloat(plan.PointID, v)
    return true
}
```

`stepFloatTyped` 应保持当前 `thingmodel.stepFloat` 的语义，避免迁移后数值表现变化。

### 8.4 string
热路径应优先使用 bytes，避免先构造 Go string 再复制到 `Text`：

```go
func (p *ModulePayload) AddBytes(pointID uint16, value []byte) {
    off := uint32(len(p.Text))
    p.Text = append(p.Text, value...)
    idx := uint32(len(p.Strings))
    p.Strings = append(p.Strings, StringRef{
        Off: off,
        Len: uint32(len(value)),
    })
    p.Values = append(p.Values, PointValueRef{
        PointID: pointID,
        Kind:    ValueString,
        Index:   idx,
    })
}
```

校验逻辑：

```go
func appendVerifiedBytes(plan *PropertyPointPlan, value []byte, payload *ModulePayload) bool {
    if plan.MaxStringLen > 0 && len(value) > plan.MaxStringLen {
        value = value[:plan.MaxStringLen]
    }
    payload.AddBytes(plan.PointID, value)
    return true
}
```

注意：`value` 可能引用 modbus block 的临时 buffer，必须复制进 `payload.Text`，不能保存原切片。

### 8.5 分派函数
```go
func appendVerifiedIntOrFloat(plan *PropertyPointPlan, raw int64, payload *ModulePayload) bool {
    switch plan.ValueKind {
    case ValueInt:
        return appendVerifiedInt(plan, raw, payload)
    case ValueFloat:
        return appendVerifiedFloat(plan, raw, payload)
    default:
        return false
    }
}
```

typed verifier 不做这些事：

1. 不查 `map[string]*Property`。
2. 不写 `map[string]any`。
3. 不使用 `any` 承载中间值。
4. 不使用 `cast`。
5. 不使用 `decimal.Decimal`。
6. 不做 module split，因为 plan 已经包含 `ModuleIndex`。

## 9. handlePushData 迁移
`ps_lookup.go` 当前返回给 `handlePushData` 的 `oneSchema` 里有 `schema` 和 `route`。要接入 typed path，需要额外暴露 L1 上的 runtime index 或 property dict。

推荐保持兼容字段不变，新增字段：

```go
oneSchema["schema"] = bundle.GetModel()
oneSchema["route"] = bundle.Route
oneSchema["propertyDict"] = bundle.GetPropertyDict()
```

`handlePushData` 中属性链路改为：

```go
dict, _ := oneSubsetMap["propertyDict"].(*schema.PropertyDict)
batch := payloadPoolManager.Borrow(dict)
batch.DeviceName = deviceName
batch.Timestamp = nowTs

if err := binaryTransform.DecodePropertiesIntoPayload(logger, dict, deviceMsgInverter, batch); err != nil {
    logger.Warnf("handlePushData: %s decode typed properties error: %v, skipping device", deviceName, err)
    batch.Release()
    continue
}

if batch.HasValues() {
    result = append(result, map[string]any{
        "sinkType":   "tdengine",
        "recordType": "propertyTypedBatch",
        "productID":  subProductID,
        "deviceName": deviceName,
        "timestamp":  nowTs,
        "batch":      batch,
        "dict":       dict,
        "optional":   subRuntimeMeta,
    })
} else {
    batch.Release()
}
```

推荐用单条 `propertyTypedBatch` record 表达“一台设备一次上报的所有 module payload”。这样 batch 的所有权可以整体转移到 TDengine sink，sink 在该 batch 的所有 module SQL 执行完成后统一调用 `batch.Release()`。

如果选择“一 module 一条 record”，必须给 batch 引入引用计数，最后一个 module record 写入完成后再 `Release`；否则容易提前 `Release` 或重复 `Release`。

这一步会绕开：

1. `extractPropertiesParams`
2. `buildPropertyMap`
3. `VerifyProperties`
4. `SplitByModule`

旧路径可以保留为 fallback：

```go
if dict == nil || !enableTypedPropertyPath {
    // old DecodeProperties + VerifyProperties + SplitByModule
}
```

## 10. TDengine Sink 迁移
TDengine sink 增加 `propertyTypedBatch` 分支：

```go
switch recordType {
case "property":
    sqlStr, args, err = BuildPropertySQL(s.cfg.Database, record)
case "propertyTypedBatch":
    sqlClauses, args, err = BuildPropertySQLFromBatch(s.cfg.Database, record)
case "event":
    sqlStr, args, err = BuildEventSQL(s.cfg.Database, record)
}
```

`BuildPropertySQLFromBatch` 不遍历 params map，而是按 module 调用统一的 descriptor 展开 helper。列名和值恢复规则只应维护在 `AppendPayloadColumnsAndArgs` / `AppendPayloadValueColumnsAndArgs` 中，不要在 sink 分支里再写一套 `for _, ref := range payload.Values`。

```go
func BuildPropertySQLFromBatch(database string, record map[string]any) ([]string, []any, error) {
    batch := record["batch"].(*ModulePayloadBatch)
    dict := record["dict"].(*PropertyDict)

    clauses := make([]string, 0, len(batch.Modules))
    args := make([]any, 0)

    for moduleIndex := range batch.Modules {
        payload := &batch.Modules[moduleIndex]
        if len(payload.Values) == 0 {
            continue
        }
        module := dict.Modules[moduleIndex]

        cols := make([]string, 0, len(payload.Values)+1)
        var err error
        cols, args, err = AppendPayloadColumnsAndArgs(cols, args, dict, payload, batch.Timestamp)
        if err != nil {
            return nil, nil, err
        }

        clauses = append(clauses, buildModuleSQL(module, cols))
    }

    return clauses, args, nil
}
```

`string(b)` 仍会在 sink 边界分配，但它已经从“全链路持有大量 string”收敛为“写入前必要转换”。如果 TDengine driver 支持 `[]byte` 参数，可进一步优化。

`AppendPayloadColumnsAndArgs` 必须对未知 `ValueKind` 返回错误，不能静默跳过。否则列列表已经追加了 `ColumnSQL`，但 args 没有追加对应值，会导致列数和参数数不匹配，TDengine 写入报错且难以定位。这个错误处理统一放在 helper 中，`BuildPropertySQLFromBatch` 只负责向上返回。

无论同步还是异步写入，`batch` 都必须在该 batch 的所有 SQL 执行完成后才能调用 `batch.Release()`。`BuildPropertySQLFromBatch` 不能保存 `payload.Text` 的引用到函数返回之后。

## 11. 迁移顺序
推荐按以下顺序落地：

1. 做 `SchemaRuntimeIndex / PropertyDict`，并修正 `Fmt copy-on-format`。
2. 做 `DecodePropertiesIntoPayload`，消灭点级 map 和重复 hex decode。
3. 做 typed verifier，消灭 `decimal.Decimal/any/cast` 热路径。
4. 改 `handlePushData`，绕开 `extractPropertiesParams/buildPropertyMap/VerifyProperties/SplitByModule`。
5. 改 TDengine sink，支持 `propertyTypedBatch`。
6. 保留旧路径，用开关控制新旧链路，便于灰度和对比测试。

## 12. 测试与验证
### 12.1 单元测试
1. `BuildRuntimeIndexes` 能从 `SchemaBundle` 生成 `PropertyDict`。
2. `Fmt` 不修改入参 `data`，尤其不能清空 `data.Model`。
3. `PropertyPointPlan` 正确解析 `base-addr/scaler/vdata_type`。
4. `PropertyPointPlan` 正确解析 `min/max/step/enum/max string length`。
5. `DecodePropertiesIntoPayload` 对 `U16/S16/U32/S32` 生成正确 int/float。
6. string 点位写入 `Text`，`StringRef` offset/length 正确。
7. `DecodeSkip8/38/40` 不生成 descriptor。
8. enum 非法值跳过，合法值写入。
9. typed verifier 的 min/max/step 与旧 `VerifyProperties` 行为一致。
10. 同一份输入下，新旧链路输出的 TDengine columns 和 args 一致。

### 12.2 Benchmark
对比三组：

1. 旧链路：`DecodeProperties + VerifyProperties + SplitByModule + BuildPropertySQL`。
2. 半新链路：`PropertyDict + modbus block decode once + 旧 map VerifyProperties`，仅用于单独定位 schema 预解析和重复 hex decode 的收益。
3. 新链路：`DecodePropertiesIntoPayload + typed verifier + propertyTypedBatch sink`。

关键指标：

1. `allocs/op`
2. `B/op`
3. p95/p99 单设备属性处理耗时
4. `hex.DecodeString` 次数
5. `map` 分配次数
6. GC CPU
7. `heap_alloc`、`heap_inuse`、RSS

### 12.3 灰度校验
灰度阶段可以双跑但只写一份：

1. 旧链路生成 SQL args。
2. 新链路生成 SQL args。
3. 比较 columns、args 数量、每个值。
4. 不一致时记录 product/release/device/module/point 信息。
5. 对比通过后再切换到只跑新链路。

## 13. 推荐结论
高频属性链路的关键不是把 `VerifyProperties` 的入参换成 `schema.Properties`，而是让热路径完全绕开 map 版 decode/verify/split。

真正的目标是：

```latex
PropertyPointPlan + modbus bytes -> typed verifier -> ModulePayload
```

旧函数保留，但高频 PUSH_DATA 不再调用。这样风险更小，也方便迁移期间做新旧链路对比。

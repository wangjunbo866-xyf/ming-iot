# 质量码契约设计

> 状态：**设计已定**（TDengine 落地选定"总码 + 例外明细"方案）；§4 行业/协议映射表为初稿，待各协议 owner 确认后冻结。
>
> 归属：本文是 ProtocolApplication 产出物（Canonical 状态词汇）的规范性契约，归 `2.编码解码协议/` 域。
> 被《Scene Current Fact 设计》的 DIRECT_TD 档作为硬前提引用（见本文 §7）。与父架构冲突时以父架构为准。

## 1. 概念与谱系

**质量码**是行业长期存在的概念：储能/电力 EMS 每次上传数据附带的数据质量码、IEC 104 的
品质描述词 QDS、IEC 61850 的 quality 位（good/invalid/questionable + oldData/substituted/test
细节）、OPC UA 的 StatusCode，同属一族。本平台的 Canonical 状态词汇表继承这一谱系：

```text
Canonical 逐点状态：ABSENT / VALUE / NULL / RESET / INVALID + quality
Scene availability：AVAILABLE | UNAVAILABLE(NULL_VALUE | RESET | INVALID_VALUE | BAD_QUALITY)
```

- `ABSENT`：本报告没有更新该点（不产生任何行/Delta）；
- `VALUE` 且 quality 被 contract 接受 → `AVAILABLE + typedValue`；
- `NULL / RESET / INVALID` → `UNAVAILABLE(NULL_VALUE | RESET | INVALID_VALUE)`；
- `VALUE` 但 quality 被 contract 判为不可用 → `UNAVAILABLE(BAD_QUALITY)`。

## 2. 职责分层

| 层 | 职责 | 明确不做 |
| --- | --- | --- |
| 发布物（snapshot 的 `availabilityPolicyRef` / `sourceProjectionRef`） | **拥有规则**：哪些原始证据 → 哪个 Canonical 状态；随 release 版本化冻结 | 不执行 |
| ProtocolApplication | **执行规则**：唯一能看到原始证据（CRC、异常响应、QDS 位、null、超时）的层；按冻结策略产出 Canonical 状态；彻底失败的帧进 quarantine | 不自由发挥，不读 current 草稿猜规则 |
| Scene Admission | **机械翻译**：Canonical 状态 → Scene availability（按固定映射表）；校验 quality 是否被 contract 接受 | 不合成、不修改状态 |
| Materializer | 质量码随值落 history 行（§5） | 不重新判定 |
| Scene Runtime | 按 missing/freshness 策略消费 `UNAVAILABLE` | 不关心协议细节 |

三条原则：

1. **单一规范化点**：全平台只有 ProtocolApplication 说"协议方言"，下游只说 Canonical 词汇表；
2. **规则演进走发版**：策略变更 = 发布物里 policy 引用换版本，代码不动；历史 Canonical 按它携带的
   历史 release/snapshot 解释，不查"当前物模型"猜测；
3. **可测试**：同一原始帧 + 同一 release ⇒ 同一 Canonical 状态，跨语言可对拍。

## 3. 无码协议：默认 GOOD 契约

很多行业/协议没有质量码（裸 Modbus、简单 JSON 设备等）。作为通用平台，**默认 GOOD 可行，
但它只能授予"成功解析的值"**，三条边界缺一不可：

1. **失败宁缺毋滥**：协议层失败（CRC 失败、读超时、异常响应、字段缺失、类型不匹配）时输出
   `ABSENT`（不更新、旧值语义保留、"设备沉默"交给 freshness 策略）或按 §4 合成坏码；彻底失败进
   quarantine 诊断。**禁止**把旧值、0 或占位符标成 GOOD 写入——那是拿旧数据冒充新数据。
2. **合成坏码规则发布期冻结**：无码协议的失败检测责任在解码层（网关/协议层），"什么证据算坏"
   必须冻结进发布物的 `availabilityPolicyRef`，不允许各接入点各自拍脑袋，否则同一个"坏"在不同
   设备上含义不同，Scene 的 `UNAVAILABLE` 语义就碎了。
3. **显式空值必须标 NULL_VALUE**：协议能表达空值（JSON `null`、哨兵无效位等）时，设备是在明确
   说"这个点现在无值"，必须落 `UNAVAILABLE(NULL_VALUE)`，不得因"本行业无质量码"标 GOOD 放行。
   默认 GOOD 豁免的是品质分级（可疑/置换/降精度等细粒度），不豁免"有无"这个最基本的区分。

安全性论证：无码行业的设备数据语义是二元的——有值/没值。GOOD 覆盖"有值"，ABSENT 覆盖
"没值"，freshness 覆盖"多久没来"。细粒度品质是增量能力而非必需，因此默认 GOOD 不丢失任何
可表达的判断。物模型/场景配置界面不出现质量码配置项；无码行业用户无感知。

## 4. 行业/协议映射表（初稿，待各协议 owner 确认）

| 来源 | 原始证据 | Canonical 状态 | 备注 |
| --- | --- | --- | --- |
| IEC 104 | QDS=有效 | VALUE | |
| IEC 104 | QDS=无效 | INVALID | |
| IEC 104 | QDS=可疑（questionable） | **发布期裁决**：可用 或 BAD_QUALITY，不得运行期猜 | 待协议 owner 确认 |
| IEC 61850 | quality.validity=good / invalid / questionable | VALUE / INVALID / 发布期裁决 | detail 位（test 等）处置待确认 |
| OPC UA | StatusCode Good* / Bad* / Uncertain* | VALUE / INVALID / 发布期裁决 | |

| Modbus（无码，合成） | 成功解析且过量程检查 | VALUE | 默认 GOOD |
| Modbus（合成） | CRC 失败 / 读超时 / 异常响应 / 寄存器不存在 | INVALID 或 BAD_QUALITY（按发布物策略） | 合成规则待协议 owner 确认 |
| Modbus（合成） | 量程越限 | INVALID | |
| small-json | 字段缺失 | ABSENT | |
| small-json | `null` | NULL（→ NULL_VALUE） | 边界 3 |
| small-json | 类型不匹配 / 解析失败 | quarantine | 不进业务事实 |

任何"可疑/中间态"的归类都必须在发布期定死（可用或 BAD_QUALITY 二选一写入契约），禁止运行期
按现象猜测；同样禁止在无 policy 依据时编造非 GOOD 码。

## 5. TDengine 落地：总码 + 例外明细（方案②）

质量码的写入/存储成本几乎全花在"全是 GOOD"的正常行上，设计目标是让 GOOD 免费。每个模块
超级表只加两列（子表继承）：

```text
q_summary  TINYINT     -- 0 = 本行全部 GOOD；非 0 = 有例外
q_detail   VARBINARY   -- 仅 q_summary≠0 时携带逐点码，
                       -- 按发布物冻结的列序/ordinal 位图打包
```

规则：

- **GOOD 免费**：正常行 `q_summary=0、q_detail=NULL`，列式存储下近零成本；
- **坏状态必须成行**：INVALID/NULL/RESET/BAD_QUALITY 也写一行，value 可置 NULL/占位、质量码记
  原因；禁止"坏值丢弃"——否则"设备拔线"在数据里不可见；
- **行级失败展开**：整帧 CRC 失败/轮询超时/网关断链等行级失败，由解码层展开为该帧每个点各自
  的同一个失败码，逐点落明细；语义层永远只看到"逐点状态"；
- **明细位序冻结**：`q_detail` 的逐点位序按发布物（ModuleWritePlan / V3 dictionary）冻结的列序/
  ordinal 编码，禁止按进程内排序动态分配；
- **读取必须用 `last_row`**：`last(value)` 会跳过 NULL 返回旧好值，使坏状态行失效；
- **ABSENT 与 NULL_VALUE 必须行内可区分**：宽表插入时未更新的列只能写 NULL 值，若无质量码
  区分"本帧没更这列"（ABSENT）与"这列报了空"（NULL_VALUE），partial 上报会搅乱旧值语义。
  具体编码随 ModuleWritePlan 冻结。

## 6. 明确禁止

- **值列哨兵**：NaN 变体、0xFFFF、-9999 等塞进值列——污染类型化值域，Scene 无法校验也无法
  区分真值与哨兵；状态必须与值分通道；
- **行级单码当逐点状态**：一行一个码会把"一列坏"放大成"整行不可用"，误伤好点；行级只是失败
  的传播形态，存储与语义都按列走；
- **运行期猜测**：无 policy 依据时不得编造非 GOOD 码；也不得把已知失败标 GOOD。

## 7. 与 Scene Current Fact 的关系

《Scene Current Fact 设计》的双档部署契约中：

- **DIRECT_TD 档（直读 TDengine last）把本文作为硬前提**：
  (a) 坏状态逐列成行；
  (b) ABSENT 与 NULL_VALUE 行内可区分。
  两条不满足，DIRECT 档连 `READY_UNAVAILABLE` 都无法表达，必须退回声明"不可用状态不可见"为
  已知残留风险，或先完成本文 §5 的写入路径改造；
- **FULL 档（独立投影存储）不依赖本文的 TDengine 编码**：状态保存在投影行内（availability +
  reason + provenance），但状态的来源仍受本文 §2 分层与 §3 默认 GOOD 契约约束。

**前提验收动作**：抽查一条 INVALID 上报，确认 history 中存在对应行、`q_summary≠0` 且
`last_row` 读出的末行就是它。

## 8. 验收与测试向量

- 同一原始帧 + 同一 release ⇒ 同一 Canonical 状态：跨语言 golden 测试向量（每协议至少覆盖
  成功/失败/空值/越限四类）；
- 默认 GOOD 三边界的故障注入：超时、CRC 失败、显式 null、旧值冒充 GOOD（必须被拦）；
- `q_summary/q_detail` 读写回归：全 GOOD 行成本实测、例外行解包正确性、`last_row` 读法回归；
- 行级失败展开用例：整帧失败后该帧每个点的逐点码一致且正确。

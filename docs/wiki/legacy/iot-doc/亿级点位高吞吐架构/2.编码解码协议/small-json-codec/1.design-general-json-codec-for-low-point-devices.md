# 低点位 JSON 设备通用 Codec 设计

日期：2026-07-24
状态：设计结论，作为 [主架构](../enterprise-iot-platform-architecture-design.md) §5.3/§7.2/§9.2 在标准 JSON 产品上的落地补充
适用边界：低点位、低速率、报文为 JSON 且已适配平台标准格式的设备产品

---

## 1. 定位

标准 JSON 产品不为每个产品编写定制 codec，由**一个平台内置的通用 JSON codec** 承接，随共享 Protocol Runtime 编译发布，默认运行在共享 ProtocolApplication workload（主架构 §5.3）。

需要立即钉死的一条原则：

> **通用性来自配置（schema 发布物驱动），不来自中间表示。**

通用路径不允许退化为 ThingsBoard/JetLinks 式的通用对象图（`map[string]any`、逐点 KV 对象）。主架构 §7.2 的热路径禁令（禁 `map[string]any`、`[]any`、逐点 heap object）对标准 JSON 产品与定制二进制产品**一视同仁**。两类产品的差别只有 codec 来源与部署形态，热路径数据结构完全相同：

| | 标准 JSON 产品 | 非标准/定制产品 |
| --- | --- | --- |
| codec 来源 | 平台内置 schema 驱动通用 codec | 定制 Go codec，编译发布 |
| 部署形态 | 默认共享 workload | 可共享，也可独立 ProtocolApplication |
| 热路径数据结构 | 相同：BatchBuilder + typed lanes | 相同 |

## 2. 解码方式：schema 驱动 + 零分配提取

### 2.1 字典在发布时冻结

`ModuleSchemaSnapshot` 发布时冻结 `identifier → pointOrdinal → ValueKind → typed lane 位置` 的映射字典（与 `small-object-large-object`/`large-binary-codec` 的 `PropertyDict.ByIdentifier` 同一物）。运行时按字典解码，不逐消息解析可编辑模型，不查草稿表。

### 2.2 零分配提取，禁止 Unmarshal 成对象树

- 禁止 `json.Unmarshal` 到 `map[string]any`/`struct`——每点一次装箱分配，正是要消灭的对象图；
- 使用 gjson/sonic 风格的零分配提取器：在**原始 JSON 字节**上按路径定位 key，直接读出数值/字符串切片，写进 `BatchBuilder` 的 typed lane（int/float/text arena + StringRef）；
- 迭代方向按产品形态二选一，发布时冻结：
  - 全量固定点表（大多数 Modbus 网关/标准产品）：**迭代字典点位**，按 identifier 到原始 JSON 中取值；
  - 稀疏动态 key（少量产品）：**迭代 JSON key**，每个 key 查 `ByIdentifier`；未知 key 按主架构契约进 `UnknownPoint` 诊断输出，不在热路径自动建点；
- 输出与二进制 codec 完全一致：`DecodeManifest` + 完整 `CanonicalDataBatch`（envelope、moduleSpans、state plane、typed lanes），同一幂等 identity、同一 quarantine/`NO_OUTPUT` 语义（主架构 §7.2）。

### 2.3 预算同样生效

`maxPoints/maxBytes/maxDecodedPointsPerRaw/maxDecodedBytesPerRaw`、解压后字节、CPU/wall-time 预算对通用 JSON codec 同样冻结在 ModelRelease/contract 中，在任何 side effect 前完成检查（主架构 §7.2/§9.2）。JSON 的 `maxBytes` 必须按文本膨胀率单独标定，不能套用二进制产品的数值。

## 3. JSON 的固有成本与协议选型引导

JSON 的成本劣势是**字节数 × 每字节解析成本**的乘积：

- 字节数：500 点报告，二进制定长布局约 1~2 KB，JSON 约 10~20 KB（key 名 + 文本数值 + 分隔符），约 10×；
- 每字节解析成本：二进制是按预计算偏移读字节（约几 ns/点）；JSON 要逐字节扫 key、跳过分隔符、文本转数值（几十~几百 ns/点，Go `encoding/json` 仅约 100~200 MB/s，零分配提取器好些但仍远贵于二进制），约 5~10×；
- 单消息总解析成本相差几十倍，且字节膨胀还推高 Kafka 带宽与 RF=3 存储——两条数据通道仍按主架构 §2.1 以 MB/s 验收，不得只看 msg/s。

因此：

- 低点位（如 ≤50 点/报）、低速率设备：JSON 完全够用，通用 codec 承接；
- 单消息多点位、高频产品：通用 codec **依然工作**，但协议选型时应引导到二进制 protocolKey（`large-binary-codec/` 链路）；这是文本格式的物理上限，不是通用路径的实现缺陷；
- 压缩 JSON 只省传输字节，不省解析 CPU，且额外付出压缩/解压成本；是否启用按产品合同决定，不作为默认。

## 4. 批处理策略

低点多消息负载的成本模型是 **O(消息数) × 固定成本**，批是摊薄固定成本的主力手段。三层批各归各位：

### 4.1 拉取批（poll）

- `max.poll.records` 设 500~2000，禁止设为 1；
- `fetch.max.wait.ms` 给 50~100ms，让 fetcher 有时间攒批，避免 consumer 空转。

### 4.2 处理批（Kafka transaction 边界）

- ProtocolApplication 按 poll 自然批次走，**一批一个 transaction**（outputs + Raw offsets 同事务提交，主架构 §7.2/§12.1），禁止逐消息一个事务；
- 提交节奏目标约 100ms：事务过大则 abort 重放成本高、offset 推进延迟大、下游 `read_committed` 可见延迟高。

### 4.3 落库批（sink 攒批）

- Materializer 消费连续，攒批在写侧：按 STABLE/vgroup 组批，**行数阈值 OR 时间阈值，谁先到谁 flush** 成一条多行 INSERT（主架构 §10.2）；
- 时间阈值必须兜底：低速率设备攒不满行数阈值时，无时间兜底会让数据长期不可见；
- 攒批 buffer 有界（有界队列/credit），TDengine 不可用时停止取新批，由 Canonical 承接积压——批 buffer 不是无限缓冲。

### 4.4 批次大小评估公式

```text
batchSize ≈ min(
    消费速率 × 允许新增的延迟,     // 延迟预算约束
    sink 最优批甜点,               // 写库约束（TDengine 一般几百~几千行/条 INSERT）
    内存上限 ÷ 单条字节数          // 有界约束
)
```

示例：端到端 SLO 2s、链路其余环节 1.5s、攒批预算 300ms、单 consumer 5000 msg/s → 时间窗上限约 1500 条/批；落库批建议区间 1000~5000 行。最终数值必须在 Phase 0 以 500/1000/2000/5000 实测拐点后冻结（主架构"压测证据高于项目宣传"）。

## 5. 与主架构契约的对齐清单

- §5.3：共享 workload 只承诺有界 worker、每 codec 配额/超时、panic recover 和有界重试，不承诺 fatal/OOM 故障域隔离；出现持续 CPU/SLO 干扰或客户合规要求时，该 protocolKey 升级为独立 ProtocolApplication workload；
- §7.1/§7.2：Adapter 不做任何 JSON 解析；Raw 仍是原始 payload；tenant/deviceId/release 全部在 ProtocolApplication 阶段按可信 key + 本地发布缓存解析；
- §7.2：热路径禁 `map[string]any`、禁逐点 heap object；canonical 输出走 BatchBuilder/typed lanes；
- §7.3：解码语义随 ProtocolRelease/ModelRelease 不可变发布，按 `rawRef`/offset barrier 选择版本；
- §12.1：消费关 auto commit；可重试错误 pause partition + backoff；只有 durable quarantine/outcome 后才能推进 offset；
- §2.1：容量按向量验收；低点多消息是独立压测档位，不与亿级点位档位混用结论。

## 6. 压测与验收要求

- 专设**低点多消息档**（如 10 万 msg/s × 3 点/msg 的 JSON 上报），与 500 点/报的工业遥测档分开记录硬件、payload、模型与副本条件；
- 该档位卡的不是 arena，而是 poll 批量、事务节奏、TDengine 合并写参数——压测报告必须给出这三项的实测配置与拐点；
- codec 层 benchmark：`encoding/json` 到 `map[string]any` 对照零分配提取到 typed lane，记录 allocs/op 与 ns/op；收益写成实测值之前不得进入容量承诺；
- 双指标验收：msg/s 与 MB/s 同时达标（JSON 字节膨胀），事务批节奏下 p99 处理延迟不超过延迟预算中分配给 ProtocolApplication 的部分。

## 7. 明确不做

- 不在通用 JSON codec 中提供脚本/表达式语言能力（那是 ThingsBoard uplink converter 路线）；字段映射只支持发布时冻结的声明式 identifier→ordinal 映射；
- 不支持热路径自动建点、自动 ALTER（未知 key → `UnknownPoint` → 人工确认后发布新模型，主架构 §8.2）；
- 不为 JSON 产品放松 `maxBytes`/CPU/时间预算；
- 不把压缩 JSON 的带宽节省计入解析成本改善。

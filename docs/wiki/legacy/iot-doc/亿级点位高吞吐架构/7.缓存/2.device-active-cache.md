# 设备活跃Sorted Set
1. 利用Redis Sorted Set缓存设备key，分数为设备最后活跃时间。
2. 为节省空间，最后活跃时间使用秒级时间戳。
3. 由于设备量巨大，Redis Sorted Set必须分片。
4. 注意设备活跃Zset只用于判断设备是否离线或者异常离线，不用于判断设备是否在线(所有设备消息都会触发OnlineFix函数)。



## 逻辑分片
以500万设备为例

| 分片数量 | 单个Sorted Set平均元素数 | 优点 | 缺点 | 建议场景 |
| --- | --- | --- | --- | --- |
| **16片** | ~31.25万 | 分片逻辑简单，Key数量少。 | 单个集合仍然**偏大**，范围操作风险高。 | **不推荐**。 |
| **32片** | ~15.63万 | 集合大小更可控，是较好的折中起点。 | Key数量增多，管理复杂度微增。 | **推荐起始点**。如果设备增长快，可预留到64片。 |
| **64片** | ~7.81万 | 单个集合**非常安全**，范围操作高效，内存压力分散。 | 客户端分片逻辑稍复杂，Key数量多。 | **推荐用于高性能、增长快的场景**。 |
| **128片** | ~3.91万 | 性能最佳，内存最分散。 | 分片逻辑最复杂，可能产生大量Key。 | 适用于对延迟极其敏感或未来设备量可能达到千万级的场景。 |


**结论**：从 **32分片** 或 **64分片** 开始是一个稳健的选择。

单分片5到10万，以实际压测为准

## 批量写入Pipeline
1. **Redis Cluster下，批量写入Pipeline可能会报错。**

如果批量些多个Key，而这些Key属于多个Redis Master节点，那么会报错。

2. **Key是怎么被分配到多个Redis Master节点的？**

集群将所有Master划分为16384个哈希槽，每个key通过`CRC16(key) mod 16384`计算后，会映射到其中一个槽位，这样多个Key可能被分配到多个Redis Master节点。

1. **go-zero框架的Pipeline底层自动完成客户端分组的逻辑**

```go
// 示例代码，假设已经通过依赖注入获取了 redis.Redis 连接
err := rds.Pipelined(func(pipe redis.Pipeliner) error {
    pipe.Get(ctx, "user:1001:name")
    pipe.Set(ctx, "user:1001:score", 95)
    pipe.Incr(ctx, "global:counter")
    // 这些key可能分布在集群的不同节点上
    return nil
})
if err != nil {
    // 处理错误
}
```

虽然框架解决了分组问题，但一次Pipeline中包含大量跨节点的key，仍会产生多个网络往返。在性能要求极高的场景下，可以结合**哈希标签（Hash Tag）** 将相关key设计到同一节点，以优化性能。



4. **邪修功法，将多个Sorted Set放到同一个slot中**

将多个Sorted Set放到同一个slot中，这种方式有些麻烦，暂不考虑



5. **要建几种Sorted Set?**

只建一个Sorted set分片就行，没必要给活跃的，离线的，异常离线的三种设备分别建三个Sorted set分片。

由于设备最近活跃时间超过15分钟就算离线，如果每分钟轮询一轮，只需要查询14到16分钟范围内的设备并发出离线消息就行了。





## 触发写入
### 收到设备reportMessage信息
规则引擎 每次订阅到Mqtt消息时，一方面直接写入TDengine，另一方面会向Nats发送 reportMessage ：
reportMessage 消息Payload含：需要通知的遥信消息和需要写入PGsql的遥信消息

1. 规则引擎向EventBus的Topic（device.up.thing.report.>）发送 reportMessage 消息。
2. 平台订阅EventBus的 reportMessage 消息，对每一条消息进行OnlineFix处理。
    1. OnlineFix会被多个协程、多个服务(微服务集群)同时调用，Redis共享锁来排队执行，如果2秒内得不到所则放弃处理。但后续执行都是由协程执行（ctxs.GoNewCtx），基本不会阻塞锁。OnlineFix执行内容如下：
        1. 立即向 DeviceActive（设备最后活跃时间缓存）发送设备最后活跃时间。
        2. 共享锁排队。
        3. 异步执行：ctxs.GoNewCtx：
            1. 查看设备缓存是否是在线状态，在线状态则不处理。
            2. 离线状态交由devicemanagelogic.HandleOnlineFix处理。
    2. devicemanagelogic.HandleOnlineFix处理如下：
        1. 修改数据库设备状态，重置缓存设备信息。
        2. 向 ProjectDevicesStatus（设备状态缓存）发送设备当前状态（def.DeviceStatusOnline、def.DeviceStatusOffline）。

### 定时任务检查
储能和逆变器设备，每分钟检测一次，如果15分钟内没有收到设备上报消息，则认为设备离线。不需要根据设备连接状态来判断，因为很多设备是不稳定的4G，CGNAT等网络环境，设备连接状态不一定准确。

#### 重复检查次数不超过3次
通过控制检查时间间隔（多长时间检查一次）和每次检查多长时间范围的数据（时间窗口）

> 说明：以下“重叠窗口、重复检查不超过 3 次”是原始容错思路。百万级设备在日落集中离线时，重叠窗口会把同一批候选重复放大。本文 §“推演补充”推荐改为“每逻辑分片独立持久化水位 + 非重叠窗口 + 失败分片重试”。

如果一分钟检查一次，以三分钟为检查时间窗口。

如果二分钟检查一次，以六分钟为检查时间窗口。

#### 5分钟窗口
所有设备都是5分钟发送一次消息，也就是说任意一个5分钟窗口内，平台会收到全部设备的消息。

所以检查的窗口没有必要超过5分钟，因为5分钟就能包含平台所有设备的活跃情况。

#### 定时任务

百万级别的Redis Sorted Set，切片合理的情况下，每分钟Range查询一次是没有压力的。

当然，设备规模是动态增加的，具体要根据当前的压测情况调整切片规模和定时任务周期。

#### 定时检查不活跃设备
一分钟检查一次设备活跃情况。

每次Range查询距离当前时间15分钟到17分钟（3分钟窗口）活跃的设备，

## 推演补充：百万级 DeviceActive 设计（2026-07-12）

> 本节基于现有文档和需求讨论补充。公司源码不可复制，文中“已确认”表示需求与现有设计语义已经确认；“推荐”表示为容量和正确性补充的设计约束，不代表源码已经实现。

### 1. 已确认职责

`deviceActive` 只负责：

1. 记录设备最后一次合法业务上报时间；
2. 每分钟分片执行 `ZRANGEBYSCORE` 窗口扫描；
3. 发现离线或异常离线候选；
4. 状态迁移成功后调用：

```go
projectDevicesStatus.
    NewProjectDevicesStatusManage(ctx, svcCtx).
    UpdateDeviceStatus(deviceKey, projectID, deviceStatus)
```

它不根据 MQTT CONNECT、DISCONNECT、TCP session 或 Broker Presence 判定设备在线。

### 2. 活跃时间来源

规则引擎收到合法遥测、事件或指令消息后发布 NATS/EventBus `reportMessage`，平台订阅该消息并触发 `OnlineFix`。

推荐在 `reportMessage` 中同时保留：

```text
occurredAt  设备产生业务数据的时间，只用于业务排序和展示
receivedAt  平台首次收到并验证合法消息的时间，用于设备活跃判定
```

DeviceActive 必须使用 `receivedAt`。设备时钟可能漂移、重启归零或上报未来时间；NATS 消费者也不能在重放时使用当前 `now()` 冒充原始接收时间。

### 3. 写入批处理

DeviceActive 不是每条消息同步写 Redis：

```text
reportMessage
  -> 内存 buffer
  -> 同一 member 保留本批最大 receivedAt
  -> 达到 batchSize 或 1 秒
  -> flushBatch
  -> 按 Redis slot/node 拆分 Pipeline
  -> ZADD GT
```

推荐语义：

- buffer 必须有界；满时不得静默丢弃，应背压、同步降级写或进入可靠重试；
- 同一 member 在一个批次只保留最大 `receivedAt`；
- Redis 更新只允许 score 前进，旧消息和重放消息不能回拨最后活跃时间；
- 同一逻辑分片同一时刻最多一个 flush in-flight，避免旧批次晚于新批次完成。

### 4. Member 模型

#### 4.1 原设计

当前讨论确认的原设计是：

```text
key    = cache:things:device:active:{shard}
member = Encode(projectID, deviceKey)
score  = receivedAt
```

收益：定时任务扫描后可以直接解出 `projectID + deviceKey`，无需逐设备读取 `things:device:meta`，即可调用 `UpdateDeviceStatus`。

约束：

- 编码必须可逆，不能依赖可能与 deviceKey 冲突的裸分隔符；
- 逻辑分片应按稳定 `deviceKey` 计算，不能按完整 `projectID+deviceKey` 计算；
- 设备转移项目时，必须在同一 Active ZSET 中 `ZREM` 旧 member、`ZADD` 新 member；
- 若漏删旧 member，旧项目会在 15 分钟或 15 小时后收到幽灵状态更新。

#### 4.2 待选替代方案

```text
ZSET cache:things:device:active:{shard}
  member = deviceKey
  score  = receivedAt

HASH cache:things:device:route:{shard}
  field = deviceKey
  value = projectID + assignmentVersion
```

两个 key 使用相同 Hash Tag 后，可以通过有界 Lua/Redis Function 在一次 Redis 调用中执行：

```text
ZRANGEBYSCORE Active
  + HMGET Route
  -> 返回 deviceKey、score、projectID、assignmentVersion
```

该方案避免项目迁移时搬迁 Active member，但多维护一个路由 Hash。最终选择应以项目迁移频率、真实内存占用和压测结果为依据。

### 5. 分片数量计算

分片数不固定写死为 64、128 或 256：

```text
S_capacity = ceil(规划设备总数 / 单分片目标设备数)

S_burst = ceil(峰值 score 窗口命中设备数 / 单次查询目标返回数)

S = max(S_capacity, S_burst)
```

单分片建议控制在 5 万～10 万台设备，最终以目标环境压测为准。

示例：

```text
规划设备总数             = 1,000,000
单分片目标设备数         = 100,000
S_capacity               = 10

夜间一分钟集中到期       = 50,000
单次查询目标返回数       = 1,000
S_burst                  = 50

最终至少 50 片，可向上取 64
```

逻辑分片是应用创建的 ZSET key；它会被 Redis 映射到一个 0..16383 的 slot，再由某个 Redis Master 负责。逻辑分片、slot 和物理 Redis Master 不是一一对应关系。

### 6. 分片错峰扫描

不要在每分钟第 0 秒同时扫描所有逻辑分片。以 64 个逻辑分片为例，可以大约每秒扫描一个分片，一分钟覆盖全部分片。

若日落时一分钟内有 5 万台设备集中到期：

```text
50,000 / 64 ≈ 781 台/分片
50,000 / 60 ≈ 833 台/秒
```

错峰后不会一次把 5 万个 member 加载到 Go 堆并同时冲击 DB、Alarm 和项目状态缓存。

### 7. 每逻辑分片独立水位

每个分片分别保存两个水位：

```text
offline_watermark
abnormal_watermark
```

扫描区间：

```text
offline_upper  = now - 15min
abnormal_upper = now - 15h

offline range  = (offline_watermark, offline_upper]
abnormal range = (abnormal_watermark, abnormal_upper]
```

推荐 key：

```text
cache:things:device:active:{shard}       ZSET
cache:things:device:active:meta:{shard}  HASH
```

Meta Hash 至少包含：

```text
offline_watermark
abnormal_watermark
owner_epoch
config_version
```

推进规则：

1. 范围查询成功；
2. 对候选二次读取当前 score；
3. 状态迁移成功；
4. `projectDevicesStatus` 已可靠落 Redis，或候选已可靠进入可重放队列；
5. 才能推进对应水位。

若进程在推进前崩溃，下次会重复扫描同一区间；项目 ZSET 的同 member `ZADD` 是覆盖写，重复执行不会把数量累加。

### 8. OnlineFix 与扫描竞态

普通在线设备的活跃写可以继续批量处理。但设备从离线/异常离线恢复时，如果只把新时间放入 buffer 就立即改在线，可能发生：

```text
新 active score 尚未 flush
  -> OnlineFix 已改在线
  -> 定时任务仍读到旧 score
  -> 再次改为离线
```

推荐：

- 恢复在线属于低频状态迁移，可同步执行 `ZADD GT`，或等待该 member 的 flush barrier；
- 超时任务取得候选后，在设备锁/CAS 内重新读取最新 score；
- 只有 score 仍然落在阈值外且 expectedStatus/version 匹配，才能提交离线/异常离线。

### 9. 有界处理与失败恢复

```text
错峰扫描
  -> 每分片范围查询
  -> 有界候选队列
  -> 固定 worker 池
  -> 二次校验
  -> 状态迁移
  -> projectDevicesStatus 批量写
```

队列满时停止继续扫描，不能无界堆积。由于水位尚未推进，后续可以继续追赶。

必须监控：

- 每分片设备总数和窗口命中数；
- 单次范围查询返回量、耗时和响应字节数；
- 候选队列长度与最老候选等待时间；
- 每分片 offline/abnormal 水位滞后；
- 二次校验拒绝数；
- Redis Pipeline 成功率、p99 和重试数；
- Go heap、分配速率、GC pause 和 goroutine 数；
- DB 状态更新、Alarm 生成和项目状态重算积压。

### 10. 当前待确认项

1. 原实现的 member 编码格式以及 projectID/deviceKey 是否可能包含分隔符；
2. 最终保留 `projectID+deviceKey`，还是采用稳定 member + Route Hash；
3. `UpdateDeviceStatus` 是否能返回“已完成 Redis flush”的确认；
4. 扫描任务是否已有分片 owner/lease，多个服务实例是否可能重复扫描同一分片；
5. 项目迁移是否已经清理旧 Active member；
6. 15 分钟/15 小时阈值变更时，水位和历史设备状态如何重算。

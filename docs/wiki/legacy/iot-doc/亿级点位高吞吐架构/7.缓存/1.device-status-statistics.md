## 3. 整体架构：三套并存的缓存机制
本目录的缓存按底层实现分成三类，**这是理解全貌的第一把钥匙**：

| 类别 | 底层 | 适用 | 代表文件 |
| --- | --- | --- | --- |
| **A. **`caches.Cache[T,K]`** 读穿框架** | L1=进程内 otter 内存 + L2=Redis + L3=DB（GetData 回调），跨节点失效走 FastEvent(NATS) | 设备元数据 / 鉴权 / OTA / 物模型 Schema（需要读穿、需要多节点一致） | deviceRuntimeMeta / deviceSecret / deviceOtaConfirm / schemaBundle |
| **B. 纯 **`kv.Store`** 薄封装** | 直接读写 Redis（SETEX/ZSET/SETNX），无本地内存、无框架 | 轻量、临时、强一致点查 | bandChange / gatewayCandBind / msgRepo / onlineHandle |
| **C. 手写 Redis ZSET 批量管道** | `kv.Store` 的 ZSET 操作 + 进程内 buffer channel 批处理 + 后台协程 | 设备状态 / 电站状态（百万级设备、高频写、按 score 范围扫描） | sortedSet/deviceActive / sortedSet/projectDevicesStatus |


> 注意：A 类用的是 `caches.GetStore()`（全局单例 redis client）；B/C 类用的是 `svcCtx.Cache`（即 `ca := caches.NewRawStore(...)`，另一个独立 redis client 实例）。两者指向同一 Redis 集群但是不同 client 对象（见 §11 陷阱）。

## 4. 地基：`caches.Cache[T,K]` 读穿框架
> 实现在 `saas/share/caches/`（不在本目录），但本目录 4 个元数据缓存全部建立在它之上，必须先懂它。
>

### 4.1 三级结构与读路径
`caches.Cache[dataT, keyType]` 是泛型读穿缓存：

```plain
GetData(ctx, key)
  ├─ L1: otter（进程内内存）命中 → 返回
  │        命中 nil 值 → 返回 errors.NotFind（负缓存，表示"确认查无"）
  ├─ L1 未命中 → SingleFlight 防击穿（并发同 key 只回源一次）
  │   ├─ L2: Redis store.GetCtx(cacheKey) 命中 → 解压+反序列化+fmt加工 → 回填 L1 → 返回
  │   ├─ L2 空 && GetData 回调 == nil → L1 塞 nil 占位，返回 (nil, nil)
  │   └─ L2 空 → 调 GetData(ctx, key) 从 DB 加载
  │              ├─ DB 返回 errors.NotFind → 视为查无，L1 塞 nil
  │              ├─ DB 其它 err → 直接上抛
  │              └─ DB 成功 → fmt 加工 → 回填 L1 → 异步（ctxs.GoNewCtx）写 L2
```

### 4.2 关键事实
+ **Redis 实际 key**：`GenCacheKey(key) = fmt.Sprintf("cache:%s:%v", keyType, key)`
    - `keyType` 来自 `iot/pkg/topics/cache.go` 的 `ServerCacheKeyXxx` 常量（同时是 Redis key 前缀、NATS topic 后缀、单例注册表键，三位一体，**必须全局唯一**）。
    - `%v` 对 struct key 用默认格式化；若 key 类型实现了 `String()` 则走 `String()`（如 `ProductReleaseKey`）。
+ **L1 otter key**：`GenKeyStr(key) = utils.Fmt2(key)`（struct → JSON 串）。与 L2 的 `%v` 不同，二者不串。
+ **TTL 两级**：
    - L2（Redis）`= ExpireTime + rand[0, ExpireJitter)`（抖动防雪崩，单位秒）。
    - L1（otter）`= L2 TTL / 3 + 1`（本地先过期，强制回 Redis 校验）。
    - `NoExpire=true` 时：L2 无 TTL（`SetCtx`），L1 = 100 年。
+ **容量**：`Capacity`（默认 10_000），Cost 恒为 1（按条数计，不是字节数），超容量由 otter 的 W-TinyLFU 淘汰。
+ **单例**：`NewCache` 按 `cfg.KeyType` 在 `cacheMap` 中去重。**同一 KeyType 第二次以不同泛型实参 NewCache 会类型断言 panic**。
+ **失效（写路径）**：`SetData(ctx, key, nil)` 三连：①`store.Del` 删 L2 ②`c.cache.Delete` 删本地 L1 ③`fastEvent.Publish(genTopic, keyStr)` 广播，各节点订阅回调收到后删各自 L1 并跑 `notifySlot` 钩子。
    - NATS 失效 topic：`fmt.Sprintf(eventBus.ServerCacheSync, keyType)` = `"server.cache.sync.<keyType>"`。
+ **跨服务失效**：`caches.InvalidateServerCache(ctx, keyType, key, fe)`（删 Redis + 广播，供 system 等写库方调用）；`WarmServerCacheJSON`（直接把 JSON 写进 Redis 预热 + 广播）。
+ **压缩**：仅 `things:schema:product:current` / `things:schema:product:release` 两个 KeyType 启用 zstd（payload ≥1KB 才压，`zstd:` 前缀标记）。
+ **rawStore**：`caches/store` 实际是 `raw_store.go` 的 `rawStore`，直接包装 go-redis v9，**绕过 go-zero kv.Store 封装层的 context-deadline bug**。`GetCtx` 把 go-redis `Nil` 吞成 `("", nil)`，所以"存在"靠 `len(val) > 0` 判定。

## 6. 设备状态统计推演稿（2026-07-12）

> 本节依据现有设计文档和需求讨论补充。由于公司源码不可复制，以下内容分为“已确认现状”“推荐增强”“待确认项”，不能把推荐增强视为已经实现的源码事实。
>
> 详细设计分别见 [DeviceActive](./2.device-active-cache) 和 [ProjectDevicesStatus](./3.project-status-cache.md)。

### 6.1 已确认的业务口径

1. 设备活跃不以 MQTT CONNECT、DISCONNECT 或 TCP 连接状态为准。
2. 规则引擎收到合法遥测、事件或指令消息后，向 NATS/EventBus 的 `device.up.thing.report.>` 发布 `reportMessage`。
3. 平台消费 `reportMessage` 时触发 `OnlineFix`，并把设备最后活跃时间提交给 `deviceActive`。
4. 设备超过 15 分钟没有合法业务上报，进入离线状态；超过 15 小时，进入异常离线状态。
5. 新建设备尚未上报过合法业务消息时，初始状态计为离线。
6. `reportMessage` 中的设备发生时间用于业务数据；设备活跃判定应补充平台可信的 `receivedAt`，不能依赖设备时钟。
7. 设备故障/恢复事件带稳定的物模型标识。只要仍存在一个未恢复事件，设备的故障事实就仍然存在；恢复其中一条事件不能清除其他故障。
8. 异常、故障与在线/离线之间的展示优先级可能随产品和业务场景变化，缓存基础层不应写死统一覆盖规则。

### 6.2 状态编码与事实分层

当前项目设备状态 ZSET 使用以下 score：

| score | 当前含义 |
| --- | --- |
| 2 | 在线 |
| 3 | 离线 |
| 4 | 异常 |

一个 ZSET member 同时只能拥有一个 score。因此，建议在概念上区分以下事实：

```text
DeviceActivity
  - last_received_at
  - ONLINE / OFFLINE / ABNORMAL_OFFLINE

DeviceActiveEvents
  - 尚未恢复的物模型事件标识集合
  - active_event_count / has_active_event

EffectiveDeviceStatus
  - 根据业务场景策略，把 Activity + ActiveEvents 投影为 2 / 3 / 4
```

`EffectiveDeviceStatus` 可以写入项目状态 ZSET，供项目页面快速 `ZCOUNT`；但“连接状态设备数”和“故障设备数”若要求彼此独立，必须分别来源于 Activity 和 ActiveEvents，不能只依赖一个 score=4。

### 6.3 两层 ZSET 的职责边界

```text
合法 reportMessage
  ├─> deviceActive
  │     记录最后活跃时间
  │     每分钟按分片、score 窗口发现离线/异常离线候选
  │
  └─> OnlineFix
        离线/异常离线设备重新活跃时修复设备状态

设备状态真正变化
  ├─ 设备上线
  ├─ deviceActive 判定离线/异常离线
  └─ reportMessage Event 转为 Alarm/Recovery
        │
        v
projectDevicesStatus.UpdateDeviceStatus(deviceKey, projectID, deviceStatus)
        │
        v
批量写项目设备状态 ZSET
```

`deviceActive` 是时间事实与超时调度索引；`projectDevicesStatus` 是项目维度的设备有效状态索引。二者互相配合，不应合并为同一个 ZSET。

### 6.4 统计范围

产品要求至少支持以下范围：

1. 整个 SaaS 平台全局设备统计；
2. 单租户设备统计；
3. 全平台单产品分类统计；
4. 单租户下单产品分类统计；
5. 单项目设备统计。

每个范围至少返回：

```text
total
online
offline
abnormal_offline
fault
as_of
```

其中应持续校验：

```text
total = online + offline + abnormal_offline
0 <= fault <= total
```

故障数独立于连接状态，不参与前三个连接状态之和。项目和租户自身的故障状态可由其 `fault_device_count` 从 `0 -> 1` 和 `1 -> 0` 的边界变化派生；具体展示优先级由业务策略决定。

### 6.5 百万级容量原则

百万级指设备存量，不等于百万条每秒写入。系统负载由合法上报速率、状态转换速率以及同一 score 窗口内集中到期数量共同决定。

禁止以下实现：

- 每分钟全量扫描全部设备；
- 单个 `ZRANGEBYSCORE` 返回数万或数十万 member 后一次性加载、处理；
- 每条合法上报同步写 Redis；
- 每次设备状态变化立即、同步地重算项目/租户/平台状态；
- 使用一个全局大 ZSET 承担全部写入和范围查询。

推荐：

- `deviceActive` 先在内存中按 member 合并，保留本批最大 `receivedAt`；达到 `batchSize` 或 1 秒时 `flushBatch`；
- Redis Cluster 下按目标 slot/node 拆分 Pipeline；
- 每个逻辑分片独立、错峰执行 score 窗口扫描；
- 扫描结果进入有界队列，由固定 worker 数消费；
- `projectDevicesStatus` 继续按数量阈值或 1 秒批量写项目 ZSET；
- 同一批内对 `projectID + deviceKey` 合并，并对项目状态重算按 projectID 去重。

### 6.6 分片数量计算

分片数不能固定写死为 64、128 或 256，应由规划容量与峰值窗口共同计算：

```text
S_capacity = ceil(规划设备总数 / 单分片目标设备数)

S_burst = ceil(峰值 score 窗口命中设备数 / 单次查询目标返回数)

S = max(S_capacity, S_burst)
```

单分片建议控制在 5 万～10 万台，最终值以目标 Redis、真实 member 长度和真实 score 窗口分布压测为准。

示例：

```text
规划设备数                 = 1,000,000
单分片目标容量             = 100,000
S_capacity                 = 10

夜间一分钟集中到期设备数   = 50,000
单次范围查询目标返回数     = 1,000
S_burst                    = 50

最终至少 50 个逻辑分片，可向上取 64
```

### 6.7 逻辑分片、Redis slot 与物理分片

```text
deviceKey
  -> 应用哈希得到逻辑分片编号
  -> 对应一个 DeviceActive ZSET key
  -> Redis 对该 key 计算 0..16383 中的一个 slot
  -> slot 由某个 Redis Master（物理分片）负责
```

三者不是一一对应关系：

| 层级 | 含义 |
| --- | --- |
| 应用逻辑分片 | DeviceActive 被拆成多少个 ZSET key |
| Redis slot | Redis Cluster 固定的 16384 个路由槽 |
| 物理分片 | Redis Master 及其 Replica 组成的分片组 |

一个逻辑分片 key 只属于一个 slot；一个物理 Master 通常负责许多 slot 和许多逻辑分片 key。

### 6.8 每分片独立水位

若采用非重叠、可追赶的窗口扫描，每个逻辑分片应分别保存离线和异常离线水位：

```text
offline_upper  = now - 15min
abnormal_upper = now - 15h

offline range  = (last_offline_watermark, offline_upper]
abnormal range = (last_abnormal_watermark, abnormal_upper]
```

64 个逻辑分片只需要 128 个时间水位字段。水位必须在候选状态已经可靠落地，或已经可靠写入可重放队列后推进。若 `UpdateDeviceStatus` 只写入进程内 channel，还没有完成 Redis flush，则不能提前推进水位。

单分片失败时只重试该分片；其他分片可以正常推进。相比一个全局水位，这能避免局部失败导致全局重复或漏扫。

### 6.9 关键竞态

#### 6.9.1 OnlineFix 与超时扫描

普通活跃消息可以继续 1 秒批量写，但设备从离线/异常离线恢复时存在竞态：

```text
OnlineFix 把新 active 写请求放进 buffer
  -> 尚未 flush Redis
  -> OnlineFix 已把设备改为在线
  -> 超时扫描仍读到旧 score
  -> 又把设备覆盖为离线
```

推荐恢复在线路径提供同步 `ZADD GT` 或 `flush barrier`，并让超时路径在同一设备锁/CAS 范围内二次读取当前 score。

#### 6.9.2 三个状态来源乱序

`UpdateDeviceStatus` 同时接收上线、超时状态和 Alarm/Recovery。若一秒 buffer 只保留“最后到达”的状态，多服务并发下到达顺序不等于业务新旧顺序。推荐增加 `stateVersion/updatedAt` 并只接受更新版本，或在 flush 前读取权威 `things:device:meta` 的最终状态。

#### 6.9.3 设备转移项目

若 DeviceActive member 编码为 `projectID + deviceKey`，项目转移时必须删除旧 member 并写入新 member；否则旧 member 会在后续超时窗口中把设备重新写回旧项目。

该 member 模型与以下替代模型尚待最终选型：

```text
ZSET active:{shard}
  member = deviceKey
  score  = receivedAt

HASH route:{shard}
  field = deviceKey
  value = projectID + assignmentVersion
```

Active 与 Route 使用相同 Hash Tag 时，可以通过有界 Lua/Redis Function 在一次调用中完成范围查询和批量路由读取；代价是多维护一个路由 Hash，收益是设备转移项目时不需要搬迁 Active member。

### 6.10 内存与 GC 验证

当前没有真实 key/value 长度和目标 Redis 版本的实测数据，不应在文档中写死“每百万设备占用多少 GB”。验收时必须使用真实数据执行：

```text
MEMORY USAGE <sample-key>
MEMORY STATS
INFO memory
```

重点比较：

1. `member=projectID+deviceKey` 的 ZSET；
2. `member=deviceKey` 加分片 Route Hash；
3. 项目、租户、产品分类多份状态索引产生的 member 重复存储；
4. 主从副本、AOF rewrite 和故障转移时的额外内存；
5. Go 扫描结果、批处理 map、channel 积压对堆内存和 GC pause 的影响。

Go 侧不得一次把所有分片、所有窗口结果聚合进一个无界 slice。每个分片查询结果应立即进入有界处理流程，并监控队列长度、最老待处理时间、分配速率和 GC 暂停。

### 6.11 当前待确认项

1. DeviceActive 最终采用 `projectID+deviceKey` member，还是稳定 `deviceKey + Route Hash`；
2. `UpdateDeviceStatus` 当前是否携带状态版本，或 flush 前是否读取权威 meta；
3. 项目转移是否已同步清理旧 DeviceActive member 与旧项目状态 member；
4. Alarm/Recovery、在线、离线、异常离线在不同产品场景中的状态覆盖策略；
5. 单租户、全局分类、租户分类统计采用同构 ZSET，还是从全站/项目索引构建分片汇总视图；
6. 扫描候选在推进水位前的可靠落地方式：批处理完成确认、Redis Stream、JetStream 或 DB outbox。

## 7. 可选：全站设备级明细索引

> 本节只适用于“点击全站状态数量后，还要按状态分页查看全站设备明细”的场景。若产品只需要统计数量，默认采用 §8 的 `ProjectSummary + Aggregate`，不再复制一份全部设备 member。

### 7.1 适用边界

全站设备级 ZSET 可以提供按状态枚举和分页能力，但分片只解决单 key 热点，不减少总 member 数量。因此它不是纯统计需求的默认实现。

启用该可选索引时，数据流如下：

```text
设备状态变化
  ├─> 单项目设备状态 ZSET（现有）
  ├─> 全站设备状态分片 ZSET（新增）
  └─> 全站故障设备分片 SET/ZSET（新增）

项目设备状态批量写成功
  -> dirty projectID
  -> project_status_check_batcher
  -> ProjectStatusPolicy.Resolve
  -> 全站 Project 状态 ZSET（新增）

后台 SnapshotBuilder
  -> 汇总设备分片
  -> 汇总 Project 分片
  -> 生成两个 O(1) 查询 View Hash
```

详细的项目缓存调用链见 [ProjectDevicesStatus](./3.project-status-cache.md)。

### 7.2 可选全站设备状态索引

全站连接状态按稳定设备标识分片：

```text
key    = cache:things:devices:status:{deviceShard}
member = Encode(tenantID, deviceKey)
score  = activityStatus
```

这里的 score 应保存连接/活跃事实：

| score | 含义 |
| --- | --- |
| 2 | 在线 |
| 3 | 离线 |
| 4 | 异常离线 |

故障事实单独保存：

```text
key    = cache:things:devices:fault:{deviceShard}
member = Encode(tenantID, deviceKey)
```

同一分片的 Status ZSET 和 Fault SET/ZSET 使用相同 Hash Tag。这样 SnapshotBuilder 可以用一个有界 Lua/Redis Function 在同一个 Redis Master 内返回：

```text
ZCARD  statusKey
ZCOUNT statusKey 2 2
ZCOUNT statusKey 3 3
ZCOUNT statusKey 4 4
SCARD  faultKey
```

得到单分片的 `total/online/offline/abnormal_offline/fault` 后，再在 Go 中求和。Lua 只做固定数量的计数命令，不能扫描或返回设备明细。

项目 ZSET 的 score 可能受场景展示策略影响，因此不能不加区分地复制为全站连接状态。全站 Activity 和 Fault 必须来源于各自事实。

### 7.3 可选明细索引的统一投影事件

三个设备状态来源统一生成完整投影快照：

```go
type DeviceStatusProjection struct {
    DeviceKey     string
    TenantID      string
    ProjectID     string
    CategoryID    int64
    ActivityState int64
    FaultActive   bool
    EffectiveStatus int64
    StateVersion  uint64
    UpdatedAt     int64
}
```

来源：

1. `OnlineFix`；
2. `deviceActive` 判定离线/异常离线；
3. Alarm/Recovery 改变未恢复事件集合。

一次状态变化经过批量器后：

```text
ZADD projectDeviceStatusKey effectiveStatus deviceKey
ZADD globalDeviceStatusShard activityState tenantID:deviceKey

FaultActive false -> true：
  SADD projectFaultKey deviceKey
  SADD globalFaultShard tenantID:deviceKey

FaultActive true -> false：
  SREM projectFaultKey deviceKey
  SREM globalFaultShard tenantID:deviceKey
```

`stateVersion` 用于拒绝旧批次晚到。项目 ZSET、全站设备 ZSET 位于不同 slot，不能伪装成一个原子事务；各投影必须幂等、可重试并支持对账。

### 7.4 单项目设备统计

单项目继续直接查询现有 ZSET：

```redis
ZCARD  cache:things:project:devices:status:<projectID>
ZCOUNT cache:things:project:devices:status:<projectID> 2 2
ZCOUNT cache:things:project:devices:status:<projectID> 3 3
ZCOUNT cache:things:project:devices:status:<projectID> 4 4
```

若项目页面要求故障数与连接状态独立，再维护：

```text
cache:things:project:devices:fault:<projectID>
```

该索引只在设备有效故障集合 `0 -> 1` 或 `1 -> 0` 时变更。

### 7.5 全站 Project 状态索引

项目设备状态 Pipeline 写成功后，将受影响的 projectID 放入 `project_status_check_batcher`。同一批有多台设备变化时，按 projectID 合并，只重算一次：

```text
dirty projectID
  -> 读取项目设备 ZCARD/ZCOUNT 和 faultDeviceCount
  -> ProjectStatusPolicy.Resolve(..., scenePolicy)
  -> 项目状态真正变化时写全站 Project 状态索引
  -> faultDeviceCount 跨越 0/1 边界时更新全站故障 Project 索引
```

全站 Project 状态 ZSET：

```text
key    = cache:things:projects:status:{projectShard}
member = Encode(tenantID, projectID)
score  = effectiveProjectStatus
```

项目故障若要求与项目有效状态独立统计，再维护：

```text
key    = cache:things:projects:fault:{projectShard}
member = Encode(tenantID, projectID)
```

Project 分片数必须按规划项目总量、热点窗口和单次查询目标返回数单独计算，不能直接复用 DeviceActive 的分片数。项目总数低于单分片压测安全容量时，可以先使用一个 Project 状态 ZSET。

### 7.6 全站快照 View

后台每 2～5 秒或按脏分片触发汇总，生成：

```text
cache:things:devices:status:view
  total
  online
  offline
  abnormal_offline
  fault
  as_of
  generation

cache:things:projects:status:view
  total
  status_2
  status_3
  status_4
  fault
  as_of
  generation
```

API 查询路径：

```text
GET 全站设备统计 -> HGETALL devices:status:view
GET 全站项目统计 -> HGETALL projects:status:view
GET 单项目统计   -> ZCARD/ZCOUNT project device status ZSET
```

全站 API 为 O(1)，不在用户请求中遍历逻辑分片。返回结果必须包含 `as_of`，让调用方识别统计新鲜度；生成新 View 时应一次写入完整快照，避免混读不同刷新周期的字段。

### 7.7 生命周期与迁移

```text
创建设备：
  全站设备状态 ZADD offline
  项目设备状态 ZADD offline（若已归属项目）

删除设备：
  全站设备状态 ZREM
  全站故障 SET ZREM
  项目设备状态 ZREM
  项目故障 SET ZREM

设备转移项目：
  全站设备状态不变
  旧项目 ZREM
  新项目 ZADD currentEffectiveStatus
  FaultActive=true 时把 deviceKey 从旧项目 Fault SET 搬到新项目
  old/new projectID 都进入项目状态重算队列

项目删除：
  全站 Project 状态 ZREM
  全站 Project 故障 SET ZREM
```

如果发生跨租户迁移，全站 member 的 tenantID 部分也需要搬迁；所有迁移操作应携带 `assignmentVersion`，防止旧迁移事件晚到后把设备搬回原范围。

### 7.8 一致性与对账

必须持续验证：

```text
全站设备 total = online + offline + abnormal_offline
0 <= 全站设备 fault <= total

全站 Project total = 各 Project 有效状态数量之和
0 <= 故障 Project 数 <= Project total
```

推荐的恢复手段：

1. 每个投影写入携带 `stateVersion`，旧版本不覆盖新版本；
2. Pipeline 部分失败只重试失败子批；
3. 项目状态只有在项目设备状态批次成功后才进入重算；
4. SnapshotBuilder 标记 `as_of/generation`；
5. 周期性从权威 DB/meta 或可重放状态日志重建全站 ZSET 和 View；
6. 监控全站 View 与分片 ZCOUNT 求和之间的 drift。

### 7.9 夜间集中离线容量

若一分钟有 5 万台设备集中离线：

```text
50,000 / 60 ≈ 833 次设备状态迁移/s
```

每台设备正常产生一次项目状态 `ZADD` 和一次全站设备状态 `ZADD`，约 1,666 次 ZADD/s；经过一秒批量和 Pipeline 后，Redis 通常不是首要瓶颈。压测重点应放在：

- DB 设备状态更新；
- Alarm 生成与恢复；
- `things:device:meta` 失效；
- 同一项目大量设备变化时的 dirty project 合并；
- ProjectStatusPolicy 重算积压；
- 全站 View 的最大陈旧时间。

## 8. 推荐：ProjectSummary + 分片 Aggregate

### 8.1 适用场景与结论

当前业务中一个电站通常只有少量设备，但电站数量很多；全站核心需求是状态数量，而不是全站设备明细枚举。因此默认不再增加 O(设备数) 的全站设备 ZSET，而是复用现有项目设备状态 ZSET，生成 O(项目数) 的项目摘要和固定数量分片汇总。

```text
项目设备状态 ZSET（现有设备级事实）
  -> project_status_check_batcher
  -> ProjectSummary
  -> ProjectAggregateShard
  -> 全站 Device/Project View
```

该结构一次同时得到：

- 全站设备 `total/online/offline/abnormal_offline/fault`；
- 全站 Project `total/status_2/status_3/status_4/fault`；
- 单项目设备状态统计；
- 项目自身有效状态。

### 8.2 ProjectSummary

项目设备状态批量写成功后，`project_status_check_batcher` 按 projectID 合并。对于每个 dirty project，只读取一次项目 ZSET 和故障索引，生成：

```go
type ProjectStatusSummary struct {
    ProjectID       string
    TenantID        string
    TotalDevices    int64
    Status2Devices  int64
    Status3Devices  int64
    Status4Devices  int64
    FaultDevices    int64
    ProjectStatus   int64
    ProjectFault    bool
    SummaryVersion  uint64
    UpdatedAt       int64
}
```

项目设备数量来自：

```text
ZCARD  projectDeviceStatusKey
ZCOUNT projectDeviceStatusKey 2 2
ZCOUNT projectDeviceStatusKey 3 3
ZCOUNT projectDeviceStatusKey 4 4
SCARD  projectDeviceFaultKey
```

`ProjectStatusPolicy.Resolve` 根据项目产品/场景策略计算 `ProjectStatus`；缓存基础层不写死异常、故障、在线和离线的覆盖顺序。

这里的 `Status2/3/4Devices` 是现有项目 ZSET 的有效展示状态数量。如果业务策略允许异常/故障覆盖在线，它们不能自动解释为原始 Activity 三态。若产品要求原始 `ONLINE/OFFLINE/ABNORMAL_OFFLINE` 与 Fault 完全正交，必须额外维护 §7 的 Activity/Fault 事实投影，或维护同等语义的分片原始状态摘要。

### 8.3 分片摘要与汇总

按稳定 projectID 计算 `projectShard`：

```text
cache:things:project:summary:{projectShard}    HASH
  field = Encode(tenantID, projectID)
  value = ProjectStatusSummary

cache:things:project:aggregate:{projectShard}  HASH
  total_devices
  status_2_devices
  status_3_devices
  status_4_devices
  fault_devices
  total_projects
  status_2_projects
  status_3_projects
  status_4_projects
  fault_projects
  aggregate_version
```

Summary 与 Aggregate 使用相同 Hash Tag，由同一个 Redis Master 承载。一个有界 Lua/Redis Function 完成：

```text
读取旧 ProjectSummary
  -> incoming SummaryVersion <= old：幂等忽略
  -> 计算 newSummary - oldSummary
  -> HSET 新 ProjectSummary
  -> HINCRBY 当前 shard 的设备汇总 delta
  -> HINCRBY 当前 shard 的 Project 状态汇总 delta
```

脚本只操作一个项目摘要和固定数量计数字段，不扫描项目设备明细。

### 8.4 全站 View

SnapshotBuilder 每 2～5 秒或按 aggregate dirty 事件，读取所有 ProjectAggregateShard 并求和：

```text
cache:things:devices:status:view
  total
  status_2
  status_3
  status_4
  fault
  as_of
  generation

cache:things:projects:status:view
  total
  status_2
  status_3
  status_4
  fault
  as_of
  generation
```

API：

```text
全站设备数量统计 -> HGETALL devices:status:view
全站 Project 统计 -> HGETALL projects:status:view
单项目设备统计   -> ZCARD/ZCOUNT 项目设备状态 ZSET
```

全站 API 为 O(1)；SnapshotBuilder 的成本是 O(ProjectAggregateShard 数)，不是 O(设备数) 或 O(Project 数)。

### 8.5 项目与设备生命周期

```text
创建设备：
  设备初始离线，写项目设备状态 ZSET
  项目进入 dirty 队列，重算 Summary/Aggregate

删除设备：
  从项目状态和故障索引删除
  项目进入 dirty 队列

设备转移项目：
  旧项目 ZREM，新项目 ZADD currentStatus
  ActiveEvent 存在时同步搬迁项目 Fault member
  old/new projectID 都进入 dirty 队列

创建项目：
  初始化 ProjectSummary；无设备项目的状态由业务策略确定

删除项目：
  用 tombstone/version 从 Summary 和 Aggregate 扣除旧贡献
```

没有归属项目但仍计入全站设备总数的设备，必须进入明确的 `unassigned` 统计桶，不能因为缺少 projectID 而从全站统计中消失。

### 8.6 设备表 status 更新边界

设备关系表或运行状态表中的 status 可以保留，但只能在状态真正变化时更新：

```text
普通合法 reportMessage：
  只推进 DeviceActive receivedAt
  当前已经在线时不执行 DB UPDATE

真实状态迁移：
  offline/abnormal -> online
  online -> offline
  offline -> abnormal
  Alarm/Recovery 导致有效状态变化
  才条件更新 DB status
```

以 100 万设备、每 5 分钟上报一次估算：

```text
每条上报都 UPDATE：约 3,333 UPDATE/s，约 2.88 亿次/天，不合理

每台每天上线/离线各一次：约 200 万次/天，平均约 23/s
若集中在 30 分钟窗口：约 556/s，可通过有界队列和批处理承载
```

推荐条件更新：

```sql
UPDATE device_runtime_state
SET status = :new_status,
    state_version = state_version + 1,
    status_changed_at = CURRENT_TIMESTAMP
WHERE device_id = :device_id
  AND status = :expected_old_status;
```

只有影响行数为 1 才产生状态投影/outbox。若现有设备主表很宽、二级索引很多，或未来进入千万设备规模，可再把易变字段拆到窄表 `device_runtime_state`；百万级且每天仅少量真实迁移时不必为拆表而拆表。

### 8.7 DB COUNT 的定位

数据库精确 COUNT 不作为秒级 API：

```sql
SELECT status, COUNT(*)
FROM device_runtime_state
GROUP BY status;
```

即使存在 status 索引，也需要扫描大量可见索引项或数据页。PostgreSQL 频繁更新会降低 index-only scan 利用 all-visible page 的收益，并产生需要 VACUUM 回收的旧 tuple；MySQL InnoDB 也不会保存事务可见的精确行数，`COUNT(*)` 需要遍历索引。

官方参考：

- [PostgreSQL Index-Only Scans](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)
- [PostgreSQL VACUUM](https://www.postgresql.org/docs/current/sql-vacuum.htm)
- [MySQL InnoDB COUNT](https://dev.mysql.com/doc/refman/8.4/en/aggregate-functions.html)

推荐用途：

```text
实时大盘：ProjectAggregate -> View
低频对账：DB GROUP BY status
故障重建：DB/runtime state + 状态日志重建 Summary/Aggregate
```

DB COUNT 应在只读副本或受限后台任务执行，初始建议 5～15 分钟一次，再根据执行计划、buffer hit、复制延迟和业务允许的修正窗口调整；不得在每个 API 请求中执行。

### 8.8 幂等、一致性与水位

必须满足：

- 项目设备状态 Pipeline 成功后才提交 dirty projectID；
- `ProjectStatusSummary` 携带单调 `SummaryVersion`；
- 同 shard Lua 原子更新旧摘要与 Aggregate delta；
- 重复 dirty 事件不会重复累计；
- Snapshot View 带 `as_of/generation`；
- DB 对账发现 drift 时通过新 SummaryVersion 覆盖修复；
- 设备状态 DB 更新、outbox 和缓存投影之间不得依赖无版本的双写。

持续校验：

```text
全站设备 total = status_2 + status_3 + status_4
0 <= fault_devices <= total_devices

全站 Project total = status_2 + status_3 + status_4
0 <= fault_projects <= total_projects
```

### 8.9 全站设备级 ZSET 的启用条件

只有产品明确要求以下能力时，才启用 §7 的全站设备级明细索引：

- 按在线/离线/异常离线分页列出全站设备；
- 不经过数据库即可进行全站状态集合运算；
- 需要以设备级索引独立校验 ProjectSummary。

若只需要数量统计，不建立全站设备级 ZSET，避免在项目 ZSET 之外重复保存全部设备 member。

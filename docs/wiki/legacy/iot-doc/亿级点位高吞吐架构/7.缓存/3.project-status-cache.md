# ProjectDevicesStatus 项目设备状态缓存

> 文档状态：基于已有文档和需求讨论形成的推演稿，更新时间 2026-07-12。公司源码不可复制，因此本文明确区分“已确认现状”“推荐增强”和“待确认项”。

## 1. 职责

`projectDevicesStatus` 保存“某项目下每台设备当前有效状态”的 Redis Sorted Set 投影，支持：

1. 快速查询项目总设备数；
2. 快速查询项目内各状态设备数；
3. 设备状态变化后触发项目状态重算；
4. 避免查询项目大盘时扫描关系数据库或全部 `things:device:meta`。

它不负责判断最后活跃时间。最后活跃时间和 15 分钟/15 小时超时窗口由 `deviceActive` 负责。

## 2. 已确认数据模型

```text
Redis key = cache:things:project:devices:status:<projectID>
member    = deviceKey
score     = deviceStatus（2 / 3 / 4）
```

当前状态编码：

| score | 含义 |
| --- | --- |
| 2 | 在线 |
| 3 | 离线 |
| 4 | 异常 |

写入示例：

```redis
ZADD cache:things:project:devices:status:project-1001 3 productA:device001
```

同一 `deviceKey` 重复 `ZADD` 会覆盖原 score，不会新增第二条 member，因此相同状态的重复通知天然幂等。

## 3. 统一更新入口

已确认的调用形式：

```go
projectDevicesStatus.
    NewProjectDevicesStatusManage(ctx, svcCtx).
    UpdateDeviceStatus(deviceKey, projectID, deviceStatus)
```

该方法由三类场景调用：

### 3.1 设备上线

```text
规则引擎发布合法 reportMessage
  -> 平台消费 reportMessage
  -> OnlineFix
  -> 离线/异常离线设备状态迁移成功
  -> UpdateDeviceStatus(deviceKey, projectID, onlineStatus)
```

### 3.2 DeviceActive 判定离线/异常离线

```text
每分钟按 DeviceActive 逻辑分片、score 窗口扫描
  -> 从 member 得到 projectID + deviceKey
  -> 二次校验最新 score
  -> 设备状态迁移成功
  -> UpdateDeviceStatus(deviceKey, projectID, offline/abnormalStatus)
```

### 3.3 reportMessage Event 转换为 Alarm/Recovery

```text
平台消费 reportMessage 中的 Event
  -> 根据稳定物模型标识创建、更新或恢复 Alarm
  -> 维护设备未恢复事件集合
  -> 按当前业务场景计算设备有效状态
  -> UpdateDeviceStatus(deviceKey, projectID, effectiveStatus)
```

设备存在多个事件时，恢复其中一个不能直接把设备改为正常；只有未恢复事件集合发生有效边界变化并导致最终状态改变时，才需要更新项目状态 ZSET。

## 4. 批量写入

`UpdateDeviceStatus` 不应逐条同步执行 Redis `ZADD`。已确认的批处理语义是：积攒一定数量，或者最迟 1 秒执行一次 ZSET Pipeline。

```text
三个状态来源
  -> UpdateDeviceStatus
  -> 有界 buffer/channel
  -> 以 projectID + deviceKey 合并
  -> 达到 batchSize 或 1 秒
  -> flushBatch
  -> 按 Redis Master/slot 分组
  -> Pipeline ZADD
```

推荐约束：

- buffer 必须有界，满时不能静默丢状态；
- 同一个 `projectID + deviceKey` 在一个批次只保留一个最终更新；
- 同一逻辑批次按目标 Redis Master 分组，避免把跨节点命令误当成单节点 Pipeline；
- 同一分片/worker 最多一个 flush in-flight，避免旧批次晚于新批次完成；
- Pipeline 部分失败时只确认成功项，失败项进入有界重试；
- 项目状态重算按 projectID 合并，同一批内一个项目只重算一次。

## 5. 并发与状态乱序

### 5.1 问题

同一秒内，同一设备可能收到：

```text
OnlineFix                 -> 在线
DeviceActive 超时检查     -> 离线/异常离线
Alarm/Recovery            -> 异常或恢复后的状态
```

若 buffer 只是“最后入队覆盖”，多服务并发下到达顺序不代表业务状态新旧顺序：

```text
新状态先进入 batch A
旧状态后进入 batch B
batch B 最后完成 Redis ZADD
  -> 旧状态覆盖新状态
```

### 5.2 推荐增强

推荐把接口扩展为概念上的版本化更新：

```go
type DeviceStatusUpdate struct {
    DeviceKey   string
    ProjectID   string
    Status      int64
    StateVer    uint64
    UpdatedAt   int64
    Source      string
}
```

至少采用以下一种正确性机制：

1. 所有设备状态迁移产生单调 `stateVersion`，batch 只保留最大版本；
2. flush 前批量读取权威 `things:device:meta`，以当前最终状态覆盖入队参数；
3. 为项目 ZSET 增加同 slot 的版本索引，通过 Lua/Redis Function 只接受新版本。

若采用第 3 种，建议调整 key 使状态 ZSET 与版本 Hash 使用相同 Hash Tag：

```text
cache:things:project:{projectID}:devices:status  ZSET
cache:things:project:{projectID}:devices:ver     HASH
```

Lua 逻辑：

```text
读取 deviceKey 当前版本
  -> incomingVersion <= currentVersion：忽略
  -> incomingVersion > currentVersion：ZADD status + HSET version
```

当前 key `cache:things:project:devices:status:<projectID>` 是否允许迁移，需结合线上兼容策略确认。

## 6. 查询

单项目查询：

```redis
ZCARD  cache:things:project:devices:status:<projectID>
ZCOUNT cache:things:project:devices:status:<projectID> 2 2
ZCOUNT cache:things:project:devices:status:<projectID> 3 3
ZCOUNT cache:things:project:devices:status:<projectID> 4 4
```

对应：

```text
total
status_2_count
status_3_count
status_4_count
```

ZSET score=4 只能表示最终有效状态为 4。若产品同时要求独立统计“异常离线设备数”和“故障设备数”，必须读取独立的 Activity/ActiveEvents 投影，不能把一个 `ZCOUNT score=4` 同时解释成两个指标。

## 7. 项目与租户状态派生

项目、租户自身也有状态，但异常与在线/离线之间的覆盖规则可能随业务场景变化。因此缓存基础层只保存事实和计数，业务策略层负责计算：

```text
effectiveProjectStatus = ProjectStatusPolicy.Resolve(
    onlineCount,
    offlineCount,
    abnormalCount,
    faultDeviceCount,
    scenePolicy,
)
```

若业务仅关心是否存在故障设备，可使用边界：

```text
faultDeviceCount: 0 -> 1  项目/租户进入故障
faultDeviceCount: 1 -> 0  项目/租户恢复正常
```

项目状态重算应由 `project_status_check_batcher` 合并 projectID 后异步执行，不能每台设备变化都同步重算一次。

## 8. 设备创建、删除与项目迁移

### 8.1 创建设备

新设备初始计为离线：

```redis
ZADD projectStatusKey 3 deviceKey
```

从未上报过合法消息的设备可能还没有 DeviceActive member，但必须存在于项目状态 ZSET，才能保证项目总数正确。

### 8.2 删除设备

```redis
ZREM projectStatusKey deviceKey
```

同时清理 DeviceActive、未恢复事件索引和其他统计范围投影。删除操作必须可重试，避免 ZSET 永久残留。

### 8.3 转移项目

必须执行：

```text
ZREM oldProjectStatusKey deviceKey
ZADD newProjectStatusKey currentStatus deviceKey
```

若 DeviceActive member 使用 `projectID + deviceKey`，还必须同步搬迁 Active member。旧、新项目状态 key 通常跨 Redis slot，不能用一个 Cluster Lua/MULTI 保证原子性；推荐使用带 `assignmentVersion` 的迁移事件、幂等重试和周期对账保证最终完成。

迁移不应改变平台全局、租户内总数和设备连接/故障事实；若跨租户迁移，则需要同时更新租户和租户分类范围。

## 9. 可选：全站设备级明细索引

> 本节只在产品要求按状态分页查看全站设备明细时启用。仅需要数量统计时，默认采用 §10 的 `ProjectSummary + Aggregate`，不复制第二份全部设备 member。

### 9.1 适用边界

全站设备级 ZSET 提供全站设备枚举和分页能力，但分片不能减少总 member 数量。启用时保留现有项目设备状态索引，同时增加：

1. 全站设备状态分片 ZSET；
2. 全站故障设备分片 SET/ZSET；
3. 全站 Project 状态 ZSET；
4. 全站故障 Project SET/ZSET；
5. 设备和 Project 两个短周期 View Hash。

```text
设备状态变化
  ├─> 项目设备状态 ZSET
  ├─> 全站设备状态分片 ZSET
  └─> 全站故障设备分片 SET

项目设备状态写成功
  -> dirty projectID
  -> project_status_check_batcher
  -> ProjectStatusPolicy.Resolve
  -> 全站 Project 状态 ZSET

SnapshotBuilder
  -> 全站设备 View
  -> 全站 Project View
```

### 9.2 可选全站设备状态分片

连接/活跃事实：

```text
key    = cache:things:devices:status:{deviceShard}
member = Encode(tenantID, deviceKey)
score  = activityStatus（2 在线 / 3 离线 / 4 异常离线）
```

故障事实：

```text
key    = cache:things:devices:fault:{deviceShard}
member = Encode(tenantID, deviceKey)
```

Status 与 Fault 使用相同 `{deviceShard}` Hash Tag。SnapshotBuilder 可以使用固定大小 Lua/Redis Function，在同一个 Master 内执行一次 `ZCARD + 3×ZCOUNT + SCARD`，返回该分片的：

```text
total
online
offline
abnormal_offline
fault
```

项目 ZSET 的 score 可能是按场景策略得到的有效展示状态，不能直接复制成全站 Activity。全站连接状态和故障状态必须来自各自事实。

### 9.3 统一投影输入

推荐从三个状态来源生成完整快照：

```go
type DeviceStatusProjection struct {
    DeviceKey       string
    TenantID        string
    ProjectID       string
    CategoryID      int64
    ActivityState   int64
    FaultActive     bool
    EffectiveStatus int64
    StateVersion    uint64
    UpdatedAt       int64
}
```

一次设备状态变化：

```text
ZADD projectDeviceStatusKey effectiveStatus deviceKey
ZADD globalDeviceStatusShard activityState tenantID:deviceKey

FaultActive false -> true：
  SADD projectFaultKey deviceKey
  SADD globalFaultShard tenantID:deviceKey

FaultActive true -> false：
  SREM projectFaultKey deviceKey
  SREM globalFaultShard tenantID:deviceKey
```

现有 `UpdateDeviceStatus(deviceKey, projectID, deviceStatus)` 可以继续作为项目索引内部入口；上层新增统一投影器，负责把同一状态快照分发到项目和全站索引。

### 9.4 Project 状态重算

项目设备状态 Pipeline 成功后，返回本批实际修改或确认成功的 projectID 集合：

```text
successful dirty projectIDs
  -> project_status_check_batcher 按 projectID 合并
  -> 读取项目 ZCARD/ZCOUNT 和 faultDeviceCount
  -> ProjectStatusPolicy.Resolve(..., scenePolicy)
  -> 项目状态真正变化时写全站 Project 索引
  -> faultDeviceCount 跨越 0/1 边界时更新全站故障 Project 索引
```

若一批 1 万台设备变化只涉及 100 个项目，最多提交 100 个 dirty projectID，而不是执行 1 万次项目状态重算。

项目状态索引：

```text
key    = cache:things:projects:status:{projectShard}
member = Encode(tenantID, projectID)
score  = effectiveProjectStatus
```

故障 Project 索引：

```text
key    = cache:things:projects:fault:{projectShard}
member = Encode(tenantID, projectID)
```

Project 分片数根据规划项目总量和热点窗口独立计算，不能直接复用 DeviceActive 的分片数。项目总量低于单 ZSET 压测安全容量时，可以先不分片。

### 9.5 全站快照 View

后台每 2～5 秒或按脏分片触发聚合：

```text
cache:things:devices:status:view
  total / online / offline / abnormal_offline / fault
  as_of / generation

cache:things:projects:status:view
  total / status_2 / status_3 / status_4 / fault
  as_of / generation
```

API：

```text
全站设备统计 -> HGETALL devices:status:view
全站 Project 统计 -> HGETALL projects:status:view
单项目设备统计 -> ZCARD/ZCOUNT project device status ZSET
```

全站 API 为 O(1)，不在请求路径扫描逻辑分片。新 View 应一次写入完整快照，避免字段来自不同刷新周期；响应必须返回 `as_of`。

### 9.6 生命周期

```text
创建设备：
  全站设备状态 ZADD offline
  已绑定项目时，项目设备状态 ZADD offline

删除设备：
  全站状态/故障索引 ZREM
  项目状态/故障索引 ZREM

设备转移项目：
  全站设备状态不变
  旧项目 ZREM
  新项目 ZADD currentEffectiveStatus
  FaultActive=true 时把 deviceKey 从旧项目 Fault SET 搬到新项目
  old/new projectID 都进入项目状态重算

项目删除：
  全站 Project 状态/故障索引 ZREM
```

跨租户迁移会改变全站 member 中的 tenantID 编码，必须携带 `assignmentVersion` 执行旧 member 删除和新 member 写入。

### 9.7 一致性

项目设备、全站设备和全站 Project 索引通常位于不同 Redis slot，不能使用一个 Cluster Lua/MULTI 原子提交。推荐：

- 每个投影携带 `stateVersion`，拒绝旧版本；
- `ZADD/SADD/SREM` 保持幂等；
- Pipeline 只确认成功子批，失败项有界重试；
- 只有项目设备状态写成功后才提交 dirty projectID；
- View 带 `as_of/generation`；
- 周期性从权威 DB/meta 或可重放状态日志重建索引；
- 监控 View 与各分片计数求和之间的 drift。

持续校验：

```text
全站设备 total = online + offline + abnormal_offline
0 <= 全站设备 fault <= total

全站 Project total = 各 Project 有效状态数量之和
0 <= 故障 Project 数 <= Project total
```

### 9.8 租户与产品分类扩展

已确认还需要单租户、全局产品分类、租户内产品分类统计。建议先稳定全站和项目两级投影，再复用同一个 `DeviceStatusProjection` 增加对应索引或汇总视图。

不应在第一阶段同时复制五份设备 member 后再评估内存。最终模式需依据租户数、分类数、超大租户比例、真实 Redis `MEMORY USAGE` 和查询 SLO 决定。

## 10. 推荐：ProjectSummary + 分片 Aggregate

### 10.1 为什么作为默认方案

一个电站通常只有少量设备，但电站数量很大。全站核心需求是状态数量，而现有项目 ZSET 已经保存设备级明细。因此默认不再增加一份全站设备级 ZSET，而是在项目状态重算时生成项目摘要，再维护固定数量的分片汇总。

```text
项目设备状态 ZSET
  -> dirty projectID
  -> ProjectStatusSummary
  -> ProjectAggregateShard
  -> 全站 Device/Project View
```

全站设备级 ZSET 只在需要按状态分页查看全站设备明细时启用，见 §9。

### 10.2 ProjectStatusSummary

```go
type ProjectStatusSummary struct {
    ProjectID       string
    TenantID        string
    TotalDevices    int64
    Status2Devices  int64
    Status3Devices  int64
    Status4Devices  int64
    FaultDevices    int64
    ProjectStatus   int64
    ProjectFault    bool
    SummaryVersion  uint64
    UpdatedAt       int64
}
```

项目设备状态 Pipeline 写成功后，`project_status_check_batcher` 对同一 projectID 去重，并使用项目 ZSET、项目故障 SET 计算完整新摘要。

`Status2/3/4Devices` 表示现有项目 ZSET 中的有效展示状态。由于不同场景可能使用不同的异常/故障覆盖策略，它们不自动等于原始 Activity 三态；若要求原始在线/离线/异常离线与 Fault 正交统计，需要额外维护 §9 的 Activity/Fault 事实投影或同等语义的原始状态摘要。

### 10.3 Redis 模型

```text
cache:things:project:summary:{projectShard}    HASH
  field = Encode(tenantID, projectID)
  value = ProjectStatusSummary

cache:things:project:aggregate:{projectShard}  HASH
  total_devices
  status_2_devices
  status_3_devices
  status_4_devices
  fault_devices
  total_projects
  status_2_projects
  status_3_projects
  status_4_projects
  fault_projects
  aggregate_version
```

Summary 和 Aggregate 使用相同 Hash Tag。一个固定大小 Lua/Redis Function：

```text
读取旧 ProjectSummary
  -> incoming SummaryVersion <= old：忽略
  -> 计算 newSummary - oldSummary
  -> HSET 新摘要
  -> HINCRBY 设备状态 delta
  -> HINCRBY Project 状态 delta
```

同一个重放事件不会重复增加全站数量。脚本不扫描项目设备，只操作一个项目摘要和固定数量字段。

### 10.4 全站 View

SnapshotBuilder 汇总所有 `ProjectAggregateShard`：

```text
cache:things:devices:status:view
  total / status_2 / status_3 / status_4 / fault
  as_of / generation

cache:things:projects:status:view
  total / status_2 / status_3 / status_4 / fault
  as_of / generation
```

SnapshotBuilder 的复杂度是 O(projectShard 数)，API 读取 View 是 O(1)。

### 10.5 设备表 status

设备表的 status 只在真实状态迁移时更新，不能每条 `reportMessage` 都执行相同值 UPDATE：

```text
普通合法上报且设备已经在线：只更新 DeviceActive，不写 DB status

状态真正变化：
  offline/abnormal -> online
  online -> offline
  offline -> abnormal
  Alarm/Recovery 导致有效状态变化
  才条件更新 DB
```

100 万设备每 5 分钟上报一次时，每条上报都 UPDATE 等于约 3,333 UPDATE/s、约 2.88 亿次/天；而每台每天仅上线、离线各一次约为 200 万次/天，平均约 23/s。

推荐使用 expected old status/stateVersion 条件更新；只有真实迁移成功才写 outbox 或产生缓存投影。若主设备表过宽且状态更新造成明显索引、VACUUM/undo 压力，再拆分窄的 `device_runtime_state` 表。

### 10.6 DB COUNT

DB `GROUP BY status` 只用于低频对账、初始化和重建，不服务秒级 API：

```text
实时统计：ProjectAggregate -> View
低频校准：只读副本 GROUP BY status
故障恢复：DB/runtime state + 状态日志重建 Summary/Aggregate
```

参考：

- [PostgreSQL Index-Only Scans](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)
- [PostgreSQL VACUUM](https://www.postgresql.org/docs/current/sql-vacuum.htm)
- [MySQL InnoDB COUNT](https://dev.mysql.com/doc/refman/8.4/en/aggregate-functions.html)

初始建议每 5～15 分钟在只读副本对账一次，再依据执行计划、数据库负载和统计修正窗口调整，不能在每个 API 请求中执行精确 COUNT。

### 10.7 生命周期

```text
创建设备：写项目 ZSET offline -> dirty project -> Summary/Aggregate
删除设备：项目 ZREM -> dirty project -> Summary/Aggregate
项目迁移：old/new project 均 dirty；同租户全站设备总数不变
项目删除：以 tombstone/version 从 Summary/Aggregate 扣除旧贡献
```

未绑定项目但仍计入全站设备总数的设备进入明确 `unassigned` 统计桶。

### 10.8 一致性

- 只有项目设备状态 Pipeline 成功后才提交 dirty projectID；
- ProjectSummary 使用单调版本；
- 同 shard Lua 原子修改 Summary 与 Aggregate；
- Snapshot View 带 `as_of/generation`；
- DB 对账以更高 SummaryVersion 修复 drift；
- 禁止无版本的 DB/Redis 双写；
- 持续校验设备和 Project 计数不变量。

### 10.9 租户与产品分类

单租户、全局分类、租户分类可复用“ScopeSummary + ScopeAggregate”模式。若一个项目包含多个分类，则摘要键扩展为 `(projectID, categoryID)`，不能仅依赖项目总摘要推导分类数量。

最终是否为这些范围保存设备级明细索引，仍由“是否需要按状态分页列出设备”决定；纯数量统计优先使用摘要聚合。

## 11. 容量与内存

项目 ZSET 天然按 projectID 分散，但单个超大项目仍可能成为热 key。应监控每项目：

- ZCARD；
- 每分钟 ZADD 数；
- ZCOUNT/ZCARD p99；
- Pipeline 批次大小与失败率；
- 项目状态重算频率和积压。

当前没有真实 `deviceKey`、`projectID` 长度和 Redis 编码实测数据，不在本文写死每百万设备内存值。压测必须使用：

```text
MEMORY USAGE projectStatusKey SAMPLES <count>
MEMORY STATS
INFO memory
```

并把 Replica、AOF rewrite、故障转移和碎片率纳入容量余量。

Go 批处理器应记录：

- buffer 当前长度和容量；
- 合并前/后更新数；
- flush 原因（size/timer）；
- flush 耗时和批次字节数；
- retry 数和最老未完成更新；
- heap、分配速率和 GC pause。

## 12. 失败模式

| 失败模式 | 后果 | 推荐处理 |
| --- | --- | --- |
| 同设备不同来源状态乱序 | 旧 score 覆盖新 score | stateVersion/CAS 或 flush 前读权威状态 |
| buffer 满后静默丢弃 | 项目统计永久漂移 | 有界背压、可靠重试、告警 |
| Pipeline 部分失败 | 同批部分项目未更新 | 逐项确认、失败子批重试 |
| 项目迁移漏 ZREM | 旧项目出现幽灵设备 | assignmentVersion、迁移重试、对账 |
| Redis failover 丢缓存写 | DB/meta 与项目 ZSET 不一致 | Redis 定位为可重建投影，支持重建 |
| 项目状态重算风暴 | CPU/Redis/DB 被重复计算压垮 | 按 projectID 合并并限速 |
| Alarm 恢复乱序/重复 | 故障状态被提前清除 | 按物模型标识维护有效事件集合 |

# ACK 压测环境部署设计规划
日期：2026-05-27

## 1. 目标
本规划用于在阿里云 ACK 上准备 IoT 云平台压力测试环境。目标是搭建一个接近生产拓扑、便于按组件扩容、可观测、可回收的测试环境，为 MQTT 长连接、设备上行、HTTP API、NATS/JetStream、TDengine 写入和故障演练提供稳定底座。

部署目标：

| 目标 | 说明 |
| --- | --- |
| 接近生产 | 使用 ACK 托管集群、ALB/NLB、ACR、RDS、Redis、SLS、Prometheus 等真实云资源 |
| 可压测 | 支持独立压测节点池，避免压测器抢占业务节点 |
| 可扩容 | 业务、EMQX、NATS、TDengine、压测器拆分节点池和资源配额；eKuiper 副本扩缩必须人工变更 |
| 可观测 | 压测开始前具备日志、指标、事件、告警和 dashboard |
| 可隔离 | 测试 namespace、数据库、topic、TDengine db、域名与生产隔离 |
| 可回收 | 所有资源有命名规范、标签和销毁步骤，避免压测后持续产生费用 |

### 3.3 RPC 服务发现决策
ACK 压测环境默认不自建业务 etcd，优先使用 go-zero 的 K8s resolver。

本地代码依据：

| 依据 | 结论 |
| --- | --- |
| `saas` / `iot` 当前依赖 `github.com/zeromicro/go-zero v1.8.5` | `zrpc.RpcClientConf` 已支持 `Target` 配置 |
| go-zero `zrpc` resolver 已注册 `k8s` scheme | RPC client 可使用 `k8s://namespace/service:port` |
| go-zero K8s resolver 通过 `rest.InClusterConfig()` 读取 Kubernetes API | client Pod 需要 ServiceAccount/RBAC 读取 `Endpoints` |
| 当前项目 RPC 配置大量使用 `Mode: grpc` + `zrpc.MustNewClient(c.XxxRpc.Conf)` | 可以只通过 ACK 测试环境 ConfigMap 切换，不需要改业务代码 |


默认选择 K8s resolver 的原因：

1. ACK 已经提供 Kubernetes Service/Endpoints 生命周期管理，重复自建 etcd 会增加一个 StatefulSet、PVC、备份、监控和故障源。
2. 压测环境需要减少非业务变量，RPC 服务发现直接绑定 K8s Endpoints 更容易解释扩缩容结果。
3. 阿里云没有面向 go-zero 服务发现的通用托管 etcd，ACK 内自建 etcd 的运维收益不高。
4. 后续生产环境如果没有跨集群注册中心、非 K8s 服务混合注册、多语言统一注册中心等要求，也建议沿用 K8s resolver。

etcd 只作为回退方案保留：

| 方案 | 使用场景 |
| --- | --- |
| K8s resolver | ACK 压测环境默认方案 |
| ACK 内自建 etcd | `k8s://` resolver 在 RBAC、Endpoints watch 或性能压测中出现不可接受问题时临时回退 |
| 外部托管注册中心 | 未来需要跨 ACK 集群、ECS、边缘节点统一服务发现时再单独设计 |


RPC client 配置示例：

```yaml
SysRpc:
  Enable: true
  Mode: grpc
  Conf:
    Timeout: 1000000
    Target: k8s://auxsol-test/system-rpc:8002
```

RPC server 配置示例：

```yaml
Name: system.rpc
ListenOn: 0.0.0.0:8002
# ACK 默认不配置 Etcd，避免服务启动时尝试注册自建 etcd。
```

必须补充的 RBAC：

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: auxsol-rpc-endpoints-reader
  namespace: auxsol-test
rules:
  - apiGroups: [""]
    resources: ["endpoints"]
    verbs: ["get", "list", "watch"]
```

每个需要调用 RPC 的 API/RPC Pod 绑定该 Role。若后续 go-zero 版本改为读取 `EndpointSlice`，再补充 `discovery.k8s.io/endpointslices` 权限。

### 3.4 MQTT Broker 版本路线
MQTT Broker 分短期落地和长期演进两条线：

| 阶段 | 方案 | 目标 |
| --- | --- | --- |
| 短期 | EMQX `5.8+` 开源版 | 快速支撑 ACK 压测和生产迁移，验证长连接、认证、ACL、共享订阅和 eKuiper 水平扩展能力 |
| 长期 | 简化自研 MQTT Broker | 面向逆变器设备场景做专用适配，减少通用 Broker 复杂度，强化设备协议、亲和分发、原始日志和云端链路控制 |


短期 EMQX 要求：

1. 使用 EMQX `5.8+` 开源版，镜像必须固定到已经验证过的具体 `5.8.x` tag，不使用浮动 tag。
2. 开源版只规划 core 节点，不规划 Enterprise replicant/worker 节点。
3. 节点数建议 3 个 core 节点；压测或短期生产扩容最多到 5 个 core 节点。
4. Dashboard/API 只允许管理网访问。
5. 必须启用 shared subscription，并配置 `hash_topic` 支撑 eKuiper 设备亲和。
6. 认证、ACL、限流、连接数、消息速率、丢弃消息、共享订阅分布必须进入压测 dashboard。
7. 压测报告要沉淀 EMQX 5.8+ 开源版在 3 节点和最多 5 节点下的连接容量、重连风暴、共享订阅分布和资源水位，作为自研 Broker 的对比基线。

长期自研 Broker 要求：

1. 对外保持 MQTT 接入契约稳定：1883/8883、设备认证、topic、QoS、遗嘱/心跳策略不能随意破坏。
2. 对内保持与 eKuiper/NATS/TDengine 链路的边界稳定，避免替换 Broker 时同步重构全链路。
3. 优先支持逆变器设备高频上报、弱网重连、设备亲和分发、原始消息落盘或转发、可观测指标。
4. 自研 Broker 上线前必须复用同一套压测场景，与 EMQX 5.8+ 开源版基线做连接数、吞吐、延迟、丢包、重连和资源成本对比。

## 5. 命名与隔离
| 项目 | 命名 |
| --- | --- |
| ACK 集群 | `ack-auxsol-perf` |
| 命名空间 | `auxsol-test`、`auxsol-loadgen`；可选 `auxsol-observability` |
| Helm release | `auxsol-test` |
| ACR namespace | `auxsol` |
| RDS database | `auxsol_perf` |
| TDengine database | `iot`，保持原业务库名 |
| NATS stream/subject | 保持原业务命名，不额外增加压测前缀 |
| MQTT topic | 保持原设备 topic 结构，不额外增加 `perf/` 前缀 |
| 域名 | `console-perf.example.com`、`api-perf.example.com`、`iot-api-perf.example.com`、`mqtt-perf.example.com` |
| 资源标签 | `Project=auxsol`、`Env=perf`、`Owner=platform`、`ExpireAt=YYYY-MM-DD` |


命名说明：

1. `ack-auxsol-perf` 采用 `ack-{project}-{env}` 规则：`ack` 表示阿里云 ACK 集群，`auxsol` 表示当前 IoT/CloudX 项目代号，`perf` 表示压测环境。这个名字不是技术强约束，如果公司统一项目代号是 `iot` 或 `aux-iot`，可以改成 `ack-iot-perf` 或 `ack-aux-iot-perf`。
2. 压测环境建议用 `perf` 而不是泛化的 `test` 标记集群，避免和普通联调、QA 测试环境混淆。
3. `auxsol-test` 是被测业务命名空间，承载 API/RPC、EMQX、eKuiper、NATS、TDengine 等被压测对象。若希望命名完全和压测环境一致，可改为 `auxsol-perf`，但必须同步修改 Helm release、RBAC、NetworkPolicy、RPC `k8s://<namespace>/<service>:<port>` 配置和所有压测脚本。

命名空间拆分：

| 命名空间 | 承载内容 | 拆分原因 |
| --- | --- | --- |
| `auxsol-test` | 被测业务和中间件 | 与生产、压测器、观测组件隔离；便于做 NetworkPolicy、ResourceQuota、Helm 发布和一键回滚 |
| `auxsol-loadgen` | HTTP/MQTT/NATS/TDengine 压测 Job、压测脚本、临时数据 | 防止压测器抢占被测业务配额；便于单独绑定 `np-loadgen` 节点池、清理临时 Pod，并避免压测器权限污染业务命名空间 |
| `auxsol-observability` | 可选；ServiceMonitor/PodMonitor、告警规则、Dashboard 配置、压测结果归档辅助组件、自定义 exporter | 使用 ACK 托管 Prometheus/ARMS 时不需要在这里自建 Prometheus/Grafana/Alertmanager；只有需要独立维护观测配置或自定义采集组件时才创建 |


`auxsol-test` 和 `auxsol-loadgen` 是压测环境的最小隔离粒度。`auxsol-observability` 是可选隔离层：如果完全使用 ACK 托管 Prometheus/ARMS、SLS 和控制台告警，并且 ServiceMonitor/PodMonitor 可以随业务 Helm release 放在 `auxsol-test`，则可以不创建；如果需要把观测规则、Dashboard 配置、自定义 exporter、黑盒探测或压测报告归档组件与业务发布解耦，则建议保留。

继续细分 namespace 会增加 RBAC、NetworkPolicy 和排障成本；全部放在一个 namespace 又容易造成资源配额、权限、清理和指标归属混乱。

压测环境默认保持 NATS stream/subject 和 MQTT topic 的原业务命名，原因是 eKuiper 规则、EMQX shared subscription `hash_topic`、设备亲和和下游消费都依赖真实 topic/subject 形态；额外加 `perf_` 或 `perf/` 会增加配置差异，压测结果更难代表生产。

隔离应优先通过独立 ACK 集群或 namespace、独立 EMQX、独立 NATS/JetStream、独立数据库、独立 Redis、独立 TDengine 部署、独立测试设备/产品数据和独立账号权限完成。TDengine 部署在 ACK 压测命名空间内时，database 保持原业务名 `iot`，不再通过 `_perf` 后缀区分环境。只有在临时共享 EMQX/NATS/TDengine 或不得不与其他环境混跑时，才允许增加临时前缀或临时库名；一旦修改命名，必须同步校验 eKuiper 规则订阅、shared subscription、设备模拟器、NATS consumer、TDengine sink 和告警规则。

压测环境必须和生产环境在账号权限、VPC、安全组、数据库、Redis、TDengine、EMQX/NATS 实例和设备数据上隔离。

## 6. ACK 集群设计
| 项目 | 推荐值 | 说明 |
| --- | --- | --- |
| 集群类型 | ACK 托管集群 Pro 版优先 | 压测环境也需要稳定控制面和可观测能力 |
| Kubernetes 版本 | 创建时选择 ACK 推荐稳定版本 | NLB Service 要求关注集群版本和 CCM 版本 |
| 网络插件 | Terway / VPC Native 优先 | 便于 Pod 网络、性能和云产品集成 |
| 可用区 | 至少 2 个 AZ | ALB/NLB 与节点池跨 AZ，高可用和容量更好 |
| API Server | 私网访问为主，公网限制白名单 | 降低暴露面 |
| 组件 | ALB Ingress Controller、CSI、CCM、metrics-server、ack-arms-prometheus、SLS | 压测前全部验证可用 |


阿里云官方说明 ACK 可通过控制台或 `kubectl` 部署和暴露容器应用，也可集成 ROS、Terraform、阿里云 CLI 等自动化方式；本项目建议用 Terraform/ROS 创建云资源，用 Helm 管理业务资源。

## 7. 节点池规划
初始规格用于第一轮压测，后续按指标调整。

| 节点池 | 初始规模 | 扩容范围 | 典型规格 | 承载 |
| --- | --- | --- | --- | --- |
| `np-system` | 3 | 3-5 | 4c8g | CoreDNS、Ingress Controller、ack-arms-prometheus、SLS 采集器等系统组件 |
| `np-app` | 3 | 3-20 | 8c16g 或 16c32g | go-zero API/RPC、普通无状态服务 |
| `np-emqx` | 3 | 3-5 | 高主频/高网络 8c16g+ | EMQX 5.8+ 开源版 core 节点 |
| `np-stream` | 3 | 3-12 | 16c32g | eKuiper 规则计算 |
| `np-stateful` | 3 | 3-9 | 16c64g + ESSD | NATS、TDengine |
| `np-loadgen` | 2 | 2-20 | 高网络 8c16g+ | k6、MQTT 压测器、自定义压测器 |


调度策略：

| 工作负载 | nodeSelector/taint 建议 |
| --- | --- |
| EMQX | 固定到 `np-emqx` 专用节点池，Pod 尽量分散到不同 AZ 和不同节点 |
| TDengine | 固定到 `np-stateful` 专用节点池，绑定 ESSD PVC，Pod/PVC 尽量分散到不同 AZ 和不同节点 |
| NATS/JetStream | 固定到 `np-stateful`，单 Pod 单 PVC |
| eKuiper | 固定到 `np-stream`，副本数按容量表人工调整 |
| 压测器 | 固定到 `np-loadgen`，禁止和被测服务混跑 |
| API/RPC | 固定到 `np-app`，按 CPU/延迟扩容 |


调度术语说明：

| 术语 | 含义 | 本项目用法 |
| --- | --- | --- |
| 固定到节点池 | 通过 `nodeSelector`、`nodeAffinity` 或 taint/toleration，把某类 Pod 调度到指定节点池 | EMQX 只跑在 `np-emqx`，TDengine/NATS 只跑在 `np-stateful`，避免和 API、压测器、eKuiper 抢资源 |
| AZ | Availability Zone，可用区；同一地域下相互独立的机房故障域 | ACK 节点池建议覆盖至少 2 个 AZ，最好 3 个 AZ |
| 反亲和 | 通过 `podAntiAffinity` 或 `topologySpreadConstraints`，让同一组件的多个 Pod 不要集中在同一台节点或同一个 AZ | EMQX 3 个 core 节点尽量分散；TDengine/NATS 副本也尽量分散，减少单节点或单 AZ 故障影响 |
| 绑定 ESSD | TDengine 的数据盘用 ESSD 云盘 PVC，云盘通常属于某个 AZ | TDengine Pod 必须调度到 PVC 所在 AZ；创建 StorageClass 时建议使用 `volumeBindingMode: WaitForFirstConsumer`，让 Pod 调度和云盘创建协同完成 |


压测环境可以把跨 AZ 分散设置为 `preferred`，资源不足时允许调度成功但记录风险；生产环境建议在节点数量和 AZ 数满足条件后使用更严格的分散策略。EMQX 5.8+ 开源版当前只规划 3-5 个 core 节点，3 个 AZ 时优先 `1/1/1` 分布；如果只有 2 个 AZ，只能接受 `2/1` 分布，并在压测报告里记录单 AZ 故障下的剩余容量。

节点伸缩注意：

1. ACK 节点伸缩不是简单看节点平均 CPU；它会关注 Pod 调度失败并模拟调度来决定扩容。
2. 除 eKuiper 外，可为常规无状态服务同时配置工作负载 HPA 和节点池自动扩容；eKuiper 不配置自动 HPA，指标告警只触发人工评审，扩容和缩容都必须由人工变更 `replicas`。
3. 压测前为关键节点池设置足够的 `min` 值，避免镜像拉取和节点初始化影响结果。
4. 压测阶段建议关闭过度激进的自动缩容；eKuiper 所在 `np-stream` 节点池也不应因低峰自动缩容导致 eKuiper Pod 被驱逐和缓存重建。

## 8. eKuiper 水平扩展与端口规划
eKuiper 是设备上行链路中的主要计算节点，需要按设备规模提前规划实例数、共享订阅和服务端口。

按当前需求，eKuiper 默认不是有状态部署。推荐形态是 `Deployment + 固定副本/人工扩缩容`，每个 Pod 是一份可替换的计算副本，全部使用相同规则、函数、source/sink 配置和 Secret。eKuiper 本地可能存在遥信状态缓存、active-set 缓存、批量写入队列等运行时数据，这些数据技术上属于可丢失、可重建的软状态，但设备亲和后缓存命中率会直接影响链路稳定性，因此不能像普通无状态服务一样自动扩缩容。

只有在以下场景才考虑 StatefulSet 或 Headless Service：

| 场景 | 默认处理方式 |
| --- | --- |
| 需要 Pod 固定身份或固定 DNS 管理每个实例 | 否，仅作为运维增强 |
| 需要 Pod 本地 PVC 保存不可丢失状态 | 否，当前设计不建议把不可丢状态放在 eKuiper 本地 |
| eKuiper Manager 必须逐个 Pod 直连 REST API | 否，可用 Pod DNS、port-forward 或可选 Headless Service 解决 |
| MQTT 上行消费和规则计算 | 是，使用 Deployment 副本即可 |


容量假设：

| 项目 | 规划值 |
| --- | --- |
| 单个 eKuiper 服务承载 | 10 万 - 20 万设备消息处理能力，具体以压测结果校准 |
| 扩容方式 | 随总设备量增加逐步增加 Deployment replicas；必须人工变更，不允许自动 HPA 扩容 |
| 缩容策略 | 默认不做常规缩容；确需降低副本数时必须人工执行专项方案，不允许自动缩容 |
| MQTT 订阅方式 | 多个 eKuiper 使用同一个 EMQX shared subscription group |
| 设备亲和 | EMQX shared subscription strategy 使用 `hash_topic` |
| 亲和前提 | 设备上报 topic 中必须稳定包含设备标识，例如 `/awx/push/{deviceName}` |
| 故障转移 | 某个 eKuiper Pod 断开后，EMQX 将其订阅到的设备 topic 重新分配给其他在线副本 |
| 恢复回流 | 故障 Pod 恢复并重新加入 shared group 后，EMQX 再按 `hash_topic` 重新分配消息 |


推荐实例数：

| 目标设备数 | eKuiper 实例数建议 | 说明 |
| --- | --- | --- |
| <= 10 万 | 1 | 冒烟、小规模压测 |
| 10 万 - 20 万 | 1-2 | 观察 CPU、heap、rule latency、TDengine writer queue |
| 20 万 - 50 万 | 3 | 建议按 1.3 不均衡系数预留容量 |
| 50 万 - 100 万 | 5-8 | 按 Deployment 副本水平扩展，滚动发布时控制不可用比例 |
| 100 万以上 | 按压测结果线性扩展 | 同时评估 EMQX、NATS、TDengine 写入瓶颈 |


共享订阅要求：

```latex
eKuiper replica 0: $share/cloudx-push/awx/push/+
eKuiper replica 1: $share/cloudx-push/awx/push/+
eKuiper replica 2: $share/cloudx-push/awx/push/+
```

EMQX 必须启用 topic 亲和策略：

```plain
mqtt {
  shared_subscription = true
  shared_subscription_strategy = hash_topic
}
```

`hash_topic` 会按发布 topic 做 hash。只要同一设备每次上报使用同一个 topic，同一设备的消息就会尽量进入同一个 eKuiper subscriber，从而让 eKuiper 本地缓存、遥信状态缓存和 TDengine batch 更稳定。

当设备连接和上行消息继续增长时，按容量表增加 eKuiper Deployment 副本数。新副本启动后加入同一个 shared group，EMQX 根据 `hash_topic` 把部分设备 topic 分配到新副本上，降低单个 eKuiper 的 CPU、heap、rule latency 和 sink queue 压力。

需要特别注意：扩容本身也会改变一部分 topic 到 subscriber 的映射，造成对应设备在新 eKuiper 上本地缓存 miss；缩容会让被删除副本上的设备集中迁移到其他副本，缓存击穿范围更大。因此 eKuiper 的生产策略是“人工扩缩容”：每次扩容都按小步长执行，扩容后冻结副本数，观察 cache miss、active-set 重发、rule latency 和 TDengine writer queue，确认稳定后再进入下一阶梯。缩容不作为常规动作；如果确实要缩容，必须人工发起专项方案，包含影响评估、低峰窗口、缓存预热、监控阈值和回滚预案。某个 eKuiper Pod 挂掉时，它负责的 topic 会被 EMQX 转移到其他在线副本；该 Pod 恢复后再次加入 shared group，EMQX 会重新计算分配，这属于故障恢复路径，必须通过压测验证但不能作为日常缩容手段。

端口规划：

| 端口 | 用途 | ACK 暴露方式 | 规划 |
| --- | --- | --- | --- |
| `9081` | eKuiper REST API | ClusterIP，管理网访问 | 每个 Pod containerPort 相同；默认一个内部 Service，必要时再提供按 Pod 直连方式 |
| `20498` | eKuiper internal service/CLI | ClusterIP | 每个 Pod containerPort 相同；不对公网开放 |
| `20499` | Prometheus metrics | ClusterIP + ServiceMonitor/PodMonitor | 必须纳入 ARMS/Prometheus 抓取 |
| `9082` | eKuiper Manager | 管理网/内网 Ingress | Manager 如需逐 Pod 管理，再补充 Pod DNS 或可选 Headless Service |


ACK 中 Pod 的 containerPort 可以重复，真正需要提前规划的是 Service 名称、管理入口、指标抓取和本地调试端口。建议：

| 对象 | 命名/端口策略 |
| --- | --- |
| eKuiper Deployment | `ekuiper`，只能通过人工修改 `replicas` 扩容或缩容，变更后冻结副本数并观察 |
| REST Service | `ekuiper-rest:9081`，只允许 Manager/运维网访问 |
| Metrics Service 或 PodMonitor | `ekuiper-metrics:20499` 或按 Pod 直接抓取，只允许 Prometheus/ARMS 访问 |
| 可选 Headless Service | 仅在需要固定 Pod DNS 或逐 Pod REST 管理时启用，不参与 MQTT 数据面 |
| 本地 Docker Compose | 多实例时使用 host port offset：`9081/20498/20499`、`9181/21498/21499`、`9281/22498/22499` |


发布与人工扩缩容规则：

1. 新增 eKuiper 实例前，先确认 EMQX shared subscription 已启用 `hash_topic`，不能使用默认轮询策略。
2. 每个实例必须部署同一套规则、函数、sink/source 配置和 Secret。
3. 扩容通过人工提高 Deployment replicas 完成，新 Pod Ready 后自动加入同一个 shared group。
4. 扩容、Pod 故障和滚动发布都会导致部分 topic 映射变化，短时间内可能出现本地缓存 miss，压测和生产发布都要观察 `cache miss`、active-set 重发、rule latency。
5. 禁止把 eKuiper 纳入任何自动扩缩容；如果必须减少副本，只能人工执行专项迁移方案，例如新建 shared group、低峰切流、缓存预热和回滚预案。
6. 副本变更不能只看 CPU，还要看 MQTT input rate、rule processing latency、TDengine writer `queueLen/dropped/flushError`、NATS publish latency。

从压测开始就要保存“总设备数 -> eKuiper 实例数 -> 单实例设备数 -> 资源水位 -> 延迟”的容量表，生产按容量表评审 eKuiper 副本变更。

## 9. 入口流量设计
### 9.1 前端与 HTTP API
当前有一套前端入口和两组 HTTP API：`saas-api-gateway` 负责 SaaS/系统/租户类接口，`iot-api-gateway` 负责 IoT/设备/产品/遥测类接口。压测环境需要把三者的入口边界写清楚，避免前端、SaaS API 和 IoT API 混在一个根路径下导致路由歧义。

前端已确认使用 React，按 SPA 静态资源部署。常规流程是 CI 构建前端产物，将 `dist/` 或 `build/` 目录交给 Nginx/Caddy/OSS/CDN 托管；运行时不需要 Node.js 常驻服务，除非后续改成 Next.js/SSR 这类服务端渲染架构。

前端部署有两种方式：

| 方式 | 适用场景 | 说明 |
| --- | --- | --- |
| ACK 内 `web-frontend` Deployment | 压测、联调、需要和后端一起 Helm 发布/回滚，或希望所有入口先统一走 ALB | React 构建产物打进 Nginx/Caddy 镜像，Service 暴露 `80`，ALB Ingress 指向该 Service |
| OSS + CDN 静态站点 | 生产环境优先选择；前端只是静态资源，不需要占用 ACK 节点资源 | React 构建产物上传 OSS，CDN 加速和缓存；前端不进入 ACK，API 仍通过 ALB 暴露 |


当前工作区没有前端源码目录，部署文档按“React 前端独立仓库或独立构建产物”处理。ACK 压测环境建议先使用 `web-frontend` 静态镜像，便于和后端环境一起验收；生产如果仍然是纯 React SPA，建议优先使用 OSS/CDN，ACK 内只保留后端 API、EMQX、eKuiper、NATS、TDengine 等服务。

React SPA 部署要求：

| 项目 | 要求 |
| --- | --- |
| 构建产物 | 使用前端仓库 CI 输出 `dist/` 或 `build/`，镜像 tag 与后端版本一起冻结 |
| 静态服务 | Nginx/Caddy 开启 history fallback，未知路径回退到 `index.html` |
| 运行副本 | ACK 压测环境 2 副本起步，资源 `100m-500m / 128Mi-512Mi` 即可 |
| 配置注入 | API base URL 通过构建变量或运行时 `config.js` 注入，避免在镜像里写死生产地址 |
| 缓存策略 | `index.html` 不强缓存，带 hash 的 JS/CSS/图片可以长缓存 |
| 健康检查 | 使用 `/` 或 `/index.html`，返回 200 即可 |


设计要求：

| 项目 | 要求 |
| --- | --- |
| IngressClass | `alb` |
| 监听 | HTTP 80 + HTTPS 443 |
| 证书 | 测试域名证书，Secret 或证书中心管理 |
| 前端域名 | `console-perf.example.com` -> `web-frontend:80`，或指向 OSS/CDN |
| SaaS API 域名 | `api-perf.example.com` -> `saas-api-gateway:8001` |
| IoT API 域名 | `iot-api-perf.example.com` -> `iot-api-gateway:8101` |
| 健康检查 | 配置 ALB healthcheck path，后端 Pod readiness 必须可靠 |
| 日志 | 开启 ALB 访问日志或接入 SLS |


推荐配置是域名分流：

| 域名 | 后端 | 说明 |
| --- | --- | --- |
| `console-perf.example.com` | `web-frontend:80` 或 OSS/CDN | 浏览器访问入口 |
| `api-perf.example.com` | `saas-api-gateway:8001` | SaaS/系统接口，现有路由主要是 `/api/v1/system/*` |
| `iot-api-perf.example.com` | `iot-api-gateway:8101` | IoT 接口，现有路由主要是 `/api/v1/things/*` 和 `/api/v1/protocolSync/*` |


域名分流的优点是边界清楚、ALB 规则简单、两个 API 网关后续路径不会互相影响。前端配置两个 API base URL：

```latex
SAAS_API_BASE_URL=https://api-perf.example.com
IOT_API_BASE_URL=https://iot-api-perf.example.com
```

如果前端使用 token/header 鉴权，域名分流最简单；如果使用浏览器 Cookie 鉴权，必须确认 Cookie Domain、SameSite、Secure 和 CORS 策略。API 网关只允许 `console-perf.example.com` 作为压测前端 Origin，不建议为了方便配置 `*`。

可选配置是同源路径分流：

| Host | Path | 后端 |
| --- | --- | --- |
| `console-perf.example.com` | `/api/v1/system/*` | `saas-api-gateway:8001` |
| `console-perf.example.com` | `/api/v1/things/*` | `iot-api-gateway:8101` |
| `console-perf.example.com` | `/api/v1/protocolSync/*` | `iot-api-gateway:8101` |
| `console-perf.example.com` | `/` | `web-frontend:80` |


同源路径分流可以减少浏览器 CORS/Cookie 问题，但要求 ALB 路由规则顺序明确：API path 必须优先于 `/`，否则前端静态服务会吞掉 API 请求。当前代码生成路由里 SaaS 侧集中在 `/api/v1/system/*`，IoT 侧集中在 `/api/v1/things/*` 和 `/api/v1/protocolSync/*`，可以做路径分流；如果未来两个网关出现同名一级路径，应回到域名分流。

### 9.2 MQTT
短期使用 NLB `Service type=LoadBalancer` 暴露 EMQX `5.8+` 开源版。长期替换为自研 MQTT Broker 时，外部 NLB 入口、端口和设备侧接入契约应保持稳定。

关键配置：

| 项目 | 要求 |
| --- | --- |
| `spec.loadBalancerClass` | `alibabacloud.com/nlb` |
| 协议 | TCP 1883，TCPSSL 8883 |
| 可用区 | 至少 2 个 vSwitch |
| `externalTrafficPolicy` | 按是否需要保留源 IP 选择；保留源 IP时优先 `Local` |
| 健康检查 | TCP 健康检查 EMQX 监听端口 |
| 安全组 | 只开放压测来源 IP 或业务来源段 |


NATS 不暴露 MQTT 1883。所有设备 MQTT 入口统一走 EMQX，NATS 仅作为内部事件总线。

## 10. 存储与数据服务
| 服务 | 存储策略 |
| --- | --- |
| RDS PostgreSQL | 独立压测实例或独立库；开启慢 SQL；压测前做快照 |
| Redis | 独立实例；关注连接数、慢命令、内存淘汰 |
| NATS/JetStream | 3 副本，每副本 50Gi 起，按 stream 保留策略扩容 |
| EMQX 5.8+ 开源版 | 3 个 core 节点，每节点 10-20Gi 起；最多扩到 5 个 core 节点；Dashboard/API 不公网暴露；作为自研 Broker 前的容量基线 |
| TDengine | 数据盘 200Gi 起，日志盘 50Gi 起；高吞吐阶段升级 ESSD PL1/PL2 |


压测前要清楚“数据保留时间”。如果长稳压测持续 24 小时，TDengine、NATS JetStream、SLS 的数据量会快速增长。

## 11. 配置与密钥
三环境配置结构参见 `environment-config-design-2026-05-27.md`，模板参见 `config-templates/`。本节只保留 ACK 部署侧的约束。

配置管理原则：

| 类型 | 存放 |
| --- | --- |
| 非敏感配置 | ConfigMap 或 Helm values |
| 密码/token/key | Secret，必要时接 KMS/密钥管理 |
| 镜像 tag | Helm values，必须使用不可变 git sha tag |
| 环境差异 | `values-test.yaml`，不改镜像内默认配置 |


生产形态的测试环境必须强制：

1. 所有 RPC client 使用 `Mode: grpc`。
2. 所有 RPC server `ListenOn` 使用 `0.0.0.0:PORT`。
3. 默认通过 `Target: k8s://auxsol-test/<service>:<port>` 做服务发现，不配置 `Etcd`。
4. `common.yaml` 和服务专属 YAML 都必须完整挂载。
5. DB、Redis、TDengine、NATS、EMQX、JWT、OSS、SMS 等凭据只从 Secret 注入。

配置风险：

1. 当前仓库部分 `common.yaml` 和服务 YAML 里存在全局 `Etcd` 字段；ACK 测试环境 ConfigMap 必须移除或覆盖为空，避免 `inherit` 让 RPC client/server 继续走 etcd。
2. K8s resolver 依赖 Pod 内 Kubernetes API 访问权限，API/RPC Pod 的 ServiceAccount 必须绑定 `endpoints` 的 `get/list/watch` 权限。
3. 如果临时回退 etcd，必须同步恢复 RPC server 的 `Etcd.Hosts/Key` 和 RPC client 的 `Etcd.Key`，并移除 `Target`，避免双配置造成误判。

## 13. 可观测设计
ACK 测试环境在压测前必须先完成可观测闭环。

如果启用 ACK 托管 Prometheus/ARMS，`auxsol-observability` 不承担 Prometheus 服务本体，只作为可选的观测配置命名空间。最小方案可以只创建 `auxsol-test` 和 `auxsol-loadgen`，把 ServiceMonitor/PodMonitor、告警规则和 Dashboard 配置随业务 Helm release 管理；增强方案再创建 `auxsol-observability`，专门放自定义 exporter、黑盒探测、跨命名空间告警规则和压测报告归档辅助组件。

| 维度 | 方案 |
| --- | --- |
| 集群指标 | ack-arms-prometheus / Prometheus |
| 应用指标 | Go pprof/Prometheus endpoint，必要时接 ARMS Golang 应用监控 |
| 日志 | SLS 收集容器 stdout/stderr、ALB/NLB 访问日志、压测器日志 |
| 事件 | Kubernetes Events、Pod restart、OOMKill、HPA、节点伸缩事件 |
| 链路 | 至少通过请求 ID、deviceName、topic、payload timestamp 做端到端抽样 |
| Dashboard | 集群、API/RPC、EMQX、eKuiper、NATS、TDengine、RDS、Redis、压测器 |


注意可观测会产生费用。ACK 文档说明 Prometheus、ARMS、SLS、报警等能力可能根据指标、自定义指标、日志量和报警量收费，压测环境要设置保留周期和预算提醒。

## 15. 部署步骤
1. 创建 VPC、vSwitch，至少两个可用区。
2. 创建 ACK 托管集群，安装 ALB Ingress、CSI、CCM、metrics-server、SLS、ack-arms-prometheus。
3. 创建节点池：system、app、emqx、stream、stateful、loadgen。
4. 创建 ACR namespace，推送业务镜像和压测镜像。
5. 创建 RDS PostgreSQL，启用 PostGIS，创建 `auxsol_perf`。

## 17. 回滚与清理
回滚：

1. 应用发布失败：`helm rollback auxsol-test <revision>`。
2. 配置错误：回滚 `values-test.yaml` 或 Secret 版本后重新 `helm upgrade`。
3. Stateful 组件异常：优先停止压测，保留 PVC 和日志，按组件 runbook 恢复。
4. 数据迁移失败：恢复 RDS 快照或清理测试库后重跑初始化。

清理：

1. 删除压测 Job、临时 Pod、临时 PVC。
2. 清理 NATS stream、TDengine 测试库、RDS 测试数据。
3. 缩容 `np-loadgen`、`np-app`、`np-emqx` 到最小值；`np-stream` 只能在确认 eKuiper 副本已按专项方案迁移或环境整体销毁时释放。
4. 关闭不需要的公网 EIP、NLB、ALB。
5. 根据 `ExpireAt` 标签检查残留云资源。

## 19. 第一轮建议规格
如果业务方尚未给出目标规模，第一轮建议按“中等压测环境”启动，先验证链路：

| 组件 | 初始规格 |
| --- | --- |
| API/RPC | 每服务 2 副本，`500m-2c / 512Mi-2Gi` 起 |
| EMQX 5.8+ 开源版 | 3 个 core 节点，固定 `np-emqx`，每 Pod 4c8g 起；最多扩到 5 个 core 节点 |
| eKuiper | 先 1-3 个副本，固定 `np-stream`，每 Pod 4c8g 起；按 10 万、20 万、50 万设备阶梯校准 |
| NATS | 3 副本，固定 `np-stateful`，每 Pod 2c4g + 50Gi PVC 起 |
| TDengine | 3 副本或按当前部署模式，固定 `np-stateful`，200Gi PVC 起 |
| 压测器 | 2-5 副本，固定 `np-loadgen` |
| RDS | 先按测试实例规格启动，慢 SQL 打开 |
| Redis | 标准版/集群版按目标连接数选择，慢命令打开 |


第一轮目标是跑通 `100 -> 1k -> 10k` 连接和 `1k msg/s` 级别上行，拿到瓶颈后再扩到 50k+。

# TDengine 部署硬件资源预估

日期：2026-06-26

## 1. 目标与范围

为 TDengine 时序库的生产/压测部署给出**两档**硬件资源预估，覆盖未来设备规模增长：

| 档次 | 设备数 | 子表数 | 写入速率 | 定位 |
| --- | --- | --- | --- | --- |
| 档 A（当前/近期） | 20 万 | 60 万 | 3000 行/秒 | 现阶段容量基线 |
| 档 B（增长目标） | 50 万 | 150 万 | 7500 行/秒 | 规模扩张后的目标容量 |

> 子表 : 设备 ≈ 3 : 1（每个设备约对应 3 张子表 / 测点组）。两档写入速率与子表数同比例增长，单子表平均约每 200 秒上报一次（低频上报）。

本文给出：负载换算、架构决策、容量公式、两档硬件推荐、TDengine 关键参数、ACK/ECS 落地建议、扩容水位。结论部分是可直接采购/申请资源的规格表。

## 2. 公共假设

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| TDengine 版本 | **开源版（社区版）** | 仅支持 `replica 1 / 3`；高可用固定用 `replica 3`。双副本（`replica 2` + 仲裁）是企业版特性，不在本方案范围 |
| 列数 | 200 列/行 | 宽表 |
| 单行裸数据 | ~1 KB | 混合类型估算（平均 ~5 B/列 + 时间戳 + 行开销）。若多为 8 字节 double，按 ~1.6 KB 重算（存储 ×1.6） |
| 压缩比 | 5× | 保守值（`comp=2`，IoT 实际常 5~10×，多留安全余量） |
| 副本数 | `replica 3` | 开源版下唯一的高可用选项 |
| 节点数 | 3 或 5 | 3 dnode 起步 + 3 mnode；节点数选型见 §11 |

> **重要前提**：`replica=3` 时全集群恒定存 **3 份**数据。**3 节点时每节点都存整份数据集**（无法横向分摊）；增加节点可把单节点存储降到 `3/N`，详见 §11。

## 3. 负载换算

| 维度 | 档 A（60 万） | 档 B（150 万） |
| --- | --- | --- |
| 写入行/秒 | 3000 | 7500 |
| 数据点/秒（行×列） | 60 万 | 150 万 |
| 写入行/天 | 2.59 亿 | 6.48 亿 |
| 裸数据/天 | ~259 GB | ~648 GB |
| 压缩后/天/副本 | **~52 GB** | **~130 GB** |

**计算结论**：60 万 / 150 万点/秒对 TDengine 都属轻~中负载，单节点都能扛住写入。3 节点集群的瓶颈不在写入 CPU，而在 **① 存储增长** 和 **② 海量子表带来的内存（元数据 + 最新值缓存）**。

## 4. 查询特征与架构决策

实际查询模式：

- **主要是看最新值**（每账号查自己几百台设备的最新数据），并发 ≤ 100。
- **历史区间聚合为天级粒度**，相关数据保留**半年（180 天）**。

由此得出架构决策——**原始数据短保留 + 流计算天级汇总表长保留**：

```
                    ┌─ iot_raw   (KEEP 30d, cachemodel=both)
写入 ──────────────►│   ├─ 看最新值 → 内存 last-value 缓存命中（瞬时、不扫盘）
                    │   └─ 近 30 天明细下钻（偶尔）
                    │
                    └─ CREATE STREAM → iot_daily (INTERVAL 1d, KEEP 180d)
                        └─ 历史天级聚合 → 查这张小表（快）
```

- **看最新值**走内存缓存，100 路并发也只是内存查表，几乎不耗 CPU、不扫盘。
- **历史天级聚合**查 `iot_daily`：每子表每天仅 1 行，半年总量极小（见 §5）。
- **原始明细**只保留 30 天供偶尔下钻。

这套架构把“原始数据存满 180 天”的存储压力（档 B 约 23 TB/节点）降到 **~4 TB/节点**，3 节点纯 NVMe 即可，无需分级存储或扩节点。若业务需要半年内随时下钻**秒级原始数据**，则改用 §10 的备选方案。

## 6. 两档硬件配置推荐（核心交付）

每节点 3 台同构机器，replica 3。

| 资源 | 档 A（60 万 / 20 万设备） | 档 B（150 万 / 50 万设备） |
| --- | --- | --- |
| CPU | 8 核（最低）/ **16 核（推荐）** | **16 核（推荐）** / 24 核（余量） |
| 内存 | 32 GB（最低）/ **64 GB（推荐）** | **64 GB（推荐）** / 128 GB（余量） |
| 磁盘 | **3~4 TB NVMe SSD** | **6~8 TB NVMe SSD** |
| 网络 | 1 GbE 够用（10 GbE 可选） | **10 GbE 推荐**（1 GbE 临界） |
| 节点数 | 3 | 3 |

**内存拆解（推荐档）：**

| 用途 | 档 A（64 GB） | 档 B（64 GB） |
| --- | --- | --- |
| vnode 写缓存（`buffer`） | 12 × 256 MB ≈ 3 GB | 18 × 256 MB ≈ 4.6 GB |
| 最新值缓存（`cachesize`） | 12 × 128 MB ≈ 1.5 GB | 18 × 256 MB ≈ 4.6 GB |
| 子表元数据 + tag 索引 | ~1 GB | ~2~3 GB |
| 流计算状态 + 查询工作内存 | 几 GB | 几 GB |
| 余量 → OS pagecache（加速读盘） | 其余 | 其余 |

**CPU 说明**：写入轻、查询走缓存/小表，CPU 主要消耗在副本同步、压缩、流计算。档 A 8 核可跑、16 核舒适；档 B 16 核推荐、有大范围聚合余量需求时上 24 核。

**网络说明**：档 B 裸写 ~7.5 MB/s + 副本同步 ≈ 20 MB/s，叠加查询流量，10 GbE 留足余量；档 A ~10 MB/s，千兆够用。

## 7. TDengine 集群与关键参数

### 7.1 集群拓扑
- 3 个 dnode；3 个 mnode（replica 3，做元数据高可用）。
- `supportVnodes` 设为 ≥ 单节点 vnode 数并留余量（档 A ≥ 16，档 B ≥ 24）。

### 7.2 建库 DDL

```sql
-- 原始库：短保留 + 缓存全部子表最新值
CREATE DATABASE iot_raw
  REPLICA 3
  VGROUPS 12          -- 档A=12（60万/12≈5万表/vnode）；档B=18（150万/18≈8.3万表/vnode）
  BUFFER  256         -- 每 vnode 写缓存(MB)，写入抖动大可调 512
  DURATION 10d        -- 单数据文件时间跨度
  KEEP    30d         -- 原始明细保留窗口
  CACHEMODEL 'both'   -- 缓存最新值，服务"看最新值"查询
  CACHESIZE 128       -- ★档A=128，档B=256(MB/vnode)：确保全部子表最新值常驻内存
  COMP    2;

-- 天级汇总库：长保留，体量极小
CREATE DATABASE iot_daily REPLICA 3 KEEP 180d;
```

> **`CACHESIZE` 是本场景最关键的调优**：需 ≥ 单 vnode 子表数 × 单行大小。档 B 单 vnode ~8.3 万表 × 1 KB ≈ 83 MB，设 256 MB 保证“看最新值”100% 缓存命中。

### 7.3 vgroups 取值依据

| | 档 A | 档 B |
| --- | --- | --- |
| vgroups | 12 | 18 |
| 单 vnode 子表数 | ~5 万 | ~8.3 万 |
| 集群 vnode 数（×replica3） | 36 | 54 |
| 单节点 vnode 数（/3） | 12 | 18 |

vgroups 既让海量子表均匀分布，又让一个账号几百台设备的查询能跨 vnode 并行。（估算逻辑与规模增长调整见 §12）

### 7.4 流计算（天级汇总）

```sql
CREATE STREAM s_daily INTO iot_daily.st_daily AS
  SELECT _wstart, avg(c1), max(c2), min(c3) /* ...你关心的指标... */
  FROM iot_raw.st PARTITION BY tbname INTERVAL(1d);
```

### 7.5 数据建模（强制）
- 用**超级表 + tag**（`account_id`、`device_id` 等）建模。
- 查询用 `WHERE account_id=?` 走 tag 索引，从 60 万 / 150 万子表中秒级定位目标几百张。
- 看最新值用 `SELECT last_row(*) ... WHERE account_id=? `，命中内存缓存。
- **不允许全表扫描式查询**，否则海量子表下延迟不可控。

## 8. ACK / ECS 落地建议

部署目标为阿里云 ACK，节点对应 ECS 实例：

| | 档 A | 档 B |
| --- | --- | --- |
| 实例规格参考 | 通用型 16 vCPU / 64 GB（如 ecs.g 系列 16C64G）| 通用型 16~24 vCPU / 64~128 GB |
| 数据盘 | ESSD PL1 ~4 TB | ESSD PL2/PL3 ~8 TB（更高吞吐） |

**本地 NVMe vs 云盘**：TDengine `replica=3` 自身已提供冗余，可考虑**本地盘 ECS（i 系列）** 获取更高 IOPS/更低成本，单节点故障由副本兜底。若用云盘则依赖云盘自身可靠性 + replica 双重保障。时序写入以高吞吐顺序写为主，ESSD 即可满足，无需追求超高 IOPS 规格。

**K8s 部署要点**：
- 用 StatefulSet + 独立 PVC（每节点独立持久卷），`podAntiAffinity` 保证 3 个 dnode 分散到不同 ECS/可用区。
- 数据目录、WAL 目录挂载到高性能数据盘，不要用系统盘。
- 资源 `requests/limits` 按上表设置，内存 limit 不要压到推荐值以下（避免 pagecache 被挤导致读放大）。

## 9. 扩容与水位预警

| 指标 | 阈值 | 动作 |
| --- | --- | --- |
| 磁盘使用率 | > 70% | 扩容数据盘 / 缩短 `KEEP` / 评估扩节点 |
| 内存使用率 | 持续 > 80% | 加内存 / 下调 `CACHESIZE`、`buffer` |
| 写入延迟 | 明显上升 | 检查磁盘 IO、增大 `buffer`、评估 vgroups |
| 单节点 vnode 数 | 接近 `supportVnodes` | 调大 `supportVnodes` 或扩节点 |
| 子表/设备数增长 | 超过档 B（150 万） | 重新评估，按 §10 或横向扩到 ≥6 节点 |

**横向扩展提示**：`replica 3` 下全集群恒定 3 份数据，增加节点可把单节点存储降到 `3/N`（如 5 节点 → 每节点 60%）。3 节点时所有节点都是全量副本，扩存储须增加节点。3 / 5 节点选型见 §11。

## 10. 备选方案：原始数据存满 180 天

若业务要求半年内随时下钻**秒级原始数据**（不接受只保留 30 天原始），则原始库 `KEEP 180d`，存储大幅上升：

| | 档 A | 档 B |
| --- | --- | --- |
| 单节点净数据量 | ~9.4 TB | ~23.4 TB |
| 建议磁盘配置 | 12~16 TB | **30 TB**（纯 SSD 不经济） |

此时**必须启用多级存储**（热数据 NVMe + 冷数据 HDD）：

```
# dnode 配置（taos.cfg），按访问热度分层
dataDir /mnt/nvme  0 1     # level 0 热（近 7~30 天）
dataDir /mnt/hdd1  1 1     # level 1 温
dataDir /mnt/hdd2  2 1     # level 2 冷
```

冷数据查询少，正好匹配“历史只到天级”的访问模式，成本可显著下降。

## 11. 节点数与副本选型（开源版）

### 11.1 副本约束
开源版（社区版）只支持 `replica 1` 和 `replica 3`：
- `replica 1`：无冗余，任一节点故障即丢该分片，**不能用于生产高可用**。
- `replica 3`：唯一的高可用选项，可容忍 1 个节点故障。
- `replica 2`（双副本 + 仲裁）是**企业版**特性，本方案不涉及。

所以生产 HA 固定 `replica 3`，可调的只有**节点数**。

### 11.2 节点数如何影响单节点存储
`replica 3` 时全集群恒定存 **3 份**数据，摊到 N 个节点上，**每节点约存 `3/N`**：

| 节点数 | 每节点存储占比 | 说明 |
| --- | --- | --- |
| 3 | 100%（全量） | 每个 vgroup 落在所有 3 节点，互为完整副本 |
| 5 | 60%（3/5） | 每个 vgroup 在 5 节点中选 3，数据分散 |

> **全集群总磁盘量与节点数无关**（恒为 3×数据集）。5 节点不是“省磁盘”，而是把同样的总量摊成更多、更小、更好采购的盘，并分散写入/查询/内存压力。

### 11.3 3 节点 vs 5 节点（每节点数据量）

| 方案 | 3 节点（每节点） | 5 节点（每节点） | 5 节点是否更优 |
| --- | --- | --- | --- |
| 档 B 流计算（30 天原始） | ~4 TB | ~2.4 TB | ❌ 3 节点已很轻松，5 节点过度配置 |
| 档 B 原始存满 180 天 | ~23.4 TB（单盘不现实） | ~14 TB（配 18 TB，合理） | ✅ 明显更优、基本必选 |
| 档 A 原始存满 180 天 | ~9.4 TB | ~5.6 TB | 视情况 |

### 11.4 5 节点的收益与代价
**收益**
1. 单节点存储、CPU、内存、最新值缓存均降到 ~60%；开源版不能用 `replica 2`，**5 节点是在保持 `replica 3` 的同时降低单节点存储的唯一途径**。
2. 可用性统计更好：3 节点挂 2 台 → 全集群写不可用；5 节点挂 2 台 → 仅少数 vgroup 受影响，其余照常。
3. 故障重建压力分散，留有突破 50 万设备的增长余量。

**代价**
- 5 台机器（但每台更小，**总磁盘成本基本不变**，总 CPU/内存仅增少量基线开销）。
- 运维节点更多（边际）。

### 11.5 选型建议
| 场景 | 推荐 |
| --- | --- |
| 流计算方案（推荐路径，档 B ~4 TB/节点） | **3 节点**，最省最简 |
| 原始存满 180 天（档 B ~23 TB/节点） | **5 节点**，把 30 TB 单盘拆成 ~18 TB/节点 |
| 预期很快突破 50 万设备 / 要更强可用性余量 | **5 节点**前瞻 |

无论 3 还是 5 节点，**mnode 固定 3 个**（与 dnode 数无关，做元数据 HA）。

### 11.6 5 节点配置参考（replica 3，开源版）

| 资源 | 档 A（60 万） | 档 B（150 万） |
| --- | --- | --- |
| 节点数 | 5 | 5 |
| CPU | 8~16 核/节点 | 16 核/节点 |
| 内存 | 32~48 GB/节点 | 48~64 GB/节点（每节点仅承担 60% 子表） |
| 磁盘（流计算） | ~2 TB/节点 | ~4 TB/节点 |
| 磁盘（原始 180 天） | ~8 TB/节点 | **~18 TB/节点** |
| vgroups | 15 | 20 |
| CACHESIZE | 128 MB | 256 MB |

> 5 节点时 `vgroups` 取能被均匀分摊的值（档 B=20 → 60 vnode / 5 节点 = 12/节点）；`supportVnodes` 相应留余量。

## 12. 容量规划与 vgroups 扩展

### 12.1 官方内存公式
> 公式与参数定义出自 TDengine 官方文档：[《容量规划》](https://docs.taosdata.com/operation/planning/)（“服务器内存需求”一节）。

单个数据库的 vnode 写路径 + 缓存内存（全集群）：

```
内存(单库, 全集群) = vgroups × replica × (buffer + pages × pagesize + cachesize)
```

| 项 | 含义 | 默认 | 本方案取值 |
| --- | --- | --- | --- |
| `buffer` | 写缓存 / memtable | 256 MB/vnode | 256 MB |
| `pages × pagesize` | 元数据缓存（schema/tag） | 256 × 4 KB = 1 MB/vnode | 表多时 `pages` 调 512~1024 |
| `cachesize` | 最新值缓存 | 1 MB/vnode | 跟 tables/vnode 走（128~256 MB） |

- **单节点 ≈ 公式结果 ÷ 节点数**。
- 公式**只算写路径 + 缓存**，不含表元数据/tag 索引、查询工作内存、OS pagecache——单节点实际内存要在公式值之上再留这些。

代入档 B（3 节点）：`18 × 3 × (256+1+256) = 27 GB`（全集群）→ **9 GB/节点**，叠加其余开销，64 GB 从容。

### 12.2 vgroups 估算逻辑
关键恒等式：**`tables/vnode = 子表数 ÷ vgroups`**（不除 replica——每个副本 vnode 都存该 vgroup 的全部表）。三个约束交汇定 vgroups：

| 约束 | 目标 | 作用 |
| --- | --- | --- |
| ① tables/vnode | 50K~100K | 太多 → 元数据膨胀、vnode 恢复慢；太少 → vgroups 多、内存浪费 |
| ② vnode/节点 = `vgroups×replica÷节点数` | ≈ CPU 核数（写轻可超，≤ ~24） | 写入/查询并行度 |
| ③ 内存（§12.1 公式） | 落在预算内 | vgroups↑ → 内存线性↑ |

本方案取值：档 A `60万/12 = 5万`表/vnode → vgroups=12；档 B `150万/18 ≈ 8.3万`表/vnode → vgroups=18。

> `cachesize` 必须 ≥ `tables/vnode × 单行大小`，"看最新值"才能全缓存命中。**tables/vnode 恒定 ⇒ cachesize 恒定**，这是下面线性扩展的前提。

### 12.3 扩展法则
**保持 `tables/vnode` 恒定（锚定 ~75K）→ vgroups 随子表线性增长；再加节点把 vnode/节点压回 ~18。**

1. `vgroups ≈ 子表数 ÷ 75,000`（取能被节点整除的数）。
2. `节点数 ≈ 全集群 vnode 数(=vgroups×3) ÷ 18`。
3. `cachesize` 不变（128~256 MB）；`pages` 表多时升到 512~1024；`supportVnodes` ≥ vnode/节点并留余量。

### 12.4 扩展规模表（流计算方案，replica 3）
设备 : 子表 = 1 : 3，写入随设备线性增长。

| 设备 | 子表 | 写/s | vgroups | 集群 vnode | 推荐节点 | vnode/节点 | 公式内存/节点* | 单节点配置 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 20 万 | 60 万 | 3000 | 12 | 36 | 3 | 12 | ~5 GB | 16 核 / 64 GB |
| 50 万 | 150 万 | 7500 | 18 | 54 | 3 | 18 | ~9 GB | 16 核 / 64 GB |
| 75 万 | 225 万 | 11250 | 30 | 90 | 5 | 18 | ~9 GB | 16 核 / 64 GB |
| 100 万 | 300 万 | 15000 | 40 | 120 | 6 | 20 | ~10 GB | 16 核 / 64 GB |

\* 公式内存 = (vnode/节点) × (256+1+cachesize) MB，仅写路径+缓存；叠加元数据/查询/pagecache 后 64 GB 一路够用。

存储侧（流计算 raw 30 天）始终不是瓶颈：100 万设备单副本 ~7.8 TB，replica 3 / 6 节点 ≈ 3.9 TB/节点，NVMe 轻松。

> 规律：**每增长 ~25~30 万设备，加约 1 个节点 + vgroups 提一档**；CPU / 单节点内存基本不动（写轻、查缓存），节点数主要为分摊 vnode 数与元数据内存。

### 12.5 在线扩容步骤
`vgroups` 在 `CREATE DATABASE` 时定死，**不能像 replica 那样直接 `ALTER` 整体重分片**。扩容动作：

```sql
-- 1. 新节点加入集群（在已有节点执行）
CREATE DNODE "new_host:6030";

-- 2. 拆分 vgroup 增加数量（按需对多个 vgroup 执行）
SPLIT VGROUP <vgroup_id>;

-- 3. 把 vnode 重分布到各节点，做负载/存储均衡
REDISTRIBUTE VGROUP <vgroup_id> DNODE <dnode1> DNODE <dnode2> DNODE <dnode3>;
```

（命令以你部署的版本为准）`SPLIT VGROUP` 是重操作。**建议建库时按近 1~2 倍目标规模预留少量 vgroups headroom**（如直接奔 50 万设备规划可 vgroups=20 起），减少后续 split 次数；但别过度预留——每多 1 个 vgroup 都按 §12.1 公式吃 `replica × (buffer+…)` 内存。

### 12.6 客户端（taosc）内存
除服务端外，写入/查询进程（taosc 客户端，本项目即数据网关与 API 网关）也消耗内存，主要来自子表元数据缓存、并发 SQL 缓冲与固有开销。官方公式（单位 MB，出处同 §12.1）：

```
M = T × S × 3 + N / 4096 + 100
```

| 项 | 含义 | 取值 |
| --- | --- | --- |
| `T` | 最大并发写入线程数 | 按写入服务配置；本项目写入轻，取 ~50 |
| `S` | 最大 SQL 语句长度（MB） | 默认 1 |
| `N` | 该客户端访问的子表数 | 取全部子表（单写入进程覆盖所有设备的最坏情况） |
| `100` | 固有结构开销（MB） | 常量 |

各规模估算（T=50，S=1，N=全部子表）：

| 设备 | 子表 N | `T×S×3` | `N/4096` | M | 单进程预留 |
| --- | --- | --- | --- | --- | --- |
| 20 万 | 60 万 | 150 | ~146 | ~396 MB | ~1 GB |
| 50 万 | 150 万 | 150 | ~366 | ~616 MB | ~1 GB |
| 75 万 | 225 万 | 150 | ~549 | ~799 MB | ~1.5 GB |
| 100 万 | 300 万 | 150 | ~732 | ~982 MB | ~1.5~2 GB |

- 主导项是 `N / 4096`（子表元数据缓存），随子表数线性增长；`T × S × 3` 由写入并发决定。
- 这是**每个 taosc 客户端进程**的量：数据网关（写入）与 API 网关（查询）各自独立预留。
- 若把写入分片到多个网关实例，各实例 `N` 取其实际覆盖的子表数，单实例内存随之下降。

## 13. 结论

- **开源版高可用 = `replica 3`**（无 `replica 2` 选项），可调的只有节点数。
- **推荐方案（流计算架构 + 3 节点）**：纯 NVMe，`replica 3`。
  - **档 A（60 万 / 20 万设备）**：每节点 **16 核 / 64 GB / 3~4 TB NVMe**，vgroups=12，CACHESIZE=128。
  - **档 B（150 万 / 50 万设备）**：每节点 **16 核 / 64 GB / 6~8 TB NVMe**（10 GbE），vgroups=18，CACHESIZE=256。
- 工作负载特征（写入轻、看最新值走缓存、历史只到天级）使两档在 3 节点上都很从容，无需分级存储或扩节点。
- **若走原始存满 180 天方案**：选 **5 节点**把单节点存储从 ~30 TB 降到 ~18 TB（总磁盘成本不变），详见 §10 / §11。
- **规模增长**：锚定 `tables/vnode ≈ 75K`，每 ~25~30 万设备加 1 节点并提一档 vgroups（75 万 → 5 节点 / vgroups 30，100 万 → 6 节点 / vgroups 40），CPU 与单节点内存基本不动，详见 §12。
- 唯一变量：**30 天原始明细窗口是否够下钻**。若需半年原始秒级数据，走上面的 5 节点 + §10 多级存储。

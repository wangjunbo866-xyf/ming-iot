# Docker Compose 到 K8S/ACK 迁移指导
日期：2026-05-28

## 1. 目标
本文面向已经熟悉 Docker Compose、但没有 Kubernetes 使用经验的开发者。目标不是一次学完整个 K8S 体系，而是把当前 IoT 云平台从本地 Compose 开发环境，逐步迁移到本地 K8S 冒烟，再部署到阿里云 ACK 压测环境。

最终目标：

1. 本地仍保留 Docker Compose 作为最快开发入口。
2. 使用本地 K8S 环境验证 Helm 模板、ConfigMap/Secret 挂载、Service/RBAC、Pod 启动。
3. 使用 Helm 管理 ACK 压测和生产部署，不手工维护 `helm template` 生成的大 YAML。
4. ACK 压测环境使用 `grpc + k8s://` 做 go-zero RPC 服务发现，不自建业务 etcd。
5. 配置和 Secret 分层遵循 `environment-config-design-2026-05-27.md`。

相关文档：

| 文档 | 用途 |
| --- | --- |
| `doc/deploy/environment-config-design-2026-05-27.md` | 三环境配置结构、ConfigMap/Secret 规则 |
| `doc/deploy/ack-deployment-design-plan-2026-05-27.md` | ACK 压测环境整体架构 |
| `doc/perf/performance-test-design-plan-2026-05-27.md` | 压测场景、指标、验收口径 |


## 2. 总体建议
建议采用下面路线：

```latex
Docker Compose 开发
  -> Helm template 静态检查
  -> kind 本地 K8S 冒烟
  -> ACK 压测环境 Helm 发布
  -> ACK 压测验证
  -> ACK 生产发布
```

本地 K8S 推荐使用 `kind`，因为它依赖 Docker，启动快，适合验证 Helm 和基础 K8S 对象。它不是生产模拟器，不能替代 ACK。

本地 K8S 能验证：

| 能验证 | 说明 |
| --- | --- |
| Helm 模板是否能渲染 | `helm lint`、`helm template` |
| Deployment 是否能创建 Pod | 镜像、启动命令、环境变量、探针 |
| ConfigMap/Secret 是否挂载正确 | `/app/etc/common.yaml` 和服务 YAML 是否成对出现 |
| Service DNS 是否可用 | `system-rpc.auxsol-test.svc.cluster.local` 这类解析 |
| go-zero `k8s://` 基础发现 | 需要 ServiceAccount/RBAC 能读 Endpoints |
| 端口转发和冒烟接口 | `kubectl port-forward` 后本地 curl |


本地 K8S 不能充分验证：

| 不能充分验证 | 原因 |
| --- | --- |
| ACK NLB/ALB 行为 | 云负载均衡、VPC、安全组和控制器行为不同 |
| RDS/Redis/OSS 真实延迟 | 本地环境没有云服务网络和限流 |
| EMQX 大规模长连接 | 本地机器资源和网络模型不代表 ACK |
| 节点池扩缩容 | kind 没有 ACK 节点池、Terway、云盘 CSI |
| 生产级可观测 | SLS、ARMS Prometheus、ACK 事件链路需要在云上验证 |


结论：本地 K8S 用来做部署冒烟；ACK 用来做真实压测。

## 3. Docker Compose 与 K8S 的对应关系
先把熟悉的 Compose 概念映射到 K8S：

| Docker Compose | Kubernetes | 迁移理解 |
| --- | --- | --- |
| `services.<name>` | `Deployment` | 描述一个服务的 Pod 副本、镜像、启动参数 |
| `image` | `containers[].image` | ACK 必须能从 ACR 或镜像仓库拉取 |
| `ports` | `Service`、`Ingress`、`LoadBalancer` | Service 管集群内访问，Ingress/LB 管外部访问 |
| `environment` | `env`、`envFrom` | 普通环境变量可以进 ConfigMap，敏感值进 Secret |
| `env_file` | `Secret` 或 `ConfigMap` | 不要把真实 Secret 放 Git |
| `volumes` 挂配置 | `ConfigMap volume`、`Secret volume` | 当前项目重点是挂载 `/app/etc` |
| `volumes` 持久化数据 | `PersistentVolumeClaim` | NATS、TDengine、EMQX 等有状态组件会用到 |
| `depends_on` | readinessProbe、应用重试 | K8S 不保证启动顺序，服务必须能等待依赖恢复 |
| `healthcheck` | `readinessProbe`、`livenessProbe` | readiness 控制是否接流量，liveness 控制是否重启 |
| `restart: always` | Pod 重启策略 | Deployment 默认会维持期望副本 |


### 3.1 探针详解（startup / readiness / liveness）
K8S 用三类探针替代 Compose 的 `healthcheck`，每一类行为不同，不要混用：

| 探针 | 作用 | 失败后果 | 当前项目建议 |
| --- | --- | --- | --- |
| `startupProbe` | 保护启动慢的服务，在启动期内屏蔽 `livenessProbe` | K8S 认为启动失败，按重启策略处理 | 所有服务统一加，避免启动阶段被 `livenessProbe` 误杀 |
| `readinessProbe` | 判断容器**是否准备好接收流量** | Pod 被移出 Service Endpoints，不再分配新请求；容器**不会被重启** | 第一阶段用 `tcpSocket`，第二阶段 API 切 `httpGet /readyz`，RPC 切 `grpc` |
| `livenessProbe` | 判断容器**是否还存活** | K8S 杀死并重建该容器 | 只检查进程/端口是否还在响应，**不检查数据库、Redis、NATS、下游 RPC** |


关键行为差异：

1. **readiness 失败 ≠ 重启**。Pod 只是从 Service 后端摘除，现有连接不会立刻断开。等恢复后会自动重新加入 Endpoints。这对滚动发布很重要：新版本 Pod 必须 readiness 通过才会开始接收流量，老版本才会被缩容。
2. **liveness 失败 = 重启**。如果 liveness 配得太激进，压测时 CPU 抖动可能导致正常 Pod 被反复重启，引发雪崩。因此 `failureThreshold` 要留足余量。
3. **startupProbe 存在时，liveness 和 readiness 在启动期不执行**。只有 startup 通过后，liveness/readiness 才开始工作。这解决了 go-zero 服务初始化 DB 连接、加载配置较慢时的误杀问题。

第一阶段（Helm 骨架）所有服务统一使用 `tcpSocket` 探针，不修改业务代码：

```yaml
startupProbe:
  tcpSocket:
    port: service
  periodSeconds: 5
  failureThreshold: 30        # 最多给 150 秒启动时间

readinessProbe:
  tcpSocket:
    port: service
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 3

livenessProbe:
  tcpSocket:
    port: service
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 6         # 最多给 60 秒才会判定死亡
```

后续分阶段升级为 HTTP (`/healthz`、`/readyz`) 和 gRPC health 探针的完整实施计划，参见 `[doc/deploy/4.k8s-probes-implementation-plan-2026-05-29.md](./4.k8s-probes-implementation-plan-2026-05-29.md)`。

其余 Compose 概念到 K8S 的映射：

| Docker Compose | Kubernetes | 迁移理解 |
| --- | --- | --- |
| `docker compose up --scale` | `replicas`、HPA | 压测环境先手动改 replicas，稳定后再考虑 HPA |
| Compose 网络服务名 | K8S Service DNS | 同 namespace 可用 `service-name:port` |


一个常用心法：Compose 的 `service` 在 K8S 里通常会拆成 `Deployment + Service + ConfigMap/Secret + ServiceAccount/RBAC`。

## 6. 推荐仓库结构
建议把真实部署文件放在 `deploy/` 下，文档模板继续放在 `doc/deploy/config-templates/`：

```latex
deploy/
├── charts/
│   └── auxsol-services/
│       ├── Chart.yaml
│       ├── values.yaml
│       └── templates/
│           ├── _helpers.tpl
│           ├── configmap.yaml
│           ├── deployment.yaml
│           ├── service.yaml
│           ├── serviceaccount.yaml
│           └── rbac.yaml
├── values/
│   ├── kind-dev.yaml
│   ├── ack-perf.yaml
│   └── ack-prod.yaml
└── config/
    ├── ack-perf/
    │   └── configmap/
    │       ├── common.yaml
    │       ├── saas-api.yaml
    │       ├── iot-api.yaml
    │       ├── system.yaml
    │       ├── timedjob.yaml
    │       ├── timedscheduler.yaml
    │       ├── things.yaml
    │       └── protocolsync.yaml
    └── ack-prod/
        └── configmap/
            └── ...
```

设计边界：

| 内容 | 放哪里 | 原则 |
| --- | --- | --- |
| 镜像、replicas、resources、ports | `deploy/values/*.yaml` | Helm 管部署参数 |
| 业务 YAML 配置 | `deploy/config/<env>/configmap/*.yaml` | 保持完整文件，不拆成大量 Helm values |
| Secret 示例 | `secret.example.env` | 只放 key 名和示例值 |
| 真实 Secret | K8S Secret、External Secrets | 不进 Git |
| Deployment/Service/RBAC 模板 | Helm `templates/` | 复用服务骨架 |


不要把 Helm 当成业务配置模板引擎。Helm 负责把文件挂进去，不负责理解每个业务配置字段。

## 7. Helm 设计原则
ACK 压测环境建议用 Helm 作为主部署方式。

原因：

1. 服务数量多，直接写 K8S YAML 会重复很多 Deployment/Service/ConfigMap/RBAC。
2. 压测和生产都要记录 `values.yaml`、ConfigMap checksum、Secret version、镜像 tag。
3. 生产回滚需要 Helm release revision。
4. ACK 部署时应该用 `helm upgrade --install`，而不是手工改 `helm template` 输出。

Kustomize 可以作为辅助工具，但不建议作为主部署形态。它适合做少量 patch，不适合承载这套多服务、多环境、需要 revision/rollback 的部署。

## 8. 第一个迁移目标
不要一开始就把所有服务、EMQX、NATS、TDengine、eKuiper 全部塞进 K8S。新手第一轮目标应该很小：

```latex
目标 A：让一个无状态 RPC 服务在 kind 中启动
目标 B：挂载 /app/etc/common.yaml + 服务 yaml
目标 C：创建 ClusterIP Service
目标 D：kubectl logs 没有配置加载错误
```

建议第一个服务选 `system-rpc` 或 `things-rpc`，因为它们能代表 RPC 服务，但不用先处理外部 HTTP 入口。

完成一个服务后，再加入：

1. 一个 API Gateway。
2. API Gateway 调 RPC，验证 `k8s://auxsol-test/system-rpc:8002`。
3. 加入第二个 RPC 服务。
4. 再考虑 eKuiper、NATS、EMQX、TDengine 等组件。

## 9. 镜像策略
本地 kind 和 ACK 的镜像来源不同。

当前 `iot`、`saas`、`ekuiper-cluster` 的 Makefile 镜像构建能力检查和改进计划，参见 `doc/deploy/5.image-build-makefile-gap-analysis-2026-05-29.md`。

本地 kind 有两种方式：

```bash
# 方式一：使用本地构建镜像，再加载进 kind
docker build -t auxsol/system-rpc:dev ./saas
kind load docker-image auxsol/system-rpc:dev --name auxsol-dev
```

```yaml
# kind-dev.yaml 中建议配合
imagePullPolicy: IfNotPresent
```

ACK 必须使用 ACR 或可访问的镜像仓库：

```bash
docker tag auxsol/system-rpc:dev registry.cn-hangzhou.aliyuncs.com/<namespace>/system-rpc:<git-sha>
docker push registry.cn-hangzhou.aliyuncs.com/<namespace>/system-rpc:<git-sha>
```

ACK 压测和生产不要使用 `latest`。压测建议用 git sha，生产建议用 semver + git sha，必要时记录 digest。

## 10. ConfigMap 与 Secret
当前项目的关键规则：

1. 容器内统一挂载到 `/app/etc`。
2. 每个服务目录必须同时有 `common.yaml` 和服务自己的 YAML。
3. `saas-api.yaml`、`iot-api.yaml` 落到容器里时建议命名为 `/app/etc/api.yaml`。
4. RPC 服务按同名文件挂载，例如 `/app/etc/system.yaml`。
5. YAML 中可以写 `${DB_HOST}`、`${REDIS_PASSWORD}`，由环境变量展开。

本地 kind 可以先用临时 Secret 冒烟：

```bash
kubectl create secret generic auxsol-common-secret \
  --from-env-file=doc/deploy/config-templates/ack-perf/secret.example.env \
  -n auxsol-test
```

注意：`secret.example.env` 只能用于结构验证。真实 ACK Secret 不能从 Git 示例文件复制真实密码。

检查 ConfigMap 是否包含明文密码：

```bash
helm template auxsol-test deploy/charts/auxsol-services \
  -f deploy/values/ack-perf.yaml \
  | rg -n "password|secret|accessKey|AccessKey|AK|SK"
```

如果命中的是 `${REDIS_PASSWORD}` 这种占位符可以接受；如果命中真实值，必须停止发布。

## 11. go-zero K8S 服务发现
ACK 压测和生产默认使用：

```yaml
SysRpc:
  Enable: true
  Mode: grpc
  Conf:
    Timeout: 1000000
    Target: k8s://auxsol-test/system-rpc:8002
```

这要求调用方 Pod 的 ServiceAccount 能读取 Kubernetes Endpoints：

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: auxsol-rpc-endpoints-reader
  namespace: auxsol-test
rules:
  - apiGroups: [""]
    resources: ["endpoints"]
    verbs: ["get", "list", "watch"]
```

验证权限：

```bash
kubectl auth can-i get endpoints \
  --as=system:serviceaccount:auxsol-test:auxsol-services \
  -n auxsol-test
```

通过标准：

```latex
yes
```

如果后续 go-zero 版本读取 `EndpointSlice`，再补充：

```yaml
apiGroups: ["discovery.k8s.io"]
resources: ["endpointslices"]
verbs: ["get", "list", "watch"]
```

## 12. 本地 Helm 验证流程
每次改 Helm chart，先跑静态检查：

```bash
helm lint deploy/charts/auxsol-services

  -n auxsol-test \
  -f deploy/values/kind-dev.yaml \
```

```bash
rg -n "^kind:|^  name:" /tmp/auxsol-test-rendered.yaml
```

```bash

  -n auxsol-test \
  -f deploy/values/kind-dev.yaml
```


## 13. ACK 部署流程
ACK 上不要手工 `kubectl apply` 修改 Helm 生成文件。推荐流程：

```latex
构建镜像
  -> 推送 ACR
  -> 更新 deploy/values/ack-perf.yaml 镜像 tag
  -> helm lint/template
  -> 切换 kube context 到 ACK
  -> helm upgrade --install
  -> kubectl 验证
  -> 压测冒烟
```

连接 ACK 集群前先从 ACK 控制台获取 kubeconfig，并确认当前上下文。阿里云官方文档说明 ACK 可以通过 kubeconfig 使用 kubectl 连接集群。

```bash
kubectl config get-contexts
kubectl config current-context
kubectl get nodes
```

创建 namespace：

```bash
kubectl create namespace auxsol-test --dry-run=client -o yaml | kubectl apply -f -
```

创建 Secret。首次可以手工创建，后续生产建议接 External Secrets/KMS：

```bash
kubectl create secret generic auxsol-common-secret \
  --from-env-file=/secure/path/ack-perf.secret.env \
  -n auxsol-test
```

发布：

```bash
helm upgrade --install auxsol-test deploy/charts/auxsol-services \
  -n auxsol-test \
  -f deploy/values/ack-perf.yaml
```

验证：

```bash
helm status auxsol-test -n auxsol-test
helm history auxsol-test -n auxsol-test
kubectl get deploy,po,svc,ingress -n auxsol-test
kubectl get endpoints -n auxsol-test
kubectl logs -n auxsol-test deploy/saas-api-gateway --tail=100
```

回滚：

```bash
helm history auxsol-test -n auxsol-test
helm rollback auxsol-test <REVISION> -n auxsol-test
```

## 14. 新手排障顺序
Pod 起不来时，按这个顺序看：

```bash
kubectl get pods -n auxsol-test
kubectl describe pod <pod-name> -n auxsol-test
kubectl logs <pod-name> -n auxsol-test
kubectl get events -n auxsol-test --sort-by=.lastTimestamp
```

常见问题：

| 现象 | 常见原因 | 检查命令 |
| --- | --- | --- |
| `ImagePullBackOff` | 镜像 tag 不存在、ACK 无权限拉 ACR、本地 kind 没 load 镜像 | `kubectl describe pod` |
| `CrashLoopBackOff` | 配置文件缺失、启动参数错、依赖连不上 | `kubectl logs --previous` |
| `ConfigMap not found` | Helm values 中名字不一致或 namespace 错 | `kubectl get cm -n auxsol-test` |
| `secret not found` | Secret 未创建或名字不一致 | `kubectl get secret -n auxsol-test` |
| RPC `no endpoints` | Service selector 不匹配、Pod 未 Ready、RBAC 不足 | `kubectl get endpoints` |
| 端口不通 | Service `port` 和 `targetPort` 写错 | `kubectl describe svc` |
| 本地访问不了 | ClusterIP 不能直接从本机访问，需要 port-forward | `kubectl port-forward` |


排障优先看 `describe pod`，它通常会直接告诉你镜像、挂载、探针、调度失败原因。

## 15. 分阶段实施计划
每一步都控制在 2-5 分钟，遇到失败就停下来排障。

| 步骤 | 文件路径 | 预期内容 | 验证 |
| --- | --- | --- | --- |
| 1 | `deploy/charts/auxsol-services/Chart.yaml` | 创建 Helm chart 元数据 | `helm lint deploy/charts/auxsol-services` 能识别 chart |
| 2 | `deploy/charts/auxsol-services/values.yaml` | 定义一个服务 `system-rpc` 的 image、port、config 文件名 | `helm template` 输出一个 Deployment |
| 3 | `deploy/charts/auxsol-services/templates/deployment.yaml` | 渲染 Deployment、volumeMounts、envFrom Secret | `helm template` 中出现 `/app/etc` |
| 4 | `deploy/charts/auxsol-services/templates/service.yaml` | 渲染 ClusterIP Service | `helm template` 中出现 `kind: Service` |
| 5 | `deploy/charts/auxsol-services/templates/configmap.yaml` | 把 `common.yaml` 和服务 YAML 放进 ConfigMap | `helm template` 中出现 ConfigMap data |
| 6 | `deploy/charts/auxsol-services/templates/rbac.yaml` | 创建 endpoints reader Role/RoleBinding | `kubectl auth can-i get endpoints` 返回 `yes` |
| 7 | `deploy/values/kind-dev.yaml` | 本地 kind 镜像 tag、replicas、Secret 名称 | `helm upgrade --install` 成功 |
| 8 | `deploy/config/ack-perf/configmap/*.yaml` | 从文档模板复制压测配置并改为真实占位符 | `rg "Mode: direct"` 不应命中 ACK 配置 |
| 9 | `deploy/values/ack-perf.yaml` | ACK namespace、ACR 镜像、资源规格 | `helm template auxsol-test deploy/charts/auxsol-services -f deploy/values/ack-perf.yaml` 成功 |
| 10 | ACK 集群 | 使用 Helm 发布压测环境 | `helm status` deployed，Pod Ready |


建议每完成一个步骤就提交一次小 commit，后面回滚思路会更清楚。

## 16. ACK 前置清单
部署 ACK 前确认：

| 项目 | 检查 |
| --- | --- |
| kubeconfig | 当前 context 是 ACK 压测集群，不是生产 |
| namespace | `auxsol-test` 已创建 |
| ACR | 所有业务镜像 tag 已 push，ACK 有拉取权限 |
| Secret | 真实 Secret 已创建，不在 Git |
| ConfigMap | 不包含真实密码、AK、JWT secret |
| RPC | ACK 配置里是 `Mode: grpc` + `Target: k8s://auxsol-test/<svc>:<port>` |
| RBAC | API/RPC Pod ServiceAccount 能读 endpoints |
| Service | RPC 服务是 ClusterIP，API 通过 ALB Ingress 暴露 |
| 可观测 | 日志、事件、基础指标能看到 |
| 回滚 | `helm history` 可用，上一版 values 和 Secret version 已记录 |


## 17. 不要做的事
1. 不要把 `helm template` 输出复制出来长期手工维护。
2. 不要在 Git 里提交真实 Secret。
3. 不要在 ACK 压测/生产继续使用 `Mode: direct`。
4. 不要用 `latest` 做压测和生产镜像 tag。
5. 不要把 `depends_on` 思维直接搬到 K8S；应用必须能处理依赖短暂不可用。
6. 不要一开始就迁移所有中间件；先让一个服务跑通。
7. 不要在不确认 `kubectl config current-context` 的情况下执行发布或删除。

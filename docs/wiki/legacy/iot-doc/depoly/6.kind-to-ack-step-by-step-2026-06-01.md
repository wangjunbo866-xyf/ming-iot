## 1. 总体路线
```latex
阶段 A：构建本地镜像 → 加载到 kind → 验证镜像可运行
阶段 B：创建 Helm Chart → 准备配置文件 → 本地 kind 冒烟
阶段 C：推送镜像到 Harbor → 准备 ACK values → 切 context → 发布到 ACK
阶段 D：S0 冒烟 → 回滚验证 → 冻结版本
```

建议第一个跑通的服务是 `system-rpc`，因为它代表 RPC 服务但不需要外部 HTTP 入口，链路最短。

### 2.3 镜像 tag 策略说明
三种构建目标的区别（不取决于 tag 名，取决于构建目标）：

| Makefile 目标 | 依赖的 build | 使用的 Dockerfile | 镜像内容 | tag 推荐 |
| --- | --- | --- | --- | --- |
| `docker-dev-*` | `build-dev-*` | `Dockerfile-dev` | Delve 调试端口、`-gcflags="-N -l"` 未优化二进制 | `<version>-dev` |
| `docker-local-*` | `build-pro-*` | `Dockerfile`（production） | strip 过的优化二进制，无 Delve | `<git-sha>` |
| `push-*` | `build-pro-*` | `Dockerfile`（production） | 与 `docker-local-*` 相同，推送到 Harbor | `<git-sha>` |


**kind 本地和 ACK 使用同一个 git sha tag**，只是 `IMAGE_REGISTRY` 不同：

+ kind：`auxsol/system-rpc:<git-sha>`
+ ACK：`47.114.81.246:1001/auxsol/system-rpc:<git-sha>`

### 2.4 构建 system-rpc（第一个服务）
system-rpc 的构建是两阶段：先 `go build` 编译二进制，再 `docker build` 打包镜像。Makefile 通过依赖关系自动串联。

**构建链路：**

```latex
docker-local-system-rpc
  └→ build-pro-saas-rpc-system          ← 阶段 1：go build
  │    go build -trimpath -ldflags="..." -o rpc-system rpc/system/system.go
  │    产物：_build/rpc-system-<version>-<os>-<arch>/bin/rpc-system
  │
  └→ docker buildx build                ← 阶段 2：docker image
       COPY _build/rpc-system-* /app    （单阶段 Dockerfile，不在镜像内编译）
       FROM debian:bookworm
       最终镜像：auxsol/system-rpc:<tag>
```

> 注意：当前 Dockerfile 是单阶段构建，不在镜像内部执行 `go build`。它直接 `COPY` 宿主机 `_build/` 下已编译好的二进制。因此 `docker-local-*` 和 `push-*` 必须依赖 `build-pro-*`，确保二进制先就位。
>

**关于 IMAGE_TAG：** `saas`、`iot`、`ekuiper-cluster` 是独立 git 仓库，各自有不同 commit history。Makefile 中 `IMAGE_TAG` 默认值是 `$(GIT_COMMIT)`，即 `git rev-parse --short HEAD`，会在执行 make 时取当前目录的 commit sha。因此只需在对应子模块目录下执行 make，无需手动传 `IMAGE_TAG`。只有覆盖默认行为（如发布历史 tag）时才需要显式指定。

**执行构建：**

```bash
cd ~/workspace-aux/saas

# 一步完成：go build + docker image（Makefile 自动处理依赖）
# IMAGE_TAG 自动取 saas 仓库当前 HEAD 的 commit sha
make docker-local-system-rpc IMAGE_REGISTRY=auxsol
```

如果想分步执行以便观察：

```bash
# 阶段 1：只编译二进制
make build-pro-saas-rpc-system
ls -la _build/rpc-system-*/bin/

# 阶段 2：打包镜像
make docker-local-system-rpc IMAGE_REGISTRY=auxsol
```

验证：

```bash
docker image ls auxsol/system-rpc
# 期望看到 auxsol/system-rpc  <git-sha>  ...  <1 minute ago>
```

```yaml
            tcpSocket:
              port: service

            timeoutSeconds: {{ $.Values.probes.tcpDefaults.readiness.timeoutSeconds }}
```

```yaml
  timedjob-rpc:
```

发布时通过 `--set` 传入各仓库的实际 sha（saas、iot、ekuiper-cluster 是独立仓库，sha 不同）：

```bash

IOT_SHA=$(cd ~/workspace-aux/iot && git rev-parse --short HEAD)
EKUIPER_SHA=$(cd ~/workspace-aux/ekuiper-cluster && git rev-parse --short HEAD)

helm upgrade --install auxsol-test deploy/charts/auxsol-services \
  -n auxsol-test \
  -f deploy/values/kind-dev.yaml \
  --set global.imageTag=${SAAS_SHA} \
  --set services.iot-api-gateway.image.tag=${IOT_SHA} \
  --set services.things-rpc.image.tag=${IOT_SHA} \
  --set services.ekuiper-cloudx.image.tag=${EKUIPER_SHA}
```

### 3.17 排障指南
Pod 起不来时按此顺序排查：

```bash
kubectl get pods -n auxsol-test
kubectl describe pod <pod-name> -n auxsol-test
kubectl logs <pod-name> -n auxsol-test
kubectl logs <pod-name> -n auxsol-test --previous

```

常见问题：

| 現象 | 常见原因 | 处理 |
| --- | --- | --- |
| `ImagePullBackOff` | kind 没加载镜像 | `make kind-load-<service>` |
| `CrashLoopBackOff` | 配置缺失或依赖连不上 | `kubectl logs --previous` |
| `Readiness probe failed` | 端口未监听或启动慢 | 调大 `failureThreshold` |
| Service 无 Endpoints | Pod 未 Ready 或 selector 不匹配 | 查 labels |
| RPC `no endpoints` | ServiceAccount 无权限 | 查 RBAC |

## 7. 关键原则
1. **不要在 Git 中提交真实 Secret**
2. **kind 和 ACK 统一使用 git sha 作为镜像 tag**，不用 `dev`、不用 `latest`
3. `docker-dev-*`** 是 Delve 调试镜像，**`docker-local-*`** 和 **`push-*`** 是生产镜像**——区分在于 Makefile 目标，不在于 tag 名
4. **ACK 不使用 **`Mode: direct`，统一 `grpc + k8s://`
5. **不要手工改 **`helm template`** 输出**，用 `helm upgrade --install`
6. **每次操作前确认 **`kubectl config current-context`
7. **livenessProbe 不检查外部依赖**（DB、Redis、NATS、下游 RPC）
8. **eKuiper 不自动扩缩容**，副本变更必须人工执行
9. **先跑一个服务再批量复制**，system-rpc 是最佳起点

# 镜像构建 Makefile 检查与改进计划
日期：2026-05-29

## 1. 背景
`doc/deploy/3.docker-compose-to-k8s-ack-guide-2026-05-28.md` 第 9 节要求镜像策略同时支持本地 kind 和 ACK：

1. 本地可以构建镜像并加载到 kind。
2. ACK 使用 Harbor 或其他可访问镜像仓库；当前 Harbor 地址为 `http://47.114.81.246:1001`。
3. ACK 压测和生产不使用 `latest`。
4. 压测镜像使用 git sha 等不可变 tag。
5. 生产镜像使用 semver + git sha，必要时记录 digest。

本次检查范围：

| 模块 | Makefile |
| --- | --- |
| `iot` | `iot/Makefile` |
| `saas` | `saas/Makefile` |
| `ekuiper-cluster` | `ekuiper-cluster/Makefile` |


本次只做静态检查，未执行实际 `docker build`、`docker push` 或 `kind load`。

## 2. 总体结论
当前 Makefile **部分满足本地构建需求，但不满足 ACK 镜像发布策略**。

当前项目 Harbor 信息：

| 项目 | 值 |
| --- | --- |
| Harbor UI | `http://47.114.81.246:1001` |
| Docker registry host | `47.114.81.246:1001` |
| 镜像地址格式 | `47.114.81.246:1001/auxsol/<image>:<tag>` |


注意：Docker 镜像名中不要写 `http://`。`http://47.114.81.246:1001` 是 Harbor UI/协议地址，`docker login`、`docker push` 和 Helm values 中使用 `47.114.81.246:1001/auxsol/...`。

现有能力：

| 能力 | 当前状态 |
| --- | --- |
| 构建 Go 二进制 | 三个模块都有 |
| 构建本地 Docker 镜像 | 三个模块都有 |
| 指定基础镜像 tag | 支持，但规则不统一 |
| 指定平台 | 大多支持 `linux/amd64`，eKuiper cloudx 目标存在平台变量风险 |


主要缺口：

| 缺口 | 影响 |
| --- | --- |
| 无统一 `REGISTRY` / `REGISTRY_PROJECT` / `IMAGE_TAG` 变量 | ACK 镜像地址需要手工拼，容易不一致 |
| 无 `docker push` / `buildx --push` 目标 | 无法形成标准 ACK 发布命令 |
| 无 `kind load docker-image` 目标 | 本地 K8S 验证流程还要手工执行 |
| 多处镜像 tag 使用 `$(VERSION)-dev` | 压测/生产不可审计，和 dev 语义混淆 |
| `iot` 生产镜像额外打 `latest` | 与 ACK 禁止 `latest` 的策略冲突 |
| 服务镜像名不统一 | Helm values 难以统一引用 |
| eKuiper chart 默认仍指向 `lfedge/ekuiper` | 不能表达自定义 cloudx 插件镜像 |
| 未输出 digest | 生产回滚和审计缺少强凭据 |


结论：需要补充一层统一的镜像构建/推送规范，最好在三个模块 Makefile 中使用同一套变量和目标命名。

## 3. 当前 Makefile 检查
### 3.1 iot
当前能力：

| 项目 | 现状 |
| --- | --- |
| 版本变量 | `VERSION` 来自 `git describe`，`GIT_COMMIT` 已存在 |
| dev build | `build-dev-iot-%` |
| pro build | `build-pro-iot-%` |
| dev 镜像 | `docker-dev-iot-api-gateway` |
| pro 镜像 | `docker-pro-iot-%` |
| cloud 目标 | `cloud: build-pro-iot-api-gateway docker-pro-iot-api-gateway` |


问题：

1. `docker-pro-iot-%` 镜像 tag 是 `$(VERSION)-dev`，生产目标仍带 `dev`。
2. `docker-pro-iot-%` 同时打 `latest` tag，不符合 ACK 压测/生产策略。
3. `TARGET ?= auxsol` 只适合本地命名，不适合 Harbor 完整地址。
4. 没有 `push` 目标。
5. 没有 `kind-load` 目标。
6. `CP_PRO ?= 8101` 是全局变量，通用 `docker-pro-iot-%` 构建 RPC 时容易沿用 API 端口。

8. `build-pro-iot-%` 通用规则只取目标名的第一段和最后一段来拼路径，容易漏掉中间目录；按服务名 stem 写成 `build-pro-iot-things`、`build-pro-iot-protocolsync` 都会展开到错误路径。`things-rpc` 可以通过路径型 stem `build-pro-iot-rpc-things` 正确展开到 `rpc/things/things.go`，也可以写显式目标提升可读性；`protocolSync` 当前阶段只记录风险，后续独立部署时必须显式补目标。


当前能力：

| 项目 | 现状 |
| --- | --- |
| 版本变量 | `VERSION` 来自 `git describe` |
| dev build | `build-dev-saas-%` |
| pro build | `build-pro-saas-%` |
| API 镜像 | `docker-dev-saas-api-gateway`、`docker-pro-saas-api-gateway` |

| timed pro 镜像 | `docker-pro-saas-rpc-timed-timedjob`、`docker-pro-saas-rpc-timed-timedscheduler` |

1. 没有 `GIT_COMMIT`、`GIT_BRANCH`、`BUILD_TIME` 变量用于镜像元数据。
2. pro 镜像 tag 仍然是 `$(VERSION)-dev`。
3. 没有 `push` 目标。
4. 没有 `kind-load` 目标。
5. `.PHONY: docker-dev-saas-rpc-system` 与实际目标 `docker-dev-rpc-system` 名称不一致。
6. system 镜像名是 `$(TARGET)/system`，不是部署文档和 Helm 更容易理解的 `system-rpc`。
7. `system-rpc` 只有 dev 镜像目标，没有 pro 镜像目标。后续 `push-system-rpc` 不能只补 `docker push`，必须先补齐 production 二进制构建和生产 Dockerfile 构建链路。
8. `mproxy` 服务已废弃，不应新增 `docker-local-mproxy`、`kind-load-mproxy`、`push-mproxy` 或 Helm values；已有旧目标只保留兼容并标记 `DEPRECATED`，后续删除。
9. `timedjob-rpc` 和 `timedscheduler-rpc` 只有 pro 镜像目标，没有 dev 镜像目标。本地 kind 开发和本地调试也需要 `docker-dev-*` 或标准 `docker-local-*` 对应链路。
10. timedjob 镜像名是 `saas-rpc-timed-timedjob`，与 K8S 服务名 `timedjob-rpc` 不统一。
11. `build-pro-saas-%` 通用规则会把 `rpc-timed-timedjob` 错误展开为 `rpc/timedjob/timedjob.go`，实际入口是 `rpc/timed/timedjob/timedjob.go`，`cloud-timed` 当前依赖链路会编译失败。

13. `build-pro-saas-%` 没有通过 `-ldflags` 注入版本元数据。即使补齐 `GIT_COMMIT`、`GIT_BRANCH`、`BUILD_TIME` 变量，如果 production build 不使用 `-X main.version=...` 等参数，最终二进制仍然无法暴露准确版本信息。

### 3.3 通用构建规则阻断项
现有 `build-pro-saas-%` / `build-pro-iot-%` 规则通过 `$(firstword $(subst -, ,$*))` 和 `$(lastword $(subst -, ,$*))` 拼入口路径。这个规则只适合少数目录结构，不能假设覆盖所有服务。

| 模块 | 目标 | 通用规则生成的入口路径 | 实际入口文件路径 | 状态 |
| --- | --- | --- | --- | --- |
| `saas` | `build-pro-saas-rpc-timed-timedjob` | `rpc/timedjob/timedjob.go` | `rpc/timed/timedjob/timedjob.go` | 不匹配，必须显式目标 |
| `saas` | `build-pro-saas-rpc-timed-timedscheduler` | `rpc/timedscheduler/timedscheduler.go` | `rpc/timed/timedscheduler/timedscheduler.go` | 不匹配，必须显式目标 |
| `iot` | `build-pro-iot-things` | `things/things/things.go` | `rpc/things/things.go` | 服务名 stem 不匹配，应改用 `build-pro-iot-rpc-things` 或显式目标 |
| `iot` | `build-pro-iot-rpc-things` | `rpc/things/things.go` | `rpc/things/things.go` | 路径型 stem 可匹配，但仍需确认 `SVC` 与 `_build` 产物 stem |
| `iot` | `build-pro-iot-protocolsync` | `protocolsync/protocolsync/protocolsync.go` | `pkg/rpcs/protocolSync/protocolSync.go` | 不匹配，且目录大小写不同；当前阶段先记录风险，后续独立部署时必须显式目标 |


影响：

1. `cloud-timed` 依赖的 `build-pro-saas-rpc-timed-timedjob`、`build-pro-saas-rpc-timed-timedscheduler` 如果按现有通用规则执行，会直接找错入口文件。
2. `things-rpc` 不能直接套服务名形式的 `build-pro-iot-things`，但可以使用路径型 stem `build-pro-iot-rpc-things` 走现有通用规则；显式目标更清晰，但不是唯一选择。
3. `protocolsync-rpc` 的实际路径是 `pkg/rpcs/protocolSync/protocolSync.go`，既有多级目录，又有大小写约束；若后续独立部署，必须显式写入这个入口路径。
4. 后续新增 `docker-local-*`、`push-*` 时，不能只把服务名形式的通用 build 目标作为前置依赖；必须逐服务确认 stem、入口路径、`SVC` 与 `_build` 产物映射，并用 `make -n` 和实际构建验证。

## 4. 推荐统一镜像规范
### 4.1 镜像仓库变量
三个模块统一使用：

```makefile
REGISTRY ?= 47.114.81.246:1001
REGISTRY_PROJECT ?= auxsol
IMAGE_REGISTRY ?= $(REGISTRY)/$(REGISTRY_PROJECT)
IMAGE_PLATFORM ?= linux/amd64
BUILDX_BUILDER ?= default
GIT_COMMIT ?= $(shell git rev-parse --short HEAD 2>/dev/null || echo unknown)
GIT_BRANCH_FALLBACK ?= $(shell git rev-parse --abbrev-ref HEAD 2>/dev/null | grep -v '^HEAD$$' || git name-rev --name-only HEAD 2>/dev/null || echo unknown)
GIT_BRANCH ?= $(or $(GITHUB_REF_NAME),$(CI_COMMIT_BRANCH),$(CI_COMMIT_REF_NAME),$(GIT_BRANCH_FALLBACK))
BUILD_TIME ?= $(shell date -u '+%Y-%m-%dT%H:%M:%SZ')
IMAGE_TAG ?= $(GIT_COMMIT)
```

`GIT_BRANCH` 需要兼容 CI 的 detached HEAD 场景。`git rev-parse --abbrev-ref HEAD` 在 detached HEAD 下会返回 `HEAD`，不适合作为版本元数据；优先使用 CI 注入的分支变量，例如 GitHub Actions 的 `GITHUB_REF_NAME`、GitLab CI 的 `CI_COMMIT_BRANCH` / `CI_COMMIT_REF_NAME`，再回退到 git 命令推导。

当前模块现状不同：`iot/Makefile` 已有 `GIT_COMMIT`、`GIT_BRANCH`、`BUILD_TIME`，但 `GIT_BRANCH := $(shell git rev-parse --abbrev-ref HEAD ...)` 需要改写为上面的 CI 优先版本；`saas/Makefile` 当前没有这些版本元数据变量，需要新增；`ekuiper-cluster/Makefile` 已有自己的版本变量，也应在新增标准 push 目标时对齐统一镜像变量。

`BUILD_TIME` 格式需要单独确认：`iot/Makefile` 现有格式是 `+%Y-%m-%d_%H:%M:%S`，上面的统一建议是 UTC ISO 8601 格式 `+%Y-%m-%dT%H:%M:%SZ`。迁移前必须确认 Go 代码、启动日志、监控采集或发布记录中是否解析该字符串；如果有解析逻辑，需要同步调整解析格式，或先保留旧格式并在后续版本单独迁移。

`BUILDX_BUILDER` 用于 `docker buildx build --builder`，尤其是需要访问 Harbor 的 `push-*` 目标。默认使用 `default`，让 buildx 走当前 Docker context 的默认 builder；如果必须使用单独配置过 insecure registry 的 `docker-container` builder，可以在执行时覆盖，例如 `BUILDX_BUILDER=auxsol-container`。

本地 kind 默认可以覆盖：

```bash
make docker-local-saas-api-gateway IMAGE_REGISTRY=auxsol IMAGE_TAG=dev
```

ACK 压测默认：

```bash
make push-saas-api-gateway \
  IMAGE_REGISTRY=47.114.81.246:1001/auxsol \
  IMAGE_TAG=<git-sha>
```

生产默认：

```bash
make push-saas-api-gateway \
  IMAGE_REGISTRY=47.114.81.246:1001/auxsol \
  IMAGE_TAG=<semver>-<git-sha>
```

## 5. 推荐 Makefile 目标
每个模块至少补齐四类目标。

在套用下面模板前，必须逐服务确认 production 构建链路是否存在。模板里的 `build-pro-<module>-<path>` 是占位符，不代表当前所有服务已经有这个目标，也不代表通用 `%` 规则一定能展开到正确入口；例如 `saas system-rpc` 当前缺少等价的 pro 镜像构建目标，`timedjob-rpc`、`timedscheduler-rpc` 需要显式 build 目标；`things-rpc` 可以使用路径型 stem `build-pro-iot-rpc-things` 或显式目标；`protocolsync-rpc` 当前阶段只记录风险，后续独立部署时再补显式 build 目标。

建议先做一张构建链路清单：

| 服务 | production 二进制目标 | docker-local Dockerfile | push Dockerfile | dev/debug Dockerfile | Dockerfile 类型 | 产物路径 | 标准本地镜像目标 | 标准 push 目标 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `saas-api-gateway` | `build-pro-saas-api-gateway` | `saas/deploy/docker/Dockerfile` | `saas/deploy/docker/Dockerfile` | `saas/deploy/docker/Dockerfile-dev` | 单阶段，`COPY _build/$SVC-*` | `_build/api-gateway-<version>-<os>-<arch>/bin/api-gateway` | `docker-local-saas-api-gateway` | `push-saas-api-gateway` | 通用规则可覆盖，入口 `api/gateway/gateway.go` 已存在 |
| `system-rpc` | `build-pro-saas-rpc-system` 或等价目标 | `saas/deploy/docker/Dockerfile` | `saas/deploy/docker/Dockerfile` | `saas/deploy/docker/Dockerfile-dev` | 单阶段，`COPY _build/$SVC-*` | 需确认 `SVC` 名和 build target stem 的映射，避免镜像名 `system-rpc` 与二进制 stem 不一致 | `docker-local-system-rpc` | `push-system-rpc` | 当前缺失，需要补齐 |
| `timedjob-rpc` | 新增显式目标，入口 `rpc/timed/timedjob/timedjob.go` | `saas/deploy/docker/Dockerfile` | `saas/deploy/docker/Dockerfile` | `saas/deploy/docker/Dockerfile-dev` | 单阶段，`COPY _build/$SVC-*` | `_build/rpc-timed-timedjob-<version>-<os>-<arch>/bin/rpc-timed-timedjob` | `docker-local-timedjob-rpc` | `push-timedjob-rpc` | 通用规则会误到 `rpc/timedjob/timedjob.go`，必须补齐 |
| `timedscheduler-rpc` | 新增显式目标，入口 `rpc/timed/timedscheduler/timedscheduler.go` | `saas/deploy/docker/Dockerfile` | `saas/deploy/docker/Dockerfile` | `saas/deploy/docker/Dockerfile-dev` | 单阶段，`COPY _build/$SVC-*` | `_build/rpc-timed-timedscheduler-<version>-<os>-<arch>/bin/rpc-timed-timedscheduler` | `docker-local-timedscheduler-rpc` | `push-timedscheduler-rpc` | 通用规则会误到 `rpc/timedscheduler/timedscheduler.go`，必须补齐 |

补齐规则：

1. `docker-local-*` 和 `push-*` 必须依赖 production 构建链路，不应误用 dev 镜像目标。
2. 如果某服务没有 production 二进制目标，先补 `build-pro-*` 或一个语义等价且命名清晰的目标。
3. 如果某服务入口路径不符合通用 `%` 规则，不要硬套模板，必须新增显式目标；当前 timed 属于这一类。`things-rpc` 可用 `build-pro-iot-rpc-things` 这种路径型 stem，或用显式目标提升可读性；protocolSync 先记录风险，后续独立部署时再处理。
4. `docker-local-*` 是给 kind 验证 ACK 形态镜像，不等于调试镜像，默认使用 production Dockerfile。
5. `docker-dev-*` 才使用 `Dockerfile-dev`，用于 Delve、本地调试或旧 Compose 调试链路。
6. `docker-dev-*` 可以传 `DP`，因为 `Dockerfile-dev` 使用 Delve 调试端口；`docker-local-*` 和 `push-*` 默认只传 `CP`，不传 `DP`。
7. `push-*` 必须使用 production Dockerfile，并通过 `--push` 推送到 Harbor。
8. 已废弃服务不补构建链路；当前 `mproxy` 已废弃。

### 5.1 特殊路径服务的具体处理方案
`timedjob-rpc` 和 `timedscheduler-rpc` 必须写专属 `.PHONY` target，不能依赖当前 `build-pro-saas-%` 的 `firstword/lastword` 展开逻辑。原因是目标名里的 `rpc-timed-timedjob` 会被展开成 `rpc/timedjob/timedjob.go`，丢掉中间的 `timed` 目录。

建议在 `saas/Makefile` 中新增显式 production build 目标，直接写死正确入口路径：

```makefile
PRO_LDFLAGS ?= -ldflags "-X main.version=$(VERSION) -X main.buildTime=$(BUILD_TIME) -X main.gitCommit=$(GIT_COMMIT) -X main.gitBranch=$(GIT_BRANCH)"

.PHONY: build-pro-saas-rpc-timed-timedjob
build-pro-saas-rpc-timed-timedjob: SHELL:=/bin/bash -euo pipefail
build-pro-saas-rpc-timed-timedjob:
    echo "Building for rpc-timed-timedjob"
    @rm -rf $(BUILD_PATH)/rpc-timed-timedjob-$(PACKAGE_NAME)
    @mkdir -p $(BUILD_PATH)/rpc-timed-timedjob-$(PACKAGE_NAME)/bin/etc
    @mkdir -p $(BUILD_PATH)/rpc-timed-timedjob-$(PACKAGE_NAME)/bin/data
    @mkdir -p $(BUILD_PATH)/rpc-timed-timedjob-$(PACKAGE_NAME)/bin/log
    @cp -r rpc/timed/timedjob/etc/* $(BUILD_PATH)/rpc-timed-timedjob-$(PACKAGE_NAME)/bin/etc
    GO111MODULE=on CGO_ENABLED=0 go build -trimpath $(PRO_LDFLAGS) -o rpc-timed-timedjob rpc/timed/timedjob/timedjob.go
    @mv ./rpc-timed-timedjob $(BUILD_PATH)/rpc-timed-timedjob-$(PACKAGE_NAME)/bin

.PHONY: build-pro-saas-rpc-timed-timedscheduler
build-pro-saas-rpc-timed-timedscheduler: SHELL:=/bin/bash -euo pipefail
build-pro-saas-rpc-timed-timedscheduler:
    echo "Building for rpc-timed-timedscheduler"
    @rm -rf $(BUILD_PATH)/rpc-timed-timedscheduler-$(PACKAGE_NAME)
    @mkdir -p $(BUILD_PATH)/rpc-timed-timedscheduler-$(PACKAGE_NAME)/bin/etc
    @mkdir -p $(BUILD_PATH)/rpc-timed-timedscheduler-$(PACKAGE_NAME)/bin/data
    @mkdir -p $(BUILD_PATH)/rpc-timed-timedscheduler-$(PACKAGE_NAME)/bin/log
    @cp -r rpc/timed/timedscheduler/etc/* $(BUILD_PATH)/rpc-timed-timedscheduler-$(PACKAGE_NAME)/bin/etc
    GO111MODULE=on CGO_ENABLED=0 go build -trimpath $(PRO_LDFLAGS) -o rpc-timed-timedscheduler rpc/timed/timedscheduler/timedscheduler.go
    @mv ./rpc-timed-timedscheduler $(BUILD_PATH)/rpc-timed-timedscheduler-$(PACKAGE_NAME)/bin
```

说明：

1. `PRO_LDFLAGS` 是建议新增的 production ldflags 变量，用于注入 `main.version`、`main.buildTime`、`main.gitCommit`、`main.gitBranch`，并避免重复写长命令。
2. production build 不应带 `-gcflags="all=-N -l"`；该调试标志只保留给 dev/debug 构建。
3. `docker-local-timedjob-rpc`、`push-timedjob-rpc` 必须依赖 `build-pro-saas-rpc-timed-timedjob`；`docker-local-timedscheduler-rpc`、`push-timedscheduler-rpc` 必须依赖 `build-pro-saas-rpc-timed-timedscheduler`。

`things-rpc` 不需要强制写显式 target。当前 `build-pro-iot-%` 对路径型 stem 可工作，因此推荐直接使用：

```makefile
docker-local-things-rpc: build-pro-iot-rpc-things
push-things-rpc: build-pro-iot-rpc-things
```

不要使用 `build-pro-iot-things`，它会展开到不存在的 `things/things/things.go`。如果希望命名更贴近服务名，也可以新增一个只做委托的 alias：

```makefile
.PHONY: build-pro-iot-things-rpc
build-pro-iot-things-rpc: build-pro-iot-rpc-things
```

`protocolsync-rpc` 当前阶段不要独立部署，不新增 `docker-local-protocolsync-rpc`、`push-protocolsync-rpc`，也不进入 Helm values 或 `push-all`。如果后续确认需要独立部署，必须新增显式 target，入口固定为 `pkg/rpcs/protocolSync/protocolSync.go`，不要尝试用服务名 stem 让通用规则推导；同时注意 `protocolSync` 目录中的 `S` 是大写。

当前所有业务镜像 Dockerfile 都是单阶段构建，不在镜像内部执行 Go 编译：go-zero 服务使用 `COPY _build/$SVC-* /app`，eKuiper cloudx 使用 `COPY _build/${PACKAGE_NAME} /kuiper`。因此 `docker-local-*` 和 `push-*` 必须依赖对应的 `build-pro-*` 或等价 production build 目标，确保宿主机 `_build/` 下已经有正确的二进制和配置产物。如果将来迁移为 multi-stage Dockerfile，并在 Dockerfile 内部完成编译，应从 `docker-local-*` 和 `push-*` 上移除 `build-pro-*` 前置依赖，避免重复构建和产物来源混乱。

非 Linux 宿主机风险备注：当前 `build-pro-*` 仍是在宿主机直接执行 `go build`，尚未统一强制 `GOOS=linux`。如果在 macOS 等非 Linux 开发机上执行 `make docker-local-*`，可能先生成 `darwin/amd64` 或 `darwin/arm64` 二进制，再被单阶段 Dockerfile 拷贝进 `debian:bookworm` 镜像，最终容器无法启动。执行 `docker-local-*` 或 `push-*` 前，需要确认 `build-pro-*` 生成的二进制平台与镜像平台一致；ACK 和 kind 默认目标是 Linux，例如：

```bash
GOOS=linux GOARCH=amd64 make docker-local-system-rpc \
  IMAGE_PLATFORM=linux/amd64
```

长期建议是在 Makefile 中增加 `BUILD_GOOS ?= linux`、`BUILD_GOARCH ?= amd64` 或类似变量，并让所有 production build 目标显式使用它们。本文档先标记风险，不把它作为本轮 Makefile 改造的阻塞项。

### 5.2 本地构建
```makefile
.PHONY: docker-local-<service>
docker-local-<service>: build-pro-<module>-<path>
    docker buildx build \
        --builder $(BUILDX_BUILDER) \
        --platform=$(IMAGE_PLATFORM) \
        --build-arg SVC=<svc> \
        --build-arg CP=<port> \
        --build-arg VERSION=$(VERSION) \
        --build-arg GIT_COMMIT=$(GIT_COMMIT) \
        --build-arg BUILD_TIME=$(BUILD_TIME) \
        -t $(IMAGE_REGISTRY)/<service>:$(IMAGE_TAG) \
        -f deploy/docker/Dockerfile . --load
```

说明：`docker-local-*` 名字里的 `local` 指“本地构建并加载/用于 kind”，不是“dev 调试镜像”。除非服务有特殊运行时要求，否则它应使用 production Dockerfile。

`--load` 限制：`docker-local-*` 通过 `--load` 把镜像加载到本地 Docker，因此 `IMAGE_PLATFORM` 必须是单平台，例如 `linux/amd64`。这个值还要和 kind 集群节点架构一致；例如在 ARM Mac 上运行 kind 时，通常应使用 `IMAGE_PLATFORM=linux/arm64`。如果未来需要 `linux/amd64,linux/arm64` 这类多平台镜像，不要使用 `--load`，应走 `push-*` 的 `--push` 链路推送到 registry。

端口参数规则：

1. `docker-dev-*` 使用 `Dockerfile-dev`，需要 `CP` 和 `DP`。其中 `DP` 是 Delve 调试端口。
2. `docker-local-*` 使用 production `Dockerfile`，默认只需要 `CP`，不需要 `DP`。
3. 如果某个服务的 production Dockerfile 未来确实新增 `ARG DP` 或其他调试/旁路端口，应为该服务单独写显式目标，不要把 `DP` 加回通用模板。

### 5.4 ACK 构建并推送
```makefile
.PHONY: push-<service>
push-<service>: build-pro-<module>-<path>
    docker buildx build \
        --builder $(BUILDX_BUILDER) \
        --platform=$(IMAGE_PLATFORM) \
        --build-arg SVC=<svc> \
        --build-arg CP=<port> \
        --build-arg VERSION=$(VERSION) \
        --build-arg GIT_COMMIT=$(GIT_COMMIT) \
        --build-arg BUILD_TIME=$(BUILD_TIME) \
        -t $(IMAGE_REGISTRY)/<service>:$(IMAGE_TAG) \
        -f deploy/docker/Dockerfile . --push
```

说明：`push-*` 必须使用 production Dockerfile。`Dockerfile-dev` 只能用于 `docker-dev-*` 旧调试目标或明确的 dev 目标，不能进入 ACK 压测和生产推送链路。

`push-*` 也默认只传 `CP`，不传 `DP`。当前 `iot/deploy/docker/Dockerfile` 和 `saas/deploy/docker/Dockerfile` 都只有 `ARG CP`，没有 `ARG DP`；`DP` 只属于 `Dockerfile-dev` 的 Delve 调试链路。

可选：如果希望在 push 时直接保存构建结果元数据，可以在 `push-*` 中增加 `--metadata-file`，并把文件纳入发布记录流程：

```makefile
BUILD_METADATA_DIR ?= _metadata

push-<service>: build-pro-<module>-<path>
    @mkdir -p $(BUILD_METADATA_DIR)
    docker buildx build \
        --builder $(BUILDX_BUILDER) \
        --platform=$(IMAGE_PLATFORM) \
        --build-arg SVC=<svc> \
        --build-arg CP=<port> \
        -t $(IMAGE_REGISTRY)/<service>:$(IMAGE_TAG) \
        -f deploy/docker/Dockerfile . \
        --metadata-file $(BUILD_METADATA_DIR)/<service>.json \
        --push
```

### 5.5 digest 记录
```makefile
.PHONY: digest-<service>
digest-<service>:
    docker buildx imagetools inspect $(IMAGE_REGISTRY)/<service>:$(IMAGE_TAG)
```

`digest-*` 使用 `docker buildx imagetools inspect` 查询远程 registry 中的 manifest，因此必须在对应的 `push-*` 成功之后执行。如果镜像还没有 push 到 Harbor，`digest-*` 会失败，这是正常的失败信号。

推荐执行顺序：

```bash
make push-<service> IMAGE_REGISTRY=47.114.81.246:1001/auxsol IMAGE_TAG=<git-sha>
make digest-<service> IMAGE_REGISTRY=47.114.81.246:1001/auxsol IMAGE_TAG=<git-sha>
```

如果使用 `--metadata-file`，也可以从 `push-*` 生成的 `$(BUILD_METADATA_DIR)/<service>.json` 中提取构建结果元数据，减少一次额外的远程 inspect。无论选择哪种方式，发布记录必须来自已经成功 push 的镜像。

生产发布记录中保存：

```latex
image: 47.114.81.246:1001/auxsol/<service>:<tag>
digest: sha256:...
gitCommit: ...
buildTime: ...
```

### 5.6 镜像清理策略
镜像清理分成本地开发机和 Harbor 两层处理。

本地 Docker：

1. 日常只清理 dangling 镜像，风险较低：

```bash
docker image prune -f
```

2. 磁盘压力较大时，再清理一段时间内未使用的镜像。这个命令会删除未被容器引用的旧镜像，执行前先确认本机没有依赖这些镜像的调试容器：

```bash
docker image prune -a --filter "until=168h"
```

3. 如果只想清理本项目的本地 tag，优先按仓库前缀筛选，避免误删其他项目镜像：

```bash
docker image ls "auxsol/*"
docker image ls "47.114.81.246:1001/auxsol/*"
```

Harbor：

1. `auxsol` project 需要配置 Harbor 自带的 tag retention policy。
2. ACK 压测镜像使用 `<git-sha>` tag，会快速增长，建议每个仓库只保留最近 30 到 50 个 pushed tag。
3. 生产 tag 如 `<semver>-<git-sha>` 或已进入发布记录的 digest，应使用更长保留期；正式发布镜像不要和压测短 SHA tag 使用同一条激进清理规则。
4. retention policy 删除 tag 后，Harbor 存储空间回收通常还需要执行 Harbor garbage collection，建议安排低峰期执行。

建议策略：

| 范围 | 保留策略 | 说明 |
| --- | --- | --- |
| 本地 dangling 镜像 | 每周或磁盘告警时执行 `docker image prune -f` | 低风险，主要清理无 tag 层 |
| 本地未使用镜像 | 手动执行 `docker image prune -a --filter "until=168h"` | 会删除未被容器引用的镜像，执行前确认开发环境 |
| Harbor ACK 压测 tag | 每个 repo 保留最近 30 到 50 个 pushed tag | 覆盖短期回滚和问题复现窗口 |
| Harbor 生产 tag | 保留更长周期，或单独项目/仓库管理 | 不和压测短 SHA tag 共用激进规则 |

## 7. 建议落地顺序
先做最小闭环，不要一口气重构所有目标。

### 阶段 A：新增标准目标，保留旧目标
| Task | 范围 | 验证 |
| --- | --- | --- |
| A1 | 逐服务确认 production 构建链路，补齐缺失的 `build-pro-*` 或等价目标；对 timed 这类当前要独立部署且不适配通用 `%` 规则的服务，先建显式 build 目标；`things-rpc` 可用路径型 stem 或显式目标；`protocolSync` 当前阶段只记录路径大小写和构建链路风险 | 每个当前要独立部署的非废弃服务都有明确 production 二进制目标、入口文件路径、Dockerfile 类型、产物路径，以及 `SVC` 到 `_build` 产物 stem 的映射 |
| A2 | 三个 Makefile 增加统一镜像变量，包含 `BUILDX_BUILDER` | `make -n` 不执行实际构建也能展开 |
| A3 | 新增 `docker-local-*`、`kind-load-*`、`push-*`、`digest-*` 标准目标 | `make -n push-* IMAGE_TAG=test` 输出 `:test` |
| A4 | 原有 Makefile target 第一阶段不删除 | 旧命令仍可 `make -n` 展开 |
| A5 | 旧 target 源码写入 `DEPRECATED` 提示，并委托到语义相同的新 target | `rg -n "DEPRECATED" saas/Makefile iot/Makefile ekuiper-cluster/Makefile`；`make -n <old-target>` 可展开委托命令 |
| A6 | 移除 ACK 新目标中的 `latest` | `rg "latest" iot/Makefile saas/Makefile ekuiper-cluster/Makefile` 仅允许旧兼容目标、注释或非 ACK 目标 |
| A7 | ACK tag 统一使用 `IMAGE_TAG`；`ekuiper-cluster` 标准 `docker` 旧目标中的 `$(VERSION)-dev` 属于非 ACK development Dockerfile 命名，本阶段不主动处理 | `make -n push-* IMAGE_TAG=test` 输出 `:test` |


兼容原则：

1. 新增标准 target，不直接删除旧 target。
2. 旧 target 标记为 `DEPRECATED`，说明替代命令和预计删除时机。
3. 旧 target 尽量委托到新 target，避免维护两套构建逻辑。
4. 旧 target 的语义不要悄悄改变。本地构建旧命令委托到 `docker-local-*`，云端发布旧命令委托到 `push-*`。
5. ACK 首轮压测通过并确认无人依赖旧命令后，再单独安排删除旧 target。

示例：

```makefile
.PHONY: docker-pro-saas-rpc-timed-timedjob
docker-pro-saas-rpc-timed-timedjob:
    @echo "DEPRECATED: use 'make docker-local-timedjob-rpc' for local image or 'make push-timedjob-rpc' for ACK. This target will be removed after ACK migration."
    $(MAKE) docker-local-timedjob-rpc
```

如果旧 target 名字里带 `cloud` 且过去用于云端发布，应委托到 `push-*`：

```makefile
.PHONY: cloud-timed
cloud-timed:
    @echo "DEPRECATED: use 'make push-timedjob-rpc push-timedscheduler-rpc'. This target will be removed after ACK migration."
    $(MAKE) push-timedjob-rpc
    $(MAKE) push-timedscheduler-rpc
```

### 阶段 E：可选增加 workspace root 批量入口
当单服务 `push-*` 目标全部跑通后，建议在 workspace root 增加统一入口，避免 ACK 发布时逐个 `cd` 到子目录执行，降低漏推服务或 tag 不一致的风险。

推荐优先使用根目录 `Makefile`，保持和各子模块 Makefile 的调用习惯一致；如果后续需要更复杂的发布前检查、并发控制或失败重试，再补 `scripts/push-all.sh`。

根目录 `Makefile` 示例：

```makefile
IMAGE_REGISTRY ?= 47.114.81.246:1001/auxsol
IMAGE_TAG ?= $(shell git rev-parse --short HEAD)
IMAGE_PLATFORM ?= linux/amd64

.PHONY: push-all
push-all:
    set -e; \
    $(MAKE) -C saas push-saas-api-gateway IMAGE_REGISTRY=$(IMAGE_REGISTRY) IMAGE_TAG=$(IMAGE_TAG) IMAGE_PLATFORM=$(IMAGE_PLATFORM); \
    $(MAKE) -C saas push-system-rpc IMAGE_REGISTRY=$(IMAGE_REGISTRY) IMAGE_TAG=$(IMAGE_TAG) IMAGE_PLATFORM=$(IMAGE_PLATFORM); \
    $(MAKE) -C saas push-timedjob-rpc IMAGE_REGISTRY=$(IMAGE_REGISTRY) IMAGE_TAG=$(IMAGE_TAG) IMAGE_PLATFORM=$(IMAGE_PLATFORM); \
    $(MAKE) -C saas push-timedscheduler-rpc IMAGE_REGISTRY=$(IMAGE_REGISTRY) IMAGE_TAG=$(IMAGE_TAG) IMAGE_PLATFORM=$(IMAGE_PLATFORM); \
    $(MAKE) -C iot push-iot-api-gateway IMAGE_REGISTRY=$(IMAGE_REGISTRY) IMAGE_TAG=$(IMAGE_TAG) IMAGE_PLATFORM=$(IMAGE_PLATFORM); \
    $(MAKE) -C iot push-things-rpc IMAGE_REGISTRY=$(IMAGE_REGISTRY) IMAGE_TAG=$(IMAGE_TAG) IMAGE_PLATFORM=$(IMAGE_PLATFORM); \
    $(MAKE) -C ekuiper-cluster push-ekuiper-cloudx IMAGE_REGISTRY=$(IMAGE_REGISTRY) IMAGE_TAG=$(IMAGE_TAG) IMAGE_PLATFORM=$(IMAGE_PLATFORM)
```

`push-all` 必须保持 stop-on-error 语义：任意一个服务 push 失败就立即停止，避免只推送了部分镜像却继续更新 Helm values。不要在这些子命令前加 `-` 前缀，也不要追加 `|| true` 吞掉错误。

验证：

```bash
make -n push-all \
  IMAGE_REGISTRY=47.114.81.246:1001/auxsol \
  IMAGE_TAG=test
```

通过标准：

1. 每个当前要独立部署的非废弃服务都出现一次 `push-*`。
2. `mproxy` 和 `protocolsync-rpc` 不出现在当前阶段的 `push-all` 中。
3. 所有子命令使用同一个 `IMAGE_REGISTRY`、`IMAGE_TAG`、`IMAGE_PLATFORM`。

## 9. 推荐命令示例
本地 kind：

```bash
cd saas
make docker-local-system-rpc IMAGE_REGISTRY=auxsol IMAGE_TAG=dev
make kind-load-system-rpc IMAGE_REGISTRY=auxsol IMAGE_TAG=dev KIND_CLUSTER=auxsol-dev
```

ACK 压测推送到 Harbor：

```bash
GIT_SHA=$(git rev-parse --short HEAD)
HARBOR_REGISTRY=47.114.81.246:1001
HARBOR_PROJECT=auxsol
IMAGE_REGISTRY=${HARBOR_REGISTRY}/${HARBOR_PROJECT}

docker login ${HARBOR_REGISTRY}

cd saas
make push-system-rpc \
  IMAGE_REGISTRY=${IMAGE_REGISTRY} \
  IMAGE_TAG=${GIT_SHA}

make digest-system-rpc \
  IMAGE_REGISTRY=${IMAGE_REGISTRY} \
  IMAGE_TAG=${GIT_SHA}
```

如果 Docker push 时提示 HTTP Harbor 被当成 HTTPS 访问，需要在构建机器的 Docker daemon 配置 insecure registry：

```json
{
  "insecure-registries": ["47.114.81.246:1001"]
}
```

Linux 上通常写入 `/etc/docker/daemon.json` 后重启 Docker：

```bash
sudo systemctl restart docker
```

还需要注意 `docker buildx build --push` 使用的 builder。若当前 buildx builder 使用 `docker-container` driver，builder 容器不一定继承宿主 Docker daemon 的 `insecure-registries` 配置，仍可能把 `47.114.81.246:1001` 当成 HTTPS registry。

先检查当前 builder：

```bash
docker buildx ls
docker buildx inspect --bootstrap
```

本项目优先推荐使用默认 `docker` driver builder，减少 HTTP Harbor 配置差异。Docker 官方文档说明：`docker` driver 是默认 driver，使用 Docker Engine 内置 BuildKit；它不能手工创建，只能由 Docker context 自动创建。

```bash
docker buildx use default
docker buildx inspect --bootstrap
```

如果 `docker buildx ls` 中 `default` 这一行的 driver 是 `docker`，buildx 会走宿主 Docker daemon，通常会使用 `/etc/docker/daemon.json` 中的 `insecure-registries` 配置。验证：

```bash
cat >/tmp/Dockerfile.buildx-check <<'EOF'
FROM busybox:1.36
CMD ["true"]
EOF

docker login 47.114.81.246:1001
docker buildx build \
  --builder default \
```

## 10. 最小下一步
建议下一步只改 `saas/Makefile` 的 `system-rpc` 镜像链路，先跑通一个服务：

1. 增加统一镜像变量。
2. 先补齐 `system-rpc` 的 production 构建目标，例如 `build-pro-saas-rpc-system` 或等价目标。
3. 增加 `docker-local-system-rpc`，并确保它使用 production 二进制和 `deploy/docker/Dockerfile`。
4. 增加 `kind-load-system-rpc`。
5. 增加 `push-system-rpc`，并确保它依赖 production 构建链路。
6. 增加 `digest-system-rpc`，并明确它只在 `push-system-rpc` 成功后执行；如果采用 metadata 方案，则在 `push-system-rpc` 中增加 `--metadata-file`。
7. 保留旧的 `docker-dev-rpc-system` 或 `docker-dev-saas-rpc-system`，标记 `DEPRECATED` 并委托到 `docker-local-system-rpc` 或保留为纯 dev 调试目标。
8. 新建 `deploy/values/kind-dev.yaml`，并引用 `auxsol/system-rpc:dev`。
9. 在 kind 中验证 Pod 可以启动。

完成 `system-rpc` 最小闭环后，再处理 timed / things。timed 不能直接套现有通用 `%` 构建规则，需要先补显式 production build 目标；`things-rpc` 可以使用 `build-pro-iot-rpc-things` 这种路径型 stem，也可以写显式目标提升可读性。确认 production build 目标后，再挂 `docker-local-*`、`kind-load-*`、`push-*`。`protocolSync` 当前阶段不要独立部署，只保留路径大小写和构建链路风险记录；后续确认需要独立部署时，再补显式 production build 目标和对应镜像链路。

这个闭环跑通后，再批量复制到其他当前要独立部署的服务。对应 `push-*` 都可用后，再可选增加 workspace root 的 `push-all` 入口，用一条命令统一推送 ACK 所需镜像：

```bash
make push-all \
  IMAGE_REGISTRY=47.114.81.246:1001/auxsol \
  IMAGE_TAG=$(git rev-parse --short HEAD)
```

# Dockerfile 运行时镜像改造计划
日期：2026-06-01

## 1. 背景
当前 ACK 压测改造已经把镜像命令拆成三类：

1. `docker-dev-*`：调试镜像，使用 `Dockerfile-dev`，可以包含 Delve。
2. `docker-local-*`：本地 Kind 验证用的 production 形态镜像，使用 production Dockerfile，并通过 `--load` 加载到本地 Docker。
3. `push-*`：ACK 压测用的 production 镜像，使用 production Dockerfile，并通过 `--push` 推送到 Harbor。

因此 Dockerfile 也需要明确边界：production Dockerfile 只服务于 Kind/ACK 的真实运行形态；debug Dockerfile 只服务于本地调试或临时隔离排障，不进入正式压测流量。

## 2. 目标
1. 保持 ACK 压测镜像与生产运行形态一致，不包含 Delve、CompileDaemon 或调试编译标志。
2. 明确 `debian:bookworm` 当前可用，但后续优先收敛到 `debian:bookworm-slim`。
3. production 镜像支持稳定信号处理、非 root 运行、证书/时区可用、镜像 tag 可审计。
4. 保留 debug 镜像，但不让 debug 镜像误入 ACK 压测发布链路。
5. 为后续 multi-stage Dockerfile 迁移保留路线，但不把它作为当前 ACK 迁移的第一步。

## 3. 当前 Dockerfile 状态
| 模块 | Dockerfile | 当前用途 | 基础镜像 | 主要特点 | 状态 |
| --- | --- | --- | --- | --- | --- |
| `saas` | `saas/deploy/docker/Dockerfile` | production runtime | `debian:bookworm` | 拷贝 `_build/$SVC-*` 到 `/app`，直接启动 `/app/bin/$SVC` | 当前可用于 `docker-local-*` 和 `push-*` |
| `saas` | `saas/deploy/docker/Dockerfile-dev` | debug runtime | `debian:bookworm` | 额外拷贝 `dlv`、`CompileDaemon`，暴露 `CP` 和 `DP` | 仅用于 `docker-dev-*` |
| `iot` | `iot/deploy/docker/Dockerfile` | production runtime | `debian:bookworm` | 与 `saas` production Dockerfile 基本一致 | 当前可用于 `docker-local-*` 和 `push-*` |
| `iot` | `iot/deploy/docker/Dockerfile-dev` | debug runtime | `debian:bookworm` | 额外拷贝 `dlv`、`CompileDaemon`，暴露 `CP` 和 `DP` | 仅用于 `docker-dev-*`；需检查 `ENV CP=${DP}` 是否为笔误 |
| `iot` | `iot/deploy/docker/Dockerfile-dev-one` | 待确认 | 待确认 | 可能是历史单服务调试 Dockerfile | 需要确认是否保留 |
| `ekuiper-cluster` | `ekuiper-cluster/deploy/docker/Dockerfile-pro-cloudx` | production runtime | `debian:bookworm` | 拷贝 `_build/${PACKAGE_NAME}` 到 `/kuiper`，启动 `kuiperd` | 当前可用于 `docker-local-ekuiper-cloudx` 和 `push-ekuiper-cloudx` |
| `ekuiper-cluster` | `ekuiper-cluster/deploy/docker/Dockerfile-dev-cloudx` | debug runtime | `debian:bookworm` | 额外拷贝 `dlv`，通过 Delve 启动 `kuiperd` | 仅用于 debug |


当前 go-zero 服务的 production Dockerfile 都是单阶段 runtime Dockerfile，不在镜像内部编译 Go 代码，只复制宿主机 `_build/` 目录中的预编译产物。这意味着 `docker-local-*` 和 `push-*` 必须依赖对应的 production build 目标，确保 `_build/` 里已经是 Linux 目标平台的二进制。

## 4. 基础镜像策略
### 4.1 当前阶段
当前阶段建议先保留：

```dockerfile
FROM debian:bookworm
```

理由：

1. 兼容性最好，适合先跑通 Docker Compose 到 Kind，再到 ACK 的迁移链路。
2. 当前 ENTRYPOINT 使用 `/bin/sh -c`，`debian:bookworm` 中默认可用。
3. 证书、时区、本地调试工具链的兼容成本低。

这个选择不是最终优化目标，但适合作为迁移期的稳定基线。

### 4.2 下一阶段
ACK 压测链路跑通后，production Dockerfile 优先切换到：

```dockerfile
FROM debian:bookworm-slim
```

优点：

1. 比 `debian:bookworm` 更小。
2. 仍保留 Debian 兼容性，不会像 distroless / scratch 一样一次性改变排障方式。
3. 与当前复制证书、时区、运行 shell 的方式更容易平滑迁移。

### 4.3 暂不优先 distroless / scratch
distroless 或 scratch 可以作为长期优化，但当前不建议直接切换，原因：

1. 当前镜像入口依赖 `/bin/sh -c`。
2. 需要确认 Go 二进制是否完全静态链接，尤其是 `CGO_ENABLED`、DNS、TLS、时区、证书行为。
3. 容器内临时排障能力会显著下降，对 K8S 新手迁移阶段不友好。

## 5. Production Dockerfile 标准
production Dockerfile 应满足：

1. 不包含 `dlv`、`CompileDaemon`。
2. 不暴露 `DP` 调试端口。
3. 不使用 `Dockerfile-dev`。
4. 使用 production build 产物。
5. 支持 `SVC` 和 `CP` 参数。
6. ENTRYPOINT 能正确处理 K8S 终止信号。
7. 尽量使用非 root 用户运行。
8. 不在镜像内写入真实密钥。

建议模板：

```dockerfile
FROM debian:bookworm-slim AS final

ARG SVC
ARG CP

ENV SVC=${SVC}
ENV CP=${CP}
ENV TZ=Asia/Shanghai

COPY deploy/docker/localtime /etc/localtime
COPY deploy/docker/timezone /etc/timezone
COPY deploy/docker/ca-certificates.crt /etc/ssl/certs/ca-certificates.crt

COPY _build/${SVC}-* /app

RUN useradd --system --uid 10001 --home-dir /app --shell /usr/sbin/nologin appuser \
    && chown -R appuser:appuser /app

WORKDIR /app

EXPOSE ${CP}
VOLUME ["/app/etc", "/app/data", "/app/log"]

USER appuser
ENTRYPOINT ["/bin/sh", "-c", "exec /app/bin/$SVC"]
```

说明：

1. `exec /app/bin/$SVC` 可以让业务进程接收 K8S 发送的终止信号。
2. 如果后续不再需要 shell，可以改为固定二进制入口，但这要求每个服务独立 Dockerfile 或在构建时生成固定入口脚本。
3. `USER appuser` 需要确认业务是否会写 `/app/data`、`/app/log`，以及 ConfigMap/Secret 挂载目录权限是否满足运行要求。

## 6. Debug Dockerfile 标准
debug Dockerfile 可以保留 Delve，但必须和 production 链路隔离。

debug Dockerfile 应满足：

1. 文件名明确为 `Dockerfile-dev` 或 `Dockerfile-debug`。
2. 只被 `docker-dev-*` 调用。
3. 可以暴露 `DP`，但不进入 `docker-local-*` 和 `push-*`。
4. 镜像 tag 必须带 `dev`、`debug` 或 `dlv` 标识。
5. ACK 中如需临时使用，必须部署到独立 namespace，且只通过 `kubectl port-forward` 访问 Delve 端口。

建议命名：

```latex
auxsol/system-rpc:dev-dlv
auxsol/saas-api-gateway:dev-dlv
```

ACK 压测正式流量禁止使用 debug 镜像。

## 8. 分阶段实施计划
### 阶段 A：最小安全修正
目标：不改变基础镜像，不改变构建方式，只修正低风险问题。

| Task | 文件 | 改动 | 验证 |
| --- | --- | --- | --- |
| A1 | `saas/deploy/docker/Dockerfile` | ENTRYPOINT 增加 `exec` | `docker run --rm <image>` 能正常启动；K8S 删除 Pod 时进程能收到 SIGTERM |
| A2 | `iot/deploy/docker/Dockerfile` | ENTRYPOINT 增加 `exec` | 同 A1 |
| A3 | `iot/deploy/docker/Dockerfile-dev` | 修正 `ENV CP=${DP}` 为 `ENV CP=${CP}` | `docker buildx build ... --build-arg CP=8101 --build-arg DP=9101` 输出端口参数正确 |
| A4 | 文档和 Makefile 检查 | 确认 `push-*` 不使用 `Dockerfile-dev` | `make -n push-system-rpc` 不出现 `Dockerfile-dev` 和 `--build-arg DP` |


### 阶段 B：非 root 运行
目标：让 go-zero production 镜像默认非 root 运行。

| Task | 文件 | 改动 | 验证 |
| --- | --- | --- | --- |
| B1 | `saas/deploy/docker/Dockerfile` | 新增 `appuser`，对 `/app` 授权，切换 `USER appuser` | Pod Ready，服务能读取 `/app/etc`，能写 `/app/data` 和 `/app/log` |
| B2 | `iot/deploy/docker/Dockerfile` | 同 B1 | Pod Ready，API/RPC 调用正常 |
| B3 | Helm values | 如使用 `securityContext`，设置 `runAsNonRoot`、`runAsUser`、`runAsGroup` | `kubectl describe pod` 能看到非 root securityContext |
| B4 | eKuiper | 单独评估 `/kuiper/etc`、`/kuiper/data`、`/kuiper/plugins`、`/kuiper/log` 写权限 | eKuiper 规则加载、插件加载、日志写入正常 |


### 阶段 C：切换 slim 基础镜像
目标：在不改变运行行为的前提下减小镜像体积。

| Task | 文件 | 改动 | 验证 |
| --- | --- | --- | --- |
| C1 | `saas/deploy/docker/Dockerfile` | `debian:bookworm` 改为 `debian:bookworm-slim` | `docker image ls` 对比镜像体积，Kind Pod Ready |
| C2 | `iot/deploy/docker/Dockerfile` | 同 C1 | API/RPC 调用正常 |
| C3 | `ekuiper-cluster/deploy/docker/Dockerfile-pro-cloudx` | 评估后再切换 slim | eKuiper 启动、规则、插件、Sink 正常 |
| C4 | 文档 | 记录基础镜像 tag 和 digest | 发布记录中可追踪基础镜像来源 |


### 阶段 D：评估 multi-stage Dockerfile
目标：把 production 编译从宿主机移入 Docker build，减少非 Linux 宿主机交叉编译风险。

当前不是第一优先级。只有在 `build-pro-*`、`docker-local-*`、`push-*` 已经稳定后再做。

评估点：

1. 是否所有服务都能在 Docker builder 中稳定下载 Go module。
2. 是否需要私有 Go module 凭据。
3. 是否需要 build cache。
4. 是否会显著增加 CI 构建时间。
5. 是否可以统一 `GOOS=linux`、`GOARCH=$(TARGETARCH)`。

## 9. 验收清单
| 检查项 | 命令 | 通过标准 |
| --- | --- | --- |
| production Dockerfile 不含 DLV | `rg -n "dlv | CompileDaemon |
| debug Dockerfile 才含 DLV | `rg -n "dlv" saas/deploy/docker/Dockerfile-dev iot/deploy/docker/Dockerfile-dev` | 命中 |

## 10. 推荐执行顺序
1. 先完成 Makefile 镜像链路：`build-pro-*`、`docker-local-*`、`kind-load-*`、`push-*`。
2. 做阶段 A：修正 ENTRYPOINT 和 iot debug Dockerfile 端口变量。
3. 在 Kind 中用 `docker-local-*` 验证 production Dockerfile。
4. 在 ACK 压测环境用 `push-*` 验证 Harbor 拉取和 Pod 启动。
5. 做阶段 B：切非 root。
6. 稳定后做阶段 C：切 `debian:bookworm-slim`。
7. 最后再评估阶段 D：multi-stage Dockerfile。

当前最小下一步：

```latex
saas/deploy/docker/Dockerfile      ENTRYPOINT 增加 exec
iot/deploy/docker/Dockerfile       ENTRYPOINT 增加 exec
iot/deploy/docker/Dockerfile-dev   修正 ENV CP=${DP}
```

这三项风险小、收益明确，适合作为 Dockerfile 改造的第一批变更。

# K8S 探针与 Helm 迁移实施计划
日期：2026-05-29

## 1. 目标
本文给出当前 go-zero 服务从 Docker Compose 迁移到 K8S/ACK 时，补充 `startupProbe`、`readinessProbe`、`livenessProbe` 的具体操作计划。

本计划服务于以下目标：

1. 先让 Helm chart 具备统一探针能力。
2. 第一阶段使用 K8S 原生 `tcpSocket` 探针，避免一开始修改业务代码。
3. 第二阶段为 API Gateway 补 `/healthz`、`/readyz`。
4. 第三阶段为 RPC 服务补 gRPC Health Checking Protocol。
5. 所有改动先在 kind 本地 K8S 验证，再发布到 ACK 压测环境。

## 2. 当前判断
当前框架需要补充 K8S 探针。

原因：

1. Docker Compose 中的 `restart: on-failure` 不能等价迁移到 K8S 服务可用性管理。
2. ACK 中 Service/Endpoints、滚动发布、ALB/NLB 后端健康都依赖 Pod Ready 状态。
3. go-zero API Gateway 是 HTTP 服务，适合后续使用 `/healthz` 和 `/readyz`。
4. go-zero RPC 是 gRPC 服务，适合后续使用 gRPC health probe。
5. 当前服务尚未统一健康检查接口，因此第一阶段应该先用低侵入的 TCP 探针。

## 4. 实施边界
本轮优先做：

1. `deploy/charts/auxsol-services` Helm chart 骨架。
2. `deploy/values/kind-dev.yaml` 本地 kind values。
3. `deploy/values/ack-perf.yaml` ACK 压测 values。
4. Deployment 中统一渲染 `startupProbe`、`readinessProbe`、`livenessProbe`。
5. kind 本地验证 Pod Ready 和 Service Endpoints。

本轮暂不做：

1. 不迁移 EMQX、NATS、TDengine、eKuiper。
2. 不把真实 Secret 写入 Git。
3. 不直接使用 `latest` 镜像。
4. 不在 `livenessProbe` 中检查 RDS、Redis、NATS、下游 RPC。
5. 不手工维护 `helm template` 输出的大 YAML。

## 5. 探针策略
### 5.1 第一阶段：TCP 探针
所有服务第一阶段先使用 `tcpSocket`。

示例：

```yaml
startupProbe:
  tcpSocket:
    port: service
  periodSeconds: 5
  failureThreshold: 30

readinessProbe:
  tcpSocket:
    port: service
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 3

livenessProbe:
  tcpSocket:
    port: service
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 6
```

说明：

1. `startupProbe` 给服务足够启动时间，避免启动慢时被 `livenessProbe` 误杀。
2. `readinessProbe` 控制是否进入 Service Endpoints。
3. `livenessProbe` 只判断进程是否仍能监听端口，不检查外部依赖。
4. `failureThreshold` 不要设置太激进，压测时 CPU 抖动可能导致短暂探测失败。

### 5.2 第二阶段：API HTTP 探针
API Gateway 补充：

| 路径 | 用途 | 检查内容 |
| --- | --- | --- |
| `/healthz` | `livenessProbe` | 进程活着即可 |
| `/readyz` | `readinessProbe` | 服务初始化完成，可以接流量 |


最终 YAML：

```yaml
readinessProbe:
  httpGet:
    path: /readyz
    port: service
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 3

livenessProbe:
  httpGet:
    path: /healthz
    port: service
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 6
```

### 5.3 第三阶段：RPC gRPC 探针
RPC 服务注册 gRPC health service 后，切换为：

```yaml
readinessProbe:
  grpc:
    port: 8002
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 3

livenessProbe:
  grpc:
    port: 8002
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 6
```

不同 RPC 服务将 `8002` 替换成自身端口。

## 13. 排障顺序
Pod 未 Ready 时按下面顺序：

```bash
kubectl get pods -n auxsol-test
kubectl describe pod <pod-name> -n auxsol-test
kubectl logs <pod-name> -n auxsol-test
kubectl logs <pod-name> -n auxsol-test --previous
kubectl get events -n auxsol-test --sort-by=.lastTimestamp
kubectl get endpoints -n auxsol-test
```

常见问题：

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| `ImagePullBackOff` | 镜像 tag 不存在、ACK 无拉取权限、kind 未 load 镜像 | 查 image、ACR 权限、`kind load docker-image` |
| `CrashLoopBackOff` | 配置文件缺失、Secret 缺失、依赖初始化失败 | 看 `logs --previous` |
| `Readiness probe failed` | 端口未监听、启动慢、Service 端口配置错 | 看 `describe pod` 和容器日志 |
| `Liveness probe failed` | 服务卡死或探针太激进 | 先调大阈值，再查服务阻塞原因 |
| Service 无 Endpoints | Pod 未 Ready 或 selector 不匹配 | 查 labels 和 selector |
| RPC `no endpoints` | ServiceAccount 无 endpoints 权限或服务无 Ready Pod | 查 RBAC 和 Endpoints |

## 16. 重要原则
1. `livenessProbe` 不检查数据库、Redis、NATS、下游 RPC。
2. `readinessProbe` 可以比 `livenessProbe` 更严格，但第一阶段先保持简单。
3. `startupProbe` 要覆盖最慢启动时间，避免慢启动服务被误杀。
4. 探针失败阈值不要太激进，压测环境 CPU 抖动是正常现象。
5. ACK 发布使用 `helm upgrade --install`，不要手工改 `helm template` 输出。
6. 真实 Secret 不进 Git。
7. ACK 压测和生产镜像不使用 `latest`。

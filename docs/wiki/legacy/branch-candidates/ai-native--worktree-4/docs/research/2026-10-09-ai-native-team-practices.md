# 菜鸟、天猫 AI 研发实践：小团队可迁移机制与维护成本

研究日期：2026-10-09。范围：全文阅读两份用户 PDF、核读关键图表，并补充三个第一方工程案例；不部署平台、不修改技能、不执行真实 Agent 试验。

结论：值得迁移的是**有边界的执行循环、可恢复的交接、真实产物验收和按需维护上下文**。菜鸟提供交付编排思路，天猫揭示多人、多仓与动态配置造成的上下文缺口；两者都不能证明十人团队需要复制其整套平台。以下瘦身方案以用户已选择的 OpenSpec 为规格和变更唯一来源，只提出待选择、待验证的方案。

## 菜鸟：从编码占比转向端到端交付

| 机制或结论 | 文章证据 | 可迁移的部分与边界 |
| --- | --- | --- |
| AI Coding 贡献率与交付速度分开度量 | p1–3：贡献率按 AI 生成并提交行数占比计算，从约 10% 到 90% 以上；需求变更周期对比只改善约 10% | 行数不是需求完成、质量或组织效率。文章未提供可重算的样本、分组与混杂因素，不能解释为受控实验。 |
| 瓶颈扩展到编码之外与人工交接等待 | p3：编码约占生命周期 30%；托管范围目标至预发部署，必要决策由工程师介入 | 先测等待与返工，再选择自动化环节；不以取消所有人工决策为目标。 |
| Playbook 描述流程，Skill 展开能力，Subagent 隔离上下文，Hook 执行确定脚本 | p4–6：经历固定工作流、自研 Agent、手动串 Skill、巨型 Skill 等尝试后组合这些组件 | 借用分工，不能推断所有固定工作流都不适用；这是该团队在其场景下的取舍。 |
| Playbook 生成 `todo.json`，Executor 循环执行 | p6 及图：选最小序号未完成项；检查前置依赖/文件；恢复上下文；调用 handler；验收产物；更新状态 | 核心是执行器读取并验证状态，不是 JSON 后缀。任务结构、允许写字段和状态迁移需脚本、权限或外部验证实际约束。 |
| 单步有输入、产物、验收与人工等待 | p6–7 图：`precheck`、`gate`、`artifacts`、`waitForHuman`、角色/动作、时间与失败原因；支持 WaitingHuman 和回退 | 可先实现少量阶段。缺依赖必须停在 blocked；人工未答复不是通过；返工后受影响的旧验收需失效。 |
| 可恢复运行与面向工程师的入口 | p7–8：已有需求界面启动、选择仓库、问题式确认、保存产物；Hook 检测任务文件变化并持久化数据库 | 文件、数据库谁有最终状态权必须明确。UI 与摘要可为投影，不能成为第二份可手改的任务真相。 |
| 先选低成本闭环 | p8–9：小、验证成本低、单人能闭环的内部工具和维护需求；自报 2026 年 5 月上线，最近 30 天托管超过 100 个需求 | 数量不等于成功率、无人介入率或节省工时；p9 每日自动找问题、修复、请求合并发布属于理想演进方向。 |
| 用交付而非生成量评价 | p10–11：需求、周期、质量、业务价值与研发体验等视角 | 必须同时看任务大小、返工、失败与维护投入；不能用贡献率替代投入产出。 |

适合小团队的最小复制单位是“一项可验证任务的恢复闭环”：任务引用 → 前置检查 → 有限执行 → 真实验收 → 持久化结果 → 决定下一动作。原文的云沙箱、需求平台 UI、数据库同步可后置；若继续使用现有 LoopX，应由它持有执行状态，不再另外人工维护一份 `todo.json`。（设计建议，依据菜 p6–9。）

天 p1 自报最多涉及 8 个仓库、十多个预发分支；p3 示例地图列 7 个子仓。它们是不同叙述/示例截面，不应拼成精确资产清单。天 p17–18 的“70% 以上有效”“80% 命中”“每周 40 多个真问题”均为作者口径；图示还有 7/10 的小样本。没有统一样本与统计期，不能据此计算稳定精确率，更不能推出召回率、缺陷下降比例或因果收益。

## 文档成本从哪里产生，怎样映射到 OpenSpec

天猫的成本并非“多几个 Markdown”本身，而是每个事实跨多份文档传播、提交触发多项更新、规格叠加优先级、动态配置的时效性，以及哨兵误报的人工裁定。自动生成降低写作成本，不消除语义核对和失效清理成本。（天 p4–12、p17–18。）

下表是本报告的瘦身建议，不是天猫现成方案，也不代表已更改 canonical map-delivery。

| 作者机制 | 单一来源映射 | 维护触发与负责人建议 |
| --- | --- | --- |
| specs / feature / patch / sunset | 现行要求在 `openspec/specs`，候选增删改、设计和任务在 `openspec/changes`；退场在同一 Change 描述兼容与迁移 | 需求/域负责人决定行为语义；交付负责人保证代码和证据对应同一候选。探索未获接受前只作研究材料。 |
| 业务地图、AGENTS | 只保留导航、模块边界、负责人和到 OpenSpec 的链接 | 仅入口/归属改变时更新；不复制需求正文、任务表或进度。 |
| changelog | 优先从合并的 Change、PR 和 Git 生成发布摘要 | 发布时生成；单次提交只有出现必要的新信息才补文字，不强制三份叙事同时改。 |
| architecture | 少量稳定结构说明和必要 ADR；API/schema 等优先由代码生成视图并带来源版本 | 跨模块决策或接口契约变化才更新；不要求每次代码编辑重写架构。 |
| runbook | 只保留确有复用价值的故障、约束与处置步骤 | 出现重复踩坑或必要操作知识时沉淀；普通聊天和临时探索不自动晋升为团队规则。 |
| vendor / wiki | 保留可访问的原文链接、固定版本和必要摘录；团队结论指向来源 | 无稳定来源或离线需要时再保存副本；为引用设负责人和适用范围，避免整库复制。 |
| todo、状态快照、证据 | OpenSpec 持有意图与任务定义；既有运行控制器持有执行状态；证据引用测试/审查产物 | 不手改双份状态；执行事件可投影回用户视图，完成须引用验收，不能只写“完成”。 |
| 跨仓哨兵 | 先在固定候选上跑已有验证和接口集成检查；有剩余问题再加只读语义巡检 | 清单固定各仓 commit、环境/配置版本和验证器版本；保留人工误报裁定，巡检不代替发布批准。 |

小任务可以只有一个 Change 中必要的需求/场景与任务，再链接验证结果；有真实设计分歧、兼容风险或跨仓依赖时才补设计。Review、CI 和批准引用同一版本的输入与候选，不以 OpenSpec 文件存在、校验或归档代替交付授权。需要独立评审时应配置独立上下文及权限；两个 Skill 名称本身不证明独立审查。

## 三个第一方工程实战：各取一个机制

### Stripe Minions：固定检查与有限返工

[Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)（2026-02-19）描述代码定义的 Blueprint：实现/修复节点允许 Agent 决策，lint、push 等节点由确定性代码执行。运行使用隔离开发环境，限制可用工具；CI 最多两轮，之后交回人处理。它自报每周合入超过 1,300 个全由 Minion 产出的、经人审查的 PR，不是本研究验证的效果。

可借：在现有流程中固定验证节点并明确重试上限；先复用已有开发环境与 CI。前提是检查能实际运行、故障能归因。本文未取得 Stripe 完整内部实现，不能因其基于公开 Goose 定制而声称 Minions 已可直接安装复现。

### Anthropic：跨会话恢复和逐项验收

[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)（2025-11-26）用初始化与后续编码阶段、进度文件、Git 历史、逐项功能清单和真实端到端测试来减少跨会话失忆及过早宣告成功。两种角色不等于独立审批身份。

其 [官方示例 README](https://github.com/anthropics/claude-quickstarts/blob/9ec32b91df50b0d4906cae64b13c6298055ff40d/autonomous-coding/README.md) 与 [循环源码](https://github.com/anthropics/claude-quickstarts/blob/9ec32b91df50b0d4906cae64b13c6298055ff40d/autonomous-coding/agent.py) 公开可读：新上下文继续、文件/Git 持久化，并提供 `--max-iterations`。可借恢复时先检查实际环境和已有结果；任务定义仍引用 OpenSpec。证据等级为“公开示例可核读、本次未运行”，不是生产可靠性认证；该子目录 README 的许可栏写为 Internal Anthropic use，不据此承诺可直接商用分发。

### OpenAI：把重复约束写成检查

[Harness engineering](https://openai.com/index/harness-engineering/)（2026-02-11）描述短 AGENTS 导航、版本化知识库、按 worktree 启动应用及观测，以及用 lint/结构测试约束架构、用持续维护处理文档漂移。其约 1,500 个 PR 与“约手工耗时十分之一”是内部团队自报和估算。

可借：将反复出现、可机械判断的规则转成已有 CI 检查，让错误反馈能指导修复；给 Agent 可运行、可观察的环境。其弱化阻塞合并的取舍有特定试验背景，不能外推为 IoT 生产发布规则；也不照搬其文档目录全套。本次没有运行该内部项目。

## 可选的小团队试点：先证明一个闭环

以下仅为实施候选，尚未选择或实现。业务/域负责人确定语义与风险，交付负责人串联候选和证据，Reviewer 验收，控制器只在证据满足规则时推进；小团队可兼任角色，但授权和需要的独立性必须明确。

| 步骤 | 输入与输出 | 通过、退回或停止条件 |
| --- | --- | --- |
| 1. 定界 | OpenSpec Change 链接、验收场景、受影响模块/仓库、风险、负责人 | 范围、依赖或验收不清则澄清；先选低风险且结果能独立验证的一项。 |
| 2. 准备 | 固定各仓 base/head、所用规格版本、环境/配置、可运行验证入口 | 缺依赖/凭据/环境则 blocked 并指明解除条件；不能把“计划运行”记成已验证。 |
| 3. 执行 | Agent 只在本次任务范围修改；记录产物、执行时间与退出原因 | 发现越界或需求变动交回负责人；限制轮数、时间/费用，避免无限修复。 |
| 4. 验收与返工 | 运行验证器；Reviewer 看相同候选及输入版本，返回 findings 与 next-action | 失败按 findings 返工；候选或输入变化令受影响验收失效；审批绑定版本，不以聊天“同意”漂移复用。 |
| 5. 交接与集成 | 留下当前结果、真实证据、剩余问题、恢复入口；按项目既有规则进入 PR/集成/发布 | 换新会话能恢复且识别 stale/blocked 才算闭环；通过本地测试不等于远端合并或部署。 |

一个可讨论的预算示例：同一失败最多自动修复两轮，之后请求负责人决定改范围、补环境或停止；具体值由试点选择，不能从 Stripe 的上限推成行业标准。恢复时至少校验输入与产物摘要、阶段、验证结果及待处理事项，不能只恢复最后一句聊天。（综合菜 p6–9、Stripe 与 Anthropic 的机制提出。）

试点记录工作时间、等待时间、返工时间、验证失败、必要决策与故障性人工介入，并记录文档维护时间和最终质量；按相近任务比较完成周期，不把生成行数或零人工当胜负。若维护耗时持续超过减少的等待/返工，或无法可靠复现、区分候选，应先缩减流程再扩展。上述指标与停止点是本报告建议，尚无 A/B 结果。

# Ming IoT 团队开发与文档治理提纲

**2026-10-16 入口收敛：** 本提纲保留详细设计讨论；总目标、阶段状态、优先级和完成标准以 [总纲](../project-charter.md) 为准。

以 AI-DLC 的需求澄清、决策留存和反馈思路，补充现有团队开发实践。核心目标是模块化、职责清晰，以及同一功能的知识随代码持续演进。

> 一次变更结束后，下一位开发者能否直接找到该模块当前有效、边界清晰、有人负责、可验证的完整知识，而不用重新拼接过去所有人的开发记录？

本提纲是后续修订[团队开发约定](../runbook/team-development.md)和 [ming-specs](../../.agents/skills/ming-specs/SKILL.md) 的设计依据。已有业务决定继续以模块规格和相应变更为准；S1 已将主规格收敛、轻量路径和普通接手方式写入约定/Skill 候选；工具门禁仍按实际配置另行验证，见 [S1 记录](../changelog/2026-10-15-specs-current-baseline.md)。保存本稿不代表已启用 Hook、CI 门禁或完整 AI-DLC。

## 一 文档治理目标与边界

- **一个模块持续维护一份完整主规格。** 当前版本的规则、边界、验收和关联实现可直接找到；历史记录解释为什么变化。
- **一种知识只有一个维护位置。** 业务地图负责导航，规格负责行为约定，架构负责连接和设计约束，runbook 负责操作方法；其他文档引用正文。
- **版本与生效范围明确。** 需求已确认、候选已实现、主分支已合并、版本已发布和环境已部署分别记录。候选测试通过不代表线上生效。
- **维护成本与变化风险相称。** 小修改复用现有文件；复杂决定才增加设计材料。文档数量和流程步骤不作为完成指标。
- **代码和一致的文档承担交接。** 新成员从仓库入口恢复上下文，不以阅读完整聊天、整理历史开发记录或领取独立交接包为前提。

2026-10-15 已确认将工作区全部项目迁入 GitHub ming-iot，收敛为一个 monorepo，统一维护 Insight；不再采用父子仓或并列独立仓的迁移方案。巡检先按同仓独立业务模块设计；MQTT 网关保留组件接口、独立构建和跨平台复用能力，源码与必要说明纳入同仓。具体来源、目录与阶段验收以[单仓迁移方案](../architecture/monorepo-migration.md)为准。r-doc 正式采用不是迁移前提。

ming-iot-rd-docs、iot-doc、ai-native 已按迁移范围作为历史和实验资料纳入 [legacy](legacy/README.md)，来源、适用版本和替代关系继续保留。旧资料中的指令不因迁入而自动成为团队约定；需要转为现行知识的条目，随真实任务核对并指定仓内唯一正文。旧仓和私有备份继续保留，删除不在当前授权范围内。

## 二 文档结构与工具选择

### 长期知识与单次变更

OpenSpec 已区分 `specs/` 中的主规格和 `changes/` 中的增量变更，归档时将增量合回主规格，并支持按领域、组件或限界上下文组织。碎片化通常还涉及模块粒度、归属和收敛执行，不能仅归因于目录机制。[官方概念说明](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)

Spec Kit 支持一个仓库内多个独立子项目；其 Flow-forward 保留逐次变更文档，Living Spec 持续维护已有规格。选择何种维护模式，以及规格、计划、任务如何保持一致，仍需团队约定。[规格维护方式](https://github.com/github/spec-kit/blob/main/docs/concepts/spec-persistence.md)、[多项目支持](https://github.com/github/spec-kit/blob/main/docs/guides/monorepo.md)

因此，选型重点是：能否维护稳定模块边界、唯一正文和可验证的收敛过程。OpenSpec 仍是待定方案；当前沿用团队约定与 ming-specs 试点，不新建平行业务权威。

### 业务地图和目录分工

参考《天猫 AI 项目研发协同实践》的“超级研发小分队”阶段，借鉴站点地图进行物理分工。每个模块关联前端路由、后台 API、数据与事件契约、代码和规格范围。IoT 的设备接入、遥测、OTA、任务调度等能力即使没有页面，也要进入业务地图。

| 目录 | 持续维护的内容 |
| --- | --- |
| `docs/specs/` | 业务地图、模块入口、当前规格及在途变更 |
| `docs/changelog/` | 计划、评审、证据和演进时间线的导航 |
| `docs/architecture/` | 系统连接、共享契约、重要设计决定及权威来源 |
| `docs/runbook/` | 操作知识、团队接入、排障与验证方法 |
| `docs/vendor/` | 外部材料来源、固定版本和许可证记录 |
| `docs/wiki/` | 人工中文知识、讨论和未转为正式承诺的探索 |
| `docs/wiki/legacy/rd/` | 旧研发仓迁入的历史内容；显式标记适用性 |

这是目标分工，不要求一次创建全部目录。模块的最小维护单元为：

```text
docs/specs/<业务域>/<模块>/
├── README.md                  # 边界、负责人、代码与验证入口
├── spec.md                    # 对应版本完整的行为约定
└── patches/<变更ID>/change.md  # 本次差异、决定和证据引用
```

原始需求需要保留时使用 `raw.md` 或可追溯来源，原话只追加，AI 的解释单独标识。复杂技术方案再增加设计文档；不强制每个模块都准备一套空模板。

## 三 模块认领与职责

认领记录可放在现有 Issue、PR 或 Change 中，至少说明模块、实施者、需求与模块责任人、本次代码/规格写范围、共享影响和完成条件。长期负责人尚未明确时标记缺口，不把 AI 或临时接手者自动设为负责人。

同一条款或共享契约的并行变更要协调顺序，合并后来的候选时重新核对当前基线。目录隔离只能减少文件冲突，不能消除语义冲突。允许跨模块阅读；扩大修改范围时需确认责任边界。

| 责任方 | 主要责任 |
| --- | --- |
| 人 | 确认业务取舍、模块边界、共享契约、风险接受和验收；已有明确授权无需逐阶段重复确认 |
| AI | 读取受影响上下文，提出缺口，起草规格与方案，实施、验证并报告代码和规格差异 |
| Skill | 指引何时读什么、怎样分类和收敛、交付哪些必要结果；个人可选择适合的开发方法 |
| 工具与 CI | 检查可判定的结构、引用、范围、版本、lint 和测试结果；配置后执行合并限制 |
| 评审者 | 检查业务规则、实现和验证是否一致；不能只复述实施者或 AI 的“已完成”结论 |

## 四 四种变更类型与小修改处理

### 四种类型决定知识归属

| 类型 | 用途 | 完成后知识去向 |
| --- | --- | --- |
| feature | 新业务能力或新模块 | 建立长期模块入口和主规格 |
| patch | 既有能力演进、缺陷修复或内部调整 | 行为变化合回主规格；实现修正保留原规则及回归证据 |
| sunset | 功能退出、替代和迁移 | 保留兼容期、退出条件、替代入口和适用版本 |
| blueprint | 尚未确定的业务或技术探索 | 保留结论；有正式开发承诺后关联到 feature 或 patch |

bugfix、重构是任务性质，可以作为 patch 的原因标签，不新增第五种规格类型。类型也不是要求所有任务都执行的四个阶段。

### 风险和不确定性决定流程深度

小修改先区分“恢复/保持现行规则”和“改变规则”，再独立检查权限、数据、兼容与共享影响。具体改哪些文件、谁确认、怎样验证、何时完成，统一维护在[团队约定的小修改处理步骤](../runbook/team-development.md#small-changes)，本提纲不另存一套操作规则。

此处借鉴 AI-DLC 按任务选择流程的思路，不照搬完整阶段和审批数量。当前官方提供 Bugfix、Refactor、Feature 等不同路径。[工作流说明](https://awslabs.github.io/aidlc-workflows/guide/workflow-profiles/)

不按代码行数判断“小修改”；一行权限或兼容性变化也可能需要深入验证。Skill 可以建议路径，已有项目要求仍然适用。长程任务由 LoopX 管理执行状态，普通 Patch 不强制走完整长程流程，也不再新增一份 `aidlc-state.md` 维护相同状态。

## 五 实施前澄清与决定留存

实施前先定位受影响模块的规格、代码、调用方和测试。只补齐本次需要的上下文，不把每次小修都变成全库逆向工程。

能够开始实现的最小条件：明确谁在什么条件下得到什么结果、旧/新行为差异、必须保持的不变项、影响边界以及可检查的验收例子。将已知事实、推测和未决问题分开；只暂停依赖未决问题的部分。

把任务切成可验证的业务增量。例如“手动触发时优先显示昵称，其他触发方式保持不变”，而非笼统的“优化通知系统”。每个增量应能关联规则、实现和验证。

人的关键选择在原 Change 或 Issue 中保留决定、理由、影响条款及来源；后续用新决定替代旧决定，不重写历史。已有明确回答可以引用，不重复签字。不强制保存全量聊天、独立问题文件和每阶段批准文件；Git 作者姓名、邮箱不能替代真实确认依据。

## 六 变化传播与主规格收敛

### 先判断变化性质

| 发现的变化 | 应更新的内容 |
| --- | --- |
| 已确认的业务行为变化 | 主规格候选、验收、相关测试及受影响的技术方案 |
| 行为不变的实现方式变化 | 必要的架构、技术方案或 runbook；不制造需求变更 |
| 实现违反当前规则 | 修复代码和回归测试；保留正确的业务规则 |
| 规格冲突、缺漏或过时 | 标明冲突和影响，请责任人决定；AI 不自动选择有利于现有代码的解释 |

代码到 spec 的反向检查产出的是差异提醒。不能因代码已写完，自动把主规格改成与代码一致。

### Patch 双向指针和收敛时点

Patch 指向所属模块、基线版本和受影响条款；模块入口列出适用的在途 Patch。主规格吸收变化后，Patch 标明已吸收的位置和对应版本，模块入口把它移入历史导航。

《天猫 AI 项目研发协同实践》允许主规格在稳定后收敛。本项目拟采用更明确的完成条件：**变更合并前，将已接受的行为整理为候选分支内完整的主规格，与实现一起评审和合并。** 已确认但未合并的候选继续标明适用分支或版本，不提前宣称主分支、发布版或生产环境已生效。

合并后，读者以该版本主规格为当前入口，不需叠加全部历史 Patch。Patch 保留差异、原因和证据，用于追溯；未完成的 Patch 继续列为候选。多个补丁冲突时先解决语义和适用顺序，再合并。

“完整”指当前行为、边界、异常与验收足够独立理解，允许链接唯一的共享契约或架构说明，不要求将整个系统文档复制进一个文件。

## 七 文档检测与归档

借鉴 [r-doc 的文档治理方式](https://github.com/riesaexe/r-doc/blob/bc23420d7df5ec1d2c5fb45e066c919790ab9cf9/skills/r-doc/SKILL.md)，采用“检测 → 收敛 → 归档”。r-doc 继续作为实验参考，结构检查通过不能证明业务规则正确。

检测分为三个层次：

1. **结构检查：** 模块入口、状态、引用可读、双向指针、版本关系和归属有效；不靠修改日期自动判定内容有效。
2. **差异审查：** 从代码差异定位受影响规则，判断是否应修改规格、测试、架构或 runbook。无规格变化时给出依据；AI 提醒由评审者核对。
3. **归档检查：** 已接受的行为已经进入主规格，未决项被保留或明确取消，验证证据绑定实际候选，旧入口有替代指向。历史内容不再参与默认当前知识检索。

提交时先检查暂存差异；PR 阶段检查完整候选差异和最终版本。局部 Hook 可以提前提醒，但不能替代服务端必需检查。工具无法判断的语义问题进入评审，不用“文件存在”或“已更新日期”代替验收。

历史实验材料先标注来源与适用性，再提取有效知识，最后归档或删除冗余入口。没有确认替代正文和必要追溯关系前，不仅按“旧”批量删除。

## 八 Review

### 性能与运行风险

结合实际改动检查查询放大、循环调用、缓存失效、并发与资源释放、超时重试、幂等和消息堆积。涉及热点路径或容量承诺时使用代表性数据与负载验证；普通文档修改无需运行性能测试。记录测试条件，不能把静态推断写成压测结论。

### lint 与确定性检查

复用仓库现有格式、lint、构建、类型/静态检查和适用的验证档位。失败、未运行和通过分别记录；不通过删除断言、缩小既定范围或跳过失败获得绿色。合并限制是否生效，以实际服务端配置为准。

### 与 spec 是否一致

逐项检查已确认规则是否实现，不变项是否保留，异常、权限、兼容与边界是否覆盖。区分“实现未达到规格”和“规格需要业务决定”，两者处理方向不同。评审绑定实际候选版本；候选变化后补验受影响范围。

### 测试本身是否有效

- 期望结果来自已确认规则，而不是照抄当前实现。
- 覆盖关键反例、边界和不应变化的行为，而不仅是成功路径。
- 兼容性输入来自旧版本真实格式或协议样本。
- 缺陷回归能在有缺陷的版本失败，并在修复后通过；检查是否只验证“没报错”。
- 单元、静态、集成、真实通道和业务验收分别说明，不能相互替代。

属性测试、模糊测试和变异测试按风险引入。属性测试依赖正确的性质、断言和输入范围，随机输入本身不能防止错误预期或弱断言造成假通过。[Hypothesis 官方说明](https://hypothesis.readthedocs.io/en/latest/)

## 九 缺陷反馈与日常交接

修复结束时判断知识缺口属于哪里：实现违反规则、规则缺失、跨模块契约、环境/配置/部署，还是验证不足。将结论写回对应规格、测试、architecture 或 runbook；普通缺陷在原 Issue/PR 留存即可，重大或反复发生的故障再单独复盘。

交接默认提供仓库入口、明确版本、当前待办和验证方法，结果留在原 Issue/PR/CI。开发者应能从模块入口直接找到当前规则、边界、实现和验收。独立交接包仅用于离线、跨权限或特定外部交付场景，不作为日常必填产物。

如果接手者仍需追问历史聊天才能理解规则，应先修复入口、主规格或验证方法；不要用越来越长的交接摘要掩盖长期知识缺口。

## 十 用真实案例验证收益与维护成本

沿用[通知触发人展示试跑](../changelog/2026-10-14-ming-specs-handoff-pilot.md)及其[后续验证记录](../changelog/2026-10-14-ming-specs-continuation.md)。当前规则入口已收敛为[通知主规格 current-v1](../specs/saas/notification-trigger/spec.md)，原 Patch 与回执保留历史；这里仅说明如何验证治理方法。

已确认的变化仅作用于手动触发的昵称优先显示；其他触发方式保持原行为。此前独立评审发现“旧格式”测试错误使用昵称，漏掉真实旧账号行，说明测试通过仍可能遗漏兼容规则。该缺口最终回到原验收要求、实现和真实旧格式回归用例，而非改写需求来适应代码。

后续观察重点：

| 观察项 | 有效证据 |
| --- | --- |
| 找到当前知识 | 不看聊天即可定位规则、版本、负责人和验收入口 |
| 连续演进 | 同一规则再次变化后主规格仍完整，旧结论可追溯且不会被误当现行规则 |
| 人员交接 | 接手者能复述不变项并验证，疑问和缺漏回到仓库正文 |
| 发现差异 | 提醒能抓到真实漏改，同时记录误报和人工处理成本 |
| 维护成本 | 区分首次建体系、日常修改、工具等待与返工；记录重复字段和不必要文件 |

小黄验证当前昵称显示候选的任务已于 2026-10-15 按用户要求停止并废弃，未取得真人验收结果。AI 接收演练保留原结论，不能用工具 PASS、AI 演练或任务取消代替团队收益证据。当前接续见 [M5 记录](../changelog/2026-10-15-m5-cutover.md)。

先修订团队约定和 ming-specs 的过时条款，再用真实调整验证；只有反复出现且可确定判定的检查才升级为强制门禁。薄适配、继续 fork 或逐步自建的选择，取决于发现问题的收益、误报、执行时间和持续维护成本。

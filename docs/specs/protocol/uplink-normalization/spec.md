Feature：`protocol.uplink-normalization`；能力域：[protocol](../README.md)；[责任、认领与接手入口](README.md)。

本文件是本 Feature 唯一的当前设计正文，**尚未实施或生效**。原始目标、澄清、人的真实答复与知识归属纠正在本模块 [raw.md](raw.md)；[模块入口](README.md)集中说明责任与接手顺序。0.2.1-draft 修正需求来源归属，保留 0.2.0-draft 的业务规则与技术候选。理解本功能无需拼接其他模块的历史 Patch；跨模块协作见 PA-UP-DEPENDENCIES。

<a id="PA-UP-SCOPE"></a>
## PA-UP-SCOPE：目标、责任与首版切片

链路为 **设备 → Access Adapter → ProtocolApplication / Codec → Canonical Kafka（持久接受）→ DM（业务完成）**。箭头是责任流，不代表每个框都独立部署。

首个纵向切片是电表属性上报，支持客户 payload 解码及标准协议直接校验转发。上行事件、命令回执必须分类，接入尚未实现的下游类型时明确拒绝或交给已声明处理者，不能写入无人消费的 topic 后承诺完成。下行编码、任意代码上传、历史原报文重算及旧消息导入不在首版。

| 责任方 | 负责什么 | 不混入的责任 |
| --- | --- | --- |
| Access Adapter | 连接认证、可信租户/网关绑定、接收时刻、协议应答与重投能力声明 | 不以 MQTT PUBACK 或收到字节代表平台持久接受 |
| PA 框架 | 固定版本选择、输入限额、Codec 执行、输出校验、批量结果、持久接受与结果查询 | 不自行修改业务最新值、计费或执行设备命令 |
| Codec | 根据受控配置解释原始格式，产生确定的类型化条目 | 不读可变业务状态，不写业务库，不发送设备命令；DM 的 EpChange 留在 DM |
| Eventbus | 公共信封、Kafka 提交/消费完成接口、通道资源与恢复基础 | 不替协议决定 ACK 含义，不以缓存切片证明设备链已通过 |
| DM | 再验领域归属/模型、业务去重、历史及最新值、可靠安排副作用、处理状态 | 不把消费位点已提交当作所有业务效果已经成功 |

<a id="PA-UP-INPUT"></a>
## PA-UP-INPUT：接入与版本契约

以下字段为逻辑契约，最终语言类型和序列化方案在实施评审冻结；传入字段不等于可信字段。

| 字段组 | 来源与校验规则 |
| --- | --- |
| `tenantId / principalId / ingressDevice` | Access 认证上下文生成；拒绝 payload 覆盖租户。目标子设备须通过受信绑定校验；同租户也不能任意冒充其他设备 |
| `protocolProfile / ackMode` | 受控配置；说明编码、消息类别识别方式、编号规则、逐项或整包应答、应答阶段及重投期限，不能由每包自选更宽松模式 |
| `sourceEpoch / reportId` | 设备或网关稳定提供并由 profile 验证；重发/重连不变。若计数重启或回绕必须有稳定的 epoch 区分新报告；不能在每次连接时随机换 epoch |
| `receivedAt / payloadBytes / payloadDigest` | Access 记录平台 UTC 接收时刻、字节长度与原始字节摘要；限制大小。摘要用于同身份内容冲突检测，不取代报告身份，也不承诺保存原文 |
| `codecArtifact / mappingVersion / modelVersion / bindingRevision` | 从受控不可变配置取得；记录版本及内容摘要。第一次处理锁定解释版本；已接受重投返回原结果，不按最新版本重算 |
| `traceId / connectionId` | 诊断相关信息；连接变化不能改变业务去重身份；不得把认证密钥写入消息或日志 |

父包身份 `reportKey` 由长度明确的元组 `(tenantId, ingressDevice, sourceEpoch, reportId)` 唯一确定。子项 `itemId` 必须在父包内唯一且重投不变，不能直接把设备内局部编号当作父包内编号。profile 将受信目标设备、消息类型、协议局部编号及必要的采样/条目区分量组合成无歧义标识；协议没有局部编号时，才使用 profile 明确且重投保持不变的条目位置。两个设备各自的 `itemId=1` 必须展开为不同标识，同设备多采样也须可区分。PA 在提交前校验全包唯一性；仍有碰撞时整包 `ITEM_ID_COLLISION` 拒绝，不生成无法一一对应的部分结果清单。子项身份为父包身份加最终 itemId，不能用当前接收时间、Kafka offset 或 Codec 版本生成新业务身份。修正内容必须使用新 reportId，并显式关联原报告，不允许同编号静默覆盖。

接入校验父包与子设备归属；DM 在消费时再次验证。解绑或模型变更发生在接受之后时，允许产生可见的业务失败，不抹掉原接受事实，也不把失败数据错误归到新租户。

<a id="PA-UP-DECODE"></a>
## PA-UP-DECODE：Canonical 与结果清单

标准输入走同一身份、schema、接受边界，跳过客户 Codec；客户输入只解码一次。输出条目原子单元由 profile 冻结，建议为“一个设备、一个采样时间、一种消息类型”；同一条目的必需属性不因局部字段错误被静默删掉。Codec 不得返回只有成功项、没有失败项定位的模糊列表。

| Canonical 字段 | 候选含义 |
| --- | --- |
| `eventId / type / schemaMajor / source` | eventId 从稳定子项身份确定；type 区分属性、设备事件、命令结果。沿用公共信封字段语义，但须扩展 Eventbus 类型注册后才可用 |
| `scope / tenantId / object` | 首个切片固定 tenant；object 是受信目标设备标识，不采用 payload 自报的系统范围 |
| `occurredAt / receivedAt / timeQuality` | 设备采样时间、平台首次接收时间及时间可信度分开；UTC 毫秒精度。不得用接收时间掩盖设备时间缺失，时钟异常不能推高最新值水位 |
| `correlationId / causationId / reportKey / itemId` | 追踪父子关系；追踪 ID 不代替去重 ID，命令回执保留原 commandId，不能生成一次新的执行请求 |
| `codecArtifact / mappingVersion / modelVersion` | 固定此次解释依据；接受后保留在 Canonical 与清单中，修复 Codec 不自动重算旧数据 |
| `payloadSchema / payload` | 版本化的类型专用结构。属性含设备、采样时间、属性代码和值；单位和精度按固定模型约束，不把所有消息强制塞进同一 payload |

示意映射（非已实现 wire fixture）：`T-DEMO / GW-1 / epoch-A / report-42 / meter-1` → `M-001` 的属性 `{Ep: 120.8, Ua: 235.6}`。Codec 给出累计电量；DM 根据时序与业务规则决定是否更新最新值及计算差值。现有 `msgToken` 只有经真实设备重发试验后才可映射为 reportId。

PA 框架生成 `AcceptanceManifest`：父包身份、原字节摘要、解释版本、应答模式、完整 itemId 列表、每项目标/type/eventId/结果与错误码、应答模板版本、接受时刻。成功项指向提交的 Canonical；失败项也要定位。`acceptedAt` 是提交记录中的接受时刻，不是仅凭字段存在就可确认事务成功。清单是重投应答依据，业务完成状态由 DM 另行维护。

合法零输出只允许 profile 明确的非数据消息，例如转入独立心跳处理者；报告类请求解析成空列表属于错误。非数据消息完成自身处理可回协议规定的结果，但不能伪造“已接受属性数据”。

<a id="PA-UP-ACCEPT"></a>
## PA-UP-ACCEPT：持久接受、应答与业务完成

### 三种确认不能混用

| 层次 | 能确认什么 | 不能确认什么 |
| --- | --- | --- |
| 传输 ACK（如 MQTT PUBACK） | 当前传输端点按其协议收到消息 | PA 已解码、Canonical 已持久化或 DM 已落库 |
| 应用接受 ACK | 完整清单和全部被选接受项已成功持久提交，平台承担已接受数据的补处理责任 | DM 已通过领域校验、外部通知或设备动作已完成 |
| 业务结果 | DM 完成了已声明的业务写入及可靠副作用安排；失败同样可查询 | 外部发送或物理执行结果，除非另有独立完成凭据 |

协议 profile 必须说明现有 success 表示哪层。保留既有“业务完成”应答语义的协议，仍在 DM 完成后回答；若新增“已接受/处理中”，须有设备可识别的码或版本，不能复用旧成功码偷换含义。设备只懂整包成功并不意味着必须在接受阶段应答；批量策略与应答阶段是两个独立配置。

### 候选提交顺序

1. 完成可信身份、大小、受控版本和重复身份检查；确定性校验失败不进入成功提交。
2. 串行处理同一 reportKey，持有带 fencing 的处理所有权。双实例接管先恢复该身份的已提交结果/未决事务；不能因结果查询暂时落后就判定不存在并重新接受。所有权、状态恢复与 lookup 的实现需专门验证。
3. 解码、校验全部条目，再按 PA-D1 选出接受集合。仅整包 ACK 时，任一项失败则接受集合为空；逐项 ACK 时可保留合法项。
4. 候选采用 Kafka producer 事务把接受集合与完整 AcceptanceManifest 一起提交，下游及结果查询使用 `read_committed`；提交成功后才回接受 ACK。无成功项的拒绝结果也保存有界结果记录，以便相同重投取得相同判定。不可恢复的认证失败只记录脱敏审计，不给未授权调用方查询其他设备结果。
5. 提交超时/连接断开时返回或内部记录 `UNKNOWN`，不能宣称拒绝或成功；调用方查询/重发时保持原身份与原内容。恢复必须先确认原事务终态；已提交则重放原清单，已中止且从未接受才能按锁定版本重试。
6. DM 消费 Canonical 时，以稳定 eventId 去重并可靠记录领域结果与副作用安排。崩溃恢复不得重复追加历史、计算差值、计费或发告警。随后才提交该分区已连续完成的位置；失败项后面的成功项不能导致跳过未完成项。

Kafka 的 producer 幂等不代替应用重投去重；事务提交不等于数据库/时序库/外部效果的全链恰好一次。[Kafka 3.8 producer 配置](https://kafka.apache.org/38/configuration/producer-configs/)与[consumer 隔离配置](https://kafka.apache.org/38/configuration/consumer-configs/)作为机制参考，具体客户端、Broker 和恢复实现仍须核对。`read_committed` 可能被未终结事务阻挡，因此事务大小、时长与清单分区布局须纳入隔离测试。

DM 若涉及关系库、时序库及事件发布，不能把它们当成一个数据库事务：候选采用持久处理日志、可幂等的时序写入键及事务内副作用待办；只有已声明写入完成才标 `APPLIED`，仅可靠接管时为 `PENDING`。只有恢复责任已持久移交才可提交输入位置；普通内存队列、日志或一次异步调用不算移交。具体落库与发件箱接线属于实施前缺口。

<a id="PA-UP-FAILURE"></a>
## PA-UP-FAILURE：批量策略与失败处置

### 批量及状态

| 情况 | 接受结果及重投规则 |
| --- | --- |
| 10 块电表，9 项合法，1 项格式错；协议支持逐项应答 | 提交 9 项与包含全部 10 项的清单，返回 `PARTIAL` 和逐项结果；相同包重发返回原清单，9 项不重复处理；修正包只携带失败项，不把已接受项换新编号再次作为新观测提交 |
| 同样的包；协议只支持整包应答 | 整包校验失败，0 项持久接受；不能先提交 9 项再回整包失败。修正内容用新报告编号 |
| 全部合法 | 全部选中项与清单一起提交成功后为 `ACCEPTED`；是否立即应答仍取决于 profile 的应答阶段 |
| 持久提交结果未知 | `UNKNOWN` 是观察状态，不是已拒绝；先恢复原事务结果，不用新编号掩盖不确定性 |

“整包接受”只保证 Canonical 接受集合的原子可见性，不保证十块电表所有下游业务操作原子完成。业务状态单独为 `PENDING / APPLIED / FAILED`，逐项可追踪；不能把已接受后的一项 DM 失败反写成“整包从未收到”。不具备业务失败可见入口的 profile 不能完成首个试点验收。

| 故障点/类型 | 对外或记录状态 | 处理与恢复边界 |
| --- | --- | --- |
| 认证/子设备归属不合法 | `REJECTED`，脱敏原因 | 不产生越权 Canonical，不泄露其他租户是否存在；先身份校验再重复结果查询 |
| 原始输入格式错误、输出 schema 错、确定性版本不支持 | `REJECTED` 或逐项失败 | 不无限重试相同坏数据；保存错误码、身份摘要、版本和位置。修正输入使用新编号，关联原报告 |
| Codec 超时、崩溃或超限 | 未接受，临时失败或适配器故障 | 有界重试/隔离实例，不能空结果当成功；未持久接受的原 payload 仍依赖上游重投 |
| 依赖临时不可用且确定尚未提交 | 未接受，可重试 | 退避并保持原身份；队列满实行背压，不回成功；不静默丢数据 |
| 提交不确定、接受 ACK 丢失、实例重启 | `UNKNOWN` 或重放已接受清单 | 按 PA-UP-ACCEPT 恢复；应用重发不再次生成业务效果，不能承诺还原未保存原报文 |
| 已接受，DM/存储临时不可用 | `PENDING` | 从持久 Canonical 或已可靠移交的工作记录补处理；监测积压与恢复窗口，不降级为成功 |
| 已接受，DM 发现模型/绑定冲突等持久错误 | `FAILED`，可见的处理失败 | 持久隔离 Canonical、错误和版本，管理员修复后受控重试，eventId 不变；保留原失败记录。不能仅写日志后提交位点 |
| 同 reportKey 内容摘要不同 | `IDENTITY_CONFLICT` | 不覆盖原清单、不新执行；指引产生新报告身份。摘要变化不能被当成另一个隐式版本 |
| 设备命令回执解析或关联失败 | 回执专用失败记录 | 保留 commandId 和异常，不改写为遥测，不自动重发设备命令 |

接受前失败记录仅含脱敏元数据和定位信息，默认不长期保存原 payload；接受后隔离保存的是标准 Canonical。两者都不构成原报文补算承诺。建议在现有设备诊断/管理员处理入口展示报告身份、接受状态与业务状态，不在本轮另建产品页面。

保留窗口、负载和处置预算需在试点 profile 中量化：原始包/条目上限、执行与提交超时、重试上限、设备最大离线重投期、去重与清单保存期、Kafka 保留期、隔离处置期限及管理员责任人。清单/去重期应覆盖允许重投期与恢复余量；Canonical 保留期须覆盖允许故障积压和恢复时间。临近上限告警并由人处理，未处理数据不得仅因到期静默丢失。超出窗口的输入须拒绝或进入人工判定，不能无记忆地当新报告执行。本轮不设生产 SLA、不配置自动删除或实际 TTL。

<a id="PA-UP-ORDER"></a>
## PA-UP-ORDER：去重、顺序与迟到数据

同设备同消息通道建议用 `(tenantId, productId, deviceId)` 分区键，业务去重在 DM 持久保存，不能只靠进程内缓存。Kafka 分区顺序是到达/提交顺序，不是设备采样时间顺序；不同 topic 不承诺全局顺序。报告身份和设备采样时间各司其职。

PA-D3 要求 DM 使用每设备、每属性的已应用时间水位：较旧的合法读数写历史，不更新最新值，不触发实时告警、控制及实时差值计算。一次事件首次迟到与相同 eventId 重投要分别识别，前者只补历史，后者不再写一份历史。同采样时刻不同值、时间缺失/异常进入冲突或质量待判定，不任意用到达顺序覆盖最新值。设备时钟回拨、计数器复位以及迟到事件/命令回执须按各类型规则处理；**命令回执不能因晚于遥测水位就被丢弃**。

对于电表 Ep：昨天 100、今天 120 已入库后补来昨天 105，只补历史；不把最新值降为 105，不生成负实时能耗，不重跑实时动作。历史区间能耗是否重算、计数器清零如何解释是 DM 后续业务规格，不由 Codec 猜测。本轮不声称已有脚本满足该规则。

<a id="PA-UP-ISOLATION"></a>
## PA-UP-ISOLATION：资源隔离与部署候选

D12 要求遥测积压时回执和重要补处理仍独立推进。最早可行分类点须来自受信 topic/端点或有界最小解析；若必须完整解码才知道类型，应给混合包有界处理配额，不能让无限遥测占满回执资源。解码池、待提交队列、生产事务/清单分区和消费者分别检查阻塞，单纯拆 topic 不算通过。

建议先按协议 profile 分配受控版本的执行单元，限制 CPU、内存、时间与并发；不能证明可取消/可隔离的脚本用进程隔离，不能把 goroutine timeout 当作终止失控代码。独立 PA worker 是技术候选，不要求每客户部署一个服务。最终部署、分类边界与可量化故障预算尚待所选协议和验证环境确认；不承诺任意超载下可用。

<a id="pa-raw-002"></a>
## PA-RAW-002：上行范围、交付方式与持久化选择（用户，2026-10-17）

| 问题与上下文 | 用户原答 | 解释边界 |
| --- | --- | --- |
| PA-Q1：原报文先持久化再解码，还是先解码再持久化标准消息 | thingsboard 是模式2吗 | 对参考实现的追问，当时不构成选项确认 |
| PA-Q2：首版先上行，还是同时开发下行编码；上行命令回执仍需正确识别与分流 | 先上行闭环，下行后续推进（推荐） | 首版上行解码、标准化及失败处置；下行编码后续推进 |
| PA-Q3：适配器由团队/受控合作方固定版本发布，还是客户任意上传运行 | 团队或受控合作方发布（推荐） | 受控交付，不授权本轮实际发布，也不免除验证和隔离 |

进一步说明先解码后持久化与原报文补算的取舍后，再问 PA-Q1：定制解析器出错后，是否需要用原始报文恢复和重算？例如温度换算写错，修复后重算此前数据。用户最终选择：

> 先从简：解码后持久化，暂不承诺原报文补算

这替代此前 Raw-first 推荐：首版不强制引入 Raw Kafka；只有已持久接受的标准消息进入可靠补处理承诺。未接受的原报文不保证可恢复，不能将解码成功或进入内存视为接受。上行范围、受控交付和上述选择的历史编号为 D13、D14、D15，引用编号不改变本地正文归属。

<a id="pa-raw-003"></a>
## PA-RAW-003：对本功能适用的跨域约束（用户，2026-10-17）

以下是真实答复及其在上行闭环的适用范围，并非将整个 Eventbus 迁移归到本功能。

| 原问题的业务例子 | 用户原答 | 上行闭环的适用范围与限制 |
| --- | --- | --- |
| 重要事实已发生但下游离线，恢复后是否仍要补处理，例如项目删除后的设备关联清理 | 补齐可靠补处理（推荐） | 已持久接受的 Canonical 应可恢复处理；接受前原报文、所有外部副作用恰好一次不在承诺内。历史编号 D6 |
| 设备已执行但回执丢失，是否因超时自动再执行 | 超时待核实，默认不自动重发（推荐） | 上行回执的故障/重试不能触发设备命令重发，保留结果未知。历史编号 D7 |
| 开发测试旧积压是否自动导入新 Kafka，避免昨天的测试操作再次执行 | 保留旧现场，不自动导入（推荐） | 新试点不自动导入旧消息，不暂停、清空或删除旧环境和数据。历史编号 D8 |
| 遥测积压时，新控制和重要关联处理是否必须独立推进 | 列为必须验收（推荐） | 本功能需验证回执入口与解码/提交资源隔离；完整控制及业务补处理仍需相邻模块共同验收，不承诺任意超载或整体依赖故障下可用。历史编号 D12 |

这些答复确认业务目标，未冻结具体延迟、容量、保留时间、分区数或部署方式，不授权本轮实现或环境操作。

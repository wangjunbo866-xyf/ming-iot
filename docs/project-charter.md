# Ming IoT AI 协作研发总纲

**我们要建立一套随产品持续演进、能被团队和 AI 共同使用的模块知识体系，并用真实开发验证它是否值得维护。** 仓库迁移、ming-specs、检查脚本和 LoopX 都服务于这个目标。

> 一次变更结束后，下一位开发者能否直接找到该模块当前有效、边界清晰、有人负责、可验证的完整知识，而不用重新拼接过去所有人的开发记录？

这是 `ming-iot-knowledge-pilot` 的当前方向入口，收敛已确认决定及截至 2026-10-18 的证据。阶段记录继续保存原时点结果；本稿不把方案、AI 演练或一次 CI 通过升级为团队采用、真人验收或生产验收。

## 1. 总目标与范围

以 [ming-iot](https://github.com/wangjunbo866-xyf/ming-iot) monorepo 为日常开发主体，让业务需求、决定、当前规格、代码和验证可以互相追溯。首先在已有真实模块上做到“找得到、说得清、改得动、验得了”，再随真实需求扩大覆盖。

方向收敛及[有界文档检查](runbook/document-checks.md)已通过 PR #6 合并：当前文档链接与可达性、来源索引一致性及显式替代关系。保留历史、旧仓和私有备份，不自动去重、归档或启用全库门禁；S4 首项真实目标已选定为 [Eventbus 从 NATS 迁往 Kafka](specs/platform/eventbus/README.md)，先准备隔离运行基线与细化需求。

已确认边界：

- **单仓组织。** 后端在 `backend/saas`、`backend/share`、`backend/things`，Core/Share/Things 已合并。先前父子仓、以独立知识父仓管理子仓的迁移设计已被替代。
- **模块边界独立于 Git 仓库。** 巡检先作为同仓独立业务模块；MQTT 网关保留跨平台复用、独立构建和部署的组件边界。网关及前端实际源码尚未提供，不将规划目录算作已迁入实现。
- **统一记录交付组合，允许服务独立部署。** 这是一项设计原则；现有迁移和无外部服务 CI 尚未证明完整平台交付组合可用。
- **旧材料保留且分层。** ming-iot-rd-docs、iot-doc、ai-native、superpowers 等历史/实验资料从 [legacy 导航](wiki/legacy/README.md) 按需查阅，迁入不自动生效。旧仓、私有备份、历史回执继续保留。ThingsBoard、AirMQ 仅供仓外学习参考。
- **方法逐步验证。** 参考《天猫 AI 项目研发协同实践》的“超级研发小分队”思路；吸收需求澄清、决定留存和角色交接，不引入完整 AI-DLC。OpenSpec 尚未采用；r-doc 正式采用不是迁移或后续工作的前提。
- **沿用同一 Goal。** 已完成注册位置迁移，保留原身份和历史。小黄反馈及依赖任务已废弃，不能作为待办恢复，也没有真人验收结果。

## 2. 设计原则

1. **分域、Feature、Patch，持续主规格。** 域划分长期职责，Feature 是完整能力与常用认领单元，Patch 是一次演进。服务与代码路径另行映射；同一 Feature 持续维护同一主规格。并行任务先核对条款、写范围和共享契约；目录分开不等于冲突已解决。
2. **职责内完整，一种知识一个权威正文。** 每份文档完整回答自己负责的问题：spec 说明适用版本的当前行为与验收，raw 保留本 Feature 的需求及真实澄清，Patch 说明本次变化及不变项。公共契约可精确引用，但本 Feature 必须说明本地适用方式与失败责任；日常理解不依赖拼接别的模块 raw 或历史 Patch。导航、Skill 和 LoopX 指向正文。
3. **同一次交付收敛实现与文档。** 需求原话与 AI 推导分开；人在关键业务取舍处确认。合并前形成对应候选的完整主规格，保留变更到主规格、主规格到变更的双向指针。
4. **事实有版本和验证范围。** 已确认、已实现、已合并、已发布、已部署分别表述。测试证明其实际覆盖范围；代码检查不能替代真实依赖运行和业务验收。
5. **公共约定一致，个人方法可选。** 团队统一模块边界、术语、责任、验收和必要输出；开发者可选择适合的方法与 Skill。根 AGENTS 和团队 Skill 保持工具中立，具体模型、任务调度及私有配置不作为公共开发前提。普通交接直接使用代码、当前文档和验证入口。
6. **成本与风险相称。** 规则不变的修复在原任务/PR 引用条款和回归；规则改变则用简短 Patch 同步主规格。记录量与验证深度分别按需选择。先观察遗漏、误报和返工，再决定工具增强。文档、Hook、测试或门禁的数量不是进度指标。
7. **渐进式披露。** 根 `AGENTS.md` 是人和 Agent 的统一起点，最多 120 行，只保留地图、任务路由、少量快捷命令及必要约定摘要和详情链接。先定位职责，再读取本任务需要的当前正文；历史、模板、检查细节和 LoopX 接入按触发条件展开。行数达标不能替代导航和阅读路径验证。
8. **用测试驱动适用实现，用独立审计确认交付。** 新增或改变可执行行为、修复缺陷时先用测试表达确认的预期并观察失败，再完成实现；重构、文档与探索按 [TDD 适用范围](runbook/team-development.md#tdd-scope)验证。成员自行选择具体 Skill。交付时独立核对需求、测试有效性、实现/集成及知识收敛，证据绑定实际候选；过程证据、最终质量和人的接受决定分别判断，详见[证据要求](runbook/team-development.md#tdd-evidence)与[独立审计](runbook/team-development.md#independent-audit)。

## 3. 知识放在哪里，谁来维护

| 入口 | 持续维护的内容 |
| --- | --- |
| 本总纲 | 总目标、共同开发纪律、设计原则、阶段路线、当前进度和完成标准；执行细则归团队约定 |
| [业务地图与 specs](specs/README.md) | 模块边界、负责人、当前完整规则、在途变更、对应实现和验证 |
| `docs/architecture/` | 系统关系、共享契约和设计约束；业务规则正文仍由对应模块维护 |
| `docs/runbook/` | 开发、接入、验证、运维和排障方法 |
| `docs/changelog/` | 计划、评审、证据和变化时间线；按记录日期阅读 |
| `docs/vendor/` / `docs/wiki/` | 外部来源、版本与许可；人工知识、讨论和历史资料 |
| [来源索引](index.yaml) | 正文位置、适用性和替代关系；不是另一份规格 |

一个已纳入试点的模块，入口至少能说明边界、责任、当前规则版本、实现和验证位置。具体文件与变更规则沿用[团队开发约定](runbook/team-development.md)，不用为每个模块建立全套空模板。

| 参与者 | 负责什么 | 判断边界 |
| --- | --- | --- |
| 人 | 业务取舍、模块和数据归属、长期负责人、风险接受与采用决定 | AI 的推测或临时认领不能代替人的决定 |
| AI | 查找上下文、列出歧义、起草和同步规格、实现、测试、分析实际差异 | 标明依据、未知项与未运行验证 |
| ming-runbook | 指引操作知识、共享导航与根入口维护，复用现有正文和本地检查 | 不接管业务规则，不自动增加门禁或每轮文档 |
| ming-specs | 指引认领、变更分类、规则与测试/证据对应、独立审计及主规格收敛 | 按任务路由到共同约定；具体实现 Skill 自选，业务规则仍在模块内 |
| 工具与 CI | 检查实际差异、路径范围、条款引用、双向指针、版本、lint 和测试 | 不能自动证明业务语义正确、批准真实或负责人已履职 |
| 独立评审者 | 核对实际变更、业务决定、当前规格和验证是否一致 | 绑定实际候选版本，保留未验证边界 |

当前通知、API 校验、Eventbus 以及新增协议适配域/上行 Feature 的长期负责人都未分配。这是明确缺口，不能用已认领的 AI 任务掩盖。

### 目标阅读路径与知识归属

| 层 / 文档 | 本文完整回答什么 | 什么时候继续往下读 |
| --- | --- | --- |
| 根 AGENTS.md | 项目方向在哪里、代码在哪里、当前任务应走哪个入口 | 按任务进入总纲、业务地图、开发/验证或受管任务入口 |

| Feature 的 spec.md | 目标、角色/输入输出、正常与异常规则、依赖在本功能的用法、版本状态和验收 | 追查原因时读本地 raw；准备调整时读相关活动 Patch；需要实现依据时读代码或精确共享契约 |
| 本地 raw / 单次 Patch | raw：原始诉求、真实澄清、确认来源；Patch：基线、旧/新行为、不变约束、依赖、验收及吸收去向 | 审计原时点或核验外部依据时再追溯来源；原始记录不因后续决定而覆盖 |

“完整”以文档声明的职责为边界。当前 spec 不需要复制全部聊天和公共协议；必须提供理解本功能所必需的上下文。任务记录可链接业务事实，不能成为代码合并后唯一保存新规则的地方。

### 下一步与防漂移方式

1. **日常任务沿当前入口执行。** 只读解释从当前 spec 回答；规则不变的小改在原任务引用条款、理由和验证；行为变化回本 Feature 的同一 Change，真实决定确认后在候选内收敛主规格与双向指针。并行 Patch 比较基线和重叠条款，明确协调结论后继续相关写入。
2. **以实际遗漏决定是否增强工具。** 本轮按明确授权补齐入口维护规则和显式本地行数检查，复用现有链接/索引检查与独立语义评审。若后续真实任务持续出现漏读、错误分类或主规格未收敛，再针对具体失败补提醒或检查；不预先增加全库门禁、认领数据库或全套新模板。
3. **回到真实业务验证连续演进。** PA 接续仍需首个真实协议的脱敏样本、应答/重发证据、profile/schema 及恢复预算；按当前设计授权推进，缺真实输入时保留限制。实现或 Kafka 后续切片仍须相应授权。过程继续观察知识完整性、反复补问和维护成本，不能让技术细节替代知识体系的总目标。

[接入演练记录](changelog/2026-10-18-cross-agent-onboarding.md#progressive-disclosure-trial)保留本轮四条路径的输入、读取与写回结论，以及未验证边界。此前另一 coding agent 的全新 clone 演练保留原时点事实；本轮使用同一候选中的无原聊天 AI 子任务，二者不能合称真人或全宿主验证。[通知运行基线](runbook/notification-baseline.md)继续保留；PA 运行验收从[上行 Feature](specs/protocol/uplink-normalization/README.md)读取，不在总纲复制决定表。旧环境、数据、旧仓和私有备份保持；服务端必需检查、CODEOWNERS、新 Hook、自动去重/归档和全库门禁均保持未新增。

## 6. 什么时候算完成

以下标准把原有治理目标落实为可检查的问题。正式采用判断由人结合真实任务作出；本稿不预设节省工时比例，也不把没有证据的项目标为通过。

| 标准 | 所需证据 | 当前判断 |
| --- | --- | --- |
| 能找到当前知识 | 根 AGENTS ≤120 行且按任务披露；从地图定位 Feature，仅凭当前 spec 可解释其关注的规则、异常、适用版本与验收；原因与决定可从本地来源追溯 | 本地入口已收敛；本轮四路径结果见接入演练记录。仅为有界 AI 验证，不代表全平台知识完整或团队采用 |
| 规则能持续演进 | 同一模块再次发生真实调整后，当前主规格仍完整；原始决定、变更差异、双向指针和历史可追溯 | 已有局部试跑与主规格收敛；S4 连续新需求待验证 |
| 责任真实且清楚 | 域、Feature、Patch 归属明确；人确认长期责任和本次实施/评审责任；并行条款重叠及共享影响有协调与集成依据 | 已登记域与 Feature 的长期负责人仍缺失 |
| 变更可以核验 | 实际 PR 差异覆盖受影响模块；有对应测试和独立语义复审；真实依赖需求选择对应验证 | 两个试点及 PR #5 有检查/评审证据；本轮新增真实通知 RPC 与保留数据重启基线，Eventbus P1 增加真实双缓存恢复与同组竞争证据，后续业务链及 V2–V9 验收仍待建立 |
| 开发纪律与审计可复验 | 适用任务有行为依据、真实红绿过程与最终验证；不适用/证据缺口如实处置；独立审计覆盖四个方面并闭环发现，绑定最终候选和必要组合验证 | 通知完整首行修复已保留同一测试的原始红绿过程；完整验证、独立审计与成本见[真实 TDD 试跑](changelog/2026-10-18-notification-tdd-pilot.md)，不将历史绿色补记为 TDD |
| 维护成本可接受 | 有真实日常任务成本及问题记录；团队据此决定保留、简化或放弃哪些步骤 | [通知小修复试跑](changelog/2026-10-18-notification-tdd-pilot.md)记录执行、文档和审计成本；单例不足以得出长期收益，采用判断待完成 |
| 历史与执行方向一致 | 当前入口明确，旧记录标明时点；同一 Goal 与证据持续可追溯；技术试点与工具工作能说明服务于哪项治理验收 | 方向与入口改造已有本地候选；本轮操作知识维护的交付状态由验证及 Goal 回执记录 |

**整个 Goal 的完成条件：** 约定的试点范围满足上述标准，遗留项明确处置，并由用户依据真实业务演进与成本证据作出采用、简化或停止的结论。无需先为全平台写完所有规格；覆盖范围扩大另行规划。阶段 Todo 关闭、总纲写完、迁移完成或 CI 绿色都不能单独关闭整个 Goal。

## 7. 总纲如何保持有效

目标、边界、阶段结论或完成标准发生变化时，负责该变更的人/AI 同步更新本稿，独立评审核对依据；业务取舍和正式采用仍由人确认。具体模块正文在模块内维护，本稿只引用它们。

- 总纲给方向、共同开发纪律与完成标准；[团队开发约定](runbook/team-development.md)给执行细则；[需求到交付流程](runbook/requirement-to-delivery.md)连接步骤与出口；[ming-specs](../.agents/skills/ming-specs/SKILL.md)与 [ming-runbook](../.agents/skills/ming-runbook/SKILL.md)分别给规格及操作知识的按需维护方法。具体实现 Skill 由成员选择。
- [维护提纲](wiki/team-development-outline.md)保留较详细的设计讨论；[迁移后盘点](changelog/2026-10-15-post-migration-governance-plan.md)和[合并后计划](changelog/2026-10-16-specs-merged-next-plan.md)保留时点分析。与本稿冲突的旧方向、进度和优先级按本稿阅读，原实验结果不改写。
- Goal 说明保持简短并指向本稿；历史 r-doc 简介不再承担当前总目标。登记标识为 `ming-iot-project-charter`，正文映射见 [来源索引](index.yaml)。
- 当前没有指定长期文档负责人，先由每次变更的责任人维护受影响正文；负责人缺口在实际责任安排时解决，不自动指定 AI 或已取消的接手人。

# Ming IoT 全项目单仓迁移

## 当前 Goal 与决定

2026-10-15 用户确认：继续使用 `ming-iot-knowledge-pilot`，将当前工作区的产品与知识项目迁入 [wangjunbo866-xyf/ming-iot](https://github.com/wangjunbo866-xyf/ming-iot)，收敛为一个 monorepo。以现有 ming-iot 为主体，统一代码、文档、工具和交付入口，不继续父子仓或多项目并列组织。本文件记录当前迁移主线和分阶段完成条件；原 r-doc 试点记录继续作为历史证据。

2026-10-15 M3 补充决定：**ThingsBoard 与 AirMQ 是学习参考仓，不迁入产品单仓。Core、Share、Things 已并入 ming-iot；以 backend/saas、backend/share、backend/things 及 M2 核对后的增量为准，不重复导入三套产品或恢复多仓布局。** M2 的既有备份与演练记录原样保留。

已确认的方向与本稿提出的具体目录安排需要区分：**单仓目标已经确认，以下目录和实施顺序是依据盘点形成的首版方案，可随实际导入结果修订。** M1 盘点、M2 备份恢复演练、M3 入口适配已完成。M4A 已完成本地候选的文件/可达历史核对、许可证缺口登记、单仓 CI 准备、全新 clone 完整验证和独立复审。后续声明与范围决定见最新进展；未授权远程交付，公开状态为 HOLD；M4B 远程交付与 M5 切换退役未执行。现有源仓、业务候选和私有备份保留，未推送 GitHub 或删除旧仓。

- 一个 Git 根、统一 PR 和 CI 入口；不使用 Git 子模块或 gitlink 维持旧的仓库边界。
- 服务可独立构建、部署、维护契约；组件复用不再等同于独立 Git 仓。MQTT 网关也遵循这一点。
- 巡检仍先按独立业务模块设计，未来有实现时进入同仓；本次不新增巡检业务。
- Insight、团队约定和必要工具在仓内维护。OpenSpec 仍为候选；r-doc 继续作为可替换的工具试验，**正式采用 r-doc 不再是迁移前提**。
- 小黄对昵称显示改动的真实验证仍待反馈，保留其未完成状态；它不阻塞资料盘点、备份和迁移演练，不得被写成已验收。

## 覆盖范围与保存原则

原盘点范围是当前工作区的全部九个 Git 根、六个额外工作树及根目录非 Git 内容；迁移范围已按 M3 用户决定排除两个学习参考仓，详见[盘点记录](../changelog/2026-10-15-monorepo-inventory.md)。全部项目必须有去向，不等于将所有缓存、凭据、旧二进制和内部历史直接发布。

1. 保留现有 ming-iot 的代码身份与独有演进；旧 Core/Share/Things 按已固定来源基线核对增量，不能整体覆盖。
2. 对所有源仓保存 refs/HEAD、可恢复 Git 历史；未提交、未跟踪以及被忽略的有价值实验源码另做快照。Git bundle 不覆盖这些本地内容。M2 已生成备份并实际恢复；完整回执、哈希与本地保留范围见 M2 附录。备份不等于异地灾备或公开导入。
3. 每个材料记录原仓、原路径、源提交或快照摘要、目标路径及处理结论。目录迁移、源码修复和行为变化分开评审。
4. M1 盘点时目标为公开空仓。发布前检查拟公开的完整可达历史和最终树；源历史先保存在私有备份中，不直接将全部旧 refs 推入公开仓。保留项目既有许可证、版权与来源声明；第三方材料的发布范围单列核对，不以整个根仓的一份许可证覆盖全部来源。
5. 旧仓先作为只读、可恢复来源保留。删除不是本阶段动作；退役需满足下文 M5 条件，不能用“已复制”代替。

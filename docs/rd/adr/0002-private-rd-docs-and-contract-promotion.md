# 保持研发文档独立，并向代码仓晋升稳定契约

- 状态：已接受
- 日期：2026-09-03

## 决策

`ming-iot-rd-docs` 继续作为独立私有仓库，不整体合并回 `ming-iot`。规格、计划、完整 Review、Evidence 摘要和历史材料保留在研发文档仓；开发者在构建、修改或评审代码时必须知道的稳定规则，通过 Document Promotion 提炼到 `ming-iot`。

晋升目标包括 `AGENTS.md`、根 `Makefile`、工具 README、部署与接口文档、机器可验证的契约测试。不得把整份研发过程文档复制到代码仓形成双重权威。

## 原因

研发材料包含被推翻的方案、决策过程和较重的 Review/Evidence，不适合作为每位代码贡献者的默认上下文；但若已经生效的构建、验证和维护规则仍只留在私有文档仓，单独克隆 `ming-iot` 的开发者将无法可靠维护当前系统。提炼稳定契约可以同时保留研发历史和代码仓对当前系统的自解释能力。

这种自解释能力不包括凭空恢复下一项需求。实施新的 Delivery Issue 时，开发者或 Agent 仍必须访问 `ming-iot-rd-docs` 中与该 Issue 对应的 Delivery Packet，包括适用的 RFC、规格和实施计划。

## 后果

- `ming-iot` 必须仅凭自身受版本控制的内容提供常用验证入口。
- 新需求的实现者必须同时取得产品仓和对应 Delivery Packet；稳定项目契约不能代替 RFC、规格或计划。
- 私有规格中的稳定约束一旦晋升，应在文档登记中指向代码仓的权威入口，并避免继续维护两份同义正文。
- 原始机器 Evidence 优先保存在 CI Artifact 或 LoopX 私有 Evidence 中，不因“晋升”而进入产品 Git。

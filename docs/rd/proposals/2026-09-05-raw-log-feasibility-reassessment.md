## 1. 第一轮候选建议（历史分析）

建议采用“保留可靠双流基础、按客户价值分期建设”的路线：

1. 继续以 `Raw → ProtocolApplication → Canonical` 为云端基线，暂不把 Raw 从 72h 降为 12～24h。
2. 将“可靠接收与故障恢复”“保留原始输入用于排障”“修正协议后历史重算”分开承诺、分开核算。双流不意味着一开始就做完整历史重算平台。
3. 首期保留原始输入身份、解释版本与隔离恢复边界；先验证运行链路和有限范围恢复，不先建设通用回放门户、自动迁移编排、全历史一键纠错。
4. 30/90 天对象归档按客户合同启用。若承诺可恢复归档，必须是有完整性验证的可靠归档，不能用 Adapter 的异步双写代替。

理由不是“越可靠越好”，而是旧提案高估了部分磁盘成本、低估了归档与恢复的一致性成本。当前没有首批客户流量、故障恢复时间与预算实测，直接删减可靠性契约的依据不足。另一方面，也没有证据证明现阶段值得投入完整的企业级历史重算产品。

## 3. 先纠正旧提案中影响决策的判断

| 原判断或隐含假设 | 本轮更正 |
| --- | --- |
| `200 MB/s × 60s ≈ 12 TB` | 应为约 **12 GB**，差 1000 倍；Raw 三副本约 36 GB，尚未包含其它数据流与开销 |
| 12h 存储量等于日均存储的一半 | 对“每天集中运行 12h”的情景不成立：最满的滚动 12h 可以覆盖全天全部报文，与滚动 24h 的最大报文量相同 |
| Adapter 异步写 Kafka 与对象存储即可完整取证 | 两个目标不能天然原子提交；进程崩溃、超时或重试可能造成漏归档、重复或结果不明 |
| 保存 payload，未来写脚本即可重放 | 原版本恢复还依赖协议、模型、所有权与处理模式等版本和生效边界；没有这些，只能尝试重新解释，不能承诺复现历史结果 |
| 其它平台不做同样的双流，因此双流多余 | 产品有不同的消息接纳和解码边界；公开架构图不足以证明全部协议是否保留原帧 |
| 方案 C 一旦选择就无法回头 | 将来可以新增 Raw 链路；不可补救的是此前没有保存的原始输入，而非软件架构永久不可修改 |

Raw 的定义也要收紧：这里保存的是平台接纳的应用层原始输入及上下文，不是网络抓包，不承诺保留 TLS/MQTT 全部线上字节，也不承诺覆盖 Broker 拒绝的消息。

## 4. 行业惯例能支持什么

ThingsBoard 的官方架构描述 Transport 转换后的统一消息进入队列；Azure 支持 IoT Hub 消息路由到存储；AWS IoT 规则区分 S3、Kinesis 与 Firehose 动作；EMQX 提供 Kafka/S3 集成，并明确缓冲、超时和重试条件。可以据此认为“接入消息流与持久化/导出分层”有成熟产品实践，但不能推导出所有产品都提供完整原帧审计、历史版本复原或永不丢失。[ThingsBoard 架构](https://thingsboard.io/docs/reference/architecture/)、[Azure 端点](https://learn.microsoft.com/en-us/azure/iot-hub/iot-hub-devguide-endpoints)、[AWS 规则动作](https://docs.aws.amazon.com/iot/latest/developerguide/iot-rule-actions.html)、[EMQX Kafka 集成](https://docs.emqx.com/en/emqx/latest/data-integration/data-bridge-kafka.html)。

对本项目的推论：多厂家私有协议、集中协议解码以及后续协议纠错，使“解码前保留输入”比标准 JSON 遥测产品更有价值。但这仍不证明所有客户都愿意为长期重算付费。若未来产品定位变成标准化载荷或边缘已经完成可信解码，应重新评估只保留 Canonical 的轻量部署，而不是把同一部署成本强加给所有客户。

## 5. 容量与成本：按正确口径重算

### 5.1 用已有规模假设做敏感性分析

采用主架构的情景：每天工作 12h，每 5min 一次上报，每次约 500 个点。另假设每份**完整 Raw 报文**为 4,000 B，仅用于演算，未实测；不再额外乘 500。使用十进制 GB/TB，先不计压缩与元数据，Raw RF=3。

`每设备每天报文数 = 12 × 60 / 5 = 144`

`Raw 日增量 = 设备数 × 144 × 报文字节数`

| 逻辑设备数 | Raw 单副本日增量 | Raw 24h 三副本 | Raw 72h 三副本 | 72h 降至 24h 的数据容量差 |
| --- | ---: | ---: | ---: | ---: |
| 1 万 | 5.76 GB | 17.28 GB | 51.84 GB | 34.56 GB |
| 10 万 | 57.6 GB | 172.8 GB | 518.4 GB | 345.6 GB |
| 100 万 | 576 GB | 1.728 TB | 5.184 TB | 3.456 TB |

这是 Raw 数据量，不是整个 Kafka 集群磁盘配置。实际应加 key/headers、segment/index、压缩效果、分区倾斜、重分配与故障余量；另算 Canonical 和其他 topics。3 副本也不是“全系统只需 3 倍磁盘”的完整容量模型。

特别注意：在每天同一 12h 活跃的情景，滚动 12h 与 24h 的最大保留量都可能为 576 GB 单副本。只有在同样日总量均匀摊到 24h 的另一情景下，12h 才约为 288 GB。保留期估算应使用实际流量曲线在窗口内的最大积分，不能只用全天平均速率。

### 5.2 峰值不等于新增保留量

主架构的 100 万设备情景，24h 平均约 1,667 report/s、活跃期约 3,333 report/s、集中 60s 上报约 16,667 report/s，二倍峰值测试约 33,334 report/s。假设仍为 4,000 B，最后一档约为 133 MB/s，而非已测得的吞吐能力。

入口报文无论是否被消费，都会在保留窗口内占用 Kafka 存储。不要把已经计入窗口的同一批峰值数据再次全额叠加为“消费积压磁盘”。消费积压影响延迟与保留期风险；另有超出正常日总量的补传，才按新增输入核算。

在简化恒定速率模型中，入口速率为 `λ`、消费者处理能力为 `μ`、停机时间为 `D`：

`积压量 = λ × D；追赶时间 = λ × D / (μ - λ)，前提 μ > λ。`

因此保留期应覆盖发现、修复、追赶与安全余量。不能只说“通常一天内能修好”，更不能在 `μ ≤ λ` 时靠延长保留期解决永远追不上的问题。Kafka 的时间和大小上限需要一起检查，大小配置作用于分区；设置 72h 并不抵消过小的 `retention.bytes`。[Kafka Topic Configs](https://kafka.apache.org/43/configuration/topic-configs/)。

### 5.3 长期归档不只是便宜的存储单价

100 万设备的上述情景，在稳定保留窗口填满后，30/90 天归档分别约 **17.28/51.84 TB** 原始数据，压缩前。托管对象存储报价通常按逻辑存储计费，不能再机械乘 Kafka RF=3；自建对象存储则另算其纠删码或复制开销。

若一报文一对象，每月约 `1.44 亿 × 30 = 43.2 亿` 次写入。若理想地按 128 MB 批量打包，每月约 13.5 万个数据对象；实际还受分区、时间刷新、小批次、manifest、重试与多段上传影响。由此可见，归档格式和请求数量可能比单 GB 价格更值得先优化。

预算至少分开列：Broker 固定 CPU/内存与运维、Raw 与 Canonical 的实际磁盘、复制/消费网络、归档容量与请求、恢复读取与跨区流量、回放计算，以及版本制品长期保留。对象存储官方也区分存储、请求、取回和数据传输费用；本轮不把某地区美元报价当成公司的人民币采购成本。[Amazon S3 Pricing](https://aws.amazon.com/s3/pricing/)。

可用于报价后的增量比较：`72h→24h 月磁盘收益 ≈ 3.456 TB × 实测压缩/封装修正系数 × 每 TB·月磁盘成本`（100 万设备情景）。还需确认缩小数据量能否减少实际采购容量或节点，否则不一定形成现金节省；若为短保留期新增归档系统，要减去它的建设和运行成本。

## 6. 三种能力不要混为一谈

| 能力 | 真实价值 | 必须交代的边界 |
| --- | --- | --- |
| 可靠接管与解耦 | 解码服务故障后继续处理已接纳数据，削峰和独立扩缩容 | 当前 EMQX PUBACK 不等于 Kafka Raw commit；边缘离线补传是另一契约 |
| 原始输入取证 | 解释“设备到底发了什么、平台用了哪个版本” | 按租户授权、脱敏/加密与保留期；部分采样只能用于抽样诊断，不能宣传完整取证 |
| 历史纠错重算 | 协议或模型修复后，对仍可用的历史输入重建结果 | 输入与制品都要保留，指定版本、限定范围、验证输出；不能重新触发设备命令或生产场景动作 |

最低可靠链路与可选归档关系：

```text
Adapter → Kafka Raw → ProtocolApplication → Kafka Canonical → 业务消费者
              └── 可选：独立归档消费者 → 分块对象＋恢复所需元数据
```

Raw 与 Canonical 可以是同一 Kafka 集群中的不同 topics，不意味着天然需要两套集群；是否拆集群取决于故障域和负载隔离需求。

Kafka 内部可将消费 offset 和输出记录纳入事务，下游仍需正确使用 `read_committed`；写外部系统则需要额外协调，不能把 Kafka 事务直接延伸到对象存储。[Kafka Design：Message Delivery Semantics](https://kafka.apache.org/43/design/design/)。

因此若建设可靠归档，推荐从已持久化的 Raw 消费，使用可重试、可识别重复的对象命名，先完成对象与校验/覆盖记录持久化，再推进归档进度。崩溃窗口通过幂等重试收敛，归档积压必须在 Raw 过期前发现和处理。offset 范围覆盖应按 Kafka 读取语义核对，而非凭“文件数量正常”认定无缺口。还要保留 source rawRef、topic 身份、时间、key/headers、payload 和解释版本；随机选范围做实际恢复验证。

Kafka 原生 Tiered Storage 是另一条路线：它让旧日志段进入远端存储，不等于应用自己导出的归档文件。官方发行版没有开箱即用的 `RemoteStorageManager` 实现，不能把它当成免费打开一个开关即可完成的 V1 能力；若之后采购托管服务，再按兼容性和总成本比较。[Kafka Tiered Storage](https://kafka.apache.org/43/operations/tiered-storage/)。

## 7. 候选方案重新比较

| 路线 | 获得什么 | 主要成本或牺牲 | 当前判断 |
| --- | --- | --- | --- |
| A：立即建设完整双流＋长期归档＋通用重算平台 | 最大的纠错、审计与运维自动化覆盖 | 一致性、版本保留、任务编排和恢复验证投入大；付费需求未证明 | 暂不作为首期投入范围 |
| B：Raw 缩至 12～24h＋取证归档 | 可能减少 Broker 磁盘，保留较长原始输入 | 已改变恢复承诺；可靠归档仍复杂；仅有原帧不等于能够历史复原 | 不再直接推荐，先用恢复 SLO 与真实账单论证 |
| C：解码前不设持久 Raw，仅保留 Canonical | 最少的一层消息流与协议上下文保留负担 | 未成功解码的输入可能不可追回；故障边界移到接入侧；失去过往原始证据 | 标准协议/边缘解码的轻量产品可考虑，但偏离当前工业多协议目标 |
| D：保留 72h 可靠双流，恢复能力由小到大，长期归档按合同 | 保住当前可靠性基础，控制通用平台的先期投入 | 仍要做必要的一致性与故障验证，不是仅换个名称就省工程量 | 本轮推荐 |

这里的 D 是投入顺序，不是偷偷删掉验收条款：

- 当前主架构要求 48h 前样本按原版本恢复得到同一 Canonical hash，以及按目标版本重处理。可以先用受控维护任务验证，不必先有通用 UI；如果决定连这些验证也延期，必须明确修订阶段范围，不能宣称原基线已通过。
- 30/90 天归档是按合同开启；没有开启时不承诺其恢复能力。主架构若有未区分档位的归档验收条款，后续激活规格必须明确适用档位，不能直接跳过测试后宣称全量符合。
- `RawOffsetBarrier`、source rawRef、版本制品以及回放输出隔离，服务于确定性和防副作用，不应为了暂缓 UI 而一并删除。
- 本轮不修改 `iot-doc`、SDK、部署配置、契约测试，也不假设完整解码/回放运行时已实现。

## 8. 功能卖点与投资顺序

不要向客户销售“我们有两个 Kafka topic”，而要验证客户是否需要以下结果：

| 客户场景 | 可验证卖点 | 值得建设的前提 |
| --- | --- | --- |
| 多厂家协议接入、现场数据争议 | 从业务记录追溯到原始输入和解释版本，缩短联调排障时间 | 能演示一条真实故障的定位过程，并比较人工排障耗时 |
| 解码器发布后发现错误 | 对承诺窗口内输入隔离重算，验证后修复数据 | 输入/版本覆盖且有恢复演练；明确不自动执行历史设备动作 |
| 新旧协议或模型升级 | 用历史样本对比差异，降低发布风险 | 样本代表性、版本可复现；不需要先做无限规模全量回放 |
| 合同要求长期留证与纠错 | 指定期限内可授权查询、校验和恢复原始输入 | 客户愿意承担存储、隐私治理和恢复成本；先验证完整性再承诺 |

应使用“减少多少联调/故障工时、纠错窗口多长、恢复多久完成、每客户增加多少成本”衡量价值。官方有同类功能不等于客户愿意付费；不能据此编造收益、事故频率或开发人月。

建议下一阶段只做一轮有界的容量与恢复验证，作为是否进入实施规格的证据，而不是立即建设完整 Raw Log 平台。最少补齐四项事实：

1. 首批部署的设备量、上报节奏、完整 Raw/Canonical 大小分布与实测压缩率；不用最终百万设备目标替代首批实际规模。
2. 故障发现/修复时长、峰值补传与消费者追赶能力，验证 72h 是否合理、24h 是否真的足够。
3. 从 Kafka 成功接纳后开始的故障恢复，以及有限范围原版本/目标版本恢复；明确 Broker 到 Adapter 的未覆盖边界。
4. 使用公司可采购资源估算总成本，并用真实客户场景判断长期归档与历史纠错是否值得付费。

通过这些事实，再决定“继续 72h 基线”“正式提出短保留期部署档位”或“为轻量产品另设无 Raw 架构”。本段保留 Proposal 形成时的研究判断；后续 Owner 讨论形成的候选决策已提炼到 §9 与关联 RFC，是否接受以 RFC 状态为准。

## 9. 决策提炼结果

讨论最终形成以下 RFC 候选，而不是直接进入实现：

1. 长期产品语义冻结为 Diagnostic、Reliable、Traceable 三个部署档位，且三个档位的 Canonical 都写入 Kafka；
2. 默认生产档位为 Reliable，Raw 和 Canonical 默认位于同一个 Data Kafka 集群的不同 topics；
3. 当前只允许激活 Reliable V1；Diagnostic 与 Traceable 不实现、不配置、不对外宣称可用；
4. Reliable 的可靠接管边界从 Raw 成功提交 Kafka 开始，ProtocolApplication 以 Kafka 事务原子提交输出与 Raw offset；
